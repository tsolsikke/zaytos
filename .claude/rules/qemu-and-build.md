## QEMU の「沈黙の失敗」を必ず可視化する
トリプルフォルト等の致命的例外は、デフォルト設定の QEMU では
黙って無限リブートし、外部から観測不能になる。これを防ぐため、
QEMU 実行コマンド（`xtask` 側）には常に以下を含めること。

```
-no-reboot -no-shutdown -d int,cpu_reset
```

- `-no-reboot -no-shutdown`: 異常時に再起動せず停止させる
- `-d int,cpu_reset`: 発生した割り込み/例外と CPU リセット要因をログに残す

「ハングした」と判断する前に、まずこのログで例外の有無を確認すること。

**例外は1つある。運用者が手で触るための起動（`cargo xtask run --manual`）だけは
`-d cpu_reset` に絞る。** **`-no-reboot -no-shutdown` は落とさない。**

理由は実測である。**`-d int` は割り込み1件ごとに CPU の全状態を書く**（1件約 1.3KiB）。
**シェルは `read(0)` を回して待つ**ので、**`int 0x80` が毎秒約 39,000 件出る**——
**既定構成の 120 秒の起動で、記録は 5.6GiB になった**（実測。事象 4,657,255 件のうち
`v=80` が 99.7%）。**手で触る起動は上限を外すので、`int` を残したままだと
1分あたり約 2.9GiB でディスクが埋まる。**

**失うのは割り込みの列だけである。** トリプルフォルトの再起動要因（`cpu_reset`）と
シリアルは残る。**原因を追う段になったら `--manual` を外して起こし直すこと。**
**自動検査の経路は1つも変えていない。**

**この例外の前提は、シェルが `read(0)` を回して待っていることである。**
**待つ形（眠って起こされる形）が入れば `int 0x80` の 99.7% が消えるので、前提は変わる。**
**そのときは、この例外を残すかを測り直して決めること**
（`docs/deferred-decisions.md` に行がある）。

## ビルド環境の再現性

- `rust-toolchain.toml` で Rust バージョン（チャンネル）を固定する。
- `Cargo.lock` はリポジトリにコミットする。
- 「バージョン差による謎の失敗」（EDK2 で経験した事象）を構造的に排除するのが目的。
- **ファームウェアと対象トリプルは `docs/architecture.md` の「技術スタック」にある。**
  OVMF の導入方法と EDK2 に触れないことは、そちらが本体である。
