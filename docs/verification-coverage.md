# 主張と検査の対応

ZaytOSの文書は「常にこうである」「必ずこうする」と書いている性質をいくつも持つ。
このファイルは、その主張ごとに対応する検査があるかどうかを並べたものである。

作った動機は、`cargo fmt`と`cargo clippy`が2日間ずっと未達だったことに気づかなかった経験である。
原因は個々の見落としではなく、維持していることを確認する手順がどこにも無かったことだった。
主張だけがあって検査が無い状態は、時間が経つほど気づきにくくなる。

`deferred-decisions.md`とは役割が違う。
あちらは「いつか判断する項目」、こちらは「主張と検査の対応表」である。

状態の区分は次の3つ。

- 検査あり: 機械的な検査があり、破れば落ちる
- 測定のみ: 値は測っているが、違反しても止まらない
- 検査なし: 対応する検査が無い

---

**節番号は安定していない。** 節は増減するので、他の文書やコミットメッセージから番号で参照しない（見出しの文言で参照する）。実際にS0-aで1節を移したときに後続の番号を詰めた。詰めた時点で古い番号への参照は無かったことを履歴も含めて確認しているが、参照があれば静かに別の節を指す状態になっていた。

## 1. 検査なし

現時点で違反は確認していないが、破っても誰も気づかない。

### 1.1 割り込みハンドラは何も出力しない

出典: ADR-0018 §5、`architecture.md` §6.8

観測はカウンタ越しに行い、ハートビート1行へ集約する設計である。
ハンドラの中から`Logger`を呼んでいないことは検査していない。

足すなら、ハンドラの関数本体に`logger`や`write!`が現れないことを見る形になる。
ハンドラの範囲を機械的に決めにくいのが難点で、現状は費用に見合わないと判断している。
M5-dでハンドラからスケジューラを呼ぶようになると、ハンドラ内で呼べるものの範囲が広がるため、その時点で再検討する。

### 1.2 画面とシリアルの両方へ出す場合はシリアルを先に書く

出典: ADR-0013、ADR-0017、`architecture.md` §6.7

`log_both`の実装がその順序になっているだけで、呼び出し側が別の順序で書くことを妨げるものは無い。
画面出力が壊れたときにシリアルだけは残る、という保証がこの順序に依存している。

足すなら、`log_both`以外から`Console`へ直接書く経路が無いことを見る形になる。

### 1.3 ページテーブルでNXを立てない

出典: `architecture.md` §6.6、`kernel/src/paging/table.rs`

EFER.NXEを有効にしていない段階でNXを立てると、予約ビット違反のページフォルトになる。
稼働中テーブルの読み戻しはPCDと恒等性は照合するが、NXは見ていない。

同じ節の「PSビットはPDレベルのみ」は、`translate()`がPDPTレベルのPS=1を`UnsupportedGiantPage`として弾くため、実質的に検査されている。

足すのは容易で、読み戻しの照合にビット63を加えるだけである。
M5-eで権限の細分化に入るときに、NXの扱いを決めるのとあわせて足すのが自然である。

### 1.4 ターゲットの既定値への依存

出典: `architecture.md` §5、§5.1

kernelは`x86_64-unknown-none`の`disable-redzone`と`+soft-float`に依存している。
red zoneが有効に戻ると、割り込みが入った瞬間に呼び出し元のローカル変数が壊れる。
§5.1は「rustflagsやターゲットを変更した際は、この確認をやり直すこと」と書いているが、やり直しを促す仕組みは無い。

stableでは`--print target-spec-json`が使えないため、確認は生成コードを読む形になり、機械化しにくい。
`.cargo/config.toml`と`rust-toolchain.toml`が変更されたときに気づける形にするのが現実的である。

## 2. 検査あり

### 2.1 ビルド・テスト・静的解析

`cargo xtask check`は次を実行する。

| 項目 | 内容 |
|---|---|
| build | bootloader（`x86_64-unknown-uefi`）/ kernel（`x86_64-unknown-none`）/ common / xtask |
| test | `cargo test --workspace` |
| clippy | 上記4構成すべてに`-D warnings` |
| fmt | `cargo fmt --all -- --check` |
| unsafe | `unsafe`ブロックの直前のコメント塊に`SAFETY`があること（追跡済みと未追跡の両方が対象） |
| cli/sti | 直接の`cli`/`sti`が許可リストの`(file, item)`に載っていること |
| 境界の可視性 | 内部を隠す約束のモジュール配下の`mod`宣言と`use`にprivate以外の可視性修飾が無いこと（対象の一覧は検査が毎回印字する） |
| 既定feature | 既定のkernelビルドにサボタージュfeatureが混ざっていないこと |
| トランポリン | ビルド済みkernel.elfの入口24バイトが期待リテラルと一致すること |
| コミット | コミット件名に和文と英数字の間の半角空白が無いこと（規約を適用し始めた日時以降が対象） |

`cargo xtask check --full`は、これにQEMUを起動する回帰チェック（exception / critical / paging / stack / task / ring3 / syscall / interruptの各表と、keyboard・panic）と、higher-halfの破壊確認（`highhalf-*`と`highhalf-trampoline-absolute-ref`の静的検査）を加える。
種類の一覧は`xtask/src/main.rs`の各テスト表を正とし、項目数は下の項目会計に従う。

`--full`は、xtaskが「起動しなかった」と判定した項目に限り、自動で1回だけ再試行する。
テストの失敗（実装の問題）では再試行しない。落ちるものは落ちたまま報告する。
1回に限るのは、回数を増やすと「何度も失敗したが最後に通った」状態を成功として扱うことになるためである。
再試行したことは都度出力し、最後に件数と項目名をまとめて出す。

**基準線は0件である。1件でも出たら異常の兆候として扱う。**
この再試行は当初、OVMFがまれに起動に失敗する既知の事象への対処として入れた。
ところがその事象は環境要因ではなく、varstoreを使い回していた自作の不具合だった（`troubleshooting.md` 2026-07-22）。
直した後は0件が続いている。
したがって現在の位置づけは「頻繁に起きることへの対処」ではなく「起きないはずのことが起きたときの保険」である。

### かつての確率的フレークと、サボタージュを arm 窓へ絞った理由

`task-test preempt-in-critical`はかつて約10%で落ちた。**原因は当初の想定（タイマプリエンプトが cli 除去窓に当たるか）ではなかった。** 実測で判明した真因と解消を記録する。将来「この分岐は複雑だから消そう」とサボタージュを大域へ戻すと再発するため、なぜ今の形かを残す（`const fn`を失った理由やマーカー文字列を変えた理由と同じ性質の記録）。

**真因。** このテストのサボタージュは2つある（`preempt-in-critical-break`＝`InterruptGuard`の cli 省略、`task-preempt-in-critical`＝`on_timer_tick`の防御スキップ除去）。当初は**どちらも大域的**で、プリエンプティブデモの開始（`setup_preemptive_tasks`の`InterruptGuard`区間や`yield`付近）まで perturb した。そのため検査対象（二重取得を狙う保持窓）へ到達する前に、ワーカーが1度も走らず`switches=0, iterations=0`で「the timer did not preempt fairly; halting」と落ちた。観測される失敗署名は「double acquisition detected が出ず halt」だが、実体はこの startup レースである。既定ビルドは20/20健全で、サボタージュ有効時だけ約10%落ちたことから、カーネル本体ではなくサボタージュが原因と実測で確定した。1回目に当てた修正（保持窓を tick 条件化）は無変更と同率で no-op だった（真因が保持窓ではなかったため）。

**解消（案E）。** サボタージュを大域から**arm 窓へ絞った**。`common::critical`に`SABOTAGE_ARMED`を置き、`InterruptGuard`は arm されている間だけ cli を省く。`on_timer_tick`の防御スキップも arm 中だけ bypass する。ワーカーは`preemptive_loop_top`で`DEMO_LOCK`を握る直前に arm し（RAII、Drop で disarm）、その保持窓だけを壊す。デモ開始は arm の外なので正常な cli の下で走り、startup レースが起きない。**production は不変**（arm 判定はすべて feature 下で、既定ビルドでは cli も防御スキップも常時有効）。修正後、単体30回連続 PASS（全て二重取得経由、`made no progress`は0回）・`--full`の全通過・既定20回で`made no progress`=0 を確認した。

**フレーク判断の手順（この種の確率的取りこぼしが再発したとき用に残す）。** 失敗署名を確認し、`exception: vector=`・cpu_reset の増加・別マーカーの欠落なら回帰として調査する。取りこぼし署名（`made no progress`・`switches=0`等）なら、単体で数回再実行し、`cargo xtask check --full`の全通過を確認する。同じ署名で繰り返すなら確率が高すぎるので、確率性そのものを潰すまで先へ進めない。

### 意図的に壊す feature の一覧

「検査が実際に働くこと」を確かめるため、意図的に壊した経路をfeatureとしてコードに残している。
いずれも既定ビルドには入らない。

| `interrupt-test-enable-only` | 全IRQをマスクしたまま`sti`する | 何も届かないこと |
| `interrupt-test-irq-path` | `int 0x40`を発行する | IRQ経路がGPRを復元すること |
| `misalign-test` | IRQスタブのスタック16バイト調整を外す | 境界検証が発火すること |
| `interrupt-test-timer` | タイマを動かす | ティックが増え続けること |

| `gfx-test-pattern` | コンソールを起動せず描画テストパターンを描く | 描画の基盤 |

| `highhalf-bad-high-slot` | 静的初期テーブルの `PDPT_high` のエントリを `510`→`509` へずらす | 高位 `_start` への jmp 先が未マップで起動が進まないこと。判定は `no-identity-in-boot-pt` と同一署名 |
| `highhalf-no-kernel-high-in-live-table` | M2-d/A-1 の `map_kernel_high_half` 呼び出しを外す（本流テーブルにカーネル高位マッピングを張らない） | M2-d の CR3 切替後に高位で #PF して停止すること。判定=`higher-half: arrived at high VA` present / `paging: CR3 switch verified` absent + heartbeat=0 |

`cargo xtask check`は、`kernel/Cargo.toml`の`default`から推移的に辿って、これらのいずれにも行き着かないことを検査する。

int 0x80システムコールの検証（M5-f-1-2）について、2点を明記する。

- **RCX/R11はクロバー扱いで、保存に依存する検査を書かない。** ADR-0020のとおり、`int 0x80`の間はRCX/R11が実際には保存されるが、`syscall`/`sysret`へ移る段でこれらは命令が破壊する。ここでRCX/R11の保存を検査に固定すると、移行時の破壊が検査に守られて表面化しなくなる。probe発行ルーチンはRCXへ番兵を入れるが、これは`syscall-test-arg4-rcx`が第4引数をRCXから誤読したときに決定的な食い違いを起こすためで、RCX/R11が保存されることを確かめる検査ではない。
- **RSP0スタックでの走行の破壊featureは新設せず、`ring3-test-drop-rsp0`を指す（判断B）。** syscall経路のRSP0据え付けは`ring3::enter`の`set_rsp0`を再利用しているため、これを落とす破壊は`ring3-test-drop-rsp0`と同一で、重複featureを作らない。一方で**検証項目は新規に持つ**: syscall経路では「`syscall_entry`のRSP（`rsp_at_call`）が遠征スタック範囲内にある」ことを読み戻す。`ring3-test-drop-rsp0`が見るのは#GP例外ハンドラの着地で、syscallが見るのは`syscall_entry`の着地であり、破壊featureは共通でも検証対象が違う。

ユーザーポインタ検証（M5-f-2-1、`user_range_accessible`）について、3点を明記する。

- **単独破壊で隔離できるのはU=1判定と全ページ走査だけである。** 検証器は (a)長さのオーバーフロー、(b)ユーザー範囲、(c-present)各ページのpresent、(c-U=1)各階層のU=1、を見る。このうち (a)(b)(c-present) は互いに、そして (c-U=1) に**冗長**（多層防御）で、1つだけ外しても別のチェックが後追いで拒否するため、単独破壊ではhaltしない。具体的には、範囲下限外（カーネルポインタ、PML4[0]）はpresentだがU=0なので範囲判定を外してもU判定が弾く。未マップはゼロ埋め（U=0）なのでpresent判定を外してもU判定が弾く。長さオーバーフローはbufがユーザー範囲（< 2^40）にあるため、wrap後の末尾が範囲外になり範囲判定が、あるいは上端先が未マップなのでpresent判定が後追いで弾く。したがって破壊featureは隔離できる `skip-us`（U=1判定）・`skip-laststep`（全ページ走査）・`skip-all`（検証器全体）の3種とする。範囲/present/overflowの各チェックは、defaultのbatteryでfirst-lineの拒否者として実運用・実証される（batteryの無効1〜5が拒否されること自体が、これらのチェックの正しさを担保する）が、単独破壊testとしては設けない。
- **この隔離不能は現在のアドレス空間レイアウトに依存する。** 「U=1はユーザーサブツリー`PML4[USER_PML4_INDEX]`の外に一切存在しない」（`audit_user_supervisor`が`kernel_violations==0`を毎起動でアサート）ため、範囲外・未マップが必ずU=0になり、U判定が範囲判定・present判定を後追いで肩代わりする。**higher-half B後にレイアウトが変わり（カーネルを上位半分へ、ユーザーを低位へ拡張）「カーネル=必ずU=0」の前提が変われば、この冗長性は再評価が要る。** `syscall::USER_VIRT_MIN`/`USER_VIRT_MAX`もPML4[1]前提なので同時に見直す。M5-e-2で`drop-rsp0`の配置依存を記録したのと同じ、検査の成立が構造条件に依存することの記録である。
- **`user_range_accessible`はlen==0を常に受理する契約である。** 0バイトのアクセスはbufを問わず安全であり、この短絡は検証器の内部に置く（呼び出し側で短絡しない）ので、この検証器を共有する全syscallが同じ契約を継承する。batteryはlen=0を有効bufと無効bufの両方でテストする。

`walk_user_accessible`が中間階層U=0（葉U=1でも中間U=0なら`translate`の葉Uでは見逃す穴）を弾くことは、一度きりの確認（中間テーブルのUビットを直接落として`walk`が`SupervisorOnly`で弾く一方`translate`の葉Uでは通してしまうことの対比）で実証した。侵襲的setupを恒久コードに残さないため恒久featureにはせず、確認後に戻している。

`copy_from_user`と検証済みトークン`UserSlice`（M5-f-2-2）について、3点を明記する。

- **型で保証される範囲と、規律で守る範囲の境界。** `UserSlice`はフィールドprivateで公開コンストラクタを持たず、構築できるのは検証器`validate_user_range`だけである。`copy_from_user`が`&UserSlice`を要求するので、**モジュール外の全呼び出し元に対しては「検証を経ないとユーザーメモリを読めない」ことが型で保証される。** ただしこの保証はモジュール境界に依存する。同一`syscall.rs`モジュール内からはprivateフィールドに触れるため`UserSlice { .. }`を直接構築できてしまう。したがってモジュール内の直接構築は`copy-skip-validate`破壊feature専用であり、通常コードでは行わない（この規律は型ではなくレビューで守る）。`copy-skip-validate`はまさにこの境界を突く破壊である。
- **TOCTOU（検証と読みのアトミック性）は構造条件に依存する。** 検証と読みが実質アトミックなのは、`syscall_entry`が割り込みゲート（IF=0）で入りプリエンプトが来ないこと、シングルコアであること、ユーザーページをアンマップする経路が`syscall`中に走らないこと、の構造条件による。**将来IFを立てる`syscall`（長時間ブロッキング等）を導入すると、この前提が崩れTOCTOU（検証後・読み前にアンマップ/再マップ）が現実化する**ため再検証が要る。`user_range_accessible`のレイアウト依存と同じ、安全性の成立が構造条件に依存することの記録である。
- **`UserSlice`の有効期間は同一`syscall`内・同一アドレス空間に限る。** 跨いで保持しない（staticに置かない）。higher-half B後のプロセス別アドレス空間では、トークンは「そのCR3の下でのみ有効」になるため、CR3を跨いで使わない制約をf-3で型（世代/CR3を持たせる等）またはdocで担保する（再確認の申し送り）。加えて、`SYS_CHECKSUM`のバッファ容量超過（`len > CHECKSUM_BUF_LEN`）を現状`-EFAULT`で代用しているが、意味的には「容量超過」でありポインタ不正（Bad address）とは異なる。errno体系が育つ段（POSIX互換の構想）で見直す。

higher-halfの破壊feature（B-2a-5、破壊feature `highhalf-*`）について、5点を明記する。

- **(a)(b)(c)はトリプルフォルト（cpu_reset）しない。判定にcpu_resetを使わない。** これは直感に反するので明記する。(a)(b)はトランポリン/最初期の#PFが**我々のIDT導入前**に起きるため、UEFIのIDTが拾いファームウェアが制御を取り戻す（-d intにファームウェア領域のRIP、CR3=firmware、INT 0x20 servicingが残る）。(c)はM2-d切替後に高位で#PFして停止する（ファームウェア復帰もしない）。いずれもCPU Resetは起動時の2回のまま増えない。**cpu_resetを判定条件にすると4種すべてFALSEで通ってしまう（実際に最初cpu_resetで判定して4種FAILした）。** したがって判定は位置署名（present/absentマーカー）+定常未到達（heartbeat=0）で行い、cpu_reset数とファームウェア復帰の有無は参考情報として出す。将来「cpu_resetで判定すべきでは」と誤って直さないための記録である。
- **(a)(b)がファームウェアへ制御を渡す機構は完全には解明していない。** UEFIのIDTが#PFをどう処理して自身のアイドルループへ戻すのかは追っていない。テストの妥当性（位置署名+定常未到達）には影響しないが、解明済みではない。
- **(a)(b)の失敗モードはファームウェアへ逃げる形なので、OVMFのバージョン更新時にこの2テストの挙動が変わりうる。** UEFIのIDT/フォルト処理が変われば、位置署名やheartbeat=0の成立が崩れる可能性がある。OVMFを更新したときの確認対象とする。
- **M2-d/A-1の切替前検査は物理範囲のメンバシップ検査のみで、高位マッピングの欠落を検出しない。** `highhalf-no-kernel-high-in-live-table`(c)がこれを実証した。必須マッピング検証は「切替後の必須領域が物理範囲に属するか」を見るだけで、A-1/B-1が持つ「新テーブルを独立walkerで実際に引く」検査を持たない。恒等が物理を覆っている限り高位マッピングの欠落を見逃す。walkベースへの強化はB-2bの検討事項（ADR-0024 / ADR-0021 B Addendum）。
- **トランポリンのバイト単位一致検査（base検査）。** ビルド済みkernel.elfの入口24バイトを期待リテラルと比較する（`common::elf`再利用、新規外部クレートなし）。既定ビルドで一致（B-2a-2/B-2a-3b/B-2a-5で3度、再リンク・B-1撤去を跨いで不変を実証）、`highhalf-trampoline-absolute-ref`で不一致。rel32がすべて`.text.trampoline`内なので配置非依存で安定。`cargo xtask check`のbase検査なので`--full`でなくても毎回走る。

**項目会計**: 検査を足したとき数が閉じていることを、この行だけで追う。**現在の項目数は`cargo xtask check`の出力（`all N check(s) passed`）を正とし、docsの他の場所には書かない。** 総数は検査を足すたびに増えるので、導出元から離れた場所に書けば必ずstaleになる（実際に`--full`=64がroadmapとdeferred-decisionsに残り、同じ型の誤りの3件目になった）。数え方は、base = `CHECKS`（build 4 / test 1 / clippy 4 / fmt 1）+ 静的検査、`--full` = base + QEMU + highhalfである。

### 文体の検査を補助スクリプトからxtaskへ移した範囲

`docs/coding-standards.md` §1の文体規則のうち、**機械的に判定できる2つを`cargo xtask check`へ移した**（base 17）。

- タスクリストのマーカー（`- [ ]` / `- [x]`）直後に半角空白があること
- 行結合の痕跡（和文の句読点・閉じ括弧の直後の半角空白、および直前に空白の無い`/`の直後の半角空白）

対象は`git ls-files`が挙げる追跡対象の`.md`だけである。コードフェンス・インデントコード・表の行は後者の対象にせず、インラインコードの中身は潰してから見る。

**移した動機は、規律で守っている箇所が実際に破れたことである。** 文体の検査はローカルの補助スクリプトで行っていたが、**回し忘れて閉じ括弧の直後に半角空白が入った差分をコミットした。** 原因は個々の見落としではなく、**1ファイルを直した直後に走らせて満足し、その後の別ファイルの編集後に走らせ直さなかった**という手順の穴である。`cargo fmt`と`clippy`が2日間未達だったのと同じ型で、**検出機構が手順の外にあると必ず起きる。**

**移していない検査がある。ここが覆う範囲を過大に読まないこと。**

| 検査 | xtaskへ移したか | 理由 |
|---|---|---|
| タスクリストの空白 | 移した | 正規表現だけで判定できる |
| 行結合の痕跡 | 移した | 同上。**実際に破れたのはこれである** |
| 閉じない強調 | **移していない** | レンダリング結果を見る必要がある |
| 見出しレベルの飛び・フェンスの対 | **移していない** | 同上 |
| リンク先とアンカーの生存 | **移していない** | 同上 |
| 変更前後のタグ列・語彙の比較 | **移していない** | レンダリングと、比較対象のリビジョンが要る |

**移していないものはローカルの補助スクリプトが引き続き担う。** Markdownレンダラが必要で、そのために新しいクレート依存を増やす判断はしていない（`rust-toolchain.toml`と`Cargo.lock`で再現性を固定する方針との兼ね合い）。**したがって「xtaskが通れば文体が守られている」ではない。** 覆っているのは「回し忘れても落ちる」範囲だけである。

**和文と英数字の間の空白（規則1）は、コミットメッセージの件名についてのみ検査がある**（既存のbase検査）。Markdownドキュメント本文には無い。移すなら既存の違反を洗ってからになるので、必要が生じた時点で別の段として扱う。

**この行の数はxtaskの定数と対で持つ。** `xtask/src/main.rs`の`EXPECTED_CHECK_COUNT`（`base` / `full`）が現在値を持ち、`cmd_check`の末尾で実際に走った項目数と照合する。**合わないと検査が落ちる。**

**強制されるのは定数の更新だけである。この行の更新は強制されない。** 検査を足すと定数の照合が落ち、直すには定数を上げる必要がある。定数のdoc がこの行を指しているので「検査を足したら会計行を見る」が構造から促されるが、**促されるだけで、定数だけ上げてこの行を放置することはできる。** **半分だけ構造へ移った状態であり、残りの半分は依然として規律である。**

**この行を機械で読んで完全に強制する案は採らない。** 数字をMarkdownから抜き出せば強制できるが、**xtaskがこの行の書式へ結合する。** 見出しの文言・強調・推移の書き方を変えると検査が落ちるようになり、**文書の書き方が検査の都合で固定される。** この行は人が読んで経緯を辿るための散文なので、その代償は釣り合わない。

**以前この案を見送ったときの理由の一部は、正確でなかった。** 「走らせずに総数を出せるよう`cmd_check`を組み替えるのが前提になる」と書いていたが、**照合するだけなら組み替えは要らない。** `total`は`cmd_check`の末尾で既に確定している（`all N check(s) passed`がそれを印字している）。組み替えが要るのは「走らせる前に印字する」形の場合だけである。もう一つの理由「二重持ちの場所が変わるだけ」も、**片方が機械で強制されるなら両方が静かに腐るのとは性質が違う**という点をweighできていなかった。**この行が2段ぶん古くなった実例が出たので、採ることにした。**

- **記録でしか守れない群**: (11) kernel_startの生の低位read [862/900行]、および boot_info の低位デレフ [468行]。これらは`DirectMap`を構築せず生の低位アドレスを直接読む/デレフするので、関門を通らず捕まえられない。**どちらも高位化できない**（(11)は862/900行がA-2[991行]より前でdirect_map()がbase=0を返す。boot_infoは468行がinit_direct_map[477行]より前で同様）。したがって「恒等除去より前に走る／参照されない」ことにのみ依存し、コードの境界コメント（(11)=862行、boot_info=最終利用の992行直後と除去予定点1166行の両側）とこの一覧で守る。**順序要件は「(11)とboot_infoの利用が除去点より前にある」こと**（(11)を除去点の後ろへ、または除去点を(11)/boot_info利用の前へ動かすのが違反。除去点をさらに後ろへ動かすのは安全）。

**コードとこの一覧の同期。** かつて「コード内採番を始めて途中でやめた」（`main.rs:480`の`(1)`止まり）ことが列挙の未完を招いた。同じ失敗を繰り返さないため、採番はコードから外しこの一覧を正とする。恒等前提の箇所はコードに固有マーカーを置いてある。未解決は `未解決の恒等前提`、解消済みは `解消済みの恒等前提` で、状態を表す語を接頭に出してある。かつては未解決 `恒等前提の箇所` と解消済み `恒等前提だった箇所` を使っていたが、語幹「恒等前提」と接尾「箇所」を共有し状態語（の／だった）が中間に埋もれていたため、語幹でgrepすると両者を拾い目視でも紛れやすく、実際に解消済みを未解決と取り違える誤りが起きた。接頭を分けたので `未解決の恒等前提` と `解消済みの恒等前提` はどちらも他方を部分一致で拾わない。現状 `grep '未解決の恒等前提' kernel/src/main.rs` = 3件で、各々「なぜ未解決側に残るか」がコメントと本一覧に書いてある: boot_info[468]（除去前に消費・468<477で高位化不可）、必須マッピング検証[745]（BootInfo_startを低位=物理として見る恒等前提・除去より前に走る）、kernel_start低位read[862]（順序依存・862<991で高位化不可・記録で守る）。解決した箇所はマーカーを「解消済みの恒等前提（…で解消）」に変えて `未解決の恒等前提` のgrepから外す（ヒープ[B-2b-2]・image_physのRSP/RIP変換[B-2a-2]がその例）。同期の不変条件を精密に書く。**`grep '未解決の恒等前提'` の結果は、この一覧のうち「まだ恒等前提が残っている（未解決の）箇所」の部分集合である。** 解決した箇所（高位化した等）はコードのマーカーを「解消済みの恒等前提（…で解消）」へ変えてgrepから落とす。これで双方向に食い違いを検出できる: 新しい恒等前提を足したのに一覧へ書き忘れれば、grepに出て一覧に無い（検出）。解決したのに一覧を直し忘れれば、grepから消えて一覧では未解決のまま残る（検出）。「高位化した」群と除去手順ステップ4の必須領域リストも一致していること（新しく高位化する低位ポインタを増やしたら、コードのマーカー・この一覧・必須領域リストを同時に更新する）。

順序を守る機構は**反転設計**にした。「除去が各サイトの完了を検査する」ではなく「恒等窓の構築が除去済みでないことを検査する」。`common::addr`に`IDENTITY_REMOVED`フラグを置き、除去（B-2b-4）が`mark_identity_removed()`で立てる。`DirectMap::new`は`base==0`（恒等窓。`identity()`もここを通る）のとき`IDENTITY_REMOVED`を検査してfail-fastする。利点は、cfg非依存（paging-testで検証サイトがcfg除外される穴が構造的に消える）、後から追加された恒等利用も自動的に守られる、単一の関門で各サイトを個別に編集しない、違反した箇所で正確に落ちる、の4つ。この関門のため`new`/`identity`は`const fn`ではなくなった（実行時にフラグを読むため。const文脈での利用は無いことを確認済み）。**関門でカバーできない残存分**: (11)のような生の低位readは`DirectMap::new`を経由しないので関門では捕まらない。列挙とコメントで管理する（(11)はM2-d切替直後で除去点よりはるか手前なので実リスクは低い）。また`DirectMap::new(base==0)`の直接呼び出しは捕まるが、`direct_map()`（登録窓の読み出し、モジュール内の構造体リテラル）は関門を通らない（登録窓の読み出しは対象ではないので正しい）。

恒等除去は**CR3リロード（全TLBフラッシュ）で行う。invlpgでは足りない**（`PML4[0]`を落とすと下位512GiBの写像が消えるが、TLBにキャッシュされた低位変換は残る。invlpgは1ページ単位で512GiB分の無効化手段にならない。G=0維持なのでCR3リロードで確実に落ちる。ADR-0018/M5-e-2）。落としてからフラッシュするまでTLBが生きているので実行継続・書き戻し可能。これを使い、除去を「検証可能で復帰可能な前段付きの不可逆な一手」にする（A-1/B-1の型を除去へ適用。**軸5=M2-d/A-1のCR3切替前検査のwalkベース強化とは別物**。軸5は既存のCR3切替を守るもので除去を守らない）。手順:

1. `PML4[0]`エントリを保存する。
2. 落とす前に`PML4[0]`配下を辿ってフレーム数を数えログに出す（フレーム会計をここで閉じる。孤立フレームは意図的リーク。A-1本流18フレームから恒等サブツリーは10枚前後=約40KiBと見込み、解体コードのリスクを負うより小さなリークで足りる。実測値で判断）。
3. `PML4[0]`を落とす（TLBが生きており実行継続可能）。
4. 独立walkerで検証。必須領域リスト=RIP / RSP / カーネルイメージ / direct map窓 / フレームバッファの高位VA / **ヒープの高位VA**が恒等なしで解決し、かつ`PML4[0]`が空であること（boot_infoは高位化しない=除去後に参照されないのでリストに含めない。上記の再分類による）。**このリストは恒等前提の列挙の「高位化が要る」群と同期している必要がある**（新しく高位化したポインタを増やしたらリストにも足す。この安全網の前提）。読み戻しは**walkで**行う（「低位VAが未マップ」をデレフで試すとフォルトするので、テーブルを辿ってNotPresentを読む）。
5. 検証失敗→`PML4[0]`を書き戻してhalt（メッセージ付き）。**フラッシュ前なので復帰可能**。検証成功→CR3リロード（全TLBフラッシュ）。
6. フラッシュ後の読み戻し（walk）: 低位VAが未マップ・高位が健全であることを実状態で確認。その後`mark_identity_removed()`。

**この検証は列挙した必須領域の安全網であって完全性の保証ではない。** リストに無い何かが壊れていればフラッシュ後に死んで復帰できない。完全性は依然としてgrepによるsweepに依存する。

順序逆転の破壊feature（高位化より前に除去を置く→恒等除去の瞬間に低位ポインタが見えず死ぬ）でこの順序依存を検査する。判定はB-2a-5と同じ位置署名+定常未到達（トリプルフォルトするとは限らない）。

**網羅の限界（正直に記録する）。** このsweepはgrep（`PhysAddr::new`/`VirtAddr::new`/`as *const`・`*mut`）+ パニック経路の目視。テストは実行された経路しか覆わない。feature下のみ到達する経路（(4)paging-test）、エラー処理、まだ発火させていないパニックは、grepが主たる保証でテストで完全性は証明できない。これは弱点の告白ではなく保証範囲の明示である。paging-testビルドでは検証サイト(5-8)がcfg除外される。B-2b-4(d)で恒等除去を `#[cfg(not(feature="paging-test"))]` で除外すると決めた（paging-testはsplit/unmapの破壊検査が目的で、恒等除去まで通す必要がない）。したがって**paging-testビルドでは恒等除去が検査されない**（カバレッジ穴として明示する）。**恒等除去が実際に走るビルド**は、除去点（`start_timer`より前・4検証サイト+checksumより後の1168付近）へ到達する `not(paging-test)` ビルドである。B-2b-4(d)の実測で確認した例: 既定（6段完走→定常到達=heartbeat）、`highhalf-remove-verify-fail`（step4失敗→5a復帰でhalt）、`preempt-in-critical`（除去`done`まで完走→その後デモの二重取得が発火＝CR3リロード後もデモ健全）、`exception-test`（除去`done`まで完走→その後に意図した例外が発火）。除去より前でhaltする破壊（highhalf a/b/c、検証サイト系のring3/syscall）は除去に到達しない。

**パニック/例外経路が恒等非依存である理由（load-bearingな性質。壊さないこと）。** 初期の設計判断（シリアルログ最優先、ADR-0003）の成果であり偶然ではない。(a) 出力がI/Oポート経由のシリアルのみ（ページング非依存）、(b) レジスタ値のみでメモリをデレフしない（CR2も値として読むだけ）、(c) テーブルwalkをしない、ため恒等除去後も動く。将来パニック経路に画面出力やテーブルwalkを足すとこの性質を壊す。**B-2b-4(e)の `highhalf-panic-after-remove` で実測で閉じた**（恒等を外した後に `panic!` して、パニックハンドラがシリアルへメッセージと `rsp` を出して halt する＝恒等非依存で動くことを確認）。

**`highhalf-remove-before-highify` と `highhalf-panic-after-remove` は「例外/パニックのダンプが出ることが成功署名」であり、フレーク判断の一般手順とは区別される。** 「確率的なテストとフレークの署名」の手順は「`exception: vector=` が出たら回帰として調査」と書いているが、この2種は**意図的に**例外/パニックを起こす破壊featureで、ダンプが出るのが正常である（before-highify は除去後に低位ヒープを触る #PF、panic-after-remove は意図的 `panic!`）。両者を混同して「例外が出ているから回帰では」と誤読しないこと。判定は各featureの present/absent マーカー（before-highify は `cr2=0x00000000…` で低位フォルトを、panic-after-remove は固有のパニックメッセージを確認）で行い、一般手順の対象ではない。この2種が有効なビルドは `test hooks:` のWARNに列挙されるので、そこで「意図的破壊ビルドか」を先に判別できる。

### 検査や計測が正しく機能していなかった事例

検査は存在するだけでは機能しない。過去に次の形で壊れていた。

**この節が集めるのは「検査があるのに働いていなかった」形である。** 「そもそも検査では見えない」形は性質が違うので、下の別の節へ分けてある。混ぜると、対策（検査を直す / 別の検出手段を探す）まで混ざる。

- スタブ表のstride検証、`!Send`のコンパイル時検査、正規化テキストによる内容不変検証。いずれも「わざと壊して検出されること」を確認して発覚した
- マーカーテストが`expected_markers`の先頭1本だけを見て打ち切っていたため、実装が正しくても残りの出力を取りこぼしてFAILになりうる状態だった。全部そろうまで待つ形に直した。到達しなければ`deadline`で打ち切る。期待マーカーが複数ある構成はすべて同じ競合を抱えており、まとめて解消した（`troubleshooting.md` 2026-07-22）
- 回帰チェック一式が実装ループにも`check`にも入っておらず、2日間走っていなかった。`--full`を追加して解消した
- **借りてきた観測量が、観測したい区間の外で更新されていた**（S2-c）。Local APICタイマの較正で「窓の間にティックを取りこぼしていないこと」を示すため、`interrupts::max_tick_jump()`を窓の前後で読んで比べる形にした。**あの値を更新するのは`run_timer_loop`の定常ループで、較正はその手前で走る。** したがって前後どちらを読んでも0のままで、「前後が同じ0だから取りこぼしが無い」と読めるが、実際は「まだ数えていない」だけである。実測で0/0が出たときに、値が綺麗すぎると思って更新箇所を辿って気づいた

  **上の3件とは下位型が違う。** あちらは「検査が壊れて何も見なくなった」、可視性検査の件は「列挙の外を静かに通した」、これは「**観測量が窓の中で生きていなかった**」である。対処も違う。**観測量を他所から借りるときは、それがいつ更新されるかを確かめること。** 直し方は2つで、較正自身が進み幅を数える形にしたことと、**名目のティック数ではなく実測のティック数で割る**ようにしたことである。後者は取りこぼしを検出するのではなく、**取りこぼしても結果が正しいままにする**（系統誤差を構造的に消す）。

  **この事例はレビュー側の提案から生まれた。** 「`max_tick_jump`を使えば安上がりに観測できる」という提案を、更新箇所を確かめずに実装した。**レビュー側の提案も、実装側の設計と同じ検算にかけること。**
- **`unsafe`の`SAFETY`コメント検査が、新しいファイルを見ていなかった。** 対象を`git ls-files "*.rs"`で列挙しており、追跡済みのファイルしか出ない。新しいファイルを書いてから検査を通し、その後に`git add`してコミットする、という自然な順序だと、そのファイルの最初の検査は追跡される前に走る。素通りしたまま「通った」と報告される。実際に`kernel/src/paging/verify.rs`が2コミットのあいだ見逃されていた。`--cached --others --exclude-standard`へ変えて解消した。未追跡の`.rs`に`SAFETY`無しの`unsafe`を置き、変更前は素通りし変更後は検出されることを確認している

  この形の見落としは、検査の対象範囲が「今そこにあるもの」ではなく「gitが知っているもの」で決まっていたことによる。新規追加が最も検査を必要とする場面なのに、そこだけ穴が空いていた。`tools/docstyle.py`にも同じ列挙方法の穴があり、あわせて直した。他の検査についても、対象の列挙方法が同じ性質を持たないかを見ておくこと

  **なお`--exclude-standard`は`.gitignore`だけでなく`.git/info/exclude`も参照する。** つまり検査の対象範囲が、リポジトリに含まれないローカル設定によって決まる。ローカル専用のファイルを拾わないために必要な挙動だが、これも「対象が環境によって変わる」という点で今回の穴と同じ系統である。別の環境で検査を走らせたときに対象が変わりうることを承知しておくこと

- **直接`cli`/`sti`の許可リスト検査が、3つの検出経路のうち2つで何も見ていなかった**（seam整備の項目2で追加した直後に発覚）。追加時の破壊確認は`cpu::disable_interrupts()`の呼び出し1経路だけを壊して「検査は働く」と確認していた。**その1経路は実際に働いていたが、他の2経路は壊れていた。**

  - asmのオペランドは`"  cli",`のように**引用符の内側にインデントを付けて**書かれる。`"cli"`の完全一致で探していたため拾えなかった
  - 生の命令は`asm!(`と**別の行**に書かれる。`asm!`を含む行だけを見ていたため、複数行の`asm!`ブロック内を追えていなかった（`global_asm!`だけは塊を追跡していた）

  取りこぼしていたのが**許可リスト10箇所のうち唯一「本物の排他」である`kernel/src/task.rs`の`global_asm!`内の`cli`/`sti`**（`GPR_BUF`を守る直接操作）だった。許可エントリが載っているのに検出されない、つまりそのエントリが死んでおり、**asm内に`cli`を書く限りこの検査は何も守らなかった**。発覚の契機は「許可エントリ数と出現数の単位を明示する」という指摘で出現数を数え直したことである。数を数えたら0件のファイルがあった

  修正後は、文字列リテラルをtrimして先頭トークンで判定する形と、`asm!(`から`);`までを塊として追う形にした。出現数は10から12へ増えた（`task.rs`の2件が新たに数えられるようになった）

- **`asm!`が同じ行で閉じる形（`asm!("cli")`）で、塊の追跡が解除されず残りのファイル全部をasm内と誤認していた**（上の修正の直後に、経路ごとの破壊確認を続けて発覚）。単一行では閉じ`);`が独立した行に現れないため`in_asm`が立ったままになる。実測では、単一行の`global_asm!`を1つ置くだけで`current_item`が固定され、`interrupts.rs`の許可済み5箇所すべてが所属名の不一致で未許可と判定された。**FAILする方向なので静かには壊れない**が、正当な1行形を書くと検査が使えなくなる。`asm!(`の`(`から括弧の残高を数え（文字列リテラル内は数えない）、同じ行で閉じるなら塊に入れない形へ直した。検出は`opens_asm`でその行自体を拾う

  **単一行の`asm!`内の`cli`そのものは、修正前から検出できていた**（取りこぼしではなく、追跡状態の漏れだった）。検出経路は4つ（primitiveの呼び出し / 通常の複数行`asm!` / `global_asm!` / 単一行`asm!`）あり、修正後に4経路すべてを個別に壊して所属アイテム名まで特定してFAILすることを確認している

#### 追跡状態の漏れには2つの向きがあり、危険なのは静かな方である

上の修正で塞いだのは単一行の形だが、**塊の終端判定は今も「trim後に`);`で始まる行」という整形の形に依存している**。漏れたときに何が起きるかは、漏れた変数によって正反対である。

- **`in_asm`だけが漏れた場合（通常の`asm!`）: うるさい方。** 所属名の追跡は壊れない（`current_item`を更新する分岐は`in_asm`を見ないため）。影響は生命令の検出範囲が広がることだけで、しかも先頭トークンが`cli`/`sti`の文字列に限られる。実測でも許可済みは壊れずOKのままだった
- **`in_global_asm`が漏れた場合: 静かな方。見逃しになる。** `current_item`が`"global_asm!"`に固定される。許可リストは`(file, item)`で照合するので、**そのファイルに`(file, "global_asm!")`の許可エントリがあると、以降の未許可の`cli`/`sti`がその許可エントリと一致して素通りする**。`kernel/src/task.rs`には実際にそのエントリがある（GPR_BUFを守る例外(g)）

後者を実測した。非準拠の閉じ方をする複数行`global_asm!`（`cli`/`sti`を含まない）を`task.rs`へ置き、その後ろの通常の関数へ未許可の`asm!("cli")`を入れると、**FAILせずOKのまま通った**。唯一の痕跡は出現数が12から13へ増えたことだけである（許可済みとして数えられた）。

**この静かな経路を実際に塞いでいるのは`cargo fmt`である。** 非準拠の閉じ方を書いても、`cargo fmt`が単一行へ整形し直す（式レベルの`asm!`だけでなく、**itemレベルの`global_asm!`も正規化することを実測で確認した**）。単一行は上の修正で塊に入れないので、`in_global_asm`は漏れない。つまり不変条件「複数行のasmは`);`始まりの行で閉じる」は、**同じ検査一式に入っている`cargo fmt --all -- --check`が強制している**。

**したがって、fmt検査が守っているのは体裁ではなく見逃しの経路である。** fmt検査を外す、rustfmtの挙動が変わる、あるいはこの検査を`#[rustfmt::skip]`の付いたコードへ適用する場合は、この静かな経路が開く。下の分離提案を実施すれば、この依存は消える。

**【論点・未着手】検出をブロック追跡から切り離す。** 現在の構造は検出そのものが`asm!`塊の追跡に依存しており、**`asm!`の書き方の変種が増えるたびに取りこぼしや誤認のriskが出る**（実際にこの検査だけで3回それで壊れた）。
代案: 検出は「先頭トークンが`cli`/`sti`の文字列リテラル」だけで行い（この判定は既に実装済み）、**塊の追跡は所属名の特定にのみ使う**。
そうすると検出が書き方に依存しなくなり、壊れやすい機構が**安全性の経路から診断の経路へ移る**（追跡が甘くても「どこか分からない」だけで見逃しにはならない）。
誤検出のriskは小さい（`"client"`は先頭トークンが`client`で不一致、`"sti-check …"`も同様）。
**壊れやすい機構をload-bearingにしない**という、このリポジトリが繰り返してきた形である（`alloc`を未importにして確保を不可能にする、フィールドを削除して二重の真実を不可能にする）。

**この提案を支える証拠は3件ある。いずれも「その場しのぎのスキャナでソースを解析している」という同じ原因から出ている。**

1. 引用符の内側のインデント（`"  cli"`）を拾えなかった
2. 複数行の`asm!`ブロックを追えていなかった。さらにその修正後も、単一行の形で追跡状態が漏れた
3. `asm_call_closes_on_same_line`が文字列内のエスケープ`\"`で`in_string`を誤って反転させる（現コードには該当箇所が無く実害は無い。同関数は`line.find("asm!(")`で**最初の1つ**しか見ない点も同様）

3件目は対処していない。**分離すれば、これらはいずれも「所属名が分からない」だけの問題に落ちて見逃しにはならなくなる。** 上の「fmt検査への依存」も同時に消える。
急がないので、項目1の後か気づいたときに扱う。

**【論点・未着手】許可エントリごとに出現数を宣言する。** 許可リストの各エントリに、そのエントリが覆う出現数を持たせ（`{ file, item, reason, occurrences }`）、検査は実測の出現数と宣言値を照合して、食い違えばFAILする。
上の静かな見逃し（`in_global_asm`が漏れて未許可の`cli`/`sti`が`(task.rs, "global_asm!")`のエントリへ吸収される）は、痕跡が出現数の増加だけだった。宣言値と照合すれば実測3に対し宣言2でFAILするので、**静かな見逃しがうるさい失敗に変わる**。
`cargo fmt`への依存もload-bearingでなくなる。fmt検査を外しても`#[rustfmt::skip]`を使っても、静かな経路は数の照合で塞がれ、壊れ方がうるさい側に収まるためである。
「時点依存の数字を離れた場所に書かない」原則には反しない。数はエントリごとの局所的な事実であり、宣言は対象の隣に置かれる。正当な変更で数が変われば照合がFAILして再承認が強制される（許可エントリを行番号ではなく関数名で識別する利点と同じ論理である）。
上の分離提案とは直交する。分離は所属名の精度を、数の照合は取りこぼしの検出を守るので、分離を実施しても無駄にならない。変更としては分離より小さい。

**ここから一般則を1つ立てる。検出経路が複数あるなら、破壊は経路ごとに行う。**
1経路で発火したことは、他の経路の健全性を何も意味しない。
上の事例では4経路（primitiveの呼び出し / 通常の複数行`asm!`内の生命令 / `global_asm!`内の生命令 / 単一行`asm!`）があり、確認したのは1経路だけだった。
修正後は4経路すべてを個別に壊して、いずれも所属アイテム名まで特定してFAILすることを確認している。
BKL本体で新しい検査を作るときも、まず検出経路を数え、経路ごとに壊すこと。

**経路の数え上げ自体が更新される点にも注意する。** この節は最初「3経路」と書いていた。単一行`asm!`という4つ目に気づいたのは、経路ごとの破壊確認を実際に進めている途中である。
数えたつもりの一覧が完全である保証はないので、**新しい書き方に出会ったらその都度経路として数え直すこと。**

- **同一の出所から両辺を導く検査は、その出所の誤りを検出できない**（S2-d-2）。LAPICタイマの起動時判定は、要求周波数と実効周波数を比べて許容幅の内にあることを見る。**実効周波数は較正値と初期カウントから導き、初期カウントも較正値から導く。** したがって較正値が2倍になれば初期カウントも2倍になり、**比は`100.000 Hz`のまま一致して通る。** 整数の割り算で生じるずれは捕まるが、較正値そのものの誤りは自己無矛盾のまま素通りする。

  **これは「検査が壊れていた」形ではない。検査は設計どおり動いており、設計が覆えない範囲にあった。** ホストの実時間を基準にする検査（`lapic-timer-test`）を足して初めて捕まった。**一般則は「両辺が同じ出所から出ていないかを確かめること。同じなら独立の基準が要る」である。** 独立性は精度とは別の性質で、桁が合っているかしか見ない粗い検査でも、出所が独立していれば覆える。**逆に、いくら精密でも出所が同じなら覆えない。**

  借りてきた観測量が窓の外で更新されていた件（S2-c）とは下位型が違う。あちらは**観測量が窓の中で生きていなかった**、こちらは**観測量は生きているが両辺が同じ値の関数である**。

- **同値である間は分類の誤りが観測できない。値が分かれる段で初めて出る**（S2-d-2）。e2dfc4bで`first_pic_vector()`の突き合わせ先を`timer_delivery_vector()`に分類した。**あの改名の時点では両者が同値だった**（タイマがまだ8259経由で、どちらも`0x20`）ので、分類が誤っていても出力は正しく、どのテストでも捕まらなかった。S2-d-2でタイマが`0xFE`へ移って値が分かれた瞬間に顕在化し、**実際に落ちた。**

  `first_pic_vector()`が記録するのは「PICの採番範囲で最初に届いたベクタ」で、定義からして8259由来の観測である。**突き合わせるべきは8259の採番（`PIC_TIMER_VECTOR`）であって、現在の配送先ではない。** 「インヘレントメソッドがトレイトメソッドに食われていた」件と同じく**結果の値が一致していたので値を見る検査では原理的に見えない**が、あちらは`dead_code`警告が検出手段になった。**こちらには検出手段が無く、値が分かれるまで待つしかなかった。**

  **一般則は「同値な2つを結ぶ記述を書いたら、それが同値でなくなる段を書き添えること」である。** 分岐や別名を導入する段は、たいてい事前に分かっている（この場合はS2-d-2と書いてあった）。**分かっているなら、そのときに見直す対象として記録できる。**

- **行が出た時刻は、その行が述べる観測の時刻ではない**（S2-d-2）。既定ビルドでは`timer: first tick arrived as vector 0x20`が、タイマをLAPICへ移す`lapic-timer:`の5行より**後**に出る。それでもこの行は正しい。`first_pic_vector()`が値を記録したのは割り込み文脈で、**較正中（切り替え前）の出来事**だからである。**ログの並び順を観測の順と読むと、この行は「切り替えた後もPICのベクタで届いている」と読めてしまい、逆の結論になる。**

  **「マーカーは行の部分文字列であって、行の構造や書式の証拠にならない」と同じ系列である。** あちらは行の中身についての誤読、こちらは行の位置についての誤読で、**どちらも「ログに見えているもの」と「ログが述べていること」を同一視したことから出る。** 観測を記録する時点と、それを印字する時点が離れている量（カウンタ・`Once`・`static`に溜めて後で出す形すべて）では常にこの差が生じる。

  **一般則は「時点を問う主張をログの並び順で検証しないこと。値がいつ記録されたかをコードで確かめること」である。**

- **検査がどのビルド構成で走っているかを、検査の意味を語る前に確かめる**（S2-d-2）。`alt-offset-test`がS2-d-2で何を示すようになったかを判断する際、**既定ビルドの起動ログでマーカーの前後関係を調べ、その結論を`alt-offset`ビルドへ当てはめた。** 誤りである。`interrupt-test`系のビルドは`start_timer`にAPICを`None`で渡すので（`kernel/src/main.rs:2786`。既定ビルドは同`1500`で`mapped_apic.as_ref()`を渡す）、**較正も切り替えも1度も起きない。** 既定ビルドに存在する`lapic-timer:`の5行が、そのビルドには存在しない。

  結果として「意味が切り替え前の窓に狭まった」と書いたが、**狭まったのではなく、この検査は最初から切り替えが存在しないビルドを見ていた。** 覆う範囲はS2-d-2で変わっていない。

  **「同じ条件で比べていないものを比べた」の再演である。** イメージ会計でサボタージュ付きビルドを測った件と同じ型だが、**今回は「値は起動ログから取る」という対処を守っていた。** 守ったうえで、**どのビルドの起動ログかを取り違えた。** 対処が一段しかないと、その一段の内側で同じ誤りが起きる。

  **判別に使える観測量がある。** `heartbeat`の`max tick jump`が既定ビルドでは256、`interrupt-test`系では2になる（較正がメインループを止めるかどうかの差）。`lapic-timer:`の行数（既定は5、`interrupt-test`系は0）でも分かる。**破壊featureの名前が壊し方を指すのと同じく、検査の名前はビルド構成を指していない。**

- **動機が無い段で、正しく使えない機構を入れない**（S3-b-1）。`cpu_id()`を実IDにするためにGSベースを入れる計画だったが、**GSベースの唯一の動機は`cpu_id()`の速さだった。** `common/src/percpu.rs`のモジュールdocが「GS化で変わるのは`cpu_id()`がGS読みになる点だけで、`PerCpu::this_cpu`は依然として配列を索引する」と明言しており、**データがGS相対へ移るわけではない。**

  そして正しく使うには`swapgs`が要る。`swapgs`が無い状態では、GSセレクタのロードでGSベースが0へ戻り（`ring3.rs`のRing 3復帰後のデータセグメント復元で毎回起きる）、恒等除去済みなので`gs:[0]`が未マップの線形アドレス0を触って #PF になる。**速さのために入れる機構が、正しさを壊す。**

  **したがってGSベースはS3から外し、`swapgs`・ユーザーTLS・`syscall`/`sysret`と同時に扱う段（S9以降）へ送った。** 土台はLocal APIC IDにした。**「先回りの抽象化をしない」の隣にある別の型で、あちらは「まだ要らないものを作らない」、こちらは「要るが正しく使えないものを作らない」である。**

- **標本数を増やすと、この指標の分解能は上がる**（S3-b-2a）。`iterations`について「小さい退行は見えない」と書いたが、**それは標本3つのときの話だった。** `sgdt`由来の`cpu_id()`を測ったとき、12標本（対照は6標本）で**約8%の差が幅の非重複として出た**（2004-2173 対 2176-2305。差は3カウントで、平均は2088対2247）。

  **したがって「見えない」ではなく「標本数で決まる」が正しい。** 桁の退行（却下したMMIO読みの5.92倍）は3標本でも明白に出るが、**1桁パーセントの差を主張するには標本を増やす必要がある。** 幅が重ならないことを根拠にするなら、**標本数を併記すること。**

  **それでも限界はある。** 12標本で非重複といっても差は3カウント（約0.1%）なので、**「8%の退行がある」は言えるが「8%より小さい退行は無い」は言えない。** 主張の向きを取り違えないこと。

- **除外リストは、その項目のジッタを免除するものであって、系統的なシフトを免除するものではない**（S3-b-1）。`cpu_id()`をLocal APICのMMIO読みにした形を測ったところ、プリエンプティブデモの周回数が**2214から374へ落ちた**（3回ずつ起動。幅は2180-2254と368-380で重ならない。**約5.9倍**）。`loop iterations`は除外リストに載っているので、「除外対象だから結論に影響しない」と書くことはできた。**それは誤りである。**

  除外リストに載せた理由は「起動ごとに揺れるから細かい比較に使えない」であって、**6倍のシフトを見なかったことにする根拠ではない。** 実際、baselineの幅は74（約3%）しかなく、**6倍は幅の外どころか桁が違う。** ここで除外リストを持ち出せば「検査があるように見えて何も検査していない」の再演になる。

  **ハートビートが114と115で違ったのを「変動フィールドなので結論に影響しない」と切り分けたのとは別の話である。** あちらは幅の内側、こちらは幅の外側である。**一般則は「除外は幅の内側にだけ効く。幅の外へ出た値は、除外リストに載っていても報告すること」である。**

- **足した検査が、それまで動いていた構成を止めることがある。検査が緑でも気づけない**（S3-b-1）。per-CPUスロットの境界（列挙コア数 > `MAX_CPUS`）を起動時に停止させる形で入れたところ、**`-smp 2`の構成で停止した**（2コア列挙 / スロット1）。それまでその構成は完走していた。

  **`acpi-smp-test smp2-enumeration`は緑のままだった。** この項目が見るのはMADTの列挙行（`2 local APIC(s) of which 2 usable`）だけで、**それは停止点より前に出る。** しかも早期打ち切りの項目なのでマーカーが出た時点でQEMUを落とす。**「検査が緑」と「系が悪くなっていない」は別である。**

  **検査自体が過剰だったのが根本である。** この段では`cpu_id()`が定数`0`を返し、カーネルコードを実行するのはbootstrap processorだけなので、**列挙が`MAX_CPUS`を超えても配列外の索引は起きない。** 「スロットが足りない」が「配列外を索引する」に直結するのは`cpu_id()`が非`0`を返しうる段（S3-b-2a）である。**保証をその段へ置き、この段では警告に留めた。**

  **一般則は2つである。** 「**停止させる検査を足したら、既存の全構成で完走することを確かめる**」（既存の検査項目が緑であることは、その保証にならない）。そして「**停止の条件は、守りたい不変条件が実際に破れうる段に置く。** 早く置くほど安全とは限らない」。

  **検査の側も直した。** `acpi-smp-test smp2-enumeration`の期待マーカーに`heartbeat: ticks=`を足し、禁止マーカーに`halting`を足した。期待マーカーに入れると**打ち切りの条件が「これも出るまで待つ」に変わる**ので、`-smp 2`で定常状態まで到達することが要求される。**QEMUの起動回数は増えない**（既に走っている項目である）。

  **捕まえているのは`heartbeat: ticks=`のほうである。** 停止を一時的に戻して確かめたところ、判定は次のようになった。

  | 判定 | 結果 |
  |---|---|
  | `heartbeat: ticks=`が現れる | **NG（これが落とした）** |
  | `halting`が現れない | OK（**捕まえていない**） |

  **`halting`は`cpu::halt_forever()`自身が出す語ではない。** 呼び出し側がログへ書いたときにだけ現れる。したがって**禁止マーカーの`halting`は二次的な網で、ログを書かずに停止する経路は捕まえられない。** 主たる根拠は定常状態への到達である。**「禁止マーカーがあるから停止は捕まる」と読まないこと。**

  **この発見の波及を洗った（記録）。** `halting`を「停止していないこと」の根拠に使っている箇所は**この1件だけ**だった（他の出現はすべて期待マーカー側で、停止を意図する破壊確認なので正しい）。あわせて**既定ビルドを走らせる項目で完走の根拠を持たないもの**を探したところ、`apic-decode-test ioapic-decodes`が同じ死角だった（早期打ち切りで、`min_heartbeats`も無く、期待マーカーが2つとも起動の途中に出る）。**`heartbeat: ticks=`を足した。** `APIC_TESTS`が同じ理由で既にこれを入れており（「検出した後もカーネルが動き続けることまで見る」）、**その慣習に揃えた形である。**

  **既定ビルドを走らせる項目は、完走の根拠を1つ持つこと。** 破壊確認の項目は停止を期待するので対象外である。

  **期待マーカーへ`heartbeat: ticks=`を入れると、打ち切りが定常状態まで延びるので走行時間が伸びる。** 実測で2秒程度なので現在は無視できるが、`--full`の所要時間の内訳を気にする段が来たときにこの2項目が効く。

- **検査が対象と交差していないなら、それは検査ではない**（S3-b-1）。「Ring 3往復のあとも`cpu_id()`が正しい値を返すこと」を到達条件にしようとしたが、**現在の起動順では構成できない。** `verify_ring3_excursion`と`verify_syscall_roundtrip`は`map_and_probe`より前に走るので、**実装を据えた後にRing 3往復が1度も起きない。** 据える前の`cpu_id()`は定数`0`を返す経路なので、**Ring 3往復はMMIO読みの経路に一度も触れていない。**

  **「壊れないことを確かめた」と書けたが、正しいのは「交差していない」である。** 前者は検査の結果、後者は検査が成立していないことの説明で、**緑という見た目は同じになる。** 交差の有無は、検査の対象と実行順を突き合わせないと分からない。

  **代わりに置いた検査も、redundantだと分かって落とした。** 恒等除去を跨いでLocal APICが読めることを確かめる案だったが、**S2-d-2のLAPICタイマが恒等除去より後に動いてティックを届けているので、既に示されている。** Versionレジスタの併読も、S1-cの`probe_local_apic`が同じ判定（`version == 0x00 || 0xFF`で停止）を持っていた。**足す前に、同じことを言う検査が既に無いかを見ること。**

- **公開範囲が広いと、未使用のコードが見えない。** 割り込み層の境界（S0-a）で`pub mod pic;`を`mod pic;`へ落とした瞬間、`pic::send_end_of_interrupt`が`dead_code`として現れた。公開モジュールの中では「外から呼ばれうる」と見なされて警告されないためである。**境界を閉じることは、死にコードの自動的な露出でもある。** 実際にはEOIの経路は`send_eoi_for(eoi_action_for(...))`だけで、この関数はどこからも呼ばれていなかった。

#### 列挙で守る検査は、列挙に無い形を静かに通す

**これは上の3件とは別の型である。** 上の3件は「検査が壊れて何も見なくなった」形で、こちらは**検査が見る範囲を最初から取りこぼしている**形である。対処法も違う。前者は破壊確認を増やすことで捕まるが、後者は破壊確認を増やしても、列挙に無い形を思いつかなければ捕まらない。

S0-aだけで2回起きた。いずれもコミット前に捕まえたので実害は出ていない。

- 当初の静的検査の案は「境界の外に`pic::`の参照が無いこと」を見る形だった。ところが非公開化と組み合わせると、参照はコンパイラが禁じるので、**検査が実際に見るのはコメントだけ**になっていた（設計段階で差し替えた）
- 可視性検査は`mod`と`use`だけを列挙しており、`pub type Alias = pic::Inner;`を素通りさせていた。別名を通せば内部の型を外から掴めるので、`pub use`と同じ実在の穴である（破壊確認の直前に気づいて`type`を足した）

**教訓は「列挙型の検査を作ったら、列挙に無い形で同じ結果に到達できないかを別途探す」である。** 探し方は、検査ではなく**目的**から測ることになる。可視性検査でいえば「境界の外に1行置いてビルドが通るか」を測る手順がその探索そのものだった。検査がFAILすることと、実際に到達できることは別の命題である。

**起動ログを解析する前に、完走していることを確かめること。** 起動ログは書かれている途中でも読めるので、**まだ出ていない行を「無い」と読める。** 背景実行にして完了を待たずに読んだり、`--no-limit`を付けずに打ち切られたログを読んだりすると起きる。**実際に踏んだ**（S3-b-1で、背景実行中の起動ログからイメージ会計を取った。値そのものは起動の最初期に出る行なので変わらなかったが、**変わらなかったのは運である**）。

確かめ方は、**末尾付近に必ず出る行の存在を見ることである。** 既定ビルドなら`heartbeat: ticks=`（定常状態に達した証拠）、加えて`[ERROR]` / `panic` / `halting`が無いこと。**「読みたい値が見つかったから読めた」で済ませないこと。** 値が早い行に出るものほど、この誤りに気づけない。

**ビルド成果物を測るときは、どのfeature構成でビルドされたものかを確かめること。** `cargo xtask check --full`の最後の項目はサボタージュfeature付きのビルドなので、`target/`にはその成果物が残る。直後に`nm`で`__kernel_end`を測ると、既定ビルドとは違う値（実測で0x248小さい）を静かに読む。実際にS0-bの報告で1度これをやり、「コードが縮んだ」と誤った記録を書いた（同一コミットで再ビルドして再現しないことから発覚した）。**規律ではなく出所で防ぐ。** 手順を「測る前に既定ビルドをやり直す」とすると規律に頼ることになるので、**イメージ会計の値は起動ログから取ることを既定にする**（起動ログには既定ビルドの値しか出ない）。これは「同じ条件で比べていないものを比べていた」の系列で、比較の対象がログではなく成果物になった形である。実際、当時ログと`nm`は食い違っており、**ログのほうが正しかった**。

**静的検査の対象指定は、宣言がどこに書かれているかに依存する。** これは上の「列挙に無い形」と同じfamilyの別の面で、**対象範囲の外を静かに通す**形である。S0-bで可視性検査の対象へ`kernel/src/task/`を足したが、**破壊確認が発火しなかった**。`mod scheduler;`の宣言は`kernel/src/task.rs`にあり、ディレクトリの外だったためである（`irq`は宣言が`irq/mod.rs`の中にあるので、この依存に気づく機会が無かった）。ファイルを明示して対象に入れ、再度の破壊確認でFAILすることを確かめた。**対象をディレクトリで指定したときは、守りたい宣言がそのディレクトリの中にあるかを確かめること。**

**禁じている形と、実際に漏れる形は一致しない。** 可視性検査が禁じる6形のうち、外から到達できるのは5つで、配下の非公開ファイルからの`pub(crate) use`だけは到達できない（実効可視性が親モジュールで頭打ちになる）。**保守的に禁じているだけの形が混じっていることを、検査のコメントに明記した。** 「6形すべてを壊してFAILした」とだけ書くと、6形すべてが実在の穴だったと読めてしまう。

**マーカーは行の部分文字列であって、行の構造や書式の証拠にはならない。** xtaskの期待マーカーは`contains`で照合するので、行の前半だけを切り取った文字列が入っている。これを見て「行がこう組み立てられている」と判断すると誤る。S0-aの設計中に2回、存在しない書式の食い違いを想定した（要約行のベクタ範囲は静的な文字列リテラルであり、IMRのログ行は元から期待値の後置きを持っていた）。**書式を論じるときは起動ログの実際の行を見る。**

同じ型の誤り（検査があるように見えて何も検査していない）は本節でこれが3件目である。
`ADR-0018`のAddendum 4が「過去2回の誤り」として記録していたおかげで、3件目だと即座に分かった。
記録しておくと、次に踏んだときに単発の失敗ではなく反復として扱える。

計測についても同じ型の失敗をしている。いずれも「同じ条件で比べていないものを比べていた」というものである。

- 比較用のworktreeと本体を交互に走らせるつもりで、`cd`がループの次の行にも効いていたため6回すべてworktree側で走っていた。所要時間が109.35 / 109.36 / 109.37秒とほぼ同一だったことが手掛かりになった。数字が揃いすぎているのは異常である
- worktreeを`/tmp`の深い階層に置いたため、そちらだけmonitorソケットのパス長が上限を超えて失敗していた。場所の違いが結果の違いとして現れており、比べたかった変更の効果ではなかった。本体で条件を切り替えて測り直した

**数字が出ていても、条件が違えば意味を持たない。**
比較する前に、比べている2つが本当に他の条件で揃っているかを確かめること。

コミットの検査は件名だけを見ており、**本文は対象外と決めている**。
文体規約の目的は公開時の見え方を整えることで、主な対象はREADME・docs・コード内コメントである。
本文には識別子や式（`is_multiple_of`、`% 16 == 0`、`#TS / #NP / #SS / #GP`など）がそのまま現れ、和文と隣り合う箇所で空白を落とすと読みにくくなる。
バッククォートで囲む書き方をコミットメッセージへ課すのは一般的でなく、揃えるために履歴の書き換えを増やすコストにも見合わない。
保留ではなく決定であり、後から再検討しない。

### 検査では原理的に見えない誤り

上の節と分けてあるのは、対策が違うためである。あちらは検査を直せば捕まる。こちらは**どのテストを足しても捕まらない**ので、別の検出手段に頼るしかない。

- **インヘレントメソッドがトレイトメソッドに食われていた**（S1-b-2）。`RootEntries`に`fn count(&self)`を定義したが、`entries.count()`が呼んでいたのは`Iterator::count`だった。Rustのメソッド探索は受け手の型を`T`→`&T`→`&mut T`の順に試し、各段でインヘレントを先に見る。したがって**値レシーバのトレイトメソッドは、`&self`のインヘレントメソッドより先に一致する。** `entry_count`へ改名して解消した。

  **結果の値が一致していたので、どのテストでも捕まらなかった。** 数え方が同じである以上、出力は正しい。唯一の検出経路は`dead_code`警告（定義したのに呼ばれていない）だった。**警告を`-D warnings`で落としていることが、ここでは検出手段そのものになっている。** 一般化すると、「別のものが呼ばれているが結果は同じ」という誤りは、値を見る検査では原理的に見えない

### 保守的な検査が実コードで働いた例

破壊確認ではなく、通常の実装中に発火した記録である。**検査が生きていることの証拠になるので残す。**

- **可視性の静的検査が、新規コードの入れ子`pub mod`を捕まえた**（S1-b-2）。`kernel/src/acpi/madt.rs`にエントリ種別の定数群を`pub mod entry_type { … }`として書いたところFAILした。実効可視性は親（`mod madt`）が非公開なので外からは触れず、漏れる形ではない。それでも禁じているのは、`mod madt`を`pub`にする1文字で漏れる形へ変わるためで、S0-aで`pub(crate) use super::pic::*;`を保守的に禁じたのと同じ判断である。

  **緩めなかった。** 入れ子を許すと「親が非公開だから漏れない」という推論が毎回必要になる。この検査の価値は推論が要らないことにある。接頭辞つきの定数（`TYPE_LOCAL_APIC`など）へ平坦化して解消し、平坦化した理由をコードに残した（残さないと、きれいにしようとした人が入れ子へ戻す）

- **スタブ表の検査が、専用スタブへの差し替えを捕まえた**（S2-d-1a）。スプリアスベクタ`0xFF`を例外スタイルのスタブから専用スタブ（`zaytos_spurious_stub`）へ載せ替えたとき、`check_stub_table`の除外リストへ足すのを忘れたまま起動した。**起動時の検証が`entries=NG`で落ちて止まった。** 除外を足して解消している。

  **ここから一般則を1つ立てる。列挙型の検査は「列挙にあるはず」を検査する向きに書けば、漏れが静かに通らず落ちる。** `check_stub_table`が見ているのは「全ベクタのゲートが例外スタブ表の対応する位置を指す」という**あるべき形**で、そこから外れるベクタを除外リストで抜く構造である。除外し忘れると、そのベクタは条件を満たさないのでFAILする。**上の「列挙で守る検査は、列挙に無い形を静かに通す」と向きが逆である。** あちらは禁じたい形を列挙するので列挙の外が素通りし、こちらはあるべき形を全体で言い切るので列挙からの漏れが落ちる。**次に列挙型の検査を書くときは、この向きに取れないかを検討すること。** 取れるとは限らない（可視性検査は「あるべき形」を全体では書けない）が、取れるなら、更新漏れの扱いが見逃しから停止へ変わる。

  **ただし、その除外リストのほうは静かに通す向きだった。** 上の一般則を立てた直後に、同じ変更が裏側で穴を作っていたことに気づいた。次の節で塞いだ。

### 例外スタブ表の外のベクタは、それぞれの専用スタブを指す

出典: `kernel/src/idt/mod.rs`（`dedicated_stubs` / `check_dedicated_stubs`）

**この検査は、直前の変更が空けた穴を塞ぐために作った。** `check_stub_table`の除外リストへベクタを足すと、**そのベクタについてこの検査は何も見なくなる。** 除外されるのはyield（`0x41`）・syscall（`0x80`）・スプリアス（`0xFF`）の3本で、`check_irq_stub_table`が見るのは`0x20`-`0x40`だけなので、**3本とも「ゲートの指す先を誰も見ていない」状態だった。**

**失敗の形は静かである。** ゲートの代入を落としても、`idt::init`が先に256本すべてを例外スタイルのスタブで埋めているので、そのベクタはpresentのまま例外スタブを指す。present / ゲート種別 / DPLを見る既存の検査は全部通る。**起動は緑のまま進み、そのベクタが実際に起きたときに初めて壊れる。** yieldとsyscallは戻らない経路（`exception_entry`は`-> !`）へ落ち、スプリアスはS2-b以前の「起きたら止まる」状態へ戻る。

**構造で塞いだ。規律では塞いでいない。** 一覧（`dedicated_stubs`）を1つ置き、**飛ばす側（`check_stub_table`）と確かめる側（`check_dedicated_stubs`）が同じ配列を読む。** 片方だけを更新して食い違わせられないので、「除外に足したが検査に足し忘れる」という今回の形が起こらない。

**見るのはハンドラのアドレスだけである。** present / ゲート種別 / DPLは全256ベクタを対象にした既存の検査が見ており、syscallのDPLは`SYSCALL_GATE_DPL`という本ごとの期待値を持っている。**属性を一律に見ると、DPL 3が正しいsyscallで落ちる。**

**破壊確認は3本それぞれで行った。1本で落ちたことは他の2本の健全性を意味しない。**

| 破壊 | 先に落ちた検査 | 出力 |
|---|---|---|
| スプリアス（`0xFF`）のゲート代入を消す | 本検査 | `vector 0xff points at 0x…e270, expected its dedicated stub at 0x…e4c0` |
| yield（`0x41`）のゲート代入を消す | 本検査 | `vector 0x41 points at 0x…d690, expected its dedicated stub at 0x…e520` |
| syscall（`0x80`）のゲートをyieldのスタブへ向ける | 本検査 | `vector 0x80 points at 0x…e520, expected its dedicated stub at 0x…e530` |

いずれもベクタを名指ししてERRORを出し、`halt_forever`で停止した。

**syscallだけ破壊の形が違う。理由を書く。** 代入を消す形にすると、**本検査より前にDPLの検査が落ちる**（実測: `DPL layout ok=false (syscall vector 0x80 DPL=Some(0))` → `idt: entry checks failed; halting`）。それでは本検査が働いたことにならないので、属性を保ったままアドレスだけを誤らせる形にした。3本目の実測では`DPL layout ok=true`のまま本検査だけが落ちており、**既存の検査では捕まらない誤りを捕まえている**ことが同じログの中で見える。

**破壊は作業ツリーがクリーンでない状態で行った。** 本検査の実装が未コミットだったためで、`coding-standards.md`の代替手順（作業ツリーの外へコピー → 壊す → 書き戻す → 機械で一致を確認）に従った。3回とも`diff`が空かつ`md5sum`が一致することを確認している。

**検査項目は増えていない。** 起動時の検証であって`--full`の項目ではないので、項目数は変わらない（**総数は書かない。会計行を見ること。** ここに書いた「`--full`は77項目」はS2-d-1cとS2-d-2で増えた分だけ古くなった。時点依存の数字を導出元から離れた場所に書くと必ずこうなる、の実例をもう1件足したことになる）。起動ログには1行増える（`idt: dedicated stubs outside the exception table: 3 checked, every gate points at its own stub=true`）。

### IMRへの書き込みは割り込み層の境界の内側だけに存在する

出典: ADR-0018、`architecture.md` §6.8、seam整備の項目1（S0-a）

かつてここには「IRQの解禁は1箇所へ集約する」と書き、検査は無いとしていた。
S0-aで`kernel/src/irq/`の内部（`pic` / `pit`）を非公開にしたので、**境界の外からIMRの読み書き関数を呼ぶとビルドが落ちる**。参照が無いことはコンパイラが保証し、その保証が外されないことを可視性の静的検査が守る。

**見出しを書き直したのは、保証できる範囲が「解禁が1箇所」ではないためである。** 解禁の呼び出しは現在2箇所ある（タイマとキーボードで前提条件が違う）。無理に1箇所へ寄せる理由が無いので、集約は求めない。呼び出し箇所の集約を将来求めるなら、それは別の論点として`deferred-decisions.md`へ置く。

この検査が守らない範囲を明示する。

- **境界の公開関数が生の値を返す形は捕まらない。** `pub fn read_masks() -> (u8, u8)`を`irq`へ足せば、可視性はprivateのままでも呼び出し側はPICの語彙を持てる。これはレビューで守る
- **コメント内の言及は対象外。** コメントは実行されないので結合を作らない。`pic`は`topic`の部分文字列でもあり、素朴な一致は誤検出源になる
- **生のI/Oポート直叩きは対象外。** 境界の外から`outb(0x21, …)`と書けばIMRは触れる。現在そのような箇所が無いことは実測で確認したが（`outb` / `inb`の全件を見て、PICのポートを触るのは`irq/`の中だけ）、この検査はそれを見ていない。`cli`/`sti`を`common::cpu`へ集約したときと同じ構造で、primitiveの集約が先にあって初めて「経由しない呼び出し」を検査できる
- **禁じている形と実際に漏れる形は一致しない。** 破壊確認では、`pub mod` / `pub(crate) mod` / `pub use` / `pub type`の4つが外から到達でき、配下の非公開ファイルからの`pub(crate) use`は到達できなかった（実効可視性が親モジュールで頭打ちになるため）。後者は保守的に禁じているだけである。禁じたままにするのは、`mod compat;`を`pub mod compat;`に変えるだけで到達できる形になるためで、その1文字の差を検査の外に置きたくない

### 割り込み層の境界（S0-a）からS2への申し送り

PIC/PITをLocal APIC / IO-APICへ差し替える段（S2）で、境界の内側だけでは済まない箇所がある。S0-aの作業中に実測で分かったものを残す。

**xtaskのマーカーがPIC固有の文言と値に依存している（3件）。** いずれも部分一致で照合しているので、文言が変わればテストが落ちる。S2ではマーカー側を問いベース（`MaskCheck::matches`など）へ移す作業が要る。

| マーカー | 依存しているテスト | 何がPIC固有か |
|---|---|---|
| `pic: IMR after unmasking IRQ0 master=0xfe slave=0xff` | interrupt-test timer / no-eoi | IMRが2バイトという形 |
| `pit: channel 0 set to divisor=11932` | interrupt-test no-eoi | 分周値はPITの語彙 |
| `sti-check summary: 4. PIC remapped to 0x20-0x2F = UNVERIFIABLE` | interrupt-test enable-only | ベクタ範囲 |

境界の観測値のうち、依存があるのは`MaskCheck`と`TimerSetup`のDisplayである。`ObservedMasks` / `managed_vectors` / `ServiceSnapshot`が出す行にはどのテストも一致を取っていない（実測で確認）。

**S2で形が変わる観測値。** `ServiceSnapshot`はマスタのISRだけを持つが、IO-APICに従属コントローラは無いのでmaster/slaveの区別自体が消える。`MaskCheck`のIMR 2バイトも、redirection tableでは成り立たない。

**`sti-check`の要約行の項目名は静的な文字列である。** 項目4は`4. interrupt delivery vectors are set as intended`で、ベクタオフセットから組み立てていない。**この文言はS2-d-1cで書き直したものである**（以前は`4. PIC remapped to 0x20-0x2F`で、`alt-offset-test`では事実と食い違っていた。現在の文言はどちらの構成でも成り立つので、この食い違いは解消している）。なお**この項目が`UNVERIFIABLE`なのは、sti前の時点でICW2を読み戻せないためである。** 再マップが実際に効いていることは`alt-offset-test`と最初のティックの到達が事後に示しており、カバレッジの穴ではない。**S2-d-2で判明したとおり、この`UNVERIFIABLE`は恒久的である**（下記「タイマをLocal APICタイマへ移す（S2-d-2）」）。

**起動ログを変更前後で突き合わせるときに除外するもの。** 変動フィールド（ティック数・経過秒・ループ周回数・`max tick jump`・`resumes` / `iterations` / `switches`・実アドレス・**Local APICタイマの較正値**（S2-c。中央値・ばらつき・標本の並びという**値だけ**。起動ごとに揺れる。実測で865 ppm。**同じ行にある`divide by 16`や`window 10 PIT tick(s)`は除外しない。** 変わってはいけない構造的な記述なので、行ごと落とすと変化に気づけない））に加えて、**UEFIメモリマップ由来の値**を除く。具体的には`descriptors_len`と、そこから導かれる空きフレーム数・除外ページ数・使用中の空き範囲数・メモリマップバッファの終端である。理由は、**同一コミット・同一のQEMU引数でも130本と132本の両方が出る**ためで、単調増加でもない。OVMFの変数ストアは毎回テンプレートから作り直しているので蓄積ではなく、機序は特定していない。現時点でこれらの値に一致を取っている検査は無い（実測で確認）。空き範囲は9〜10 / 256で、容量に対する余裕は十分ある。

**余裕の定義を変えた。以後はページ丸めの端から測る。** 知りたいのは「いつ`PML4[511]`のPT枚数が3から4へ変わるか」であり、それを決めるのは**写像が2MiB境界を跨ぐかどうか**である。写像はページ粒度なので、変わる瞬間を決めるのは`__kernel_end`そのものではなく、それを4KiBへ切り上げた端である。`__kernel_end`起点の値は、その瞬間を1ページ分ずれて予測する。

    余裕 = 0x200000 - ((__kernel_end の物理 + 0xfff) & !0xfff)

**切り替え時点の値を両方並べる。系列に定義の切れ目が入ることを書いておかないと、後から並べた人が「急に数KiB減った」と読む。** 切り替えたのはS2-d-1aの次のコミット（専用スタブの検査）で、その時点の物理`__kernel_end`は`0x1b72d0`である。

| 起点 | 端 | 余裕 |
|---|---|---|
| 旧定義（`__kernel_end`） | `0x1b72d0` | `0x48d30` = 約291.3 KiB |
| **新定義（ページ丸め）** | `0x1b8000` | `0x48000` = **288.0 KiB** |

**下の系列は旧定義のままである。** 遡って引き直していないので、上の切り替え時点より前の数字と直接引き算しないこと。

**イメージ肥大の会計。** S2-d-2完了時点で`__kernel_end`は`0xffffffff801be2f0`（物理`0x1be2f0`、新定義の端`0x1bf000`、余裕`0x41000` = **260.0 KiB**）。直前のコミット（e2dfc4b。タイマのベクタ定数の分離）は`0x1bb2f0`（新定義の端`0x1bc000`、余裕`0x44000` = 272.0 KiB）で、**S2-d-2での増加は`0x3000` = 12.0 KiB**（余裕は同じだけ減る）。**この2点は同じ定義どうしの比較である。**

**S2-d-1bとS2-d-1cの完了時点の値は記録されていない。会計行の欠落である。** 専用スタブの検査（`0x1b72d0`）からe2dfc4b（`0x1bb2f0`）までの3コミットぶんで`0x4020` = 約16.0 KiB増えているが、**その内訳をどのコミットに帰属させるかは測っていない。** S2-d-2の増加はe2dfc4bを起点に測っているので、この欠落の影響を受けない。**増減の両方を書くという規則からすると、当時に測るべきだった。**

専用スタブの検査の時点で`__kernel_end`は`0xffffffff801b72d0`（物理`0x1b72d0`、新定義の余裕288.0 KiB）。S2-d-1a完了時点は`0x1b62d0`で、`__kernel_end`は**1バイトも動いていない**（S2-d-0と同値。`.text`が256バイト、`.rodata`が16バイト増えたが4KiBの量子に収まった。下の節を見ること）。S2-d-0完了時点で`__kernel_end`は`0xffffffff801b62d0`（物理`0x1b62d0`）、2MiB境界（物理`0x200000`）までの余裕は`0x49d30` = 約295.3 KiB。S2-c完了時点は`0x1b42d0`（余裕`0x4bd30` = 約303.3 KiB）で、S2-d-0での増加は`0x2000` = 8.0 KiB。S2-b完了時点は`0x1b02d0`（余裕`0x4fd30` = 約319.3 KiB）で、S2-cでの増加は`0x4000` = 16.0 KiB。S2-a完了時点は`0x1ae2d0`（余裕`0x51d30` = 約327.3 KiB）で、S2-bでの増加は`0x2000` = 8.0 KiB。S1-c完了時点は`0x1ac2d0`（余裕`0x53d30` = 約335.3 KiB）で、S2-aでの増加は`0x2000` = 8.0 KiB。S1-b-2完了時点は`0x1a82d0`（余裕`0x57d30` = 約351.3 KiB）で、S1-cでの増加は`0x4000` = 16.0 KiB。S1-b-1完了時点は`0x1a12d0`（余裕`0x5ed30` = 約379.3 KiB）、S1-a完了時点は`0x19c2d0`（余裕`0x63d30`）、S0-b完了時点は`0x19c2c8`（余裕`0x63d38`）、S0-a完了時点は`0x19c2d0`である。**値は既定ビルドの起動ログから取ること。** 「起動ログから取る」だけでは足りない。**`cargo xtask check --full`のログを使わないこと。** `--full`のQEMU項目は最初から破壊featureつきのビルドで走るので、ログに最初に現れる`higher-half: arrived at high VA`の行は既定ビルドのものではない。**実際に踏んだ**（S2-bで`--full`のログから拾って`0x1af1e8`を得たが、既定ビルドの値は`0x1b02d0`だった）。既定ビルドを別に起動して取ること。その起動ログは既定ビルドの実行結果そのものなので、サボタージュ成果物を読む余地が構造的に無い（`higher-half: arrived at high VA`の行が`__kernel_end`を含む）。`nm`を使うのは、ログに出ていない記号を見たいときに限り、そのときは明示的に既定ビルドをやり直す。`cargo xtask check --full`の最後はサボタージュfeature付きのビルドで終わるので、その直後に`target/`の成果物を測ると別のビルドの値を読む（実測で`0x19c080`になり、既定より0x248小さい）。カーネル高位マッピングのページテーブルは3枚（`PML4[511]`）のままで、2MiB境界を跨いでいない。跨ぐとPTが1枚増えてこの数字が変わる。

**この値は段の完了ごとに動くので、前段の値を次段の前提として持ち越すと必ず古くなる。** 実際に1件起きている。S2-d-0の実装が未コミットだった時点の`0x1b52d0`（余裕`0x4ad30` = 約299.3 KiB）が、コミットで`0x1b62d0`へ動いた後もそのまま次段の前提として使われていた。**「記録された数字が古くなったまま前提に使われる」の系列である。** 前提として使う前に、既定ビルドの起動ログから取り直すこと。

**`__kernel_end`は4KiB単位で量子化されている。「増加0バイト」は「コードが増えていない」を意味しない。** リンカスクリプトは各セクションを`ALIGN(4K)`で配置し、`__kernel_end`は`.bss`の末尾である。したがってこの値が動くのは、`.text`/`.rodata`/`.data`の増加が4KiB境界を越えて`.bss`の開始位置を押し出したときか、`.bss`自体が増えたときだけである。実測（S1-b-1）では、コードと文字列リテラルを足しても`__kernel_end`が1バイトも動かない一方、`higher-half: arrived at high VA`行のRIPは動いていた。**バイナリが違うことはRIPが示し、`__kernel_end`が同値であることはセクションの余白が吸ったことを示す。** 同値を見たときは、測り間違い（別構成のビルドを読んだ等）と量子化を区別すること。区別する材料はRIPと`readelf -S`のセクション境界である。

### ACPIテーブルへ触る前提（S1-b）

**参照する物理アドレスは、読む前に`ActivePageTable::translate`で実際にwalkして確かめる。** 計画（`MappedRanges::contains_range`）は「そう張るつもりだった」ことしか言わず、「計画にあるが実際には張られていない」を見逃す。B-2a-5が実証した穴と同じ性質である。walkは翻訳の有無だけでなく、**翻訳が当の物理ページを指していること**まで見る（direct map窓は`base + phys`なので、翻訳結果は元の物理と一致するはずである）。マップされていなければ`#PF`で落ちず、検出して報告する。

**マップされるかは型で決まる。回数では決めない。** `classify()`は型を見てマップするかを決めるので、ACPIテーブルが載っているUEFIメモリ記述子の型が分かれば、その領域がマップされるかは構造的に決まる。`EfiACPIReclaimMemory` / `EfiACPIMemoryNVS`なら常に写り、`EfiReservedMemoryType`なら常に写らない。メモリマップの細部（各領域の大きさや個数）は起動ごとに揺れるが、この関係は動かない。「何回起動しても毎回マップされていた」を根拠にすると、20回連続PASSでベースラインを誤った件と同じ型の誤りになる。**したがって観測して記録するのは型である。**

実測（QEMU + OVMF、`-m 256M`、5回の起動）では、RSDP・XSDT・MADTの3つとも同じ記述子`0xf76d000..0xf77f000`に載っており、その型は`EfiACPIReclaimMemory`（型9）である。`classify()`は`ReservedButMapped { cacheable: true }`を返すので、この領域は常にマッピング計画へ入る。**この記述子は`EfiReservedMemoryType`の穴（実測`0xf6ed000..0xf76d000`、architecture §6.4）の直上にある。** 穴の側に落ちていれば写らなかった。危険は仮想のものではない。

5回の起動は「型が起動ごとに変わらないこと」の確認に使ったのであって、回数そのものを根拠にはしていない。**根拠は型である。**

**ACPIテーブル用の一時マッピングは作らない（S1-b-3の結論。この段は畳んだ）。** ただし根拠の中で構造と観測を混ぜないこと。**「型9がマップ対象である」は構造**で、`classify()`がそう決めている以上揺れない。**「テーブルが型9に載っている」は観測**であり、別のファームウェアや実機では変わりうる。5回同じだったことはこの観測を強めるが、構造にはしない。したがって結論はこうなる。

- テーブルが型9に載る限り、構造的にマップされる。だから一時マッピングを先回りで作る必要は無い
- どの型に載るかは観測でしか分からないので、**観測側は実行時の`translate`チェックが覆っている。** 型が変われば、そこで検出されて報告される

**`translate`チェックは保険ではなく、この結論の一部である。** 「型9だから安全」とだけ読んだ人がこのチェックを冗長だと判断して外すと、結論の観測側の根拠が消える。外さないこと。

**RSDPが名乗る長さは「検証済み / 不正 / 検証不能」の3状態で扱う。** 仕様の最小サイズ（36バイト）を下回る値はどの版でも正当になりえないので不正である。一方、読み取りバッファ（64バイト）を超える長さは**壊れているとは限らない**。将来の版が長いRSDPを出すことは仕様の範囲内で、こちらが読めないだけである。これを不正として報告すると観測していないことを観測したと書くことになり、黙って36バイトで検算すると「検証したことにする」ことになる。どちらも避けるために第3の区分を置いた。`sti`前の7項目が同じ3状態を持ち、PICの再マップが書き込み専用レジスタゆえに「検証不能」へ落ちるのと同じ形である。検証不能な長さでチェックサムの検算へ進めないことは型で塞いである（`VerifiableLength`は`declared_length`だけが作れる）。

**S1では検出して報告し、起動は継続する。** ACPIが読めないだけで単一コアのカーネルが起動しなくなるのは機能的な後退である。致命へ格上げするのはACPI無しでは進めなくなるS2（APIC移行）である。破壊featureの期待マーカーにハートビートを入れてあるのは、検出した後もカーネルが動き続けることまで見るためである。

**MADTのエントリ走査が止まることは、打ち切りカウンタではなく不変条件で保証する。** エントリは「type(1) + length(1) + 本体」の可変長で、`length`はファームウェアが書いた値だから0でありうる。素朴に`offset += length`と書くと同じ位置を読み続けて無限ループになり、症状は「起動ログが途中で止まる」という切り分けにくい形で出る。守りは2つで、片方では足りない。エントリ長が最小（2）未満なら停止するので前進量は必ず2以上になり、`length`が残りバイト数を超えるなら停止するので範囲外へ出ない。前者だけでは最後のエントリが残りを超えたときに範囲外へ出て、後者だけでは`length == 0`で残りが減らずに回り続ける。両方あって初めて「残りは単調に減り、0未満にならない」が成立する。ホストテストでは、任意のバイト列256通りに対して有限回で終わることを確かめている。

**S1-b-2の破壊feature 6種は、検出経路ごとに分けてある。** 署名・チェックサム・長さ・エントリ長0・未マップ・窓の外である。1つの破壊で複数の経路が同時に落ちると、どれが働いたのかが分からない。エントリ長0の破壊がチェックサムのバイトを合わせ直しているのはそのためで、合わせ直さないと先にチェックサムが破れて走査へ到達せず、「エントリ長0の検出を見た」ことにならない。破壊した経路と観測した経路が食い違う形は、このプロジェクトが繰り返している誤りの型そのものである。**未マップの破壊はアドレスをリテラルで持たない。** `classify()`が`Unmapped`にする最大の記述子の中点を実行時に求める。穴の位置は起動ごとに揺れるので、リテラルで焼き込むと穴が動いた起動で破壊が破壊にならず、検査が静かに通る。中点を採るのは、未マップ領域の先頭が隣の2MiBページに巻き込まれて写っている可能性を構造的に排除するためである。

**`-smp 2`での列挙は検査項目にした。** roadmapのS1到達条件に「`-smp 2`で起動しても列挙結果がQEMUの指定と一致すること」とあるのに、手動実行でしか確かめていなかった。**手動確認は再現されず、必ず腐る。** 全項目を複数のコア数で回すと項目数も時間も倍になるので、この1項目だけを2コアで回す（費用はQEMU起動1回）。禁止マーカーは`1 local APIC(s) of which 1 usable`で、これは既定（1コア）の起動で毎回出る行である。**したがってこの項目は`-smp`が効いていなければ通らない。**

### APICのレジスタの現在値（S2-a）

**読むだけの段の記録である。** 割り込みの経路は変えていない（PIC / PITのまま）。I/O APICのIOREGSELへの書き込みだけを伴う。読みたいレジスタを選ぶセレクタであって割り込みの設定ではないが、**S2で最初の書き込みがここである。**

**ファームウェアは既にLAPICを有効化し、virtual wire modeを構成している。**

| レジスタ | 実測値 | 意味 |
|---|---|---|
| SVR | `0x0000010f` | bit 8 = ソフトウェア有効化済み。spurious vector = `0x0f` |
| LVT LINT0 | `0x00000700` | ExtINT、マスクなし |
| LVT LINT1 | `0x00000400` | NMI、マスクなし |
| LVT Timer | `0x00030020` | マスク済み、periodic（bits 18:17 = 1）、vector `0x20` |
| LVT Thermal / PMC / Error | `0x00010000` | いずれもマスク済み |
| TPR | `0x00000000` | |

**「LAPICを有効化する瞬間」は存在しない。** したがって「有効化した瞬間に8259経由のタイマが死ぬ」という形の危険は起きない。**危険は消えたのではなく、位置が変わっている。**

- **危険なのは、SVRのbit 8を落とすことと、LINT0をマスクすることである。** どちらかを行えばPITのIRQ0が即座に届かなくなる
- **SVRのベクタ欄（bits 7:0）の書き換えは、この危険に含まれない。** bit 8を立てたままなら現在の配送は壊れない

**安全条件を、危険より広く書かないこと。** 「タイマが移り終わるまでSVRに書き込まない」と書くと、ベクタ欄の設定まで先送りされる。**広すぎる条件は、後で「条件に触れるから」という理由で正しい操作を止める。** 条件は上の2つに限る。

**spurious vectorが`0x0f`である。ベクタ15はCPUの予約例外ベクタの範囲（0から31）の中である。** 現在はLAPIC由来の割り込みを1つも構成していないので潜在的だが、**LAPICが配送を担い始める時点（S2-d-1）より前に設定し直す必要がある。** 放置してスプリアスが起きれば、予約例外として解釈される。設定は遅くともS2-bからS2-cで行う。併せて次が要る。

- **新しいスプリアスベクタのIDTゲートを用意すること。** 設定だけしてハンドラが無いと、起きたときに別の失敗になる
- **スプリアスハンドラはEOIを送らない。** PICの規約と違う点であり、`eoi_action_for`が実装によって答えを変える実例そのものである
- 値は下位4ビットが`F`のもの（`0xFF`など）を採る。古いCPUではSVRの下位4ビットが1に固定されていた経緯があり、慣例としてそちらが安全である。採る値と理由は設定する段で書く

**上の要求は3件とも決着済みである。** 上の記述はS2-aを終えた時点のもので、残してあるのは経緯を辿れるようにするためである。ベクタの移動と値の選択（`0xFF`）はS2-bで行った（「スプリアスベクタを予約例外ベクタの外へ移す（S2-b）」）。IDTゲートは元から256本すべてがpresentだったので新設は要らず、**それが例外スタイルのスタブを指していた点**と**EOIを送らない判定**はS2-d-1aで閉じた（「スプリアスベクタをIRQスタイルのスタブへ載せる（S2-d-1a）」）。

**LAPICのISR/IRRは8本ずつ読み戻せた**（OR値はISR / IRRとも`0x00000000`）。**これは「読み戻せる」ことしか示さない。** 読んだのはハンドラの外なのでISRが0なのは当然である。sti-checkの項目7（ハンドラがEOIを発行）の格上げには**ハンドラの中で**読む必要があり、S2-aはハンドラに触っていない。**判定はS2-d-1以降で行う。** ExtINT配送の割り込みはLAPICのISR / IRRに載らないと考えられる（8259からのベクタはINTAサイクルでCPUへ渡り、LAPICは追跡しない）ため、IO-APIC配送が始まるまでハンドラ内で読んでも0しか見えない見込みである。**これは推論であって実測ではない。S2-d-1で確かめること。**

**I/O APICのMMIOは実際にデコードされる。S1-cの積み残しが閉じた。**

| 対象 | 実測値 |
|---|---|
| ID レジスタ | `0x00000000`（bits 27:24 = ID 0） |
| Version レジスタ | `0x00170020`（version `0x20`、Max Redirection Entry = 23） |
| redirection entry 0から23 | すべて low = `0x00010000` / high = `0x00000000`（マスク済み、vector 0、destination 0） |

**Max Redirection EntryはMax LVT Entryと同じ罠を持つ。** SDMはこれを**エントリの個数から1を引いた値**と定義しているので、23は24本を意味する。名前を`max_redirection_entry`にして生値を持ち、個数は別に出している。

**デコードの判定は根拠を2つ独立に取る。** versionレジスタが未デコードの見え方（全0 / 全1）でないこと、およびIDレジスタが名乗るIDがMADTの名乗ったIDと一致することである。**片方だけでは弱い。** 全0のページでもIDは0に見えるので、MADTのIDが0の環境ではIDの一致だけでは未デコードと区別できない。出所が別（MMIOとファームウェアの表）なので、2つそろえば偶然の一致になりにくい。この判定は検査項目`apic-decode-test ioapic-decodes`が毎回見る。**マーカーに実測値そのもの（`0x00170020`）を書いていない。** 構成が変われば動く値をマーカーにすると、何を主張していた検査なのかが読めないまま落ちる。

**24本はPICの16本を超えている。** S0-aで`check_masks`をスライス受けにし、`managed_vectors`が本数を返さない形にしたのは、この数のためである。**先回りが実測で裏付けられた。**

**S2-aは破壊featureを足していない。** 読むだけの段で、写像や読み経路が壊れる形はS1-cの`apic-test-wrong-target`が既に覆っている。代わりに既定ビルドの判定行に一致を取ることで、読み経路の回帰を`--full`が捕まえる形にした。

### S2で変わってよい起動ログの行（S2-bで作った一覧）

**この一覧は恒久的な除外リストではない。** 上の「起動ログを変更前後で突き合わせるときに除外するもの」は、ティック数や実アドレスのように**毎回変わる値**を挙げたもので、性格が違う。こちらは**S2で一度だけ変わる行**の一覧である。**隣に置くので、区別を明示しないと恒久的な除外として読まれ、将来の照合が緩む。**

**失効条件。** S2-d（PIC / PITからLocal APIC / IO-APICへの切り替え）が完了し、各行が実際に変わった時点でこの節は役目を終える。**そのとき節を消さず、「変わった記録」へ書き換える**（行を消さず状態を書き換える。`coding-standards.md`の「記録の更新」）。変わらなかった行が残っていれば、それは想定が外れたということなので、理由を書く。**S2完了後もこの一覧が「変わってよい」のまま残っていたら、それは更新漏れである。**

変わってよい行（出力側）

| 行 | 何がPIC / PIT固有か |
|---|---|
| `pic: IMR before remap …` | IMRの2バイト |
| `pic: programmed …` | master / slaveのベクタ範囲と「ICW2 is write-only」 |
| `pic: IMR after remap …` | 同上 |
| `pic: IMR after unmasking IRQ0 …` | 同上 |
| `pic: IMR after unmasking IRQ1 …` | 同上 |
| `pit: channel 0 set to …` | 分周値 |
| `pit: IMR after configuring the PIT …` | IMRの2バイト |
| `sti-check 4`（PIC remapped）とsummaryの該当行 | ICW2が読み戻せないという前提ごと消える |
| `sti-check 5`（IRQs without a handler are masked）とsummaryの該当行 | 読む対象がIMRからredirection entryのmaskビットへ変わる |
| ハートビートの`PIC ISR=`欄 | master / slaveの区別が消える |

**このうち検査が一致を取っているのは3件である**（実測。xtaskをgrepして確認した）。

| 検査 | 依存しているマーカー |
|---|---|
| `interrupt-test timer` | `pic: IMR after unmasking IRQ0 master=0xfe slave=0xff` |
| `interrupt-test alt-offset` | 同上 |
| `interrupt-test no-eoi` | `pit: channel 0 set to divisor=11932` |

禁止マーカー側にも2件ある。`the PIC vector offset (ICW2) is wrong`と`configuring the PIT changed the interrupt mask`である。**S2-dでこれらを問いベースへ移す。** 移す先は`MaskCheck::matches`の結果と、`TimerSetup::requested_hz` / `TimerSetup::actual_millihertz`である（S2-bで公開した問い）。

### 境界の整備（S2-b）

**振る舞い不変の段である。既存のログ行を1文字も変えていない。** 実測で確かめた（下記）。

**`TimerSetup`と`MaskCheck` / `ObservedMasks`を、列挙子で実装差を持つ形にした。** 分周値はPITの語彙でLocal APICタイマには無く、IMRの2バイトという形はIO-APICのredirection table（実測で24本）では成り立たない。**2つ目の実装が来ても列挙子を1つ足すだけで済み、既存の腕とその`Display`は触らないので、PIC / PITの出力する文字列は変わらない。** 振る舞い不変のリファクタを2度行わずに済ませるための形である。

- **trait の関連型にしない。** 切り替えが**実行時**に起きるためである。S2-dは起動の途中でPITからLocal APICタイマへ移る。関連型にすると呼び出し側が実装ごとに総称化され、実行時の切り替えを跨げない
- **trait object にしない。** 値として返して保持したいためである

**実装に依存しない問いを公開した。** `TimerSetup::requested_hz`と`TimerSetup::actual_millihertz`である。S2-dでマーカーを問いベースへ移すときの移し先になる。**一致ではなく許容幅で見るのは後者である**（整数の分周や初期カウントを使う以上、要求どおりぴったりにはならない）。

**`mask_all()`を足した。** `init()`の全マスクを流用していない。`init()`はICW1からICW4を書く初期化で、S2で要るのは無効化である。**副作用が一致することを理由に流用すると、後から読んだ人が「なぜ移行の途中で初期化するのか」を毎回考えることになる。** PCAT_COMPATが立っている（実測で確定）ので需要は既にある。**使うから足すのであって、将来のために足すのではない。**

**`irq_for`のスレーブオフセットへの暗黙依存を閉じた。** 以前は`MASTER_VECTOR_OFFSET .. +16`という1つの連続範囲で見ており、スレーブ = マスタ + 8を仮定していた。マスタとスレーブの範囲を別々に見る形へ変えたので、スレーブがマスタ + 8でなくても正しい。**現行の2構成（通常の`0x20`/`0x28`と`alt-offset-test`の`0x30`/`0x38`）では結果が以前と一致する**ので、振る舞いは変わらない。**依存の実体は`kernel/src/idt/mod.rs`ではなく`kernel/src/irq/mod.rs`にあった**（`idt::pic_irq_for`は`usize`を`u8`へ狭めるラッパにすぎない）。S0-aで計算が`irq`へ移ったときに、保留項目の出典欄が追随していなかった。

**trait化はS2-bでは行っていない。** S0-aが「実装が2つになるまではモジュール集約でよい」と決めており（`roadmap.md`のS0-a）、S2-bの時点で実装はまだ1つ（PIC / PIT）である。2つ目が現れるのはS2-d-1なので、切るのはそこである。方向だけ決めてある。`Controller`（unmask / mask_all / end_of_interrupt / is_spurious / check_masks）と`TimerSource`（configure_timer）の2本にする。**「LAPICタイマがLAPICの一部である」のは実装の事情であって責務ではない**ので、1つの型が両方を実装すれば済む。1本に畳むと、IO-APICが「タイマ源でもある」ことを強いられる。**APIC側の`Controller`はIO-APIC（マスク）とLAPIC（EOI・spurious）の2デバイスにまたがるファサードになる**ので、PIC側が1デバイス1実装だったのとは形が違う。**2つ目を書くときに初めて正しい形が見える。**

**振る舞い不変の段の到達条件は、こう書くこと。** 「起動ログが1文字も変わらないこと」では足りない。**行の追加も変化である**ので、条件を満たしているのに満たしていないと読めてしまう。正しくは次である。

- **既存の行が1つも変わらないこと**
- **追加された行を全件挙げられること**

**これは人が行う照合であって、検査項目ではない。** `--full`が緑でもこの条件は担保されない。手順は次である。**数値を一律に潰さないこと。**

- ハートビート行（回数が実行時間で変わる）とxtask自身のエピローグを除く
- **変わる値を「名前で」潰す。** `median=`・`spread=`・`descriptors_len=`・空きフレーム数のように、除外リストに挙がっているフィールドだけを置換する
- 実アドレス（`0x…`）は一律に潰してよい

**`s/[0-9]+/N/g`のように全ての数値を潰す形は採らないこと。** S2-cで一度その形で書いて気づいた。較正の行には変わる値（`median=`）と**変わってはいけない構造的な記述**（`divide by 16`、`window 10 PIT tick(s) at 100 Hz`、`5 sample(s)`）が同居しており、**一律に潰すと分周を32に変えても窓を5ティックに変えても照合が素通りする。** さらにその行を`grep -v`で丸ごと落としていたので、二重に広かった。**「安全条件を危険より広く書かない」の、照合手順への適用である。**

**この手順で、S2-bとS2-cの主張を検証し直した。以前の主張は実際より強かった。**

| 段 | 以前の主張 | 直した手順での実測 |
|---|---|---|
| S2-b | 変わった既存行 0 / 追加 3 | **変わった既存行 2** / 追加 3 |
| S2-c | 変わった既存行 0 / 追加 4 | **変わった既存行 2** / 追加 4 |

**広すぎる正規化を使っていたのはこの2件だけである**（`s/[0-9]+/N/g`を含む手順を書いたのがS2-bのコミット、直したのがS2-cのコミットである）。それ以前の段の照合手順はこの記述の対象外なので、ここで訂正するのはS2-bとS2-cの2件に限る。

**見えていなかったのは、どちらも`kernel entries=`の行である。**

| 遷移 | イメージの増加 | ページ数 | `kernel entries` |
|---|---|---|---|
| S2-a から S2-b | `0x2000` | 2 | 3534 から 3536（+2） |
| S2-b から S2-c | `0x4000` | 4 | 3536 から 3540（+4） |

**増加ページ数と完全に一致する。** カーネルイメージの高位マッピングは4KiBページなので、イメージが2ページ増えればエントリも2つ増える。**変化は正常であり、しかも会計の突き合わせになっている。**

**したがってこの値は除外してはならない。** 潰すと、イメージ会計（`__kernel_end`）と独立にページテーブルの実体を確かめる手段が1つ消える。**「毎回変わる値」ではなく「変わるべきときに変わる値」である。** 除外リストとの区別はここで、前者は起動ごとに揺れるもの、後者は変更に応じて動くものである。

**訂正の趣旨。** 作業をやり直す必要は無い（変化は説明がつき、異常ではない）。直すのは**記録の強さ**である。「既存の行が1つも変わらなかった」は、当時の手順では**言えなかった**。

**S2-d-1bで手順を1つ足した。以後はこちらを標準とする。** 上の「変わる値を名前で潰す」は、変化を1件ずつ説明で許容していく形なので、行数が増えるほど弁明が積み上がる。**代わりに、変わってはいけない部分を名指しで比較する。** 手順は3段で、上の正規化と併用してよいが、この3段だけでも成立する。

1. **行数を種別ごとに数える。** ハートビートは実行時間で本数が揺れるので分けて数える（実測でS2-d-1bの前後は115と114で、これは正常な揺れである）。それ以外の行数が「追加した行数ぶんだけ」増えていることを見る
2. **追加した行を取り除いてからdiffを取り、hunkの種別を見る。** カーネルのログ行だけに絞ったうえで、`c`（置換）しか無く`a`（挿入）も`d`（削除）も0であることを確かめる。**これで「既存の行が1つも増減していない」が言える。** 個々の値の変化とは独立に成立する主張である
3. **判定フィールドだけを抜き出して数え上げ、完全一致を見る。** `=true` / `=false` / `: OK` / `: NG` / `ok=` / `violations…=` を全件抜き出し、ソートして数え、両者を`diff`する。**変わってよい値（アドレス・較正値・反復回数）は含まれないので、正規化が要らない。**

**なぜこちらが強いのか。** 名前で潰す手順は「潰す名前の一覧」が完全であることに依存し、一覧に無い値が変わると照合が落ちる（正しい変化でも落ちる）か、潰しすぎて素通りする。3段の手順は**変化の許容を説明で積み上げない。** 増減が無いことと判定が同じことを、値の中身と無関係に示す。実測ではS2-d-1bで置換33件が出たが、内訳の弁明を要さずに「既存行の増減0、判定フィールド完全一致」を示せた。

**この手順も検査項目ではない。** 人が行う照合である。

#### 数える前に、数える対象を定義する

**検査の会計で数が食い違うときは、たいてい数え方が複数あることが原因である。** 値が間違っているのではなく、**何を1と数えるかが合っていない。**

実例。`interrupt-test keyboard`の主張の数が、同じ検査について3通りに読めた。

| 数え方 | 数 |
|---|---|
| ソースの中の番号つきコメント（`1.` から `4.`） | 4 |
| ソースの中の合否を出す`println!` | 7 |
| **実行時に出る合否行** | 8 |

どれも間違っていない。ずれの正体は、**qemuログの確認がソース上1箇所でマーカー2つのループになっており、実行時は2行出る**ことである。同じ検査を、報告のたびに違う数え方で数えていた。

**この検査については「実行時に出る合否行」で数えると決めた。** 実際に判定される数であり、ソースの見た目に依存しないためである。

**一般則。数える前に、何を1と数えるかを決めて書くこと。** 数字だけを報告すると、読み手は自分の数え方で検算して食い違い、どちらが誤りかを判定できない。**検査項目数・ホストテスト数・主張数のいずれでも同じ混乱が起きている。**

- 検査項目数は`cargo xtask check`と`--full`が印字する総数を採る（会計行にのみ書く）
- ホストテストの数は`cargo test`が印字する数を採る
- 1つの検査の中の主張は、**実行時に出る合否行**を採る

**ループで複数回出る出力は、ソース上の1箇所ではなく出力の回数で数える。** ここが今回のずれの発生源である。

**S2-bは検査項目を増やしていない。** スプリアスは誘発手段が無く（ADR-0018 §6が同じ理由で「誘発手段が無いまま先に実装する」と決めている）、`mask_all()`が効かない形の破壊は意味を持つのがS2-d以降である。**到達条件の「一覧の行を除いてログが変わらないこと」は人が行う照合であって、検査項目ではない。`--full`が緑でもこの条件は担保されない。** 「77項目が緑だから振る舞い不変である」とは読めない。

### スプリアスベクタを予約例外ベクタの外へ移す（S2-b）

**ここがLocal APICへの最初の書き込みである。** 上の「境界の整備」は振る舞いを変えないリファクタで、ハードウェアへの書き込みを含まない。こちらはSVRを書き換えるので別のコミットに分けてある。

**スプリアスベクタを`0x0f`から`0xFF`へ移した。**

**これで危険が減ったわけではない。** `0x0f`も`0xFF`もどちらも例外スタイルのスタブに載っており、**どちらも起きればカーネルが停止する。** 移動で消えたのは「**予約例外として解釈される**」という誤診断の余地だけであって、停止そのものではない。**停止をやめさせたのはS2-d-1aである**（「スプリアスベクタをIRQスタイルのスタブへ載せる（S2-d-1a）」）。**S2-bを終えた時点では、まだ起きれば止まる状態だった。** この節を「安全になった」と読まないこと。

- ファームウェアが残した`0x0f`は**CPUの予約例外ベクタの範囲（0から31）の中にある**。Local APIC由来の割り込みを1つも構成していない今は潜在的だが、LAPICが配送を担い始めるS2-d-1より前に移す必要がある
- **read-modify-writeでbit 8を保つ。** 危険なのはbit 8であってベクタ欄ではない（S2-aの節）。書いた後に読み戻し、`software_enabled kept = true`を確かめている。実測は`0x0000010f` → `0x000001ff`
- **下位4ビットが`F`の値を採った。** 古いCPUではSVRの下位4ビットが1に固定されており、書いた値がそのまま読み戻せなかった。慣例に合わせておけば読み戻しが書いた値と食い違わない
- **IDTゲートは足していない。既にある。** IDTは256本すべてがpresentで（`idt: 256 entries, all present=true`）、`0xFF`にもスタブが入っている。**確かめたのは「足したこと」ではなく「既にあること」である**（gate type `0xe`、DPL 0を読み戻した）
- **`0xFF`は今のところ「起きたら止まる」経路にある。** `idt::init`は256本すべてを例外スタイルのスタブで埋めてから、IRQスタイルのスタブで上書きするのは`0x20`-`0x3F`とyield / syscallだけである。**`0xFF`はどれにも当たらないので例外スタイルのままで**、その先の`exception_entry`は`-> !`でレジスタを出して`halt_forever`する（ADR-0004のHalt and Dump）。したがってEOIは送られないが、**それは「スプリアスだから」でも「PIC由来でないから」でもなく、そもそも戻ってこないからである。** ベクタを`0x0f`から動かしたことで「予約例外として解釈される」問題は消えたが、**「起きたら止まる」は残っている**（**S2-d-1aで専用スタブへ載せ替えて解消した。** 上の記述はS2-bを終えた時点の状態である）

**この2つは、S2-bの最初の記述が誤っていた箇所である。** 当初は「共通ディスパッチがPICの範囲外だからEOIを送らない」と書いたが、**`0xFF`はその共通ディスパッチに届かない。** 例外スタイルのスタブへ行く。実コードを辿って正した。**「正しい振る舞いが正しい理由で成立していない」と書いたその理由自体が間違っていた**ので、記録に残す。

**S2-d-1aで直した。決着済みである。** Local APICが配送を担い始めるとスプリアスは実際に起こりうる（ADR-0018 §6はPICについて同じ理由で先に実装している）。要ったのは、`0xFF`をIRQスタイルのスタブへ載せ、**EOIを送らずに戻り**、回数を数える形である。そのまま配送を始めれば、スプリアスが1回起きた時点でカーネルが停止していた。**S2-bの時点では起こりえなかった**（Local APIC由来の割り込みを1つも構成していない）ので、S2-bでは直さずに申し送りにしてあった。**誘発手段が無いのはS2-d-1aを終えた今も同じである**ので、実際に受けて戻ることは観測していない。

### Local APICタイマの較正（S2-c）

**測るだけである。タイマとしては使わない。** LVT Timerはマスクされたままで、LAPICタイマ由来の割り込みは1本も発生しない。**LINT0とSVRのbit 8には触らない**（前後で読み戻して確認する）。

**書くのはDivide ConfigurationとInitial Countの2本だけである。** LVT Timerには触らない。マスクされているので数え下がりが始まっても割り込みは出ず、窓（100ms）はカウンタの一周（16分周・`u32::MAX`から数えて数十秒規模）より遥かに短いので、ファームウェアが残したperiodicのままでも窓の途中で再装填されない。

**呼び出し位置は`run_timer_loop`の中、`sti`の直後・定常ループの前である。**

- 基準に使う`TIMER_TICKS`はIRQ0が増やすので、`sti`より前では進まない
- `start_timer`は`-> !`で戻らず、通常起動では`run_timer_loop`も戻らない。**したがって「割り込みが有効で、かつ定常ループへ入る前」という区間はここにしか存在しない**
- **APIC関連の他の処理（`kmain`の前半）から離れているのはこの理由による。まとめないこと。** コードにも同じことを書いてある

**PITのチャネル2を使う案は検討して退けた。** チャネル2なら割り込み禁止のまま測れ、呼び出し位置も動かさずに済む。**退けた理由は「PITへ書き込まないため」ではない。** 実際の危険は「動作中のチャネル0を乱さない」ことで、チャネル2は別チャネルなのでその危険には当たらない。退けたのは、**チャネル2のモード設定とポート`0x61`のread-modify-writeという新しいデバイス操作が増え、一度きりのAPIを境界の内側へ足すことになる**からである。**「PITは触れない」という制約として読まないこと。**

**(a)を選んだ代償**（チャネル2案なら生じなかったもの）。

- **割り込みが有効な区間で測る**ので、較正窓の間にプリエンプションが起こりうる。両方のカウンタは走り続けるので測定自体は成立するが、**ティックの取りこぼしが現実の誤差源になる**
- **`interrupts.rs`に手を入れる。** このファイルは`cli`/`sti`の許可リスト検査の対象である。実測で検査の値は不変だった（7エントリ / 12箇所。編集の前後で同じ）

**窓の両端をティックのエッジで揃える。** `TIMER_TICKS`は10ms刻みなので、任意の時点でサンプルすると±1ティック = ±10msの誤差が乗る。N=10の窓なら±10%で、較正としては使えない。**変化した瞬間を捉えれば誤差はµs級へ落ちる。**

**Nは誤差の見積りから決めた。先に決めていない。** 片端の見積りは、`timer_ticks()`のポーリング粒度5µs、割り込み遅延のばらつき10µs（TCGなので大きめに見る）、Current Countの読み取り粒度1µsで**16µs**、両端で**32µs**である。

| N | 窓 | 相対誤差の上限 |
|---|---|---|
| 1 | 10ms | 0.32% |
| 5 | 50ms | 0.064% |
| **10** | **100ms** | **0.032%（採用）** |
| 20 | 200ms | 0.016% |

**較正自身の誤差が、許容幅の下限を決める。** 0.032%（320 ppm）は起動ごとのばらつきより十分小さいので、これ以上窓を伸ばして起動を遅くする理由が無い。

**取りこぼしは較正自身が数える。`max_tick_jump`は使えない。**

**一度`max_tick_jump`の前後を出す形で書いてしまった。** あれを更新するのは`run_timer_loop`の定常ループで、較正はその手前で走るので、**前後どちらを読んでも0のままである。** 「前後が同じ0だから取りこぼしが無い」と読めるが、実際は「まだ数えていない」だけで、**何も検査していない**。実測で0/0が出たときに気づいて直した。現在はエッジ待ちの関数が進み幅を返し、較正窓の中で見た最大の進み幅を出す。実測は全5起動で**1**（毎回すべてのエッジを捉えている）。

さらに、**名目のNではなく実際に進んだティック数で割る**ようにした。飛び越えた場合でも結果が正しいままになるので、**系統誤差が構造的に消える**。

**実測（既定ビルド、TCG、5回の起動）。**

| 起動 | 中央値 | 起動内のばらつき |
|---|---|---|
| 1 | 62,539,560 Hz | 376,130 Hz |
| 2 | 62,510,090 Hz | 481,990 Hz |
| 3 | 62,513,860 Hz | 125,960 Hz |
| 4 | 62,485,420 Hz | 108,550 Hz |
| 5 | 62,501,900 Hz | 113,090 Hz |

**起動をまたいだ中央値のばらつきは54,140 Hz = 865 ppm（0.0865%）である。**

**中央値を採るのは、第1標本が系統的に低く出るためである。平均ではない。** 標本の並びが取れた7起動すべてで、**第1標本は残り4件の平均を下回っていた**（不足は677 ppmから15,310 ppmまで幅がある）。**厳密な最小だったのは7起動中5回**で、常に最小とは限らない。

**機序は特定していない。** ウォームアップ（初回のエッジ待ちで分岐予測やキャッシュが温まっていない、TCGの翻訳ブロックが未生成など）が疑わしいが、**確かめていない。** `descriptors_len`が130本と132本の両方を出す件と同じ扱いで、**未特定の機序として記録する。** 「ウォームアップと見られる」で止めず、見られるが確かめていないと書く。

**中央値は実害を消すが、機序を隠す。** 第1標本を捨てる形にしなかったのは、捨てると系統的なずれが観測できなくなるためである。標本の並びをログへ出しているのはこのためで、`--calibration-spread`も並びを出す。

約62.5MHzは、16分周を戻すと約1GHzである。QEMUのLAPICタイマの基準は1GHzなので、桁は合っている。**ただしこれはTCGでの値である**（下記）。

**S2-d-2で使う許容幅の導出。**

- 較正自身の誤差の上限 320 ppm
- 起動をまたいだ中央値のばらつき 865 ppm（実測）
- 合わせて約 1,200 ppm = 0.12%

**推奨は±0.5%（5,000 ppm）である。導出は「較正自身320 ppm + 起動間865 ppm ≒ 1,200 ppm、その約4倍」である。** 数字を書き残すのは、後から「なぜ0.5%か」を再構成できるようにするためである。実測の不確かさに対して約4倍の余裕があるので、正常な起動で誤って落ちることはない。**この値はS2-d-2の破壊で確認するまで暫定である。** 破壊がこの幅の外へ出なければ幅が広すぎるので狭める。暫定と書いていない数字は確定として読まれるので、そう書いておく。**ただし広ければよいわけではない。** 許容幅は「実測のばらつきより広く、かつ壊れたときに落ちる」幅でなければならない。広すぎて落ちない幅は、検査があるように見えて何も検査していない形になる。**妥当性はS2-d-2の破壊（較正を飛ばして既定値を使う）が実際にこの幅の外へ出ることで示すこと。** 出なければ幅が広すぎるということなので、そのときは狭める。

**QEMUで測っているものの限界（観測していないことを観測したと書かない）。**

- TCG（純粋エミュレーション）でのLAPICタイマの進み方が、ホストの実時間と単純な比例関係にある保証は無い。ADR-0015 Addendumが「計測結果は絶対値ではなく比較対象との比で判断する」と既に書いている
- **したがってS2-cで確かめられたのは「較正の機構が動くこと」までである。値が実機で意味を持つかは確かめていない**
- **`--kvm`で走らせた場合の較正結果も測っていない。** 既定はTCGで、KVMでの挙動は未観測である
- 実機での妥当性は、実機で動かす段が来たときに見る

**`--calibration-spread`は検査項目ではない。** 起動を繰り返して較正値を並べて出すだけで、合否を判定しない。**手で5回回して記録する形を採らなかったのは、手動確認が再現されず必ず腐るからである**（`-smp 2`の確認を検査項目にしたのと同じ判断）。ここでは合否を決められないので検査項目にはできないが、**手順だけはコマンドとして固定した。** したがって`--full`の項目数は増えない。

### 待ちループでの読みには可視性が必須である

**`scheduler`の記録（volatileの3フィールド）とは機構が違うので、並べて書く。**

- `scheduler`の`iterations` / `resumes` / `switches`は**volatile**である。あの記録は「会計が成立するのは書き手が止まっているからである」で終わっており、**待ちループの場合を扱っていない**
- `TIMER_TICKS`のほうは**アトミック**である（`AtomicU64`。読み出しは`load(Ordering::Relaxed)`。`kernel/src/idt/mod.rs`）

**待ちループで条件を読むときは、素の読みにしないこと。** 素の読みだと、コンパイラが読みをループの外へ持ち上げてよく、持ち上げられると値が永久に更新されずに無限ループになる。volatileでもアトミックでも持ち上げは起きないが、**普通の読みでは起きうる。**

S2-cの較正はこの形の待ちループを持つ（`TIMER_TICKS`のエッジを待つ）。**既存の`run_timer_loop`が既に正しい形だったので、同じアクセサ（`idt::timer_ticks()`）を使うだけで済んでいる。** 危険が成立しなかったのは偶然ではなく、アクセサが最初から正しいからである。

**併せて、待ちループには上限を付けること。** 既存の`run_timer_loop`はTSC基準の期限を持ち、来なければ停止する。較正側も同じ形で期限を持ち、閉じなければ較正を諦めて報告する（停止はしない。S2は情報を集める段の延長である）。

### Interrupt Source Overrideの解決（S2-d-0）

**実測（既定ビルド）。** MADTのInterrupt Source Overrideは5件で、中身は次である。

| source IRQ | GSI | flags | 極性 | トリガ |
|---|---|---|---|---|
| 0 | **2** | `0x0000` | active high（バス既定） | edge（バス既定） |
| 5 | 5 | `0x000d` | active high | **level** |
| 9 | 9 | `0x000d` | active high | **level** |
| 10 | 10 | `0x000d` | active high | **level** |
| 11 | 11 | `0x000d` | active high | **level** |

`0x000d`は`0b1101`で、極性（bits 1:0）が`0b01` = active high、トリガ（bits 3:2）が`0b11` = levelである。**バス既定（`00`）と明示指定の両方が実在する**ので、「既定はISAならアクティブハイ・エッジ」という解釈が効く経路と、明示が来る経路の両方をホストテストで固定してある。

**S2-dの設計の前提と突き合わせた結果、1つ合い、1つ外れていた。**

- 合っていた: **IRQ0がGSI2へ移る。** 典型例として挙げた前提は、この構成で実際にそうであった
- 外れていた: 「ISOが5件あるので配送の切り替えに効く」と書いたが、**S2-d-1が移すキーボード（IRQ1）にはISOが無い。** 5件はIRQ 0 / 5 / 9 / 10 / 11 で、IRQ1を含まない。したがってキーボードは恒等（GSI1）で、redirection entryの添字も1である。**S2-d-1のISO処理は1件も適用されない**

さらに**IRQ0のISOもS2-d-2では使われない。** S2-d-2はタイマをLocal APICタイマへ移すので、IRQ0をI/O APIC経由で配送しない。**ISOが効くのは「レガシーIRQをI/O APIC経由で配送する」場合だけである。**

**この実測により、見立てていた破壊が1つ成立しなくなった。**

前回の見立てには「**ISOを無視してirq=gsiとする → 該当IRQが届かない**（ISOが5件あるので実測で差が出る構成である）」があったが、**括弧の中が実測で否定された。** キーボード（IRQ1）にISOが無い以上、無視しても恒等で同じ結果になる。**この破壊は何も壊さず、しかも緑になる。** 「壊したつもりで緑」であり、緑なので誰も気づかない。**この見立ては撤回する。**

**採った対処は「破壊を落とし、示せる範囲だけを主張する」である。**

- **ISOの解決関数そのもの**（純粋関数）はホストテストで閉じてある。バス既定と明示指定の両方、および恒等へ落ちる場合を固定した
- **その関数が配送経路で効いていること**は、**この構成では実機で観測できない。** IRQ1に適用されるISOが存在しないためである
- 合成のISO（例: IRQ1→GSI5）を注入する案は採らない。**注入した側が「真」になるので、何を証明したことになるかが曖昧になる。** 観測できないことを観測できないと書くほうが、注入で作った状況から結論を引くより強い
- IRQ0をI/O APIC経由で配送する構成を一時的に作る案も採らない。S2-d-2の方針（タイマはLocal APICへ）と衝突する

**代わりに、表が読めていることの実行時の証拠は残す。** 起動時に`gsi_for_irq(0)`と`gsi_for_irq(1)`の解決結果をログへ出す。非恒等の枝が実在すること（IRQ0→GSI2）はここで見える。**ただしこれは「表が読めている」ことであって「配送経路で効いている」ことではない。** 区別して書くこと。

### スプリアスベクタをIRQスタイルのスタブへ載せる（S2-d-1a）

**配送は1つも変えていない。** PIC / PITのままである。S2-d-1を3つに分けたうちの最初で、あとの2つがtrait化（S2-d-1b、振る舞い不変）とIO-APICへの切り替え（S2-d-1c、配送が変わる）である。分けた根拠は、S2-bでスタブを1本足すだけの作業が罠を2つ踏んだことにある。同じコミットへ積むと、落ちたときに切り分けられない。

**S2-bの申し送り（`0xFF`は起きたら止まる）を閉じた。** 専用スタブ`zaytos_spurious_stub`を置いて`zaytos_irq_common`へ合流させ、`irq_entry`がこのベクタを名指しで判定し、EOIを送らずに戻る。

**EOIを送らない判定を明示にした。** S2-bまでこのベクタにEOIが送られなかったのは「PICの担当範囲の外だから」であり、スプリアスだからではなかった。S2-d-1cでLocal APIC由来のベクタが増えると、その偶然の一致は壊れる。**偶然で成立している振る舞いを、問いの形へ置き換えたということである。**

**回数はPICのスプリアス（IRQ7 / IRQ15）とは別のカウンタで数える。** 機序が違い、合流させるとハートビートを見たときにどちらが起きたのか分からなくなる。

**この経路は実行時に一度も通っていない。** Local APIC由来の割り込みを1本も構成していないので、スプリアスはまだ起こりえない。**確かめたのは配置と判定の静的な正しさまでで、実際に割り込みを受けて戻ることは観測していない。** 誘発手段が無いのはADR-0018 §6がPICについて書いているのと同じ事情である。

**`push`の符号拡張を、アセンブラの選択に任せずバイトで固定した。** `push imm8`は64ビットへ符号拡張されるので、`0xff`をimm8で積むと`-1`になる。スタブ表の中のベクタ（`0x20`-`0x40`）はどれも`0x80`未満なので、この問題は今まで現れなかった。**実測の逆アセンブル**は次で、上位3バイトが0のimm32である。

    ffffffff8012da70 <zaytos_spurious_stub>:
    ffffffff8012da70:  68 ff 00 00 00     push $0xff
    ffffffff8012da75:  eb 09              jmp  zaytos_irq_common

**測ったのはdebugビルドである**（`target/x86_64-unknown-none/debug/kernel`）。`cargo xtask`が起動に使うのはこちらで、releaseビルドではアドレスが違う（実際に一度releaseで測っており、条件の違う成果物を測る形になっていた。「同じ条件で比べていないものを比べた」の系列である）。**アドレスは構成で動くが、`68 ff 00 00 00`というバイト列は動かない。** 主張はバイト列のほうにある。

**`zaytos_irq_stubs_end`と`zaytos_spurious_stub`は同じアドレスである**（実測でどちらも`0xffffffff8012da70`）。表の末尾が既に16バイト境界にあるため、あいだの`.p2align 4`が何も進めないことによる。**`check_irq_stub_table`の範囲判定は半開区間（`handler >= end`を表の外とする）なので、スプリアスのスタブを表の中と誤認しない。** 表の大きさも`0x210`（33本 * 16バイト）のままで変わっていない。**シンボルが重なること自体は正しさの根拠ではない。** 境界が動けば重なりは消えるので、**この記録は現時点の実測であって不変条件ではない。**

**イメージの端（`__kernel_end`）は1バイトも動いていないが、コードは増えている。** 起動ログの`kernel image 0x100000..0x1b62d0`はf0373f3と同じ値で、**これを「増加0バイト」と読むと誤る。** 区別はセクションの大きさで取る（`readelf -S`）。f0373f3と比べて`.text`が`0x66d34`から`0x66e34`へ**256バイト**、`.rodata`が`0x17fc7`から`0x17fd7`へ**16バイト**増えており、`.data`と`.bss`は不変である。`.bss`の開始が4KiB境界で、手前の増加がその量子に収まったので端が動かなかった。**比較はf0373f3をworktreeへ取り出して同じdebug構成でビルドして行った**（作業ツリーには触っていない）。

**起動ログの変化は2件である。**

- `apic: vector 0xff is still on the exception-style stub …`（WARN）が、スタブと判定の現状を述べるINFOへ変わった
- ハートビートに`lapic_spurious=`欄が増えた

**どちらも検査のマーカーではない**（xtaskをgrepして確認した。ハートビートの照合は`heartbeat: ticks=`の前方一致で、欄の追加に影響されない）。

### コントローラのtrait化と2つ目の実装（S2-d-1b）

**振る舞い不変の段である。配送はPIC / PITのままで、切り替えていない。**

**到達条件を満たした。** 既存の行が1つも増減せず、判定フィールドが完全一致し、追加された行は1行である（手順は上の「振る舞い不変の段の到達条件」の3段。実測はハートビート115から114、それ以外303から304、カーネルのログ行はhunk 33件すべてが置換で挿入も削除も0、判定フィールドは完全一致）。

**`Controller`と`TimerSource`の2本を切った。** 分けたのは、「LAPICタイマがLAPICの一部である」のが実装の事情であって責務ではないためで、1本に畳むとIO-APICが「タイマ源でもある」ことを強いられる。

**`Controller`の実装は2つ**（`Legacy` = 8259 PICと8254 PIT、`Apic` = Local APICとIO-APIC）。**`TimerSource`の実装は1つのままである。** Local APICタイマ側はS2-d-2で足す。**単一実装のtraitはS0-aの「実装が2つになるまでtraitを切らない」の例外である**ので、そう書いてある（`kernel/src/irq/mod.rs`のモジュールdoc）。遅らせなかったのは、2本のtraitを責務で対にして決めたためで、片方だけ遅らせると`configure_timer`だけがモジュール関数として残り公開面がもう1種類増える。

**列挙子は置いていない。** dispatchが最終的に列挙子になること（関連型では実行時の切り替えを跨げず、trait objectは値として返せない）は変わらないが、切り替えの無いこの段で置くと選ばれない腕を先回りで作ることになる。**S2-d-1cで入れる。そのとき「どちらが有効か」は実行時に可変なstaticになり、割り込みハンドラ（EOIの経路）から読まれる。** 素の`static mut`にしないこと。守り方はS2-d-1cの設計で決める。

**2つ目の実装を1回だけ読ませた。** 較正の直後にIO-APICのredirection entryのマスクビットを読み、観測を1行出す。**書き込みはしない。** 呼ぶ理由は、どこからも呼ばずにS2-d-1c（配送が変わる段）へ入ると、そこで落ちたときに「切り替えが悪いのか実装が悪いのか」を切り分けられないためである。**振る舞いが変わらないうちに、読めることだけを確かめておく。** S1-cで「写像したうえで読んで確かめた」のと同じ形である。

    apic: the I/O APIC controller reads its redirection entries:
      entries=24 masked=0x0000000000ffffff (expected 0x0000000000ffffff)
      [read back from hardware], all masked=true

`entries=24`はVersionレジスタのMax Redirection Entry 23に1を足した本数で、S2-aの実測と一致する。`0xffffff`は下位24ビットが全部1、すなわち24本すべてマスクである。

**期待にPICのマスク状態を持ち込んでいない。** IRQ0とIRQ1はPIC側で開いているが、IO-APIC経由では1本も配送していないので、redirection entryは全本マスクのままであるべきである。**別のコントローラの状態を混ぜない。**

**マスクの状態は256ビットのビットマップで持つ。** Max Redirection EntryはVersionレジスタの8ビット欄なので、entryは最大256本である。**取りこぼしが起こらない幅**を選んである。語をまたぐ位置（63 / 64 / 255）はホストテストで固定した。

**`dead_code`は出なかった。** 呼ばれるのは`Apic::new`と`check_masks`だけで、`unmask` / `mask_all` / `end_of_interrupt` / `is_spurious`は誰も呼んでいないが、**traitのimplブロックの中のメソッドは`dead_code`の対象にならない**ためである。lintが出るかどうかと、2つ目の実装を1回読ませることの価値は独立なので、出なくても読ませる形を採った。

**この段で実行していない経路を明示する。**

- `Apic`の`unmask` / `mask_all` / `end_of_interrupt` / `is_spurious`は**一度も実行していない**。書き込み経路は動かしていない
- **IRQからGSIへの解決（`entry_for_irq`）も一度も通っていない。** `check_masks`へ渡すIRQが空だからである。**S2-d-1cの到達条件に「実際に通ること」を入れてある**（`roadmap.md`。`irq::mask_all()`と`smp::trampoline_frame()`と同じ扱いである）。通らないまま終えると、「解決表を通している」という設計上の主張が実行で裏付けられないまま残る

**境界の非対称が1つ残った。** S0-aの「IMRへの書き込みは境界の内側だけに存在する」は、**PICについては真だが、IO-APICについては偽である。** redirection entryの読み書きは`crate::apic`にあり、割り込み層の外である。可視性の静的検査は`kernel/src/irq/`の内側だけを見るので捕まらない。レジスタの配置を知るモジュールを1つに保つほうを優先した結果で、到達範囲は`pub(crate)`まで狭めてある。解禁条件つきで`deferred-decisions.md`へ置いた。**記録済みの「境界の公開関数が生の値を返す形は捕まらない」とは性質が違う。** あちらは境界自身の公開関数、こちらは別のモジュールが境界の持ち物を公開している形である。

### キーボードの配送をIO-APICへ切り替える（S2-d-1c）

**配送が変わる段である。振る舞い不変ではない。**

**キーボード（IRQ1）だけを移した。タイマ（IRQ0）は8259経由のままである。** したがって**中間状態が実在する**——同じカーネルの中で、EOIの宛先がIRQごとに違う。

**配送先ベクタを`0x21`から`0x42`へ変えた。理由は2つあり、どちらか片方では足りない。**

- **観測。** `0x21`のままだと、届いたことが配送経路の証拠にならない。8259経由でもIO-APIC経由でも同じベクタで届くので、`keyboard: first key arrived as vector 0x21`は移行の前後で同じまま通り、**何も新しいことを示さない。** 8259が出しえないベクタで届けば、到達がそのまま経路の証拠になる
- **構造。** ベクタからIRQを引く経路がPICの採番表に依存していた。同じベクタを使うとその依存が残ったまま動いてしまう。**動く理由が正しい理由でなくなる**

**ベクタ番号の選択は、優先度クラスの選択でもある。** x86ではベクタ番号を16で割った値が優先度クラスで、`0x21`はクラス2、**`0x42`はクラス4**である。したがってこの移行で**キーボードがタイマ（`0x20`、クラス2）より高い優先度になった。** 実害は無い見込みで（ゲートは割り込みゲートなので入れ子は起きず、TPRは0でどのクラスも遮断していない）、実測でも異常は出ていないが、**自明ではないので書いておく。** S2-d-2でタイマを`0xFE`（クラス15）へ移すと同じ性質の副作用が起きる。

**`pic_irq_for`はEOIの入口ではなく、IRQ処理全体の入口だった。** ベクタからIRQを引く関数が`Some`を返したときにだけ入るブロックの中に、ティックの加算もキーボードのハンドラ呼び出しも入っている。**引けなければハンドラごと呼ばれない。** PICの採番表しか見ない`irq_for`（`const fn`。`TIMER_VECTOR`が`const`項目なので消せない）とは別に、移行済みの表も見る実行時関数`irq_for_vector`を足し、`pic_irq_for`を`irq_for_vector`へ改名した。

**移行状態はIRQ単位で持つ。単一の状態では成立しない。** 単一の状態をAPICへ倒した瞬間、タイマ割り込みのEOIがLAPICへ送られ、8259はEOIを受け取らない。**タイマが止まる。** ビットマップ（`AtomicU32`）と配送先ベクタの表（`AtomicU8`×16）で持ち、読みは割り込みハンドラから、書きは起動時の切り替え1回である。**素の`static mut`にしない。**

**切り替えの3操作は割り込み禁止区間で囲う。** 状態そのものはアトミックだが、「PICでマスク → 状態を立てる → IO-APICで解禁」の途中で割り込みが入ると、古い状態でEOIを送る経路が成立する。**アトミック1つでは足りない。**

**検査項目は増やしていない。** 既存の`interrupt-test keyboard`が実際にキーを送り（QEMUのmonitorの`sendkey`）、`--full`に入っている。その中の主張を3つから7つへ増やした。

| 主張 | 見るもの |
|---|---|
| 期待した文字列になる | デコードまで通っている |
| **`0x42`で届く** | **到達。8259が出しえないベクタなので経路の証拠になる** |
| **旧ベクタ`0x21`で届いたキーが無い** | **二重配送の検出。移行前は区別できなかった** |
| **entryのベクタ欄が書いた値である** | **設定の検出経路** |
| **entryのマスクが外れている** | **解禁の検出経路** |
| 送った本数と受け取った本数が一致する | 取りこぼしなし（EOIが効いている） |
| 会計が閉じている | 経路の取り違えなし |

**ベクタ欄とマスクビットを別々に見る。** 最初は1つの主張に畳んでいたが、**マスクを外し忘れた構成で「設定が書けていない」と読めてしまい、2つの経路が独立していることを示せなかった**（実測で気づいて分けた）。分けたことで、`skip-unmask`の破壊が「ベクタは正しい・マスクだけ落ちる」と出るようになった。

**破壊は4つ作り、3つを残した。予測は2つ外れた。**

| 破壊 | 予測 | 実測 |
|---|---|---|
| `ioapic-wrong-vector` | 読み戻しと到達の両方が落ちる | **予測どおり** |
| `ioapic-skip-unmask` | 読み戻しは通り到達だけ落ちる | **予測どおり**（主張を分けた後） |
| `ioapic-legacy-spurious` | 誤判定でEOIが送られず、以後届かなくなる | **外れた。何も壊れずPASSした** |
| `ioapic-keep-pic-irq1` | 二重配送が旧ベクタで観測できる | **外れた。二重配送に至る前に止まる** |

**`ioapic-legacy-spurious`は撤回した。** 予測は「移行済みのIRQで8259のISRを読むと、ビットが立っていないのでスプリアスと誤判定する」だったが、**`pic::is_spurious`はIRQ7とIRQ15以外ではISRを見ずに`false`を返す。** IRQ1では読んでも判定が変わらない。**何も壊さず緑になる破壊は置かない**（S2-d-0でISOの破壊を撤回したのと同じ扱いである）。

**したがって、`is_spurious`の移行状態による分岐は、現在の構成では観測可能な効果を持たない。** 残してあるのは、所有していないコントローラのI/Oポートを割り込みハンドラの中で読まずに済むことと、IRQ7かIRQ15を移した場合には実際に判定が変わることによる。**「必要だから入れた」ではなく「今は効果を観測できない」と書く。**

**`ioapic-keep-pic-irq1`は残したが、何を検出しているかが予測と違う。** この破壊が示すのは「**二重配送に至る状態へ進むことを拒否する**」であって、「二重配送が起きたら検出できる」ではない。**別の主張である。** 二重配送に至る前に、**`sti`前の項目5のほうが先に落ちる**（8259のIMRが`0xfc`で、移行後の期待値`0xfe`と食い違う）ので、カーネルは割り込みを有効にせず停止する。**予測より早く、より強い。** ただし「1本も届かない」だけを見ると原因を問わず通るので、**`sti`を拒否した痕跡も主張に加えた**（`refused to sti`）。**どこで止まったかを名指ししない破壊は、壊れ方を区別できない。**

**二重配送そのものは依然として未観測である。** 起こす手段が無いので、「起きたときに検出できるか」はこの破壊では何も言えない。**観測していないことを観測したと書かない。**

**破壊featureの名前は壊し方を指しており、検出されるものを指していない。** `ioapic-keep-pic-irq1`は「PIC側のIRQ1をマスクしない」という壊し方の名前で、他の破壊featureと命名が揃っている。**名前から検出内容を推測しないこと。** 何が検出されるかは上の記述にある。

**`sti`前の項目5の期待値を、移行状態から作るようにした。** 移行後は8259側でIRQ1が**マスクされているのが正しい。** 固定で「IRQ0とIRQ1が開いているはず」と期待すると、**正しい状態でこの検査が落ちる**（実際に落ちた。最初の実行で`refusing to sti`になって気づいた）。

**`sti`前の項目4は主題を書き直したが、格上げしていない。** 旧「PIC remapped to 0x20-0x2F」はPIC固有の主題だったので、「割り込みの配送先ベクタが意図どおりに設定されている」へ変えた。**状態はUNVERIFIABLEのままである。** IO-APICのredirection entryは読み戻せるが、**タイマはまだ8259を通っており、そちらのICW2はwrite-onlyである。** 全経路が読み戻せるのはPICが消えるS2-d-2で、格上げはそこで行う。

**`KEYBOARD_VECTOR`を`PIC_KEYBOARD_VECTOR`へ改名した。** `vector_for(1)`から導く`const`項目で、配送が`0x42`になると**名前が事実と合わなくなる。** 現在の配送先は実行時に決まるので`delivery_vector()`を足した。名前が事実と食い違ったまま残るのは、このリポジトリが繰り返し直してきた型である（`pic_irq_for`の改名と同じ理由）。

**S2-d-1bで書いて未実行だった経路が、この段で実際に通った。** `Apic::entry_for_irq`（IRQからGSIへの解決）、`Apic::route`、`Apic::unmask`の3つである。**ただし`entry_for_irq`が通ったことは「解決表が効いている」ことの証明ではない。** IRQ1にISOが無いので結果は恒等で、無視する実装に差し替えても同じ答えになる（S2-d-0の記録どおり、この構成では実機で示せない）。

### S2-d-2で使うベクタ番号（S2-d-0で確認した）

**Local APICタイマには専用のベクタを与える。** 現在のLVT Timerはファームウェアが残した`vector 0x20`で、`TIMER_VECTOR`と同値である。同じままだと、移行の瞬間にどちらの源（PIT経由のIRQ0か、Local APICタイマか）から来たかがログで区別できない。「PICを全マスクせずに移行」という破壊確認も、二重配送を数でしか観測できず弱くなる。**源が観測できないと、破壊が破壊になっているかを示せない。**

**現在使われているベクタを数え上げた。**

| 範囲 | 用途 |
|---|---|
| `0x00`-`0x1F` | CPU例外 |
| `0x20`-`0x40` | IRQスタイルのスタブ表（33本）。**`alt-offset`ビルドではPICが`0x30`-`0x3F`を使う** |
| `0x40` | `TEST_VECTOR` |
| `0x41` | `YIELD_VECTOR` |
| `0x80` | `SYSCALL_VECTOR` |
| `0xFF` | `SPURIOUS_VECTOR`（S2-b） |

**空いているのは`0x42`-`0x7F`と`0x81`-`0xFE`である。採るのは`0xFE`とする。** スプリアスの`0xFF`と隣り合い、どちらもスタブ表の外なので専用スタブが要る点も同じで、扱いが揃う。**`alt-offset`ビルドのPIC（`0x30`-`0x3F`）とも衝突しない。**

**`TIMER_VECTOR`の`const`制約（区分D）には触れない。** あれが`const`項目なのは`irq::vector_for(0)`（PICの採番）から導いているためで、Local APICタイマのベクタは別の定数として置けばよい。`SPURIOUS_VECTOR`を`0xFF`の定数にしたのと同じ形である。

**S2-d-2の順序。** 次の順で行う。

1. **新ベクタのスタブとハンドラを用意する**（ハンドラが無い状態でマスクを外すと、最初のティックで停止する）
2. **PICを全マスクする**（`irq::mask_all()`。二重配送を避ける）
3. **LVT Timerのマスクを外す**

**2と3を逆にすると二重配送が起きる。** 別ベクタを採るのでEOIの宛先の曖昧さ自体は消えるが、順序は依然として重要である。

**S2への申し送り（S1-b-2の実測）。** MADTのFlagsは`0x1`で、**PCAT_COMPATが立っている。** この系にはデュアル8259があるという意味なので、Local APIC / IO-APICへ移る前にPICをマスクする必要があることは確定している。Local APICは`0xfee00000`、IO-APICは`0xfec00000`（IDは0、GSIベースは0）で、いずれもMADTから得た値である（既定値のハードコードではない）。Local APIC Address Overrideのエントリは無かった。**Interrupt Source Overrideが5件ある。** S1では記録だけで解釈していないので、レガシーIRQとGSIの対応（IRQ0がGSI2へ移る形など）はS2で解釈すること。

**S3への申し送り（テーブル読み取りバッファの限界）。** MADTは概ね`44 + N×8`バイトなので、**100コア規模で1KiBの読み取りバッファを超え、「検証不能」に落ちる。** ZaytOSがその規模を扱う日は遠いが、限界が存在することを知らずに踏むのとは違う。超えたときはチェックサムを検算していないので中身を使わない、という扱いのままである。

**`ReadError`の5区分のうち、実機で到達させているのは2つである。** `OutsideWindow`と`NotMapped`は上記の破壊featureで到達する。`Aliased`は窓の登録値を壊す必要があるが、その破壊（`paging-test-directmap-wrong-base`）はA-2の検証で先に停止するのでここへは届かない。`Untranslatable`は1GiBページに当たった場合で、ZaytOSは1GiBページを作らないため到達手段が無い。**「到達手段が無い」と「足していない」を混ぜない。**

**S1-b-1の時点で、実機では正常系しか通っていない。** 未マップの物理を踏んだときの検出、署名・チェックサム・長さの破れの検出は、いずれもホストテストで判定側を閉じただけである。実機での破壊確認はS1-b-2の破壊featureで行う。`ReadError`の5区分のうち`OutsideWindow`と`NotMapped`は、RSDPの物理アドレスを故意に差し替える破壊featureで到達できる（S1-b-2で検討する）。`Aliased`は窓の登録値を壊す必要があるが、その破壊（`paging-test-directmap-wrong-base`）はA-2の検証で先に停止するのでここへは届かない。`Untranslatable`は1GiBページに当たった場合で、ZaytOSは1GiBページを作らないため到達手段が無い。

### タイマをLocal APICタイマへ移す（S2-d-2）

**配送が変わる段である。振る舞い不変ではない。** これでS2の移行が閉じ、**8259経由の通常の配送は1本も残らない。**

**タイマはPITで起動し、較正の後に初めてLAPICへ移る。** この順序は選択ではなく制約である。較正の基準は`TIMER_TICKS`で、それを増やすのはPIT経由のIRQ0だから、較正は`sti`の後・PITが動いている間にしか成立しない。**したがって「起動直後はPIT、途中からLAPICタイマ」という2区間が必ず存在する。** 下の`alt-offset-test`の項がこの帰結を扱う。

**切り替えの順序は4段で、割り込み禁止区間で囲う。**

1. LAPICタイマを設定する（**LVTはマスクしたまま**）
2. 【区間開始】8259を全マスクする（`irq::mask_all()`）
3. 移行状態（`TIMER_ON_LAPIC`）を立てる
4. LVTのマスクを外す【区間終了】

1でマスクしたまま設定するのは、ベクタが載る前に満了させないためである。**2と4が逆だと両方が開いて二重にティックが来る。** 区間を囲う理由は、マスク直前に飛び込んだ最後のPITティックの扱いを確定させることである。囲わないと「全マスクした直後・LVTを開ける前」にハンドラが走って8259へEOIを送る。**そのEOI自体は無害だが、区間の中で何が起きたかを後から説明できなくなる。**

**この区間ではティックが1本も来ない。** したがって**区間の中で`TIMER_TICKS`を待つ処理を挟むと戻ってこない。** 較正がエッジ待ちを使うので、順序を誤れば実際に起こりうる。較正はこの関数より前に済ませてある。

**移行状態を`ROUTED_TO_APIC`に乗せなかった。** LAPICタイマはIO-APICではなくLVT経由で、**IRQ番号を持たない。** IRQ0のビットを立てて表すと、ビットマップの意味が「IO-APIC経由である」から「PICでなくなった」へ静かにずれる。別の器（`TIMER_ON_LAPIC`）で持つ。**したがって`ROUTED_TO_APIC`に立つのは今もIRQ1の1本だけである。**

**dispatchは3形態になった。** LVT由来のベクタ（タイマ`0xFE`とスプリアス`0xFF`。**ベクタで名指しに判定し、IRQ番号へ変換しない**）、IO-APIC経由のIRQ（`irq_for_vector`が移行済みの表から引く。EOIはLAPIC）、8259経由（**通常の配送は無いが、スプリアスIRQ7だけは`0x27`で届きうる**）である。**判定はLVT由来を先に見る。** 後ろに置くと、このベクタがPICの採番表に当たる構成で誤る。現行の2構成（`0x20`-`0x2F`と`0x30`-`0x3F`）では当たらないが、依存を残さない。

**`init()`（PICの再マップ）は呼び続ける。飾りではない。** 既定の採番だとIRQ7が`0x0F`（予約例外）に落ちるので、スプリアスIRQ7のために再マップが必要である。**「PICを使わない」と「PICを設定しない」を混ぜない。**

**ベクタの割り当てはこの段で確定した。** 上の「S2-d-2で使うベクタ番号（S2-d-0で確認した）」は計画時点の一覧で、**空き範囲の記述はその時点のものである**（`0x42`はS2-d-1cでキーボードが、`0xFE`はこの段でタイマが埋めた）。現在の割り当ては次のとおりで、**空きは`0x43`-`0x7F`と`0x81`-`0xFD`である。**

| ベクタ | 用途 |
|---|---|
| `0x00`-`0x1F` | CPU例外 |
| `0x20`-`0x40` | IRQスタイルのスタブ表。**`alt-offset`ビルドではPICが`0x30`-`0x3F`を使う** |
| `0x40` | `TEST_VECTOR` |
| `0x41` | `YIELD_VECTOR` |
| `0x42` | キーボード（IO-APIC経由。S2-d-1c） |
| `0x80` | `SYSCALL_VECTOR` |
| `0xFE` | タイマ（LAPICタイマ。S2-d-2） |
| `0xFF` | `SPURIOUS_VECTOR` |

**`0x20`-`0x40`の外へ置くベクタは専用スタブが要り、`dedicated_stubs()`の一覧に足す必要がある**（忘れれば起動時の検査が落ちる）。**`push imm8`は符号拡張されるので、`0x80`以上のベクタはバイトを明示して`imm32`を固定する**（`0xFE`が`-2`になる罠で、`0xFF`と同じ形である）。

**ベクタ番号の選択は、優先度クラスの選択でもある。** `0xFE`はクラス15で、**タイマが最上位クラスになる。** S2-d-1cでキーボード（`0x42`、クラス4）がタイマ（`0x20`、クラス2）より高くなったのが、ここで逆転する。実害は無い見込みで（割り込みゲートなので入れ子は起きず、TPRは0）、実測でも異常は出ていないが、**自明ではないので書いておく。**

**分周を較正の戻り値に含めた。規律ではなく構造で塞いだ。** `median_hz`は「この分周設定のもとで数え下がる速さ」であって、分周が変われば意味を失う。周波数と分周を別々に持つと、**較正を16分周で行って運用を別の分周で設定する**という罠が開く。同じ構造体で運び、片方だけを持ち出せない形にしてある。`calibrate_timer`が返すのは**実際に`write_lapic`へ渡した値そのもの**で、定数を再掲していない（再掲すると片方だけを変えたときに食い違う）。

**カーネル側の許容幅は較正の誤りを検出できない。**

これがこの段で最も重要な記録である。起動時の判定が比べているのは「要求周波数」と「較正値と初期カウントから導いた実効周波数」で、**どちらもカーネルの内側の値である。** 初期カウントは較正値を要求周波数で割って出すので、較正値が2倍になれば初期カウントも2倍になり、**比は`100.000 Hz`のまま一致する。** 整数の割り算で生じるずれは捕まるが、較正値そのものの誤りは**自己無矛盾のまま通る。**

**PITは今マスクしたので、カーネル内にはもう独立の時間基準が無い。** したがってこの検査はホスト側に置くしかない。`lapic-timer-test`が、ハートビートの報告する経過秒とホストで測った実時間の比を見る。許容幅はカーネル側の±0.5%より大きく取ってある（QEMUの実行が実時間に対して一定の比で進む保証が無く、起動処理やホストの負荷も混ざる）。**ここで見たいのは桁が合っているかであって、較正の精度ではない。**

**S2-cが暫定としていた±0.5%は、この段で確定した。** 破壊（`scaled-calibration`）は幅の外へ出る。**ただし出る先はカーネル側の判定ではなくホスト側の比である。** S2-cは「破壊がこの幅の外へ出ることで妥当性を示す」と書いていたが、**その幅の側では出ない。** 上の自己無矛盾がその理由で、S2-cの見込みが外れた点として記録する。

**検査は4件で、`--full`に入る（`--lapic-timer-test <kind>`）。**

| kind | feature | 何を見るか |
|---|---|---|
| `rate` | なし（既定ビルド） | ホストの実時間との比が幅の内にあること |
| `scaled-calibration` | `lapic-timer-scale-calibration-test` | 較正値が初期カウントへ実際に流れていること |
| `wrong-divide` | `lapic-timer-wrong-divide-test` | 較正時と運用時で分周が揃っていること |
| `no-mask-all` | `lapic-timer-no-mask-all-test` | 8259が全マスクされていること |

**`scaled-calibration`は空振りしうるので、適用の痕跡を必須にしてある。** 較正が呼ばれない構成ではフックが踏まれず、**壊したつもりで緑になる。** 適用したことをログへ出し、出ていなければxtask側で落とす。ACPIの未マップ破壊で採ったのと同じ形である。

**遅くなる向きの破壊は「ハートビートが1本も出ない」形で現れる。** 測定窓の中に1本も入らないためで、**「測れなかった」で片づけると、壊れていることを検出できたのに落としてしまう。** 幅の外へ出ると宣言した構成に限り、これを幅の外の一形態として扱う。ただし起動そのものの失敗と区別するため、切り替えが実際に起きたことを併せて見る。

**`no-mask-all`は速さの比では捕まらない。** 名指しの検査（切り替え直後のIMRの読み戻し）が落ちて停止する。**これは`irq::mask_all()`が実際に呼ばれていることの裏返しの証明でもある。** S2-bで書いてからS2-d-2まで呼び出し元が無く、`pub`だから`dead_code`にもならなかった。**S2の到達条件に入れていた項目がここで閉じた。**

**破壊は、守っている構造ごとに要る。落ちる場所が同じでも構わない。**

`wrong-divide`の検出経路は`scaled-calibration`と同じ（ホストの実時間との比）である。**それでも残す。** 主張が違うからである。`scaled-calibration`は「較正値が初期カウントへ流れること」を、`wrong-divide`は「較正時と運用時で分周が揃うこと」を守っている。**後者を守っているのは分周を戻り値に含める構造であって、前者とは別の構造である。**

**これは基準の書き換えである。** 旧基準は「検出経路が同じなら落とす」だった。この段で`wrong-divide`を落とすかどうかを判断する際に、経路の同一性は主張の同一性を意味しないことが分かった。**新基準は「破壊は、守っている構造ごとに要る。落ちる場所が同じでも構わない」である。**

**基準を書き換えても、過去の判断は覆らない。** これを併記するのは、基準の変更が遡って効くと誤読されないためである。

- `skip-calibration`（較正を飛ばして既定値を使う）を落とした判断は**新基準でも正しい。** あれは`scaled-calibration`と同じ構造を守っており、別の構造を守っていなかった
- `ioapic-legacy-spurious`を撤回した判断も**新基準でも正しい。** あれは経路が重複していたのではなく、**何も壊していなかった**（`pic::is_spurious`はIRQ1ではISRを見ない）

**落とす基準は「経路が重複しているか」ではなく「守っている構造が重複しているか、あるいは何も壊していないか」である。**

**`alt-offset-test`は撤去しない。以前の「S2-d-2で意味を失う」という判断は、前提が誤っていた。**

以前は「PICが消えればICW2の検査は意味を失う」と見込んでいた。**PICは配送から消えたが、起動直後の窓では消えていない。** 上のとおりタイマはPITで起動して較正の後に移るので、**最初のティックは今も8259経由で届く。** `first_pic_vector()`が記録するのはその窓のベクタで、`alt-offset`ビルドでは`0x30`になる。**この検査は今もICW2の書き込みが効いていることを検証している。**

**やることは撤去ではなく、この検査が動いているビルドを正確に書くことである。**

**`interrupt-test`系のビルドでは切り替えが1度も起きない。** `interrupt-test-timer`の経路は`start_timer(logger, console, STOP_AFTER_TICKS, None)`を呼び、**APICを`None`で渡す**（`kernel/src/main.rs:2786`）。既定ビルドの呼び出し（同`1500`）は`mapped_apic.as_ref()`を渡すので、こちらだけが較正と切り替えを行う。したがって`alt-offset`・`timer`・`no-eoi`のいずれのビルドでも、

- 較正が走らない（`apic: LAPIC timer calibration:`の行が出ない）
- 切り替えが起きない（`lapic-timer:`の5行が1つも出ない）
- **タイマは最後までPIT経由の8259配送である**
- キーボードもIRQ1のまま8259に残る（`ioapic: no I/O APIC was mapped`）

実測で確認した（`target/interrupt-test-serial.log`に`lapic-timer:`が0件、`apic: LAPIC timer calibration:`も0件、`ioapic: no I/O APIC was mapped`が出ている）。**既定ビルドとの区別は`heartbeat`の`max tick jump`にも出る**（既定は256、`interrupt-test`は2。較正がメインループを止めるかどうかの差である）。

**したがって`alt-offset-test`の覆う範囲は、S2-d-2で変わっていない。** このビルドではPICが配送から消えないので、3つのマーカーはいずれもM4-d-2当時と同じものを示している。

| マーカー | 何を示すか | S2-d-2での変化 |
|---|---|---|
| `pic: IMR after unmasking IRQ0 …` | IMRが2バイトという形 | なし |
| `timer: first tick arrived as vector 0x30` | ICW2の書き込みが効いていること | なし |
| `interrupt-test: timer OK` | **8259経由のハンドラがEOIを発行していること** | なし |

**「意味が狭まった」という一段前の記述は誤りだったので撤回する。** 狭まったのではなく、**この検査が最初から別のビルド構成を見ており、その構成はS2-d-2の変更が届かない場所にある。** 「切り替え前の窓を覆う」という言い方も正確ではない。窓ではなく、切り替えが存在しないビルドである。

**この誤りは「同じ条件で比べていないものを比べた」の再演である。** マーカーの前後関係を**既定ビルドの起動ログで**調べ、その結論を`alt-offset`ビルドへ当てはめた。既定ビルドでは確かに`lapic-timer:`の5行が`timer: first tick arrived`より前に出るが、**`alt-offset`ビルドにはその5行が存在しない。** イメージ会計でサボタージュ付きビルドを測った件と同じ型で、**今回は「起動ログから取る」を守っていたのに、どのビルドの起動ログかを取り違えた。**

**それでも一般則としては生きている記述がある。** 既定ビルドでは`timer: first tick arrived as vector 0x20`が切り替えの5行より**後**に出るが、`first_pic_vector()`が値を記録したのは較正中（切り替え前）である。**行が出るのは後だが、行が述べている観測は前の出来事である。** 下の事例節に一般則として書いた。

**突き合わせ先の分類を誤った件は、これとは別に実在する。** e2dfc4bで`first_pic_vector()`の突き合わせを`timer_delivery_vector()`へ分類したとき、両者は同値だったので誤りが観測できなかった。S2-d-2で既定ビルドの値が`0x20`と`0xFE`に分かれて初めて顕在化し、実際に落ちた。**現在は`PIC_TIMER_VECTOR`と突き合わせている。**

**`sti`前の項目4は、恒久的にUNVERIFIABLEである。到達条件から外すが、項目そのものは消さない。**

S2-d-1cは「PICが消えるS2-d-2で格上げする」と書いた。**格上げできない。順序の制約による。**

較正はPITのティックを要するので`sti`の後でなければ走らず、切り替えは較正の後でなければならない。**したがってこの検査点では、タイマは必ずまだ8259経由である。** 8259のICW2はwrite-onlyなので読み戻せない。**これは実装の不足ではなく、検査点の位置とハードウェアの性質から出る帰結である。** 段を進めても閉じない。

**項目を消さないのは、覆われていない範囲を記録に残すためである。** 「検証済みの6項目と検証不能の1項目」は、「7項目すべて検証済み」とは違う主張である。消すと後者に見える。

**代わりに何が覆っているかを明示する。** 設定の読み戻しは、それぞれの設定箇所で行っている。

| 経路 | 読み戻し | 場所 |
|---|---|---|
| IO-APIC経由（IRQ1） | redirection entryのベクタ欄とマスク | ルーティング直後 |
| LVT（タイマ） | LVT Timerのベクタ・マスク・periodic | 切り替え直後 |
| 8259（ICW2） | **読み戻せない** | `alt-offset-test`が外から示す |

**「その検査点では検証できない」を正直に持てるのが3状態設計（`Verified` / `Failed` / `Unverifiable`）の値であり、ここで報われている。** `true`に丸める設計だと、この項目は「格上げした」と書かれて終わっていた。

**この段で実行していない経路と、未確認のまま残るものを明示する。**

- **`Apic::entry_for_irq`の非恒等の枝は今も実行されていない。** IRQ1にISOが無いので結果は恒等である。タイマはIRQ番号を持たないのでこの経路を通らない。**S2-d-0の記録どおり、この構成では実機で示せない**
- **`sti`前の項目7（ハンドラがEOIを発行）は、LAPICタイマについて破壊で確かめていない。** 切り替え後もティックが増え続けることは既定ビルドで実測しているので、**発行していることの証拠はある。** 欠けているのは「落としたら止まる」側である。**`no-eoi-test`は`cfg`の箇所としてはLAPICタイマのEOIも落としている**（`kernel/src/idt/mod.rs:814`と`:865`の2箇所）**が、この経路は実行されない。** 理由は較正の失敗ではなく、**`interrupt-test`系のビルドがAPICを`None`で渡すので切り替えが1度も起きないこと**である（上記`alt-offset-test`の節）。ベクタ`0xFE`が発火しないので、`:814`の`cfg`は到達しない。**つまりこの破壊featureは、2箇所を落としているように見えて、実際に落ちているのは8259側の1箇所だけである。** LAPICタイマの割り込みはLAPICのISRに載るので、ハンドラ内でISRを読めば機序を直接観測できる見込みだが、**実現可能性は未検証である**
- **二重配送そのものは依然として未観測である。** `no-mask-all`は「二重配送に至る状態へ進むことを拒否する」ことを示すのであって、二重配送が起きたときに検出できることは示さない（S2-d-1cの`ioapic-keep-pic-irq1`と同じ）

**起動ログの変化は5行の追加である。** いずれも`lapic-timer:`で始まる（設定、LVTの読み戻し、8259の全マスクの読み戻し、許容幅の判定、配送先ベクタの宣言）。既存の行では`timer: waiting for the first tick`の期待ベクタが`0x20`のまま（この時点ではまだPIT経由なので正しい）である。

### APIC MMIOを写像する前提（S1-c）

**写像するのはLocal APICとIO-APICのMMIOだけである。** ACPIテーブル本体は`EfiACPIReclaimMemory`に載っていて既に写っているので、足すものは無い（上節）。APIC移行そのもの（S2）、AP起こし（S3）、per-CPU、IPIは実装していない。**割り込みはPICのままである。**

**粒度が4KiBであることは、そう書いたからではなく構造でそうなる。** 写像は`ActivePageTable::map_4kib`を通す。この関数には2MiBへ昇格する経路が存在しないので、「意図せず2MiBで張ってしまう」形をここに書けない。確認するのではなく不可能にする、の適用である。

**ページテーブル構築時の`extra`へ足す形は採らなかった。理由は2つある。**

- **順序が合わない。** `extra`を組み立てるのはページテーブルを作る時点だが、APICのアドレスが分かるのはMADTを読んだ後である。前へ動かすには、ACPI走査をdirect map窓の高位化より前へ移すことになり、走査の下限（物理を読むのに窓が要る）と衝突する
- **`MappedRanges::build`の隣接結合を通ってしまう。** 結合はキャッシュ属性が同じ隣接範囲をまとめるので、**将来`0xFEC00000`や`0xFEE01000`に隣接するMMIO記述子を出すファームウェアでは、結合された範囲の2MiB整列した核がhugeへ昇格しうる。** 実測の構成では起きないが、**起きない理由が「今のファームウェアがそう出すから」になる。** 構造と観測の区別で言えば観測に寄りかかった形であり、`map_4kib`を通せばその依存が消える

**アドレスはハードコードしない。** Local APICはMADT固定部の`local_apic_address`、IO-APICはMADT type 1の`address`から取る。Local APIC Address Override（type 5）があればそちらが固定部より優先される（実測の構成にはtype 5は無い）。

**MMIOを読む前に`IA32_APIC_BASE`（MSR `0x1B`）を見る。ENビットだけでは足りない。**

- **EN（bit 11）が落ちていればAPICは無効**で、MMIOに触ると`#GP`になる
- **EXTD（bit 10）が立っていればx2APICモード**で、**このときMMIOによるアクセスは無効化されている。** x2APICではLocal APICをMSR経由で触るので、やはり`#GP`になる。「ENが立っているから読める」は成立しない
- 判定は「EN=1かつEXTD=0のときだけ読む」。EXTD=1だった場合は報告して読まない（x2APIC対応はS2以降の話である）
- BSP（bit 8）も同じMSRにあるので記録する。S3の入力になる

**MSRとMADTが食い違ったら、読まないだけでなく写像もしない。** 「MADTのアドレスにLocal APICが無いかもしれない」と判断した直後にそのアドレスをPCDで写像すると、後段が「写っているのだから正しいのだろう」と読む余地を作る。**正当化できない写像を残さない。** S1は情報を集める段なので、食い違いという情報が得られた時点で目的は達している。なお**MSRのベースはbit 12以上（MAXPHYADDRまで）なので、比較の前にマスクする。** 桁を間違えると常に食い違って見える。マスクの生成は純粋関数（`interpret_apic_base`）に切り出してホストテストで固定した。`rdmsr`はCPL 0でしか実行できず、読み取りそのものはホストで走らせられないためである。

**汎用の`read_msr`は公開しない。** 生のMSR番号と生の64ビット値を外へ出すと、ビット位置の知識が呼び出し側へ散る。公開するのは解釈済みの`ApicBase`（`enabled` / `x2apic` / `bootstrap_processor` / `base`）だけで、ビットの意味は1か所に集まる。S0-aの`irq`、S1-bの`acpi`と同じ方針である。

**写像の前後で`translate`を撮る。** 前が「翻訳なし」、後が「期待の物理」という対にしてある。**この対が、破壊featureを使わずに「写像が実際に何かを変えた」ことの観測になる。** 後の側は翻訳の有無だけでなく、**翻訳が当の物理を指していること**まで見る。指していることを見ないと、別の物理を指す翻訳でも通る。

**`AlreadyMapped`は失敗とは限らない。** 別のファームウェアがこの領域を`EfiMemoryMappedIO`として出せば、`classify()`が`ReservedButMapped { cacheable: false }`にするのでdirect mapが2MiBのhugeで既に覆っている状態になりうる。これを一律にエラー扱いすると、その環境で不必要に失敗する。**`translate`で期待の物理を指していることを確かめ、指していれば「既に写っている」として先へ進む。** 指していなければエラーである。上の隣接結合の議論と根が同じなので、扱いを揃えてある。

**到達条件の観測はVersionレジスタで行う。IDの一致では足りない。** BSPのAPIC IDは0であり、MADTが名乗る値も0なので、**IDの突き合わせは両辺とも0になる。** この比較は「シフトを忘れた（IDはビット31:24にある）」「ゼロ埋めのページを読んだ」「読みがLocal APICへ届いていない」のいずれでも通ってしまう。**退化した検査である。**

そこでVersionレジスタ（オフセット`0x30`）を併読する。ビット7:0がversion、ビット23:16がMax LVT Entryで、**非ゼロで構造のある値**なのでゼロページや未マップと区別がつく。読み取り専用で副作用も無い。実測は`version_raw=0x00050014`、すなわちversion `0x14`、Max LVT Entry 5であった（統合APICのversionは概ね`0x10`から`0x15`）。**Max LVT Entryは個数ではない。** Intel SDMはこれを**LVTエントリの個数から1を引いた値**と定義しているので、5は「5個」ではなく「エントリ番号の最大が5」＝6個を意味する。生の値をそのまま持ち、名前を`max_lvt_entry`にして事実へ合わせた（`max_lvt_entries`と書くと個数を1つ少なく主張することになる）。+1して個数として持つ形は、どこで+1したかを追う必要が出るので採らない。`0x00`と`0xFF`はそれぞれ「何も無いところを読んだ」「デコードされていないMMIOを読んだ」の典型的な見え方なので、この2値はエラーとして報告する。IDの突き合わせは残してあるが、**「IDが一致したから届いている」とは読まないこと。** この比較が意味を持つのはIDが0でないコアが現れるS3以降である。コード側にも同じ注意を書いてある。

**IO-APICは写像するが読まない。** IO-APICのレジスタを読むにはIOREGSEL（オフセット`0x00`）へ書いてからIOWIN（`0x10`）を読む必要があり、**それは書き込みである。** セレクタであって割り込みの設定ではないと主張はできるが、書き込みであることは事実なので、「読むだけで設定は変えない」という到達条件に対して一貫させるためこの段では避けた。**したがってIO-APICのMMIOが本当にデコードされるかはS2まで未確認である。** ここで確かめられているのは翻訳が張られたことだけで、それは`translate`が見ている。**観測していないことを観測したと書かない。**

**S1-cの破壊feature 3種は、検出経路ごとに分けてある。**

| feature | 壊すもの | 捕まえる経路 |
|---|---|---|
| `apic-test-skip-map` | 写像そのものを省く | 「張った後」の`translate`が翻訳なしを見る |
| `apic-test-wrong-target` | 写像先の物理だけを稼働中のPML4へ差し替える | 「張った後」の`translate`が期待と違う物理を見る |
| `apic-test-base-mismatch` | MADTが名乗るアドレスを1ページずらす | MSRとの突き合わせが食い違いを見る |

`wrong-target`は**翻訳が張られる**ので、「翻訳がある」だけを見る検査では通ってしまう形である。禁止マーカーに`still has no translation`を入れて、`skip-map`と同じ経路で止まっていないことを確かめている。`base-mismatch`は突き合わせで止まるため**写像そのものへ到達しない**ので、禁止マーカーに`apic: mapped the local APIC`を入れてある。差し替え先をリテラルで持たないのはS1-b-2と同じで、`wrong-target`は稼働中のPML4（必ず存在し、必ず写像済みで、APICでないことが確実）を実行時に読む。

**`wrong-target`の手法は破壊専用である。通常経路へ持ち込まないこと。** これが作るのは**同一物理ページに対するメモリ型の異なる別名**である。PML4のフレームは本流のdirect map窓からWBで写っているので、そこへPCDの写像を重ねることになる。x86では同一物理ページに異なるメモリ型の別名を張ることは未定義の領域である。サボタージュビルド限定で、直後の照合が検出して読みへ進まないため破壊の手段としては成立するが、**便利な手筋として通常の写像経路へ再利用しないこと。** 静かな不具合の温床になる。

**破壊確認していない分岐を明示する。** 「Versionが`0x00`または`0xFF`」の分岐には到達手段を用意していない。写像が正しければ実際のAPICが応答し、写像が誤っていれば手前の`translate`の照合が先に捕まえるためである。**「到達手段が無い」と「足していない」を混ぜない**の適用で、この分岐は前者ではなく**後者に近い**（原理的に不可能ではなく、そのためだけに写像の照合を無効化する破壊を足すことになるので割に合わない、という判断である）。

**S2への申し送り（可視性の静的検査の対象）。** `kernel/src/apic.rs`は検査の対象へ加えていない。**単一ファイルで`pub mod`/`use`/`type`を持たないので、加えても破壊が作れない。** 破壊を作るには先に構造を変える必要があり、それは「検査があるように見えて何も検査していない」を1件増やすことになる。**加えるべきなのはS2で`apic/`がサブモジュールを持つ形になったときである。** そのとき対象へ加え、S1-b-1と同じ2形（`pub mod`と`pub use`）で破壊確認をすること。**構造を変えるときに対象への追加が落ちないよう、ここに書いておく。**

**フレーム会計。** 写像で消費したフレームは**2枚**であった（実測。`50992`→`50990`）。導出は次のとおりで、予測と一致している。

- 窓のVAは`DIRECT_MAP_BASE + phys`。`DIRECT_MAP_BASE = 0xFFFF_8000_0000_0000`
- Local APIC `0xfee00000` → VA `0xffff8000fee00000`、IO-APIC `0xfec00000` → VA `0xffff8000fec00000`
- PML4添字はどちらも256、PDPT添字はどちらも3（`0xfec00000 >> 30 = 3`、`0xfee00000 >> 30 = 3`）
- PD添字は502（`0xfec00000 >> 21 = 2038`、`2038 & 511 = 502`）と503（`2039 & 511 = 503`）
- **PDPTとPDは既に在る。** 実測のメモリマップにある`EfiMemoryMappedIO`の記述子`0xffc00000`（4MiB）が同じGiB（添字3）に入っており、PD添字510と511を2MiBのhugeで占めている。したがって新たに要るのはPT 2枚だけである
- 恒等側には張らない。恒等（`PML4[0]`）はB-2bで除去済みなので、張る先は窓の1つだけである

`0xffc00000`の記述子が無いファームウェアでは、PDとPDPTも要るので+4になる。**この予測は起動ログで確認すること。予測を記録に書かない。**

### SMPで既存の検査がどう変わるか（S1からS6の申し送り）

複数コアになると、既存の検査のうちいくつかは「通るが意味が変わる」状態になる。着手時に気づけるよう、実コードで確認した範囲を記録する。

- **QEMUのコア数は検査の構成軸になる。** 現在xtaskは`-smp`を渡していない（既定1コア）。`-smp 1` / `2` / `4`を回すことになるが、QEMUを起動する項目をすべて3構成にすると項目数が3倍になり所要時間もそのまま3倍になる。**どの項目を3構成で回すかの基準を先に決めること**（例: per-CPUデータに触る / スケジューラに触る / 割り込みに触る）。基準がないと選び方が恣意的になる。項目数が変われば会計行も更新する。
- **割り込みの会計はコアごとの帰属を失う。** `INTERRUPT_COUNTS`（ベクタ別カウンタ）は共有の`AtomicU64`配列で、`TIMER_TICKS`も大域である。複数コアでは合計としては閉じるが、「どのコアが受けたか」は分からなくなる。ハートビートをper-CPUへ広げるかをS3の到達条件と併せて決める。
- **`task-preempt-in-critical`が見ているものが変わる。** 現在は「同一コアで`critical`区間にプリエンプトが食い込み二重取得を検出する」を見ている。複数コアではBKLの本来の競合は「別コアが同じロックを取る」形になる（`deferred-decisions.md`の該当行）。
- **per-CPUデータの置き場所が破壊featureを壊しうる。** `highhalf-remove-verify-fail`はサボタージュVA`0xffff808000000000`（`PML4[257]`）が空であることに依存している。per-CPUデータを`PML4[257]`へ置くとこの破壊が意味を失う。置き場所を決めるときにサボタージュVAの移動をセットで扱う。
- **BKLで確かめるのは排他だけではない。** 恒等除去のような不可逆な操作ではないので復帰経路は要らないが、失敗の形が「デッドロックして静かに止まる」になる。安全性（カーネル内の同時進入数が1）と進行性（全コアが進んでいる）の両方を見て、待ちがタイムアウトしたら無言で継続せず原因を出すこと。

### 公開前の監査

公開リポジトリに、実装内容と無関係なもの（個人メモ、作業ログ、意図せず混入した一時ファイル）が残っていないかを確認する。
次の順序で行う。

1. `git ls-files`と`git rev-list --all --objects`の**全件を目視**し、想定外のファイルが無いか確認する。ビルドや実行に不要なものが混ざっていないかを見る
2. 非ASCIIファイル名の検出（`grep -P '[^\x00-\x7F]'`）。日本語名の一時ファイルは意図せず混入しやすい
3. **ファイル内容の文字種検査。** 追跡対象ファイルと未コミットの変更を対象に、非ASCII文字をUnicodeブロック別に集計し、想定外のものが無いか確認する。想定しているのは、ひらがな・カタカナ・CJK統合漢字・CJK記号句読点・半角全角形・矢印・罫線素片・数学記号・`§`のみ。想定するブロック以外が現れたら、その所在を確認する

   ファイル名だけを見ても内容の混入は分からない。見た目が同じでもコードポイントの異なる字が紛れうるので、目視ではなくブロック別に機械的に集計する
4. 現在の追跡ファイルと全履歴パスの差分を取り、削除・改名されたものを洗い出す
5. **その後に**キーワード検索を行う

**キーワード検索は補助であって主ではない。**
パターンに含まれないものは見つからないため、検索の「出力なし」は、そのパターンに含まれていない対象については何も証明しない。
まず全件を見ること。

あわせて、全コミットメッセージと著者・コミッタ情報、ライセンス表記も確認する。

いずれも「間違えても即座には落ちず、しばらく動いた後に壊れる」性質を持つ。
落ちた時点と原因の距離が遠いため、書いた直後に確認する価値が最も高い。

マイルストーンへ到達した時点でも同じ確認を行う。
これは変更の種類ではなく時点だが、区切りごとに全体を見直す機会として扱う。

上記以外の純粋ロジック・ドキュメント・テスト・ビルドスクリプトの変更は、この扱いの対象外である。
