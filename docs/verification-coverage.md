# 主張と検査の対応

ZaytOSの文書は「常にこうである」「必ずこうする」と書いている性質をいくつも持つ。
このファイルは、その主張ごとに対応する検査があるかどうかを並べたものである。

作った動機は、`cargo fmt`と`cargo clippy`が2日間ずっと未達だったことに気づかなかった経験である。
原因は個々の見落としではなく、維持していることを確認する手順がどこにも無かったことだった。
主張だけがあって検査が無い状態は、時間が経つほど気づきにくくなる。

`deferred-decisions.md`とは役割が違う。
あちらは「いつか判断する項目」、こちらは「主張と検査の対応表」である。

状態の区分は次の3つ。

- 検査あり: 機械的な検査があり、破れば落ちる
- 測定のみ: 値は測っているが、違反しても止まらない
- 検査なし: 対応する検査が無い

---

## 1. 検査なし

現時点で違反は確認していないが、破っても誰も気づかない。

### 1.1 割り込みハンドラは何も出力しない

出典: ADR-0018 §5、`architecture.md` §6.8

観測はカウンタ越しに行い、ハートビート1行へ集約する設計である。
ハンドラの中から`Logger`を呼んでいないことは検査していない。

足すなら、ハンドラの関数本体に`logger`や`write!`が現れないことを見る形になる。
ハンドラの範囲を機械的に決めにくいのが難点で、現状は費用に見合わないと判断している。
M5-dでハンドラからスケジューラを呼ぶようになると、ハンドラ内で呼べるものの範囲が広がるため、その時点で再検討する。

### 1.2 画面とシリアルの両方へ出す場合はシリアルを先に書く

出典: ADR-0013、ADR-0017、`architecture.md` §6.7

`log_both`の実装がその順序になっているだけで、呼び出し側が別の順序で書くことを妨げるものは無い。
画面出力が壊れたときにシリアルだけは残る、という保証がこの順序に依存している。

足すなら、`log_both`以外から`Console`へ直接書く経路が無いことを見る形になる。

### 1.3 IRQの解禁は1箇所へ集約する

出典: ADR-0018、`architecture.md` §6.8

IMRを触る箇所が増えていないことを検査していない。
解禁が散らばると「どのIRQがいつ開いたか」を追えなくなる。

足すなら、`pic`モジュールの外からIMRの書き込み関数を呼んでいないことを見る形になる。

### 1.4 ページテーブルでNXを立てない

出典: `architecture.md` §6.6、`kernel/src/paging/table.rs`

EFER.NXEを有効にしていない段階でNXを立てると、予約ビット違反のページフォルトになる。
稼働中テーブルの読み戻しはPCDと恒等性は照合するが、NXは見ていない。

同じ節の「PSビットはPDレベルのみ」は、`translate()`がPDPTレベルのPS=1を`UnsupportedGiantPage`として弾くため、実質的に検査されている。

足すのは容易で、読み戻しの照合にビット63を加えるだけである。
M5-eで権限の細分化に入るときに、NXの扱いを決めるのとあわせて足すのが自然である。

### 1.5 ターゲットの既定値への依存

出典: `architecture.md` §5、§5.1

kernelは`x86_64-unknown-none`の`disable-redzone`と`+soft-float`に依存している。
red zoneが有効に戻ると、割り込みが入った瞬間に呼び出し元のローカル変数が壊れる。
§5.1は「rustflagsやターゲットを変更した際は、この確認をやり直すこと」と書いているが、やり直しを促す仕組みは無い。

stableでは`--print target-spec-json`が使えないため、確認は生成コードを読む形になり、機械化しにくい。
`.cargo/config.toml`と`rust-toolchain.toml`が変更されたときに気づける形にするのが現実的である。

## 2. 検査あり

### 2.1 ビルド・テスト・静的解析

`cargo xtask check`が12項目を実行する。

| 項目 | 内容 |
|---|---|
| build | bootloader（`x86_64-unknown-uefi`）/ kernel（`x86_64-unknown-none`）/ common / xtask |
| test | `cargo test --workspace`（289件） |
| clippy | 上記4構成すべてに`-D warnings` |
| fmt | `cargo fmt --all -- --check` |
| unsafe | `unsafe`ブロックの直前のコメント塊に`SAFETY`があること（追跡済みと未追跡の両方が対象） |
| コミット | コミット件名に和文と英数字の間の半角空白が無いこと（規約を適用し始めた日時以降が対象） |

`cargo xtask check --full`は、これに回帰チェック14種（例外4種、critical 2種、interrupt 6種、keyboard、panic）を加える。

`--full`は、xtaskが「起動しなかった」と判定した項目に限り、自動で1回だけ再試行する。
テストの失敗（実装の問題）では再試行しない。落ちるものは落ちたまま報告する。
1回に限るのは、回数を増やすと「何度も失敗したが最後に通った」状態を成功として扱うことになるためである。
再試行したことは都度出力し、最後に件数と項目名をまとめて出す。

**基準線は0件である。1件でも出たら異常の兆候として扱う。**
この再試行は当初、OVMFがまれに起動に失敗する既知の事象への対処として入れた。
ところがその事象は環境要因ではなく、varstoreを使い回していた自作の不具合だった（`troubleshooting.md` 2026-07-22）。
直した後は0件が続いている。
したがって現在の位置づけは「頻繁に起きることへの対処」ではなく「起きないはずのことが起きたときの保険」である。

### 意図的に壊す feature の一覧

「検査が実際に働くこと」を確かめるため、意図的に壊した経路をfeatureとしてコードに残している。
いずれも既定ビルドには入らない。

| feature | 何を壊すか | 何を検証するか |
|---|---|---|
| `panic-test` | bootloaderで意図的にpanicする | パニックハンドラが停止とダンプを行うこと |
| `exception-test-*` | 除算例外・不正命令・ページフォルト・ダブルフォルトを起こす | 例外ハンドラとGPRダンプ、ISTの切り替え |
| `critical-test-double-lock` | 同じロックを保持したまま再取得する | 二重取得の検出 |
| `critical-test-restore-enabled` | IF=1から`InterruptGuard`へ入る | 復元経路 |
| `interrupt-test-enable-only` | 全IRQをマスクしたまま`sti`する | 何も届かないこと |
| `interrupt-test-irq-path` | `int 0x40`を発行する | IRQ経路がGPRを復元すること |
| `misalign-test` | IRQスタブのスタック16バイト調整を外す | 境界検証が発火すること |
| `interrupt-test-timer` | タイマを動かす | ティックが増え続けること |
| `no-eoi-test` | タイマハンドラのEOI発行を落とす | ティックが1回で止まること |
| `alt-offset-test` | PICを0x30-0x3Fへ再マップする | ICW2が実際に効いていること |
| `tiny-key-buffer` | キーバッファを極小にする | オーバーフロー検出 |
| `paging-test` | 壊さない。追加の検証を走らせる | PCD付き2MiBページの分割で属性が残ること |
| `paging-test-drop-pcd` | 分割時にPCDを落とす | 読み戻し照合が不一致を検出すること |
| `paging-test-wrong-order` | 分割の順序を逆にし、中間状態を意図的に踏む | 中間状態が #PF になること。CR2が踏んだアドレスを指すこと |
| `paging-test-bad-index` | アンマップの添字を間違える | 別のページが消えたことを検出すること |
| `paging-test-unmap-fault` | アンマップしたページを読む | `invlpg`を発行した場合に #PF になること |
| `paging-test-no-invlpg` | アンマップ後の`invlpg`を落とす | 古い翻訳がTLBに残り、フォルトせずに読めること |
| `paging-test-split-heap` | 壊さない。稼働中のヒープが載るページを分割する | 使いながら分割でき、翻訳が粒度だけ変わること |
| `paging-test-directmap-low-window` | direct map の窓を高位ではなく低位（恒等と同じ）で張る | 独立 walker が高位窓の不在を検出し、CR3 を切り替えずに止まること |
| `paging-test-directmap-wrong-base` | A-2 の登録窓の base を 1 ページずらす | 差し替え後の phys_to_virt 検証が食い違いを検出し、高位アクセスの前に止まること |
| `stack-guard-test` | カーネルスタックを溢れさせてガードページを踏む | #PF（vector 14）が IST2 上で、CR2 = ガードページとして報告され、#DF へ昇格しないこと |
| `stack-overflow-df-test` | 溢れさせ、#PF に IST を与えず #DF へ昇格させる | スタックオーバーフローが本来の連鎖で #DF になること（M4-b-2 の代用とは別経路） |
| `task-switch-drop-reg` | 協調的スイッチで次タスクの rbx を壊す | 復帰したタスクが GPR 照合で検出して止まること |
| `task-switch-no-swap` | 協調的スイッチで RSP の差し替えを省く | スイッチが起きず会計が合わないことを検出して止まること |
| `task-switch-yield-in-critical` | InterruptGuard 保持中に yield を呼ぶ | on_yield のガードが critical nesting depth を見て fail-fast すること |
| `gfx-test-pattern` | コンソールを起動せず描画テストパターンを描く | 描画の基盤 |

これらが有効なビルドでは、起動時に`test hooks:`のWARNが出て内訳が列挙される。
何も有効でない場合も`test hooks: none enabled (this is a normal build)`と1行出す。
「出ていない」と「そもそも報告していない」を区別するためである。

`cargo xtask check`は、`kernel/Cargo.toml`の`default`から推移的に辿って、これらのいずれにも行き着かないことを検査する。
壊れた状態で測った結果を正常な結果として扱う事故を防ぐためのものである。

### 検査や計測が正しく機能していなかった事例

検査は存在するだけでは機能しない。過去に次の形で壊れていた。

- スタブ表のstride検証、`!Send`のコンパイル時検査、正規化テキストによる内容不変検証。いずれも「わざと壊して検出されること」を確認して発覚した
- マーカーテストが`expected_markers`の先頭1本だけを見て打ち切っていたため、実装が正しくても残りの出力を取りこぼしてFAILになりうる状態だった。全部そろうまで待つ形に直した。到達しなければ`deadline`で打ち切る。期待マーカーが複数ある構成はすべて同じ競合を抱えており、まとめて解消した（`troubleshooting.md` 2026-07-22）
- 回帰チェック一式が実装ループにも`check`にも入っておらず、2日間走っていなかった。`--full`を追加して解消した
- **`unsafe`の`SAFETY`コメント検査が、新しいファイルを見ていなかった。** 対象を`git ls-files "*.rs"`で列挙しており、追跡済みのファイルしか出ない。新しいファイルを書いてから検査を通し、その後に`git add`してコミットする、という自然な順序だと、そのファイルの最初の検査は追跡される前に走る。素通りしたまま「通った」と報告される。実際に`kernel/src/paging/verify.rs`が2コミットのあいだ見逃されていた。`--cached --others --exclude-standard`へ変えて解消した。未追跡の`.rs`に`SAFETY`無しの`unsafe`を置き、変更前は素通りし変更後は検出されることを確認している

  この形の見落としは、検査の対象範囲が「今そこにあるもの」ではなく「gitが知っているもの」で決まっていたことによる。新規追加が最も検査を必要とする場面なのに、そこだけ穴が空いていた。`tools/docstyle.py`にも同じ列挙方法の穴があり、あわせて直した。他の検査についても、対象の列挙方法が同じ性質を持たないかを見ておくこと

  **なお`--exclude-standard`は`.gitignore`だけでなく`.git/info/exclude`も参照する。** つまり検査の対象範囲が、リポジトリに含まれないローカル設定によって決まる。ローカル専用のファイルを拾わないために必要な挙動だが、これも「対象が環境によって変わる」という点で今回の穴と同じ系統である。別の環境で検査を走らせたときに対象が変わりうることを承知しておくこと

計測についても同じ型の失敗をしている。いずれも「同じ条件で比べていないものを比べていた」というものである。

- 比較用のworktreeと本体を交互に走らせるつもりで、`cd`がループの次の行にも効いていたため6回すべてworktree側で走っていた。所要時間が109.35 / 109.36 / 109.37秒とほぼ同一だったことが手掛かりになった。数字が揃いすぎているのは異常である
- worktreeを`/tmp`の深い階層に置いたため、そちらだけmonitorソケットのパス長が上限を超えて失敗していた。場所の違いが結果の違いとして現れており、比べたかった変更の効果ではなかった。本体で条件を切り替えて測り直した

**数字が出ていても、条件が違えば意味を持たない。**
比較する前に、比べている2つが本当に他の条件で揃っているかを確かめること。

コミットの検査は件名だけを見ており、**本文は対象外と決めている**。
文体規約の目的は公開時の見え方を整えることで、主な対象はREADME・docs・コード内コメントである。
本文には識別子や式（`is_multiple_of`、`% 16 == 0`、`#TS / #NP / #SS / #GP`など）がそのまま現れ、和文と隣り合う箇所で空白を落とすと読みにくくなる。
バッククォートで囲む書き方をコミットメッセージへ課すのは一般的でなく、揃えるために履歴の書き換えを増やすコストにも見合わない。
保留ではなく決定であり、後から再検討しない。

### 2.2 起動時に実機の状態を読み戻すもの

いずれも一致しなければその場で停止する。

| 対象 | 読み戻す手段 |
|---|---|
| GDT・セグメントレジスタ | `sgdt` / `str` / セグメントレジスタ |
| IDT | `sidt`、全256エントリのゲート種別とDPL |
| スタブ表 | 例外用256本とIRQ用17本を別々に、先頭からの距離で照合 |
| スタックの16バイト境界 | スタブが`call`直前に読んだ実測RSP |
| PICのIMR | 再マップ前後のIMRを読み戻して照合 |
| `sti`前の7項目 | ADR-0018 §2。`Verified` / `Failed` / `Unverifiable`の3状態 |
| ページテーブル | 稼働中のテーブルをwalkし、`plan`の意図と照合 |
| 恒等マッピング | 翻訳結果の物理アドレスが仮想アドレスと一致すること |
| キャッシュ属性 | PCDが`plan`の意図と一致すること |
| Gビット | 1つでも立っていたら停止（M5-a-2で測定のみから変更） |
| マッピング粒度 | RIP・RSP・ヒープ・フレームバッファが翻訳できること |
| ヒープの写像 | アリーナ全体がマップ済みであること |
| 非正規アドレス | `None`ではなくエラーとして区別されること |
| スタックのカナリア | 犠牲領域の毒値`0xC5`が保たれていること |

### 2.3 実行中に継続して確認するもの

| 対象 | 内容 |
|---|---|
| 割り込みの会計 | `keys + stray`がハンドラ呼び出し回数とベクタ別カウンタに一致すること |
| ハートビート | 止まった理由の切り分け材料（i8042のOBF、PICのISR）を毎回出す |

### 2.4 文書とリポジトリ

文書の文体を機械的に書き換えたときに、内容とレンダリング結果が変わっていないことを検査している。
見ているのは5項目で、GFMタスクリストのマーカー直後の空白、行結合の痕跡、閉じない強調、フェンスの対と見出しレベルの飛び、リンクとアンカーの生存。
この検査に`--base <ref>`を渡すと、レンダリング結果・正規化テキスト・ASCII語彙を変更前と比較する。

公開前の監査は常時走るものではない。手順は下記の「公開前の監査」節にある。

### 公開前の監査

公開リポジトリに、実装内容と無関係なもの（個人メモ、作業ログ、意図せず混入した一時ファイル）が残っていないかを確認する。
次の順序で行う。

1. `git ls-files`と`git rev-list --all --objects`の**全件を目視**し、想定外のファイルが無いか確認する。ビルドや実行に不要なものが混ざっていないかを見る
2. 非ASCIIファイル名の検出（`grep -P '[^\x00-\x7F]'`）。日本語名の一時ファイルは意図せず混入しやすい
3. **ファイル内容の文字種検査。** 追跡対象ファイルと未コミットの変更を対象に、非ASCII文字をUnicodeブロック別に集計し、想定外のものが無いか確認する。想定しているのは、ひらがな・カタカナ・CJK統合漢字・CJK記号句読点・半角全角形・矢印・罫線素片・数学記号・`§`のみ。想定するブロック以外が現れたら、その所在を確認する

   ファイル名だけを見ても内容の混入は分からない。見た目が同じでもコードポイントの異なる字が紛れうるので、目視ではなくブロック別に機械的に集計する
4. 現在の追跡ファイルと全履歴パスの差分を取り、削除・改名されたものを洗い出す
5. **その後に**キーワード検索を行う

**キーワード検索は補助であって主ではない。**
パターンに含まれないものは見つからないため、検索の「出力なし」は、そのパターンに含まれていない対象については何も証明しない。
まず全件を見ること。

あわせて、全コミットメッセージと著者・コミッタ情報、ライセンス表記も確認する。

### 変更の危険度による扱いの区別

次に該当する変更は、確定させる前に差分と関連ログを突き合わせて確認する。
まとめて後から見直さない。

- `unsafe`ブロックを新規に含む、または既存の`unsafe`の前提を変える変更
- 割り込みハンドラ（IDT）・例外ハンドラに関わる変更
- ページテーブル操作・仮想メモリマッピングに関わる変更
- GDT / TSS / セグメンテーション周りの変更
- クリティカルセクション（`cli`/`sti`による割り込み禁止区間）の設計変更
- `architecture.md` §2の確定済みアーキテクチャに影響する変更

いずれも「間違えても即座には落ちず、しばらく動いた後に壊れる」性質を持つ。
落ちた時点と原因の距離が遠いため、書いた直後に確認する価値が最も高い。

マイルストーンへ到達した時点でも同じ確認を行う。
これは変更の種類ではなく時点だが、区切りごとに全体を見直す機会として扱う。

上記以外の純粋ロジック・ドキュメント・テスト・ビルドスクリプトの変更は、この扱いの対象外である。

## 3. 測定のみ

現時点で該当なし。

Gビットはここにあったが、M5-a-2の分割手順がその前提に依存するため検査ありへ移した。
