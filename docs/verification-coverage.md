# 主張と検査の対応

ZaytOSの文書は「常にこうである」「必ずこうする」と書いている性質をいくつも持つ。
このファイルは、その主張ごとに対応する検査があるかどうかを並べたものである。

作った動機は、`cargo fmt`と`cargo clippy`が2日間ずっと未達だったことに気づかなかった経験である。
原因は個々の見落としではなく、維持していることを確認する手順がどこにも無かったことだった。
主張だけがあって検査が無い状態は、時間が経つほど気づきにくくなる。

`deferred-decisions.md`とは役割が違う。
あちらは「いつか判断する項目」、こちらは「主張と検査の対応表」である。

状態の区分は次の3つ。

- 検査あり: 機械的な検査があり、破れば落ちる
- 測定のみ: 値は測っているが、違反しても止まらない
- 検査なし: 対応する検査が無い

---

**節番号は安定していない。** 節は増減するので、他の文書やコミットメッセージから番号で参照しない（見出しの文言で参照する）。実際にS0-aで1節を移したときに後続の番号を詰めた。詰めた時点で古い番号への参照は無かったことを履歴も含めて確認しているが、参照があれば静かに別の節を指す状態になっていた。

## 1. 検査なし

現時点で違反は確認していないが、破っても誰も気づかない。

### 1.1 割り込みハンドラは何も出力しない

出典: ADR-0018 §5、`architecture.md` §6.8

観測はカウンタ越しに行い、ハートビート1行へ集約する設計である。
ハンドラの中から`Logger`を呼んでいないことは検査していない。

足すなら、ハンドラの関数本体に`logger`や`write!`が現れないことを見る形になる。
ハンドラの範囲を機械的に決めにくいのが難点で、現状は費用に見合わないと判断している。
M5-dでハンドラからスケジューラを呼ぶようになると、ハンドラ内で呼べるものの範囲が広がるため、その時点で再検討する。

### 1.2 画面とシリアルの両方へ出す場合はシリアルを先に書く

出典: ADR-0013、ADR-0017、`architecture.md` §6.7

`log_both`の実装がその順序になっているだけで、呼び出し側が別の順序で書くことを妨げるものは無い。
画面出力が壊れたときにシリアルだけは残る、という保証がこの順序に依存している。

足すなら、`log_both`以外から`Console`へ直接書く経路が無いことを見る形になる。

### 1.3 ページテーブルでNXを立てない

出典: `architecture.md` §6.6、`kernel/src/paging/table.rs`

EFER.NXEを有効にしていない段階でNXを立てると、予約ビット違反のページフォルトになる。
稼働中テーブルの読み戻しはPCDと恒等性は照合するが、NXは見ていない。

同じ節の「PSビットはPDレベルのみ」は、`translate()`がPDPTレベルのPS=1を`UnsupportedGiantPage`として弾くため、実質的に検査されている。

足すのは容易で、読み戻しの照合にビット63を加えるだけである。
M5-eで権限の細分化に入るときに、NXの扱いを決めるのとあわせて足すのが自然である。

### 1.4 ターゲットの既定値への依存

出典: `architecture.md` §5、§5.1

kernelは`x86_64-unknown-none`の`disable-redzone`と`+soft-float`に依存している。
red zoneが有効に戻ると、割り込みが入った瞬間に呼び出し元のローカル変数が壊れる。
§5.1は「rustflagsやターゲットを変更した際は、この確認をやり直すこと」と書いているが、やり直しを促す仕組みは無い。

stableでは`--print target-spec-json`が使えないため、確認は生成コードを読む形になり、機械化しにくい。
`.cargo/config.toml`と`rust-toolchain.toml`が変更されたときに気づける形にするのが現実的である。

## 2. 検査あり

### 2.1 ビルド・テスト・静的解析

`cargo xtask check`は次を実行する。

| 項目 | 内容 |
|---|---|
| build | bootloader（`x86_64-unknown-uefi`）/ kernel（`x86_64-unknown-none`）/ common / xtask |
| test | `cargo test --workspace` |
| clippy | 上記4構成すべてに`-D warnings` |
| fmt | `cargo fmt --all -- --check` |
| unsafe | `unsafe`ブロックの直前のコメント塊に`SAFETY`があること（追跡済みと未追跡の両方が対象） |
| cli/sti | 直接の`cli`/`sti`が許可リストの`(file, item)`に載っていること |
| 境界の可視性 | 内部を隠す約束のモジュール配下の`mod`宣言と`use`にprivate以外の可視性修飾が無いこと（対象の一覧は検査が毎回印字する） |
| 既定feature | 既定のkernelビルドにサボタージュfeatureが混ざっていないこと |
| トランポリン | ビルド済みkernel.elfの入口24バイトが期待リテラルと一致すること |
| コミット | コミット件名に和文と英数字の間の半角空白が無いこと（規約を適用し始めた日時以降が対象） |

`cargo xtask check --full`は、これにQEMUを起動する回帰チェック（exception / critical / paging / stack / task / ring3 / syscall / interruptの各表と、keyboard・panic）と、higher-halfの破壊確認（`highhalf-*`と`highhalf-trampoline-absolute-ref`の静的検査）を加える。
種類の一覧は`xtask/src/main.rs`の各テスト表を正とし、項目数は下の項目会計に従う。

`--full`は、xtaskが「起動しなかった」と判定した項目に限り、自動で1回だけ再試行する。
テストの失敗（実装の問題）では再試行しない。落ちるものは落ちたまま報告する。
1回に限るのは、回数を増やすと「何度も失敗したが最後に通った」状態を成功として扱うことになるためである。
再試行したことは都度出力し、最後に件数と項目名をまとめて出す。

**基準線は0件である。1件でも出たら異常の兆候として扱う。**
この再試行は当初、OVMFがまれに起動に失敗する既知の事象への対処として入れた。
ところがその事象は環境要因ではなく、varstoreを使い回していた自作の不具合だった（`troubleshooting.md` 2026-07-22）。
直した後は0件が続いている。
したがって現在の位置づけは「頻繁に起きることへの対処」ではなく「起きないはずのことが起きたときの保険」である。

### かつての確率的フレークと、サボタージュを arm 窓へ絞った理由

`task-test preempt-in-critical`はかつて約10%で落ちた。**原因は当初の想定（タイマプリエンプトが cli 除去窓に当たるか）ではなかった。** 実測で判明した真因と解消を記録する。将来「この分岐は複雑だから消そう」とサボタージュを大域へ戻すと再発するため、なぜ今の形かを残す（`const fn`を失った理由やマーカー文字列を変えた理由と同じ性質の記録）。

**真因。** このテストのサボタージュは2つある（`preempt-in-critical-break`＝`InterruptGuard`の cli 省略、`task-preempt-in-critical`＝`on_timer_tick`の防御スキップ除去）。当初は**どちらも大域的**で、プリエンプティブデモの開始（`setup_preemptive_tasks`の`InterruptGuard`区間や`yield`付近）まで perturb した。そのため検査対象（二重取得を狙う保持窓）へ到達する前に、ワーカーが1度も走らず`switches=0, iterations=0`で「the timer did not preempt fairly; halting」と落ちた。観測される失敗署名は「double acquisition detected が出ず halt」だが、実体はこの startup レースである。既定ビルドは20/20健全で、サボタージュ有効時だけ約10%落ちたことから、カーネル本体ではなくサボタージュが原因と実測で確定した。1回目に当てた修正（保持窓を tick 条件化）は無変更と同率で no-op だった（真因が保持窓ではなかったため）。

**解消（案E）。** サボタージュを大域から**arm 窓へ絞った**。`common::critical`に`SABOTAGE_ARMED`を置き、`InterruptGuard`は arm されている間だけ cli を省く。`on_timer_tick`の防御スキップも arm 中だけ bypass する。ワーカーは`preemptive_loop_top`で`DEMO_LOCK`を握る直前に arm し（RAII、Drop で disarm）、その保持窓だけを壊す。デモ開始は arm の外なので正常な cli の下で走り、startup レースが起きない。**production は不変**（arm 判定はすべて feature 下で、既定ビルドでは cli も防御スキップも常時有効）。修正後、単体30回連続 PASS（全て二重取得経由、`made no progress`は0回）・`--full`の全通過・既定20回で`made no progress`=0 を確認した。

**フレーク判断の手順（この種の確率的取りこぼしが再発したとき用に残す）。** 失敗署名を確認し、`exception: vector=`・cpu_reset の増加・別マーカーの欠落なら回帰として調査する。取りこぼし署名（`made no progress`・`switches=0`等）なら、単体で数回再実行し、`cargo xtask check --full`の全通過を確認する。同じ署名で繰り返すなら確率が高すぎるので、確率性そのものを潰すまで先へ進めない。

### 意図的に壊す feature の一覧

「検査が実際に働くこと」を確かめるため、意図的に壊した経路をfeatureとしてコードに残している。
いずれも既定ビルドには入らない。

| `interrupt-test-irq-path` | `int 0x40`を発行する | IRQ経路がGPRを復元すること |
| `misalign-test` | IRQスタブのスタック16バイト調整を外す | 境界検証が発火すること |

| `syscall-test-copy-overrun` | `copy_from_user` が `len` を 1 バイト超えて読む | 末尾の余分な既知バイトが総和へ混ざり、`checksum mismatch` で決定的に止まること（bounded read が範囲を守ることの実証。#PF は副次的位置づけ） |
| `gfx-test-pattern` | コンソールを起動せず描画テストパターンを描く | 描画の基盤 |

| `highhalf-bad-high-slot` | 静的初期テーブルの `PDPT_high` のエントリを `510`→`509` へずらす | 高位 `_start` への jmp 先が未マップで起動が進まないこと。判定は `no-identity-in-boot-pt` と同一署名 |
| `highhalf-no-kernel-high-in-live-table` | M2-d/A-1 の `map_kernel_high_half` 呼び出しを外す（本流テーブルにカーネル高位マッピングを張らない） | M2-d の CR3 切替後に高位で #PF して停止すること。判定=`higher-half: arrived at high VA` present / `paging: CR3 switch verified` absent + heartbeat=0 |
| `highhalf-trampoline-absolute-ref` | トランポリンに絶対メモリ参照命令（`mov rbx, [0x2000]`）を 1 命令挿入する | トランポリンのバイト単位一致検査が落ちること（**静的検査。QEMU 不要**。実行時は `0x2000` が恒等で読めるので落ちない） |

何も有効でない場合も`test hooks: none enabled (this is a normal build)`と1行出す。
「出ていない」と「そもそも報告していない」を区別するためである。

`cargo xtask check`は、`kernel/Cargo.toml`の`default`から推移的に辿って、これらのいずれにも行き着かないことを検査する。
壊れた状態で測った結果を正常な結果として扱う事故を防ぐためのものである。

int 0x80システムコールの検証（M5-f-1-2）について、2点を明記する。

- **RCX/R11はクロバー扱いで、保存に依存する検査を書かない。** ADR-0020のとおり、`int 0x80`の間はRCX/R11が実際には保存されるが、`syscall`/`sysret`へ移る段でこれらは命令が破壊する。ここでRCX/R11の保存を検査に固定すると、移行時の破壊が検査に守られて表面化しなくなる。probe発行ルーチンはRCXへ番兵を入れるが、これは`syscall-test-arg4-rcx`が第4引数をRCXから誤読したときに決定的な食い違いを起こすためで、RCX/R11が保存されることを確かめる検査ではない。
- **RSP0スタックでの走行の破壊featureは新設せず、`ring3-test-drop-rsp0`を指す（判断B）。** syscall経路のRSP0据え付けは`ring3::enter`の`set_rsp0`を再利用しているため、これを落とす破壊は`ring3-test-drop-rsp0`と同一で、重複featureを作らない。一方で**検証項目は新規に持つ**: syscall経路では「`syscall_entry`のRSP（`rsp_at_call`）が遠征スタック範囲内にある」ことを読み戻す。`ring3-test-drop-rsp0`が見るのは#GP例外ハンドラの着地で、syscallが見るのは`syscall_entry`の着地であり、破壊featureは共通でも検証対象が違う。

ユーザーポインタ検証（M5-f-2-1、`user_range_accessible`）について、3点を明記する。

- **単独破壊で隔離できるのはU=1判定と全ページ走査だけである。** 検証器は (a)長さのオーバーフロー、(b)ユーザー範囲、(c-present)各ページのpresent、(c-U=1)各階層のU=1、を見る。このうち (a)(b)(c-present) は互いに、そして (c-U=1) に**冗長**（多層防御）で、1つだけ外しても別のチェックが後追いで拒否するため、単独破壊ではhaltしない。具体的には、範囲下限外（カーネルポインタ、PML4[0]）はpresentだがU=0なので範囲判定を外してもU判定が弾く。未マップはゼロ埋め（U=0）なのでpresent判定を外してもU判定が弾く。長さオーバーフローはbufがユーザー範囲（< 2^40）にあるため、wrap後の末尾が範囲外になり範囲判定が、あるいは上端先が未マップなのでpresent判定が後追いで弾く。したがって破壊featureは隔離できる `skip-us`（U=1判定）・`skip-laststep`（全ページ走査）・`skip-all`（検証器全体）の3種とする。範囲/present/overflowの各チェックは、defaultのbatteryでfirst-lineの拒否者として実運用・実証される（batteryの無効1〜5が拒否されること自体が、これらのチェックの正しさを担保する）が、単独破壊testとしては設けない。
- **この隔離不能は現在のアドレス空間レイアウトに依存する。** 「U=1はユーザーサブツリー`PML4[USER_PML4_INDEX]`の外に一切存在しない」（`audit_user_supervisor`が`kernel_violations==0`を毎起動でアサート）ため、範囲外・未マップが必ずU=0になり、U判定が範囲判定・present判定を後追いで肩代わりする。**higher-half B後にレイアウトが変わり（カーネルを上位半分へ、ユーザーを低位へ拡張）「カーネル=必ずU=0」の前提が変われば、この冗長性は再評価が要る。** `syscall::USER_VIRT_MIN`/`USER_VIRT_MAX`もPML4[1]前提なので同時に見直す。M5-e-2で`drop-rsp0`の配置依存を記録したのと同じ、検査の成立が構造条件に依存することの記録である。
- **`user_range_accessible`はlen==0を常に受理する契約である。** 0バイトのアクセスはbufを問わず安全であり、この短絡は検証器の内部に置く（呼び出し側で短絡しない）ので、この検証器を共有する全syscallが同じ契約を継承する。batteryはlen=0を有効bufと無効bufの両方でテストする。

`walk_user_accessible`が中間階層U=0（葉U=1でも中間U=0なら`translate`の葉Uでは見逃す穴）を弾くことは、一度きりの確認（中間テーブルのUビットを直接落として`walk`が`SupervisorOnly`で弾く一方`translate`の葉Uでは通してしまうことの対比）で実証した。侵襲的setupを恒久コードに残さないため恒久featureにはせず、確認後に戻している。

`copy_from_user`と検証済みトークン`UserSlice`（M5-f-2-2）について、3点を明記する。

- **型で保証される範囲と、規律で守る範囲の境界。** `UserSlice`はフィールドprivateで公開コンストラクタを持たず、構築できるのは検証器`validate_user_range`だけである。`copy_from_user`が`&UserSlice`を要求するので、**モジュール外の全呼び出し元に対しては「検証を経ないとユーザーメモリを読めない」ことが型で保証される。** ただしこの保証はモジュール境界に依存する。同一`syscall.rs`モジュール内からはprivateフィールドに触れるため`UserSlice { .. }`を直接構築できてしまう。したがってモジュール内の直接構築は`copy-skip-validate`破壊feature専用であり、通常コードでは行わない（この規律は型ではなくレビューで守る）。`copy-skip-validate`はまさにこの境界を突く破壊である。
- **TOCTOU（検証と読みのアトミック性）は構造条件に依存する。** 検証と読みが実質アトミックなのは、`syscall_entry`が割り込みゲート（IF=0）で入りプリエンプトが来ないこと、シングルコアであること、ユーザーページをアンマップする経路が`syscall`中に走らないこと、の構造条件による。**将来IFを立てる`syscall`（長時間ブロッキング等）を導入すると、この前提が崩れTOCTOU（検証後・読み前にアンマップ/再マップ）が現実化する**ため再検証が要る。`user_range_accessible`のレイアウト依存と同じ、安全性の成立が構造条件に依存することの記録である。
- **`UserSlice`の有効期間は同一`syscall`内・同一アドレス空間に限る。** 跨いで保持しない（staticに置かない）。higher-half B後のプロセス別アドレス空間では、トークンは「そのCR3の下でのみ有効」になるため、CR3を跨いで使わない制約をf-3で型（世代/CR3を持たせる等）またはdocで担保する（再確認の申し送り）。加えて、`SYS_CHECKSUM`のバッファ容量超過（`len > CHECKSUM_BUF_LEN`）を現状`-EFAULT`で代用しているが、意味的には「容量超過」でありポインタ不正（Bad address）とは異なる。errno体系が育つ段（POSIX互換の構想）で見直す。

higher-halfの破壊feature（B-2a-5、破壊feature `highhalf-*`）について、5点を明記する。

- **(a)(b)(c)はトリプルフォルト（cpu_reset）しない。判定にcpu_resetを使わない。** これは直感に反するので明記する。(a)(b)はトランポリン/最初期の#PFが**我々のIDT導入前**に起きるため、UEFIのIDTが拾いファームウェアが制御を取り戻す（-d intにファームウェア領域のRIP、CR3=firmware、INT 0x20 servicingが残る）。(c)はM2-d切替後に高位で#PFして停止する（ファームウェア復帰もしない）。いずれもCPU Resetは起動時の2回のまま増えない。**cpu_resetを判定条件にすると4種すべてFALSEで通ってしまう（実際に最初cpu_resetで判定して4種FAILした）。** したがって判定は位置署名（present/absentマーカー）+定常未到達（heartbeat=0）で行い、cpu_reset数とファームウェア復帰の有無は参考情報として出す。将来「cpu_resetで判定すべきでは」と誤って直さないための記録である。
- **(a)(b)がファームウェアへ制御を渡す機構は完全には解明していない。** UEFIのIDTが#PFをどう処理して自身のアイドルループへ戻すのかは追っていない。テストの妥当性（位置署名+定常未到達）には影響しないが、解明済みではない。
- **(a)(b)の失敗モードはファームウェアへ逃げる形なので、OVMFのバージョン更新時にこの2テストの挙動が変わりうる。** UEFIのIDT/フォルト処理が変われば、位置署名やheartbeat=0の成立が崩れる可能性がある。OVMFを更新したときの確認対象とする。
- **M2-d/A-1の切替前検査は物理範囲のメンバシップ検査のみで、高位マッピングの欠落を検出しない。** `highhalf-no-kernel-high-in-live-table`(c)がこれを実証した。必須マッピング検証は「切替後の必須領域が物理範囲に属するか」を見るだけで、A-1/B-1が持つ「新テーブルを独立walkerで実際に引く」検査を持たない。恒等が物理を覆っている限り高位マッピングの欠落を見逃す。walkベースへの強化はB-2bの検討事項（ADR-0024 / ADR-0021 B Addendum）。
- **トランポリンのバイト単位一致検査（base検査）。** ビルド済みkernel.elfの入口24バイトを期待リテラルと比較する（`common::elf`再利用、新規外部クレートなし）。既定ビルドで一致（B-2a-2/B-2a-3b/B-2a-5で3度、再リンク・B-1撤去を跨いで不変を実証）、`highhalf-trampoline-absolute-ref`で不一致。rel32がすべて`.text.trampoline`内なので配置非依存で安定。`cargo xtask check`のbase検査なので`--full`でなくても毎回走る。

**項目会計**: 検査を足したとき数が閉じていることを、この行だけで追う。**現在の項目数は`cargo xtask check`の出力（`all N check(s) passed`）を正とし、docsの他の場所には書かない。** 総数は検査を足すたびに増えるので、導出元から離れた場所に書けば必ずstaleになる（実際に`--full`=64がroadmapとdeferred-decisionsに残り、同じ型の誤りの3件目になった）。数え方は、base = `CHECKS`（build 4 / test 1 / clippy 4 / fmt 1）+ 静的検査、`--full` = base + QEMU + highhalfである。

### higher-half B-2b: 恒等除去の設計（着手前の棚卸し）

- **反転関門で守られる群**: (5-8) 4検証サイト。これらは`DirectMap::identity`（恒等窓）を構築して作業する。恒等除去後に誤って再実行されると、`DirectMap::new`の`IDENTITY_REMOVED`関門がfail-fastで捕まえる（構築を通るため）。
- **記録でしか守れない群**: (11) kernel_startの生の低位read [862/900行]、および boot_info の低位デレフ [468行]。これらは`DirectMap`を構築せず生の低位アドレスを直接読む/デレフするので、関門を通らず捕まえられない。**どちらも高位化できない**（(11)は862/900行がA-2[991行]より前でdirect_map()がbase=0を返す。boot_infoは468行がinit_direct_map[477行]より前で同様）。したがって「恒等除去より前に走る／参照されない」ことにのみ依存し、コードの境界コメント（(11)=862行、boot_info=最終利用の992行直後と除去予定点1166行の両側）とこの一覧で守る。**順序要件は「(11)とboot_infoの利用が除去点より前にある」こと**（(11)を除去点の後ろへ、または除去点を(11)/boot_info利用の前へ動かすのが違反。除去点をさらに後ろへ動かすのは安全）。

**コードとこの一覧の同期。** かつて「コード内採番を始めて途中でやめた」（`main.rs:480`の`(1)`止まり）ことが列挙の未完を招いた。同じ失敗を繰り返さないため、採番はコードから外しこの一覧を正とする。恒等前提の箇所はコードに固有マーカーを置いてある。未解決は `未解決の恒等前提`、解消済みは `解消済みの恒等前提` で、状態を表す語を接頭に出してある。かつては未解決 `恒等前提の箇所` と解消済み `恒等前提だった箇所` を使っていたが、語幹「恒等前提」と接尾「箇所」を共有し状態語（の／だった）が中間に埋もれていたため、語幹でgrepすると両者を拾い目視でも紛れやすく、実際に解消済みを未解決と取り違える誤りが起きた。接頭を分けたので `未解決の恒等前提` と `解消済みの恒等前提` はどちらも他方を部分一致で拾わない。現状 `grep '未解決の恒等前提' kernel/src/main.rs` = 3件で、各々「なぜ未解決側に残るか」がコメントと本一覧に書いてある: boot_info[468]（除去前に消費・468<477で高位化不可）、必須マッピング検証[745]（BootInfo_startを低位=物理として見る恒等前提・除去より前に走る）、kernel_start低位read[862]（順序依存・862<991で高位化不可・記録で守る）。解決した箇所はマーカーを「解消済みの恒等前提（…で解消）」に変えて `未解決の恒等前提` のgrepから外す（ヒープ[B-2b-2]・image_physのRSP/RIP変換[B-2a-2]がその例）。同期の不変条件を精密に書く。**`grep '未解決の恒等前提'` の結果は、この一覧のうち「まだ恒等前提が残っている（未解決の）箇所」の部分集合である。** 解決した箇所（高位化した等）はコードのマーカーを「解消済みの恒等前提（…で解消）」へ変えてgrepから落とす。これで双方向に食い違いを検出できる: 新しい恒等前提を足したのに一覧へ書き忘れれば、grepに出て一覧に無い（検出）。解決したのに一覧を直し忘れれば、grepから消えて一覧では未解決のまま残る（検出）。「高位化した」群と除去手順ステップ4の必須領域リストも一致していること（新しく高位化する低位ポインタを増やしたら、コードのマーカー・この一覧・必須領域リストを同時に更新する）。

順序を守る機構は**反転設計**にした。「除去が各サイトの完了を検査する」ではなく「恒等窓の構築が除去済みでないことを検査する」。`common::addr`に`IDENTITY_REMOVED`フラグを置き、除去（B-2b-4）が`mark_identity_removed()`で立てる。`DirectMap::new`は`base==0`（恒等窓。`identity()`もここを通る）のとき`IDENTITY_REMOVED`を検査してfail-fastする。利点は、cfg非依存（paging-testで検証サイトがcfg除外される穴が構造的に消える）、後から追加された恒等利用も自動的に守られる、単一の関門で各サイトを個別に編集しない、違反した箇所で正確に落ちる、の4つ。この関門のため`new`/`identity`は`const fn`ではなくなった（実行時にフラグを読むため。const文脈での利用は無いことを確認済み）。**関門でカバーできない残存分**: (11)のような生の低位readは`DirectMap::new`を経由しないので関門では捕まらない。列挙とコメントで管理する（(11)はM2-d切替直後で除去点よりはるか手前なので実リスクは低い）。また`DirectMap::new(base==0)`の直接呼び出しは捕まるが、`direct_map()`（登録窓の読み出し、モジュール内の構造体リテラル）は関門を通らない（登録窓の読み出しは対象ではないので正しい）。

恒等除去は**CR3リロード（全TLBフラッシュ）で行う。invlpgでは足りない**（`PML4[0]`を落とすと下位512GiBの写像が消えるが、TLBにキャッシュされた低位変換は残る。invlpgは1ページ単位で512GiB分の無効化手段にならない。G=0維持なのでCR3リロードで確実に落ちる。ADR-0018/M5-e-2）。落としてからフラッシュするまでTLBが生きているので実行継続・書き戻し可能。これを使い、除去を「検証可能で復帰可能な前段付きの不可逆な一手」にする（A-1/B-1の型を除去へ適用。**軸5=M2-d/A-1のCR3切替前検査のwalkベース強化とは別物**。軸5は既存のCR3切替を守るもので除去を守らない）。手順:

1. `PML4[0]`エントリを保存する。
2. 落とす前に`PML4[0]`配下を辿ってフレーム数を数えログに出す（フレーム会計をここで閉じる。孤立フレームは意図的リーク。A-1本流18フレームから恒等サブツリーは10枚前後=約40KiBと見込み、解体コードのリスクを負うより小さなリークで足りる。実測値で判断）。
3. `PML4[0]`を落とす（TLBが生きており実行継続可能）。
4. 独立walkerで検証。必須領域リスト=RIP / RSP / カーネルイメージ / direct map窓 / フレームバッファの高位VA / **ヒープの高位VA**が恒等なしで解決し、かつ`PML4[0]`が空であること（boot_infoは高位化しない=除去後に参照されないのでリストに含めない。上記の再分類による）。**このリストは恒等前提の列挙の「高位化が要る」群と同期している必要がある**（新しく高位化したポインタを増やしたらリストにも足す。この安全網の前提）。読み戻しは**walkで**行う（「低位VAが未マップ」をデレフで試すとフォルトするので、テーブルを辿ってNotPresentを読む）。
5. 検証失敗→`PML4[0]`を書き戻してhalt（メッセージ付き）。**フラッシュ前なので復帰可能**。検証成功→CR3リロード（全TLBフラッシュ）。
6. フラッシュ後の読み戻し（walk）: 低位VAが未マップ・高位が健全であることを実状態で確認。その後`mark_identity_removed()`。

**この検証は列挙した必須領域の安全網であって完全性の保証ではない。** リストに無い何かが壊れていればフラッシュ後に死んで復帰できない。完全性は依然としてgrepによるsweepに依存する。

順序逆転の破壊feature（高位化より前に除去を置く→恒等除去の瞬間に低位ポインタが見えず死ぬ）でこの順序依存を検査する。判定はB-2a-5と同じ位置署名+定常未到達（トリプルフォルトするとは限らない）。

**網羅の限界（正直に記録する）。** このsweepはgrep（`PhysAddr::new`/`VirtAddr::new`/`as *const`・`*mut`）+ パニック経路の目視。テストは実行された経路しか覆わない。feature下のみ到達する経路（(4)paging-test）、エラー処理、まだ発火させていないパニックは、grepが主たる保証でテストで完全性は証明できない。これは弱点の告白ではなく保証範囲の明示である。paging-testビルドでは検証サイト(5-8)がcfg除外される。B-2b-4(d)で恒等除去を `#[cfg(not(feature="paging-test"))]` で除外すると決めた（paging-testはsplit/unmapの破壊検査が目的で、恒等除去まで通す必要がない）。したがって**paging-testビルドでは恒等除去が検査されない**（カバレッジ穴として明示する）。**恒等除去が実際に走るビルド**は、除去点（`start_timer`より前・4検証サイト+checksumより後の1168付近）へ到達する `not(paging-test)` ビルドである。B-2b-4(d)の実測で確認した例: 既定（6段完走→定常到達=heartbeat）、`highhalf-remove-verify-fail`（step4失敗→5a復帰でhalt）、`preempt-in-critical`（除去`done`まで完走→その後デモの二重取得が発火＝CR3リロード後もデモ健全）、`exception-test`（除去`done`まで完走→その後に意図した例外が発火）。除去より前でhaltする破壊（highhalf a/b/c、検証サイト系のring3/syscall）は除去に到達しない。

**パニック/例外経路が恒等非依存である理由（load-bearingな性質。壊さないこと）。** 初期の設計判断（シリアルログ最優先、ADR-0003）の成果であり偶然ではない。(a) 出力がI/Oポート経由のシリアルのみ（ページング非依存）、(b) レジスタ値のみでメモリをデレフしない（CR2も値として読むだけ）、(c) テーブルwalkをしない、ため恒等除去後も動く。将来パニック経路に画面出力やテーブルwalkを足すとこの性質を壊す。**B-2b-4(e)の `highhalf-panic-after-remove` で実測で閉じた**（恒等を外した後に `panic!` して、パニックハンドラがシリアルへメッセージと `rsp` を出して halt する＝恒等非依存で動くことを確認）。

**`highhalf-remove-before-highify` と `highhalf-panic-after-remove` は「例外/パニックのダンプが出ることが成功署名」であり、フレーク判断の一般手順とは区別される。** 「確率的なテストとフレークの署名」の手順は「`exception: vector=` が出たら回帰として調査」と書いているが、この2種は**意図的に**例外/パニックを起こす破壊featureで、ダンプが出るのが正常である（before-highify は除去後に低位ヒープを触る #PF、panic-after-remove は意図的 `panic!`）。両者を混同して「例外が出ているから回帰では」と誤読しないこと。判定は各featureの present/absent マーカー（before-highify は `cr2=0x00000000…` で低位フォルトを、panic-after-remove は固有のパニックメッセージを確認）で行い、一般手順の対象ではない。この2種が有効なビルドは `test hooks:` のWARNに列挙されるので、そこで「意図的破壊ビルドか」を先に判別できる。

### 検査や計測が正しく機能していなかった事例

検査は存在するだけでは機能しない。過去に次の形で壊れていた。

**この節が集めるのは「検査があるのに働いていなかった」形である。** 「そもそも検査では見えない」形は性質が違うので、下の別の節へ分けてある。混ぜると、対策（検査を直す / 別の検出手段を探す）まで混ざる。

- スタブ表のstride検証、`!Send`のコンパイル時検査、正規化テキストによる内容不変検証。いずれも「わざと壊して検出されること」を確認して発覚した
- マーカーテストが`expected_markers`の先頭1本だけを見て打ち切っていたため、実装が正しくても残りの出力を取りこぼしてFAILになりうる状態だった。全部そろうまで待つ形に直した。到達しなければ`deadline`で打ち切る。期待マーカーが複数ある構成はすべて同じ競合を抱えており、まとめて解消した（`troubleshooting.md` 2026-07-22）
- 回帰チェック一式が実装ループにも`check`にも入っておらず、2日間走っていなかった。`--full`を追加して解消した
- **`unsafe`の`SAFETY`コメント検査が、新しいファイルを見ていなかった。** 対象を`git ls-files "*.rs"`で列挙しており、追跡済みのファイルしか出ない。新しいファイルを書いてから検査を通し、その後に`git add`してコミットする、という自然な順序だと、そのファイルの最初の検査は追跡される前に走る。素通りしたまま「通った」と報告される。実際に`kernel/src/paging/verify.rs`が2コミットのあいだ見逃されていた。`--cached --others --exclude-standard`へ変えて解消した。未追跡の`.rs`に`SAFETY`無しの`unsafe`を置き、変更前は素通りし変更後は検出されることを確認している

  この形の見落としは、検査の対象範囲が「今そこにあるもの」ではなく「gitが知っているもの」で決まっていたことによる。新規追加が最も検査を必要とする場面なのに、そこだけ穴が空いていた。`tools/docstyle.py`にも同じ列挙方法の穴があり、あわせて直した。他の検査についても、対象の列挙方法が同じ性質を持たないかを見ておくこと

  **なお`--exclude-standard`は`.gitignore`だけでなく`.git/info/exclude`も参照する。** つまり検査の対象範囲が、リポジトリに含まれないローカル設定によって決まる。ローカル専用のファイルを拾わないために必要な挙動だが、これも「対象が環境によって変わる」という点で今回の穴と同じ系統である。別の環境で検査を走らせたときに対象が変わりうることを承知しておくこと

- **直接`cli`/`sti`の許可リスト検査が、3つの検出経路のうち2つで何も見ていなかった**（seam整備の項目2で追加した直後に発覚）。追加時の破壊確認は`cpu::disable_interrupts()`の呼び出し1経路だけを壊して「検査は働く」と確認していた。**その1経路は実際に働いていたが、他の2経路は壊れていた。**

  - asmのオペランドは`"  cli",`のように**引用符の内側にインデントを付けて**書かれる。`"cli"`の完全一致で探していたため拾えなかった
  - 生の命令は`asm!(`と**別の行**に書かれる。`asm!`を含む行だけを見ていたため、複数行の`asm!`ブロック内を追えていなかった（`global_asm!`だけは塊を追跡していた）

  取りこぼしていたのが**許可リスト10箇所のうち唯一「本物の排他」である`kernel/src/task.rs`の`global_asm!`内の`cli`/`sti`**（`GPR_BUF`を守る直接操作）だった。許可エントリが載っているのに検出されない、つまりそのエントリが死んでおり、**asm内に`cli`を書く限りこの検査は何も守らなかった**。発覚の契機は「許可エントリ数と出現数の単位を明示する」という指摘で出現数を数え直したことである。数を数えたら0件のファイルがあった

  修正後は、文字列リテラルをtrimして先頭トークンで判定する形と、`asm!(`から`);`までを塊として追う形にした。出現数は10から12へ増えた（`task.rs`の2件が新たに数えられるようになった）

- **`asm!`が同じ行で閉じる形（`asm!("cli")`）で、塊の追跡が解除されず残りのファイル全部をasm内と誤認していた**（上の修正の直後に、経路ごとの破壊確認を続けて発覚）。単一行では閉じ`);`が独立した行に現れないため`in_asm`が立ったままになる。実測では、単一行の`global_asm!`を1つ置くだけで`current_item`が固定され、`interrupts.rs`の許可済み5箇所すべてが所属名の不一致で未許可と判定された。**FAILする方向なので静かには壊れない**が、正当な1行形を書くと検査が使えなくなる。`asm!(`の`(`から括弧の残高を数え（文字列リテラル内は数えない）、同じ行で閉じるなら塊に入れない形へ直した。検出は`opens_asm`でその行自体を拾う

  **単一行の`asm!`内の`cli`そのものは、修正前から検出できていた**（取りこぼしではなく、追跡状態の漏れだった）。検出経路は4つ（primitiveの呼び出し / 通常の複数行`asm!` / `global_asm!` / 単一行`asm!`）あり、修正後に4経路すべてを個別に壊して所属アイテム名まで特定してFAILすることを確認している

#### 追跡状態の漏れには2つの向きがあり、危険なのは静かな方である

上の修正で塞いだのは単一行の形だが、**塊の終端判定は今も「trim後に`);`で始まる行」という整形の形に依存している**。漏れたときに何が起きるかは、漏れた変数によって正反対である。

- **`in_asm`だけが漏れた場合（通常の`asm!`）: うるさい方。** 所属名の追跡は壊れない（`current_item`を更新する分岐は`in_asm`を見ないため）。影響は生命令の検出範囲が広がることだけで、しかも先頭トークンが`cli`/`sti`の文字列に限られる。実測でも許可済みは壊れずOKのままだった
- **`in_global_asm`が漏れた場合: 静かな方。見逃しになる。** `current_item`が`"global_asm!"`に固定される。許可リストは`(file, item)`で照合するので、**そのファイルに`(file, "global_asm!")`の許可エントリがあると、以降の未許可の`cli`/`sti`がその許可エントリと一致して素通りする**。`kernel/src/task.rs`には実際にそのエントリがある（GPR_BUFを守る例外(g)）

後者を実測した。非準拠の閉じ方をする複数行`global_asm!`（`cli`/`sti`を含まない）を`task.rs`へ置き、その後ろの通常の関数へ未許可の`asm!("cli")`を入れると、**FAILせずOKのまま通った**。唯一の痕跡は出現数が12から13へ増えたことだけである（許可済みとして数えられた）。

**この静かな経路を実際に塞いでいるのは`cargo fmt`である。** 非準拠の閉じ方を書いても、`cargo fmt`が単一行へ整形し直す（式レベルの`asm!`だけでなく、**itemレベルの`global_asm!`も正規化することを実測で確認した**）。単一行は上の修正で塊に入れないので、`in_global_asm`は漏れない。つまり不変条件「複数行のasmは`);`始まりの行で閉じる」は、**同じ検査一式に入っている`cargo fmt --all -- --check`が強制している**。

**したがって、fmt検査が守っているのは体裁ではなく見逃しの経路である。** fmt検査を外す、rustfmtの挙動が変わる、あるいはこの検査を`#[rustfmt::skip]`の付いたコードへ適用する場合は、この静かな経路が開く。下の分離提案を実施すれば、この依存は消える。

**【論点・未着手】検出をブロック追跡から切り離す。** 現在の構造は検出そのものが`asm!`塊の追跡に依存しており、**`asm!`の書き方の変種が増えるたびに取りこぼしや誤認のriskが出る**（実際にこの検査だけで3回それで壊れた）。
代案: 検出は「先頭トークンが`cli`/`sti`の文字列リテラル」だけで行い（この判定は既に実装済み）、**塊の追跡は所属名の特定にのみ使う**。
そうすると検出が書き方に依存しなくなり、壊れやすい機構が**安全性の経路から診断の経路へ移る**（追跡が甘くても「どこか分からない」だけで見逃しにはならない）。
誤検出のriskは小さい（`"client"`は先頭トークンが`client`で不一致、`"sti-check …"`も同様）。
**壊れやすい機構をload-bearingにしない**という、このリポジトリが繰り返してきた形である（`alloc`を未importにして確保を不可能にする、フィールドを削除して二重の真実を不可能にする）。

**この提案を支える証拠は3件ある。いずれも「その場しのぎのスキャナでソースを解析している」という同じ原因から出ている。**

1. 引用符の内側のインデント（`"  cli"`）を拾えなかった
2. 複数行の`asm!`ブロックを追えていなかった。さらにその修正後も、単一行の形で追跡状態が漏れた
3. `asm_call_closes_on_same_line`が文字列内のエスケープ`\"`で`in_string`を誤って反転させる（現コードには該当箇所が無く実害は無い。同関数は`line.find("asm!(")`で**最初の1つ**しか見ない点も同様）

3件目は対処していない。**分離すれば、これらはいずれも「所属名が分からない」だけの問題に落ちて見逃しにはならなくなる。** 上の「fmt検査への依存」も同時に消える。
急がないので、項目1の後か気づいたときに扱う。

**【論点・未着手】許可エントリごとに出現数を宣言する。** 許可リストの各エントリに、そのエントリが覆う出現数を持たせ（`{ file, item, reason, occurrences }`）、検査は実測の出現数と宣言値を照合して、食い違えばFAILする。
上の静かな見逃し（`in_global_asm`が漏れて未許可の`cli`/`sti`が`(task.rs, "global_asm!")`のエントリへ吸収される）は、痕跡が出現数の増加だけだった。宣言値と照合すれば実測3に対し宣言2でFAILするので、**静かな見逃しがうるさい失敗に変わる**。
`cargo fmt`への依存もload-bearingでなくなる。fmt検査を外しても`#[rustfmt::skip]`を使っても、静かな経路は数の照合で塞がれ、壊れ方がうるさい側に収まるためである。
「時点依存の数字を離れた場所に書かない」原則には反しない。数はエントリごとの局所的な事実であり、宣言は対象の隣に置かれる。正当な変更で数が変われば照合がFAILして再承認が強制される（許可エントリを行番号ではなく関数名で識別する利点と同じ論理である）。
上の分離提案とは直交する。分離は所属名の精度を、数の照合は取りこぼしの検出を守るので、分離を実施しても無駄にならない。変更としては分離より小さい。

**ここから一般則を1つ立てる。検出経路が複数あるなら、破壊は経路ごとに行う。**
1経路で発火したことは、他の経路の健全性を何も意味しない。
上の事例では4経路（primitiveの呼び出し / 通常の複数行`asm!`内の生命令 / `global_asm!`内の生命令 / 単一行`asm!`）があり、確認したのは1経路だけだった。
修正後は4経路すべてを個別に壊して、いずれも所属アイテム名まで特定してFAILすることを確認している。
BKL本体で新しい検査を作るときも、まず検出経路を数え、経路ごとに壊すこと。

**経路の数え上げ自体が更新される点にも注意する。** この節は最初「3経路」と書いていた。単一行`asm!`という4つ目に気づいたのは、経路ごとの破壊確認を実際に進めている途中である。
数えたつもりの一覧が完全である保証はないので、**新しい書き方に出会ったらその都度経路として数え直すこと。**

- **公開範囲が広いと、未使用のコードが見えない。** 割り込み層の境界（S0-a）で`pub mod pic;`を`mod pic;`へ落とした瞬間、`pic::send_end_of_interrupt`が`dead_code`として現れた。公開モジュールの中では「外から呼ばれうる」と見なされて警告されないためである。**境界を閉じることは、死にコードの自動的な露出でもある。** 実際にはEOIの経路は`send_eoi_for(eoi_action_for(...))`だけで、この関数はどこからも呼ばれていなかった。

#### 列挙で守る検査は、列挙に無い形を静かに通す

**これは上の3件とは別の型である。** 上の3件は「検査が壊れて何も見なくなった」形で、こちらは**検査が見る範囲を最初から取りこぼしている**形である。対処法も違う。前者は破壊確認を増やすことで捕まるが、後者は破壊確認を増やしても、列挙に無い形を思いつかなければ捕まらない。

S0-aだけで2回起きた。いずれもコミット前に捕まえたので実害は出ていない。

- 当初の静的検査の案は「境界の外に`pic::`の参照が無いこと」を見る形だった。ところが非公開化と組み合わせると、参照はコンパイラが禁じるので、**検査が実際に見るのはコメントだけ**になっていた（設計段階で差し替えた）
- 可視性検査は`mod`と`use`だけを列挙しており、`pub type Alias = pic::Inner;`を素通りさせていた。別名を通せば内部の型を外から掴めるので、`pub use`と同じ実在の穴である（破壊確認の直前に気づいて`type`を足した）

**教訓は「列挙型の検査を作ったら、列挙に無い形で同じ結果に到達できないかを別途探す」である。** 探し方は、検査ではなく**目的**から測ることになる。可視性検査でいえば「境界の外に1行置いてビルドが通るか」を測る手順がその探索そのものだった。検査がFAILすることと、実際に到達できることは別の命題である。

**ビルド成果物を測るときは、どのfeature構成でビルドされたものかを確かめること。** `cargo xtask check --full`の最後の項目はサボタージュfeature付きのビルドなので、`target/`にはその成果物が残る。直後に`nm`で`__kernel_end`を測ると、既定ビルドとは違う値（実測で0x248小さい）を静かに読む。実際にS0-bの報告で1度これをやり、「コードが縮んだ」と誤った記録を書いた（同一コミットで再ビルドして再現しないことから発覚した）。**規律ではなく出所で防ぐ。** 手順を「測る前に既定ビルドをやり直す」とすると規律に頼ることになるので、**イメージ会計の値は起動ログから取ることを既定にする**（起動ログには既定ビルドの値しか出ない）。これは「同じ条件で比べていないものを比べていた」の系列で、比較の対象がログではなく成果物になった形である。実際、当時ログと`nm`は食い違っており、**ログのほうが正しかった**。

**静的検査の対象指定は、宣言がどこに書かれているかに依存する。** これは上の「列挙に無い形」と同じfamilyの別の面で、**対象範囲の外を静かに通す**形である。S0-bで可視性検査の対象へ`kernel/src/task/`を足したが、**破壊確認が発火しなかった**。`mod scheduler;`の宣言は`kernel/src/task.rs`にあり、ディレクトリの外だったためである（`irq`は宣言が`irq/mod.rs`の中にあるので、この依存に気づく機会が無かった）。ファイルを明示して対象に入れ、再度の破壊確認でFAILすることを確かめた。**対象をディレクトリで指定したときは、守りたい宣言がそのディレクトリの中にあるかを確かめること。**

**禁じている形と、実際に漏れる形は一致しない。** 可視性検査が禁じる6形のうち、外から到達できるのは5つで、配下の非公開ファイルからの`pub(crate) use`だけは到達できない（実効可視性が親モジュールで頭打ちになる）。**保守的に禁じているだけの形が混じっていることを、検査のコメントに明記した。** 「6形すべてを壊してFAILした」とだけ書くと、6形すべてが実在の穴だったと読めてしまう。

**マーカーは行の部分文字列であって、行の構造や書式の証拠にはならない。** xtaskの期待マーカーは`contains`で照合するので、行の前半だけを切り取った文字列が入っている。これを見て「行がこう組み立てられている」と判断すると誤る。S0-aの設計中に2回、存在しない書式の食い違いを想定した（要約行のベクタ範囲は静的な文字列リテラルであり、IMRのログ行は元から期待値の後置きを持っていた）。**書式を論じるときは起動ログの実際の行を見る。**

同じ型の誤り（検査があるように見えて何も検査していない）は本節でこれが3件目である。
`ADR-0018`のAddendum 4が「過去2回の誤り」として記録していたおかげで、3件目だと即座に分かった。
記録しておくと、次に踏んだときに単発の失敗ではなく反復として扱える。

計測についても同じ型の失敗をしている。いずれも「同じ条件で比べていないものを比べていた」というものである。

- 比較用のworktreeと本体を交互に走らせるつもりで、`cd`がループの次の行にも効いていたため6回すべてworktree側で走っていた。所要時間が109.35 / 109.36 / 109.37秒とほぼ同一だったことが手掛かりになった。数字が揃いすぎているのは異常である
- worktreeを`/tmp`の深い階層に置いたため、そちらだけmonitorソケットのパス長が上限を超えて失敗していた。場所の違いが結果の違いとして現れており、比べたかった変更の効果ではなかった。本体で条件を切り替えて測り直した

**数字が出ていても、条件が違えば意味を持たない。**
比較する前に、比べている2つが本当に他の条件で揃っているかを確かめること。

コミットの検査は件名だけを見ており、**本文は対象外と決めている**。
文体規約の目的は公開時の見え方を整えることで、主な対象はREADME・docs・コード内コメントである。
本文には識別子や式（`is_multiple_of`、`% 16 == 0`、`#TS / #NP / #SS / #GP`など）がそのまま現れ、和文と隣り合う箇所で空白を落とすと読みにくくなる。
バッククォートで囲む書き方をコミットメッセージへ課すのは一般的でなく、揃えるために履歴の書き換えを増やすコストにも見合わない。
保留ではなく決定であり、後から再検討しない。

### 検査では原理的に見えない誤り

上の節と分けてあるのは、対策が違うためである。あちらは検査を直せば捕まる。こちらは**どのテストを足しても捕まらない**ので、別の検出手段に頼るしかない。

- **インヘレントメソッドがトレイトメソッドに食われていた**（S1-b-2）。`RootEntries`に`fn count(&self)`を定義したが、`entries.count()`が呼んでいたのは`Iterator::count`だった。Rustのメソッド探索は受け手の型を`T`→`&T`→`&mut T`の順に試し、各段でインヘレントを先に見る。したがって**値レシーバのトレイトメソッドは、`&self`のインヘレントメソッドより先に一致する。** `entry_count`へ改名して解消した。

  **結果の値が一致していたので、どのテストでも捕まらなかった。** 数え方が同じである以上、出力は正しい。唯一の検出経路は`dead_code`警告（定義したのに呼ばれていない）だった。**警告を`-D warnings`で落としていることが、ここでは検出手段そのものになっている。** 一般化すると、「別のものが呼ばれているが結果は同じ」という誤りは、値を見る検査では原理的に見えない

### 保守的な検査が実コードで働いた例

破壊確認ではなく、通常の実装中に発火した記録である。**検査が生きていることの証拠になるので残す。**

- **可視性の静的検査が、新規コードの入れ子`pub mod`を捕まえた**（S1-b-2）。`kernel/src/acpi/madt.rs`にエントリ種別の定数群を`pub mod entry_type { … }`として書いたところFAILした。実効可視性は親（`mod madt`）が非公開なので外からは触れず、漏れる形ではない。それでも禁じているのは、`mod madt`を`pub`にする1文字で漏れる形へ変わるためで、S0-aで`pub(crate) use super::pic::*;`を保守的に禁じたのと同じ判断である。

  **緩めなかった。** 入れ子を許すと「親が非公開だから漏れない」という推論が毎回必要になる。この検査の価値は推論が要らないことにある。接頭辞つきの定数（`TYPE_LOCAL_APIC`など）へ平坦化して解消し、平坦化した理由をコードに残した（残さないと、きれいにしようとした人が入れ子へ戻す）

### IMRへの書き込みは割り込み層の境界の内側だけに存在する

出典: ADR-0018、`architecture.md` §6.8、seam整備の項目1（S0-a）

かつてここには「IRQの解禁は1箇所へ集約する」と書き、検査は無いとしていた。
S0-aで`kernel/src/irq/`の内部（`pic` / `pit`）を非公開にしたので、**境界の外からIMRの読み書き関数を呼ぶとビルドが落ちる**。参照が無いことはコンパイラが保証し、その保証が外されないことを可視性の静的検査が守る。

**見出しを書き直したのは、保証できる範囲が「解禁が1箇所」ではないためである。** 解禁の呼び出しは現在2箇所ある（タイマとキーボードで前提条件が違う）。無理に1箇所へ寄せる理由が無いので、集約は求めない。呼び出し箇所の集約を将来求めるなら、それは別の論点として`deferred-decisions.md`へ置く。

この検査が守らない範囲を明示する。

- **境界の公開関数が生の値を返す形は捕まらない。** `pub fn read_masks() -> (u8, u8)`を`irq`へ足せば、可視性はprivateのままでも呼び出し側はPICの語彙を持てる。これはレビューで守る
- **コメント内の言及は対象外。** コメントは実行されないので結合を作らない。`pic`は`topic`の部分文字列でもあり、素朴な一致は誤検出源になる
- **生のI/Oポート直叩きは対象外。** 境界の外から`outb(0x21, …)`と書けばIMRは触れる。現在そのような箇所が無いことは実測で確認したが（`outb` / `inb`の全件を見て、PICのポートを触るのは`irq/`の中だけ）、この検査はそれを見ていない。`cli`/`sti`を`common::cpu`へ集約したときと同じ構造で、primitiveの集約が先にあって初めて「経由しない呼び出し」を検査できる
- **禁じている形と実際に漏れる形は一致しない。** 破壊確認では、`pub mod` / `pub(crate) mod` / `pub use` / `pub type`の4つが外から到達でき、配下の非公開ファイルからの`pub(crate) use`は到達できなかった（実効可視性が親モジュールで頭打ちになるため）。後者は保守的に禁じているだけである。禁じたままにするのは、`mod compat;`を`pub mod compat;`に変えるだけで到達できる形になるためで、その1文字の差を検査の外に置きたくない

### 割り込み層の境界（S0-a）からS2への申し送り

PIC/PITをLocal APIC / IO-APICへ差し替える段（S2）で、境界の内側だけでは済まない箇所がある。S0-aの作業中に実測で分かったものを残す。

**xtaskのマーカーがPIC固有の文言と値に依存している（3件）。** いずれも部分一致で照合しているので、文言が変わればテストが落ちる。S2ではマーカー側を問いベース（`MaskCheck::matches`など）へ移す作業が要る。

| マーカー | 依存しているテスト | 何がPIC固有か |
|---|---|---|
| `pic: IMR after unmasking IRQ0 master=0xfe slave=0xff` | interrupt-test timer / no-eoi | IMRが2バイトという形 |
| `pit: channel 0 set to divisor=11932` | interrupt-test no-eoi | 分周値はPITの語彙 |
| `sti-check summary: 4. PIC remapped to 0x20-0x2F = UNVERIFIABLE` | interrupt-test enable-only | ベクタ範囲 |

境界の観測値のうち、依存があるのは`MaskCheck`と`TimerSetup`のDisplayである。`ObservedMasks` / `managed_vectors` / `ServiceSnapshot`が出す行にはどのテストも一致を取っていない（実測で確認）。

**S2で形が変わる観測値。** `ServiceSnapshot`はマスタのISRだけを持つが、IO-APICに従属コントローラは無いのでmaster/slaveの区別自体が消える。`MaskCheck`のIMR 2バイトも、redirection tableでは成り立たない。

**`sti-check`の要約行の項目名は静的な文字列である。** `4. PIC remapped to 0x20-0x2F`はベクタオフセットから組み立てていないので、`alt-offset-test`（0x30-0x3Fへ再マップする構成）では事実と食い違う。直すと当該ビルドのログ文言が変わるため、振る舞い不変を要求される段では触れない。なお**この項目が`UNVERIFIABLE`なのは、sti前の時点でICW2を読み戻せないためである。** 再マップが実際に効いていることは`alt-offset-test`と最初のティックの到達が事後に示しており、カバレッジの穴ではない。

**起動ログを変更前後で突き合わせるときに除外するもの。** 変動フィールド（ティック数・経過秒・ループ周回数・`max tick jump`・`resumes` / `iterations` / `switches`・実アドレス）に加えて、**UEFIメモリマップ由来の値**を除く。具体的には`descriptors_len`と、そこから導かれる空きフレーム数・除外ページ数・使用中の空き範囲数・メモリマップバッファの終端である。理由は、**同一コミット・同一のQEMU引数でも130本と132本の両方が出る**ためで、単調増加でもない。OVMFの変数ストアは毎回テンプレートから作り直しているので蓄積ではなく、機序は特定していない。現時点でこれらの値に一致を取っている検査は無い（実測で確認）。空き範囲は9〜10 / 256で、容量に対する余裕は十分ある。

**イメージ肥大の会計。** S1-b-2完了時点で`__kernel_end`は`0xffffffff801a82d0`（物理`0x1a82d0`）、2MiB境界（物理`0x200000`）までの余裕は`0x57d30` = 約351.3 KiB。S1-b-1完了時点は`0x1a12d0`（余裕`0x5ed30` = 約379.3 KiB）で、S1-b-2での増加は`0x7000` = 28.0 KiB。S1-a完了時点は`0x19c2d0`（余裕`0x63d30`）、S0-b完了時点は`0x19c2c8`（余裕`0x63d38`）、S0-a完了時点は`0x19c2d0`である。**値は起動ログから取ること。** 起動ログは既定ビルドの実行結果そのものなので、サボタージュ成果物を読む余地が構造的に無い（`higher-half: arrived at high VA`の行が`__kernel_end`を含む）。`nm`を使うのは、ログに出ていない記号を見たいときに限り、そのときは明示的に既定ビルドをやり直す。`cargo xtask check --full`の最後はサボタージュfeature付きのビルドで終わるので、その直後に`target/`の成果物を測ると別のビルドの値を読む（実測で`0x19c080`になり、既定より0x248小さい）。カーネル高位マッピングのページテーブルは3枚（`PML4[511]`）のままで、2MiB境界を跨いでいない。跨ぐとPTが1枚増えてこの数字が変わる。

**`__kernel_end`は4KiB単位で量子化されている。「増加0バイト」は「コードが増えていない」を意味しない。** リンカスクリプトは各セクションを`ALIGN(4K)`で配置し、`__kernel_end`は`.bss`の末尾である。したがってこの値が動くのは、`.text`/`.rodata`/`.data`の増加が4KiB境界を越えて`.bss`の開始位置を押し出したときか、`.bss`自体が増えたときだけである。実測（S1-b-1）では、コードと文字列リテラルを足しても`__kernel_end`が1バイトも動かない一方、`higher-half: arrived at high VA`行のRIPは動いていた。**バイナリが違うことはRIPが示し、`__kernel_end`が同値であることはセクションの余白が吸ったことを示す。** 同値を見たときは、測り間違い（別構成のビルドを読んだ等）と量子化を区別すること。区別する材料はRIPと`readelf -S`のセクション境界である。

### ACPIテーブルへ触る前提（S1-b）

**参照する物理アドレスは、読む前に`ActivePageTable::translate`で実際にwalkして確かめる。** 計画（`MappedRanges::contains_range`）は「そう張るつもりだった」ことしか言わず、「計画にあるが実際には張られていない」を見逃す。B-2a-5が実証した穴と同じ性質である。walkは翻訳の有無だけでなく、**翻訳が当の物理ページを指していること**まで見る（direct map窓は`base + phys`なので、翻訳結果は元の物理と一致するはずである）。マップされていなければ`#PF`で落ちず、検出して報告する。

**マップされるかは型で決まる。回数では決めない。** `classify()`は型を見てマップするかを決めるので、ACPIテーブルが載っているUEFIメモリ記述子の型が分かれば、その領域がマップされるかは構造的に決まる。`EfiACPIReclaimMemory` / `EfiACPIMemoryNVS`なら常に写り、`EfiReservedMemoryType`なら常に写らない。メモリマップの細部（各領域の大きさや個数）は起動ごとに揺れるが、この関係は動かない。「何回起動しても毎回マップされていた」を根拠にすると、20回連続PASSでベースラインを誤った件と同じ型の誤りになる。**したがって観測して記録するのは型である。**

実測（QEMU + OVMF、`-m 256M`、5回の起動）では、RSDP・XSDT・MADTの3つとも同じ記述子`0xf76d000..0xf77f000`に載っており、その型は`EfiACPIReclaimMemory`（型9）である。`classify()`は`ReservedButMapped { cacheable: true }`を返すので、この領域は常にマッピング計画へ入る。**この記述子は`EfiReservedMemoryType`の穴（実測`0xf6ed000..0xf76d000`、architecture §6.4）の直上にある。** 穴の側に落ちていれば写らなかった。危険は仮想のものではない。

5回の起動は「型が起動ごとに変わらないこと」の確認に使ったのであって、回数そのものを根拠にはしていない。**根拠は型である。**

**ACPIテーブル用の一時マッピングは作らない（S1-b-3の結論。この段は畳んだ）。** ただし根拠の中で構造と観測を混ぜないこと。**「型9がマップ対象である」は構造**で、`classify()`がそう決めている以上揺れない。**「テーブルが型9に載っている」は観測**であり、別のファームウェアや実機では変わりうる。5回同じだったことはこの観測を強めるが、構造にはしない。したがって結論はこうなる。

- テーブルが型9に載る限り、構造的にマップされる。だから一時マッピングを先回りで作る必要は無い
- どの型に載るかは観測でしか分からないので、**観測側は実行時の`translate`チェックが覆っている。** 型が変われば、そこで検出されて報告される

**`translate`チェックは保険ではなく、この結論の一部である。** 「型9だから安全」とだけ読んだ人がこのチェックを冗長だと判断して外すと、結論の観測側の根拠が消える。外さないこと。

**RSDPが名乗る長さは「検証済み / 不正 / 検証不能」の3状態で扱う。** 仕様の最小サイズ（36バイト）を下回る値はどの版でも正当になりえないので不正である。一方、読み取りバッファ（64バイト）を超える長さは**壊れているとは限らない**。将来の版が長いRSDPを出すことは仕様の範囲内で、こちらが読めないだけである。これを不正として報告すると観測していないことを観測したと書くことになり、黙って36バイトで検算すると「検証したことにする」ことになる。どちらも避けるために第3の区分を置いた。`sti`前の7項目が同じ3状態を持ち、PICの再マップが書き込み専用レジスタゆえに「検証不能」へ落ちるのと同じ形である。検証不能な長さでチェックサムの検算へ進めないことは型で塞いである（`VerifiableLength`は`declared_length`だけが作れる）。

**S1では検出して報告し、起動は継続する。** ACPIが読めないだけで単一コアのカーネルが起動しなくなるのは機能的な後退である。致命へ格上げするのはACPI無しでは進めなくなるS2（APIC移行）である。破壊featureの期待マーカーにハートビートを入れてあるのは、検出した後もカーネルが動き続けることまで見るためである。

**MADTのエントリ走査が止まることは、打ち切りカウンタではなく不変条件で保証する。** エントリは「type(1) + length(1) + 本体」の可変長で、`length`はファームウェアが書いた値だから0でありうる。素朴に`offset += length`と書くと同じ位置を読み続けて無限ループになり、症状は「起動ログが途中で止まる」という切り分けにくい形で出る。守りは2つで、片方では足りない。エントリ長が最小（2）未満なら停止するので前進量は必ず2以上になり、`length`が残りバイト数を超えるなら停止するので範囲外へ出ない。前者だけでは最後のエントリが残りを超えたときに範囲外へ出て、後者だけでは`length == 0`で残りが減らずに回り続ける。両方あって初めて「残りは単調に減り、0未満にならない」が成立する。ホストテストでは、任意のバイト列256通りに対して有限回で終わることを確かめている。

**S1-b-2の破壊feature 6種は、検出経路ごとに分けてある。** 署名・チェックサム・長さ・エントリ長0・未マップ・窓の外である。1つの破壊で複数の経路が同時に落ちると、どれが働いたのかが分からない。エントリ長0の破壊がチェックサムのバイトを合わせ直しているのはそのためで、合わせ直さないと先にチェックサムが破れて走査へ到達せず、「エントリ長0の検出を見た」ことにならない。破壊した経路と観測した経路が食い違う形は、このプロジェクトが繰り返している誤りの型そのものである。**未マップの破壊はアドレスをリテラルで持たない。** `classify()`が`Unmapped`にする最大の記述子の中点を実行時に求める。穴の位置は起動ごとに揺れるので、リテラルで焼き込むと穴が動いた起動で破壊が破壊にならず、検査が静かに通る。中点を採るのは、未マップ領域の先頭が隣の2MiBページに巻き込まれて写っている可能性を構造的に排除するためである。

**`-smp 2`での列挙は検査項目にした。** roadmapのS1到達条件に「`-smp 2`で起動しても列挙結果がQEMUの指定と一致すること」とあるのに、手動実行でしか確かめていなかった。**手動確認は再現されず、必ず腐る。** 全項目を複数のコア数で回すと項目数も時間も倍になるので、この1項目だけを2コアで回す（費用はQEMU起動1回）。禁止マーカーは`1 local APIC(s) of which 1 usable`で、これは既定（1コア）の起動で毎回出る行である。**したがってこの項目は`-smp`が効いていなければ通らない。**

**S2への申し送り（S1-b-2の実測）。** MADTのFlagsは`0x1`で、**PCAT_COMPATが立っている。** この系にはデュアル8259があるという意味なので、Local APIC / IO-APICへ移る前にPICをマスクする必要があることは確定している。Local APICは`0xfee00000`、IO-APICは`0xfec00000`（IDは0、GSIベースは0）で、いずれもMADTから得た値である（既定値のハードコードではない）。Local APIC Address Overrideのエントリは無かった。**Interrupt Source Overrideが5件ある。** S1では記録だけで解釈していないので、レガシーIRQとGSIの対応（IRQ0がGSI2へ移る形など）はS2で解釈すること。

**S3への申し送り（テーブル読み取りバッファの限界）。** MADTは概ね`44 + N×8`バイトなので、**100コア規模で1KiBの読み取りバッファを超え、「検証不能」に落ちる。** ZaytOSがその規模を扱う日は遠いが、限界が存在することを知らずに踏むのとは違う。超えたときはチェックサムを検算していないので中身を使わない、という扱いのままである。

**`ReadError`の5区分のうち、実機で到達させているのは2つである。** `OutsideWindow`と`NotMapped`は上記の破壊featureで到達する。`Aliased`は窓の登録値を壊す必要があるが、その破壊（`paging-test-directmap-wrong-base`）はA-2の検証で先に停止するのでここへは届かない。`Untranslatable`は1GiBページに当たった場合で、ZaytOSは1GiBページを作らないため到達手段が無い。**「到達手段が無い」と「足していない」を混ぜない。**

**S1-b-1の時点で、実機では正常系しか通っていない。** 未マップの物理を踏んだときの検出、署名・チェックサム・長さの破れの検出は、いずれもホストテストで判定側を閉じただけである。実機での破壊確認はS1-b-2の破壊featureで行う。`ReadError`の5区分のうち`OutsideWindow`と`NotMapped`は、RSDPの物理アドレスを故意に差し替える破壊featureで到達できる（S1-b-2で検討する）。`Aliased`は窓の登録値を壊す必要があるが、その破壊（`paging-test-directmap-wrong-base`）はA-2の検証で先に停止するのでここへは届かない。`Untranslatable`は1GiBページに当たった場合で、ZaytOSは1GiBページを作らないため到達手段が無い。

### SMPで既存の検査がどう変わるか（S1からS6の申し送り）

複数コアになると、既存の検査のうちいくつかは「通るが意味が変わる」状態になる。着手時に気づけるよう、実コードで確認した範囲を記録する。

- **QEMUのコア数は検査の構成軸になる。** 現在xtaskは`-smp`を渡していない（既定1コア）。`-smp 1` / `2` / `4`を回すことになるが、QEMUを起動する項目をすべて3構成にすると項目数が3倍になり所要時間もそのまま3倍になる。**どの項目を3構成で回すかの基準を先に決めること**（例: per-CPUデータに触る / スケジューラに触る / 割り込みに触る）。基準がないと選び方が恣意的になる。項目数が変われば会計行も更新する。
- **割り込みの会計はコアごとの帰属を失う。** `INTERRUPT_COUNTS`（ベクタ別カウンタ）は共有の`AtomicU64`配列で、`TIMER_TICKS`も大域である。複数コアでは合計としては閉じるが、「どのコアが受けたか」は分からなくなる。ハートビートをper-CPUへ広げるかをS3の到達条件と併せて決める。
- **`task-preempt-in-critical`が見ているものが変わる。** 現在は「同一コアで`critical`区間にプリエンプトが食い込み二重取得を検出する」を見ている。複数コアではBKLの本来の競合は「別コアが同じロックを取る」形になる（`deferred-decisions.md`の該当行）。
- **per-CPUデータの置き場所が破壊featureを壊しうる。** `highhalf-remove-verify-fail`はサボタージュVA`0xffff808000000000`（`PML4[257]`）が空であることに依存している。per-CPUデータを`PML4[257]`へ置くとこの破壊が意味を失う。置き場所を決めるときにサボタージュVAの移動をセットで扱う。
- **BKLで確かめるのは排他だけではない。** 恒等除去のような不可逆な操作ではないので復帰経路は要らないが、失敗の形が「デッドロックして静かに止まる」になる。安全性（カーネル内の同時進入数が1）と進行性（全コアが進んでいる）の両方を見て、待ちがタイムアウトしたら無言で継続せず原因を出すこと。

### 公開前の監査

公開リポジトリに、実装内容と無関係なもの（個人メモ、作業ログ、意図せず混入した一時ファイル）が残っていないかを確認する。
次の順序で行う。

1. `git ls-files`と`git rev-list --all --objects`の**全件を目視**し、想定外のファイルが無いか確認する。ビルドや実行に不要なものが混ざっていないかを見る
2. 非ASCIIファイル名の検出（`grep -P '[^\x00-\x7F]'`）。日本語名の一時ファイルは意図せず混入しやすい
3. **ファイル内容の文字種検査。** 追跡対象ファイルと未コミットの変更を対象に、非ASCII文字をUnicodeブロック別に集計し、想定外のものが無いか確認する。想定しているのは、ひらがな・カタカナ・CJK統合漢字・CJK記号句読点・半角全角形・矢印・罫線素片・数学記号・`§`のみ。想定するブロック以外が現れたら、その所在を確認する

   ファイル名だけを見ても内容の混入は分からない。見た目が同じでもコードポイントの異なる字が紛れうるので、目視ではなくブロック別に機械的に集計する
4. 現在の追跡ファイルと全履歴パスの差分を取り、削除・改名されたものを洗い出す
5. **その後に**キーワード検索を行う

**キーワード検索は補助であって主ではない。**
パターンに含まれないものは見つからないため、検索の「出力なし」は、そのパターンに含まれていない対象については何も証明しない。
まず全件を見ること。

あわせて、全コミットメッセージと著者・コミッタ情報、ライセンス表記も確認する。

### 変更の危険度による扱いの区別

次に該当する変更は、確定させる前に差分と関連ログを突き合わせて確認する。
まとめて後から見直さない。

- `unsafe`ブロックを新規に含む、または既存の`unsafe`の前提を変える変更
- 割り込みハンドラ（IDT）・例外ハンドラに関わる変更
- ページテーブル操作・仮想メモリマッピングに関わる変更
- GDT / TSS / セグメンテーション周りの変更
- クリティカルセクション（`cli`/`sti`による割り込み禁止区間）の設計変更
- `architecture.md` §2の確定済みアーキテクチャに影響する変更

いずれも「間違えても即座には落ちず、しばらく動いた後に壊れる」性質を持つ。
落ちた時点と原因の距離が遠いため、書いた直後に確認する価値が最も高い。

マイルストーンへ到達した時点でも同じ確認を行う。
これは変更の種類ではなく時点だが、区切りごとに全体を見直す機会として扱う。

上記以外の純粋ロジック・ドキュメント・テスト・ビルドスクリプトの変更は、この扱いの対象外である。
