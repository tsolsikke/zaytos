目的は、同じ問題に再び時間を溶かさないこと（EDK2 での挫折の教訓）。

- 設計判断は ADR（`adr/`）へ。ここには**実装上の詰まりと解法**を書く。
- 解決した非自明な問題は、その都度ここに追記する。

- 解法: どう直したか
- 教訓 / 再発防止: 次回同種の問題を避けるための注意点（任意）

## （例）YYYY-MM-DD QEMU が無言で無限リブートする
- 症状: カーネル起動直後、画面もログも出ずに再起動を繰り返す。
- 原因: トリプルフォルト。QEMU デフォルト設定では再起動して原因が見えない。
- 解法: QEMU 起動オプションに `-no-reboot -no-shutdown -d int,cpu_reset` を追加し、
  例外ログを取得して原因の割り込み/例外を特定した。
- 教訓: この 3 オプションは常時付与する。「ハング」と決めつける前に
  まず例外ログを確認する。

## 2026-07-19 `-d int,cpu_reset` ログに "CPU Reset (CPU 0)" が出るが異常ではなかった（M0）
- 症状: `cargo xtask run`（OVMF のみ、ブート可能デバイスなし）実行時、
  ログの冒頭に "CPU Reset (CPU 0)" が 2 回出力され、一見トリプルフォルトの
  無限リブートに見えた。
- 原因: 誤りではなく正常な電源投入シーケンス。1 回目は QEMU 自体の初期化、
  2 回目はリセットベクタ（`EIP=0000fff0`）へのジャンプであり、実機の電源投入
  直後の CPU リセットに相当する。その後 OVMF は正常に long mode
  （`CS64` / `EFER` の LME・LMA ビット）まで到達し、以降はタイマ割り込み
  （`Servicing hardware INT=0x20`）を継続的に処理するアイドルループに入って
  いた（ブート可能デバイスがないため、それ以上は進まない）。
- 解法: 対処不要。ログ全体を見て "CPU Reset" の後に long mode 到達・
  `INT=0x20` の定常的な処理が続いていることを確認し、実際の無限リブート
  ループ（"CPU Reset" が全編にわたって連続する）ではないと判断した。
- 教訓 / 再発防止: 起動直後の "CPU Reset" が 1〜2 回だけなら正常な電源投入
  シーケンスの一部であり得る。異常判定は「"CPU Reset" の有無」ではなく、
  「ログの後半まで見て long mode 到達後もリセットが連続しているか」で行う。
  M1 以降で本物のトリプルフォルトを疑う際は、この基準ログ（起動直後 2 回で
  収束し、その後は `INT=0x20` の定常ループになる）と比較すること。
