## （例）YYYY-MM-DD QEMU が無言で無限リブートする
- 症状: カーネル起動直後、画面もログも出ずに再起動を繰り返す。
- 原因: トリプルフォルト。QEMU デフォルト設定では再起動して原因が見えない。
- 解法: QEMU 起動オプションに `-no-reboot -no-shutdown -d int,cpu_reset` を追加し、
  例外ログを取得して原因の割り込み/例外を特定した。
- 教訓: この 3 オプションは常時付与する。「ハング」と決めつける前に
  まず例外ログを確認する。

## 2026-07-19 `-d int,cpu_reset` ログに "CPU Reset (CPU 0)" が出るが異常ではなかった（M0）
- 症状: `cargo xtask run`（OVMF のみ、ブート可能デバイスなし）実行時、
  ログの冒頭に "CPU Reset (CPU 0)" が 2 回出力され、一見トリプルフォルトの
  無限リブートに見えた。
- 原因: 誤りではなく正常な電源投入シーケンス。1 回目は QEMU 自体の初期化、
  2 回目はリセットベクタ（`EIP=0000fff0`）へのジャンプであり、実機の電源投入
  直後の CPU リセットに相当する。その後 OVMF は正常に long mode
  （`CS64` / `EFER` の LME・LMA ビット）まで到達し、以降はタイマ割り込み
  （`Servicing hardware INT=0x20`）を継続的に処理するアイドルループに入って
  いた（ブート可能デバイスがないため、それ以上は進まない）。
- 解法: 対処不要。ログ全体を見て "CPU Reset" の後に long mode 到達・
  `INT=0x20` の定常的な処理が続いていることを確認し、実際の無限リブート
  ループ（"CPU Reset" が全編にわたって連続する）ではないと判断した。
- 教訓 / 再発防止: 起動直後の "CPU Reset" が 1〜2 回だけなら正常な電源投入
  シーケンスの一部であり得る。異常判定は「"CPU Reset" の有無」ではなく、
  「ログの後半まで見て long mode 到達後もリセットが連続しているか」で行う。
  M1 以降で本物のトリプルフォルトを疑う際は、この基準ログ（起動直後 2 回で
  収束し、その後は `INT=0x20` の定常ループになる）と比較すること。

## 2026-07-19 OVMF が ESP の kernel.efi を自動起動せず、内蔵 UEFI Shell で止まる（M1）
- 症状: `target/esp/EFI/BOOT/BOOTX64.EFI` を用意し、QEMU の `fat:rw:` ドライバで
  仮想 FAT ドライブとして渡しても、`cargo xtask run` はシリアル出力・画面
  出力とも変化がなく、`-d int,cpu_reset` のログ上は「ブート可能デバイスが
  ない場合」と全く同じ定常アイドルループ（`Servicing hardware INT=0x20` が
  同一 IP アドレスで反復するだけ）に見えた。
- 原因の切り分け: QEMU モニタ（unix ソケット経由の HMP）で `info block` を
  確認したところ、ドライブ自体（`ide0-hd0`, vvfat 経由）は正しく認識されて
  いた。`screendump` で実際の画面を確認すると、OVMF は ESP を自動起動する
  のではなく、既定の起動オプションとして組み込みの **UEFI Interactive
  Shell** を起動し、`Shell>` プロンプトで待機していることが判明した
  （machine type を q35→pc に変更した経緯は ADR-0007 参照。この Shell への
  フォールバック自体は machine type に依らず発生した）。
- 対処（回避策）: シェルは起動直後に `startup.nsh` を探して自動実行する
  （"Press ESC in N seconds to skip startup.nsh..." の表示で確認できる）。
  そこで `xtask` から ESP のルートに `startup.nsh`
  （内容: `FS0:\EFI\BOOT\BOOTX64.EFI`）を書き込み、シェル経由で明示的に
  `kernel.efi` をチェインロードさせることで起動できるようにした。
- **これは回避策であり、根本解決ではない。** なぜこの Ubuntu 配布の OVMF
  ビルドが `\EFI\BOOT\BOOTX64.EFI` の既定起動探索より先に組み込み Shell を
  優先するのか（ビルド時の設定・NVRAM 初期値・BootOrder の既定値など）は
  未調査・未解明のまま。`startup.nsh` が無い環境や、OVMF のバージョン/
  ビルド設定が変わった場合には再度この問題に当たる可能性がある。
- 教訓 / 再発防止: 「ブートデバイスが認識されない」ように見える symptom は、
  実際には「シェルへ既定でフォールバックしていて何も画面に出ていないだけ」
  である場合がある。QEMU モニタ（`info block`）とスクリーンダンプ
  （`screendump`）で実際の画面状態を確認してから原因を切り分けること。
  根本原因の調査（OVMF のビルド設定・BDS 挙動の追跡）は、この回避策が
  何らかの理由で崩れたときに改めて着手する。

## 2026-07-20 UEFI メモリマップの "reserved" 合計が 12GiB 相当と異常に大きい（M2-c）
- 症状: 物理フレームアロケータ初期化時のログで、QEMU に `-m 256M` しか
  割り当てていないにもかかわらず、`EfiReservedMemoryType` として除外した
  ページ数の合計が 3,145,856 ページ（4096 バイト/ページ換算で約 12GiB）と
  表示され、実装ミスを疑った。
- 原因の切り分け: 一時的な診断コード（`kernel::memory_map::parse_entries`
  の結果を `RESERVED` エントリに限定してシリアルへダンプ）を追加したところ、
  以下の 2 エントリが見つかった。
  ```
  RESERVED phys_start=0xf6ed000    page_count=128     (0 MiB)
  RESERVED phys_start=0xfd00000000 page_count=3145728 (12288 MiB)
  ```
  後者の `phys_start=0xfd00000000`（約 1TB 付近）は、実際に搭載されている
  RAM（256MiB）とは無関係な、**PCI の 64bit MMIO BAR 用に予約された
  アドレス空間**である。QEMU/OVMF の既定構成では、実装されている物理
  メモリ量に関わらず、PCI デバイスの 64bit BAR を将来割り当てるための
  巨大なアドレス空間を `EfiReservedMemoryType` としてメモリマップに
  含めることがある。これは実 RAM の存在を意味せず、単なるアドレス空間の
  予約表明である。
- 解法: 対処不要。これは実装バグではなく、UEFI メモリマップの正常な
  内容である。`EfiReservedMemoryType` は元々「空き」の判定対象外（本文の
  型ベースの方針により自動的に除外）のため、フレームアロケータの動作
  そのものには影響しない。空きフレーム数（実測 205MiB / 256MiB 中）が
  実際に割り当てたメモリ量と整合していることの方が重要な確認ポイントで
  あり、そちらは正しかった。
- 教訓 / 再発防止: 「除外の内訳の合計」と「実際に割り当てたメモリ量」を
  単純に比較して「多すぎる/少なすぎる」と早合点しないこと。UEFI の
  メモリマップにはアドレス空間の予約（実 RAM の裏付けがないもの）が
  型 `EfiReservedMemoryType` 等として含まれうる。異常を疑ったら、まず
  型別の内訳ログ（本プロジェクトでは `frame allocator: excluded
  breakdown` に出力済み）でどの型が大きいかを確認し、必要なら該当型の
  生エントリ（`phys_start`/`page_count`）を個別にダンプして、その
  `phys_start` が実装物理メモリの範囲内かどうかを見る。今回のように
  `phys_start` が実装メモリを大きく超えるアドレス（例: 1TB 付近）を
  指していれば、実 RAM ではなくアドレス空間予約であると判断してよい。
  次に同じ規模の "reserved" 値を見ても、この記録を見れば再調査は不要。

## 2026-07-20 kernel/build.rs がターゲットを問わず link.ld を適用し、ホストテストが SIGSEGV する（M2-c）
- 症状: kernel クレートに `lib.rs` を新設し `cargo test -p kernel --lib`
  を実行したところ、テストの一覧表示（`--list`）の時点で
  `signal: 11, SIGSEGV: invalid memory reference` が発生した。
  個別のテストを絞り込んでも、テスト名が1つも表示される前にクラッシュした。
- 原因: `kernel/build.rs` が、ビルド対象（Cargo のターゲットトリプル）を
  一切確認せず、常に `cargo:rustc-link-arg=-T{manifest_dir}/link.ld` を
  発行していた。`link.ld` は `x86_64-unknown-none` 向け
  （エントリポイント `_start`、全セクションを `0x100000` に配置）を
  前提にしたリンカスクリプトであり、これをホスト向けの通常の実行可能
  ファイル（`cargo test -p kernel --lib` はデフォルトでホストターゲット
  向けにビルドされる）に適用すると、OS のプロセスローダーが期待する
  通常の ELF 構造（crt0・エントリポイント等）が壊れ、プロセス起動直後に
  セグメンテーション違反を起こす。
- 解法: `build.rs` で `std::env::var("TARGET")` を確認し、
  `x86_64-unknown-none` の場合のみリンカ引数を発行するよう修正した。
- 教訓 / 再発防止: `build.rs` はパッケージのどのターゲット（bin/lib、
  どのコンパイル対象トリプル向けか）をビルドする際にも実行される。
  クレート内に「特定のビルド対象専用」の設定（リンカスクリプト、
  特定アーキテクチャ向けの `cargo:rustc-link-arg` 等）を `build.rs` で
  注入する場合は、必ず `TARGET` 環境変数で対象を確認してから適用する
  こと。特に、bin クレートに後から `lib.rs`（ホストテスト用）を追加する
  ときは、既存の `build.rs` がホストビルドにも無条件に適用されてしまわ
  ないか必ず確認する。

## 2026-07-20 ページング計画の容量見積もり（64）が実機で不足した（M2-d, d-1）
- 症状: `kernel::paging::plan::MappedRanges` の初期実装時、容量
  （`DEFAULT_CAPACITY`）を「メモリ型ごとに 1 エントリ程度、10 前後」と
  見積もって 64 にしたところ、実機（QEMU + OVMF, 256MiB 割り当て）で
  実際にビルドしたところ `mapped-range capacity exceeded` エラーで
  fail-fast した。
- 原因: 見積もりが誤りだった。UEFI メモリマップは、同じメモリ型でも
  物理アドレス上で連続しない小さな断片が多数現れることがある
  （`EfiBootServicesData` 等が、ファームウェアの内部処理の都合で
  複数の離れた小領域として記録されるため）。「型ごとに1エントリ」を
  前提にした見積もりは、実際のメモリマップの構造を確認せずに行った
  ものだった。
- 解法: 容量を、マージ前の最悪ケース（メモリマップの総ディスクリプタ数）
  まで余裕を持たせ、フレームアロケータと同じ 256 に引き上げた。
- 教訓 / 再発防止: 固定長データ構造の容量を見積もる際は、「型ごとに
  1エントリ」のような単純化した仮定を置かず、実際のメモリマップの
  構造（総ディスクリプタ数、型ごとの断片化度合い）を実機で確認して
  から決めること。今回のように、容量超過を握りつぶさず fail-fast
  する設計にしていたため、実装ミスではなく見積もりの問題であることが
  即座に判明した（この設計判断の価値が実際に発揮された例）。

## 2026-07-20 GOP フレームバッファが UEFI メモリマップに含まれない（M2-d, d-1）
- 症状: `kernel::paging::plan::MappedRanges` をメモリマップのみから構築し、
  ページテーブルを実際に構築した後、必須領域の充足検証で
  `required range [framebuffer] 0x80000000..0x803e8000: NG` と表示された。
  フレームバッファの物理アドレス（`BootInfo.framebuffer.physical_address`）
  が、どのメモリマップエントリにも含まれていなかった。
- 原因の切り分け: 除外内訳ログの `mmio=1024`（1024 ページ = 4MiB）という
  数字が、フレームバッファのサイズ（4096000 バイト ≈ 1000 ページ）と
  近かったため、当初「フレームバッファは `EfiMemoryMappedIO` として
  メモリマップに含まれている」と誤って仮定していた。実際にはこの
  `mmio=1024` エントリは `phys_start=0xffc00000`（4GiB 直前の、PCI の
  低位 MMIO 窓としてよくある位置）であり、フレームバッファ
  （`phys_start=0x80000000`）とは無関係だった。GOP のフレームバッファは
  PCI デバイスの BAR（Base Address Register）としてマップされており、
  UEFI の `GetMemoryMap` が返す一般的なシステムメモリマップとは別の
  仕組み（PCI コンフィグ空間の走査）で見つかるものであり、そもそも
  メモリマップに現れるとは限らない。
- 解法: `MappedRanges::build` に `extra: &[(start, end, cacheable)]`
  引数を追加し、`BootInfo.framebuffer` から得たフレームバッファの範囲を
  メモリマップとは独立に明示的に追加するようにした（`cacheable=false`
  として、他の MMIO 領域と同様にキャッシュ無効でマップする）。
- 教訓 / 再発防止: 「除外内訳の値が近い」ことは、その領域が目的の
  ものであることの根拠にはならない（今回のように無関係な偶然の一致
  でありうる）。デバイスの MMIO 領域（フレームバッファ等）がメモリマップ
  由来の情報だけで必ず説明できるとは限らない。BootInfo 等、他の経路で
  得られる情報がある場合は、それをメモリマップとは独立の「明示的に
  マップすべき領域」として扱う設計にしておくと、こうした不整合を
  実行時の充足検証で機械的に検出できる（今回まさにその検証が機能した）。

## 2026-07-20 `cargo test` がワークスペース全体で失敗する（M3-b）
- 症状: `cargo test -p kernel`（`--lib` 無し）および workspace ルートでの
  `cargo test` が `error[E0152]: found duplicate lang item panic_impl` で
  失敗する。`cargo test -p kernel --lib` なら通るため、それまで気づいて
  いなかった。
- 原因: `kernel` と `bootloader` は bin ターゲットが `no_std`/`no_main` で
  独自の `#[panic_handler]` を持つ。`cargo test` は既定で bin ターゲットも
  テストバイナリとしてビルドしようとするが、テストバイナリは `std` に
  依存するため、`std` 側の `panic_impl` と衝突する。lib ターゲットは
  `#![cfg_attr(not(test), no_std)]` としてあるため影響を受けない。
- 解法: 両クレートの `Cargo.toml` に `[[bin]] test = false, bench = false`
  を指定し、bin をホストのテスト対象から外した。ホストで検証するロジックは
  もともと lib 側（`src/lib.rs` 配下）に置く方針なので、bin を外しても
  検証範囲は変わらない。
- 教訓 / 再発防止: `no_std` の bin と、ホストテスト用の lib を同じクレートに
  同居させる場合は、bin を `test = false` にしておく。`--lib` を付ければ
  通るという回避策で済ませると、標準的な `cargo test` が通らない状態が
  放置され、CI や他人の手元で最初につまずく。

## 2026-07-20 KVM では `-d int` の記録が一切残らない（計測環境の整備時）
- 症状: 転送コストの計測のために `cargo xtask run --kvm` を用意したところ、
  `target/qemu-debug.log` が TCG の 14,400 行から 56 行に激減した。
- 原因: 誤りではなく、KVM では例外・割り込みの大半が CPU の仮想化機能
  （VT-x）側で処理され、QEMU を経由しないため。QEMU の `-d int` は
  QEMU 自身が割り込みを注入・処理する経路にしか仕込まれておらず、KVM が
  ゲスト内で完結させた分は記録されない。
- 実測（同じ起動シーケンス）:

  | 記録 | TCG | KVM |
  |---|---|---|
  | ログ行数 | 14,400 | 56 |
  | `Servicing hardware INT` | 652 件 | **0 件** |
  | `v=` を含む行 | 652 件 | **0 件** |
  | `CPU Reset` | 2 件 | 2 件 |

- **最も危険な点**: これまで異常判定に使ってきた
  `grep -c -E "v=0e|v=08" target/qemu-debug.log` は、KVM では**常に 0 を
  返す**。ページフォルトやダブルフォルトが実際に起きていても 0 になるため、
  「例外なし」という誤った確認結果を得てしまう。
- 解法 / 使い分け: **デバッグ・動作確認は TCG（既定）、計測のみ KVM。**
  `cargo xtask run --kvm` は opt-in にしてあり、既定は TCG のまま。
  `--kvm` 指定時は「例外ログはほぼ取れない」旨を起動時に表示する。
  `-d cpu_reset` は KVM でも機能する（CPU Reset とレジスタダンプは残る）ため、
  トリプルフォルトによるリセットの検出だけは KVM でも可能。
- 教訓 / 再発防止: 実行環境を変えたら、**まず観測手段が同じように機能して
  いるかを確かめる**。「異常が出ていない」ことと「異常を検出できる状態に
  ある」ことは別である。今回は行数の激減で気づいたが、`grep -c` の結果
  だけを見ていれば、壊れた計測器で正常を宣言するところだった。
