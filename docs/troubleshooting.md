## （例）YYYY-MM-DD QEMUが無言で無限リブートする
- 症状: カーネル起動直後、画面もログも出ずに再起動を繰り返す。
- 原因: トリプルフォルト。QEMUデフォルト設定では再起動して原因が見えない。
- 解法: QEMU起動オプションに`-no-reboot -no-shutdown -d int,cpu_reset`を追加し、例外ログを取得して原因の割り込み/例外を特定した。
- 教訓: この3オプションは常時付与する。「ハング」と決めつける前にまず例外ログを確認する。

## 2026-07-19 `-d int,cpu_reset`ログに "CPU Reset (CPU 0)" が出るが異常ではなかった（M0）
- 症状: `cargo xtask run`（OVMFのみ、ブート可能デバイスなし）実行時、ログの冒頭に "CPU Reset (CPU 0)" が2回出力され、一見トリプルフォルトの無限リブートに見えた。
- 原因: 誤りではなく正常な電源投入シーケンス。1回目はQEMU自体の初期化、2回目はリセットベクタ（`EIP=0000fff0`）へのジャンプであり、実機の電源投入直後のCPUリセットに相当する。その後OVMFは正常にlong mode（`CS64` / `EFER`のLME・LMAビット）まで到達し、以降はタイマ割り込み（`Servicing hardware INT=0x20`）を継続的に処理するアイドルループに入っていた（ブート可能デバイスがないため、それ以上は進まない）。
- 解法: 対処不要。ログ全体を見て "CPU Reset" の後にlong mode到達・`INT=0x20`の定常的な処理が続いていることを確認し、実際の無限リブートループ（"CPU Reset" が全編にわたって連続する）ではないと判断した。
- 教訓 / 再発防止: 起動直後の "CPU Reset" が1〜2回だけなら正常な電源投入シーケンスの一部であり得る。異常判定は「"CPU Reset" の有無」ではなく、「ログの後半まで見てlong mode到達後もリセットが連続しているか」で行う。M1以降で本物のトリプルフォルトを疑う際は、この基準ログ（起動直後2回で収束し、その後は`INT=0x20`の定常ループになる）と比較すること。

## 2026-07-19 OVMFがESPのkernel.efiを自動起動せず、内蔵UEFI Shellで止まる（M1）
- 症状: `target/esp/EFI/BOOT/BOOTX64.EFI`を用意し、QEMUの`fat:rw:`ドライバで仮想FATドライブとして渡しても、`cargo xtask run`はシリアル出力・画面出力とも変化がなく、`-d int,cpu_reset`のログ上は「ブート可能デバイスがない場合」と全く同じ定常アイドルループ（`Servicing hardware INT=0x20`が同一IPアドレスで反復するだけ）に見えた。
- 原因の切り分け: QEMUモニタ（unixソケット経由のHMP）で`info block`を確認したところ、ドライブ自体（`ide0-hd0`, vvfat経由）は正しく認識されていた。`screendump`で実際の画面を確認すると、OVMFはESPを自動起動するのではなく、既定の起動オプションとして組み込みの **UEFI Interactive Shell** を起動し、`Shell>`プロンプトで待機していることが判明した（machine typeをq35→pcに変更した経緯はADR-0007参照。このShellへのフォールバック自体はmachine typeに依らず発生した）。
- 対処（回避策）: シェルは起動直後に`startup.nsh`を探して自動実行する（"Press ESC in N seconds to skip startup.nsh..." の表示で確認できる）。そこで`xtask`からESPのルートに`startup.nsh`（内容: `FS0:\EFI\BOOT\BOOTX64.EFI`）を書き込み、シェル経由で明示的に`kernel.efi`をチェインロードさせることで起動できるようにした。
- これは回避策であり、根本解決ではない。 なぜこのUbuntu配布のOVMFビルドが`\EFI\BOOT\BOOTX64.EFI`の既定起動探索より先に組み込みShellを優先するのか（ビルド時の設定・NVRAM初期値・BootOrderの既定値など）は未調査・未解明のまま。`startup.nsh`が無い環境や、OVMFのバージョン/ビルド設定が変わった場合には再度この問題に当たる可能性がある。
- 教訓 / 再発防止: 「ブートデバイスが認識されない」ように見えるsymptomは、実際には「シェルへ既定でフォールバックしていて何も画面に出ていないだけ」である場合がある。QEMUモニタ（`info block`）とスクリーンダンプ（`screendump`）で実際の画面状態を確認してから原因を切り分けること。根本原因の調査（OVMFのビルド設定・BDS挙動の追跡）は、この回避策が何らかの理由で崩れたときに改めて着手する。

## 2026-07-20 UEFIメモリマップの "reserved" 合計が12GiB相当と異常に大きい（M2-c）
- 症状: 物理フレームアロケータ初期化時のログで、QEMUに`-m 256M`しか割り当てていないにもかかわらず、`EfiReservedMemoryType`として除外したページ数の合計が3,145,856ページ（4096バイト/ページ換算で約12GiB）と表示され、実装ミスを疑った。
- 原因の切り分け: 一時的な診断コード（`kernel::memory_map::parse_entries`の結果を`RESERVED`エントリに限定してシリアルへダンプ）を追加したところ、以下の2エントリが見つかった。
  ```
  RESERVED phys_start=0xf6ed000    page_count=128     (0 MiB)
  RESERVED phys_start=0xfd00000000 page_count=3145728 (12288 MiB)
  ```
  後者の`phys_start=0xfd00000000`（約1TB付近）は、実際に搭載されているRAM（256MiB）とは無関係な、PCIの64bit MMIO BAR用に予約されたアドレス空間である。
  QEMU/OVMFの既定構成では、実装されている物理メモリ量に関わらず、PCIデバイスの64bit BARを将来割り当てるための巨大なアドレス空間を`EfiReservedMemoryType`としてメモリマップに含めることがある。
  これは実RAMの存在を意味せず、単なるアドレス空間の予約表明である。
- 解法: 対処不要。これは実装バグではなく、UEFIメモリマップの正常な内容である。`EfiReservedMemoryType`は元々「空き」の判定対象外（本文の型ベースの方針により自動的に除外）のため、フレームアロケータの動作そのものには影響しない。空きフレーム数（実測205MiB / 256MiB中）が実際に割り当てたメモリ量と整合していることの方が重要な確認ポイントであり、そちらは正しかった。
- 教訓 / 再発防止: 「除外の内訳の合計」と「実際に割り当てたメモリ量」を単純に比較して「多すぎる/少なすぎる」と早合点しないこと。UEFIのメモリマップにはアドレス空間の予約（実RAMの裏付けがないもの）が型`EfiReservedMemoryType`等として含まれうる。異常を疑ったら、まず型別の内訳ログ（本プロジェクトでは`frame allocator: excluded breakdown`に出力済み）でどの型が大きいかを確認し、必要なら該当型の生エントリ（`phys_start`/`page_count`）を個別にダンプして、その`phys_start`が実装物理メモリの範囲内かどうかを見る。今回のように`phys_start`が実装メモリを大きく超えるアドレス（例: 1TB付近）を指していれば、実RAMではなくアドレス空間予約であると判断してよい。次に同じ規模の "reserved" 値を見ても、この記録を見れば再調査は不要。

## 2026-07-20 kernel/build.rsがターゲットを問わずlink.ldを適用し、ホストテストがSIGSEGVする（M2-c）
- 症状: kernelクレートに`lib.rs`を新設し`cargo test -p kernel --lib`を実行したところ、テストの一覧表示（`--list`）の時点で`signal: 11, SIGSEGV: invalid memory reference`が発生した。個別のテストを絞り込んでも、テスト名が1つも表示される前にクラッシュした。
- 原因: `kernel/build.rs`が、ビルド対象（Cargoのターゲットトリプル）を一切確認せず、常に`cargo:rustc-link-arg=-T{manifest_dir}/link.ld`を発行していた。`link.ld`は`x86_64-unknown-none`向け（エントリポイント`_start`、全セクションを`0x100000`に配置）を前提にしたリンカスクリプトであり、これをホスト向けの通常の実行可能ファイル（`cargo test -p kernel --lib`はデフォルトでホストターゲット向けにビルドされる）に適用すると、OSのプロセスローダーが期待する通常のELF構造（crt0・エントリポイント等）が壊れ、プロセス起動直後にセグメンテーション違反を起こす。
- 解法: `build.rs`で`std::env::var("TARGET")`を確認し、`x86_64-unknown-none`の場合のみリンカ引数を発行するよう修正した。
- 教訓 / 再発防止: `build.rs`はパッケージのどのターゲット（bin/lib、どのコンパイル対象トリプル向けか）をビルドする際にも実行される。クレート内に「特定のビルド対象専用」の設定（リンカスクリプト、特定アーキテクチャ向けの`cargo:rustc-link-arg`等）を`build.rs`で注入する場合は、必ず`TARGET`環境変数で対象を確認してから適用すること。特に、binクレートに後から`lib.rs`（ホストテスト用）を追加するときは、既存の`build.rs`がホストビルドにも無条件に適用されてしまわないか必ず確認する。

## 2026-07-20 ページング計画の容量見積もり（64）が実機で不足した（M2-d, d-1）
- 症状: `kernel::paging::plan::MappedRanges`の初期実装時、容量（`DEFAULT_CAPACITY`）を「メモリ型ごとに1エントリ程度、10前後」と見積もって64にしたところ、実機（QEMU + OVMF, 256MiB割り当て）で実際にビルドしたところ`mapped-range capacity exceeded`エラーでfail-fastした。
- 原因: 見積もりが誤りだった。UEFIメモリマップは、同じメモリ型でも物理アドレス上で連続しない小さな断片が多数現れることがある（`EfiBootServicesData`等が、ファームウェアの内部処理の都合で複数の離れた小領域として記録されるため）。「型ごとに1エントリ」を前提にした見積もりは、実際のメモリマップの構造を確認せずに行ったものだった。
- 解法: 容量を、マージ前の最悪ケース（メモリマップの総ディスクリプタ数）まで余裕を持たせ、フレームアロケータと同じ256に引き上げた。
- 教訓 / 再発防止: 固定長データ構造の容量を見積もる際は、「型ごとに1エントリ」のような単純化した仮定を置かず、実際のメモリマップの構造（総ディスクリプタ数、型ごとの断片化度合い）を実機で確認してから決めること。今回のように、容量超過を握りつぶさずfail-fastする設計にしていたため、実装ミスではなく見積もりの問題であることが即座に判明した（この設計判断の価値が実際に発揮された例）。

## 2026-07-20 GOPフレームバッファがUEFIメモリマップに含まれない（M2-d, d-1）
- 症状: `kernel::paging::plan::MappedRanges`をメモリマップのみから構築し、ページテーブルを実際に構築した後、必須領域の充足検証で`required range [framebuffer] 0x80000000..0x803e8000: NG`と表示された。フレームバッファの物理アドレス（`BootInfo.framebuffer.physical_address`）が、どのメモリマップエントリにも含まれていなかった。
- 原因の切り分け: 除外内訳ログの`mmio=1024`（1024ページ = 4MiB）という数字が、フレームバッファのサイズ（4096000バイト ≈ 1000ページ）と近かったため、当初「フレームバッファは`EfiMemoryMappedIO`としてメモリマップに含まれている」と誤って仮定していた。実際にはこの`mmio=1024`エントリは`phys_start=0xffc00000`（4GiB直前の、PCIの低位MMIO窓としてよくある位置）であり、フレームバッファ（`phys_start=0x80000000`）とは無関係だった。GOPのフレームバッファはPCIデバイスのBAR（Base Address Register）としてマップされており、UEFIの`GetMemoryMap`が返す一般的なシステムメモリマップとは別の仕組み（PCIコンフィグ空間の走査）で見つかるものであり、そもそもメモリマップに現れるとは限らない。
- 解法: `MappedRanges::build`に`extra: &[(start, end, cacheable)]`引数を追加し、`BootInfo.framebuffer`から得たフレームバッファの範囲をメモリマップとは独立に明示的に追加するようにした（`cacheable=false`として、他のMMIO領域と同様にキャッシュ無効でマップする）。
- 教訓 / 再発防止: 「除外内訳の値が近い」ことは、その領域が目的のものであることの根拠にはならない（今回のように無関係な偶然の一致でありうる）。デバイスのMMIO領域（フレームバッファ等）がメモリマップ由来の情報だけで必ず説明できるとは限らない。BootInfo等、他の経路で得られる情報がある場合は、それをメモリマップとは独立の「明示的にマップすべき領域」として扱う設計にしておくと、こうした不整合を実行時の充足検証で機械的に検出できる（今回まさにその検証が機能した）。

## 2026-07-20 `cargo test`がワークスペース全体で失敗する（M3-b）
- 症状: `cargo test -p kernel`（`--lib`無し）およびworkspaceルートでの`cargo test`が`error[E0152]: found duplicate lang item panic_impl`で失敗する。`cargo test -p kernel --lib`なら通るため、それまで気づいていなかった。
- 原因: `kernel`と`bootloader`はbinターゲットが`no_std`/`no_main`で独自の`#[panic_handler]`を持つ。`cargo test`は既定でbinターゲットもテストバイナリとしてビルドしようとするが、テストバイナリは`std`に依存するため、`std`側の`panic_impl`と衝突する。libターゲットは`#![cfg_attr(not(test), no_std)]`としてあるため影響を受けない。
- 解法: 両クレートの`Cargo.toml`に`[[bin]] test = false, bench = false`を指定し、binをホストのテスト対象から外した。ホストで検証するロジックはもともとlib側（`src/lib.rs`配下）に置く方針なので、binを外しても検証範囲は変わらない。
- 教訓 / 再発防止: `no_std`のbinと、ホストテスト用のlibを同じクレートに同居させる場合は、binを`test = false`にしておく。`--lib`を付ければ通るという回避策で済ませると、標準的な`cargo test`が通らない状態が放置され、CIや他人の手元で最初につまずく。

## 2026-07-20 KVMでは`-d int`の記録が一切残らない（計測環境の整備時）
- 症状: 転送コストの計測のために`cargo xtask run --kvm`を用意したところ、`target/qemu-debug.log`がTCGの14,400行から56行に激減した。
- 原因: 誤りではなく、KVMでは例外・割り込みの大半がCPUの仮想化機能（VT-x）側で処理され、QEMUを経由しないため。QEMUの`-d int`はQEMU自身が割り込みを注入・処理する経路にしか仕込まれておらず、KVMがゲスト内で完結させた分は記録されない。
- 実測（同じ起動シーケンス）:

  | 記録 | TCG | KVM |
  |---|---|---|
  | ログ行数 | 14,400 | 56 |
  | `Servicing hardware INT` | 652件 | **0件** |
  | `v=`を含む行 | 652件 | **0件** |
  | `CPU Reset` | 2件 | 2件 |

- **最も危険な点**: これまで異常判定に使ってきた`grep -c -E "v=0e|v=08" target/qemu-debug.log`は、KVMでは**常に0を返す**。ページフォルトやダブルフォルトが実際に起きていても0になるため、「例外なし」という誤った確認結果を得てしまう。
- 解法 / 使い分け: デバッグ・動作確認はTCG（既定）、計測のみKVM。 `cargo xtask run --kvm`はopt-inにしてあり、既定はTCGのまま。`--kvm`指定時は「例外ログはほぼ取れない」旨を起動時に表示する。`-d cpu_reset`はKVMでも機能する（CPU Resetとレジスタダンプは残る）ため、トリプルフォルトによるリセットの検出だけはKVMでも可能。
- 教訓 / 再発防止: 実行環境を変えたら、**まず観測手段が同じように機能しているかを確かめる**。「異常が出ていない」ことと「異常を検出できる状態にある」ことは別である。今回は行数の激減で気づいたが、`grep -c`の結果だけを見ていれば、壊れた計測器で正常を宣言するところだった。

## 2026-07-21 再マップ前のPICが既に全マスクだった（v=20が674件出ているのに）（M4-c-3）
- 症状: PIC再マップの前にIMRを読んだところ、マスタ・スレーブとも`0xFF`（全IRQマスク済み）だった。一方、同じ実行の`target/qemu-debug.log`には`v=20`（`Servicing hardware INT=0x20`）が674件記録されている。「割り込みが674回配送されているのに、その割り込みコントローラは全マスク」という一見矛盾した観測になる。
- 原因: 矛盾ではなく、時系列が違う。`v=20`はすべて**カーネル起動前**の記録である。ログ上の該当行は`CS=0x38` / `IP=0x0d……`・`0x0f……`と、UEFI由来のGDTとファームウェア領域を指しており、カーネル開始後の`v=`は1件も無い。つまりファームウェア（OVMF）が動作中はベクタ0x20でタイマ割り込みを処理しており、ExitBootServicesの前後でそれをマスクしてから制御を渡してきた、という順序になる。
- ここから分かること: OVMFは既にPICを0x20ベースへ再マップしていた可能性が高い。 8259Aの既定は0x08-0x0Fなので、既定のままならタイマは`v=08`として記録されたはずである。
- 解法: 対処不要。M4-c-3の再マップは、この状態に対する上書きになる。
- **申し送り（M4-dで重要）**: 上記が正しければ、今回の再マップは「同じ値への上書き」である。ICW2（ベクタオフセット）は書き込み専用で読み戻せないため、こちらのICW2の書き方が間違っていても、ハードウェアが既に正しい状態にあるせいでM4-dのタイマが普通に動いてしまう可能性がある。M4-dで「動いた」ことをもってICW2の実装が正しいと結論づけないこと。 判定するには、意図的に別のオフセット（例: 0x30-0x3F）へ再マップし、そのベクタで届くことを確認する必要がある（ADR-0018 Addendum）。
- 補足: このログだけでは、`v=20`を上げていたのが8259AなのかLAPICなのかは区別できない。QEMUの`-d int`はベクタ番号しか残さないため、配送元までは分からない。上記の「別オフセットへ再マップして確かめる」実験は、この点も同時に切り分けられる（8259A経由なら移動し、LAPIC経由なら0x20のまま）。
- **決着（2026-07-21、M4-d-2）**: 実験を行い、両方の疑いが晴れた。`cargo xtask run --interrupt-test alt-offset`でPICを0x30-0x3Fへ再マップしたところ、**ティックはベクタ0x30で届き、0x20では届かなかった**。したがって、
  1. ZaytOSのICW2書き込みは実際にオフセットを動かしている（「OVMFが設定した状態にただ乗りしている」わけではない）
  2. 配送元は8259Aである（LAPIC経由ならベクタは移動しない）上記の申し送りは解消済み。回帰チェックとして常設した。
- 教訓 / 再発防止: 「読み戻せる値」と「読み戻せない値」を混ぜて報告しない。IMRは読み戻せるので検証できるが、ICW2は読み戻せないので検証できない。同じログ行に両方を並べて書くと、検証済みの範囲を実際より広く見せてしまう。

## 2026-07-21 押していないのにスキャンコードが1回届く（M4-e）
- 症状: IRQ1を解禁した直後、キーを一度も押していないのに`keyboard: scancode 0x67`が1回だけ記録される。押してもいないキーが最初の入力として現れる形になる。
- **誤った仮説**: 「ファームウェアが残したバイトを読み捨てそこねている」。IRQ1解禁の前に出力バッファをドレインしているが、瞬間のOBFしか見ていないため取り残したのだろう、と考えた。これは違った。 ドレインを「一定回数のあいだ見張って、出てきた分も捨てる」形に広げても`0x67`は消えなかった。つまり**ドレインの時点では存在しない**。
- 原因: こちらのコンフィグバイト読み出しが、自分でIRQ1をラッチさせていた。 i8042はOBFが立つたびにIRQ1を上げるが、これは**キー入力に限らない**。コントローラ宛コマンド（コンフィグバイトの読み出し0x20）への応答でもOBFは立ち、IRQ1が上がる。その割り込みはIRQ1をマスクしている間にPICのIRRへラッチされ、**マスクを外した瞬間に1回だけ配送される**。応答バイト自体は既にこちらが読み終えているので、ハンドラが0x60を読んでも意味のある値は返らない（`0x67`はその残骸）。
- 解法: ハンドラで**読む前にOBFを確認**し、立っていなければ「データを伴わないIRQ1」として専用カウンタ`stray`に計上して値は捨てる。 読み出し自体は省かない。 読み飛ばす分岐を作ると、そこが将来「バッファが満杯だから読まない」に育つ余地になる。それをやると出力バッファが空かず、以後のIRQ1が来なくなる。
- 対処せず受け入れた点: コマンド送信中だけキーボード割り込みを無効化すればラッチを防げる見込みはあるが、行わない。「増え続けるかどうか」という指標として機能するので、常に0にして異常検出の手掛かりを失うより価値がある。
- **未解明**: strayの回数はrunごとに0と1が入れ替わる（同一構成の4回で1,1,1,0）。上記の「コンフィグバイト読み出しがラッチさせる」は`0x67`が消えた事実と整合する仮説だが、**回数が揺れる理由までは突き止めていない**。ドレインとマスク解除の間に入る動作のタイミングで、IRRへのラッチが起きたり起きなかったりするのだろうと考えているが、確認していない。判定基準は「起動直後に0か1なら正常、増え続けるなら異常」とする。
- 教訓 / 再発防止: i8042はキー入力以外でもIRQ1を上げる。 「IRQ1が来た = キーが押された」ではない。同様に、マスク中に発生した割り込みはPICのIRRにラッチされ、マスクを外した瞬間に配送される。「マスクしていたから何も起きていないはず」は成り立たない。
- 会計で捕まえる: `keys + stray == ハンドラ呼び出し回数 == IDTのベクタ別カウンタ`が常に成り立つことをハートビートに出している（`balanced=true`）。数字が説明できない状態を残さないための仕組みで、今回の切り分けにも使った（別runのログを混同していたことがこれで判明した）。
