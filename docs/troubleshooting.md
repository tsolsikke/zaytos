## （例）YYYY-MM-DD QEMUが無言で無限リブートする
- 症状: カーネル起動直後、画面もログも出ずに再起動を繰り返す。
- 原因: トリプルフォルト。QEMUデフォルト設定では再起動して原因が見えない。
- 解法: QEMU起動オプションに`-no-reboot -no-shutdown -d int,cpu_reset`を追加し、例外ログを取得して原因の割り込み/例外を特定した。
- 教訓: この3オプションは常時付与する。「ハング」と決めつける前にまず例外ログを確認する。

## 2026-07-19 `-d int,cpu_reset`ログに "CPU Reset (CPU 0)" が出るが異常ではなかった（M0）
- 症状: `cargo xtask run`（OVMFのみ、ブート可能デバイスなし）実行時、ログの冒頭に "CPU Reset (CPU 0)" が2回出力され、一見トリプルフォルトの無限リブートに見えた。
- 原因: 誤りではなく正常な電源投入シーケンス。1回目はQEMU自体の初期化、2回目はリセットベクタ（`EIP=0000fff0`）へのジャンプであり、実機の電源投入直後のCPUリセットに相当する。その後OVMFは正常にlong mode（`CS64` / `EFER`のLME・LMAビット）まで到達し、以降はタイマ割り込み（`Servicing hardware INT=0x20`）を継続的に処理するアイドルループに入っていた（ブート可能デバイスがないため、それ以上は進まない）。
- 解法: 対処不要。ログ全体を見て "CPU Reset" の後にlong mode到達・`INT=0x20`の定常的な処理が続いていることを確認し、実際の無限リブートループ（"CPU Reset" が全編にわたって連続する）ではないと判断した。
- 教訓 / 再発防止: 起動直後の "CPU Reset" が1〜2回だけなら正常な電源投入シーケンスの一部であり得る。異常判定は「"CPU Reset" の有無」ではなく、「ログの後半まで見てlong mode到達後もリセットが連続しているか」で行う。M1以降で本物のトリプルフォルトを疑う際は、この基準ログ（起動直後2回で収束し、その後は`INT=0x20`の定常ループになる）と比較すること。

## 2026-07-19 OVMFがESPのkernel.efiを自動起動せず、内蔵UEFI Shellで止まる（M1）
- 症状: `target/esp/EFI/BOOT/BOOTX64.EFI`を用意し、QEMUの`fat:rw:`ドライバで仮想FATドライブとして渡しても、`cargo xtask run`はシリアル出力・画面出力とも変化がなく、`-d int,cpu_reset`のログ上は「ブート可能デバイスがない場合」と全く同じ定常アイドルループ（`Servicing hardware INT=0x20`が同一IPアドレスで反復するだけ）に見えた。
- 原因の切り分け: QEMUモニタ（unixソケット経由のHMP）で`info block`を確認したところ、ドライブ自体（`ide0-hd0`, vvfat経由）は正しく認識されていた。`screendump`で実際の画面を確認すると、OVMFはESPを自動起動するのではなく、既定の起動オプションとして組み込みの **UEFI Interactive Shell** を起動し、`Shell>`プロンプトで待機していることが判明した（machine typeをq35→pcに変更した経緯はADR-0007参照。このShellへのフォールバック自体はmachine typeに依らず発生した）。
- 対処（回避策）: シェルは起動直後に`startup.nsh`を探して自動実行する（"Press ESC in N seconds to skip startup.nsh..." の表示で確認できる）。そこで`xtask`からESPのルートに`startup.nsh`（内容: `FS0:\EFI\BOOT\BOOTX64.EFI`）を書き込み、シェル経由で明示的に`kernel.efi`をチェインロードさせることで起動できるようにした。
- これは回避策であり、根本解決ではない。なぜこのUbuntu配布のOVMFビルドが`\EFI\BOOT\BOOTX64.EFI`の既定起動探索より先に組み込みShellを優先するのか（ビルド時の設定・NVRAM初期値・BootOrderの既定値など）は未調査・未解明のまま。`startup.nsh`が無い環境や、OVMFのバージョン/ビルド設定が変わった場合には再度この問題に当たる可能性がある。
- 教訓 / 再発防止: 「ブートデバイスが認識されない」ように見えるsymptomは、実際には「シェルへ既定でフォールバックしていて何も画面に出ていないだけ」である場合がある。QEMUモニタ（`info block`）とスクリーンダンプ（`screendump`）で実際の画面状態を確認してから原因を切り分けること。根本原因の調査（OVMFのビルド設定・BDS挙動の追跡）は、この回避策が何らかの理由で崩れたときに改めて着手する。

## 2026-07-20 UEFIメモリマップの "reserved" 合計が12GiB相当と異常に大きい（M2-c）
- 症状: 物理フレームアロケータ初期化時のログで、QEMUに`-m 256M`しか割り当てていないにもかかわらず、`EfiReservedMemoryType`として除外したページ数の合計が3,145,856ページ（4096バイト/ページ換算で約12GiB）と表示され、実装ミスを疑った。
- 原因の切り分け: 一時的な診断コード（`kernel::memory_map::parse_entries`の結果を`RESERVED`エントリに限定してシリアルへダンプ）を追加したところ、以下の2エントリが見つかった。
  ```
  RESERVED phys_start=0xf6ed000    page_count=128     (0 MiB)
  RESERVED phys_start=0xfd00000000 page_count=3145728 (12288 MiB)
  ```
  後者の`phys_start=0xfd00000000`（約1TB付近）は、実際に搭載されているRAM（256MiB）とは無関係な、PCIの64bit MMIO BAR用に予約されたアドレス空間である。
  QEMU/OVMFの既定構成では、実装されている物理メモリ量に関わらず、PCIデバイスの64bit BARを将来割り当てるための巨大なアドレス空間を`EfiReservedMemoryType`としてメモリマップに含めることがある。
  これは実RAMの存在を意味せず、単なるアドレス空間の予約表明である。
- 解法: 対処不要。これは実装バグではなく、UEFIメモリマップの正常な内容である。`EfiReservedMemoryType`は元々「空き」の判定対象外（本文の型ベースの方針により自動的に除外）のため、フレームアロケータの動作そのものには影響しない。空きフレーム数（実測205MiB / 256MiB中）が実際に割り当てたメモリ量と整合していることの方が重要な確認ポイントであり、そちらは正しかった。
- 教訓 / 再発防止: 「除外の内訳の合計」と「実際に割り当てたメモリ量」を単純に比較して「多すぎる/少なすぎる」と早合点しないこと。UEFIのメモリマップにはアドレス空間の予約（実RAMの裏付けがないもの）が型`EfiReservedMemoryType`等として含まれうる。異常を疑ったら、まず型別の内訳ログ（本プロジェクトでは`frame allocator: excluded breakdown`に出力済み）でどの型が大きいかを確認し、必要なら該当型の生エントリ（`phys_start`/`page_count`）を個別にダンプして、その`phys_start`が実装物理メモリの範囲内かどうかを見る。今回のように`phys_start`が実装メモリを大きく超えるアドレス（例: 1TB付近）を指していれば、実RAMではなくアドレス空間予約であると判断してよい。次に同じ規模の "reserved" 値を見ても、この記録を見れば再調査は不要。

## 2026-07-20 kernel/build.rsがターゲットを問わずlink.ldを適用し、ホストテストがSIGSEGVする（M2-c）
- 症状: kernelクレートに`lib.rs`を新設し`cargo test -p kernel --lib`を実行したところ、テストの一覧表示（`--list`）の時点で`signal: 11, SIGSEGV: invalid memory reference`が発生した。個別のテストを絞り込んでも、テスト名が1つも表示される前にクラッシュした。
- 原因: `kernel/build.rs`が、ビルド対象（Cargoのターゲットトリプル）を一切確認せず、常に`cargo:rustc-link-arg=-T{manifest_dir}/link.ld`を発行していた。`link.ld`は`x86_64-unknown-none`向け（エントリポイント`_start`、全セクションを`0x100000`に配置）を前提にしたリンカスクリプトであり、これをホスト向けの通常の実行可能ファイル（`cargo test -p kernel --lib`はデフォルトでホストターゲット向けにビルドされる）に適用すると、OSのプロセスローダーが期待する通常のELF構造（crt0・エントリポイント等）が壊れ、プロセス起動直後にセグメンテーション違反を起こす。
- 解法: `build.rs`で`std::env::var("TARGET")`を確認し、`x86_64-unknown-none`の場合のみリンカ引数を発行するよう修正した。
- 教訓 / 再発防止: `build.rs`はパッケージのどのターゲット（bin/lib、どのコンパイル対象トリプル向けか）をビルドする際にも実行される。クレート内に「特定のビルド対象専用」の設定（リンカスクリプト、特定アーキテクチャ向けの`cargo:rustc-link-arg`等）を`build.rs`で注入する場合は、必ず`TARGET`環境変数で対象を確認してから適用すること。特に、binクレートに後から`lib.rs`（ホストテスト用）を追加するときは、既存の`build.rs`がホストビルドにも無条件に適用されてしまわないか必ず確認する。

## 2026-07-20 ページング計画の容量見積もり（64）が実機で不足した（M2-d, d-1）
- 症状: `kernel::paging::plan::MappedRanges`の初期実装時、容量（`DEFAULT_CAPACITY`）を「メモリ型ごとに1エントリ程度、10前後」と見積もって64にしたところ、実機（QEMU + OVMF, 256MiB割り当て）で実際にビルドしたところ`mapped-range capacity exceeded`エラーでfail-fastした。
- 原因: 見積もりが誤りだった。UEFIメモリマップは、同じメモリ型でも物理アドレス上で連続しない小さな断片が多数現れることがある（`EfiBootServicesData`等が、ファームウェアの内部処理の都合で複数の離れた小領域として記録されるため）。「型ごとに1エントリ」を前提にした見積もりは、実際のメモリマップの構造を確認せずに行ったものだった。
- 解法: 容量を、マージ前の最悪ケース（メモリマップの総ディスクリプタ数）まで余裕を持たせ、フレームアロケータと同じ256に引き上げた。
- 教訓 / 再発防止: 固定長データ構造の容量を見積もる際は、「型ごとに1エントリ」のような単純化した仮定を置かず、実際のメモリマップの構造（総ディスクリプタ数、型ごとの断片化度合い）を実機で確認してから決めること。今回のように、容量超過を握りつぶさずfail-fastする設計にしていたため、実装ミスではなく見積もりの問題であることが即座に判明した（この設計判断の価値が実際に発揮された例）。

## 2026-07-20 GOPフレームバッファがUEFIメモリマップに含まれない（M2-d, d-1）
- 症状: `kernel::paging::plan::MappedRanges`をメモリマップのみから構築し、ページテーブルを実際に構築した後、必須領域の充足検証で`required range [framebuffer] 0x80000000..0x803e8000: NG`と表示された。フレームバッファの物理アドレス（`BootInfo.framebuffer.physical_address`）が、どのメモリマップエントリにも含まれていなかった。
- 原因の切り分け: 除外内訳ログの`mmio=1024`（1024ページ = 4MiB）という数字が、フレームバッファのサイズ（4096000バイト ≈ 1000ページ）と近かったため、当初「フレームバッファは`EfiMemoryMappedIO`としてメモリマップに含まれている」と誤って仮定していた。実際にはこの`mmio=1024`エントリは`phys_start=0xffc00000`（4GiB直前の、PCIの低位MMIO窓としてよくある位置）であり、フレームバッファ（`phys_start=0x80000000`）とは無関係だった。GOPのフレームバッファはPCIデバイスのBAR（Base Address Register）としてマップされており、UEFIの`GetMemoryMap`が返す一般的なシステムメモリマップとは別の仕組み（PCIコンフィグ空間の走査）で見つかるものであり、そもそもメモリマップに現れるとは限らない。
- 解法: `MappedRanges::build`に`extra: &[(start, end, cacheable)]`引数を追加し、`BootInfo.framebuffer`から得たフレームバッファの範囲をメモリマップとは独立に明示的に追加するようにした（`cacheable=false`として、他のMMIO領域と同様にキャッシュ無効でマップする）。
- 教訓 / 再発防止: 「除外内訳の値が近い」ことは、その領域が目的のものであることの根拠にはならない（今回のように無関係な偶然の一致でありうる）。デバイスのMMIO領域（フレームバッファ等）がメモリマップ由来の情報だけで必ず説明できるとは限らない。BootInfo等、他の経路で得られる情報がある場合は、それをメモリマップとは独立の「明示的にマップすべき領域」として扱う設計にしておくと、こうした不整合を実行時の充足検証で機械的に検出できる（今回まさにその検証が機能した）。

## 2026-07-20 `cargo test`がワークスペース全体で失敗する（M3-b）
- 症状: `cargo test -p kernel`（`--lib`無し）およびworkspaceルートでの`cargo test`が`error[E0152]: found duplicate lang item panic_impl`で失敗する。`cargo test -p kernel --lib`なら通るため、それまで気づいていなかった。
- 原因: `kernel`と`bootloader`はbinターゲットが`no_std`/`no_main`で独自の`#[panic_handler]`を持つ。`cargo test`は既定でbinターゲットもテストバイナリとしてビルドしようとするが、テストバイナリは`std`に依存するため、`std`側の`panic_impl`と衝突する。libターゲットは`#![cfg_attr(not(test), no_std)]`としてあるため影響を受けない。
- 解法: 両クレートの`Cargo.toml`に`[[bin]] test = false, bench = false`を指定し、binをホストのテスト対象から外した。ホストで検証するロジックはもともとlib側（`src/lib.rs`配下）に置く方針なので、binを外しても検証範囲は変わらない。
- 教訓 / 再発防止: `no_std`のbinと、ホストテスト用のlibを同じクレートに同居させる場合は、binを`test = false`にしておく。`--lib`を付ければ通るという回避策で済ませると、標準的な`cargo test`が通らない状態が放置され、CIや他人の手元で最初につまずく。

## 2026-07-20 KVMでは`-d int`の記録が一切残らない（計測環境の整備時）
- 症状: 転送コストの計測のために`cargo xtask run --kvm`を用意したところ、`target/qemu-debug.log`がTCGの14,400行から56行に激減した。
- 原因: 誤りではなく、KVMでは例外・割り込みの大半がCPUの仮想化機能（VT-x）側で処理され、QEMUを経由しないため。QEMUの`-d int`はQEMU自身が割り込みを注入・処理する経路にしか仕込まれておらず、KVMがゲスト内で完結させた分は記録されない。
- 実測（同じ起動シーケンス）:

  | 記録 | TCG | KVM |
  |---|---|---|
  | ログ行数 | 14,400 | 56 |
  | `Servicing hardware INT` | 652件 | **0件** |
  | `v=`を含む行 | 652件 | **0件** |
  | `CPU Reset` | 2件 | 2件 |

- **最も危険な点**: これまで異常判定に使ってきた`grep -c -E "v=0e|v=08" target/qemu-debug.log`は、KVMでは**常に0を返す**。ページフォルトやダブルフォルトが実際に起きていても0になるため、「例外なし」という誤った確認結果を得てしまう。
- 解法 / 使い分け: デバッグ・動作確認はTCG（既定）、計測のみKVM。`cargo xtask run --kvm`はopt-inにしてあり、既定はTCGのまま。`--kvm`指定時は「例外ログはほぼ取れない」旨を起動時に表示する。`-d cpu_reset`はKVMでも機能する（CPU Resetとレジスタダンプは残る）ため、トリプルフォルトによるリセットの検出だけはKVMでも可能。
- 教訓 / 再発防止: 実行環境を変えたら、**まず観測手段が同じように機能しているかを確かめる**。「異常が出ていない」ことと「異常を検出できる状態にある」ことは別である。今回は行数の激減で気づいたが、`grep -c`の結果だけを見ていれば、壊れた計測器で正常を宣言するところだった。

## 2026-07-21 再マップ前のPICが既に全マスクだった（v=20が674件出ているのに）（M4-c-3）
- 症状: PIC再マップの前にIMRを読んだところ、マスタ・スレーブとも`0xFF`（全IRQマスク済み）だった。一方、同じ実行の`target/qemu-debug.log`には`v=20`（`Servicing hardware INT=0x20`）が674件記録されている。「割り込みが674回配送されているのに、その割り込みコントローラは全マスク」という一見矛盾した観測になる。
- 原因: 矛盾ではなく、時系列が違う。`v=20`はすべて**カーネル起動前**の記録である。ログ上の該当行は`CS=0x38` / `IP=0x0d……`・`0x0f……`と、UEFI由来のGDTとファームウェア領域を指しており、カーネル開始後の`v=`は1件も無い。つまりファームウェア（OVMF）が動作中はベクタ0x20でタイマ割り込みを処理しており、ExitBootServicesの前後でそれをマスクしてから制御を渡してきた、という順序になる。
- ここから分かること: OVMFは既にPICを0x20ベースへ再マップしていた可能性が高い。8259Aの既定は0x08-0x0Fなので、既定のままならタイマは`v=08`として記録されたはずである。
- 解法: 対処不要。M4-c-3の再マップは、この状態に対する上書きになる。
- **申し送り（M4-dで重要）**: 上記が正しければ、今回の再マップは「同じ値への上書き」である。ICW2（ベクタオフセット）は書き込み専用で読み戻せないため、こちらのICW2の書き方が間違っていても、ハードウェアが既に正しい状態にあるせいでM4-dのタイマが普通に動いてしまう可能性がある。M4-dで「動いた」ことをもってICW2の実装が正しいと結論づけないこと。判定するには、意図的に別のオフセット（例: 0x30-0x3F）へ再マップし、そのベクタで届くことを確認する必要がある（ADR-0018 Addendum）。
- 補足: このログだけでは、`v=20`を上げていたのが8259AなのかLAPICなのかは区別できない。QEMUの`-d int`はベクタ番号しか残さないため、配送元までは分からない。上記の「別オフセットへ再マップして確かめる」実験は、この点も同時に切り分けられる（8259A経由なら移動し、LAPIC経由なら0x20のまま）。
- **決着（2026-07-21、M4-d-2）**: 実験を行い、両方の疑いが晴れた。`cargo xtask run --interrupt-test alt-offset`でPICを0x30-0x3Fへ再マップしたところ、**ティックはベクタ0x30で届き、0x20では届かなかった**。したがって、
  1. ZaytOSのICW2書き込みは実際にオフセットを動かしている（「OVMFが設定した状態にただ乗りしている」わけではない）
  2. 配送元は8259Aである（LAPIC経由ならベクタは移動しない）上記の申し送りは解消済み。回帰チェックとして常設した。
- 教訓 / 再発防止: 「読み戻せる値」と「読み戻せない値」を混ぜて報告しない。IMRは読み戻せるので検証できるが、ICW2は読み戻せないので検証できない。同じログ行に両方を並べて書くと、検証済みの範囲を実際より広く見せてしまう。

## 2026-07-21 押していないのにスキャンコードが1回届く（M4-e）
- 症状: IRQ1を解禁した直後、キーを一度も押していないのに`keyboard: scancode 0x67`が1回だけ記録される。押してもいないキーが最初の入力として現れる形になる。
- **誤った仮説**: 「ファームウェアが残したバイトを読み捨てそこねている」。IRQ1解禁の前に出力バッファをドレインしているが、瞬間のOBFしか見ていないため取り残したのだろう、と考えた。これは違った。ドレインを「一定回数のあいだ見張って、出てきた分も捨てる」形に広げても`0x67`は消えなかった。つまり**ドレインの時点では存在しない**。
- 原因: こちらのコンフィグバイト読み出しが、自分でIRQ1をラッチさせていた。i8042はOBFが立つたびにIRQ1を上げるが、これは**キー入力に限らない**。コントローラ宛コマンド（コンフィグバイトの読み出し0x20）への応答でもOBFは立ち、IRQ1が上がる。その割り込みはIRQ1をマスクしている間にPICのIRRへラッチされ、**マスクを外した瞬間に1回だけ配送される**。応答バイト自体は既にこちらが読み終えているので、ハンドラが0x60を読んでも意味のある値は返らない（`0x67`はその残骸）。
- 解法: ハンドラで**読む前にOBFを確認**し、立っていなければ「データを伴わないIRQ1」として専用カウンタ`stray`に計上して値は捨てる。読み出し自体は省かない。読み飛ばす分岐を作ると、そこが将来「バッファが満杯だから読まない」に育つ余地になる。それをやると出力バッファが空かず、以後のIRQ1が来なくなる。
- 対処せず受け入れた点: コマンド送信中だけキーボード割り込みを無効化すればラッチを防げる見込みはあるが、行わない。「増え続けるかどうか」という指標として機能するので、常に0にして異常検出の手掛かりを失うより価値がある。
- **未解明**: strayの回数はrunごとに0と1が入れ替わる（同一構成の4回で1,1,1,0）。上記の「コンフィグバイト読み出しがラッチさせる」は`0x67`が消えた事実と整合する仮説だが、**回数が揺れる理由までは突き止めていない**。ドレインとマスク解除の間に入る動作のタイミングで、IRRへのラッチが起きたり起きなかったりするのだろうと考えているが、確認していない。判定基準は「起動直後に0か1なら正常、増え続けるなら異常」とする。
- 教訓 / 再発防止: i8042はキー入力以外でもIRQ1を上げる。「IRQ1が来た = キーが押された」ではない。同様に、マスク中に発生した割り込みはPICのIRRにラッチされ、マスクを外した瞬間に配送される。「マスクしていたから何も起きていないはず」は成り立たない。
- 会計で捕まえる: `keys + stray == ハンドラ呼び出し回数 == IDTのベクタ別カウンタ`が常に成り立つことをハートビートに出している（`balanced=true`）。数字が説明できない状態を残さないための仕組みで、今回の切り分けにも使った（別runのログを混同していたことがこれで判明した）。

## 2026-07-22 回帰チェックが2日間走っておらず、alt-offsetが壊れていたことに気づかなかった（M4-e〜M5-a-1）

- **本題は「2日間気づかなかったこと」の方である**: スタブ表に穴があったこと自体より、それを検出する手段が動いていなかったことが問題である。回帰チェック14種は`cargo xtask check`にも実装ループにも入っておらず、M4-e以降M5-a-1まで一度も走っていなかった。通常起動では観測できないため、起動ログをいくら読んでも見つからない。

- 教訓 / 再発防止: 検査は、存在するだけでは機能しない。走っていなければ無いのと同じである。`docs/verification-coverage.md`のC-6として「回帰テスト一式を通す運用が主張されているが、走らせる仕組みが無い」と挙げていた項目が、そのまま現実になった事例である。

## 2026-07-22 「OVMFがまれに起動に失敗する」は環境要因ではなく自作の不具合だった
- 症状: `cargo xtask run`系のテストで、カーネルが起動せずOVMFがシェルまたはアイドルループへ落ちる。シリアルログに起動マーカーが1行も出ず、`qemu-debug.log`のRIPがファームウェア領域を指す。xtaskはこれを検出して「kernel did not start (environment, not the code); re-run」と報告する。

- 実際の原因: `xtask`の`prepare_ovmf_vars`が、OVMFのvarstore（`target/ovmf/OVMF_VARS_4M.fd`）を**ファイルが存在しないときだけ**テンプレートからコピーする作りになっていた。QEMUへは書き込み可能で渡しているため、OVMFは起動のたびにこれを書き換える。つまりテスト実行のたびに状態が持ち越されていた。
- 実測した内容: テンプレート（`/usr/share/OVMF/OVMF_VARS_4M.fd`）との比較で、540672バイト中80448バイトが書き換わっていた。中身には`Boot0000` / `Boot0002` / `Boot0003` / `Boot0004` / `Boot0005`と、`EFI Internal Shell`、`UEFI PXEv4 (MAC:525400123456)`、`UEFI PXEv6`、`UEFI HTTPv4`の起動項目が蓄積していた。症状が「シェルへ落ちる」であることと噛み合う。
- 比較: varstoreを使い回す実装では`check --full`の3回中3回で起動失敗が発生した。毎回テンプレートから作り直す実装では2回中0件だった。
- **原因の特定は途中で止めている**: varstoreのどの変数（BootOrderなのか別のものか）が効いているかまでは調べていない。書き換わったバイト列と症状が整合するという以上のことは言えない。また、書き換わったvarstoreのまま単独実行を5回したときは5回とも通っており、varstoreの内容だけで決まるわけではない。連続起動の回数や順序も効いている可能性が残る。
- 解法: 毎回テンプレートからコピーする。費用はファイルコピー1回で、失うのは前回の起動でOVMFが覚えた設定だけである。ZaytOSは毎回同じESPから同じ構成で起動するので、覚えていてほしいものは無い。原因が確定していなくても、テストのたびに状態が持ち越される作り自体が「実行ごとに条件が変わる」という観測上の不確実性であり、無くす価値がある。
- 教訓 / 再発防止: **既知の不具合というラベルが自作のバグを覆い隠していた。** 「環境要因」「既知の事象」として説明を打ち切ると、そこで調査が止まる。同じ症状に3回遭遇しても、ラベルが貼ってあるだけで誰も実装を疑わなかった。次に似た症状に当たったときは、既知の事象で片付ける前に、自分の実装がその症状を作っていないかを先に確かめること。
- 自動再試行の位置づけが変わった: 起動失敗と判定した場合に1回だけ再試行する処理は残すが、これは「頻繁に起きる既知事象への対処」ではなく「起きないはずのことが起きたときの保険」になった。基準線は0件であり、1件でも出たら異常の兆候として扱う。

## 2026-07-22 「順序を逆にすると壊れる」は、意図的に踏まないと観測できない（M5-a-2-2）
- 背景: 2MiBページの分割は、PTを確保してゼロ埋め → 512エントリを書く → PDエントリを8バイト1回で差し替え → TLB無効化、の順で行う。順序を逆にして「PDエントリの差し替えを先、512エントリの書き込みを後」にすると、PDがゼロ埋めのPTを指す中間状態が生じる。
- **当初の想定が誤っていた**: 順序を逆にすれば即座にフォルトする、と考えていた。実際は違う。中間状態が存在するのは512回の書き込みをしている間だけで、その間にCPUがその領域へ触らなければ、何事もなく完了してしまう。実行中のコードやスタックがその2MiBページに載っていれば命令フェッチやスタックアクセスが踏むが、実測ではコードもスタックも4KiBページに載っており（`granularity:`の行）、そもそも2MiBの分割対象にならない。影響のない領域を対象にした場合は、誰も触らないのでフォルトしない。
- **中間状態が危険であることと、それを観測できることは別の事実である**: 順序を逆にして何も起きなかったとしても、それは「安全だった」ことを意味しない。たまたま誰もその瞬間に触らなかっただけである。したがって「順序を逆にしたら動いてしまった」を記録しても、順序の正しさの証明にはならない。証明したいのは「順序を守らないと壊れる」であって「たまたま動いた」ではない。
- 解法: PDエントリを差し替えた直後に、対象領域の先頭を1バイト読む処理を挟む（`paging-test-wrong-order`）。中間状態を確実に踏む。結果は #PF（`exception: vector=14`）で、`cr2=0x0000000001800000`はスクラッチ領域の先頭、すなわち踏んだアドレスそのものを指した。`qemu-debug.log`の`v=0e`も1件で一致する。正しい順序では同じ位置で何も起きない。
- 同じ型の誤りをもう1件踏んだ: `invlpg`を落とす検証（`paging-test-no-invlpg`）で、アンマップ対象のページを**アンマップ前に一度も触っていなかった**。触っていないページにはTLBエントリが存在しないので、`invlpg`を落としても「古い翻訳が残る」状態にならない。最初に書いた形では、invlpgを発行するビルドと落としたビルドの両方が #PF になり、invlpgの有無が結果に現れなかった。アンマップ前に1回書き込むようにしたところ、落としたビルドではフォルトせずに書いた値（`0x123456789abcdef0`）がそのまま読め、発行するビルドでは #PF になった。**対にして初めて「invlpgが効いている」と言える。**
- 教訓 / 再発防止: 「壊した状態を作った」だけでは検査にならない。壊れた結果が観測できる経路まで用意して、初めて検査になる。壊しても何も起きないなら、それは検査が届いていないということであって、実装が安全だということではない。

## 2026-07-22 検査は通っていたが、対象に入っていなかった（unsafeのSAFETYコメント）
- 症状: `cargo xtask check`の「unsafeブロックがSAFETYコメントを伴っているか」の検査が通っていた。ところが後日、同じコミットを取り出して同じ検査を走らせると落ちる。コードは1行も変わっていない。
- 原因: 検査の対象を`git ls-files "*.rs"`で列挙していた。**これは追跡済みのファイルしか出さない。** 新しく書いたファイルは、`git add`するまで対象に入らない。
- **なぜ気づかなかったか**: 作業の順序である。新しいファイルを書く → 検査を通す → `git add`してコミットする、という自然な順序だと、**そのファイルの最初の検査は追跡される前に走る。** 素通りしたまま「すべて通過」と報告され、次に検査が走るまで誰も気づかない。実際に`kernel/src/paging/verify.rs`が2コミット（7425d17、2070f8e）のあいだ見逃されていた。この2コミットは検査が落ちる状態のまま履歴に残してある。隠すより、こういう見落としが起きる形を残すほうが役に立つ。
- 裏付け: 同一ファイル・同一内容で、追跡状態だけを変えた対照実験を行った。未追跡の`.rs`にSAFETYコメント無しの`unsafe`を置くと`--- unsafe/SAFETY: OK`（素通り）、`git add -N`した直後に同じ検査を走らせると`--- unsafe/SAFETY: FAILED (1 block(s))`となる。追跡状態以外は何も変えていない。
- 解法: 列挙を`git ls-files --cached --others --exclude-standard`へ変えた。追跡済みと、無視されていない未追跡の両方が対象になる。`--exclude-standard`を付けるのはローカル専用のファイルやビルド成果物を拾わないためである。`tools/docstyle.py`も同じ列挙方法だったので、あわせて直した。どちらも修正後に同じ対照実験を行い、未追跡でも検出されることを確認している。
- 教訓 / 再発防止: **検査の対象範囲が「今そこにあるもの」ではなく「gitが知っているもの」で決まっていた。** 新規追加こそ最も検査を必要とする場面なのに、そこだけ穴が空いていた。検査を書くときは、何を検査するかと同じくらい、何を対象として列挙するかを見ること。「検査が通った」は「対象に入っていた」ことを含意しない。
- 関連: 同じ日に、コミット文体の検査が基準コミット自身を対象外にしていたことも判明した。`b22c360..HEAD`は`b22c360`を含まないため、規約を適用した最初のコミットだけが検査されていなかった。基準を日付へ変えた際に、集合を突き合わせて発覚した。件数だけを見ていたら気づかない。

- 教訓 / 再発防止: featureの下にあって既定ビルドに入らない経路は、`--full`を走らせるまで壊れたことに気づけない。`--full`は「大きな節目」で走らせる決まりだが、T-2の完了時には走っていなかった。ビルドが通ることを型の正しさの証明にできるのは、その経路が実際にビルドされる構成に限る。

## 2026-07-23 例外テストの捕捉が先頭行で打ち切られ、後続のマーカーを取りこぼす
- 症状: `cargo xtask check --full`で`exception-test double-fault`がまれに落ちる。`on IST1=true`が捕捉したシリアルに含まれず`markers=false`になる。単体（`cargo xtask run --exception-test double-fault`）では毎回通り、`on IST1=true`まで全行出る。
- 原因: `cmd_exception_test`の待機ループが、待ち条件をダンプの**先頭行**（`[ERROR] exception: vector=8 `）だけにしていた。それが現れた瞬間にQEMUをkillするため、後続のダンプ（GPR・CR2・`on IST`・`halting`）がシリアルへ書き出される前に切れることがある。ハンドラは`vector=`の後に十数行を続けて出すので、killがその書き出しと競合する。
- 解法: 待ち条件に**ダンプの終端行**（`[ERROR] halting (cli + hlt loop)`）を加え、`vector=X`と終端行の両方がそろうまで待ってからkillする。ハンドラは必ず最後にこの行を出すので、これで全行がそろう。マーカーテストで既に踏んだ「先頭のマーカーで打ち切ると最後のマーカーを取りこぼす」（2026-07-22の項）と同じ型で、例外テスト側にも同じ穴が残っていた。
- 教訓 / 再発防止: 「あるマーカーが出たら打ち切る」は、そのマーカーが最後に出る場合にしか正しくない。複数行のダンプを検証する待機は、終端行を見てから打ち切ること。

## 2026-07-23 デモ用のNOPそりが.textを膨らませ、カーネルイメージが2MiB境界をまたいでH-2が壊れた（M5-d）
- 症状: M5-dのプリエンプティブデモで、set→storeの窓を広げるためワーカー本体にNOPそりを長く積んだところ、H-2（カーネル高位マッピングの構築・検証、`kernel/src/paging/verify.rs`）が`UnexpectedHugePageEntry`で失敗した。デモのコード量を増やしただけで、ページング周りには一切触れていない。
- 原因: NOPそりが`.text`を膨らませ、カーネルイメージが2MiB境界をまたいで育った。その結果、実行中のコードとスタック（RIP/RSP）が2MiBページに載り、4KiB粒度を前提にH-2のwalkerがそこを辿ると2MiBのhuge pageエントリに当たって`UnexpectedHugePageEntry`を返す。deferred-decisionsに「`StackBlock`が2MiBページに載ると事前アサートで止まる」として登録してあった2MiB境界の事象を、そりの膨張が実際に引き起こしていた。
- 解法: NOPそりをメモリカウンタの遅延ループへ置き換えた。`mov`でカウンタに初期値を入れ、`dec`/`jnz`で回す数命令で済み、そりの長さ（`PREEMPT_WINDOW_SLED`）がコード量に効かない。カウンタはメモリに置くのでpatternを保持する15本のGPRも壊さない。窓を広げる目的（プリエンプトがset→storeの窓に落ちる確率を上げること）はループ回数で調整でき、`task-widen-preempt-window`で長くしても`.text`は膨らまない。
- 教訓 / 再発防止: 予見して登録しておいた保留項目（deferred-decisionsの「ガードページのsplit化」＝`StackBlock`が2MiBに載る事象）が、まったく別の変更（デモのコード膨張）で現実になった。解禁条件を「`StackBlock`が2MiBページに載るレイアウト変更が起きたとき」と具体に書いておいたことが、原因の特定に直接効いた。deferred-decisionsの該当項目が実際に機能した実例である。コード量を増やすだけの変更でも、イメージサイズが境界をまたぐと低レイヤの前提（4KiB粒度）が崩れうる。デモや検証コードの膨張も、機能追加と同じくイメージレイアウトへの影響として見ること。

## 2026-07-23 共有バッファがstore後・照合前のプリエンプトで別ワーカーに上書きされ誤検出（M5-d）
- 症状: M5-dのプリエンプティブデモで、GPR照合がまれに「タグが壊れた」と報告してhaltする。実際にはコンテキストスイッチは15本のGPRを正しく保存・復元しており、破壊ビルドでもない通常のワーカーで起きた。
- 原因: 15本のGPRを書き出す共有バッファ`GPR_BUF`は、ワーカーA/Bで1個を共有している（一度に1タスクしか走らないので、協調的なM5-cでは共有で問題が無かった）。プリエンプティブでは、あるワーカーが`GPR_BUF`へstoreした後・`verify_preemptive_gprs`で照合する前にtimerがプリエンプトすると、別のワーカーが同じ`GPR_BUF`を自分の値で上書きする。照合が走るときには他タスクの値が入っており、自分のbaseと食い違って誤検出になる。
- 解法: ワーカー本体で、store直前に`cli`し、照合を呼んだ後に`sti`する。この区間だけは別タスクがプリエンプトできないので、storeした値をそのまま照合できる。検査対象の窓（15本をsetしてから`cli`するまで、`IN_GPR_WINDOW=1`の区間）は`cli`の前にあり、プリエンプト可のまま残す。保存・復元が正しいかはその窓で検査し、共有バッファの上書きはその後の`cli`区間で防ぐ。二つは別の関心事なので、保護する区間を分けた。
- 教訓 / 再発防止: 「一度に1タスクしか走らないから共有でよい」という前提は、協調的（自発的yieldのみ）でしか成り立たない。プリエンプティブになると、straight-lineに見えるコードの任意の位置で別タスクへ切り替わる。M5-cからM5-dへ移るとき、共有状態を触る区間が「yieldを挟まないから安全」なのか「プリエンプトされても安全」なのかを区別すること。前者はM5-dで崩れる。

## 2026-07-24 Ring 3遠征の畳み（longjmp）後にDS/SSがnullのままでsti前検査が落ちる（M5-e-3）
- 症状: Ring 3遠征そのもの（iretqでRing 3へ落ち、cliが#GPになり、予期の畳みでカーネルへ戻る）は成功しているのに、遠征の後段でsti前検査（ADR-0018 §2）の項目1が`DS=0x0000 SS=0x0000`（期待0x0010）で落ちる。遠征のログはすべて正常で、#GPも正しく畳まれている。
- 原因: `long modeのiretqで低特権（Ring 3）へ落ちるとき、CPUはDPL<CPLになったDS/ES/FS/GSをnull化し、#GPの特権変化でSSもnullになる。` 遠征の戻りは、例外ハンドラの`-> !`を保つためiretqを経ないsetjmp/longjmp相当を使う。longjmpはRSPとcallee-savedは復元するが、iretqが本来やるSS/セグメントの復元は行わない。したがってDS/ES/FS/GS/SSがnullのままメインへ戻る。64bitの実行自体はnullセグメントでもフラットモデルで続くため、DS/SSを実状態で照合するsti前検査まで顕在化しなかった（それより前の64bitコードは素通りする）。
- 解法: 遠征復帰後（`ring3::enter`のlongjmp復帰直後）に、DS/ES/SS/FS/GSを`KERNEL_DATA_SELECTOR`へ明示的に再ロードする。iretqで戻る通常のタスクスイッチ（M5-c/d）ではiretqがSSを復元するのでこの問題は起きない。iretqを経ない戻り経路に固有である。
- 教訓 / 再発防止: iretqを経ない戻り（setjmp/longjmp、あるいは将来の別経路）を使うと、iretqが本来担うSS/セグメントの復元が抜ける。加えて低特権への遷移でCPUがセグメントレジスタをnull化する。この2つが重なると「実行は続くが、セグメントを実状態で見た検査だけが落ちる」という、症状の出所が分かりにくい形になる。iretqを迂回する戻りを書くときは、戻り側でセグメントを明示復元すること。syscall/sysret（M5-f第二段階）も同種の注意が要る。

## 2026-08-13 遠征スタックが静かに溢れ、離れた場所の静的変数が壊れた（S11-5のspawn）
- 症状: `spawn("/bin/hello")`が最後まで正しく走る。子は写像され、`write`と`exit`を発行し、終了状態0で戻り、空間の会計も合う（8枚消えて8枚が隔離）。**その直後**に`#PF`（error code 0x0、not present・read・supervisor、`cr2=0x1a`）で止まる。フォルトした場所は`core::ptr::drop_glue::<Option<BklGuard>>`で、`rdi`が`0x12`（18）という無意味な値だった。
- 最初の見立てと、それが外れたこと: `rdi`が壊れているので、`spawn_from_ring3`のフレームに積んだ`&mut Option<BklGuard>`が上書きされたと考えた。**上書きしうるのは、子のカーネル入場がRSP0を親のスタックに向けていた場合である。** そこで「子のカーネル入場がどのRSPで起きたか」を判定行に足したところ、**実際に親の遠征スタックの上で起きていた**（`RSP=0x...445090`が親の`0x441140..0x445140`の中）。ここまでは当たっていたが、**「RSP0の計算が間違っている」という見立ては外れていた。**
- 原因: `ring3::enter`が使う深さ（`EXCURSION_DEPTH`）そのものが壊れていた。`spawn`の入口では1と読めるのに、`run_loaded_program`の直前では`511`だったり`0xffff80000000f000`だったりする。**値が起動ごとに違い、どれも「どこかのスタックフレームに載っていそうな値」である**——ループの添字や、direct map越しのアドレス。壊れた深さで`excursion_stack_range_at`を引くと範囲外として添字0へ丸められ、**子のRSP0が親のスタックの上端になる。**
- 真の原因: **親の遠征スタック（16KiB）が溢れていた。** `spawn`が来るまで、このスタックに乗るのは`syscall_entry`と`dispatch`、あるいは畳みのハンドラだけだった。**`spawn`は同じスタックの上でローダー一式を走らせる**——`load_user_program`・`load_user_program_into`・`run_loaded_program`と、`UserProcess`（`FileTable`を含む）・`Quarantine`・`Records`。デバッグビルドでは一時オブジェクトがすべてスタックに載る。**遠征スタックは`.bss`の配列でガードページが無いので、溢れは止まらずに下の静的領域を書く。** そこに`EXCURSION_DEPTH`があった。
- 解法: 3つ。**(1) 大きさをメインのカーネルスタックと同じ64KiBにした**——起動時の`load_user_program`はあちらの上で問題なく走っており、同じ処理が乗るなら同じ大きさが要る。**(2) 使う前に既知のバイト（`0xE5`）で埋め、戻ってから下から走査して実際に使った量を測り、判定行に出す。** 実測は`syscall-test`の遠征で21096バイトだった——**16KiBを明確に超えており、溢れていたことが数字で確かめられる。** **(3) 最下部256バイトを見張り区間とし、そこが変わっていたら止める。** ガードページの代わりである。
- 教訓 / 再発防止: **最初の見立ては当たったが、原因の見立ては外れていた。** 「子のカーネル入場が親のスタックの上で起きている」までは判定行を足して実測で当てたが、そこから「RSP0の計算が間違っている」と読んだのが誤りだった。**真の原因を教えたのは値そのものである**——511、`0xffff80000000f000`。**起動ごとに違い、どれも「どこかのスタックフレームに載っていそうな値」だった。****静的変数が取りうる値ではなく、スタックの中身である。** そこで初めて溢れを疑った。**壊れた値の「顔つき」は、壊した主体を指す。** **スタックの大きさは「今そこに何が乗るか」で決まっており、乗るものが変わった時点で古くなる。** 16KiBは「システムコールのディスパッチが乗る」前提で決めた値で、その前提は`spawn`が破った。**そして遠征スタックにはガードページが無いので、破れたことが黙って起きる。** カーネルスタックにガードページを張ってあるのは同じ理由であり、**ガードが無い側にも同等の検出を置くまで、片方だけが守られている状態だった。** 症状が原因から遠い（子は完全に正常に走り終え、親が戻った後で落ちる）ので、**判定行を足して観測を原因の側へ寄せなければ、レジスタダンプからは辿り着けない。**

## 2026-08-20 像とユーザープログラムを太らせると、前提が次々に外れる（ziの段の族）

`zi`を作る途中で、**同じ族の失敗が3回出た。** 症状も直し方も違うが、**根は1つである。**

### 像を育てたら測り直す定数（4つ）

**この節は役目を終えた（e-4）。** **`build.rs`が像を建てた直後に外の道具へ訊いて定数を生成する**ので、**人が測り直す作業は無くなった**（2026-08-21の節）。**第0手は残る**——**像に入っていないことは、定数の導出では気づけない。** 以下は、なぜ手で測っていたかと、何が動いたかの記録である。

**第0手は、像に入ったことを確かめることである。**

    debugfs -R "ls /bin" <fs.img>
    debugfs -R "ls /data" <fs.img>

**定数の食い違いは「像の中身が想定と違う」の症状でもある。** 実際、`build.rs`のコピー先の一覧に足し忘れて`/bin/zi`が像に入っておらず、**測った定数が前回と食い違ったことで気づいた。** 先に中身を見れば一手で分かる。

像は`target/x86_64-unknown-none/debug/build/kernel-*/out/fs.img`にある（`ls -t`で最新を取る）。

| 定数 | 何に依存するか | 測り方 |
|---|---|---|
| `CORRUPT_FS_BLOCKS` | 使用ブロックの上端（前置きがそれを覆うこと） | `dumpe2fs <img>` の `Free blocks:` の先頭が上端+1 |
| `FS_MOTD_INODE_AT` | `/etc/motd`のinode番号。**その前に入るファイルの本数**で動く | `debugfs -R "stat /etc/motd" <img>` の1行目 |
| `FS_MOTD_DATA_BLOCK` | `/etc/motd`のデータブロック番号 | 同上の`BLOCKS:`の行 |
| `FS_INDIRECT_TABLE_BLOCK` | `/data/indirect-first`の単一間接テーブルの番号 | `debugfs -R "stat /data/indirect-first" <img>` の`(IND):` |

**動かないこともある。** `/data/sparse-hole`を足したときは`FS_INDIRECT_TABLE_BLOCK`が動かなかった（`/data`の中で`indirect-first`より後ろに来るため）。zi-d-2で`zi`が伸びたときも4つとも動かなかった（既存のブロック内に収まった）。**「足したから動くはず」と決め打たず、そのつど測ること。**

**`FS_INDIRECT_TABLE_BLOCK`はこれで7度目の移動である**（定数のdocが履歴を持っている）。**次に像を育てる者——Cの移植で確実に来る——は、落ちてから探すのではなく、先にここを読むこと。**

### なぜ「収まらなくなったら落ちる」が効いたか

3回のうち2回は、**機構が先に落ちて直し方まで言った。** `CORRUPT_FS_BLOCKS`が尽きたときは`raise CORRUPT_FS_BLOCKS`と判定行が出し、`.bss`の欠落は**区画の本数の対（`declared` / `mapped`）を判定行に足した瞬間に確定した。** **「張った本数」だけでは、正しい3本なのか4本のうち1本を落とした3本なのかが読めない**——この区別が付かずに切り分けが遠回りになったのが、対を足した理由である。

  - `zi-insert-drop-first`——**往復の判定を素通りしていた**（次項）。挿入の**本数**を数える形を足した。台本が送るのは2字である

**族として言えること。** **能力を足すと、既存の判定の前提が消えることがある。** **判定を足すときに前提を洗うのと同じく、能力を足すときにも洗うこと。** **今回なら、「像が持ち越される」を足した時点で、「建てた像の中身に寄りかかっている判定」を洗うべきだった。** **洗っていれば、2度起こす判定を書く前に見つかっていた。**

## 2026-09-03: 壊す位置を`build.rs`の定数から取っていたので、`--full`が1件落ちた

**原因は、壊す位置が構成ごとに違うことである。** **あの演習は`build.rs`が`dumpe2fs`へ訊いた番号（`INDIRECT_TABLE_BLOCK`ほか）を壊していた。** **`persist (zi)`は1度目を`zi-test`で、2度目を`persist-check-test`で建てる**——**構成が違うと`/bin/zi`の大きさが変わり、ブロックの並びがずれる。** **2度目は1度目が装置へ書いた像を読むので、自分の定数が指す先に目的の表が無い。**

**以前から在った脆さで、`ADR-0054`が像へファイルを2つ足したときに表に出た。** **`build_truncated_fs_image`のdocは、この形を半分書いていた**——「持ち越す構成では、装置の中身の使用上端が起動ごとに動きうるので、`CORRUPT_FS_LEN`が実態と合わなくなる」。**位置のほうは書かれていなかった。**

**直し方は「歩いて求める」である**（f-1の「終端は歩いて探す」と同じ形）。**カーネルは像を歩いて位置を作る。**

## 2026-08-31: 環境の源をファイルにしたら、種の中身に寄りかかった判定が3つ止まった（f-1 / f-1b）

**族は既に記録してある**（2026-08-30の「持ち越しが、起動時の判定の前提を壊した」）。**ここに書くのは、同じ族が短い間に3度出たことと、3度とも形が同じだったことである。**

**3つに共通する形が1つある。** **どれも「像の中身は建てたときのままである」を前提にしていた。** **その前提は、書き込みが持ち越されるようになった時点で、利用者の普通の操作で壊せるようになっている。**

**次に足すときの目安。** **`build.rs`が置いた中身を前提にする判定を書くなら、その前提が利用者の操作で壊せるかを先に見ること。** **壊せるなら、止める形にしない。**
