# ZaytOS の長期構想

**この文書は構想であり、決定ではない。** ADR（`adr/`）は決定の記録で
Status を持つが、ここに書くのはまだ決めていないことである。両者を混ぜると、
決まっていないものが決まったように見える。そのため独立した文書にしてある。

## この文書が現在の設計を縛らないこと

**構想を理由に先回りの抽象化を導入してはならない。**「将来 POSIX 互換に
するかもしれないから今こうしておく」という判断は、この文書を根拠にできない。
先回りの抽象化を避けることは本プロジェクト最大の設計判断であり、そちらが
優先される。

構想が現在の実装に影響してよいのは、**コストがゼロまたは無視できる場合に
限る**。たとえば、同じ実装量で名前の付け方だけが変わるような場面で、将来の
方向に沿う側を選ぶのは構わない。抽象化の層を 1 つ増やす、使う予定のない
引数を足す、といった判断の根拠にはならない。

構想を実際に着手する段になったら、その時点で ADR を書いて決定に変える。

## 当面の目標: M6 の完了

`roadmap.md` の M6 までを完走することが、当面の到達点である。

- GUI（描画は M3 で基盤ができている）

## その先の構想

**優先順位ではなく、興味の方向として並べる。** どれから着手するか、
そもそも着手するかは、その時点で決める。

### 実機（USB ブート）での起動

現在は QEMU + OVMF のみ。UEFI 経由で起動する構成（ADR-0005 / ADR-0008）は
実機でもそのまま通るはずだが、確かめていない。実機で動かすと、QEMU が
吸収していた差異（ファームウェアの実装差、タイミング、デバイスの有無）が
一気に表面化する。

M4 の時点で既にその予兆はある。`io_wait()` は QEMU では不要だが実機を
見据えて入れてあり、スプリアス割り込みの判定も QEMU ではまず発生しない
ものを先に実装している（ADR-0018 Addendum 3）。

### SMP（マルチコア）対応

ADR-0002 でシングルコアを前提と決めており、同期プリミティブは中身を
差し替えられるよう呼び出し側インターフェースだけ安定させてある
（`common::critical::Locked<T>`）。ただし現在の `Locked<T>` は「取得中は
割り込み禁止」という論法に依存しており、SMP では別コアの同時アクセスを
防げないため実装ごと見直しになる。

APIC と ACPI（MADT）が前提になる点も、M4 で PIT を選んだ理由と表裏である
（ADR-0018 §6）。

### POSIX への部分的な準拠

**完全準拠は目標としない。** POSIX の全体は膨大で、準拠そのものを目的に
すると学習という主目的から外れる。「よく使われる部分がそれらしく動く」
程度を想定する。

### Linux 互換のシステムコール

静的リンクされた Linux バイナリを、そのまま実行できるようにすること。
BusyBox の shell が動く程度を想定する。

動的リンクを避けて静的リンクに限るのは、ローダとリンカの互換性まで
踏み込むと範囲が跳ね上がるため。x86_64 の Linux ABI は安定していて
資料も多く、「実際に他所で作られたバイナリが自分の OS で動く」という
確認の仕方ができるのが利点である。

## Linux バイナリを動かすために必要になるもの（把握している範囲）

構想を実際に着手する段になったときの見落としを減らすため、**現時点で分かって
いる構造的な前提**を挙げておく。**これは着手の約束ではない。** 個々を今から
作り込むことは、この文書の冒頭で禁じたとおり行わない。

「ELF を読み込めた」で満足してしまい、その先で原因の分からない落ち方をする
箇所が複数ある。とくに TLS と初期スタックレイアウトは、**バイナリを読み込め
たのに最初の命令付近で落ちる**という形で出る。

### M5-f（ユーザーランド）の段階で要るもの

| 項目 | 内容 |
|---|---|
| **`syscall` / `sysret`** | 64bit の Linux バイナリは `syscall` を発行する。`int 0x80` は 32bit 互換経路で使われない（ADR-0020） |
| **TLS（`fs` ベース）** | musl の静的バイナリは起動時に `arch_prctl(ARCH_SET_FS)` を呼ぶ。**これが無いと最初の関数呼び出し付近で落ちる**。FS ベースは MSR（`IA32_FS_BASE`）で設定する |
| **`auxv` と初期スタックレイアウト** | ELF エントリに入る時点で、スタックに `argc` / `argv` / `envp` / `auxv` が規定の順で積まれていなければならない。`AT_PHDR` / `AT_PHENT` / `AT_PHNUM` / `AT_ENTRY` が無いと libc の初期化が失敗する |
| **`AT_RANDOM`** | musl はスタックプロテクタの初期化に使う。16 バイトの乱数へのポインタが要る |
| **`brk` / `mmap`** | 静的リンクでもヒープの取得に使う。**ユーザー空間のメモリ管理は VFS より先に要る** |
| **`PT_TLS` / `PT_GNU_STACK` の解釈** | ELF ローダーが `PT_LOAD` だけを見ていると、TLS の初期イメージが配置されない |

### M6（ユーザーランドの実用化）で要るもの

| 項目 | 内容 |
|---|---|
| **プロセスの終了と `wait4`** | 実装しないと shell が子を刈り取れず、ゾンビが溜まる。プロセス構造の寿命管理が要る |
| **シグナル** | Ctrl-C（`SIGINT`）が無いと shell が使い物にならない。**シグナル配送はユーザースタック上にフレームを積む**必要があり、コンテキストスイッチの設計に影響する |
| **VFS（ファイルディスクリプタ抽象）** | FAT を直接システムコールへ繋ぐと、後から VFS を挟むのが高くつく |
| **実時刻** | `clock_gettime` には RTC/CMOS の読み出しか TSC の較正が要る |

### ELF ローダーの移設と一体で設計すべきこと

現在 ELF パーサは bootloader 内にあり、ユーザープログラムのロードで再利用する
には `common` へ移す必要がある。**ただし単に移すだけでは足りない。**
上記の `PT_TLS` / `PT_GNU_STACK` の解釈と、初期スタックレイアウトの構築を
同じ設計の中で扱うこと。移設の時点でこのチェックリストを見直す。

### 実機まで見据えると

| 項目 | 内容 |
|---|---|
| **USB HID** | PS/2 キーボードは現代の実機にほぼ存在しない。実機起動には USB スタックが要る |
| **APIC と ACPI** | PIC / PIT は SMP では使えない。ACPI（MADT）の解析が伴う |

## 「Linux に近づく」という表現について

規模感を誤らないために、現実的な認識を書いておく。

Linux カーネルは現在**約 4000 万行**ある。ただしその大部分は**デバイス
ドライバとアーキテクチャ対応**であり、あらゆるハードウェアとあらゆる CPU に
対応してきた歴史の蓄積である。ZaytOS は x86_64 のみ（ADR-0006）で、
デバイスも QEMU が提供する最小限しか扱わない。この部分で近づくことは
そもそも目指していない。

一方、**カーネル中核**（スケジューラ、メモリ管理、VFS）は相対的に小さい。
ここは「何をどう決めたか」という設計判断の集まりであり、規模ではなく
理解の対象になる。

参考として、**Linux 0.01（1991年）は約 1 万行**だった。ZaytOS が M6 に
到達した時点で、規模・機能ともにこの水準に近くなる見込みである。

したがって:

- **機能の幅で Linux に近づくことは到達不能**である。目指さない。
- **設計の理解という意味では現実的な目標**である。「なぜそう作られているか」
  を、自分で作ることで理解する。

この区別を持っておかないと、規模の追求に引きずられて「細く長く」という
開発スタイル（`architecture.md` §1）が崩れる。
