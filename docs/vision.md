# ZaytOSの長期構想

この文書は構想であり、決定ではない。
ADR（`adr/`）は決定の記録でStatusを持つが、ここに書くのはまだ決めていないことである。
両者を混ぜると、決まっていないものが決まったように見える。
そのため独立した文書にしてある。

## この文書が現在の設計を縛らないこと

構想を理由に先回りの抽象化を導入してはならない。
「将来POSIX互換にするかもしれないから今こうしておく」という判断は、この文書を根拠にできない。
先回りの抽象化を避けることは本プロジェクト最大の設計判断であり、そちらが優先される。

構想が現在の実装に影響してよいのは、**コストがゼロまたは無視できる場合に限る**。
たとえば、同じ実装量で名前の付け方だけが変わるような場面で、将来の方向に沿う側を選ぶのは構わない。
抽象化の層を1つ増やす、使う予定のない引数を足す、といった判断の根拠にはならない。

構想を実際に着手する段になったら、その時点でADRを書いて決定に変える。

---

## 当面の目標: M6の完了

`roadmap.md`のM6までを完走することが、当面の到達点である。

- GUI（描画はM3で基盤ができている）
- マウス入力
- プリエンプティブマルチタスク（M5）
- 簡易ファイルシステム（M6、FATの読み取りから）

ここまで到達すれば「自作OS」として一通りの形になる。
その先も拡張を続ける前提だが、着手が決まっているのはM6までである。

## その先の構想

優先順位ではなく、興味の方向として並べる。
どれから着手するか、そもそも着手するかは、その時点で決める。

### 実機（USBブート）での起動

現在はQEMU + OVMFのみ。
UEFI経由で起動する構成（ADR-0005 / ADR-0008）は実機でもそのまま通るはずだが、確かめていない。
実機で動かすと、QEMUが吸収していた差異（ファームウェアの実装差、タイミング、デバイスの有無）が一気に表面化する。

M4の時点で既にその予兆はある。
`io_wait()`はQEMUでは不要だが実機を見据えて入れてあり、スプリアス割り込みの判定もQEMUではまず発生しないものを先に実装している（ADR-0018 Addendum 3）。

### ファイルシステム、GUI、ウィンドウシステムとその上のアプリケーション

M6のFAT読み取りから先。
ウィンドウシステムを載せ、その上でテキストエディタ・電卓・ゲームのような小さなアプリケーションが動くところまでを構想する。
描画の基盤はM3にあり、入力はM4のキーボードとマウス（未着手）が入口になる。

### 音声出力

出力デバイスの入口はPCIの列挙である（後述）。

### 動画再生

デコードと描画とタイミング制御が同時に要る。
音声出力とファイルシステムが揃った後の話になる。

### 3D描画

ソフトウェアレンダリング、またはvirtio-gpuを想定する。
**ベンダ固有のGPUドライバは想定しない。**
実機のGPUに個別対応し始めると、規模の主要因であるドライバの幅にそのまま踏み込むことになる。

### x86_64以外への移植可能性

ADR-0006でx86_64のみと決めており、**現時点で移植用の抽象化は作らない**。
ただしハード依存部と純粋ロジックを分離するという既存の方針（`architecture.md` §8）は、移植を考えるならそのまま準備になる。
分離を維持すること自体が目的であって、移植のために層を足すことはしない。

### SMP（マルチコア）対応

ADR-0002でシングルコアを前提と決めており、同期プリミティブは中身を差し替えられるよう呼び出し側インターフェースだけ安定させてある（`common::critical::Locked<T>`）。
ただし現在の`Locked<T>`は「取得中は割り込み禁止」という論法に依存しており、SMPでは別コアの同時アクセスを防げないため実装ごと見直しになる。

APICとACPI（MADT）が前提になる点も、M4でPITを選んだ理由と表裏である（ADR-0018 §6）。

### PCIバスの列挙（上記の多くが前提にするもの）

ストレージ、音声、virtio-gpu、ネットワークは、いずれもPCIの列挙が入口になる。
現在は未着手で、扱っているデバイスはPS/2キーボード・PIT・PIC・GOPのフレームバッファだけである。
これらはPCIを経由せずに触れる。

**依存関係の記録であって、次に着手するという意味ではない。**
着手するならADRから始める。

### POSIXへの部分的な準拠

完全準拠は目標としない。
POSIXの全体は膨大で、準拠そのものを目的にすると学習という主目的から外れる。
「よく使われる部分がそれらしく動く」程度を想定する。

### Linux互換のシステムコール

静的リンクされたLinuxバイナリを、そのまま実行できるようにすること。
BusyBoxのshellが動く程度を想定する。

動的リンクを避けて静的リンクに限るのは、ローダとリンカの互換性まで踏み込むと範囲が跳ね上がるため。
x86_64のLinux ABIは安定していて資料も多く、「実際に他所で作られたバイナリが自分のOSで動く」という確認の仕方ができるのが利点である。

## Linuxバイナリを動かすために必要になるもの（把握している範囲）

構想を実際に着手する段になったときの見落としを減らすため、**現時点で分かっている構造的な前提**を挙げておく。
これは着手の約束ではない。
個々を今から作り込むことは、この文書の冒頭で禁じたとおり行わない。

「ELFを読み込めた」で満足してしまい、その先で原因の分からない落ち方をする箇所が複数ある。
とくにTLSと初期スタックレイアウトは、**バイナリを読み込めたのに最初の命令付近で落ちる**という形で出る。

### M5-f（ユーザーランド）の段階で要るもの

| 項目 | 内容 |
|---|---|
| **`syscall` / `sysret`** | 64bitのLinuxバイナリは`syscall`を発行する。`int 0x80`は32bit互換経路で使われない（ADR-0020） |
| **TLS（`fs`ベース）** | muslの静的バイナリは起動時に`arch_prctl(ARCH_SET_FS)`を呼ぶ。**これが無いと最初の関数呼び出し付近で落ちる**。FSベースはMSR（`IA32_FS_BASE`）で設定する |
| **`auxv`と初期スタックレイアウト** | ELFエントリに入る時点で、スタックに`argc` / `argv` / `envp` / `auxv`が規定の順で積まれていなければならない。`AT_PHDR` / `AT_PHENT` / `AT_PHNUM` / `AT_ENTRY`が無いとlibcの初期化が失敗する |
| **`AT_RANDOM`** | muslはスタックプロテクタの初期化に使う。16バイトの乱数へのポインタが要る |
| **`brk` / `mmap`** | 静的リンクでもヒープの取得に使う。**ユーザー空間のメモリ管理はVFSより先に要る** |
| **`PT_TLS` / `PT_GNU_STACK`の解釈** | ELFローダーが`PT_LOAD`だけを見ていると、TLSの初期イメージが配置されない |

### M6（ユーザーランドの実用化）で要るもの

| 項目 | 内容 |
|---|---|
| **プロセスの終了と`wait4`** | 実装しないとshellが子を刈り取れず、ゾンビが溜まる。プロセス構造の寿命管理が要る |
| **シグナル** | Ctrl-C（`SIGINT`）が無いとshellが使い物にならない。**シグナル配送はユーザースタック上にフレームを積む**必要があり、コンテキストスイッチの設計に影響する |
| **VFS（ファイルディスクリプタ抽象）** | FATを直接システムコールへ繋ぐと、後からVFSを挟むのが高くつく |
| **実時刻** | `clock_gettime`にはRTC/CMOSの読み出しかTSCの較正が要る |

### ELFローダーの移設と一体で設計すべきこと

現在ELFパーサはbootloader内にあり、ユーザープログラムのロードで再利用するには`common`へ移す必要がある。
ただし単に移すだけでは足りない。
上記の`PT_TLS` / `PT_GNU_STACK`の解釈と、初期スタックレイアウトの構築を同じ設計の中で扱うこと。
移設の時点でこのチェックリストを見直す。

### 実機まで見据えると

| 項目 | 内容 |
|---|---|
| **USB HID** | PS/2キーボードは現代の実機にほぼ存在しない。実機起動にはUSBスタックが要る |
| **APICとACPI** | PIC / PITはSMPでは使えない。ACPI（MADT）の解析が伴う |

## 「Linuxに近づく」という表現について

規模感を誤らないために、現実的な認識を書いておく。

Linuxカーネルは現在**約4000万行**ある。
ただしその大部分は**デバイスドライバとアーキテクチャ対応**であり、あらゆるハードウェアとあらゆるCPUに対応してきた歴史の蓄積である。
ZaytOSはx86_64のみ（ADR-0006）で、デバイスもQEMUが提供する最小限しか扱わない。
この部分で近づくことはそもそも目指していない。

一方、**カーネル中核**（スケジューラ、メモリ管理、VFS）は相対的に小さい。
ここは「何をどう決めたか」という設計判断の集まりであり、規模ではなく理解の対象になる。

参考として、**Linux 0.01（1991年）は約1万行**だった。
ZaytOSがM6に到達した時点で、規模・機能ともにこの水準に近くなる見込みである。

したがって:

- **設計の理解という意味では現実的な目標**である。「なぜそう作られているか」を、自分で作ることで理解する。
- **機能の幅は、追わないのではなく、必要になった範囲から段階的に広げる。** Linux 0.01相当は通過点であり、その先も拡張を続けて、実用に耐える規模の自作OSとして公開・配布することを目標に含める。

ドライバとアーキテクチャ対応が規模の主要因であるという上記の分析は、そのまま正しい。
だからこそ、幅は「必要になったものから」広げる。動かしたいものが決まってから、それに要るデバイスを足す。
逆順にすると、使う予定のないデバイスへの対応が積み上がり、規模の追求に引きずられて「細く長く」という開発スタイル（`architecture.md` §1）が崩れる。

**目標が大きくなったことは、この文書冒頭の規律を緩める理由にならない。**
規模が大きくなるほど、先回りの抽象化の害は大きくなる。
「いずれGUIを載せるから今この層を作る」という判断は、これまでと同様に根拠にできない。
