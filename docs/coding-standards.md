# コーディング規約

必要が生じた項目から追記する。
現在あるのは、文体・一時的な破壊の手順・回帰チェックの必須条件・記録の更新の4つである。

---

## 1. 文体

一貫した文体は差分を読みやすくする。
表記が揺れていると、変更の本質と表記の揺れが同じ差分に混ざり、レビューで前者だけを見ることが難しくなる。

### 適用対象

| 対象 | 規則1（和文と英数字の間の空白） | 規則2から6 |
|---|---|---|
| コミットメッセージの件名 | 適用する（`cargo xtask check`が検査する） | 適用する |
| Markdownドキュメント（`docs/`・README） | 適用する | 適用する |
| `.rs`のコード内コメント | **適用しない** | 適用する |

**規則1を`.rs`へ適用しないのは、実態がそうなっているためである。**
既存の`.rs`はすべて空白を入れる書き方で統一されている。
守られていない規則を書いておくと、規則の側が信用されなくなる。
新規ファイルは周囲の`.rs`に合わせて空白ありで書くこと。

`.rs`にも適用したくなった場合は、**それを検査する仕組みを用意する作業とセットで行うこと。**
検査の無い規則は必ず腐るので、既存分を一括で直しても検査が無ければ同じ状態へ戻る。
その一括修正は他の主題と無関係なので単独のコミットにすること。

**コミットメッセージは件名だけを対象とし、本文は対象外とする。**
`cargo xtask check`の検査もそうなっている。理由は3つある。

- 規約の主な対象はREADME・docs・コード内コメントであり、コミット本文はその次の優先度になる
- 本文には識別子や式がそのまま現れる（`is_multiple_of`、`% 16 == 0`、`#TS / #NP / #SS / #GP`など）。和文と隣り合う箇所で空白を落とすと読みにくくなり、バッククォートで囲む書き方をコミットメッセージへ課すのは一般的でない
- 揃えるために履歴の書き換えを増やすコストに見合わない

「本文も直すべきでは」と後から再検討しないよう、対象外であることを明示しておく。

**適用開始時点はコミット`b22c360`である。**
それ以前の53件は規約を定める前に書かれたものであり、違反ではない。
履歴の書き換えは行わない。
開始時点が書かれていないと、過去の全コミットが違反しているという誤った認識が残る。

### 規則

1. 和文と英数字の間に半角スペースを入れない（「M4完了」「ADR-0019の段階分割」「QEMUのmonitor」）。例外はコードブロック・インラインコードの中、英語複合語の内部（Write-Combining等）、コマンド例・パス・URL、表の桁揃え
2. 文の途中で改行しない。1文1行、または段落単位で書く（Markdownは表示時に折り返されるため途中改行は不要）
3. emダッシュ（—）で文をつながない。読点・括弧を使うか文を分ける
4. 「〜することで、〜が可能になります」のような説明過多の言い回しや、同じ内容の言い換えによる水増しをしない
5. 装飾を絞る。太字は本当に強調が要る短い語句だけ、見出しはh3まで、箇条書きの入れ子は2階層まで、表は表であることに意味がある場合だけ。太字の境界が全角括弧・句読点と隣接すると強調が閉じない（CommonMarkの接規則）ため、括弧は太字の外に置く
6. 表記を揺らさない。三点リーダは「…」、和文中の括弧は全角、である調で統一し、同じ概念には同じ語を使う
7. 絵文字を使わない（コミットメッセージ・ドキュメント・コード内コメントのすべて）

**コマンド例が和文と隣り合う場合。**
規則1をそのまま当てると`cargo xtask check --fullで`のようになり読めない。
かといって空白を残すと規則違反になる。
この形は避け、コマンドを括弧に入れて文末へ置くか、文を分ける。

    悪い: feat: cargo xtask check --full で回帰チェック一式を走らせる
    良い: feat: 回帰チェック一式を走らせる（cargo xtask check --full）

### 機械的に適用するときの例外

既存の文書へ規則を機械的に適用すると、規則が効きすぎてMarkdownを壊す。
実際に規則1がタスクリストのマーカーを壊し、規則2が行の結合位置に空白を残した。

- **Markdownの構文要素の一部である空白は削除しない。** 規則1の対象外とする。タスクリストの`- [x] `、リストマーカー`- ` `1. `の後、見出しの`#`の後、引用の`>`の後、表の区切り`|`の前後が該当する。`- [x]パニック…`と書くとGFMはタスクリストと認識せず、チェックボックスが描画されない
- **行を結合する際は、結合位置に空白を残さない。** 規則2を適用するとき、和文どうしを繋ぐ場合は空白なし、英単語どうしを繋ぐ場合は空白1個とする。`する。 静的変数`のように句読点の後に半角空白が残ると、HTMLでは見える空白として描画される
- **強調の開き記号の直後をインラインコードにしない。** 直前が空白でも句読点でもない位置にアスタリスク2つを置き、その直後がバッククォートだと、左フランキングにならず記号がそのまま表示される。和文か英字かは問わない。規則5の全角括弧・句読点の件と同じ性質の問題である。**この規則はこの行自身にも効く**（アスタリスクを直接書くと、この項目の強調が閉じなくなる）

文体を機械的に変換したときは、変換後にレンダリング結果が意図どおりに変わっていることを確認する。

## 2. 一時的な破壊・変更の手順

意図的な破壊（検査が働くかの確認）や、一時的な書き換え（版を食い違わせて検出を見る等）を行うときは、**作業ツリーがクリーンな状態から始める。**
未コミットの作業があるなら、先にコミットするかstashしてから壊す。

理由は、戻し方が安全になるためである。
クリーンから始めていれば`git checkout <file>`が「一時変更だけを戻す」正しい道具になる。
未コミットの作業が同じファイルにあると、同じコマンドがその作業ごと消す。
実際に、版の食い違いを戻すつもりで`git checkout bootloader/src/loader.rs`を実行し、同じファイルにあった未コミットの実装を丸ごと失ったことがある。

「戻すべき1行だけを戻す」という規律で守る形は採らない。
覚えていないと守れないものは、いずれ守られない。
**壊す前にツリーをクリーンにする**なら、道具の側が安全になる。

### クリーンにできない場面がある

「コミット前に破壊確認を行う」と「クリーンなツリーから壊す」は両立しないことがある。
新設したモジュールに対する検査の破壊確認がそれで、対象が未追跡なら`git checkout`はそもそも効かず、同じ作業ツリーの他のファイルには未コミットの変更が乗っている。
**これは規則同士の衝突であって、どちらかの違反ではない。**

その場合は次の代替手順を使う。趣旨（規律ではなく道具の側で安全にする）は同じである。

1. 壊す前に対象ファイルを作業ツリーの外へコピーする
2. 壊して確認する
3. コピーから書き戻す
4. **バイト単位の一致を機械で確認する**（`md5sum`の一致、または`diff`が空）

4を目視で済ませないこと。
復元し忘れや部分復元は、見た目では分からない形で残る。
`git status`は未追跡ファイルの中身の違いを教えてくれない。

### 性能の比較は同一セッションで交互に測る

**A と B の性能を比べるときは、同一セッションで `A, B, A, B, …` の順に測る。**
別々の時期に測った2組を比べてはならない。

実際に起きた。`cpu_id()` の実装を変えた前後で周回数を比べ、**「約8%の退行」と結論した。誤りだった。**
別セッションで測ったbaselineと比べたためで、ホスト負荷のドリフトが差に化けていた。
交互に測り直すと差は +0.1% で、幅は完全に重なった。

**「幅が重ならない」は独立した根拠にならない。**
2組が別々の時期に測られていれば、ドリフトがそのまま非重複を作る。
実際、当時は標本を12まで増やして非重複を確かめていたが、**系統誤差は標本数では消えない。**
「標本を増やせば分解能が上がる」は偶然誤差についてのみ成り立つ。

順番に並べて測る（`AAAA…BBBB…`）のも不十分である。
前半と後半で負荷が違えば同じ誤りになる。

**これは「同じ条件で比べていないものを比べた」の2件目である。**
1件目はサボタージュfeature付きビルドの成果物を測った件で、対処は「値は既定ビルドの起動ログから取る」だった。
2件出たので、比較の手順として明文化する。
**測る前に「この2つは同じ条件か」を問うこと。** 成果物の構成（1件目）と、測った時期（2件目）の両方が条件である。

### 分けると決めたコミットでは`git add -A`を使わない

上の手順が「戻し方」なら、こちらは「載せ方」である。

**分割すると決めたコミットでは、`git add -A`ではなくパスを明示して`add`する。**
`-A`は作業ツリーの変更を全部載せるので、**別のコミットへ入れる予定だった変更が混ざる。**

実際に起きた。検査の追加を単独コミットにすると決めていたのに`git add -A`で作業し、
同じ作業ツリーにあった別件のdocsの変更を1行取り込んだ。
`git commit --amend`と書き戻しで直したが、**混ざったこと自体は`git status`では分からない**
（コミット後に`git show --stat`を見て気づいた）。

**パスを明示すれば、名前を挙げていないものは入らない。**
過剰な取り込みが「検出できる」ではなく「起こりえない」形になる。
`-A`を使ってよいのは、作業ツリーの変更を全部1つのコミットへ載せると決めているときだけである。

コミット後に`git show --stat`で載ったファイルを確認するのは、この手順を採っても続けること。

## 3. 回帰チェックの必須条件

通常の実装ループでは`cargo xtask check`を回す。
`cargo xtask check --full`はQEMUを多数回起動するため毎回は重いが、次の場合は必須とする。

- マイルストーン、または細分化された段階の完了時
- `unsafe` / 割り込み / ページテーブル / GDT / IDTに触れた変更のコミット前
- ツールチェイン、`.cargo/config.toml`、リンカスクリプト、feature構成を変更したとき

必須にする理由は実例がある。
M4-e（キーボードIRQ）が`interrupt-test alt-offset`を壊していたのに、以後M5-a-1まで誰も走らせず、気づくまで1日以上かかった。
起動時の検証は通り続けていたので、通常起動を見ているだけでは分からない。

### 原因を書くときは、そこから何が出るかを列挙する

1つの原因から帰結が複数出ることがある。**観測できた順に1つずつ書くと、観測しなかった帰結が書かれないまま残る。**

**実際に起きた（S6-a）。** `setup_preemptive_tasks`の`set_current_index(0)`から帰結が2つ出ていた——**APのアイドルタスクが切り替え先になり範囲検査が止める**のと、**BSPの落ち先が他コアのcurrentと重なり二重選択の検出器が鳴る**のと。**書かれていたのは前者だけだった。** 前者はその検査が主張しているものなので目に入り、後者は「鳴らないはず」の側だったので目に入らなかった。

**手順——原因を書いたら、そこから何が出るかをその場で数える。** 目に入った帰結が全部だと仮定しない。**根拠になった事例は`verification-coverage.md`にある。**

### コメントの置き場所——読む人で決める

**誰が読むかで置き場所が決まる。** Rustの慣行に沿う。

| 種類 | 読む人 | 書くもの |
|---|---|---|
| `///` `//!` | **使う人**（rustdocに出る） | 何をするか、契約、`# Safety`、`# Panics`、`# Errors`、使い方 |
| `//` | **触る人** | **その行の隣にないと分からない局所の事情**（なぜこの順序か、なぜこの値か） |
| docs / ADR | **設計を追う人** | 決定と理由、却下した案、測定の結果、失効条件 |

**`///` は「1行の要約 → 空行 → 詳細」で始める。**

**`///` に経緯・却下した案・測定の結果を書かない。** それらはdocsが正で、**コメント側は1行の指し先にする**（T1のB1/B3/B5と同じ形）。

**内容は資産である。文体の改善で消さない。** 測定の数字・失効条件・却下した案は残す。**変わるのは置き場所だけである。** **文体の改善と置き場所の是正は別の作業なので、同じ変更に混ぜない。**

#### docsへ寄せるときは、食い違っていないかを見る

**置き場所を是正するには「docsに同じ話があるか」を見ることになり、そこで内容の鮮度が
露出する。** 規則は2つだけである。

- **docsに同じ話があった**: 指し先1行にする前に、**食い違っていないかを見る。**
  食い違っていたら**どちらが正しいかを判断して報告する。勝手に片方へ寄せない。**
- **docsに無かった**: コメント側にしか無い事実なので残す。**鮮度は問わない**
  （比べる相手がいない）。

**限界——docsに無いものに古い記述が紛れていても、この手順では検出できない。**

#### `# Safety` と `SAFETY:` だけは、現在の呼び出し側と照合する

**コメントの内容の鮮度は、この段では原則問わない**（全コメントの内容検証になり、
掃きが終わらない）。**`unsafe` の契約だけを別枠にする。** 理由は3つ。

- **間違っていると「守ったつもりで守っていない」を作る。** ただ古いだけのコメントより
  危険である。
- **対象を機械で列挙できる**（`unsafe` に `SAFETY:` を要求する静的検査が既にある）。
- **比べる相手がはっきりしている**——「現在の呼び出し側」。呼び出し箇所が0か1なら
  1つ見るだけで済む。

**手順——`# Safety` と `SAFETY:` は、現在の呼び出し側が満たしている形と一致しているかを
見る。呼び出し箇所が多い場合は代表を1つ。一致していなければ報告する（勝手に書き換えない）。**

**洗った結果の件数を数えること。** T2-bの1本目（`paging/switch.rs`）で1件出た——
`switch_to` の契約が「恒等写像で引き続きアクセス可能であること」と書いていたが、
**恒等はB-2bで外してあり、現在の唯一の呼び出し側（`AddressSpace::activate`）は
上位256本の共有で同じ要件を満たしている。契約が2段階前の実装を前提にしていた。**
**1本目で出たので、他にもある見込みが高い。件数はS8以降への申し送りになる。**

**実際に見つけた（T2-a）。** `MAX_CPUS`のコメントが3段のうち1段目で止まっていた
（旧「4では境界を越える」→ S4-c-1の再測「越えない」→ S4-c-2で「再測の結論も失効」）。

**文体だけを見ていると、内容が正しいかを一度も問わずに、読みやすい形で誤りを保存する。**
**しかも読みやすくなったぶん信じられやすくなる。** これは文体を整える作業に構造的に
伴う穴である。

### コメントの文体——簡潔に、要点を先に

**1文を短く。要点を先に。** 次を避ける。

- **同じことを2度言う**（「Xである。つまりYである」でYがXの言い換え。T1の`C1`）
- **一般論から入る**（「一般に〜は〜である。本実装では〜」）
- **接続詞の水増し**（「なお」「ここで重要なのは」「したがって」の多用）
- **一文が長く、修飾が入れ子**
- **「〜する必要がある」で語尾を膨らませる**
- **箇条書きにできることを散文で書く**
- **コードを読めば分かることの言い直し**

**数値目標は置かない。** 「減らす」が目的化すると、**残すべきものを削る圧力になる**（T1の教訓）。

**強調（`**`）はコード内のコメントでは原則使わない。** コメントは短いので、
要点は語順で示せる。**指示文やレビューの体裁を持ち込まない**——
あちらは判断を促すために強調するが、**コメントは読んで理解するためのもので目的が違う。**

**基準は見本そのものであって、比率ではない。** `common/src/percpu.rs` を見本とする。
実測は**77% → 61%、最長ブロック 55行 → 23行**だが、**これは目安であって
達成すべき数ではない。**

### コメントだけを変えるときの安全網

**振る舞い不変を機械で言える。** 次の3つを確認する。

- **`__kernel_end` が動かないこと**
- **起動ログの正規化差分が空であること**（`cargo xtask run --boot-log-diff`）
- **`cargo xtask check --full` が緑であること**

**成果物のハッシュはこの3つに入れない。入れてはならない。** **コメントだけを変えてもカーネルのバイナリは変わる**——`expect`や`assert`が埋める`core::panic::Location`に行番号が入るので、行が動けば`.rodata`が動く。T2-bでdocを12行移したとき、`.text`は同一のまま`.rodata`が12バイト変わった。**md5を安全網に足していたら、コメントを1行移すたびに落ちる。** **`.text`の比較は切り分けには使える**（`verification-coverage.md`の「検査が落ちたときの切り分け」第2段）。安全網とは役割が違う。

**T1のときには`boot-log-diff`が無かった。** 当時はビルドと`--full`だけで、**「ログの形が変わっていないこと」を機械で言えなかった。** S6-dで作ったので、いまは言える。

**この安全網は、想定していなかった用途で効いた（T2-a）。** 見本の書き直しで
`boot-log-diff`が落ち、原因は**「コメントだけのつもりで入れたコード変更2件」**だった
（関数の畳み込みと、定数の位置の移動）。**どちらも振る舞いは同じだがコードの変更である。**
**コメントを書き換える段は、この混入が起きやすい**——読んでいるうちに直したくなる。

**安全網の強さは、対象の状態によって変わる。** 「コメントだけの変更」は
**docの付け先が正しいファイルでしか成り立たない。** 付け先が壊れている
（docが隣の項目に付いている）場合、直すには項目の移動が要り、**そのとき安全網は
「差分が空であること」から「差分の全件を挙げて理由を書くこと」へ落ちる。**

**付け先の壊れは「量が多い」問題ではなく「量が無駄になっている」問題である。**
T2-aで見つけた55行のdocブロックは`use`文に付いており、**`MAX_CPUS`自身にはdocが
無かった**——**55行が誰も読まない場所にあった。**
**「1行の要約から始める」があれば、要約を持たない55行のブロックが`use`に付く形は
書けない。**

### 分けられるとき、どちらを先にするか——中断した時点で壊れているか、重複しているか

分割の順序は**「途中で止まったらどうなるか」で決める。**

- **先に消してから足す**と、**中断した時点で壊れた指し先が残る。**
- **先に足してから消す**と、**同じ事実が2箇所にある状態が1コミットぶん生じる。**
  これは壊れではなく**重複**で、次のコミットで解消する。

**壊れと重複なら重複のほうが安全側である。** したがって**先に足してから消す。**

**T2-bの運用がこの形である**——コメントからdocsへ移すとき、**先にdocsへ足し、
次のコミットでコメントを指し先1行に変える。**

### 分けられない組——featureの3点と、シグネチャと呼び出し側

コミットを分けるとき、**同じコミットに入らなければ単独でビルドが通らない組**がある。
**分ける前に見ること。**

- **featureの宣言（`Cargo.toml`）・参照（`#[cfg(feature = ...)]`）・`TEST_HOOKS`の行**（S7-c）
- **関数のシグネチャの変更と、その呼び出し側すべて**（S7-e。`AddressSpace::new`へ
  引数を1つ足したので、`main.rs`の呼び出しが同じコミットに要った）

**どちらも「型と純粋ロジック」対「実機の経路」という軸を跨ぐ。** その軸で分けようと
すると、**前のコミット単独でビルドが落ちる。**

### featureを挟むと「型と実機」ではコミットを分けられない

コミットを分けるとき、**「型と純粋ロジック」と「実機の経路」**という軸は使いやすい。
前者は実機に触れず、後者はレビューの重さが違うからである。

**しかしfeatureを挟むと成立しない。** **featureの宣言（`Cargo.toml`の`[features]`）は、
それを`#[cfg(feature = ...)]`で参照するコードと同じコミットに要る。**
宣言を後のコミットへ回すと、**前のコミット単独では`unexpected_cfgs`で落ちる。**

**実際に踏んだ（S7-c）。** 型の側（`address_space.rs`）に破壊featureの分岐があり、
宣言だけが実機側のコミットに入っていた。**`clippy -D warnings`が捕まえた**——
S6-eで「`TEST_HOOKS`の逆向きを覆っている」と確かめた、あのlintである。

**あわせて`TEST_HOOKS`の行も同じコミットに要る**（kernelのfeatureは全件が
`TEST_HOOKS`に載っていることを`cargo xtask check`が見るため）。

**境界の引き方——featureを1つ足すなら、宣言・参照・`TEST_HOOKS`の3つは分けられない。**

### 段の刻みを見積もるときは、軸が2つ増えるものとして数える

段の着手時に「この段は何コミットの想定か」を宣言する。**そのとき「1つの段は1つの軸で
終わる」と置くと足りない**（S6は10想定で実際は12）。

**増える出所には型が2つあり、どちらもこの進め方では起きて当然である。**

- **作業中に、既存の検査や記録の誤りが見つかる。** それは独立した軸なので分ける
  （S6-a。既存の検査の禁止マーカーが誤っていた）。
- **前提となる、振る舞いを変えない移動が分かれる。** 機能変更と混ぜないので分ける
  （S6-c。ヒープの静的を bin から lib へ移した）。

**見込みに入れること。** 入れずに宣言すると、正しく分けたことが超過として出る。

### 参照（golden file）を録り直すときは、差分を全件挙げて理由を書く

起動ログの正規化差分（S6-d）のように**参照と突き合わせる検査**は、
**ログを増やす変更のたびに参照の録り直しが要る。**

**これが反射的な操作になると、差分を見ずに録り直すようになり、検査の価値が静かに消える。**
「通すために表明を弱めない」の一種である——**弱めているのは表明ではなく、確認のほうである。**

**手順——録り直すときは、変わった行を全件挙げ、変わった理由を同じコミットに書く。**
**機械にしたのは手間であって、判断ではない。**

### 畳む条件を増やすと、既存の破壊が捕まる場所が前へ移る

判定に段階がある検査では、**前段の判定を1つ増やすたびに、後段で捕まえていた破壊が前段で捕まるようになる。** 破壊が検出されなくなるのではなく、**検出する場所が前へ移る。** 期待マーカーを合わせるのを忘れると、検出の有無は変わらないのにその破壊の項目だけが落ちる。

S8で2件出た。どちらも畳みの前段の判定を足したときである。

- `gate-dpl0`（S8-a）——フォルトRIPの厳密一致を畳みの判定から外し、位置の突き合わせを畳んだ後の呼び出し側へ移した。以前は畳まれずに例外ダンプ（`exception: vector=13`）へ落ちていたのが、畳んでカーネルへ戻り呼び出し側の主張（`folded at an unexpected place`）が捕まえる形へ移った。
- `drop-rsp0`（S8-c）——フレームの信用の判定（従=ハンドラのスタック）を畳みの前に足した。以前は畳んだ後に`handler_in_excursion`が捕まえていた（`RSP0 did not take effect`）のが、畳む前の健全性判定（`exception frame is not trustworthy`）へ移った。

**予告した逆向きは起きなかった。** S8-cの時点で「S8-dでベクタを4つへ広げると、条件が緩む方向なので逆向きの移動（前段から後段へ）が起きうる」と予測したが、S8-dの2コミットは既存のどの破壊の期待マーカーも動かしていない（`git show`で確認）。ベクタ集合を広げたのは畳みの条件1を緩めたが、**緩めた先に既存の破壊が無かった**ので移動が起きなかった。予測は外れた。

**この形を踏むのは、畳む・受理する条件を足したときである。** そのとき既存の破壊の期待マーカーを1つずつ見直すこと。

### 新しい静的な検査は、主張が偽の状態を一度作って落ちることを確かめてから置く

振る舞いの検査には**破壊feature**という文化がある——**主張が偽の状態をわざと作り、
検査が実際に落ちることを確かめる。**
**静的な検査には、その対応物が無い**（シンボルの存在、項目会計、スタブ表の一致、
`TEST_HOOKS`の網羅など）。

**無いまま置くと、空振りしていても緑のままである。**
実際、これらが落ちるところは**偶然の事故で観測されただけ**である
（項目会計が2回、`TEST_HOOKS`が1回）。**意図して確かめた記録は無かった。**

**手順**——検査を置いたら、**主張が偽になる最小の変更を入れ、落ちることを見る。**
そのあと**書き戻してバイト単位の一致を確かめる**（`md5sum` か `diff`）。

**主張が偽になる道が複数あるなら、そのそれぞれについて確かめる。**
**1 つ確かめても、残りが空振りしていることは分からない。**
**最初の実例は S6-b である**——許可リストの検査が守るものは 2 つあり
（**一覧が静かに狭くなること**と、**新しい口が静かに開くこと**）、
**一覧から 1 件外す**のと**許可されていない場所に 1 つ足す**のと、両方で落ちることを見た。

**実例（S5-b）**: 世代フラッシュのシンボルを見る検査を足したとき、
`#[inline(never)]` を `#[inline(always)]` へ変えてシンボルを消し、
`guard symbols: FAILED` が出ることを確かめてから書き戻した。

**一時的な破壊の手順はこの文書の別の節に従う**（クリーンなツリーから始めるか、
コピーから書き戻して一致を機械で確かめる）。

### 判定に使ってよいのは、低い特権の側が自由に作れない量だけである

**判定できることと、判定してよいことは別である。**
Ring 3の実行を中断するか、カーネルごと停止するかを分ける判定を設計するときに出た。

低い特権の側が自由に動かせる量を「想定外だから壊れている」の根拠にすると、
**その側が1命令でカーネルを止められる。**
`RIP`と`RSP`がこれに当たる。
Ring 3はどちらも自由に動かせるので、範囲外であることは**違反**であって破損ではない。
`CS`は違う。
Ring 3は任意のセレクタを載せられないので、**既知でない値は破損の証拠になる。**

判定に使ってよい量は次の2つに絞られる。

- 低い特権の側が作れない量（`CS`、ハンドラ自身が走っているスタックの位置）
- カーネル自身が置いた状態（遠征中かどうかのフラグなど）

**採らなかった候補も、この軸で説明できる。**
`SS`はRing 3が作れない点で`CS`と同じだが、特権変化のときにCPUがnull化することがあり、
「既知の集合」にnullを入れるかで判定が曖昧になる。
`CS`で足りるので増やさない。
RFLAGSの予約ビットは、`CS`が通っているフレームでそこだけが偽になる状況を説明できない。
**説明できない検査は置かない。**

### アーキテクチャが保証しない性質を判定の根拠にしない

検査の期待には、**仕様が約束している性質だけ**を使う。
許されているだけの性質（実装がそうしてもよいが、しなくてもよいもの）を期待に置くと、無関係な変更で検査が落ち、原因の切り分けが「実装の欠陥」ではなく「検査の前提」に行き着くまで空転する。

実例（S8-d）。`tlb-no-shootdown`は「世代を上げなければAPは古い翻訳で触れて成功する」を期待に置いていた。
**TLBが翻訳を保持し続けることは、アーキテクチャが許しているだけで約束していない**——実CPUでもQEMUでも、容量の都合でいつでも捨てられてよい。
QEMUのTCGはソフトウェアTLBのエントリを無効化事象なしに捨て、どれを捨てるかがバイナリのレイアウトで決まるため、**カーネルの無関係な変更で同一バイナリ13/13の決定的なFAILになった。**
検査の本来の主張（世代を上げなければAPは世代フラッシュをしない）はフラッシュ回数の不動で観測でき、保証されない性質に頼る必要は無かった。

**「判定に使ってよいのは、低い特権の側が自由に作れない量だけである」と同じ族の規則である。**
あちらは相手が作れる量を根拠にしない、こちらは相手が守る義務のない性質を根拠にしない。

### 確率的な項目を「直した」と言う基準——5回の緑では足りない

発生率pの揺れは、n回の再試行が全部通る確率が(1-p)^nで残る。
8%なら5回とも通る確率は約66%で、**5/5は「消えた」の証拠にならない。**

「直した」と言うには次の2つを分けて書くこと。

- **機序の側の理由**——何を塞いだか、なぜその機序では再発しえないか
- **再試行の結果**——回数と、その回数で言える範囲（8%を95%の信頼で否定するには約35回要る）

機序の説明が無いまま再試行の緑だけで閉じない。
逆に機序を塞いだ場合も、再試行の結果は「再現しなかった」としてだけ書き、回数に見合わない主張をしない。

### docsを大きく組み替えるときは、正規化した差分で確かめる

**コードは組み替えても、壊せばビルドか検査が落ちる。docsは何も落ちない。**
段落を割る・重複を指し先へ寄せる・節を移すといった組み替えは、**目視でしか確かめられない**——
というのが既定の状態で、実際にそれで見落としが起きうる。

**下限を機械で与える。空白と改行を落としたテキストで差分を取る。**

    python3 - <<'EOF'
    import difflib
    a = ''.join(open('before.md').read().split())
    b = ''.join(open('after.md').read().split())
    for tag, i1, i2, j1, j2 in difflib.SequenceMatcher(None, a, b, autojunk=False).get_opcodes():
        if tag != 'equal':
            print(tag, repr(a[i1:i2][:200]), '->', repr(b[j1:j2][:200]))
    EOF

**改行と字下げだけを入れた組み替えなら、差分は空になる。**
差分が出たなら、**出た箇所が意図した削除・置換と一致することを1件ずつ確かめる。**

**この手順が答えているのは「何も落ちないので目視でしか気づけない」である。**
コード側がビルドと検査から得ている機械的な下限を、docs側にも与える。
**目視の代わりではなく、目視の前に置く関門である**——
一致していれば読む対象が「意図した差分」だけに絞れる。

**実例**: S4後の整理で9,619字の項目を4段落へ割ったとき、この差分で
「置換1件と削除1件」だけが出ることを確かめた。**割り方そのものは差分に現れない。**

**長い段落は、そのファイルを構造的に触る機会に割る。** 割るためだけにファイルを開かない。
改行を入れるだけの変更でも、**表・会計行・マーカーを載せた箇条書きに当たると壊れる**
（S4後の整理で、機械的に割ったところ会計行と表の行を壊し、どちらも検査が捕まえた）。
**得るもの（読みやすさ）に対して、単独で行う危険が釣り合わない。**
重複の解消や節の移動でそのファイルを開いたときに、ついでに割ること。

**「1,000字超の件数」は読みやすさの代理指標として機能しない。**
S4後の整理では、件数が8件から11件へ**増えた**。
一方で**最長は9,619字から3,534字へ下がっている**——
9,619字の1行を4つに割った結果、1,000字超の断片が増えたためである。
**改善した実体（最長）と悪化した見かけ（件数）が逆を向いた。**
件数だけを見て「整理して悪化した」と読まないこと。**代理指標を使うなら最長を見る。**

### バイナリを直接読むときは、各バイナリの構成を先に確かめる

イメージ会計の値は**既定ビルドの起動ログから取る**と決めてある（`verification-coverage.md`）。
**その規律は起動ログの話で、`nm`や`readelf`でバイナリを直接読む場合を覆っていない。**

`cargo xtask check --full`や個別の破壊確認は、`target/`に**破壊feature付きの成果物**を残す。
その状態で`nm`を読むと、別構成のバイナリを既定ビルドとして測る。
**実際に踏みかけた**（S4-c-4-2で、直前に破壊確認を走らせた`target/`に対して`nm`の差分を取り、報告の直前に気づいた）。

**手順**: バイナリを読む前に、**そのバイナリを既定構成で作り直す**。

    cargo build --target x86_64-unknown-none -p kernel --bin kernel

比較のために2つのバイナリを読む場合は、**両方について作り直した時点を確かめること。**
片方が古い構成のままでも、値は出てしまう。

**「読む前に作り直す」を手順に入れるのは、確かめるより作り直すほうが速く、確実だからである。**
構成を後から見分けるのは難しい（feature名はどのビルドにも文字列として現れる）。

### `--full`の完全な実行には`/dev/kvm`が要る

**TCGは2つのvCPUを並行に走らせない**（S4-aの実測。`-smp 2`を86秒回しても同時進入は0回で、入口の窓を広げても変わらなかった）。
したがって「2つのコアが同時にカーネルへ入っていること」は、TCGでは観測できない。
この観測はKVMでのみ行える。

**ただしKVMでも決定的ではない**（4回のうち3回は観測できたが、1回は116秒のあいだ観測できなかった）。
**確率的なものを`--full`へ入れると、落ちたときに退行か揺らぎかが区別できなくなる。**
したがってこの観測は検査項目にせず、`cargo xtask run --kernel-entry-concurrency`で手で回す。

**KVMが使えない環境では、「環境要因」として区別して出力する。**
主張が落ちたのと混ぜない。混ぜると、BKLの退行と読み違える。

#### 決めた方針が、後から該当した項目へ適用されていない

**上の判断（確率的なものは`--full`へ入れず手で回す）は`kernel-entry-concurrency`にだけ適用されている。**
**同じ性質の項目が、少なくとも4つ`--full`に入ったままである。**

| 項目 | 症状 | 観測した頻度 |
|---|---|---|
| `smp-ap-test tlb-shootdown` | APが4ティックで止まり、探りの2度目の触りが起きない | 単独12回中1回（約8%） |
| `interrupt-test keyboard` | 設定は全てOKでスキャンコードが1つも届かない | S5-bとT2-cで各1回。単独では通る |
| `smp-ap-test smp-stimulus-layer1-off` | 第2層が弾いた行が出ない | T2-cで1回。単独5回は通る |
| `smp-ap-test smp-stimulus-both-layers-off` | 二重選択の検出行が出ない | T2-cで1回。単独5回中1回 |

**この一覧は、`--full`を回していて落ちたものだけを載せている。**
**載っていない項目について言えるのは「まだ落ちるところを見ていない」ことだけで、決定的であることを意味しない。**
**`--full`の実行回数が増えればこの一覧は増える見込みが高い。**
**実際、3項目を並べた直後に4つ目が出た。表が既に古くなったこと自体が、この一覧の性質の証拠である。**

**4つ目は3つ目と同じ梯子の項目だが、症状は同じでない。** 3つ目は第2層が弾いた行が出ず、4つ目は二重選択の検出行が出ない。
**同じ刺激（`sched-keep-workers-runnable`）を使うので同じ弱さを持つと見ているが、落ちる場所が違う。**

**T2-cでの実測**: `--full`を15回回して4回落ちた（約27%）。**4回とも`.text`の比較で切り分けており、退行は1件も無い。**

**これは「条件が発火したのに追わない」とは別の型である。**
あちらは追跡の先送りで、こちらは**方針の適用漏れ**である。方針は決まっており前例もあるのに、後から出た同種の項目へ適用されていない。
**3つとも、決めた時点では存在しなかった項目である**（`tlb-shootdown`はS5-c、`smp-stimulus-layer1-off`はS4-c-4-3、`interrupt-test keyboard`の主張が7つへ増えたのはS2-d-1c）。
**方針を決めたら、後から足す項目がその方針に該当しないかを足す時点で見ること。**

`smp-ap-test smp-stimulus-layer1-off`については`verification-coverage.md`に「AP起こし周りの時間の摂動に弱い」と記録があり、摂動を外して5/5へ戻したと書いてある。
**摂動が無くても落ちるので、その記録は実態より弱い。**

以下は`smp-ap-test tlb-shootdown`について詳しく調べたぶんである。**他の2つも同じ扱いでよい。**

**`smp-ap-test tlb-shootdown`は確率的なまま`--full`に入っている。**
T2-cで2度落ちた。**発生率は単独12回中1回（約8%）で、`--full`の中でだけ落ちるのではない。**
落ちた回のログはどちらも`ap_ticks=cpu1=4`が15秒間そのままで、**APが早期に止まっている。**

**切り分けは`.text`の比較で閉じる**（この文書の安全網の節と、`verification-coverage.md`の切り分けの第2段）。
コメントだけの変更なら`.text`が同一なので、その変更が原因でないことは言える。
**「単独で通ること」を根拠に数えないこと**——8%の発生率は標本3では捉えられない。
実際、1度目に落ちたときは単独3回が通ったので「`--full`の中でだけ落ちる」と分類したが、**その分類は誤りだった。**

**直すなら、前提条件を確かめて環境要因として区別する形になる。**
APのティックが進んでいることを検査の前提として確かめ、進んでいなければ主張の失敗ではなく環境要因として出す。
KVMの項で採った形と同じである。
**T2-cでは着手しない**（あの段の目的は大きいファイルのコメントを処理して次へ進むことで、検査の作り替えは範囲外である）。

**ビルドが通ったことをもって正しさの証明としない。**
低レイヤのバグは実行するまで顕在化しないことが多い。
QEMU実行とシリアルログでの確認までを1ループとする。

## 4. 記録の更新

docs（`roadmap.md`・`deferred-decisions.md`・`verification-coverage.md`・ADR）に書いた状態が変わったとき、**行を消さずに状態を書き換える。**
消すと、その判断がいつ何を根拠に変わったのかを後から辿れなくなる。
保留していた項目を解禁したときも、行は残して「決着済み」と分かる形にする。

### 状態を書き換えるときは、その行を最後まで読み直す

見出しや状態欄だけを直しても、**本文の中に命令形が残る。**
実際に起きた: 保留項目の1行について、項目名と解禁条件の欄を「決着済み」へ直したが、本文の中に「……をS1で判断する」「……を決め、理由を残すこと」という指示が3か所残っていた。
行の末尾には決着した旨が書いてあったので、通しで読めば矛盾には気づく。
しかし**途中だけを読んだ人には、未決の指示に見える。**

記録は行の一部だけを読まれる。
状態を書き換えるときは、次の2つを行うこと。

- その行に残っている命令形（「決めること」「判断する」「残すこと」）を、実施済みを示す形へ書き換えるか、決着の記述を指すようにする
- その項目を解禁条件として参照している他の記述を、`grep`で洗って追随させる

**まだ生きている規則は残す。** 上の例では「アドレスをハードコードしないこと」を残した。
粒度の判断は決着したが、この規則は次の段でも生きているためである。
「決着した判断」と「決着の結果として残る規則」を区別すること。

### 段を閉じるときは、その段の名前で全docsをgrepする

段（S3やM5-a-2のような細分化された単位）を完了にする前に、その段の名前で`docs/`を全件grepし、その段に割り当てられた項目が処理済みかを1件ずつ確かめる。

**割り当ては、その段の記述の中には無い。**
別の段の「実装しなかったもの」や、保留項目の解禁条件や、申し送りとして、離れた場所に書かれる。
段の中だけを見て作業すると、割り当てられていること自体が視界に入らない。
段を閉じる側は自分が書いた記述を読み直すので、他人が別の段で書いた割り当てだけが残る。

実際に落ちた。S3を完了にしたとき、`TIMER_TICKS`のper-CPU化を実施せず、次の段への申し送りにも書かなかった。
この項目はS0-bとS2の「実装しなかったもの」、および`verification-coverage.md`の申し送りの計3か所でS3へ割り当てられており、どれもS3の記述の中には無い。
同じ段で、検査項目の会計行（`verification-coverage.md`の推移）の更新も落ちた。
この行はS3-b-2b-1までしか伸びておらず、S3で最後に足した1項目が入っていない。
どちらもS3をgrepすれば当たる位置にある。

grepで当たった行は、次の3つのどれかへ落とす。**行は消さない。**

- 処理済み: 割り当て元の行を、処理済みを示す形へ書き換える
- 別の段へ移す: 移した先と理由を書き、割り当て元の段名も書き換える
- 未達のまま先送り: 何が未達かと、解禁条件を書く

到達条件として書いた項目が未達のまま段を閉じるなら、**その到達条件の文自体を書き換える。**
段の見出しだけを完了にして、同じ行の中に未達の到達条件を残さないこと。
これは上の「状態を書き換えるときは、その行を最後まで読み直す」を、段の単位で行うものである。

### ADRを書くかの条件

段を閉じるときや方針を決めたときに、それをADRにするかを次の条件で判断してきた。
**条件の文言はどこにも書かれていなかった。** 使う側の記憶に置いたまま、`roadmap.md`の2箇所（S6の締めとS7の締め）が「4条件に当てた結果」として結論だけを書いている。
**書かれていない基準は検算できない**ので、ここに起こす。

**根拠のあるもの**（`roadmap.md`に文言つきで現れている）。

- 条件(1) 複数の有力案から一つを選ぶ
- 条件(2) 後から変更すると作り直しが生じる
- 条件(4) 将来の保守者が単純化すると壊す

**(3)は再構成できなかった。** `docs/`の全文にも全履歴にも「条件(3)」は一度も現れず、条件の一覧を書いた記述も見つからない。
**したがってここでは3つとし、番号(3)は欠番のまま残す。**
番号を詰めないのは、`roadmap.md`の既存の2箇所が(1)(2)(4)という番号で参照しているためである。

**「4条件」という呼び方は、ここから使わない。** 数えられるのは3つである。
`roadmap.md`の2箇所は当時の記述としてそのまま残す（§4の「行を消さずに」に従う）。
**(3)にあたる条件を思い出した場合は、ここへ番号(3)として足すこと。** 欠番はそのための場所である。

条件に当てた結果は、ADRを書く場合はADR自身に、書かない場合は`roadmap.md`のその段の記述に残す。
**当たらなかった条件も書く。** 当たった条件だけを書くと、他を検討したのか漏らしたのかが後から分からない。

## 5. 報告に載せるコマンド出力

**報告に載せるコマンド出力は、実際の出力をそのまま貼ること。主題から再構成しないこと。**
再構成した出力は、**実在しないものを実在するように見せる。**

実際に起きた。ある段の報告の`git status`に`M docs/adr/0018-interrupt-enable-checklist.md`と載っていたが、**この名前のファイルは一度も存在していない。**
実在するのは`docs/adr/0018-interrupt-foundation.md`である。
到達不能なオブジェクトまで潰して確かめた（`git rev-list --all --reflog --objects`と、`git fsck --lost-found`が挙げるdangling commit全件の`git ls-tree -r`）ので、改名やrebaseで消えた版の可能性も否定できる。
ADRの主題が割り込みの有効化で、本文に「事前に潰すバグ（実装時のチェックリスト）」という節があるため、**出力を貼らずに主題から名前を組み立てたと推測される**（断定はできない。証拠で言えるのは「実在しないパスが載っていた」までである）。

**害は伝播する形で出た。** その報告を読んだ側が引き継ぎ文へ写し、次の作業者が存在しないファイルを探すところまで進んだ。
**実害が出なかったのは`ls docs/adr/`で即座に分かったからにすぎない。**
存在しないファイルではなく、存在するが内容の違うファイルを指していたら、気づかずに誤った前提で作業していた。

この運用は「報告はコピーである」ことに全面的に乗っている。
コミットハッシュ・検査項目数・実測値・ファイルパスは、いずれも読み手が検算する前提で書かれている。
**再構成した出力が1つ混ざると、検算そのものが成立しなくなる。**
