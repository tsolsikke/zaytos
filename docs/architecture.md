# ZaytOSアーキテクチャ方針

本ファイルは、現時点で確定しているアーキテクチャ・設計方針の 「現在の結論」を1箇所に集約したものである。
個別の判断に至った経緯・却下案の詳細は`adr/`以下の各ADRを参照。

- 詳細な経緯・却下案 → `adr/`（1決定 = 1ファイル）
- 要点の集約（このファイル）→ 現在確定している方針の一覧
- 保留した判断 → `deferred-decisions.md`（解禁条件つきの一覧）
- 主張と検査の対応 → `verification-coverage.md`（常に維持すると書いた性質に検査があるか）

---

## 1. プロジェクトの性格

- **主目的**: 学習。OSの基本機能を、理解しながら自作すること自体が目的。したがって基本的な機能（保護機構、割り込み、マルチタスク等）は省略しない。
- **開発スタイル**: 細く長く。堅牢性・理解を、機能量・速度より優先する。

## 3. 「堅牢さ」の定義（本プロジェクトでの立場）

堅牢さには2つの方向がある。

1. **防御的な堅牢さ**: 保護機構を厚くし、バグの被害を局所化する（Linux / Redox型）。
2. **単純さによる堅牢さ**: 保護機構を削り、コード量と複雑度を減らす（TempleOS型）。

本プロジェクトは学習目的のため **1（防御的な堅牢さ）** を採る。
保護機構は学習対象そのものであり、省略しない。
ただし規模の暴走を避けるため、モノリシック構成で全体の複雑度は抑える（マイクロカーネルの強い分離は初期段階では採らない）。

## 4. 技術スタック

```
[QEMU]                      … フルシステムエミュレータ（テスト環境）
  └─ [OVMF]                 … UEFI ファームウェア（既製ビルドを導入して使用）
       └─ [bootloader crate (.efi)]  … x86_64-unknown-uefi, uefi クレートで実装
            └─ [kernel crate (ELF)]  … x86_64-unknown-none, モノリシックカーネル本体
                 （bootloader が ELF ローダー経由でロードし制御を渡す。ADR-0008）

[common crate] … bootloader / kernel の両方から使う共有ロジック
                 （serial, log, cpu。#[panic_handler] は含まない）
```

- 言語: Rust。bootloaderは`x86_64-unknown-uefi`、kernelは`x86_64-unknown-none`（ADR-0008）。
- UEFI: `uefi`クレート（uefi-rs）。EDK2のビルドシステムは使わない。
- ファームウェア: OVMF（`apt install ovmf`等でパッケージ導入）
- エミュレータ: QEMU（`-serial stdio -no-reboot -no-shutdown -d int,cpu_reset`）。後半3つは常時付与する。既定のQEMUはトリプルフォルト等の致命的例外で無言のまま再起動を繰り返し、外から観測できなくなる。これを止めて例外とCPUリセット要因をログに残すためのもの。「ハングした」と判断する前に、まずこのログで例外の有無を確認する。
- 開発環境: WSL2（Ubuntu系）+ WSLg
- ビルド自動化: `cargo xtask`パターン

## 5. `x86_64-unknown-none`ターゲットの既定値（M2-0bで確認）

kernelクレートが使う`x86_64-unknown-none`は、ビルトインターゲットとして以下の既定値を持つ（`rustc -Z unstable-options --print target-spec-json`で確認、Rust 1.99.0-nightly時点）。
M4（割り込みハンドラ）・M5（コンテキストスイッチ）で影響しうるため記録する。

| 項目 | 既定値 | 意味・影響 |
|---|---|---|
| `disable-redzone` | `true` | レッドゾーン無効。割り込みハンドラが現在のスタックをそのまま使っても、呼び出し元のレッドゾーン領域を破壊する心配がない。**M4の割り込みハンドラはこの設定に依存している**（下記参照）。 |
| `features` | `-sse,-sse2,...,-avx2,+soft-float` | SSE/AVX全無効・ソフトウェア浮動小数点。通常のコード生成がXMM/YMMレジスタを一切使わないため、M4の割り込みハンドラでFPU/SSEレジスタの退避・復帰は不要（今後SSEを明示的に有効化する場合を除く）。 |
| `panic-strategy` | `abort` | unwind情報不要。bootloader側の判断（M1）と一致。 |
| `code-model` | `kernel`（高位負アドレス前提） | kernelをhigher-half（`0xffffffff80000000`）へリンクするので、既定の`kernel`をそのまま使う（ADR-0024）。恒等リンクの間は`small`へ上書きしていたが、B-2a-3の再リンクで既定へ戻した（ADR-0009、`.cargo/config.toml`）。 |
| `position-independent-executables` | `true`（PIE既定） | 固定アドレスへの静的リンク（higher-half、ADR-0024）と相性が悪いため、`relocation-model=static`で無効化している（`.cargo/config.toml`）。 |

上記の`code-model` / `relocation-model`の上書きは`.cargo/config.toml`の`[target.x86_64-unknown-none]`セクションに集約している。

### 5.1 red zone無効化への依存（M4で初めて実際に効く）

`disable-redzone`はM2-0bでターゲットの既定値として確認したが、**この設定が実際に効くのはM4の割り込みハンドラが最初**である。
red zone（RSPの下128バイト）が有効なままだと、リーフ関数がそこにローカル変数を置き、割り込みが入った瞬間にCPUがスタックフレームを積んで**その領域を破壊する**。

`.cargo/config.toml`のrustflags（`relocation-model=static`, `code-model=small`）はこの設定を上書きしない。
stableでは`--print target-spec-json`が使えないため、**実際のコード生成で確認した** （2026-07-20時点、rustc 1.97.1）。

| ターゲット | リーフ関数のスタック使用 | red zone |
|---|---|---|
| `x86_64-unknown-none`（kernel） | `subq $64, %rsp`して正のオフセット | **無効** |
| `x86_64-unknown-linux-gnu`（ホスト） | RSPを動かさず`-8(%rsp)`を直接使用 | 有効 |

rustflagsやターゲットを変更した際は、この確認をやり直すこと。

## 6. bootloader→kernel引き渡し（M2-0c）に関する申し送り事項

### 6.1 ExitBootServicesの呼び出し方針

`bootloader/src/loader.rs`は`unsafe { uefi::boot::exit_boot_services(...) }`（uefi-rs組み込みの実装）をそのまま使い、自前でリトライループを実装していない。
理由:

- `uefi::boot::exit_boot_services`は「メモリマップ取得 → `ExitBootServices()`呼び出し」を、間に他のBoot Services呼び出しを一切挟まず一つの関数内で行う。マップキー不整合で失敗した場合は最大2回まで再試行し（Linuxカーネルの実装と同じ方針）、それでも失敗した場合はコールドリセットする。
- **前提**: この安全性は「メモリマップ取得と`ExitBootServices`呼び出しの間に何もアロケーションを挟まない」ことに依存している。そのため`BootInfo`に埋め込むメモリマップは、`exit_boot_services()`が返す`MemoryMapOwned`をそのまま使い、別途`uefi::boot::memory_map()`を自前で呼び直してはいけない（呼び直すと、そのタイミングでアロケーションが発生し、それより前に取得したマップキーが古くなる可能性がある）。この関数は「呼ぶ側が独自にリトライや二重取得をしない」ことを前提に安全性を担保しているため、uefi-rsをアップデートする際は、この呼び出しパターン（取得とexitを分離しない）が変わっていないかを確認すること。
- `MemoryMapOwned`はスコープを抜けると`free_pool`（Boot Services）を呼ぼうとするDrop実装を持つ。ExitBootServices成功後にこれが走ると未定義動作になるため、`bootloader/src/loader.rs`では必要な値を`BootInfo`へコピーした直後に`core::mem::forget`で明示的にリークしている（uefi-rs側にも`are_boot_services_active()`によるガードはあるが、それに依存しない）。

### 6.2 メモリ種別に関するM2-cへの申し送り（重要）

kernel本体・`BootInfo`・メモリマップバッファは、いずれも`MemoryType::LOADER_DATA`としてページ確保される（`bootloader/src/loader.rs`の該当する`allocate_pages`/`exit_boot_services`呼び出しで実際に指定していることをコードで確認済み）。
`LOADER_DATA`は一般に「OSが後で回収してよい領域」として扱われるが、M2-cの物理フレームアロケータが素朴に「`LOADER_DATA`は空き」と判断すると、実行中のkernel自身・受け取った`BootInfo`・メモリマップを空きメモリとして配ってしまう。
症状は即座には現れず、「しばらく動いた後に突然壊れる」という最も診断しにくい形になる。

M2-cのフレームアロケータ実装時、以下の3範囲は必ず予約済み扱いにすること。
kernel側からそれぞれ次の方法で特定できる。

| 範囲 | 特定方法 |
|---|---|
| kernelイメージ本体 | リンカスクリプト（`kernel/link.ld`）が定義する`__kernel_start`/`__kernel_end`シンボル |
| `BootInfo`自身 | `_start`が受け取るポインタ + `common::boot_info::BOOT_INFO_PAGE_COUNT * 4096`バイト |
| メモリマップバッファ | `BootInfo.memory_map.descriptors_ptr` + `descriptors_len` |

bootloader自身が使っていたコード・スタック領域（`EfiLoaderCode`/`EfiLoaderData`の一部）も同様にExitBootServices後はメモリマップ上「使用中」として残る。
kernelがこれを再利用したい場合（bootloaderのメモリ回収）はM2-c以降、必要になった時点で別途設計する。

`EfiBootServicesCode`/`EfiBootServicesData`についても、当面は空きとして扱わない（ADR-0010）。
UEFI仕様上はExitBootServices後に回収してよいとされるが、現時点のkernelはページテーブル・スタック・GDT/IDTをいずれもUEFI由来のまま使い続けており、これらの型を空き扱いすると実行基盤そのものを上書きしうる。
回収を解禁できるのは、自前のページテーブル・自前スタック・自前GDT/IDTがすべて揃った後（M4以降が目安）。

### 6.3 kernelのスタックについて（M4-aで対応済み）

M3までのkernelは、bootloaderが実行していたUEFI由来のスタックをそのまま使い続けていた。
M4-aで自前のスタックへ切り替えた（ADR-0018）。

- 通常実行用64KiBと、ダブルフォルト（IST1）用16KiBを`.bss`の静的配列として確保する。フレームアロケータより前に切り替えられること、kernelイメージの一部として既に予約済み・マップ済みであることが理由。確保の失敗経路が存在しない。
- 切り替えは`_start`の最初期に行う。旧スタックの上に状態を積むほど、切り替え後に「参照してはいけない領域」が増えるため。引き継ぐ値はスタックではなく静的領域（`BOOT_HANDOFF`）経由で渡す。
- 切り替え後、RSPとローカル変数の実アドレスがともに自前スタックの範囲内にあること、旧スタックを参照していないこと、実際に読み書きできることを起動時に検証してログへ出す（CR3切り替えと同じ作法）。
- スタックオーバーフローの検出は、当面**犠牲領域 + 毒値カナリア**で行う（各スタックの直下に4KiB、`0xC5`で充填）。ガードページ化は`deferred-decisions.md`を参照。
- 配置順は`#[repr(C)]`の単一構造体で固定する。静的変数の配置をリンカ任せにすると、たまたま重要なものがスタックの直下に来る。実際、最初の実装ではカーネルスタックの直下がヒープの`ALLOCATOR`と`TSS`になっており、オーバーフローが「検出のための仕組みそのもの」を最初に壊す並びだった（TSSが壊れるとISTが失われ、ダブルフォルトがトリプルフォルトになる）。
- kernelイメージの予約は43ページ → 67ページ（+96 KiB）になった。内訳はスタックブロック88 KiB（犠牲4KiB + 通常64KiB + 犠牲4KiB + IST 16KiB）、TSS・GDT・引き継ぎ領域で176バイト、コードとアラインメントで約7.9 KiB、最後にページ境界へ切り上げ。

### 6.4 M2-dのマッピング範囲の穴について（M4のACPI参照への申し送り）

M2-d (d-1)で構築したマッピング計画には、`EfiConventionalMemory`の内部に見える領域であっても`EfiReservedMemoryType`（type=0）に該当する部分は意図的にマップしていない（`memory_map::classify()`が`Unmapped`と判定するため）。
実機（QEMU + OVMF, RAM 256MiB）では`0xf6ed000..0xf76d000`（512KiB）がこれに該当することを確認済み。

一方、`EfiACPIReclaimMemory` / `EfiACPIMemoryNVS` / `EfiRuntimeServicesCode` / `EfiRuntimeServicesData`は`classify()`により`ReservedButMapped`と判定されるため、現時点では**すべてマップ済み**であることを実機ログで確認している（ACPIテーブル自体を読みに行くコードはまだ存在しないが、仮に読みに行ってもページフォルトにはならない）。

**M4でAPIC構成のためMADT（`EfiACPIReclaimMemory`にあることが多い）を読む場合の注意点:**

- 上記の通りACPI Reclaim/NVS領域自体は現状マップ済みなので、MADTの在り処がこれらの型の範囲内である限り、そのままではページフォルトは起きないはずである。
- ただし、ACPIテーブル（RSDP → XSDT/RSDT → MADT）を辿る過程で参照する物理アドレスが、`EfiReservedMemoryType`やUEFIメモリマップに一切現れない領域（ファームウェア実装依存）を指す可能性がある。その場合は本節の穴と同じ理由（`Unmapped`判定）でページフォルト（`v=0e`）になる。
- 「ACPIを読もうとしたらページフォルト」となった場合は、まず`qemu-debug.log`の`CR2`（フォルトしたアドレス）を確認し、それがUEFIメモリマップ上どの型（またはマップ範囲外）に該当するかを`docs/troubleshooting.md`の要領で切り分けること。対応としては、M2-dのフレームバッファと同様に、判明した範囲を明示的な`extra`範囲としてマッピング計画に追加する形になる見込み。

### 6.5 M4まで割り込みを禁止する（M2-d完了時点の判断）

CR3を自前のページテーブルへ切り替えた（d-2）時点でも、IDT（割り込み記述子テーブル）はまだUEFIがExitBootServices前に設定したものをそのまま使っている。
割り込みが発生すれば、恒等マッピングにより「たまたま到達可能なだけの、自前で検証していない」UEFI由来のハンドラに制御が渡りうる。

実機確認（`kernel::_start`冒頭でRFLAGS.IFを測定）の結果、実際にはExitBootServices後の時点で`IF`はすでに`false`（割り込み無効）だった。
想定していた「有効なまま」という状況ではなかったが、以降も無効であることを構造的に保証しておく価値は変わらない。
ページテーブルの回収予定（ADR-0010で保留した`EfiBootServicesCode`/`Data`の回収）や、今後のメモリレイアウト変更によって、この領域はいつ壊れてもおかしくないため。

**対応**: `kernel::_start`の冒頭（BootInfo検証より前）で`cli`により割り込みを禁止し、M4で自前のIDT・例外ハンドラを導入するまでこの状態を維持する。
切り替え前後の`RFLAGS.IF`はシリアルログに残す（`common::cpu::read_rflags`/`disable_interrupts`）。
M4で自前IDTを用意した後、初めて割り込みを再度有効化する。

**M4で割り込みを有効化する際に見直すべき実装（一覧）**:
- 上記の`cli`（`kernel::_start`冒頭）自体の要否・タイミング。
- ~~`kernel::heap::allocator::Locked<T>`の`unsafe impl Sync`~~ M4-c-2で対応済み。`common::critical::Locked<T>`へ移し、前提を「取得中は割り込み禁止」へ差し替えた（ADR-0012 Addendum）。ガードが`InterruptGuard`を保持する間だけ割り込みを禁止するため、`sti`後も排他が保たれる。二重取得検出も追加した。
- 画面コンソール（M3-c）をグローバル状態で持つ場合、同じ前提への依存がもう1つ増える（ADR-0013）。あわせて、パニック時の画面出力を解禁するかどうかもこの時点で再検討する。

### 6.6 メモリ管理の確定構成（M2完了時点）

M2で実装したメモリ管理の現在の姿。
経緯はADR-0010〜0012を参照。

**物理フレームアロケータ**（`kernel/src/frame_allocator.rs`, ADR-0011）
- データ構造は範囲リスト（`(start_frame, frame_count)`のソート済み・隣接結合済み固定長配列、容量256）。`dealloc`と隣接結合に対応。
- 「空き」と判定するのは`EfiConventionalMemory`のみ。物理アドレス0を含むページは型に関わらず除外する。
- 容量超過は握りつぶさず`CapacityExceeded`としてfail-fast。
- 連続フレームの確保は`allocate_contiguous`。ヒープ本体やフレームバッファ用の大きなバッファはこれを直接使い、ヒープを経由しない。

**ページテーブル**（`kernel/src/paging/`）。**これはM2完了時点のスナップショットである。higher-half移行で恒等マッピングは外れた。現在の確定構成は§6.9を参照。**
- 恒等マッピング。2MiBページを核とし、境界の端数のみ4KiBに分解する。
- フレームバッファとMMIOはPCD（キャッシュ無効）でマップする。Write-Combiningは採用していない。
- 「空き」判定とマッピング対象判定は`memory_map::classify()`の一箇所に集約し、アロケータとページング計画が同じ基準を見るようにしている。アロケータの空き範囲が全てマップ済みであることは実行時に検証する。
- 新規に確保したページテーブル用フレームは必ずゼロ埋めする。NXは立てない。PSビットはPDレベルのみ。
- CR3はM2-d (d-2)で自前のテーブルへ切り替え済み。UEFI由来の旧ページテーブルは回収していない。
- 稼働中のテーブルは起動時にwalkして読み戻し、計画と突き合わせる（M5-a-1、`paging::active`）。エントリのビット操作（2MiBと4KiBで位置が違うPATの移送を含む）は`paging::entry`に分離し、ホストテストで固定している。

**カーネルヒープ**（`kernel/src/heap/`, ADR-0012）
- 起動時に`allocate_contiguous`で1MiB（256フレーム）を一度だけ確保する固定サイズ。拡張機構は持たない。
- 侵入型連結リスト + 隣接結合。配置・分割・結合の判断ロジックは`heap::plan`に分離してホスト`cargo test`で検証し、実ポインタを触る部分だけ`heap::allocator`に閉じ込めている。
- ヘッダにマジック値と要求サイズを持たせ、`dealloc`時に検証する。不一致は二重解放・破壊としてパニックする。解放ブロックは毒値`0xDE`で埋める（`heap-poison` feature、既定有効）。
- 確保失敗時は診断情報をログに出してからnullを返し、既定のalloc error handler経由で既存のパニックハンドラに合流する。

### 6.7 描画系の確定構成（M3完了時点）

M3で実装した描画とコンソールの現在の姿。
経緯はADR-0013 / 0016 / 0017。

**graphics層**（`kernel/src/graphics/`）
- `layout`: bootloaderから渡された形状を検証し、通ったものだけを`FramebufferLayout`として返す。検証項目はピクセル形式、物理アドレスが0でなく4バイト境界にあること、幅と高さが0でないこと、`stride >= width`、`height * stride * 4 <= size_bytes`、桁溢れ。この型が存在すること自体が検証済みの証明になる。
- `color`: `Color`から`Rgb`/`Bgr`に応じた32bit値への変換。生の`u32`をコード中に書かない（形式を取り違えると赤と青が入れ替わる）。
- `framebuffer`: `write_volatile`による書き込み。画面外は無視し、はみ出した矩形は切り詰める。描画経路ではpanicしない。
- `font`: GNU Unifontのグリフ検索。半角8x16 / 全角16x16を区別し、鍵は`char`。未収録はU+FFFDへフォールバックする。
- `text`: 文字列の描画。改行・折り返しは扱わない。

扱うのは`Rgb`/`Bgr`の32bppのみ。
`Bitmask`と`BltOnly`は起動時に拒否する。

**console層**（`kernel/src/console/`）
- `grid`: カーソルと桁送り。全角は行末に1セルしか残っていなければ次行へ送る（半端に描かない）。構築時に桁数 >= 最も広いグリフ幅を検証する。制御文字は`\n` / `\r` / `\t`のみ。`\r`は行頭復帰に加えて行を消去する（厳密な端末挙動からの意図的な逸脱）。
- `dirty`: 未転送範囲を外接矩形1個で追跡し、画面内へ切り詰める。
- `backbuffer`: 通常RAM上の、フレームバッファと同一形状・同一strideの面。転送は行ごとの`copy_nonoverlapping`で行い、直後に`compiler_fence`を置く。一括操作（全面クリア・スクロール・行消去）はスライスの`fill` / `copy_within`を使う。
- `screen`: 上記を束ねた`Console`。`core::fmt::Write`を実装し、`write_fmt`をoverrideして`write!` 1回につき1回だけ転送する。

**描画とフラッシュの流れ**
- 描画はすべてバックバッファ（キャッシュ有効）に対して行う。
- フレームバッファ（PCD、キャッシュ無効）へは変更範囲だけを転送する。
- スクロールはバックバッファ内のメモリコピーで行い、画面全体が変わるためその回だけ全面転送になる。
- 実測（1280x800、起動シーケンス）では、コンソール構築からタイマ開始までに11回のフラッシュで4,402,688バイト。毎回全面転送なら45,056,000バイトなので9%。スクロールが起きる負荷（62行の連続出力）でも37%だった。

**コンソールの位置づけ**
- グローバルに置かず、ロックも持たない。割り込みハンドラから出力する要求はM4で生じるため、そのロック設計は割り込み安全性のモデルと一体で決める。
- シリアルログはコンソールから完全に独立している。`common::log::Logger`に複数の出力先は持たせない。両方へ出す場合は呼び出し側のヘルパで行い、**必ずシリアルを先に**書く。
- コンソールはフレームアロケータと新ページテーブルを必要とするため、起動シーケンスの途中でしか作れない。それより前のログはシリアルにしか出ない（実機のLinuxでprintkのログバッファとコンソールドライバ登録の関係が同じ構造）。画面の先頭に、省略された行数を出して誤解を防ぐ。
- パニック時に画面へは出さない（ADR-0013 Addendum）。

### 6.8 割り込み系の確定構成（M4完了時点）

M4で実装した割り込み基盤の現在の姿。
経緯はADR-0018。

**GDT / TSS / スタック**（`kernel/src/gdt/`, `kernel/src/stack.rs`）
- null / カーネルコード / カーネルデータ / TSS（16バイトなので2枠）の5スロット。ユーザーモード用は未追加（SYSCALLの並び順制約は`deferred-decisions.md`）。
- スタックは`.bss`の静的配列。通常64KiB、ダブルフォルト用IST1が16KiB。各スタックの直下に4KiBの犠牲領域を置き毒値`0xC5`で埋める。配置順は`#[repr(C)]`の単一構造体で固定する。
- 起動時に`sgdt` / `str` / セグメントレジスタを**読み戻して**照合する。

**IDTとスタブ表**（`kernel/src/idt/`）
- 全256ベクタを埋める。割り込みゲート（0xE）・DPL 0。
- スタブ表は2系統ある。例外用256本（`iretq`で戻らない。Ring 3由来の4ベクタだけは畳み=longjmpで遠征の呼び出し元へ制御が戻るが、フォルトした命令へは戻らない。S8）と、IRQスタイル17本（GPRを復元して`iretq`で戻る。0x20-0x2FのPIC IRQと、テスト専用の0x30）。例外をIRQ化してはならない（#DEから戻れば同じ除算命令を再実行して無限ループになる。畳みがこの罠を踏まないのは、戻り先がフォルト地点ではなく遠征の呼び出し元だからである）。**配置検証も2系統**で、片方の検証がもう片方を保証しない。
- `call`直前のRSPが16バイト境界にあることを、スタブが読んだ**実測値**で検証する。導出はADR-0018 Addendum 2。

**クリティカルセクション**（`common/src/critical.rs`）
- `InterruptGuard`はRAIIで`cli`/`sti`を対にし、**保存時にIF=1だった場合のみ**復元する（入れ子で正しく動く）。
- `Locked<T>`は取得中だけ割り込みを禁止する。ガードのフィールド順で「割り込みの復元が必ず最後」を保証し、drop順をホストテストで固定。二重取得は`AtomicBool`で検出し、panicではなくシリアルへ直接出して停止（ヒープのロックで起きた場合にpanic経路が確保を試みると悪化するため）。

**PIC**（`kernel/src/pic.rs`）
- 8259Aを0x20-0x2Fへ再マップ。**ICW2は書き込み専用で読み戻せない**ため、オフセットの正しさは最初のタイマ割り込みがベクタ0x20で届いたことで事後的に証明する（`alt-offset-test`で0x30-0x3Fへの追随も確認済み）。
- IMRは読み戻して照合する。解禁はIRQごとに1箇所へ集約。
- スプリアス（IRQ7 / IRQ15）はISRを読んで判定し、偽にはEOIを送らない。**IRQ15の偽だけはマスタにのみ送る**（マスタはカスケードを本物として受けているため）。

**PIT**（`kernel/src/pit.rs`）
- チャネル0、モード3、100Hz（分周値11932、実周波数99.998Hz）。分周値が整数のため周期は要求値と一致しない。ティック数 × 10msを時刻として使ってはいけない。

**i8042 / キーボード**（`kernel/src/keyboard/`）
- コンフィグバイトを読んで翻訳（セット1）と割り込みが有効かを確認し、必要なら立てて**読み直す**。自己テスト（0xAA / 0xAB）は行わない。
- IRQ1解禁の前に出力バッファをドレインする。
- ハンドラは**バッファが満杯でもデータポートを必ず読む**。溢れたときは新しい方を捨てて数える。データを伴わないIRQ1（コントローラ応答の余波）は`stray`として別に数える。
- 変換（セット1 → 文字）は純粋ロジックでホストテスト対象。

**メインループ**（`kernel/src/interrupts.rs`）
- `sti; hlt`を隣接させたヘルパで**無条件に眠る**。仕事の有無で眠りを決めないので`cli` → 確認 → `sti; hlt`の形は要らない。起こすものが止まると永久ハングになるが、カーネル自身は検出できない（検出コードが動かない）。外側からxtaskがハートビート本数で判定する。
- ハンドラは何も出力しない（ADR-0018 §5）。観測はカウンタ越しに行い、ハートビート1行に集約する。ハートビートには**会計**（`keys + stray`がハンドラ呼び出し回数とIDTのベクタ別カウンタに一致するか）と、**止まった理由の切り分け材料**（i8042のOBF、PICのISR）を含める。
- `sti`の直前にADR-0018 §2の7項目を実行時検証し、1つでも欠ければ`sti`せず停止する。判定は`Verified` / `Failed` / `Unverifiable`の3状態で、確かめる手段が無いものを真に丸めない。

### 6.9 higher-half B完了時点の確定構成（最終アドレスレイアウトとブートフロー、M5）

**§6.1〜6.8はM2〜M4完了時点のスナップショットである。** higher-half移行（A=direct physical map、B=カーネル高位化+恒等除去。ADR-0024がADR-0009をSupersede、ADR-0021とそのAddendum）で、§6.6の「恒等マッピング」を含むいくつかの記述はレイアウトが変わった。ここに現在（B完了時点）の確定構成を置く。過去のスナップショットは時点を明示してそのまま残す（履歴の書き換えはしない）。

**最終アドレスレイアウト（PML4のインデックス割り当て）。** カーネルは上位半分（`0xFFFFFFFF80000000`）で走り、恒等（`PML4[0]`）は外れている。

| PML4 | 仮想ベース | 用途 |
|---|---|---|
| `0` | `0x0` | 空き（B-2bで恒等を外した。M5-f-3でユーザー空間を通常の低位へ広げられる） |
| `1` | `0x0000_0080_0000_0000` | M5-eユーザーページの暫定サブツリー（512GiB。M5-f-3で低位へ移す） |
| `256` | `0xFFFF_8000_0000_0000` | direct physical map（ADR-0021。`phys_to_virt`が返す高位窓） |
| `257..510` | | 空き（SMPのper-CPU用に温存。BKLで使う。ADR-0023/ADR-0024） |
| `511` | `0xFFFF_FFFF_8000_0000` | kernelイメージ（`code-model=kernel`が要求する上位2GiB） |

**ブートフロー（B完了時点）。** エントリは`_start`ではなく`zaytos_trampoline`である（再リンクで`_start`すら低位では走れない。ADR-0021 B Addendum）。

1. bootloaderはkernel ELFを**LMA（`p_paddr`、低位）**へ配置し、`elf.entry_point`（再リンク後は高位VMA）を**LMAへ変換した低位アドレス**へjmpする（ADR-0008「ローダは薄く」を維持。変更はp_paddr配置とエントリのVMA-delta変換だけ）。
2. `zaytos_trampoline`（`.text.trampoline`、絶対即値を持たずRIP相対のみ）が静的初期テーブル（`.data.bootpt`、恒等+高位の`[0,1GiB)`）へCR3を切り替え、静的ブートスタック（`.data.bootstack`、16KiB）へRSPを移し、高位`_start`へjmpする。
3. `_start`（高位）がフレームアロケータ・本流ページテーブル（M2-d/A-1、恒等+高位+direct map）を構築しCR3を切り替える。
4. direct mapを高位窓へ差し替え（A-2）、ヒープを高位化し、各検証サイトを走らせた後、**恒等（`PML4[0]`）を外す（B-2b-4）**。除去は「フレーム会計→落とす→独立walkerで必須領域を検証→CR3リロード（全TLBフラッシュ）→読み戻し」の順で、失敗すればフラッシュ前に書き戻して復帰する。以降カーネルは高位のみで走る。

**M5の確定構成。** マルチタスクはプリエンプティブ（M5-d、タイマからのスケジューリング。コンテキストはRSP1つの保存とIRQ復元経路の再利用。ADR-0019）。ユーザーモードはRing 3への遠征（M5-e、単一アドレス空間のまま）。システムコールは`int 0x80`（M5-f、ゲートDPL=3、第4引数R10、戻り値RAX。ADR-0020）で、ユーザーポインタは実PTEを読んで検証し検証済みトークン`UserSlice`経由でのみ読む（M5-f-2）。プロセス別アドレス空間（下位を差し替え上位を共有）はB完了で解禁された独立マイルストーン（M5-f-3、ADR-0022）。

## 7. 同期・並行性方針（SMP。BKL）

- カーネル内の共有データは**BKL（big kernel lock）**で守る（ADR-0023）。カーネルへの入口で取り、出口で離す。
- **取る入口は列挙してあり、取らない入口は理由つきで並べてある**（`kernel/src/bkl.rs`の`NON_ACQUIRING_ENTRIES`）。取らないのは例外・ダブルフォルト・パニックの3つで、**取れば保持者が例外で死んだときに他コアが永久に待つ**ためである。
- BKLより下位の細かい排他は`Locked<T>`（`common/src/critical.rs`）。中身は割り込み禁止 + 取得フラグ + 保持者の記録で、**競合したら待たずに保持者を出して停止する**（fail-fast。ADR-0004）。
- **BKLを保持したまま`Locked<T>`を取ってよい。逆は作らない。** 向きを固定して循環待ちを構造から消す。
- **BKLを保持したまま眠らない・待たない。** I/O待ちが入る段（`roadmap.md`のS13）で、この前提を明示的に設計し直す。
- TLBの整合は世代方式で取る（ADR-0027）。**順序はBKL自身が与える**ので、シュートダウンのackを待たない。

**この節はS1〜S8で書き換えた。** かつては「シングルコア前提」で、「SMP対応時に中身をスピンロック/アトミックへ差し替えられるよう、呼び出し側インターフェースだけ安定させる」と書いていた。**その差し替えが実際に起きた形である。**

## 8. テスト戦略

- ハードウェア依存部（IDT、ページテーブル、MMIO）と純粋ロジック（スケジューラ判断、アロケータのビット演算、データ構造）を分離する。
- 純粋ロジックはホスト上で`cargo test`により検証する。
- QEMU起動を伴う統合的な確認と、ホスト単体テストを併用し、検証を「QEMU目視」だけに依存させない。
