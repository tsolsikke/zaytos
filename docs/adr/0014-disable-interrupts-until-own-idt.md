# 0014. 自前のIDTを用意するまで割り込みを禁止し続ける

## Status
Superseded by ADR-0018（M4-dで割り込みを有効化した）

## Date
2026-07-20

## Context
M2-dでCR3を自前のページテーブルへ切り替えた時点でも、IDT（割り込み記述子テーブル）はUEFIがExitBootServices前に設定したものがそのまま残っている。
kernelは自前のIDTをまだ持っていない。

この状態で割り込みが発生すると、恒等マッピングによって「たまたま到達可能なだけの、自前では一切検証していない」UEFI由来のハンドラへ制御が渡る。
そのコードが参照するデータ構造は、こちらの都合で上書きされうる領域にある。

さらに、この領域は今後いつ壊れてもおかしくない。
ADR-0010で保留している`EfiBootServicesCode`/`Data`の回収を将来解禁すれば、UEFIのハンドラが乗っている領域はそのまま空きメモリとして配られる。
メモリレイアウトの変更も同じ結果を招く。

実機で`kernel::_start`冒頭のRFLAGS.IFを測定したところ、実際にはExitBootServices後の時点で`IF`はすでに`false`（割り込み無効）だった。
当初想定していた「有効なまま残っている」という状況ではなかった。

## Decision
`kernel::_start`の冒頭（`BootInfo`の検証よりも前）で`cli`を実行して割り込みを禁止し、M4で自前のIDTと例外ハンドラを導入するまでこの状態を維持する。
切り替え前後の`RFLAGS.IF`はシリアルログに残す。

実測の結果すでに無効だったが、`cli`は残す。
「現状たまたま無効である」ことと「構造的に無効であることを保証している」ことは別であり、後者を選ぶ。

## Alternatives Considered
- **実測で無効だったので`cli`を入れない**: 現在のQEMU + OVMFの挙動に依存することになる。ファームウェアのバージョンや構成が変われば、有効なまま渡ってくる可能性は残る。1命令のコストで前提を保証できるなら保証する。却下。
- UEFIのIDTを暫定的に使い続け、必要な割り込みだけ有効化する: 中身を検証していないハンドラに制御を渡す点は変わらない。しかも問題が起きた場合、自前のコードではないため追跡できない。却下。
- **M2の時点で先に自前のIDTを作る**: マイルストーンを1つずつ進める方針に反する。IDTは例外ハンドラ・GDT/TSSと一体で設計すべきもので、メモリ管理の途中で片手間に入れる対象ではない。却下（M4で行う）。

## Consequences
- M4まで、タイマもキーボードも使えない。この間のkernelは起動シーケンスを直線的に実行して停止するだけであり、割り込みを必要としない。
- 「割り込みは常時禁止」という前提に依存した実装が置けるようになった。`kernel::heap::allocator::Locked<T>`の`unsafe impl Sync`がこれに当たる（ADR-0012）。この前提はM4で崩れるため、そのとき見直す実装の一覧を`docs/architecture.md` §6.5に維持する。
- M4で自前のIDTを用意した後、初めて割り込みを再度有効化する。その際は`_start`冒頭の`cli`自体の要否とタイミングも含めて再検討する。
