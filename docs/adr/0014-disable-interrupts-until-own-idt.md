# 0014. 自前の IDT を用意するまで割り込みを禁止し続ける

## Status
Accepted

## Date
2026-07-20

## Context
M2-d で CR3 を自前のページテーブルへ切り替えた時点でも、IDT（割り込み
記述子テーブル）は UEFI が ExitBootServices 前に設定したものがそのまま
残っている。kernel は自前の IDT をまだ持っていない。

この状態で割り込みが発生すると、恒等マッピングによって「たまたま到達可能
なだけの、自前では一切検証していない」UEFI 由来のハンドラへ制御が渡る。
そのコードが参照するデータ構造は、こちらの都合で上書きされうる領域にある。

さらに、この領域は今後いつ壊れてもおかしくない。ADR-0010 で保留している
`EfiBootServicesCode`/`Data` の回収を将来解禁すれば、UEFI のハンドラが
乗っている領域はそのまま空きメモリとして配られる。メモリレイアウトの変更も
同じ結果を招く。

実機で `kernel::_start` 冒頭の RFLAGS.IF を測定したところ、実際には
ExitBootServices 後の時点で `IF` はすでに `false`（割り込み無効）だった。
当初想定していた「有効なまま残っている」という状況ではなかった。

## Decision
`kernel::_start` の冒頭（`BootInfo` の検証よりも前）で `cli` を実行して
割り込みを禁止し、M4 で自前の IDT と例外ハンドラを導入するまでこの状態を
維持する。切り替え前後の `RFLAGS.IF` はシリアルログに残す。

実測の結果すでに無効だったが、`cli` は残す。「現状たまたま無効である」ことと
「構造的に無効であることを保証している」ことは別であり、後者を選ぶ。

## Alternatives Considered
- **実測で無効だったので `cli` を入れない**: 現在の QEMU + OVMF の挙動に
  依存することになる。ファームウェアのバージョンや構成が変われば、有効な
  まま渡ってくる可能性は残る。1 命令のコストで前提を保証できるなら保証する。
  却下。
- **UEFI の IDT を暫定的に使い続け、必要な割り込みだけ有効化する**: 中身を
  検証していないハンドラに制御を渡す点は変わらない。しかも問題が起きた
  場合、自前のコードではないため追跡できない。却下。
- **M2 の時点で先に自前の IDT を作る**: マイルストーンを 1 つずつ進める方針に
  反する。IDT は例外ハンドラ・GDT/TSS と一体で設計すべきもので、メモリ管理の
  途中で片手間に入れる対象ではない。却下（M4 で行う）。

## Consequences
- M4 まで、タイマもキーボードも使えない。この間の kernel は起動シーケンスを
  直線的に実行して停止するだけであり、割り込みを必要としない。
- 「割り込みは常時禁止」という前提に依存した実装が置けるようになった。
  `kernel::heap::allocator::Locked<T>` の `unsafe impl Sync` がこれに当たる
  （ADR-0012）。この前提は M4 で崩れるため、そのとき見直す実装の一覧を
  `docs/architecture.md` §6.5 に維持する。
- M4 で自前の IDT を用意した後、初めて割り込みを再度有効化する。その際は
  `_start` 冒頭の `cli` 自体の要否とタイミングも含めて再検討する。
