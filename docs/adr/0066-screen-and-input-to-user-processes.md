# 0066. 画面と入力をユーザープロセスへ渡す——Wayland のための最後の基盤

## Status

Accepted（設計。2026-09-20。運用者が Q1〜Q5・刻み・大きさの一度決めを承認）。
実装は刻みごとにレビューを受ける（`Y-a`→`Y-b`→`Y-c`→`Y-d`）。

## Date

2026-09-20

## Context

第1段階（IPC の基盤）の残りは「画面と入力をユーザープロセスへ渡す経路」である。
`docs/wayland-inventory.md` の実測に拠る——**カーネルが出すのは通信・記憶・装置だけで、
メッセージ解釈・窓管理・合成は Seinas（ユーザー空間）である。** この段でカーネルが
足すのは3つ。

- 画面へ画素を出す口（今は文字コンソールしか無い。`syscall.rs` に `framebuffer` 0 件）
- 入力の生イベントを受ける口（今の `read(0)` は前景シェルへ復号済みバイトを渡すだけ）
- 2つの理由を同時に待つ形（Seinas は入力とソケットの両方を待つ。仕様は poll を要求しない）

現在地（実測。2026-09-20）——フレームバッファは GOP の現行モードのまま
1280x800・Bgr・4,096,000バイト（FHDではない）、MMIO を direct-map 窓へ再配置済み。
コンソールは同形の裏バッファ（1000フレーム）へ描き dirty矩形だけ MMIO へ流す。
`RING3_SLOTS`=2、`Wait` は8種で1タスク1理由・完全一致で起こす。遠征スタック
64KiB×深さ2、高水位 31,864/65,536（残り904）。`MAX_SHM`=2 / `MAX_SHM_PAGES`=8。
窓 4MiB（`0x400000..0x800000`）。

## Decision

### Q1 画面へ画素を出す口——コンソールの裏バッファを再利用する

前景プロセスが「図形モード」を要求したら、裏バッファ（フレームバッファと同形。既に
起動時に確保済み）を `PTE_SHARED` で高位VA（`mmap` の 0x1000_0000 と同じ流儀。窓の外）へ
共有マップし、プロセスが画素を書く。`present(x,y,w,h)` が dirty矩形を立ててコンソールの
流しに載せ、MMIO への書き込みはカーネルが持つ。図形モードの間は文字コンソールを退ける。

- 裏バッファはカーネルが持つ（`shm` の上ではない）。マップは `PTE_SHARED` と `destroy` の
  印スキップ（`ADR-0065`）を再利用するが、参照数/解放は使わない（カーネル常駐）。
- `present` は写す（dirty矩形を裏バッファから MMIO へ blit）。切り替えではない。
- **FHD が shm の上限と無関係になる機序**——画面面は shm オブジェクトではなくカーネルの
  装置バッファなので `MAX_SHM_PAGES`（8=32KiB）に縛られない。FHD 化は裏バッファの確保
  （1000→2025フレーム）とページ表の項が増えるだけで、両方とも素直に伸びる。

### Q2 入力の生イベントを受ける口——入力 fd を別に足す。`read(0)` はそのまま

図形プロセスが「入力」fd を開き、生キーイベントを読む。源は今の `SCANCODES`輪で、
端末の復号器（`input::read_bytes`）は文字コンソール用に残す。`read(0)`（端末・復号済み・
行規律）は変えない。モード依存の `read(0)` にはしない（別fdが明快）。

- 前景の関所は開く時点の1箇所で構造的に守る（下の「入力 fd の前景の関所」）。
- 持ち越し行250（キーボード入力をどのタスクが受け取るか）をここで閉じる——Seinas が
  前景の図形プロセスとして入力を持ち、クライアントは入力を claim しない（Wayland では
  クライアントの入力は Seinas から転送される）。

#### 入力イベントの配置は Linux の `struct input_event` に合わせる（`ADR-0020`）

`docs/architecture.md` の「ABIの形は合わせる」に従う。Linux の evdev が
`/dev/input/eventX` から読ませる構造体をそのまま採る（24バイト、`repr(C)`）。

| 欄 | 型 | 意味 |
|---|---|---|
| `tv_sec` | `u64` | 単調時刻の秒（`clock_gettime` の源と同じ） |
| `tv_usec` | `u64` | 同マイクロ秒 |
| `type` | `u16` | `EV_KEY`(1) だけ（v1） |
| `code` | `u16` | キーコード（v1 は set-1 スキャンコード。下の限界） |
| `value` | `i32` | 0=離脱 / 1=押下 / 2=リピート（v1 は 0/1 だけ） |

**配置を `cc` の `offsetof` で突き合わせた**（2026-09-20。`cc` 13.3.0。`<linux/input.h>`）——
**`sizeof` 24、`time` は位置 0 で 16 バイト（`tv_sec` 8＋`tv_usec` 8）、`type` は 16、`code` は
18、`value` は 20、`EV_KEY` は 1。すべて `read_events` の書き方と一致した。** **`timespec` の
ときと同じ手である**（`ADR-0062`）。

**合わせられない所が 1 つ**——**Linux の `time` は `struct timeval`（設定可能な時計。既定は
`CLOCK_REALTIME`）だが、ZaytOS には単調時計しか無い**（W2-d+。`ADR-0062`）。**だから配置は
合うが、`time` の値は単調時刻である**（壁時計ではない）。**`docs/architecture.md` の「合わせ
られる形について適用する」に当たる**——**形（16 バイトの秒＋マイクロ秒）は合わせ、意味
（どの時計か）は ZaytOS の持つものにする。**

**v1 の限界**——`code` は set-1 のスキャンコードで、Linux の evdev コード（`KEY_*`）へは
訳さない。Wayland は `no_keymap`(0)（クライアントが生キーコードを解釈）を選べるので、
カーネルはスキャンコードを渡すだけでよい。evdev コードへの変換は Seinas（または libinput
相当）の段。契機：本番のクライアントが `KEY_*` を要るとき。

### Q3 2つの理由を同時に待つ——`Wait` を集合にする

`TaskState::Waiting(Wait)` を `Waiting(WaitSet)`（小さな固定長の集合）にし、
`wake_tasks_waiting_on(on)` の一致を `state == Waiting(on)` から「`on ∈ 集合S`」へ変える。

- 起こす側は理由を運ばない。起こされた側が集合の各理由を非ブロッキングで問い合わせ直す
  （今も「空振りは許す・起きて確かめ直す」形。`WOKEN_FOR_ANOTHER_REASON` と「woke with
  nothing」がそれを数えている）。多重待ちの syscall は戻るとき読める部分集合を返す。
- `WOKEN_FOR_ANOTHER_REASON` の不変条件は保たれる——検出器を「`on ∉ S` の者を起こした
  回数」と言い換える。本番では構造で 0（所属判定が起こす条件そのもの）。
- 破壊 `wake-ignores-the-reason`（理由を見ず全部起こす）は集合の下でも落ちる——`on ∉ S` の
  者まで起こすので `WOKEN_FOR_ANOTHER_REASON` が >0 になり、振る舞いでも落ちる。
- 一般の `poll`（`events`/`revents`/`timeout`）は作らない（仕様が要求しない）。最小の
  「このfd集合のどれかが読めるまで待つ」で足りる。

### Q4 大きさ——広げるのは遠征スタックだけ、それも測ってから

`Y-a`/`Y-b` の口の高水位を先に測り、半分（32,768）を越えるなら 64KiB→96KiB へ一度で
上げる（`.bss`）。または大きな写しを深い枠の外へ出す（`ADR-0063` の口3つと同じ手）。
スロット2・接続2・窓4MiB・`MAX_SHM_PAGES`8 は v1 では据え置く（画面面もクライアント
プールも高位VA＝窓の外。契機は本番の Seinas の段。行297/298）。**広げるなら一度に**
（参照が全部動くので、分けると `--full` を何度も回す）。

### Q5 最初の利用者——`ADR-0064` の例外を指す

Seinas はまだ無い。ソケットのときと同じ——feature で囲った検査の組（画面サーバ／
クライアント）がカーネルの口を駆動し、コンポジタの都合から切り離す（`ADR-0064`）。
Seinas が来ても残す（`sockd`/`sockc` を残したのと同じ）。

## 刻み（Y-a→Y-b→Y-c→Y-d。各段で単独に検査できる）

- **Y-a** 入力を fd にする（`File::Input`、`struct input_event` の読み口、`Wait::Keyboard`
  で1つのfdを待つ）。検査：前景プロセスが入力fdを開き、打鍵で起きて生イベントを読む。
- **Y-b** `Wait` を集合にする（多重待ち。{入力fd, ソケット} を待つ）。
- **Y-c** 画面出力（裏バッファを共有マップ＋`present`）。
- **Y-d** テストの組（画面サーバ＋クライアント）で全体を検証。

**「入力を fd にする」を「集合にする」より前に置く**——入力もソケットも fd で扱え、多重
待ちのインタフェースが揃う。`Y-a` は集合なしで単独に検査できる（切り分けのため分ける）。
ただし内部の `Wait` の種類（8種）は減らない（入力fdも内部では `Wait::Keyboard` に対応
づく）。enum の統合（`Readable{fd}`）は別の段の候補。

### 入力 fd の前景の関所は構造で守る（足す1点）

列挙（`read(0)` と入力fdの2箇所で `foreground_is_claimed` を見る）ではなく、構造で守る。

- **開く時点で前景を要求する**（1箇所）——`open_input` は前景が取られていなければ
  `-EBADF`。前景は S11-10 以来プログラムの走行の間ずっと持たれる（`run_loaded_program`
  が入口で取り出口で返す）ので、fd が前景より長生きしない。
- **fd は渡せない**——`sendmsg` の `SCM_RIGHTS` は shm の fd だけを運ぶ（`ADR-0065`）ので、
  `File::Input` は相手の表へ写らない。開いた前景の持ち主に留まる。
- したがって毎回の `read` で前景を見る必要は無い。**将来 前景の譲渡を入れる段では、ここを
  読み直す**（行250 の残り）。
- **Y-c で直した（2026-09-21）**——**実装は「誰かが前景を持っているか」（大域の印）を見ていて、
  起こしっぱなしの 1 本でも開けた。** **いまは「呼んだ者が前景の系統か」を見る**（下の Y-c の節の
  「前景の関所の穴を見つけて直した」）。

### 番号（`ADR-0020`）

- 入力fdを開く口——Linux に対応する syscall が無い（Linux は `/dev/input` を `open`）。
  `ZAYTOS_PRIVATE_BASE + N` を採る（`SYS_SPAWN` 等と同じ）。
- 入力fdの読みは `read`(0) を使う（`sys_read` が `File` の中身で分岐する）。
- `present` と多重待ちは `Y-b`/`Y-c` で番号を決める（多重待ちは Linux の `poll`(7) の
  最小の部分集合を検討する）。

## 動いてよいもの（定型4形。実装前に書く。測るのは建ててから）

1. **ページ表の項**——像は伸びる（核・口・テストの組）。4KiB の境を越えれば +1（U/S監査で
   測る）。図形モードの画面面（1000ページ）のマップは図形モードの間だけで、既定の起動に
   出ない。
2. **遠征スタックの高水位**——動く見込み。残り904バイトしかないので、大きな写し
   （`struct input_event` の配列・画素）は `dispatch` の枠ではなく別関数か静的に置く
   （`ADR-0063` の口3つと同じ手。深い枠 `load_user_program`/`run_loaded_program` は
   12,056バイトを食う——その外へ出す）。半分を越えるなら 64KiB→96KiB へ一度で。
3. **静的の置き場**——`WaitSet` はタスクの構造体（`.bss`）。入力fdの `File` 種別と計器は
   既存の表と `.bss`。画面面はカーネルが既に持つ裏バッファの再利用なので新規確保は無い。
4. **既定の起動ログ**——番地の行が動く。テストの組は feature で囲うので既定に出ない。
   syscall 数が増える（入力fdを開く番号ほか）。行数は据え置きの見込み。

## 判定ごとに破壊を1本置いた（Y-a。運用者の指摘。2026-09-21）

**最初は判定2本に破壊1本だった**——**判定1（押下のイベントが届いた）に固有の破壊が無かった。**
**自分で立てた規律に反している**（**判定を足すときは、その場で落とす破壊が在るかを確かめる。
無ければ「無い」と書く**）。**W1-c-4 で同じ指摘を受けて置いてみたら両方とも置けた前例が在るので、
ここでも試した。**

| 破壊 | すること | 落ちる判定 |
|---|---|---|
| `input-read-never-waits` | `read` が空でも待たず `-EAGAIN` | 判定2（`read` が待った） |
| `input-events-mistake-the-code` | キーコードを +1 する | 判定1（押下のイベントが届いた） |
| `input-events-zero-the-time` | 時刻のティックを 0 と読む | 判定3（時刻が入っている） |
| `foreground-ignores-the-slot` | 関所が大域の印だけを見る（Y-a の元の形） | 判定4（前景でない者は開けない） |

**判定4と4本目は Y-c で足した**（運用者の足す1点。2026-09-21）——**Y-a の検査は前景のプロセスが開けることだけを
見ていて、関所で断られる側を判定にしていなかった。** **だから関所が大域の印を見ている穴が、Y-a の検査では
見えなかった**（Y-c の節の「前景の関所の穴を見つけて直した」）。**`inputd` は最初に自分をスロット 1 へ `probe` の
引数で起こしっぱなしにし、その 1 本の `open_input` が `-EBADF` で断られることを見る**——**Y-a の単独の検査で
完結する。** **3 回とも、落ちたのは判定4だけだった**（実測）。**`screen-test` も同じ破壊を回す**（画面の関所を
見る判定3と、入力の関所を見る判定4）。

**判定3（時刻が入っている）は、この指摘で足した。** **`struct input_event` の `tv_sec`/`tv_usec` は
Linux の配置に合わせた欄なのに、どの判定も見ていなかった**——**ABI が約束している欄に覆いが
無い状態だった。** **`inputd` が時刻も印字し、判定は「両方 0 でないこと」だけを見る**
（**起動から何秒目かは負荷で揺れるので、秒の下限は主張しない**）。

**落ちる判定を 1 本ずつに分けた**——**時刻を読む行は `code=` に依らない形で拾う**
（`inputd: event ` と `value=1` で拾う）。**そうしないと、キーコードを取り違える破壊が
判定1と判定3の両方を落とし、どちらの欠陥かが判定から読めない。**

### 置けなかった破壊——「離脱を押下と読む」

**`value` を反転する破壊は置けない。** **機序**——**離鍵のスキャンコード（`a` なら `0x9E`）は
`& 0x7F` で `30` になるので、反転すると離鍵のイベントが `code=30 value=1` として出る。**
**判定1はその字面を見ているので通ってしまい、`inputd` も `value=1` を見て「押下」として
終わる。** **捕まえるには「押下が離脱より先に来る」順序か、離脱のイベント自体を主張する
判定が要る**——**どちらも今は無い。** **契機：離脱のイベントを使う段**（`wl_keyboard` は
押下と離脱の両方を送るので、本番の Seinas が要る）。

## Y-b の実装（2026-09-21）——`Wait` を集合にし、`poll` を最小の部分集合で入れた

### 番号は `poll`(7)、配置は `struct pollfd`（`ADR-0020`）

**独自番号にしなかった**——**Linux に対応する口が在る**（入力 fd を開く口は無かったので
`ZAYTOS_PRIVATE_BASE + 8` を採った。上の「番号」）。**`struct pollfd` は `fd` 4＋`events` 2＋
`revents` 2 の 8 バイトで、そのまま採った。**

**Q3 の「一般の `poll` は作らない」は、意味の側の決定として守った**——**作ったのは配置と番号で、
見るのは `POLLIN` だけ、`timeout` は -1（無限）と 0（待たない）だけである。** **それ以外は
`-EINVAL` で断る**——**黙って無視すると、書ける待ちを頼んだ側が読める待ちで眠る。**

### 集合の大きさは 4 である（測ってから決めた）

**設計の見込みは 8 だった。** **2 つの実測で 4 に決めた。**

1. **v1 で塞がりうる理由の本数**——**入力 1（キーボードは 1 つで添字を持たない）＋ listener 1
   （`MAX_LISTENERS`）＋ 接続 2（`MAX_CONNECTIONS`）＝ 4。** **`poll` に渡せる fd の上限も
   同じ値にした**（`MAX_POLL_FDS`。**集合に入らない数を受けても待てない**）。
2. **写しの費用**——**`TaskState` は `Copy` で、`scheduler::states()` が `[TaskState; TASK_COUNT]`
   を値で返す**（`schedule_switch` の枠に乗る）。**実測（`size_of`。2026-09-21）——`Wait` 16 バイト、
   配列は 96（いまの 1 理由）、432（4 本）、816（8 本）。** **遠征スタックの残りは 904 バイトなので、
   8 本は入らない。**

**ホストテストで留めた**——**`the_state_array_stays_small_enough_for_the_switch_frame` が
`[TaskState; TASK_COUNT] <= 432` を主張する。** **理由を増やすと、そこで先に落ちる。**

### 不変条件の言い換えを実装で確かめた

**`wake_tasks_waiting_on` の突き合わせを、完全一致から所属（`on ∈ S`）へ変えた。** **所属判定は
`waits_on` の 1 箇所に集めた**——**起こす側と「待っている者が居るか」（`someone_waits_on`）の
両方がそこを通る。** **2 箇所で書くと、片方だけが集合の意味からずれる。**

**`WOKEN_FOR_ANOTHER_REASON` は「`on ∉ S` の者を起こした回数」になった。** **本番では構造で 0
である**——**所属判定が起こす条件そのものだからである。** **実測で 0（`poll-test` の判定 5）。**

**`wake-ignores-the-reason`（W2-d+ の破壊）を、この検査でも回す。** **待ち 3 の間、`polld` は
{入力, 接続}、`pollc` は接続だけを待っている**——**打鍵で `pollc` まで起こすと `on ∉ S` が
1 以上になる。** **空振りの起床は無害なので走行は終わり、落ちるのは判定 5 だけである。**

### 検査の形（`poll-test`。単独で回せる）

**`init` が `/bin/polld` を前景で 1 度起こす**（`input-test` と同じ形。シェルは起こさない）。
**`polld` が自分で `/bin/pollc` を起こしっぱなしで起こす**——**Ring 3 のスロットは 2 で、
`a | b` と同じ形である。** **同じ集合で 3 回待ち、起きる理由が入れ替わる。**

| 待ち | 集合 | 起こすもの |
|---|---|---|
| 1 | {入力, listener} | `pollc` の `connect`（listener が読める） |
| 2 | {入力, 接続} | `pollc` の返し（接続が読める） |
| 3 | {入力, 接続} | 本物の打鍵（`sendkey a`） |

**判定は 6 本**——**3 回とも起きた理由が合っていること／`poll` が待ったこと／集合の外の者を
起こしていないこと／集合に 2 本入ったこと。** **打鍵は待ち 2 が終わってから送る**——**先に
送ると、待ち 1 と 2 が入力でも起きてしまい、どちらで起きたかが混ざる。**

### 破壊は 4 本。3 回ずつ落ちた（実測。2026-09-21）

| 破壊 | すること | 落ちた判定 |
|---|---|---|
| `poll-never-waits` | 読める者が居なくても待たず 0 を返す | 判定 4（待った）と判定 6（集合に 2 本） |
| `poll-mistakes-the-member` | `revents` を隣の欄へ付ける | 判定 1・2・3（どちらで起きたか） |
| `poll-waits-on-one-member` | 集合へ最初の 1 本だけを入れる | 判定 2・3・4・5・6 |
| `wake-ignores-the-reason` | 合図を見ず、待っている者を全部起こす | 判定 5 だけ |

**`wake-ignores-the-reason` は判定 5 だけを落とした**（実測。3 回とも他の 5 本は真）——**集合の
下でも、言い換えた不変条件が欠陥を捕まえる。** **空振りの起床は無害なので、`polld` も `pollc` も
終わる。**

**`poll-never-waits` は判定 6 も落とす**——**集合を組むのは待つ直前なので、待たない形では集合が
記録されない**（最大は 1 のまま。他の 1 理由の待ちが記録した値である）。**隔離できていないが、
これは機序どおりである**——**「待たない」と「集合を使った」は同じ場所で決まる。**

**`poll-waits-on-one-member` は 5 本落とす**——**落ちた合図では誰も起こさないので `polld` が
待ち 2 から戻らない。** **戻らないと計器の行が出ないので、判定 4・5・6 は `None` で落ちる**
（実測で待ち時間 128.5 秒。上限で切って判定した）。**待ち 1 だけは真のまま**——**`pollc` の
`connect` が `polld` の最初の覗きより前に着けば、待たずに戻るからである**（**判定 4 を「1 以上」
にした根拠もこれである**）。

### 測って分かったこと——EOF は「読める」である

**最初は `pollc` が返してすぐ終わっていた。** **待ち 3 が `ready=socket` で戻った**——**相手が
閉じた接続は EOF で「読める」からである**（`read` が 0 を返して終わるので、待たせてはいけない）。
**`pollc` を 2 度目の `read` で居残らせ、閉じるのは `polld` の側にした。** 詳しくは
`docs/troubleshooting.md` の 2026-09-21 の項に在る。

### 実測（2026-09-21）

- **遠征スタックの最大の高水位は 31,864 / 65,536（48%）で不変**——**`syscall-test` の載せ替えの
  経路である。** **`polld` は 14,994（22%）、`pollc` は 6,368（9%）。** **`poll` の口は
  `#[inline(never)]` で、`struct pollfd` の写し（32 バイト）は `dispatch` の枠に乗らない。**
  **96 KiB へ上げる必要は無かった**（Q4 の契機は発火していない）。
- **`poll` が待った回数 2、集合に入った理由の最大 2、`on ∉ S` の起こし 0。**

### v1 の限界——「合わせられない」と「合わせなかった」を書き分ける（運用者の指摘。2026-09-21）

**`docs/architecture.md` の「合わせられる形について適用する」は、書き分けないと「面倒なものは
合わせない」と読めるようになる。** **だから限界ごとに、どちらなのかを書く。**

**合わせられないもの**——**ZaytOS が持っていないものが在って、形を採っても値が別物になる。**

- **`struct input_event` の `time`**（Y-a）——**Linux は設定可能な時計（既定は `CLOCK_REALTIME`）
  だが、ZaytOS には単調時計しか無い**（`ADR-0062`）。**配置は合わせ、値は単調時刻である。**

**合わせなかったもの**——**持てるが、v1 では持っていない。** **理由と契機を添える。**

- **`events` は `POLLIN` だけ**（`POLLOUT` などは `-EINVAL`）。**理由**——**`revents` に立てる
  フラグを `POLLIN` 以外に増やさないため。** **黙って無視しないのも決めである**——**無視すると、
  書ける待ちを頼んだ側が読める待ちで眠る。** **契機：書ける待ちが要るとき。**
- **`timeout` は -1 と 0 だけ**（正の値は `-EINVAL`）。**理由**——**締切つきの待ちを要る利用者が
  まだ居ないため。** **持てる**——**集合に `Wait::Timer` を入れれば足りる**（**集合にしたので、
  その形は素直に入る**）。**契機：締切つきの待ちが要るとき。**
- **開いていない fd は `-EBADF`**（Linux は `revents` に `POLLNVAL` を立て、その 1 件だけを
  失敗にする）。**理由**——**上と同じで、`revents` のフラグを `POLLIN` 以外に増やさないため。**
  **fd の間違いは呼ぶ側の誤りなので、1 件ずつ報せる形が要らない。** **契機：混ざった集合を渡す
  利用者が出たとき。**
- **待てるのは入力 fd・接続・listener の 3 種だけ**（パイプと端末は `-EBADF`）。**理由**——
  **対応づけを増やすと、判定と破壊もその数だけ増えるため。** **持てる**——**パイプは
  `Wait::PipeReadable`、端末は `Wait::Keyboard` に対応づく**（どちらも既に在る）。**契機：パイプか
  端末を待つプログラムが出たとき。**

**どちらでもないもの**——**`Wait` の種類（8 種）は減らない。** **入力 fd は内部では
`Wait::Keyboard` に対応づく**（刻みの注のとおり）。**Linux に合わせる話ではなく、こちらの内部の
形である。**

## Y-c の実装（2026-09-21）——裏バッファを張り、`present` で写す

### 口の形——「合わせた」「合わせられない」「合わせなかった」「どちらでもない」

**Y-b の書き分けと同じ形で書く**（`docs/architecture.md` の「合わせられる形について適用する」）。

**合わせた**——**配置は `cc` の `offsetof` で測った**（2026-09-21。`cc` 13.3.0。`<linux/fb.h>` と
`<drm/drm.h>`）。**ホストテストが欄の位置を留めている**（`syscall::tests`）。

- **画面の形は fbdev の `ioctl` で訊く**——`FBIOGET_VSCREENINFO`（0x4600。`struct fb_var_screeninfo`
  160 バイト。`xres` 0 / `yres` 4 / `bits_per_pixel` 24 / `red` 32 / `green` 44 / `blue` 56）と
  `FBIOGET_FSCREENINFO`（0x4602。`struct fb_fix_screeninfo` 80 バイト。`smem_len` 24 / `line_length` 48）。
- **画素は `mmap(fd)` で張る**（`mmap` の 9 番を画面の fd へ広げた）。
- **`present` の矩形は `struct drm_clip_rect`**（8 バイト。`u16` の x1 0 / y1 2 / x2 4 / y2 6。半開区間）。

**合わせられないもの**——**Linux は `/dev/fb0` を `open` するが、ZaytOS に装置のファイルシステムは
無い。** **開く口は独自番号にした**（`SYS_OPEN_SCREEN` = `ZAYTOS_PRIVATE_BASE + 9`。入力 fd の `+8` と
同じ理由）。

**合わせなかったもの**（理由と契機つき）

- **`smem_start`（物理番地）は 0 を返す。** **理由**——**Ring 3 へ物理番地を出す理由が無い**
  （`mmap` は fd から張るので番地を知らなくてよい）。**契機：番地を要る利用者が出たとき。**
- **画面の fd の `read` は `-EINVAL`**（fbdev は画素を返す）。**理由**——**画素は `mmap` で読めるので、
  2 つ目の道を持たない。** **契機：`read` で画面を取る道具が要るとき。**

**どちらでもないもの**——**`present` そのもの**（`FBIOZPRESENT` = 0x5A03。`TIOCZTAKE` と同じ `'Z'` の帯）。
**fbdev は実物のフレームバッファを張るので写す口を持たない。** **ZaytOS が写す口を要るのは、Q1 で
「MMIO を Ring 3 へ出さず、裏バッファを張る」と決めたからで、こちらの内部の設計である。** **Linux で
近いのは DRM の `DRM_IOCTL_MODE_DIRTYFB` で、矩形の配置だけを採った。**

### 仕組み

- **図形モードは静的の印 1 つ**（`console::GRAPHICS_ACTIVE`。持ち主は 1 つで、2 人目は `-EBUSY`）。
  **入るのは `open_screen`、抜けるのは画面の fd の解放**（`close` か、プロセスの終わりの表の解放。
  **`close` を忘れて落ちたプログラムでも戻る**）。
- **字の経路は入口の 2 つで止める**——`write_foreground_bytes` と `flush_foreground`。**コンソールが
  裏バッファへ描く口は多い**（字・スクロール・消去・カーソル）**ので、1 つずつ塞がずに入口で分けた。**
- **抜けたら、次の流しでセルから描き直す**（`Console::request_repaint`。**描き直しは代替画面の戻りで
  使っている `repaint_from_cells` の再利用**）。**抜ける場所（fd の解放）は BKL を持っているので、
  重い描き直しは BKL を解いて呼ばれる流しまで延ばした。**
- **`present` はカーソルを描かずに矩形を写す**（`Console::present`。**`flush` は送る前にカーソルを描く**
  ——**図形モードでそれをすると、画素の上に下線が乗る**）。**BKL を解いて写す**（全面なら 5.05M サイクル）。
- **張り方は共有メモリと同じ**——**葉に `PTE_SHARED` の印を立て、`destroy` が集めない**（`ADR-0065` の
  印スキップの再利用）。**裏バッファのフレームはコンソールの持ち物で、返さない**（参照数は使わない）。

### 前景の関所の穴を見つけて直した（Y-a の直し）

**下調べで、`input::foreground_is_claimed()` が大域の印だと分かった**——**「誰かが前景を持っているか」
であって「呼んだ者が持っているか」ではない。** **Y-a の `open_input` はこれを見ていたので、起こしっぱなしの
1 本（スロット 1）でも、親が前景を持っていれば入力の fd を開けた。** **上の「入力 fd の前景の関所」は
「開く時点で前景を要求する」と書いていた——実装はそれより弱かった。**

**直し方**——**「呼んだ者が前景の系統か」を 1 つ置いた**（`input::caller_is_foreground`。**取られていて、
呼んだ者がスロット 0**。前景を取れるのはスロット 0 の系統だけで、`claim_foreground` がスロット 1 を断る）。
**`open_screen` と `open_input` の両方がこれを見る。** **検査の組の `gfxc`（スロット 1）が、画面も入力も
`-EBADF` で断られることを判定にした。**

**直していないもの**——**端末の `read(0)` は大域の印のまま**（持ち越しの行に書いた。**直すと、パイプの左の
子が端末を読んだときの振る舞いが変わる**）。**割り込みの側（`drain_keyboard`）が大域の印を見るのは正しい**
——**問いが「Ring 3 の誰かが持っているか」だからである。**

### 検査の形（`screen-test`。単独で回せる）

**`init` が `/bin/gfxd` を前景で 1 度起こす**（`input-test` と同じ形）。**`gfxd` は `/bin/gfxc` を
起こしっぱなしで起こして終わるまで待ち**（**図形モードへ入る前に見る**——入った後だと `-EBUSY` で断られ、
関所を見たことにならない）、**画面を開き、形を訊き、裏バッファを `mmap` して 160×160 の四角をマゼンタで
塗り、その矩形を `present` で写し、打鍵を待つ。** **`xtask` がその間に `screendump` で画面を読み戻し、打鍵を
送り、`gfxd` が画面の fd を閉じた後にもう 1 度読み戻す。** **マゼンタ（赤と青 0xFF、緑 0）は `Rgb` でも
`Bgr` でも同じ値になるので、判定が並びの読み違いに引きずられない。**

**判定は 4 本**——**書いた画素が MMIO に届いた**（写した直後、四角の 25,600 画素が全部マゼンタ）／**文字
コンソールが戻った**（抜けた後、四角にマゼンタが 0 画素）／**前景でない者は画面を開けない**／**前景でない者は
入力の fd を開けない。** **読み戻しは外の道具である**——**カーネルの言い分ではなく、画面の実物を読む。**

### 破壊は 3 本。3 回ずつ落ちた（実測。2026-09-21）

| 破壊 | すること | 落ちた判定 | 実測 |
|---|---|---|---|
| `screen-present-does-not-copy` | `present` が写さない | 判定 1 だけ | 写した直後もマゼンタ 0 |
| `screen-leave-does-not-repaint` | 抜けても描き直さない | 判定 2 だけ | 抜けた後もマゼンタ 23,040（戻った字の 1 行ぶん 2,560 だけ減った） |
| `foreground-ignores-the-slot` | 関所が大域の印だけを見る（Y-a までの形） | 判定 3・4 | `gfxc` が画面も入力も開けた |

**3 本目は 2 本の判定を落とす**——**関所は `open_screen` と `open_input` が共有する 1 つなので、機序どおり
である。**

### 実測（2026-09-21）

- **四角の画素**——写した直後 25,600 / 25,600、抜けた後 0。**張ったページ 1,000**（裏バッファ 4,096,000
  バイト = 1,000 フレーム）。**図形モードへ入った 1 回・抜けた 1 回・`present` 1 回。**
- **遠征スタックの最大は `syscall-test` の 31,864 / 65,536（48%）で不変。** **`gfxd` は 14,994（22%）、
  `gfxc` は 4,520（6%）。** **`ioctl` と `mmap` の口は `#[inline(never)]` で、160 バイトの構造体は
  `dispatch` の枠に乗らない。** **96 KiB へ上げる必要は無かった。**
- **器が 1 つ動いた——像が太ると動く器（定型の 5 形目）。** **起動時の ext2 の自己検査の器
  （`CORRUPT_FS_BLOCKS`）は 288 ブロックの定数だった。** **像へ `gfxd` と `gfxc` を足し、使用上端が
  284 から 293 へ上がって器を越え、既定の起動がその診断で止まった**（実測。**見込んだのは「新規の
  確保は無い」までで、像が太ることで動く器を数えていなかった**）。**1 度 320 へ上げて提示したが、
  運用者の指摘で導出する形へ直した**——**`build.rs` が像の使用上端を測って `USED_BLOCKS` に出し、器は
  `USED_BLOCKS + 16` になる**（いまは 293 + 16 = 309）。**像が太れば器も同じだけ伸びる。** **余裕の 16 は
  実測から決めた**——**persist の 3 項目の 6 回の起動で、起動時に読んだ像は建てた像より最大 +4**（前の起動が
  書いたぶん）、**構成による揺れは +1。** **使っている量と器の大きさは、毎起動の締めの行に出るように
  した**（`copy of the 293 block(s) the image uses, in a 309-block buffer`）。**規約の定型に 5 つ目として
  足した**（`docs/coding-standards.md`）。
- **ページ表の項**——**U/S 監査の kernel entries が 4,264 から 4,288（+24）。** **像の終わりが 0x486890 から
  0x49e8b0 へ +96 KiB 伸びた分である**（うち 84 KiB が器の +21 ブロック。**器を 320 の定数にしていたときは
  +35 だった**）。**ページ表のフレームは 4 のまま。** **画面の面の 1,000 ページは図形モードの間だけ張り、
  既定の起動には出ない。**
- **既定の起動ログ**——**96 行が動いた**（番地、fs の像の checksum 0x00078731→0x0007869a、器の締めの行
  「293 block(s) the image uses, in a 309-block buffer」）。**`gfxd`・`gfxc`・`screen`・`inputd probe` の行は
  既定の参照に 0 件。**

### v1 の限界（契機つき）

- **図形モードの間に書かれた字は、戻った画面に残らない**（シリアルには残る）。**セルにも置かない形に
  した**——**置くと、戻ったときに図形モードの間の字が突然現れる。** **契機：図形モードの間に端末へ書く
  利用者が出たとき**（Seinas の下で端末のクライアントが動く形）。
- **`close` しても張った面は外れない**（`munmap` が無い）。**抜けた後も書けば、文字の画面を上書きする**
  （次の描き直しで消える）。**契機：図形モードを出入りしながら走り続けるプログラムが出たとき。**
- **持ち主は 1 つで、譲れない**（2 人目は `-EBUSY`）。**契機：前景の譲渡を入れる段**（行250 の残り）。
- **同じ穴が端末の `read(0)` に残っている**（運用者の指示で明記する）。**端末の `read(0)` は、前景を
  いまも大域の印で見ている**——**起こしっぱなしの 1 本（スロット 1）でも、親が前景を持っていれば端末から
  読めて、前景の持ち主（シェル）と打鍵を取り合う。** **Y-c で直したのは開く口（`open_input`・
  `open_screen`）だけである。** **契機：起こしっぱなしの 1 本が端末を読む形が出たとき**（`a | b` の左が
  `read(0)` する形。持ち越しの行に在る）。
- **解像度は GOP の現行モードのまま**（1280×800）。**契機：FHD へ移る段。**

## Alternatives Considered

- **実 MMIO を直接ユーザーへマップ**——Ring 3 の MMIO は uncached で遅く、dirty追跡を失い、
  カーネルが画面の制御を失う。却下。
- **`blit(shm)` で毎回コピー**——クライアント用に framebuffer サイズの shm（1000ページ超）が
  要り、`MAX_SHM_PAGES` を大きく広げることになる。却下（裏バッファ再利用が確保を避ける）。
- **`read(0)` をモードで生イベントに切り替える**——`read(0)` の意味がモード依存になる。却下。
- **一般の `poll` を作る**——仕様が要求しない。最小の多重待ちで足りる。却下。
- **`Wait` を `Readable{fd}` へ全統合して種類を減らす**——pipe/socket/keyboard の利用が
  全部変わる大きな改修。この段の範囲を超える。別の段の候補。
- **入力イベントを独自の小さな構造体にする**——`struct input_event` に合わせるほうが Linux
  互換の思想（`ADR-0020`）に沿う。採らない。

## Consequences

**得るもの**——ユーザープロセスが画面へ画素を出し、生入力を受け、入力とソケットを同時に
待てる。`wl_shm` の画面側と `wl_keyboard` のイベント側の予行が動く。

**限界（契機つき）**
- FHD は入らない（v1。画面面は現行解像度に追随。解像度変更は bootloader に `set_mode` が
  無い。契機：FHD へ移る段）。
- クライアントプールは 32KiB（`MAX_SHM_PAGES`=8。契機：本番の実バッファ）。
- マウス無し（契機：`wl_pointer` を要する段）。
- 入力コードは set-1 スキャンコード（evdev の `KEY_*` へ訳さない。契機：本番のクライアント）。
- 前景の譲渡が無い（行250 の残り。契機：シェルと Seinas が入れ替わる形）。
