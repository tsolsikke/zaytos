# 0018. 割り込み基盤は下から積み、`sti`は最後の1箇所だけで行う

## Status
Accepted

## Date
2026-07-20

## Context
M4で割り込みを扱えるようにする。
範囲が広く（GDT / TSS / IDT / 例外ハンドラ / タイマ / キーボード / クリティカルセクション）、しかも**制御フローが非決定的になる最初の工程**である。
中途半端な状態で割り込みが入ると無言で落ちるため、どの順序で構築し、どの時点で有効化するかを先に決める。

前提として調べたこと:

- ツールチェインは1.97.1 **stable**。`#[unsafe(naked)]` + `naked_asm!`は使えるが、**`extern "x86-interrupt"`は使えない**（nightly限定）。割り込みハンドラのGPR退避・復帰は自前のnakedスタブで書く。
- `disable-redzone`が実際に効いていることを、コード生成で確認した（`docs/architecture.md` §5参照）。

## Decision

### 1. 段階分割

| 段階 | 内容 | 割り込み |
|---|---|---|
| M4-a | GDT / TSS / 自前カーネルスタック | 禁止のまま |
| M4-b | IDT / 例外ハンドラ / GPRフルダンプ | 禁止のまま |
| M4-c | クリティカルセクション / `Locked<T>`差し替え / PIC再マップ | 禁止のまま |
| M4-d | タイマ割り込み（**ここで初めて`sti`**） | 有効化 |
| M4-e | キーボード割り込み | 有効 |

クリティカルセクションをタイマより前に置く。
`sti`した瞬間に、ヒープの`Locked<T>`が依存している「割り込み常時禁止」という前提が崩れる。
差し替えを後回しにすると、タイマ割り込みがヒープ操作の途中に割り込んだ場合にフリーリストが壊れる。
症状は「しばらく動いた後に突然壊れる」形になる。

例外ハンドラ（M4-b）は割り込みを有効化せずに完成・検証できる。
例外（フォルト）は`IF`に関係なく発生し、`IF`で止まるのはマスク可能割り込みだけである。
したがってIDT・ハンドラ・スタブの正しさを、割り込みを一切有効化しないまま実機で検証しきれる。
`sti`を実行する時点で、その下の層がすべて実機検証済みという状態を作れる。
これがM4全体の安全性を支える。

### 2. `sti`は1箇所だけ

M4-dの1箇所でのみ実行し、直前に以下をすべて検証する。
1つでも欠ければ`sti`せずにfail-fastする。

1. 自前GDTがロード済みで、CS/DS/SSが自前ディスクリプタ（`sgdt`で読み戻す）
2. TSSがロード済みで、ISTスタックが確保・マップ済み（`str`で読み戻す）
3. IDTがロード済みで、**32個の例外ベクタすべて**にpresentなハンドラがある
4. **PICが0x20-0x2Fへ再マップ済み**
5. **ハンドラを書いたベクタ以外のIRQはすべてマスク済み**
6. `Locked<T>`が割り込み保存版に差し替わっている
7. ハンドラがEOIを発行する実装になっている

### 2.1 NMI（ベクタ2）はマスクできない

「ハンドラ入場時点で`IF=0`」という前提は、**割り込みゲートが入場時に`IF`をクリアする**ことによるものであり、`cli`がNMIを止めるという意味ではない。
NMIはマスク不能割り込みで、`IF`に関係なく到達する。

したがってNMIハンドラも、他の例外ハンドラと同じ制約に従う。
ロックも確保もコンソールも使わず、シリアルへ直接書いて停止する。
現在のQEMU構成でNMIが来ることはまずないが、来たときに何もできないハンドラだと原因が分からないまま落ちる。

### 3. 例外ハンドラの検証手段

`--panic-test`と同じ仕組みに揃え、**TCG固定**とする（KVMでは`-d int`が機能しないため。
`docs/troubleshooting.md`参照）。

```
cargo xtask run --exception-test divide-by-zero | invalid-opcode | page-fault | double-fault
```

kernel側はfeatureで切り替え、起動完了後に意図的に該当例外を起こす。
xtaskは**シリアルログのハンドラ出力**と**`qemu-debug.log`の`v=..`記録**の両方を突き合わせる。
片方だけでは「ベクタ番号を取り違えたまま動いているように見える」事故を防げない。

ダブルフォルトのテストは特に重要である。
ISTが正しく設定されていなければトリプルフォルト（無言のリセット）になるため、`v=08`が記録されて`CPU Reset`が続かないことを確認する。

**ダブルフォルトの誘発方法**: 当初は「無限再帰でスタックを溢れさせる」ことを想定していたが、**この方法はZaytOSでは機能しない**。
M4-aで導入した犠牲領域は`.bss`内のマップ済みメモリであり、溢れてもページフォルトは起きない。
単に犠牲領域を書き潰し、さらに溢れれば下の領域を壊し続けるだけでダブルフォルトには至らない。
一般のOSがこれでダブルフォルトを起こせるのはガードページがアンマップされているからであり、ZaytOSは`PageTableBuilder`がページ分割・アンマップに未対応のためガードページを置けない（`docs/deferred-decisions.md`）。

代わりに #PF（ベクタ14）のIDTゲートのPresentビットを一時的に0にしてから、意図的にページフォルトを起こす。

根拠はIntel SDM Vol.3の例外分類にある。
ダブルフォルトは「1つ目の例外を配送している最中に2つ目の例外が発生し、その組み合わせが表で`#DF`となる場合」に生じる。#PFはContributoryでもBenignでもない独立した分類（Page Fault）に置かれ、Page Faultの配送中にContributory分類の例外が起きると`#DF` になる。
ゲートのPresentビットが0だと、配送そのものが #NP（Segment Not Present、Contributory分類）を引き起こすため、「Page Fault → Contributory」の組み合わせが成立して`#DF`へ昇格する。

ハンドラは停止するのでPresentビットの復元は不要である。

### 4. GPRフルダンプは例外のみ解禁する

ADR-0004 AddendumでM4へ先送りしていた項目だが、解禁されるのは**例外ダンプだけ**である。

`panic!()`のレジスタが当てにならない理由は「`panic!`が呼ばれた時点の値は、フォーマット処理や関数呼び出しを経た後のものでしかない」ことであり、 **この理由はM4でも変わらない**。
変わるのは例外の側だけで、例外ハンドラはCPUが積んだフレーム + スタブがpushしたGPRという正確な値を持つ。

- 例外ハンドラ: RIP / CS / RFLAGS / RSP / SS + 全GPR + エラーコード + CR2（#PFの場合）
- `panic!()`: RSPと`PanicInfo`のみ（変更なし）

### 5. 割り込みハンドラからは出力しない

シングルコアで、ロック取得中に必ず割り込みを禁止するなら、割り込みハンドラがそのロックを保持中に見つけることは構造的にない（割り込みゲート経由の入場時点で`IF`はクリアされ、ロック保持区間も`IF=0`のため）。
つまりデッドロックはしない。
それでも出力しない。
理由は別にある。

1. ハンドラは短くあるべきで、転送（キャッシュ無効なフレームバッファへの書き込み）をハンドラ内で走らせたくない
2. タイマが100Hzなら毎秒100行になり、観測したい情報が埋もれる
3. ロック保持中にパニックすればパニックハンドラは同じロックを取れない（ADR-0013 Addendumと同じ問題）。出力しなければこの経路自体が生じない

| 経路 | 出力方法 |
|---|---|
| 例外ハンドラ | `SerialPort`へ直接書く（ロックなし）。**戻らない**ので再入もない |
| IRQハンドラ | 出力しない。 共有状態（カウンタ、リングバッファ）を更新するだけ |
| メインループ | 共有状態を読んで出力する。通常文脈なのでコンソールも自由に使える |

結果として、M4でもコンソールをグローバル化する必要がない。
M3-cの「グローバルにしない」判断をそのまま維持できる。

### 6. タイマはPITを使い、APICとACPIをM4の範囲外にする

APICを使うにはACPI（MADT）を読む必要があり、マッピングの穴（`docs/architecture.md` §6.4）を踏む可能性がある。
「割り込みを初めて有効化する」ことと「ACPIを初めて辿る」ことを同時にやると、問題が起きたときの切り分け軸が2つ同時に増える。
PITならI/Oポート直叩きで完結する。

### 7. 観測手段の維持

- 既定はTCGのまま。 M4では`-d int`が最も価値のある観測手段になる（どのベクタが何回配送されたかの完全な記録）。
- ハンドラはログを出さない代わりに、**ベクタ別の割り込み回数カウンタ**を持ち、メインループが一定間隔で1行にまとめて出す。出力量が入力と無関係に一定になる。
- **最後に受けた例外の記録**を静的領域に保持し、メインループが変化を検出したら出力する。
- **ハートビート**。ティック数つきの生存ログを定期的に出す。「ハング」と「ライブロック」と「タイマが来ていない」を区別できる。
- メインループは`hlt`で待つ。ビジーループにするとTCGのログが埋まる。

## 事前に潰すバグ（実装時のチェックリスト）

低レイヤで踏みやすく、しかも症状が「無言で落ちる」形になるものを列挙する。

1. **PIC未再マップ**。8259の既定ベクタは0x08-0x0FでCPUの例外ベクタと重なる。再マップせずに`sti`するとIRQ0が**ダブルフォルト（ベクタ8）として配送される**。M4で最も踏みやすい罠。
2. **EOI忘れ**。1回目の割り込みしか配送されない。「タイマが1回だけ動いて止まる」症状になる。
3. **IST未設定でのダブルフォルト**。トリプルフォルト = 無言のリセット。
4. **エラーコードの有無**。CPUがエラーコードを積む例外（#DF, #PF, #GP等）と積まない例外があり、**スタブを2種類**用意しないとスタックがずれる。
5. **GDT再ロード後のCS更新**。`lgdt`だけではCSは変わらない。far return（`retfq`）が必要。
6. **TSSディスクリプタは16バイト**。ロングモードのシステムディスクリプタは通常の8バイトではない。後続エントリがずれる。
7. **スタックオーバーフローの検出手段**。ガードページを置くには特定の4KiBをアンマップする必要があり、現在の`PageTableBuilder`は2MiBページの分割・アンマップに対応していない。当面は毒値カナリアで代替する（`docs/deferred-decisions.md`）。
8. **スプリアス割り込み（IRQ7 / IRQ15）**。8259はノイズ等で偽の割り込みを上げ、ベクタ0x27 / 0x2Fとして届く。これにEOIを送ってはいけない。 ISRレジスタを読んで真偽を判定し、偽ならEOIを送らずに戻る。スプリアスを受けた回数もカウンタに含める。
9. **共有カウンタの読み出しが最適化で消える**。メインループが通常の`static`を読むと、コンパイラが読み出しをループ外へ巻き上げ、ループ内で値が変わらなくなる。`AtomicU64`（`Relaxed`）または`read_volatile`を必須とする。「割り込みは動いているのにメインループが気づかない」という診断しにくい症状になる。
10. **`hlt`前のレース**。「条件を確認 → `hlt`」の間に割り込みが入ると、次の割り込みまで眠り続ける。`cli` → 条件確認 → `sti; hlt`の並びにし、 **`sti`と`hlt`を隣接させる**（`sti`は次の1命令の間だけ割り込みを保留するため取りこぼさない）。
11. **スタブから呼ぶRust関数のABI**。M2-0cのカーネルエントリと同じ問題。Rust ABIは不安定なので、nakedスタブから呼ぶ関数は`extern "sysv64"`で宣言する。
12. **スタックの16バイト境界**。SysV ABIは`call`直前にRSPが16バイト境界であることを要求する。CPUが積む5個（エラーコード有りなら6個）とスタブがpushするGPR数で境界がずれる。SSEを無効化しているため即死はしないが規約違反であり、**エラーコード有無の両方のスタブで境界を揃える**。
13. **red zone**。無効化されていないと割り込みハンドラが現在のスタックを破壊する。M2-0bで設定を確認済みだが、**この設定が実際に効くのはM4が初めて**である。`docs/architecture.md` §5に依存関係を明記した。

## Addendum（M4-c-3完了時点）: PICのベクタオフセットは検証できない

M4-c-3でPICを0x20-0x2Fへ再マップした。
ここで**検証範囲の限界**がはっきりしたので記録する。
§2のsti前チェックリストの項目4（「PICが0x20-0x2Fへ再マップ済み」）は、**M4-cの時点では実行時に確認できない**。

理由は8259Aのインターフェースにある。
ICW2（ベクタオフセット）は **書き込み専用**で、データポート（0x21 / 0xA1）から読めるのはIMRだけである。
「今どのベクタへ割り当てているか」を装置に問い合わせる手段が無い。

したがってM4-c-3で実際に検証できたのは次の範囲にとどまる。

| 対象 | 検証状況 |
|---|---|
| IMR（全IRQマスク） | 検証済み。 読み戻して0xFF/0xFFと照合。わざと0xFEを書いて検査が働くことも確認した |
| 再マップ先のIDTカバー | 検証済み。 0x20-0x2Fがpresentであることを再マップ前に確認。わざとPresentを落として検査が働くことも確認した |
| ベクタオフセットそのもの | **M4-d-2で検証済み**（下記Addendum 3 §5）。M4-c-3の時点では未検証だった |

マスクの読み戻しが通ったことをもって「再マップが正しい」と読んではならない。
それは検査していない対象を検査済みと錯覚する形であり、本プロジェクトで過去2回（スタブ表のstride検証、`!Send`/`!Sync`のコンパイル時検査）起きた誤りと同じ構造になる。
ログの文面も断定を避け、 "programmed ... (ICW2 is write-only; the offset cannot be read back)" とした。

オフセットが証明されるのはM4-dである。
最初のタイマ割り込みがベクタ0x20として届いた時点で初めて、ICW2が意図どおり書けていたことが分かる。
§2の項目4は「M4-dの実行結果によって事後的に満たされる」と読み替える。

### ICW2を書き間違えた場合の症状

M4-dで症状が出たときにPICのオフセットを疑えるよう、対応表を残す。

| 書き間違いの種類 | 症状 |
|---|---|
| どこにも届かないオフセット | マスクを外して`sti`しても割り込みが来ない。「PITの初期化ミス」「EOI忘れ」と誤診しやすいが、実際はベクタが別を向いている |
| 意図と違うベクタ | 全256に入れた「予期しないベクタ」ハンドラが受けて停止する。報告されたベクタ番号が0x20でなければICW2を疑う |
| 例外ベクタと重なる値 | `pic::validate_offsets`が弾くのでこの経路には入らない |

### ファームウェアが既に0x20を使っていたことによる追加のリスク

再マップ前のIMRを読んだところ0xFF/0xFF（全マスク）だった。
一方、`qemu-debug.log`にはカーネル起動前に`v=20`が674件記録されている（`docs/troubleshooting.md` 2026-07-21の記録）。
つまりファームウェアは既にベクタ0x20でタイマを処理し、制御を渡す前にマスクしていた。

ここから、**今回の再マップは「同じ値への上書き」になっている可能性が高い**。
だとすればICW2の書き間違いがあっても、ハードウェアが既に正しい状態にあるせいでM4-dでも表面化しない場合がありうる。
M4-dで「動いた」ことをもってICW2の実装が正しいと結論づけないこと。
判定するなら、意図的に別のオフセット（例: 0x30-0x3F）へ再マップして、そのベクタで届くことを確認する必要がある。

## Addendum 2（M4-d-1完了時点）: 割り込みを有効化する経路

`sti`できる状態を作るところまでをM4-d-1として切り出した。
タイマはまだ動かさない。
「`sti`すること」と「割り込みが実際に来ること」を別々に検証すると、問題が出たときに`sti`周辺とIRQ経路のどちらかへ切り分けられる。

### 1. スタックの16バイト境界（罠12の導出）

チェックリスト12は「CPUが積む5個（エラーコード有りなら6個）とスタブがpushするGPR数で境界がずれる」としか書いていなかった。
M4-d-1でIRQ経路を足す際に導出を明示したので記録する。

長モードでは、割り込み・例外の配送時に **CPUがRSPを16バイト境界へ揃えてから**フレームを積む（Intel SDM Vol.3A 6.14.2）。
したがって基準点は必ず`RSP ≡ 0 (mod 16)`で、そこから積まれる量で入場時の剰余が決まる。

| 経路 | CPUが積む | 入場時 | スタブが積む | 共通ルーチンが積む | call直前 |
|---|---|---|---|---|---|
| 例外（エラーコードなし） | 5個 = 40 → ≡ 8 | **8** | ダミーEC + ベクタ = 16 | GPR 15 + CR2 = 128 | 8 |
| 例外（エラーコードあり） | 6個 = 48 → ≡ 0 | **0** | ベクタのみ = 8 | GPR 15 + CR2 = 128 | 8 |
| IRQ | 5個 = 40 → ≡ 8 | **8** | ベクタのみ = 8 | GPR 15 = 120 | 8 |

入場時の剰余は一定ではない。
エラーコードを積む例外だけ`≡ 0`で、他は`≡ 8`である。
エラーコードなしの例外でダミーをpushしているのは`ExceptionContext`のレイアウトを揃えるためだが、結果として**剰余も揃える** 働きをしている（`8 − 16 ≡ 8`、`0 − 8 ≡ 8`）。
3経路とも`call`直前が`≡ 8`に収束するので、どれも`sub rsp, 8`で`≡ 0`にする。

「エラーコードの有無が調整の要否を分ける」ではない。
決めるのは「入場時の剰余 − 積んだ総量」であり、たまたま3経路とも同じ結論になっているだけである。
実際、設計時に「IRQ側はGPR 15個 + ベクタ = 128バイトで16の倍数だから調整不要」と誤った結論を出しかけた。
入場時が`≡ 0`でないため、これは成立しない。

### 2. 境界は手計算ではなく実測で検証する

上の導出が正しいことを、スタブが`call`直前に**レジスタから読んだRSPの実値**をハンドラへ渡して検査する形にした（`idt::check_stack_alignment`）。

`ExceptionContext`のポインタから引き算して求める方法は採らない。
それはスタブのpush量という同じ仮定から導いた値であり、仮定が間違っていても一致してしまう。**検査に見えて何も検査していない形**になる（本プロジェクトで過去2回起きた誤り）。

検査が働くことは、`STACK_ALIGN_ADJUST`を0にする`misalign-test` featureで確認した。
例外経路・IRQ経路の両方で発火して停止する。
正常ビルドでは例外テスト4種すべてで一度も発火しない。

### 3. M4-d-1のメインループは`hlt`を使わない

§7は「メインループは`hlt`で待つ」としており、そのための`common::cpu::enable_interrupts_and_halt`（`sti; hlt`隣接、罠10）もM4-d-1で用意した。
しかしM4-d-1でそれを使うと確実にハングする。

`hlt`は次の割り込みまでCPUを止める。
M4-d-1は全IRQをマスクした状態で`sti`するので、**起こしてくれるものが存在しない**。
最初の`hlt`で永久に止まり、周回カウンタもハートビートも期限判定も動かない。
外から見た症状は「`sti`した瞬間にハングした」であり、M4-d-1で切り分けたい対象そのものと区別がつかなくなる。
検証段階として機能しない。

したがってM4-d-1のループは**期限つきスピン**とする。
`hlt`を使う本来の形は起こしてくれるタイマが実在するM4-d-2で初めて成立する。
ビジーループを避ける理由（TCGのログ肥大）は、割り込みが1件も起きないM4-d-1では発生しない。
`-d int`は割り込みが起きたときだけ記録するためである。

### 4. §2の「7項目すべて」に対する明示的な例外

§2は「1つでも欠ければ`sti`せずにfail-fastする」と定めている。
M4-d-1の時点では、7項目のうち2つが「OK」でも「NG」でもなく**確かめる手段が無い**。
これを`true`に丸めると、検証していないものを検証済みとして数えることになるため、`CheckState { Verified, Failed, Unverifiable }`の3状態を型で区別し、`Unverifiable`は`sti`を妨げないこととした。
これは §2の原則に対する明示的な例外である。

| 項目 | 状態 | 理由と、いつ閉じるか |
|---|---|---|
| 4. PICが0x20-0x2Fへ再マップ済み | Unverifiable | ICW2が書き込み専用（Addendum 1）。M4-d-2で最初のタイマ割り込みがベクタ0x20として届いた時点でVerifiedへ移す |
| 7. ハンドラがEOIを発行 | Unverifiable | M4-d-1はIRQをマスク解除しないため、応答すべき割り込みが存在しない。M4-d-2で実装と同時にVerifiedへ移す |

項目4の`Unverifiable`は項目5の成立に依存する。
全IRQがマスクされているからこそ、ICW2が誤っていても何も配送されず害が生じない。
したがって実装は、項目5が`Verified`でない場合、項目4を`Unverifiable`ではなく`Failed`にする。
検証不能を許す根拠そのものが失われるためである。
型だけでは正当化されず、根拠は個別に示す必要がある。

### 5. IRQ経路は例外経路から独立させる

例外ハンドラは戻らないためGPRを退避するだけで済むが、IRQは中断した処理へ **戻る**ので、退避したものを必ず復元しなければならない。
復元を忘れると割り込まれた側のレジスタが静かに壊れ、「割り込みと無関係な場所で不定期に落ちる」という最も診断しにくい症状になる。

そのためスタブ表・共通ルーチン・コンテキスト型をすべて分けた。
例外をIRQ化してはならない点も併せて記録する。#DEからそのまま戻れば同じ除算命令を再実行して無限ループになる。
戻れるのは、原因が外部にあり再実行の必要がないIRQだけである。

スタブ表が2系統になったため、**配置検証も2系統必要**である（`check_stub_table` / `check_irq_stub_table`）。
片方の検証がもう片方を保証しない。

### 6. GPR復元の検証は13本までしかできない

`int 0x20`をソフトウェア発行し、レジスタごとに異なる既知値が復元されることを確かめる（M4-b-2のGPRダンプ検証と同じ考え方）。
ソフトウェア割り込みはPICを経由しないため、マスク状態と無関係にハンドラ経路だけを試せる。

ただしrbxとrbpは検査できない。
LLVMがこの2本を内部的に予約しており、`asm!`のオペランドに指定するとコンパイルエラーになる。
検査できるのは残る13本である。

それでも検査の意味は保たれる。**順序の取り違え**は13個の相異なる値で十分に捕まり、**本数の過不足**はRSPがずれて`iretq`の時点で即座に壊れる（`iretq`はRSPがCPUの積んだフレーム先頭を指している必要があり、1バイトでもずれると制御が飛ぶ）。
この2本だけが静かに壊れる経路は、pushとpopの両方でこの2本だけを対称に取り違えた場合に限られる。

## Addendum 3（M4-d-2進行中）: タイマを動かす

このAddendumはM4-d-2の進行に伴って追記される。
M4-d-2は3つのコミットに分けており、確定した内容から順に書いている。
途中の状態では節が欠けているが、それは未着手を意味する。

### 1. GPR復元の検証はPICの範囲外（0x30）で行う

M4-d-1では`int 0x20`でIRQ経路を試していた。
M4-d-2でEOIを実装するとこれが衝突する。
ソフトウェア割り込みは実在のIRQではないため、ハンドラが無条件にEOIを送る作りだと**起きてもいない割り込みに応答する**ことになる。
PICのISRにビットが立っていない状態でEOIを送れば、優先度スタックの状態を壊し、以降の本物の割り込みの扱いを狂わせうる。

テスト専用ベクタをPICの範囲外（0x30）へ移す。
`int 0x30`は8259Aを経由せずCPUが直接IDTを引くため、EOIの論理が一切絡まない。
PIC経由で配送されないベクタなので、「EOIを送らないハンドラ」がそのまま正しい実装になる。
検証の目的（GPR復元と`iretq`経路）はそのまま保てる。

IRQスタイルのスタブ表は17本になった。
「スタブの本数」と「PICのIRQの本数」が一致しなくなったため、定数も`IRQ_STYLE_STUB_COUNT`（17）と`PIC_IRQ_COUNT`（16）に分けてある。

却下した代替案:

- **実タイマでの検証に置き換える**: 「GPRが壊れた」ことは分かるが、壊れたのがスタブかPIT設定かEOIかを切り分けられない。ハンドラ経路だけを単独で試せるという、この検証の価値そのものが失われる。却下。
- ハンドラ側でソフトウェア割り込み由来かを判別してEOIを抑制する: 本番経路にテスト専用の分岐が入る。しかも「ソフトウェア割り込み由来か」を実行時に確実に判別する手段が無く、判別を誤れば本物の割り込みへEOIを送らない側へ倒れ、以降の割り込みが全部止まる。テストのために本番経路の信頼性を下げることになる。却下。

PICの範囲外へ移すのが、本番経路に一切手を入れずに済む唯一の案だった。

### 2. 「何も届かないこと」は増加分で判定する（0x30移設後も必要）

テスト用ベクタを0x30へ移しても、`--interrupt-test enable-only`の判定を絶対値へ戻すことはできない。
割り込み回数カウンタは**全256ベクタを合計する** ため、`int 0x30`で計上された1件は絶対値に残り続ける。
0x20が汚れなくなっただけで、絶対値では「スピン中に届いた」と誤判定する構造は変わらない。
基準点を取って増加分を見る形を維持する。

合計の対象をPICの範囲（0x20-0x2F）だけに絞る案は採らない。
ここで見たいのは「何も届かないこと」であって、対象は全ベクタである。
とくにNMI（ベクタ2）は`cli`でマスクできず、全IRQをマスクした状態でも理論上は到達しうる（§2.1）。
範囲を絞ると、まさにそのNMIが来ても検出できなくなる。

### 3. `no-eoi-test`は「失敗が報告されないこと」で判定する

EOIの動作は「ティックが増え続けること」自体が証明になる。
送らなければ1回で止まるので、わざと落としたビルドで確かめる。

当初は「`timer FAILED`の行が出ること」を期待する設計にしていたが、 **これは成立しない**。
EOIを送らなければ2回目のティックが来ず、メインループは`hlt`に入ったまま二度と起きない。
失敗を報告するコード自体が動かない。

これは §7の「メインループは`hlt`で待つ」形が持つ限界そのもの（Addendum 2 §3と同根）である。
そこで判定を反転させた。

- 期待するのは「最初の1回は確かに届いたこと」
- 禁止するのは「2回目以降が来たこと」（ハートビートが1本でも出たら失敗）
- 「出ないこと」の確認なので、期待マーカーが揃っても早期に打ち切らずタイムアウトまで待つ

限界を消そうとせず、限界をそのまま検証手段に使う形にした。

### 4. 取りこぼしの観測は「メインループの追従の遅れ」までしか測れない

メインループが1回起きるあいだに進んだティック数の最大値を記録している。
1なら毎ティック観測できており、2以上なら処理中に次が来ている（TCGでは常時2だった）。

これはハードウェアのティック取りこぼしではない。
PITが発火したのにCPUへ届かない、あるいはEOIが間に合わず次が抑止される、という本当の意味での取りこぼしは、**独立した第2の時間源が無いと検出できない**。
現状はTSCしか無く、そのTSCも仮想化環境では信用できない（`common::cpu`参照）。
測れないものを測れたことにしないため、この区別をコードのコメントにも残した。

### 5. 項目4と項目7はM4-d-2で`Verified`へ移った

§2の7項目のうち、M4-d-1で`Unverifiable`として持ち越した2つが閉じた。

| 項目 | 状態 | 何によって証明されたか |
|---|---|---|
| 4. PICが0x20-0x2Fへ再マップ済み | **Verified** | 最初のタイマ割り込みが**実際にベクタ0x20として届いた**こと。届いたベクタ番号を実値で照合し、違えばfail-fastする。さらに`alt-offset-test`で0x30-0x3Fへ再マップするとティックが0x30で届くことも確認した |
| 7. ハンドラがEOIを発行 | **Verified** | ティックが増え続けたこと。EOIを送らなければ1回で止まる。`no-eoi-test`で実際に1回で止まることを確認した |

`alt-offset-test`が重要なのは、M4-c-3で残した申し送りを閉じるからである。
通常構成の0x20はOVMFが既に使っていた可能性が高く（`docs/troubleshooting.md` 2026-07-21）、こちらのICW2が誤っていてもハードウェアが既に正しい状態にあるせいで動いてしまいうる。
別のオフセットで届けば、ZaytOSのICW2書き込みが実際にオフセットを動かしていることが示せる。
同時に**配送元がLAPICではなく8259Aである**ことも分かる（LAPIC経由ならベクタは移動しない）。

`alt-offset-test`と`interrupt-test-irq-path`は排他である。
前者はIRQ0をベクタ0x30へ動かし、それは後者がテストに使うベクタと同じ番号になる。
テスト用ベクタを別の番号へ逃がす案もあったが、featureによってテストのベクタ番号が変わるとログを読むときの混乱要因になるため、`compile_error!`でコンパイル時に弾く形にした。

### 6. スプリアス割り込みは、誘発手段が無いまま先に実装する

チェックリスト8の項目。
IRQ0しか解禁していない現状では実際にはまず発生しないが、実機で誘発する手段も無い。
「実物を観測してから実装する」というADR-0013（`Bitmask`ピクセル形式）の判断とは逆になるが、踏んだときの症状が「無言で割り込みが止まる」であり後から気づくのが困難なため、先に入れる。

代わりに**純粋ロジックはホストテストで固定する**。
ISRのビット判定と、EOIの宛先の決定（とくに下記の非対称性）は、ポートI/Oを含まない関数として切り出してある。

**スプリアスの扱いはマスタ側とスレーブ側で非対称である。**

- **IRQ7の偽**: マスタ自身が偽を上げただけでISRにビットは立っておらず、EOIを送る相手がいない。送ってはいけない。
- **IRQ15の偽**: スレーブは偽だが、マスタはIRQ2（カスケード）を本物として受け付けておりISRのビットが立っている。スレーブへ送ってはいけないが、 **マスタへは送らなければならない**。送らないとマスタが処理中のまま残り、以降マスタの全IRQが上がらなくなる。

### 7. 通常ビルドでもタイマを動かす（カーネルが停止しなくなった）

M4-d-2の到達点は「カーネルに時間が流れている」ことなので、回帰チェック用のfeatureではなく通常起動でタイマを動かす。
結果として**カーネルは停止しなくなった**。
副作用への対処:

- **到達点の目印の再定義**: `kernel: halting`はもう出ない。代わりに「最初のティックがベクタ0x20として届いた」行を「起動しきった」の目印とする。ここまで来ていればGDT / IDT / ページング / ヒープ / コンソール / PIC / PITがすべて動き、割り込みも配送されている。
- **デバッグログの増加**: `-d int`のログが実測137KB/s（100Hz、1ティックあたり20行強）で増え続ける。`cargo xtask run`に既定120秒の実行時間上限を設け、起動時に増加速度を警告する。`--no-limit`で解除できる。

## Addendum 4（M4完了時点）: §2の7項目の最終状態

M4-eまで完了し、`sti`前チェックリストの全項目が閉じた。**何によって証明されたか**を残す。

| 項目 | 状態 | 証明したもの |
|---|---|---|
| 1. GDTロード済み、CS/DS/SSが自前 | **Verified** | `sgdt`とセグメントレジスタの読み戻し。DS/SSはM4-d-1で追加した |
| 2. TSSロード済み、ISTスタックあり | **Verified** | `str`の読み戻しと、#DFゲートのISTインデックス。ダブルフォルト実機テストでIST1の使用も確認 |
| 3. IDTロード済み、32例外ベクタがpresent | **Verified** | `sidt`の読み戻し、全256のpresent / ゲート種別 / DPL、スタブ表2系統の配置検証 |
| 4. PICが0x20-0x2Fへ再マップ済み | **Verified** | 最初のタイマ割り込みが**実際にベクタ0x20として届いた**こと。`alt-offset-test`で0x30-0x3Fへ再マップするとティックが0x30で届くことも確認し、「OVMFが既に0x20を使っていただけ」という疑いも晴らした |
| 5. ハンドラを書いたベクタ以外はマスク済み | **Verified** | IMRの読み戻し。全マスク → 0xFE（タイマ）→ 0xFC（キーボード）と段階的に照合。わざと0xFEを書いて検査が働くことも確認 |
| 6. `Locked<T>`が割り込み保存版 | **Verified** | 保持中の実RFLAGSを測定。`--critical-test restore-enabled`でIF=1から入る復元経路も確認 |
| 7. ハンドラがEOIを発行 | **Verified** | ティックが増え続けたこと。`no-eoi-test`で落とすと1回で止まることを確認 |

「わざと壊して確認する」を全項目で通した。
検査があるように見えて何も検査していない、という過去2回の誤りを再導入していないことの担保である。

チェックリスト（事前に潰すバグ）についても、13項目すべてが実装または明示的な保留として決着した。
罠8（スプリアス割り込み）だけは誘発手段が無いまま先に実装している。
踏んだときの症状が「無言で割り込みが止まる」で後から気づけないため（Addendum 3 §6）。

## Alternatives Considered

- **クリティカルセクションを最後に回す**（当初案の順序）: タイマを有効化した時点でヒープの`Locked<T>`の前提が崩れる。却下。
- **例外ハンドラとタイマを同時に入れる**: `sti`の時点で未検証の層が増える。例外は`IF`に依存せず検証できるという性質を使わない手はない。却下。
- **APICを最初から使う**: SMPや高精度タイマには必要だが、ACPIを辿る必要が生じ、切り分け軸が増える。却下（M4の後かM5で）。
- **割り込みハンドラから直接ログを出す**: デッドロックはしないが、上記5の3つの理由で却下。
- **コンソールをグローバル + ロックにする**: ハンドラから出力しない設計を採るため必要性が生じない。却下（M3-cの判断を維持）。
- **ガードページでスタックオーバーフローを検出する**: 確実だが`PageTableBuilder`にページ分割・アンマップを実装する必要があり、M4-aの範囲を大きく超える。却下（保留項目として記録）。

## Consequences
- `sti`を実行する時点で、GDT / TSS / スタック / IDT / 例外ハンドラ / 排他制御がすべて実機検証済みになる。
- 例外ハンドラの検証が回帰チェックとして常設される（`--exception-test`）。
- 割り込みハンドラから出力しないため、ハンドラ内の再入・ロック・フラッシュの問題が構造的に発生しない。代わりに、割り込みで起きたことは**カウンタ越しにしか観測できない**。詳細が必要になったら、リングバッファへ記録してメインループで吐く形に広げる。
- `extern "x86-interrupt"`を使わないため、スタブは自前のnaked asmになる。エラーコードの有無で2種類必要で、境界合わせも自分で行う。nightlyへ移れば解消するが、ツールチェインをstableに固定する方針（M0）を優先する。
- ACPIとAPICはM4の範囲外に残る。タイマ精度が問題になるか、SMPへ進む時点で再検討する。
