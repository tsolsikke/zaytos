# 0018. 割り込み基盤は下から積み、`sti` は最後の 1 箇所だけで行う

## Status
Accepted

## Date
2026-07-20

## Context
M4 で割り込みを扱えるようにする。範囲が広く（GDT / TSS / IDT / 例外ハンドラ /
タイマ / キーボード / クリティカルセクション）、しかも**制御フローが非決定的に
なる最初の工程**である。中途半端な状態で割り込みが入ると無言で落ちるため、
どの順序で構築し、どの時点で有効化するかを先に決める。

前提として調べたこと:

- ツールチェインは 1.97.1 **stable**。`#[unsafe(naked)]` + `naked_asm!` は
  使えるが、**`extern "x86-interrupt"` は使えない**（nightly 限定）。
  割り込みハンドラの GPR 退避・復帰は自前の naked スタブで書く。
- `disable-redzone` が実際に効いていることを、コード生成で確認した
  （`docs/architecture.md` §5 参照）。

## Decision

### 1. 段階分割

| 段階 | 内容 | 割り込み |
|---|---|---|
| M4-a | GDT / TSS / 自前カーネルスタック | 禁止のまま |
| M4-b | IDT / 例外ハンドラ / GPR フルダンプ | 禁止のまま |
| M4-c | クリティカルセクション / `Locked<T>` 差し替え / PIC 再マップ | 禁止のまま |
| M4-d | タイマ割り込み（**ここで初めて `sti`**） | 有効化 |
| M4-e | キーボード割り込み | 有効 |

**クリティカルセクションをタイマより前に置く。** `sti` した瞬間に、ヒープの
`Locked<T>` が依存している「割り込み常時禁止」という前提が崩れる。差し替えを
後回しにすると、タイマ割り込みがヒープ操作の途中に割り込んだ場合にフリー
リストが壊れる。症状は「しばらく動いた後に突然壊れる」形になる。

**例外ハンドラ（M4-b）は割り込みを有効化せずに完成・検証できる。** 例外
（フォルト）は `IF` に関係なく発生し、`IF` で止まるのはマスク可能割り込み
だけである。したがって IDT・ハンドラ・スタブの正しさを、割り込みを一切
有効化しないまま実機で検証しきれる。`sti` を実行する時点で、その下の層が
すべて実機検証済みという状態を作れる。これが M4 全体の安全性を支える。

### 2. `sti` は 1 箇所だけ

M4-d の 1 箇所でのみ実行し、直前に以下をすべて検証する。1 つでも欠ければ
`sti` せずに fail-fast する。

1. 自前 GDT がロード済みで、CS/DS/SS が自前ディスクリプタ（`sgdt` で読み戻す）
2. TSS がロード済みで、IST スタックが確保・マップ済み（`str` で読み戻す）
3. IDT がロード済みで、**32 個の例外ベクタすべて**に present なハンドラがある
4. **PIC が 0x20-0x2F へ再マップ済み**
5. **ハンドラを書いたベクタ以外の IRQ はすべてマスク済み**
6. `Locked<T>` が割り込み保存版に差し替わっている
7. ハンドラが EOI を発行する実装になっている

### 2.1 NMI（ベクタ 2）はマスクできない

「ハンドラ入場時点で `IF=0`」という前提は、**割り込みゲートが入場時に `IF` を
クリアする**ことによるものであり、`cli` が NMI を止めるという意味ではない。
NMI はマスク不能割り込みで、`IF` に関係なく到達する。

したがって NMI ハンドラも、他の例外ハンドラと同じ制約に従う。**ロックも
確保もコンソールも使わず、シリアルへ直接書いて停止する。** 現在の QEMU
構成で NMI が来ることはまずないが、来たときに何もできないハンドラだと
原因が分からないまま落ちる。

### 3. 例外ハンドラの検証手段

`--panic-test` と同じ仕組みに揃え、**TCG 固定**とする（KVM では `-d int` が
機能しないため。`docs/troubleshooting.md` 参照）。

```
cargo xtask run --exception-test divide-by-zero | invalid-opcode | page-fault | double-fault
```

kernel 側は feature で切り替え、起動完了後に意図的に該当例外を起こす。
xtask は**シリアルログのハンドラ出力**と**`qemu-debug.log` の `v=..` 記録**の
両方を突き合わせる。片方だけでは「ベクタ番号を取り違えたまま動いているように
見える」事故を防げない。

ダブルフォルトのテストは特に重要である。IST が正しく設定されていなければ
トリプルフォルト（無言のリセット）になるため、`v=08` が記録されて
`CPU Reset` が続かないことを確認する。

**ダブルフォルトの誘発方法**: 当初は「無限再帰でスタックを溢れさせる」
ことを想定していたが、**この方法は ZaytOS では機能しない**。M4-a で導入した
犠牲領域は `.bss` 内のマップ済みメモリであり、溢れてもページフォルトは
起きない。単に犠牲領域を書き潰し、さらに溢れれば下の領域を壊し続けるだけで
ダブルフォルトには至らない。一般の OS がこれでダブルフォルトを起こせるのは
ガードページがアンマップされているからであり、ZaytOS は
`PageTableBuilder` がページ分割・アンマップに未対応のためガードページを
置けない（`docs/deferred-decisions.md`）。

代わりに **#PF（ベクタ 14）の IDT ゲートの Present ビットを一時的に 0 に
してから、意図的にページフォルトを起こす**。

根拠は Intel SDM Vol.3 の例外分類にある。ダブルフォルトは「1 つ目の例外を
配送している最中に 2 つ目の例外が発生し、その組み合わせが表で `#DF` と
なる場合」に生じる。#PF は Contributory でも Benign でもない独立した分類
（Page Fault）に置かれ、**Page Fault の配送中に Contributory 分類の例外が
起きると `#DF`** になる。ゲートの Present ビットが 0 だと、配送そのものが
#NP（Segment Not Present、Contributory 分類）を引き起こすため、
「Page Fault → Contributory」の組み合わせが成立して `#DF` へ昇格する。

ハンドラは停止するので Present ビットの復元は不要である。

### 4. GPR フルダンプは例外のみ解禁する

ADR-0004 Addendum で M4 へ先送りしていた項目だが、解禁されるのは**例外
ダンプだけ**である。

`panic!()` のレジスタが当てにならない理由は「`panic!` が呼ばれた時点の値は、
フォーマット処理や関数呼び出しを経た後のものでしかない」ことであり、
**この理由は M4 でも変わらない**。変わるのは例外の側だけで、例外ハンドラは
CPU が積んだフレーム + スタブが push した GPR という正確な値を持つ。

- 例外ハンドラ: RIP / CS / RFLAGS / RSP / SS + 全 GPR + エラーコード
  + CR2（#PF の場合）
- `panic!()`: RSP と `PanicInfo` のみ（変更なし）

### 5. 割り込みハンドラからは出力しない

シングルコアで、ロック取得中に必ず割り込みを禁止するなら、割り込みハンドラが
そのロックを保持中に見つけることは構造的にない（割り込みゲート経由の入場時点で
`IF` はクリアされ、ロック保持区間も `IF=0` のため）。つまりデッドロックは
しない。**それでも出力しない。理由は別にある。**

1. ハンドラは短くあるべきで、転送（キャッシュ無効なフレームバッファへの
   書き込み）をハンドラ内で走らせたくない
2. タイマが 100Hz なら毎秒 100 行になり、観測したい情報が埋もれる
3. ロック保持中にパニックすればパニックハンドラは同じロックを取れない
   （ADR-0013 Addendum と同じ問題）。出力しなければこの経路自体が生じない

| 経路 | 出力方法 |
|---|---|
| 例外ハンドラ | `SerialPort` へ直接書く（ロックなし）。**戻らない**ので再入もない |
| IRQ ハンドラ | **出力しない。** 共有状態（カウンタ、リングバッファ）を更新するだけ |
| メインループ | 共有状態を読んで出力する。通常文脈なのでコンソールも自由に使える |

**結果として、M4 でもコンソールをグローバル化する必要がない。** M3-c の
「グローバルにしない」判断をそのまま維持できる。

### 6. タイマは PIT を使い、APIC と ACPI を M4 の範囲外にする

APIC を使うには ACPI（MADT）を読む必要があり、マッピングの穴
（`docs/architecture.md` §6.4）を踏む可能性がある。「割り込みを初めて有効化
する」ことと「ACPI を初めて辿る」ことを同時にやると、問題が起きたときの
切り分け軸が 2 つ同時に増える。PIT なら I/O ポート直叩きで完結する。

### 7. 観測手段の維持

- **既定は TCG のまま。** M4 では `-d int` が最も価値のある観測手段になる
  （どのベクタが何回配送されたかの完全な記録）。
- ハンドラはログを出さない代わりに、**ベクタ別の割り込み回数カウンタ**を持ち、
  メインループが一定間隔で 1 行にまとめて出す。出力量が入力と無関係に一定に
  なる。
- **最後に受けた例外の記録**を静的領域に保持し、メインループが変化を検出
  したら出力する。
- **ハートビート**。ティック数つきの生存ログを定期的に出す。「ハング」と
  「ライブロック」と「タイマが来ていない」を区別できる。
- メインループは `hlt` で待つ。ビジーループにすると TCG のログが埋まる。

## 事前に潰すバグ（実装時のチェックリスト）

低レイヤで踏みやすく、しかも症状が「無言で落ちる」形になるものを列挙する。

1. **PIC 未再マップ**。8259 の既定ベクタは 0x08-0x0F で CPU の例外ベクタと
   重なる。再マップせずに `sti` すると IRQ0 が**ダブルフォルト（ベクタ 8）と
   して配送される**。M4 で最も踏みやすい罠。
2. **EOI 忘れ**。1 回目の割り込みしか配送されない。「タイマが 1 回だけ動いて
   止まる」症状になる。
3. **IST 未設定でのダブルフォルト**。トリプルフォルト = 無言のリセット。
4. **エラーコードの有無**。CPU がエラーコードを積む例外（#DF, #PF, #GP 等）と
   積まない例外があり、**スタブを 2 種類**用意しないとスタックがずれる。
5. **GDT 再ロード後の CS 更新**。`lgdt` だけでは CS は変わらない。
   far return（`retfq`）が必要。
6. **TSS ディスクリプタは 16 バイト**。ロングモードのシステムディスクリプタは
   通常の 8 バイトではない。後続エントリがずれる。
7. **スタックオーバーフローの検出手段**。ガードページを置くには特定の 4KiB を
   アンマップする必要があり、現在の `PageTableBuilder` は 2MiB ページの
   分割・アンマップに対応していない。当面は毒値カナリアで代替する
   （`docs/deferred-decisions.md`）。
8. **スプリアス割り込み（IRQ7 / IRQ15）**。8259 はノイズ等で偽の割り込みを
   上げ、ベクタ 0x27 / 0x2F として届く。**これに EOI を送ってはいけない。**
   ISR レジスタを読んで真偽を判定し、偽なら EOI を送らずに戻る。スプリアスを
   受けた回数もカウンタに含める。
9. **共有カウンタの読み出しが最適化で消える**。メインループが通常の `static` を
   読むと、コンパイラが読み出しをループ外へ巻き上げ、ループ内で値が変わらなく
   なる。`AtomicU64`（`Relaxed`）または `read_volatile` を必須とする。
   「割り込みは動いているのにメインループが気づかない」という診断しにくい
   症状になる。
10. **`hlt` 前のレース**。「条件を確認 → `hlt`」の間に割り込みが入ると、次の
    割り込みまで眠り続ける。`cli` → 条件確認 → `sti; hlt` の並びにし、
    **`sti` と `hlt` を隣接させる**（`sti` は次の 1 命令の間だけ割り込みを
    保留するため取りこぼさない）。
11. **スタブから呼ぶ Rust 関数の ABI**。M2-0c のカーネルエントリと同じ問題。
    Rust ABI は不安定なので、naked スタブから呼ぶ関数は `extern "sysv64"` で
    宣言する。
12. **スタックの 16 バイト境界**。SysV ABI は `call` 直前に RSP が 16 バイト
    境界であることを要求する。CPU が積む 5 個（エラーコード有りなら 6 個）と
    スタブが push する GPR 数で境界がずれる。SSE を無効化しているため即死は
    しないが規約違反であり、**エラーコード有無の両方のスタブで境界を揃える**。
13. **red zone**。無効化されていないと割り込みハンドラが現在のスタックを
    破壊する。M2-0b で設定を確認済みだが、**この設定が実際に効くのは M4 が
    初めて**である。`docs/architecture.md` §5 に依存関係を明記した。

## Addendum（M4-c-3 完了時点）: PIC のベクタオフセットは検証できない

M4-c-3 で PIC を 0x20-0x2F へ再マップした。ここで**検証範囲の限界**が
はっきりしたので記録する。§2 の sti 前チェックリストの項目 4
（「PIC が 0x20-0x2F へ再マップ済み」）は、**M4-c の時点では実行時に
確認できない**。

理由は 8259A のインターフェースにある。ICW2（ベクタオフセット）は
**書き込み専用**で、データポート（0x21 / 0xA1）から読めるのは IMR だけ
である。「今どのベクタへ割り当てているか」を装置に問い合わせる手段が無い。

したがって M4-c-3 で実際に検証できたのは次の範囲にとどまる。

| 対象 | 検証状況 |
|---|---|
| IMR（全 IRQ マスク） | **検証済み。** 読み戻して 0xFF/0xFF と照合。わざと 0xFE を書いて検査が働くことも確認した |
| 再マップ先の IDT カバー | **検証済み。** 0x20-0x2F が present であることを再マップ前に確認。わざと Present を落として検査が働くことも確認した |
| ベクタオフセットそのもの | **未検証。** 書いた値を表示しているだけ |

マスクの読み戻しが通ったことをもって「再マップが正しい」と読んではならない。
それは検査していない対象を検査済みと錯覚する形であり、本プロジェクトで
過去 2 回（スタブ表の stride 検証、`!Send`/`!Sync` のコンパイル時検査）
起きた誤りと同じ構造になる。ログの文面も断定を避け、
"programmed ... (ICW2 is write-only; the offset cannot be read back)" とした。

**オフセットが証明されるのは M4-d である。** 最初のタイマ割り込みが
ベクタ 0x20 として届いた時点で初めて、ICW2 が意図どおり書けていたことが
分かる。§2 の項目 4 は「M4-d の実行結果によって事後的に満たされる」と
読み替える。

### ICW2 を書き間違えた場合の症状

M4-d で症状が出たときに PIC のオフセットを疑えるよう、対応表を残す。

| 書き間違いの種類 | 症状 |
|---|---|
| どこにも届かないオフセット | マスクを外して `sti` しても割り込みが来ない。「PIT の初期化ミス」「EOI 忘れ」と誤診しやすいが、実際はベクタが別を向いている |
| 意図と違うベクタ | 全 256 に入れた「予期しないベクタ」ハンドラが受けて停止する。報告されたベクタ番号が 0x20 でなければ ICW2 を疑う |
| 例外ベクタと重なる値 | `pic::validate_offsets` が弾くのでこの経路には入らない |

### ファームウェアが既に 0x20 を使っていたことによる追加のリスク

再マップ前の IMR を読んだところ 0xFF/0xFF（全マスク）だった。一方、
`qemu-debug.log` にはカーネル起動前に `v=20` が 674 件記録されている
（`docs/troubleshooting.md` 2026-07-21 の記録）。つまりファームウェアは
既にベクタ 0x20 でタイマを処理し、制御を渡す前にマスクしていた。

ここから、**今回の再マップは「同じ値への上書き」になっている可能性が高い**。
だとすれば ICW2 の書き間違いがあっても、ハードウェアが既に正しい状態に
あるせいで M4-d でも表面化しない場合がありうる。M4-d で「動いた」ことを
もって ICW2 の実装が正しいと結論づけないこと。判定するなら、意図的に
別のオフセット（例: 0x30-0x3F）へ再マップして、そのベクタで届くことを
確認する必要がある。

## Addendum 2（M4-d-1 完了時点）: 割り込みを有効化する経路

`sti` できる状態を作るところまでを M4-d-1 として切り出した。タイマは
まだ動かさない。「`sti` すること」と「割り込みが実際に来ること」を別々に
検証すると、問題が出たときに `sti` 周辺と IRQ 経路のどちらかへ切り分け
られる。

### 1. スタックの 16 バイト境界（罠 12 の導出）

チェックリスト 12 は「CPU が積む 5 個（エラーコード有りなら 6 個）と
スタブが push する GPR 数で境界がずれる」としか書いていなかった。M4-d-1 で
IRQ 経路を足す際に導出を明示したので記録する。

長モードでは、割り込み・例外の配送時に **CPU が RSP を 16 バイト境界へ
揃えてから**フレームを積む（Intel SDM Vol.3A 6.14.2）。したがって基準点は
必ず `RSP ≡ 0 (mod 16)` で、そこから積まれる量で入場時の剰余が決まる。

| 経路 | CPU が積む | 入場時 | スタブが積む | 共通ルーチンが積む | call 直前 |
|---|---|---|---|---|---|
| 例外（エラーコードなし） | 5 個 = 40 → ≡ 8 | **8** | ダミー EC + ベクタ = 16 | GPR 15 + CR2 = 128 | 8 |
| 例外（エラーコードあり） | 6 個 = 48 → ≡ 0 | **0** | ベクタのみ = 8 | GPR 15 + CR2 = 128 | 8 |
| IRQ | 5 個 = 40 → ≡ 8 | **8** | ベクタのみ = 8 | GPR 15 = 120 | 8 |

**入場時の剰余は一定ではない。** エラーコードを積む例外だけ `≡ 0` で、他は
`≡ 8` である。エラーコードなしの例外でダミーを push しているのは
`ExceptionContext` のレイアウトを揃えるためだが、結果として**剰余も揃える**
働きをしている（`8 − 16 ≡ 8`、`0 − 8 ≡ 8`）。3 経路とも `call` 直前が `≡ 8`
に収束するので、どれも `sub rsp, 8` で `≡ 0` にする。

**「エラーコードの有無が調整の要否を分ける」ではない。** 決めるのは
「入場時の剰余 − 積んだ総量」であり、たまたま 3 経路とも同じ結論になって
いるだけである。実際、設計時に「IRQ 側は GPR 15 個 + ベクタ = 128 バイトで
16 の倍数だから調整不要」と誤った結論を出しかけた。入場時が `≡ 0` でない
ため、これは成立しない。

### 2. 境界は手計算ではなく実測で検証する

上の導出が正しいことを、スタブが `call` 直前に**レジスタから読んだ RSP の
実値**をハンドラへ渡して検査する形にした（`idt::check_stack_alignment`）。

`ExceptionContext` のポインタから引き算して求める方法は採らない。それは
スタブの push 量という同じ仮定から導いた値であり、仮定が間違っていても
一致してしまう。**検査に見えて何も検査していない形**になる（本プロジェクト
で過去 2 回起きた誤り）。

検査が働くことは、`STACK_ALIGN_ADJUST` を 0 にする `misalign-test` feature で
確認した。例外経路・IRQ 経路の両方で発火して停止する。正常ビルドでは
例外テスト 4 種すべてで一度も発火しない。

### 3. M4-d-1 のメインループは `hlt` を使わない

§7 は「メインループは `hlt` で待つ」としており、そのための
`common::cpu::enable_interrupts_and_halt`（`sti; hlt` 隣接、罠 10）も
M4-d-1 で用意した。**しかし M4-d-1 でそれを使うと確実にハングする。**

`hlt` は次の割り込みまで CPU を止める。M4-d-1 は全 IRQ をマスクした状態で
`sti` するので、**起こしてくれるものが存在しない**。最初の `hlt` で永久に
止まり、周回カウンタもハートビートも期限判定も動かない。外から見た症状は
「`sti` した瞬間にハングした」であり、M4-d-1 で切り分けたい対象そのものと
区別がつかなくなる。検証段階として機能しない。

したがって M4-d-1 のループは**期限つきスピン**とする。`hlt` を使う本来の形は
起こしてくれるタイマが実在する M4-d-2 で初めて成立する。ビジーループを
避ける理由（TCG のログ肥大）は、割り込みが 1 件も起きない M4-d-1 では
発生しない。`-d int` は割り込みが起きたときだけ記録するためである。

### 4. §2 の「7 項目すべて」に対する明示的な例外

§2 は「1 つでも欠ければ `sti` せずに fail-fast する」と定めている。M4-d-1 の
時点では、7 項目のうち 2 つが「OK」でも「NG」でもなく**確かめる手段が無い**。
これを `true` に丸めると、検証していないものを検証済みとして数えることに
なるため、`CheckState { Verified, Failed, Unverifiable }` の 3 状態を型で
区別し、`Unverifiable` は `sti` を妨げないこととした。**これは §2 の原則に
対する明示的な例外である。**

| 項目 | 状態 | 理由と、いつ閉じるか |
|---|---|---|
| 4. PIC が 0x20-0x2F へ再マップ済み | Unverifiable | ICW2 が書き込み専用（Addendum 1）。M4-d-2 で最初のタイマ割り込みがベクタ 0x20 として届いた時点で Verified へ移す |
| 7. ハンドラが EOI を発行 | Unverifiable | M4-d-1 は IRQ をマスク解除しないため、応答すべき割り込みが存在しない。M4-d-2 で実装と同時に Verified へ移す |

**項目 4 の `Unverifiable` は項目 5 の成立に依存する。** 全 IRQ がマスク
されているからこそ、ICW2 が誤っていても何も配送されず害が生じない。
したがって実装は、**項目 5 が `Verified` でない場合、項目 4 を
`Unverifiable` ではなく `Failed` にする**。検証不能を許す根拠そのものが
失われるためである。型だけでは正当化されず、根拠は個別に示す必要がある。

### 5. IRQ 経路は例外経路から独立させる

例外ハンドラは戻らないため GPR を退避するだけで済むが、IRQ は中断した処理へ
**戻る**ので、退避したものを必ず復元しなければならない。復元を忘れると
割り込まれた側のレジスタが静かに壊れ、「割り込みと無関係な場所で不定期に
落ちる」という最も診断しにくい症状になる。

そのためスタブ表・共通ルーチン・コンテキスト型をすべて分けた。例外を
IRQ 化してはならない点も併せて記録する。#DE からそのまま戻れば同じ除算
命令を再実行して無限ループになる。戻れるのは、原因が外部にあり再実行の
必要がない IRQ だけである。

スタブ表が 2 系統になったため、**配置検証も 2 系統必要**である
（`check_stub_table` / `check_irq_stub_table`）。片方の検証がもう片方を
保証しない。

### 6. GPR 復元の検証は 13 本までしかできない

`int 0x20` をソフトウェア発行し、レジスタごとに異なる既知値が復元される
ことを確かめる（M4-b-2 の GPR ダンプ検証と同じ考え方）。ソフトウェア割り込みは
PIC を経由しないため、マスク状態と無関係にハンドラ経路だけを試せる。

**ただし rbx と rbp は検査できない。** LLVM がこの 2 本を内部的に予約して
おり、`asm!` のオペランドに指定するとコンパイルエラーになる。検査できるのは
残る 13 本である。

それでも検査の意味は保たれる。**順序の取り違え**は 13 個の相異なる値で
十分に捕まり、**本数の過不足**は RSP がずれて `iretq` の時点で即座に壊れる
（`iretq` は RSP が CPU の積んだフレーム先頭を指している必要があり、
1 バイトでもずれると制御が飛ぶ）。この 2 本だけが静かに壊れる経路は、
push と pop の両方でこの 2 本だけを対称に取り違えた場合に限られる。

## Addendum 3（M4-d-2 進行中）: タイマを動かす

**この Addendum は M4-d-2 の進行に伴って追記される。** M4-d-2 は 3 つの
コミットに分けており、確定した内容から順に書いている。途中の状態では
節が欠けているが、それは未着手を意味する。

### 1. GPR 復元の検証は PIC の範囲外（0x30）で行う

M4-d-1 では `int 0x20` で IRQ 経路を試していた。M4-d-2 で EOI を実装すると
これが衝突する。ソフトウェア割り込みは実在の IRQ ではないため、ハンドラが
無条件に EOI を送る作りだと**起きてもいない割り込みに応答する**ことになる。
PIC の ISR にビットが立っていない状態で EOI を送れば、優先度スタックの状態を
壊し、以降の本物の割り込みの扱いを狂わせうる。

**テスト専用ベクタを PIC の範囲外（0x30）へ移す。** `int 0x30` は 8259A を
経由せず CPU が直接 IDT を引くため、EOI の論理が一切絡まない。PIC 経由で
配送されないベクタなので、「EOI を送らないハンドラ」がそのまま正しい実装に
なる。検証の目的（GPR 復元と `iretq` 経路）はそのまま保てる。

IRQ スタイルのスタブ表は 17 本になった。「スタブの本数」と「PIC の IRQ の
本数」が一致しなくなったため、定数も `IRQ_STYLE_STUB_COUNT`（17）と
`PIC_IRQ_COUNT`（16）に分けてある。

却下した代替案:

- **実タイマでの検証に置き換える**: 「GPR が壊れた」ことは分かるが、壊れたのが
  スタブか PIT 設定か EOI かを切り分けられない。ハンドラ経路だけを単独で
  試せるという、この検証の価値そのものが失われる。却下。
- **ハンドラ側でソフトウェア割り込み由来かを判別して EOI を抑制する**:
  本番経路にテスト専用の分岐が入る。しかも「ソフトウェア割り込み由来か」を
  実行時に確実に判別する手段が無く、判別を誤れば**本物の割り込みへ EOI を
  送らない側へ倒れ、以降の割り込みが全部止まる**。テストのために本番経路の
  信頼性を下げることになる。却下。

PIC の範囲外へ移すのが、本番経路に一切手を入れずに済む唯一の案だった。

### 2. 「何も届かないこと」は増加分で判定する（0x30 移設後も必要）

テスト用ベクタを 0x30 へ移しても、`--interrupt-test enable-only` の判定を
絶対値へ戻すことはできない。割り込み回数カウンタは**全 256 ベクタを合計する**
ため、`int 0x30` で計上された 1 件は絶対値に残り続ける。0x20 が汚れなく
なっただけで、絶対値では「スピン中に届いた」と誤判定する構造は変わらない。
基準点を取って増加分を見る形を維持する。

**合計の対象を PIC の範囲（0x20-0x2F）だけに絞る案は採らない。** ここで見たい
のは「何も届かないこと」であって、対象は全ベクタである。とくに NMI
（ベクタ 2）は `cli` でマスクできず、全 IRQ をマスクした状態でも理論上は
到達しうる（§2.1）。範囲を絞ると、まさにその NMI が来ても検出できなくなる。

## Alternatives Considered

- **クリティカルセクションを最後に回す**（当初案の順序）: タイマを有効化した
  時点でヒープの `Locked<T>` の前提が崩れる。却下。
- **例外ハンドラとタイマを同時に入れる**: `sti` の時点で未検証の層が増える。
  例外は `IF` に依存せず検証できるという性質を使わない手はない。却下。
- **APIC を最初から使う**: SMP や高精度タイマには必要だが、ACPI を辿る必要が
  生じ、切り分け軸が増える。却下（M4 の後か M5 で）。
- **割り込みハンドラから直接ログを出す**: デッドロックはしないが、上記 5 の
  3 つの理由で却下。
- **コンソールをグローバル + ロックにする**: ハンドラから出力しない設計を
  採るため必要性が生じない。却下（M3-c の判断を維持）。
- **ガードページでスタックオーバーフローを検出する**: 確実だが
  `PageTableBuilder` にページ分割・アンマップを実装する必要があり、M4-a の
  範囲を大きく超える。却下（保留項目として記録）。

## Consequences
- `sti` を実行する時点で、GDT / TSS / スタック / IDT / 例外ハンドラ /
  排他制御がすべて実機検証済みになる。
- 例外ハンドラの検証が回帰チェックとして常設される（`--exception-test`）。
- 割り込みハンドラから出力しないため、ハンドラ内の再入・ロック・フラッシュの
  問題が構造的に発生しない。代わりに、割り込みで起きたことは**カウンタ越しに
  しか観測できない**。詳細が必要になったら、リングバッファへ記録して
  メインループで吐く形に広げる。
- `extern "x86-interrupt"` を使わないため、スタブは自前の naked asm になる。
  エラーコードの有無で 2 種類必要で、境界合わせも自分で行う。nightly へ
  移れば解消するが、ツールチェインを stable に固定する方針（M0）を優先する。
- ACPI と APIC は M4 の範囲外に残る。タイマ精度が問題になるか、SMP へ進む
  時点で再検討する。
