# 0063. パイプを先に置く——ストリームソケットと共通の核を、いちばん小さい面で確かめる段として

## Status

Accepted

## Date

2026-09-18

## Context

**W2で待機と起床が入った**（`ADR-0061` / `ADR-0062`）。**第1段階の残りはパイプ／unixドメインのストリームソケット／共有メモリとFDの受け渡し／画面と入力をユーザープロセスへ渡す経路である。**

**運用者の指示は「パイプを作る方針は維持するが、ソケットの絶対的な前提にはしない。検査用の利用者や実装の共通部分を踏まえて配置する」である。**

**Waylandが要求するものを読み直した**（`docs/wayland-inventory.md`）——**接続はUNIXドメインのストリームソケット、fdの受け渡しは`wl_shm.create_pool`の1つだけ、共有メモリは`mmap`、待ち方は要求しない（`epoll`は要らない）。** **パイプは要求されない。**

**共通部分を1つずつ確かめた**（コードを読んだ。2026-09-18）。

| 要るもの | パイプ | ストリームソケット | いまのZaytOS |
|---|---|---|---|
| 2本のRing 3を既定の起動で同時に走らせる | 要る | 要る | **無い**（`start_detached`も2本目のタスクの登録も`concurrent-test`の構成だけ） |
| バイトの通り道＋読む側の待ち＋書く側の起こし | 要る（片方向1本） | 要る（接続1つ = 片方向2本） | 待ちの仕組みはW2で在る |
| 最後の書き手が閉じたらEOF、読み手が居なければEPIPE | 要る | 要る | 無い |
| `File`の種類を1つ足す（`read`/`write`は中身で分岐する形が既に在る） | 要る | 要る | 形は在る |
| 親のfdを子へ渡す口（`spawn`は子の表を新しく作る） | 要る（`a \| b`） | 要らない（パスで繋ぐ。ただしWaylandは継承したfdも認める） | 無い |
| 名前（`bind`/`listen`/`accept`/`connect`） | 要らない | 要る | 無い |
| fdを別プロセスの表へ運ぶ（`SCM_RIGHTS`） | 要らない | 要る（`wl_shm`の1つ） | 無い |

## Decision

**4つ決めた**（運用者の承認。2026-09-18）。

1. **パイプを先に置く。** **ただし「ソケットの前提」としてではなく、両方に共通する核（同時に走る2本・待ち・EOF）を、名前もacceptもfdの運搬も無しで確かめる段として置く。** **先にソケットへ行くと「同時実行が壊れているのか、acceptが壊れているのか」を同じ段で分けることになる。**
2. **利用者はシェルの`|`である**（本番の利用者。Waylandは要求しないが、本番で使われる）。**検査用の組（書き手と読み手の専用プログラム）は作らない。** **判定と破壊は台本の族に置く**——**1項目あたり台本の族は11.3秒、`--shell-test`の族は59.6秒である**（実測。負荷の低い回）。**パイプの待ちは別の`Wait`なので、台本でも本物の待ちを通る**（W2-c-2で台本が通らないと分かったのは`read(0)`の待ちである）。
3. **刻みは、(a) 2本目のRing 3を既定の起動へ出す／(b)(c) 核と利用者を1段、である。** **(b)(c)は`waitpid`相当が入るので、設計を出し直してから実装する**（運用者の指摘）。
4. **`--full`の余裕を決めた**——**上限を120分から170分へ上げる**（規則は「いちばん遅い実測の1.6倍」のまま、実測を壁時計106.1分へ更新した）。**弱点は、遅くなったことを上限が知らせなくなることである。** **打鍵を見ない`--shell-test`の破壊を台本の族へ移す手をこの段の中で行う。** **2本に分ける手には契機を2つ立てた**（`docs/deferred-decisions.md`）——**負荷の高い回でも一度でも壁時計が120分を超えたとき、または330項目を超えたとき。**

### `|`には「2本起こして、両方の終了を待つ」が要る。**待つ口がまだ無い**（運用者の指摘）

**`spawn`は入れ子で、親が待つ形である**——**`echo`が終わるまで`cat`が起きず、固定長の輪が埋まって詰まる。** **`start_detached`は2本目を走らせられるが、終了を待てない**（回収しない）。**`echo hello | cat`は、両方が同時に走り、シェルが両方の終了を待ってプロンプトを戻す形である。**

**`waitpid`相当をどこに置くかは(b)(c)の設計で決める。** **`spawn`の形を変えるのか、別の口を足すのかも、そこで決める**——**W1-cで「`spawn`は変えない」と決めた理由（シェルという利用者が居る）は、いまも生きている。**

## (a) 2本目のRing 3を既定の起動へ出す——動いてよいものを先に書く（2026-09-18）

**振る舞いは増えない**——**既定の起動には`start_detached`を呼ぶ者が居ないので、2本目のタスクは登録されず、`pick_next`は選ばない**（`Uninitialized`は走行可能でない）。

**ただし「番地だけ」ではない見込みである。** **動いてよいものは次の3つだけである。**

1. **`.bss`が68 KiB増える**（ガードページ4 KiB＋スタック本体64 KiB。**W1-c-4で`concurrent-test`の構成で測った大きさ**）。**番地がそれに続いて動く。**
2. **カーネルのページテーブルの項が増える**——**68 KiB = 17ページぶん。** **うちガードページの1ページは`unmap`するので、プロセスごとの監査の側からは1つ少なく見える**（W2-aで+5と+4になったのと同じ形）。
3. **起動ログに行が2行増える**——**ガードページが手つかずだった行と、`unmap`した行**（W2-aのBSPアイドルと同じ`install_guard_page`）。

**これ以外が動いたら止める。**

### 測ったもの——見込みと1ずつずれた。**詰め物を数えていなかった**

| 動いてよいもの | 見込み | 実測 |
|---|---|---|
| `.bss` | +68 KiB（69,632バイト） | **+73,712バイト**（0x1c6820→0x1d8810） |
| 起動ログの行 | +2 | **+2**（562→564。ガードページが手つかず／`unmap`した） |
| カーネルのページテーブルの項 | +17 | **+18**（4219→4237） |
| プロセスごとの監査 | +16 | **+17**（2840→2857） |

**ずれは1ページで、原因は`align(4096)`の詰め物である**——**`RING3_TASK_STACK`はちょうど0x11000（68 KiB）で、その手前に4,072バイトの詰め物が入った**（`nm -S`で確かめた）。**`.bss`の終わりは0x8045a000から0x8046c000へ、ちょうど18ページ動いた。** **`DETACHED_REQUEST`（56バイト）は`.data`に入る。**

**これ以外の行は1行も動いていない**（番地を伏せた差分で確かめた）。**参照は録り直した。**

**見込みの立て方を直しておく**——**`align(4096)`の構造体を`.bss`へ足すときは、大きさではなく「前の記号の終わりから次の4 KiB境界まで」を足して数えること。**
