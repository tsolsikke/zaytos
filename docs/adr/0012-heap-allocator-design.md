# 0012. カーネルヒープに単一の連結リストアロケータを採用する

## Status
Accepted

## Date
2026-07-20

## Context
M2-e でカーネルヒープ（`alloc` クレートの有効化、`GlobalAlloc` 実装）を
導入するにあたり、アロケータ方式を検討した。将来の利用シナリオとして
以下が想定されている。

- M3: FHD 32bpp のダブルバッファリング用に、約 8MiB 規模の連続バッファを
  確保する可能性がある。
- M5: タスク管理で、小さなオブジェクトの頻繁な確保・解放が発生する。

検討した4案:

- **バンプ（アリーナ）**: ポインタを前進させるだけの最も単純な方式。
  個別の `dealloc` ができず（全体リセットのみ）、`Vec`/`String`/
  `format!` 等の一時確保が積み重なると回収不能になる。GlobalAlloc の
  バッキングとしては採用できない。
- **固定サイズブロック（サイズクラスごとの segregated free list）＋
  大きい確保は連結リストへフォールバック**: 小オブジェクトの
  alloc/dealloc が高速。当初これを候補としたが、以下の理由で見送った
  （詳細は Alternatives Considered 参照）。
- **連結リスト（フリーリスト、隣接結合あり）**: 空きブロックをアドレス
  順に管理し、隣接する空きを結合する。dealloc/realloc に対応でき、
  ヒープ全体が1つのプールとして機能するため断片化が起きても「合計は
  足りているのに大きい確保が失敗する」という事態が起きにくい。
- **バディシステム**: 断片化対策として理論上優れるが、実装・検証コストが
  最も高い。現時点でその複雑さに見合う負荷（実測された性能要件）はない。

## Decision
**連結リスト（フリーリスト、隣接結合あり）を単一のアロケータとして
採用する。** サイズクラス分割・バディ等の高度化は行わない。

### ヒープの大きさと供給元
- 初期化時に固定サイズのアリーナを1回だけ確保する。拡張機構は持たない。
  サイズは名前付き定数 `kernel::heap::DEFAULT_HEAP_FRAME_COUNT`（256
  フレーム = 1MiB）とし、`FrameAllocator::allocate_contiguous` で連続
  フレームとして切り出す。
- M3 で想定される大きな連続確保（フレームバッファ用バッファ等）は、
  **このヒープを経由せず** `FrameAllocator::allocate_contiguous` から
  直接取得する。ヒープに大きな単発確保を飲み込ませると、初期アリーナを
  巨大にするか拡張機構が必要になり複雑度が上がるため、範囲リスト方式で
  連続確保に強いフレームアロケータ側で素直に扱う方針とした。

### モジュール構成（純粋ロジックとハードウェア依存の分離）
- `kernel/src/heap/plan.rs`: 空きブロックへの配置・分割・結合の判断
  ロジック（純粋、`cargo test` で検証）。
- `kernel/src/heap/allocator.rs`: 侵入型連結リストと `GlobalAlloc`
  実装（unsafe、意図的に非テスト）。

侵入型連結リスト（実ポインタを空きブロックへ直接書き込む）を採用した
理由: ADR-0011（フレームアロケータ）では固定長配列を採用したが、あれは
「UEFI メモリマップの断片数」という起動時に決まる外部入力に上限が
あったため。ヒープの空きブロック数は alloc/dealloc の履歴次第で理論上
際限なく増えうるため、固定容量配列では現実的な上限を置けない。

### アラインメント処理
空き領域 `[region_start, region_end)` に対し、`max(requested_align,
header_align)` に切り上げた位置を `user_addr` とする。`region_start` と
実際のヘッダ位置の間に生じる前方の隙間は、別ブロックとして分離せず
`AllocatedBlockHeader.block_start` に絶対アドレスとして記録し、解放時に
隙間を含めた領域全体をまるごと空きリストへ戻す。末尾の余りは
`MIN_BLOCK_SIZE`（`FreeBlockNode` が書き込める最小サイズ）以上あれば
新しい空きブロックとして分離し、それ未満なら確保領域に含める。

### 破壊検出・診断
- `AllocatedBlockHeader` にマジック値・`block_start`・`block_size`・
  `requested_size` を持たせ、`dealloc` 時にマジック値と
  `requested_size` を検証する。不一致なら（二重解放・ヒープ破壊・
  不正ポインタとして）シリアルへエラーを出力し `panic!` する。
- 解放したブロックは毒値 (`0xDE`) で埋める（`heap-poison` feature、
  既定で有効）。**毒埋めは、空きリストのノード（`FreeBlockNode` の
  `size`/`next`）を書き込むより必ず前に行う。** 逆順にするとノード
  自身のリンク情報を毒値で潰してしまうため。
- メモリ不足時: `#[alloc_error_handler]` 属性は現在も unstable
  （rust-lang/rust#51540、本プロジェクトの固定ツールチェイン 1.97.1
  でコンパイルできないことを確認済み）であり、かつ Rust 1.68 以降は
  既定の alloc error handler が標準で提供されている（属性を書かなくても
  ビルドが通ることを確認済み）ため、これを利用する。`alloc` は失敗時、
  要求 size/align・現在の空きバイト数・空きブロック数をシリアルへ
  出力した上で `null` を返す。Rust core が既定ハンドラ経由で `panic!`
  を呼び、既存のパニックハンドラ（レジスタダンプ + halt、ADR-0004）に
  合流する。パニックハンドラ自体はシリアル出力のみで完結しヒープを
  使わないため、ヒープ枯渇時にパニックハンドラが確保を試みて無限
  再帰する心配はない。
- `layout.size() == 0` は `GlobalAlloc` の契約上呼び出されないはずだが
  （Rust core は ZST に対してこの関数を呼ばない）、万一渡された場合は
  契約違反として検出し `panic!` する。

### 同期
`Locked<T>`（`UnsafeCell` ラップの最小限のラッパー）を heap 専用に置く。
「シングルコア前提かつ kernel 全体で割り込みが常時禁止されている
（`docs/architecture.md` §6.5）」ことに依存して `unsafe impl Sync` して
おり、M4 で割り込みを有効化する際は実装（cli/sti 保存復元、または
スピンロック）を見直す必要がある（`docs/architecture.md` に記録済み）。

## Alternatives Considered

### サイズクラス方式（固定サイズブロック segregated free list）
一度は候補としたが、以下の理由で見送った。

- 選択理由が「M5 で小オブジェクトの churn が起きうる」という、
  まだ存在しない・計測もしていない性能要件に基づいていた。ZaytOS には
  現時点で性能要件がなく、「先回りの作り込み」に近い判断だった。
- サイズクラス間の断片化は堅牢性の問題として効いてくる。あるサイズ
  クラスに割り当てたブロックは他クラス/大きい確保へ戻せないため、
  「空きメモリは十分あるのに大きい確保だけ失敗する」という追いにくい
  不具合になりうる。連結リスト単体（隣接結合あり）なら、ヒープ全体が
  1つのプールとして機能するため、この問題は起きない。

**再検討条件**: 実際にプロファイリングや実機観測で、小オブジェクトの
確保/解放が性能上のボトルネックになっている、あるいは連結リストの
線形探索コストが問題になっていることが確認された時点で、別 ADR として
サイズクラス方式（または他の高速化）の追加を検討する。GlobalAlloc の
内側の実装であるため、呼び出し側（`Vec`/`Box`/`String` 等の利用コード）
を変更せずに差し替えられる。

### バンプ（アリーナ）
`dealloc` が機能しないため、GlobalAlloc の一般用途バッキングとしては
そもそも要件を満たさない。却下。

### バディシステム
断片化対策として理論上優れるが、実装・検証コストが最も高い。現時点で
その複雑さに見合う負荷（多数コアでの高頻度確保など）はない。過剰設計と
判断し却下。SMP 対応等で本格的な負荷が生じた際に再検討する。

## Consequences
- **固定サイズのヒープ（拡張機構なし）**: `DEFAULT_HEAP_FRAME_COUNT`
  (1MiB) を使い切ると `alloc` が診断ログ（要求 size/align、空きバイト数、
  空きブロック数）を出して `panic!` する（実機確認済み）。この時点で
  必要サイズを見積もり直し、定数を調整するか、拡張方式を別 ADR として
  検討する。今は先回りしない。
- **`Locked<T>` の `Sync` 実装が単一コア・割り込み禁止前提に依存する**:
  M4 で割り込みを有効化する際、この前提が崩れるため必ず見直す
  （`docs/architecture.md` §6.5 に記録済み）。
- **線形探索の連結リスト**: 空きブロック数が多いと `alloc`/`dealloc` の
  探索コストが線形に増える。現時点（ヒープ1MiB、起動直後の限定的な
  用途）では問題にならないと判断している。M5 でタスク管理による churn
  が増えた際に、実測に基づいて再検討する（サイズクラス方式の再検討
  条件と同じ）。
- **大きな連続確保はヒープを経由しない**という方針を採ったため、M3 の
  フレームバッファ用バッファは `FrameAllocator::allocate_contiguous`
  を直接使う設計になる（M2-e の実装範囲外、今後の実装で踏襲する）。
- 実機確認済み: `Vec`/`Box`/`String` の確保・追記・解放（コールセック
  後にヒープ全体が1ブロックへ結合され直すことも確認）、二重解放時の
  マジック検証による `panic!`（確認後 revert）、ヒープ枯渇時の診断
  ログ出力 + 既定 OOM ハンドラ経由の `panic!` 合流（確認後 revert）。
