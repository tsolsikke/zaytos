# 0012. カーネルヒープに単一の連結リストアロケータを採用する

## Status
Accepted

## Date
2026-07-20

## Context
M2-eでカーネルヒープ（`alloc`クレートの有効化、`GlobalAlloc`実装）を導入するにあたり、アロケータ方式を検討した。
将来の利用シナリオとして以下が想定されている。

- M3: FHD 32bppのダブルバッファリング用に、約8MiB規模の連続バッファを確保する可能性がある。
- M5: タスク管理で、小さなオブジェクトの頻繁な確保・解放が発生する。

検討した4案:

- **バンプ（アリーナ）**: ポインタを前進させるだけの最も単純な方式。個別の`dealloc`ができず（全体リセットのみ）、`Vec`/`String`/`format!`等の一時確保が積み重なると回収不能になる。GlobalAllocのバッキングとしては採用できない。
- 固定サイズブロック（サイズクラスごとのsegregated free list）＋大きい確保は連結リストへフォールバック: 小オブジェクトのalloc/deallocが高速。当初これを候補としたが、以下の理由で見送った（詳細はAlternatives Considered参照）。
- **連結リスト（フリーリスト、隣接結合あり）**: 空きブロックをアドレス順に管理し、隣接する空きを結合する。dealloc/reallocに対応でき、ヒープ全体が1つのプールとして機能するため断片化が起きても「合計は足りているのに大きい確保が失敗する」という事態が起きにくい。
- **バディシステム**: 断片化対策として理論上優れるが、実装・検証コストが最も高い。現時点でその複雑さに見合う負荷（実測された性能要件）はない。

## Decision
連結リスト（フリーリスト、隣接結合あり）を単一のアロケータとして採用する。
サイズクラス分割・バディ等の高度化は行わない。

### ヒープの大きさと供給元
- 初期化時に固定サイズのアリーナを1回だけ確保する。拡張機構は持たない。サイズは名前付き定数`kernel::heap::DEFAULT_HEAP_FRAME_COUNT`（256フレーム = 1MiB）とし、`FrameAllocator::allocate_contiguous`で連続フレームとして切り出す。
- M3で想定される大きな連続確保（フレームバッファ用バッファ等）は、 **このヒープを経由せず** `FrameAllocator::allocate_contiguous`から直接取得する。ヒープに大きな単発確保を飲み込ませると、初期アリーナを巨大にするか拡張機構が必要になり複雑度が上がるため、範囲リスト方式で連続確保に強いフレームアロケータ側で素直に扱う方針とした。

### モジュール構成（純粋ロジックとハードウェア依存の分離）
- `kernel/src/heap/plan.rs`: 空きブロックへの配置・分割・結合の判断ロジック（純粋、`cargo test`で検証）。
- `kernel/src/heap/allocator.rs`: 侵入型連結リストと`GlobalAlloc`実装（unsafe、意図的に非テスト）。

侵入型連結リスト（実ポインタを空きブロックへ直接書き込む）を採用した理由: ADR-0011（フレームアロケータ）では固定長配列を採用したが、あれは「UEFIメモリマップの断片数」という起動時に決まる外部入力に上限があったため。
ヒープの空きブロック数はalloc/deallocの履歴次第で理論上際限なく増えうるため、固定容量配列では現実的な上限を置けない。

### アラインメント処理
空き領域`[region_start, region_end)`に対し、`max(requested_align, header_align)`に切り上げた位置を`user_addr`とする。
`region_start`と実際のヘッダ位置の間に生じる前方の隙間は、別ブロックとして分離せず`AllocatedBlockHeader.block_start`に絶対アドレスとして記録し、解放時に隙間を含めた領域全体をまるごと空きリストへ戻す。
末尾の余りは`MIN_BLOCK_SIZE`（`FreeBlockNode`が書き込める最小サイズ）以上あれば新しい空きブロックとして分離し、それ未満なら確保領域に含める。

### 破壊検出・診断
- `AllocatedBlockHeader`にマジック値・`block_start`・`block_size`・`requested_size`を持たせ、`dealloc`時にマジック値と`requested_size`を検証する。不一致なら（二重解放・ヒープ破壊・不正ポインタとして）シリアルへエラーを出力し`panic!`する。
- 解放したブロックは毒値(`0xDE`)で埋める（`heap-poison` feature、既定で有効）。毒埋めは、空きリストのノード（`FreeBlockNode`の`size`/`next`）を書き込むより必ず前に行う。 逆順にするとノード自身のリンク情報を毒値で潰してしまうため。
- メモリ不足時: `#[alloc_error_handler]`属性は現在もunstable（rust-lang/rust#51540、本プロジェクトの固定ツールチェイン1.97.1でコンパイルできないことを確認済み）であり、かつRust 1.68以降は既定のalloc error handlerが標準で提供されている（属性を書かなくてもビルドが通ることを確認済み）ため、これを利用する。`alloc`は失敗時、要求size/align・現在の空きバイト数・空きブロック数をシリアルへ出力した上で`null`を返す。Rust coreが既定ハンドラ経由で`panic!`を呼び、既存のパニックハンドラ（レジスタダンプ + halt、ADR-0004）に合流する。パニックハンドラ自体はシリアル出力のみで完結しヒープを使わないため、ヒープ枯渇時にパニックハンドラが確保を試みて無限再帰する心配はない。
- `layout.size() == 0`は`GlobalAlloc`の契約上呼び出されないはずだが（Rust coreはZSTに対してこの関数を呼ばない）、万一渡された場合は契約違反として検出し`panic!`する。

### 同期
`Locked<T>`（`UnsafeCell`ラップの最小限のラッパー）をheap専用に置く。
「シングルコア前提かつkernel全体で割り込みが常時禁止されている（`docs/architecture.md` §6.5）」ことに依存して`unsafe impl Sync`しており、M4で割り込みを有効化する際は実装（cli/sti保存復元、またはスピンロック）を見直す必要がある（`docs/architecture.md`に記録済み）。

## Alternatives Considered

### サイズクラス方式（固定サイズブロックsegregated free list）
一度は候補としたが、以下の理由で見送った。

- 選択理由が「M5で小オブジェクトのchurnが起きうる」という、まだ存在しない・計測もしていない性能要件に基づいていた。ZaytOSには現時点で性能要件がなく、「先回りの作り込み」に近い判断だった。
- サイズクラス間の断片化は堅牢性の問題として効いてくる。あるサイズクラスに割り当てたブロックは他クラス/大きい確保へ戻せないため、「空きメモリは十分あるのに大きい確保だけ失敗する」という追いにくい不具合になりうる。連結リスト単体（隣接結合あり）なら、ヒープ全体が1つのプールとして機能するため、この問題は起きない。

**再検討条件**: 実際にプロファイリングや実機観測で、小オブジェクトの確保/解放が性能上のボトルネックになっている、あるいは連結リストの線形探索コストが問題になっていることが確認された時点で、別ADRとしてサイズクラス方式（または他の高速化）の追加を検討する。
GlobalAllocの内側の実装であるため、呼び出し側（`Vec`/`Box`/`String`等の利用コード）を変更せずに差し替えられる。

### バンプ（アリーナ）
`dealloc`が機能しないため、GlobalAllocの一般用途バッキングとしてはそもそも要件を満たさない。
却下。

### バディシステム
断片化対策として理論上優れるが、実装・検証コストが最も高い。
現時点でその複雑さに見合う負荷（多数コアでの高頻度確保など）はない。
過剰設計と判断し却下。
SMP対応等で本格的な負荷が生じた際に再検討する。

## Consequences
- **固定サイズのヒープ（拡張機構なし）**: `DEFAULT_HEAP_FRAME_COUNT` (1MiB)を使い切ると`alloc`が診断ログ（要求size/align、空きバイト数、空きブロック数）を出して`panic!`する（実機確認済み）。この時点で必要サイズを見積もり直し、定数を調整するか、拡張方式を別ADRとして検討する。今は先回りしない。
- `Locked<T>`の`Sync`実装が単一コア・割り込み禁止前提に依存する: M4で割り込みを有効化する際、この前提が崩れるため必ず見直す（`docs/architecture.md` §6.5に記録済み）。
- **線形探索の連結リスト**: 空きブロック数が多いと`alloc`/`dealloc`の探索コストが線形に増える。現時点（ヒープ1MiB、起動直後の限定的な用途）では問題にならないと判断している。M5でタスク管理によるchurnが増えた際に、実測に基づいて再検討する（サイズクラス方式の再検討条件と同じ）。
- **大きな連続確保はヒープを経由しない**という方針を採ったため、M3のフレームバッファ用バッファは`FrameAllocator::allocate_contiguous`を直接使う設計になる（M2-eの実装範囲外、今後の実装で踏襲する）。
- 実機確認済み: `Vec`/`Box`/`String`の確保・追記・解放（コールセック後にヒープ全体が1ブロックへ結合され直すことも確認）、二重解放時のマジック検証による`panic!`（確認後revert）、ヒープ枯渇時の診断ログ出力 + 既定OOMハンドラ経由の`panic!`合流（確認後revert）。

## Addendum（2026-07-21、M4-c-2で`Locked<T>`の前提を差し替えた）

M2-e時点の`Locked<T>`は`unsafe impl Sync`の根拠を「kernel全体で割り込みが常時禁止されている」に置いていた。
M4-dで`sti`するとこの前提は崩れるため、M4-c-2で「取得中は割り込み禁止」へ差し替えた。

### なぜ新しい前提で安全か

シングルコアでデータ競合が起きるのは「実行中のコードを割り込みが中断し、そのハンドラが同じデータへ触る」場合だけである。
`lock()`はガードを返す前に`InterruptGuard`で割り込みを禁止し、ガードが生きている間その状態が続く。
したがって**保持区間中に割り込みハンドラが走ることはあり得ず**、排他が保証される。
SMPでは別コアが同時にアクセスしうるためこの論法は崩れるが、それはADR-0002のスコープ外であり、その時点でスピンロックへ差し替える。

### 変更点

- `Locked<T>`を`common::critical`へ移した（ヒープ以外からも使えるように）。
- `lock()`は`&mut T`ではなく`LockGuard<'_, T>`を返す。ガードが`InterruptGuard`を保持し、Dropで割り込みを復元する。
- **二重取得検出**を追加した。`AtomicBool`の取得中フラグを持ち、保持したまま再取得すると検出する。シングルコアかつ取得中は割り込み禁止なので通常は起きないが、「同じロックを保持したまま同じ実行文脈が再度`lock`を呼ぶ」というコードのバグでは起こりうる。放置すると無言のデータ競合になる。 **panicではなくシリアルへ直接書いて停止する**。ヒープのロックで起きた場合、panic経路が確保を試みると事態が悪化するため（ヒープ枯渇時の無限再帰と同じ懸念）。
- `LockGuard`の**フィールド宣言順に意味がある**。Dropでフラグをクリアしてから、最後のフィールドである`interrupts`が落ちて割り込みを復元する。順序が逆だと、まだ`&mut T`が生きているうちに割り込みが有効化され、ハンドラが同じデータへ触れば競合する。このdrop順はホストテストで固定した。

### 検証

- `--critical-test double-lock`で、二重取得が実際に検出されて停止することを確認した（検出をすり抜けた場合に出る目印が現れないことも確認）。
- ロック保持中にIF=0、解放後に元の状態へ戻ることを実RFLAGSで確認した。
- 既存のヒープスモークテスト（Vec / Box / String）が引き続き動作する。

### ホストテストの限界

`cli`/`sti`は特権命令（ring 0）であり、ユーザー空間で実行すると #GPになる。
そのため`Locked::lock()`自体はホスト`cargo test`から呼べない。
ホストで検証できるのは、フィールドのdrop順と`should_restore_interrupts`の判断まで。
実動作は実機で確認する。
