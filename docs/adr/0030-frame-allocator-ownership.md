# 0030. フレームアロケータをカーネル全体で1つの持ち物にし、貸し出しで渡す

## Status
Accepted

## Date
2026-08-13

## Context

フレームアロケータは`kernel_main`のローカルである。
そこから`&mut FrameAllocator`で明示的に配り回しており、**14の関数が引数として受け取り、17か所が渡している。**

**これは意図された形である。** グローバルにしていないから、**誰がフレームを確保できるかがシグネチャに出る。**

S11で`spawn`を書く段になって、この形では届かない場所が出た。
**`syscall::dispatch`が持っているのは`number`・`args`・`pml4_phys`・`direct_map`の4つだけ**で、
アロケータもロガーも無い。`spawn`は新しいアドレス空間を作るので、
**最初に要求するのがそのアロケータである。**

**`spawn`だけの話ではない。** S12（ext2の書き込み）はブロックを確保し、
S13（DMA）は物理連続の確保を要求する。**どちらも「システムコールの中でフレームを取る」形になる。**

## Decision

**フレームアロケータをカーネル全体で1つの持ち物にする。** 実体を`kernel::frame_allocator`の
`static`に置き、**借り手には`&'static mut`を渡す。**

```text
let allocator = frame_allocator::take()?;   // 借りる（コピーは起きない）
... &mut FrameAllocator として今までどおり使う ...
frame_allocator::give_back(allocator);      // 返す
```

**値では渡さない。** この型は**4104バイト**（`FrameRange`が16バイト、`CAP`が256）で、
**値で返す形にしたらカーネルスタックがガードページへ落ちた**（実測。下記）。

**排他は`AtomicBool`の`compare_exchange`が持つ。**
**成功した者だけが`&mut`を受け取る。** `load`してから`store`する形にはしない——
**2つの実行文脈が同時に通り抜けられる。** いまは単一コアの直線なので実害は出ないが、
**S13でI/O待ちが入り、割り込みハンドラから取る経路ができた時点で壊れる。**

**貸し出し中は2人目が`None`を受け取り、自分で判断する**（`spawn`なら`-EAGAIN`）。

**`&mut FrameAllocator`を受け取る14の関数は、そのままである。** 変わるのは
「どこで取り出して、どこで返すか」だけである。

**Ring 3へ落ちる前に返す。** 写像はすべて遠征の前に済むので、
**遠征の間はアロケータが`static`に在り、システムコールから取り出せる。**

## Alternatives Considered

- **値で貸し出す（`take()`が`FrameAllocator`を返す）**: 却下。**実装して実測で壊れた。**
  **この型は4104バイトである**（`FrameRange`が16バイト × `CAP`が256 = 4096、+ `range_count`が8）。借り手のローカルに乗り、返すときにもう一度動く。
  `load_user_program`は写像の間ずっとこれを抱えるので、**カーネルスタックがガードページを踏んだ**——
  観測は`#PF`（error code 0x2、not present・write・supervisor）で、
  **`rsp=0xffffffff8041abf0`がガードページ`0xffffffff8041a000`の中にあった**
  （スタックは`0x41b000..0x42b000`）。
  **`deferred-decisions.md`の「大きなスタック配列とガード幅」が言う前提**——
  「スタック上の単一の物が4096バイト以下」——**を8バイト超えている。**
  **ガードページは静かに壊れず、踏んだ瞬間に止めた。**

  **この数値をここに残すのは、次に同じ形を考える人が同じ検討をやり直さずに済むためである。**
  **`CAP`を増やせば比例して増える**ので、**「値で渡す」は`CAP`が256未満に下がらない限り成り立たない。**

- **ロックを保持したまま使う（`with(|allocator| ...)`）**: 却下。
  **`Locked<T>`は保持している間、割り込みを禁止する。**
  現在の呼び出し側には**Ring 3の遠征を含む長い区間**があり
  （`load_user_program`は写像してから`ring3::enter`する）、
  **そこを包むと遠征の間ずっと割り込みが止まる。タイマーが動かない。**
  **短い区間だけを包む形にするには、`&mut FrameAllocator`を取る14の関数を
  すべて作り替えることになる**——確保の場所まで降ろす必要がある。

- **生ポインタを`static`へ据える（`set_nest_target`と同じ形）**: 却下。最も小さいが、
  **寿命の保証が型から消える。** アロケータは`kernel_main`のローカルなので、
  「いつまで有効か」を型で言えなくなる。**`BklGuard`や`UserSlice`で
  「証明を型で持つ」形を積み上げてきたのと逆行する。**

- **ローダーと`USER_PROGRAMS`をlibへ移す**: 却下（単独では）。像の出所は既にlibにある
  （`vfs::FS_IMAGE`）が、**移せばアロケータの所有も一緒に動く**ので、
  結局この決定を含む。**順序として、所有を先に決める。**

- **現状維持（`spawn`をカーネルの直線上からだけ呼ぶ）**: 却下。
  **シェルが子を起こせないなら、それはシェルではない。**

## Consequences

- **失うもの——「誰が確保できるかがシグネチャに出る」が弱まる。**
  `take()`はどこからでも呼べる。**貸し出し中は`static`が空になる**ので、
  「同時に2人が持つ」ことは防げるが、**「取ってよい場所か」は型では言えない。**
  代わりに**`take()`の`Option`が「今は借りられない」を呼び出し側に判断させる。**

- **ロックの順序は増えない。** `bkl.rs`は「BKL → `Locked<T>`の一方向だけ」と書いているが、
  **この設計は`Locked<T>`を使わない**（旗だけである）。**葉が1つも増えない。**
  **「アロケータのロックを保持したままBKLを取る」状態が、そもそも作れない。**
  **禁じている向きを、守るのではなく作れなくしている**
  （`verification-coverage.md`の「選べなくする」の5件目）。

- **`unsafe`が1つ増える。** `static`から`&mut`を作る。
  **`SAFETY`が名指しするのは「旗が排他を保証する」ではなく
  「`compare_exchange`が成功した者だけが`&mut`を持つ」である**——保証している機構を書く。

- **割り込みが止まらない。** `Locked<T>`を使わないので、借りている間も割り込みは動く。
  **当初`Locked`を選んだ理由（排他）は旗が担い、代償（割り込み禁止）だけが消えた。**

- **返し忘れが新しい失敗の形になる。** 借りたまま戻らない経路があると、以後の確保がすべて
  `None`になる。**`Drop`で自動的に返す形は採らない**——**返す位置を明示するほうが、
  どこで返しているかが読める。**
  **`give_back`が`&'static mut`を受け取るので、返した後に使う形は型で作れない。**

  **検出は会計だけに頼らない。** 起動時の会計（消えたフレーム数と隔離へ入れた枚数の一致）は
  **間接的にしか捕まえない**——そして**`take()`が`None`を返したとき、
  「誰かが正当に使っている」のか「返し忘れ」なのかが区別できない。**

  **起動シーケンスは単一コアの直線なので、`take()`が`None`を返すこと自体が異常である**
  （遠征の中から呼ばれる場合を除く）。**貸し借りの回数を数え、判定行に出す。**
  一致していれば、**返し忘れはその時点で無い。**

- **S12とS13で同じ道が使える。** 「システムコールの中でフレームを取る」が一度通れば、
  書き込みもDMAも同じ形になる。
