# 0030. フレームアロケータをカーネル全体で1つの持ち物にし、貸し出しで渡す

## Status
Accepted

## Date
2026-08-13

## Context

フレームアロケータは`kernel_main`のローカルである。
そこから`&mut FrameAllocator`で明示的に配り回しており、**14の関数が引数として受け取り、17か所が渡している。**

**これは意図された形である。** グローバルにしていないから、**誰がフレームを確保できるかがシグネチャに出る。**

S11で`spawn`を書く段になって、この形では届かない場所が出た。
**`syscall::dispatch`が持っているのは`number`・`args`・`pml4_phys`・`direct_map`の4つだけ**で、
アロケータもロガーも無い。`spawn`は新しいアドレス空間を作るので、
**最初に要求するのがそのアロケータである。**

**`spawn`だけの話ではない。** S12（ext2の書き込み）はブロックを確保し、
S13（DMA）は物理連続の確保を要求する。**どちらも「システムコールの中でフレームを取る」形になる。**

## Decision

**フレームアロケータをカーネル全体で1つの持ち物にする。** `common::critical::Locked`で包み、
`kernel::frame_allocator`の`static`に置く。

**渡し方は「貸し出し」にする。** 借り手はアロケータを**取り出して**使い、**返す。**

```text
let mut allocator = frame_allocator::take()?;   // 取り出す（ロックはここで離す）
... &mut allocator として今までどおり使う ...
frame_allocator::give_back(allocator);          // 返す
```

**取り出している間、`static`は空である。** 二重に取り出すことはできない
（2人目は`None`を受け取り、自分で判断する。`spawn`なら`-EAGAIN`）。

**`&mut FrameAllocator`を受け取る14の関数は、そのままである。** 変わるのは
「どこで取り出して、どこで返すか」だけである。

**Ring 3へ落ちる前に返す。** 写像はすべて遠征の前に済むので、
**遠征の間はアロケータが`static`に在り、システムコールから取り出せる。**

## Alternatives Considered

- **ロックを保持したまま使う（`with(|allocator| ...)`）**: 却下。
  **`Locked<T>`は保持している間、割り込みを禁止する。**
  現在の呼び出し側には**Ring 3の遠征を含む長い区間**があり
  （`load_user_program`は写像してから`ring3::enter`する）、
  **そこを包むと遠征の間ずっと割り込みが止まる。タイマーが動かない。**
  **短い区間だけを包む形にするには、`&mut FrameAllocator`を取る14の関数を
  すべて作り替えることになる**——確保の場所まで降ろす必要がある。

- **生ポインタを`static`へ据える（`set_nest_target`と同じ形）**: 却下。最も小さいが、
  **寿命の保証が型から消える。** アロケータは`kernel_main`のローカルなので、
  「いつまで有効か」を型で言えなくなる。**`BklGuard`や`UserSlice`で
  「証明を型で持つ」形を積み上げてきたのと逆行する。**

- **ローダーと`USER_PROGRAMS`をlibへ移す**: 却下（単独では）。像の出所は既にlibにある
  （`vfs::FS_IMAGE`）が、**移せばアロケータの所有も一緒に動く**ので、
  結局この決定を含む。**順序として、所有を先に決める。**

- **現状維持（`spawn`をカーネルの直線上からだけ呼ぶ）**: 却下。
  **シェルが子を起こせないなら、それはシェルではない。**

## Consequences

- **失うもの——「誰が確保できるかがシグネチャに出る」が弱まる。**
  `take()`はどこからでも呼べる。**貸し出し中は`static`が空になる**ので、
  「同時に2人が持つ」ことは防げるが、**「取ってよい場所か」は型では言えない。**
  代わりに**`take()`の`Option`が「今は借りられない」を呼び出し側に判断させる。**

- **ロックの順序に1つ増える。** `bkl.rs`は「BKL → `Locked<T>`の一方向だけ」と書いており、
  **`Locked<FrameAllocator>`はその葉に加わる。**
  **現在の経路は向きが合っている**（実コードで確かめた)——
  `load_user_program`はBKLを取ってから`destroy`を呼び、`destroy`はアロケータを取らない。
  隔離からの返却（`release_retired`）はアロケータを取るが、**BKLを保持した側から呼ぶ形である。**
  **逆向き（アロケータを借りたままBKLを取る）は作らない。**
  **`take()`はロックを保持し続けないので、そもそも「保持したままBKLを取る」状態にならない**
  ——これが貸し出し方式の副次的な利点である。

- **返し忘れが新しい失敗の形になる。** 借りたまま戻らない経路があると、以後の確保がすべて
  `None`になる。**`Drop`で自動的に返す形は採らない**——アロケータは値として移動するので、
  **返す位置を明示するほうが、どこで返しているかが読める。**

  **検出は会計だけに頼らない。** 起動時の会計（消えたフレーム数と隔離へ入れた枚数の一致）は
  **間接的にしか捕まえない**——そして**`take()`が`None`を返したとき、
  「誰かが正当に使っている」のか「返し忘れ」なのかが区別できない。**

  **起動シーケンスは単一コアの直線なので、`take()`が`None`を返すこと自体が異常である**
  （遠征の中から呼ばれる場合を除く）。**貸し借りの回数を数え、判定行に出す。**
  一致していれば、**返し忘れはその時点で無い。**

- **S12とS13で同じ道が使える。** 「システムコールの中でフレームを取る」が一度通れば、
  書き込みもDMAも同じ形になる。
