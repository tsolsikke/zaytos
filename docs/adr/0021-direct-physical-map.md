# 0021. 物理メモリへのアクセスは direct physical map で行う

## Status
Accepted

## Date
2026-07-21

## Context

higher-half 移行（ADR-0009 の見直し）で恒等マッピングを外すと、
**「まだどこにもマップされていないフレームに書き込む」という循環**が生じる。

- ページテーブル操作: 新しく確保した PT フレームをゼロ埋めし 512 エントリを
  書くには、そのフレームが仮想アドレスから見えていなければならない
- 新規フレームのゼロ埋め（ヒープ拡張、タスクスタック、ユーザーページ）
- CoW のページコピー、ELF をプロセスのフレームへ読み込む操作（M5-f）

恒等マッピングはこれらを自明に解いていた。外した後にどう解くかは、
`PhysAddr` / `VirtAddr` 型分離の API の形（`phys_to_virt` が失敗しうるか）を
決めるため、実装より先に決定する。

## Decision

**全物理メモリを固定オフセットで高位仮想アドレスへ写す（direct physical map）。**

```text
phys_to_virt(p) = DIRECT_MAP_BASE + p          （失敗しない。単なる加算）
virt_to_phys(v) = v - DIRECT_MAP_BASE           （範囲内のときのみ Some）
```

### 仮想アドレスレイアウト（案）

| 範囲 | 用途 |
|---|---|
| `0x0000_0000_0000_0000` – `0x0000_7FFF_FFFF_FFFF` | ユーザー空間（128 TiB） |
| `0xFFFF_8000_0000_0000` – | **direct physical map**（物理 0 が起点） |
| `0xFFFF_FFFF_8000_0000` – | カーネルイメージ（上位 2 GiB。`code-model=kernel` の要求） |

### 覆う範囲は定数で決めない

「0〜4 GiB」のような固定値をハードコードしない。**現在の実測**（RAM 256 MiB、
フレームバッファが物理 2 GiB）では 4 GiB で足りるが、別構成では静かに破綻する。
実際、過去に `phys_start=0xfd00000000`（約 1 TiB）の PCI MMIO 予約領域が
観測されている。

- 覆う範囲は **`memory_map::classify()` が返すマップ対象の最大物理アドレス**
  から導出する
- 起動時に「マップすべき全範囲が direct map の範囲内に収まる」ことを検証し、
  外れたら fail-fast する（不変条件を起動時に検証する、これまでの作法）

### キャッシュ属性のエイリアスを作らない

**同じ物理ページを異なるキャッシュ属性で 2 箇所にマップしてはならない**
（Intel SDM の要求）。フレームバッファは PCD でマップしており、direct map が
同じ物理をキャッシュ有効で写すと属性が衝突する。

direct map の属性は既存の `classify()` の `cacheable` 判定をそのまま使う。
範囲ごとの属性は既に計算・テスト済みであり、`Unmapped` と判定される穴
（`EfiReservedMemoryType`）も direct map 側で同じく穴にする。

### NX は当面立てない

direct map は本来 NX（実行不可）にすべきだが、現在 `EFER.NXE` を有効化して
いない。**NXE 無効のまま NX ビット（bit 63）を立てると予約ビット違反の
ページフォルトになる**（ADR-0018 で記録済み）。NXE の有効化は独立の保留項目
とする（`deferred-decisions.md`）。

### 移行には二重マッピングと高位への飛び移りが要る

CR3 を切り替える瞬間、**実行中のコード自身がマップされ続けていなければ
ならない**。現在コードは低位（`0x100000`）で動いているため、高位だけの
テーブルへ単純に切り替えると、切り替え命令の次で落ちる。手順は次のとおり。

1. 新テーブルに**恒等マッピングと高位マッピングの両方**を作る
2. CR3 を切り替える（この時点では低位で実行を継続している）
3. 高位アドレスへジャンプする
4. その後に恒等マッピングを外す（M5-a-2 の `unmap_page` を使う）

M2-d の CR3 切り替えと同じ作法（切り替え前後で到達性をログに出す、必須領域を
実値で検証する）を適用する。higher-half 移行の段階分割では、この手順を
明示的な段階として扱う。

### MAXPHYADDR は観測のみ

`PhysAddr::new()` はビット 51 超の値を弾く（ページテーブルエントリの
アドレス欄がビット 51 までなので、符号化として十分）。CPUID の実測値では
**ゲートしない**。MAXPHYADDR は環境で変わり（QEMU 既定 40、実機 39〜52）、
構築時にゲートすると同じコードが環境によって通ったり弾かれたりして、
テストの再現性が落ちる。起動時に CPUID から読んで**ログに出すだけ**とする。

## Alternatives Considered

- **再帰マッピング（PML4 の 1 エントリを自分自身へ向ける）**: 消費が
  仮想 512 GiB のみ、追加フレーム 0 と最も安い。しかし**解けるのは
  ページテーブルへのアクセスだけ**で、フレームのゼロ埋めも CoW のコピーも
  解けない。結局そこは別方式を併用することになり、物理アクセスの方式が
  2 つ併存する。M5-f で CR3 を切り替えるたびに再帰エントリの整合も要る。却下。
- **一時マッピング（操作のたびにマップして解除）**: 消費は数ページと最小。
  しかし `phys_to_virt` が RAII ガードを返す形になり、**寿命の扱いが API 全体に
  伝播する**。アクセスのたびに `invlpg` が要る。さらに M5-d でプリエンプションが
  入ると、**一時スロットをタスクごとに持たなければ切り替え先のタスクが同じ
  スロットを上書きする**。「しばらく動いた後に突然壊れる」形の典型。却下。

## Consequences

- `phys_to_virt` は**失敗しない単なる加算**として成立する。型分離（T-1）の
  API に `Option` も RAII も持ち込まずに済む。
- 恒等マッピングからの移行は **`DIRECT_MAP_BASE` が 0 から定数に変わるだけ**。
  型分離を恒等のまま先に入れておけば、移行時の差分はこの定数 1 個に集約される。
- コスト（現在の実測に対して）: 仮想空間は物理と同量（4 GiB 分で、上半分
  128 TiB に対して無視できる）。ページテーブルは 2MiB ページで写して
  PDPT 1 枚 + PD 4 枚 = **約 20 KiB**。RAM 64 GiB でも 260 KiB に収まる。
- direct map の分だけ「全物理メモリがカーネルから常時見える」状態になる。
  分離や保護の観点では恒等マッピングと同じ性質であり、悪化はしない。
- 実装の詳細（実際のテーブル構築、検証手順、移行の実測）は、higher-half
  移行に着手した時点で **Addendum としてこの ADR に追記する**。
