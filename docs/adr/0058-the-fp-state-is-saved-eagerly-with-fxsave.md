# 0058. FPの状態は`fxsave`で常時退避する

## Status

Proposed

## Date

2026-09-07

## Context

**外のCを持ってくる段（B）で、`stb_truetype`を移す**（`docs/roadmap.md`の「CB. 外のCを持ってくる」）。
**浮動小数点は避けられない**——**`-mno-sse`で建てると`SSE register return with SSE disabled`で
コンパイルが止まる**（実測。2026-09-06。`gcc` 13.3.0）。**したがってユーザー空間でSSEを使う。**

**現在地は実測である**（2026-09-06から07）。

- **カーネルとbootloaderのXMM命令は0個である**（`objdump -d | grep -c xmm`）。
  **`x86_64-unknown-none`が持つ`target_feature`は`fxsr`だけで、SSE/SSE2は無い**（soft-float）。
- **`fxsave`/`xsave`は0箇所、CR0/CR4のFPのビットを書く箇所も0である。**
  **`#NM`はIDTの名前の表に在るだけで、専用の処理は無い。**
- **プリエンプションは在る**（LAPICタイマ）。**タスクは4本**（`TASK_COUNT`）で、
  **コア間を移動しない**（`ADR-0023`のAddendum §5）。
- **切り替えはRSPの差し替えである**（`task.rs`の`schedule_switch`）。
- **`spawn`は同じタスクの上で入れ子になる**（`ring3.rs`。深さごとに遠征スタックと
  `Recovery`を持つ。`MAX_EXCURSION_DEPTH` = 2）。**親はカーネルの中で子の実行を待つ。**

## Decision

**5つ決める。**

1. **常時退避する。** **切り替えのたびに`fxsave`で保存し、`fxrstor`で復元する。**
   **領域は512バイト・16バイト境界で、タスク1本につき1つ持つ**（`TASK_COUNT` = 4なので
   `.bss`に2KiB）。
2. **退避する場所は2つである**——**タスクの切り替え**（`schedule_switch`）**と、
   `spawn`の遠征の境界**（子へ入る前に親の状態を保存し、子が終わったら復元する）。
   **「切り替えの1点だけで足りる」は誤りだった**（下の「確かめた結果」）。
3. **有効化はコアごとに行う。** **CR0.MP=1 / CR0.EM=0、CR4.OSFXSR / CR4.OSXMMEXCPT を
   bootstrap processorとAPの両方で立てる**（**CR4はコアごとのレジスタである**）。
4. **プログラムを起こすときは、FPの状態を既定値から始める**（`fninit`相当と
   MXCSR=0x1F80）。**前のプログラムのレジスタが次のプログラムから読めてはならない。**
5. **カーネルはsoft-floatのままにする。** **カーネルがFPを使わないことが、
   「カーネルへ入って同じタスクへ戻るだけなら退避が要らない」の根拠である。**
   **この前提は機械で見る**——**`kernel.elf`のXMM命令が0個であることを静的検査にする。**

## 確かめた結果——退避の場所は1つではなく2つだった

**棚卸しの時点では「カーネルがXMMを持たないので、退避が要るのは切り替えの1点だけ」
と見ていた。** **確かめたら違った。**

**`spawn`は新しいタスクを作らない。** **同じタスクの上で遠征が入れ子になり、
親はカーネルの中で子の終了を待つ。** **したがって親がRing 3でXMMに値を持ったまま
`spawn`を呼ぶと、子がRing 3でXMMを壊し、親はそのまま再開する**——**切り替えは
1度も起きていないので、切り替えの退避では守れない。**

**この結果、増える面は2つになる**（スケジューラと遠征）。
**持ち越しの「FPU / SSEの状態保存」の行が最初からそう見積もっていたとおりである。**

## 却下した案

**遅延退避（`CR0.TS`と`#NM`）。** **使ったタスクだけ退避する形である。**
**却下する理由は3つで、重い順に並べる。**

- **所有者がコアごとの状態になる。** **いまタスクはコア間を移動しないので破綻しないが、
  それは`ADR-0023`のAddendum §5という別の決定に寄りかかることになる。**
  **移動を入れる日が来たら、遅延退避は静かに壊れる**（**「FPUの所有者」を移す処理が要る**）。
- **`#NM`の処理が要る。** **いま`#NM`は名前の表に在るだけで、専用の経路が無い。**
  **例外の経路を1本増やすのはレビュー必須の面が増えることである。**
- **得るものが小さい。** **タスクは4本で、512バイトの退避は`memcpy`1回にも満たない。**
  **常時退避の費用は測る前から無視できる。**

**`xsave`。** **AVX以降の状態まで保存できるが、XCR0の設定とCPUIDの列挙が要り、
領域の大きさが可変になる。** **いま使うのはSSEまでで、`fxsave`の512バイト固定で足りる。**
**AVXを使い始めたらここへ戻る**（下の「決めないこと」）。

**カーネルへ入るたびに退避する案。** **最も単純だが、システムコールと割り込みの
すべてに512バイトの退避が乗る。** **カーネルがXMMを使わない限り、意味が無い。**
**その「使わない」を静的検査で守るほうが安い**（Decision 5）。

## 破壊と、それが落とす判定

**破壊は「切り替えで復元しない」**（`fxrstor`を省く。保存は残す）。

**そのままでは落ちない。** **落とす判定を先に作る必要がある**——**いまFPを使う者が
1人しか居ないと、誰もXMMを汚さないので、復元を省いても値は生き残る**
（`docs/verification-coverage.md`の「機会が無い」形である）。

**したがって、破壊の構成では「もう1人のFPの使い手」を用意する。**
**カーネルの検査用タスクが、走るたびにXMMへ目印の値を書く**（feature で囲う）。
**そのうえでCのプログラムが浮動小数点の計算を回し、結果を判定する。**

- **復元が効いていれば、Cのプログラムは自分の値を見る。**
- **復元を省くと、目印の値が混ざる**——**判定が落ちる。**

**遠征の側の破壊は別に置く**（「子へ入る前に保存しない」）。
**落とす判定は「親が`spawn`を跨いで浮動小数点の値を保つ」である**——
**Cのプログラムが値を持ったまま子を起こし、戻ってから確かめる。**

## 5つの決定に、それぞれ判定と破壊が在るか

**判定を足すときに落とす破壊を確かめる規律の、逆向きである**（`docs/coding-standards.md`）。
**決めたことの側から、それを falsify する形が在るかを見る。**

| 決定 | 判定 | 破壊 |
|---|---|---|
| 1. 常時退避する | **無い**（下記。**足し上げの判定は在るが、切り替えが起きないので主張していない**） | **無い**（置こうとして、置けないと分かった） |
| 2. 場所は切り替えと遠征の2つ | 上に加えて「親が`spawn`を跨いで値を保つ」 | `fp-spawn-no-save`（子へ入る前に保存しない） |
| 2. の前提（**カーネルはFPを壊さないので、入って同じタスクへ戻るだけなら退避が要らない**） | **Ring 3で描いたビットマップが、ホストで描いたものとバイト単位で一致する**（B-d。下の Addendum） | `fp-clobber-on-kernel-entry-test`（システムコールと割り込みの両方の入口で、XMM0とMXCSRを塗る） |
| 3. コアごとに有効化する | **無い**（下記） | **無い** |
| 3. の副作用（`#XM`が届くようになる） | Ring 3が浮動小数点の例外を上げても、カーネルが止まらず、プログラムだけが畳まれる | `fp-mf-not-foldable-test`（`#MF`を畳めるベクタから外す。**`#XM`ではなく`#MF`である**——下記） |
| 5. の静的検査そのもの | `kernel.elf`のXMM命令が0個である | カーネルへ`pxor xmm0, xmm0`を1つ入れる（**一度作って落ちることを確かめた**。実測。2026-09-07） |
| 4. 起こすときは既定値から始める | **新しく起きたプログラムがXMMを読むと0である**（前のプログラムが書いた目印が読めない） | `fp-no-fresh-state`（既定値にせず、前の状態のまま起こす） |
| 5. カーネルはsoft-floatのまま | `kernel.elf`のXMM命令が0個である（静的検査） | カーネルにXMMを1命令入れると落ちる（**検査を置くときに一度作って確かめる**） |

**決定3に判定が無い理由は、観測の機会が無いことである。** **APでの有効化を省くと、
APの上でSSE命令を実行した瞬間に`#UD`で落ちる**——**しかしいまRing 3のプログラムは
bootstrap processorの上でしか走らない**（`init`もシェルもBSPの担当である）。
**したがって「APで有効化されていること」を落とす判定は、いまは作れない。**
**観測できないので、観測できないと書く**（`docs/coding-standards.md`の
「観測できないなら観測できないと書く」）。**APでRing 3を走らせる日が来たら、
そこで判定が付く。**

## 決定1に判定が付かない（実装で分かった。2026-09-07）

**置こうとして、置けないと分かった。** **経緯を残す。**

**まず「もう1人のFPの使い手」を作った。** **カーネルはXMMの命令を持たない**（決定5）
**が、目印を書くのに命令は要らない**——**`fxrstor`で目印を載せた512バイトを読み込ませれば
よい。** **検査用のワーカーが走るたびにそれを行う形にした。**

**そこで、切り替えそのものが起きないと分かった。** **Ring 3のプログラムが走っている
あいだ、走行可能なタスクはメインだけである**——**プリエンプティブのデモは`init`より前に
締切で終わり、ワーカーは`Blocked`になる。** **`schedule_switch`は`next == current`で
早く戻るので、退避のコードは1度も通らない。**

**ワーカーを起こし直す形にしたら、起動が止まった**（実測。2026-09-07。**`/bin/fptest`を
写像したところで進まない**）。**原因は`RSP0`である**——**遠征に入るとき`RSP0`はその深さの
遠征スタックを指すが、切り替えは次のタスクのカーネルスタック頂点で上書きする。**
**Ring 3の最中に切り替えて戻ると、次の割り込みが別のスタックの上に降りる。**

**したがって、いまのZaytOSは「Ring 3が走っているあいだの切り替え」を持っていない。**
**決定1の退避は正しく、いつか必ず要るが、いまは観測できない**——**観測できないので、
観測できないと書く**（`docs/coding-standards.md`）。**持ち越しに行を立てた**
（`docs/deferred-decisions.md`の「Ring 3が走っているあいだの切り替え」）。
**そこが解けたら、この判定を置くこと。**

**破壊も置かない。** **落とす判定が無い破壊は、緑を増やすだけである。**

## `OSXMMEXCPT`を立てたので、畳めるベクタを2つ増やした（2026-09-07）

**決定3の副作用である。** **`OSXMMEXCPT`を立てると`#XM`（ベクタ19）が上がりうる。**
**`MXCSR`の既定は全例外マスク（0x1F80）だが、Ring 3のプログラムは`ldmxcsr`で
マスクを外せる**——**利用者の操作で到達できる経路である。**

**畳めるベクタは`[0, 6, 13, 14]`だった**（`#DE` / `#UD` / `#GP` / `#PF`。実測）。
**`#XM`はそこに無いので、上がればdump+haltへ落ちる**——**Ring 3の1命令でカーネルが
止まる。** **`[0, 6, 13, 14, 16, 19]`にした**（`#MF`も対で足した。**x87の側も
`fldcw`で同じ経路が開く**）。

**観測できるのは`#MF`の側だけである。** **QEMUのTCGは`#XM`を配送しない**
（実測。2026-09-07。**`MXCSR`のマスクを外して0で割っても何も起きず、
`stmxcsr`で読み戻すとマスクは外れている**——**同じコードはホストで`SIGFPE`になる**）。
**x87の側は上がるので、判定と破壊はそちらに置いた**（`/bin/fpfault`が両方を試し、
上がったほうで畳まれる）。**`#XM`は実機のために入れてある。**

## Consequences

- **`.bss`が2KiB増える**（512バイト × タスク4本）。**遠征の側でも深さごとに1つ要るなら、
  さらに1KiB増える**（設計で決める）。
- **`kernel.elf`のXMM命令が0であることが、静的検査の主張になる。**
  **カーネルでうっかり浮動小数点を使うと、そこで落ちる。**
- **CR0/CR4への書き込みと新しい`unsafe`が入る。** **APの起こし方にも触る。**
  **レビュー必須である**（`CLAUDE.md`の「人間レビューが必須の変更」）。
- **可変長引数のCを書くときに、`al`の約束が効いてくる**——**SysVの規約では、
  ベクタレジスタで渡した引数の本数を`al`に載せる。** **`printf`を作る日に当たる**
  （`docs/deferred-decisions.md`の行に書いてある）。
- **タスクがコア間を移動しないという前提には寄りかからない。** **常時退避は
  移動を入れても壊れない。**

## 決めないこと

- **AVX / `xsave`**（使い始めたときに決める。`fxsave`から移る形になる）。
- **カーネル自身がFPを使うか**（いまは使わない。使うなら退避の場所が増える）。
- **遅延退避へ戻るか**（**測って「常時退避が重い」と分かったときに考える**。
  いまは測る対象すら無い）。

## Addendum（B-d。2026-09-11）——決定2の前提に判定が付いた

**決定2はこう言っている**——「**カーネルがFPを使わないことが、『カーネルへ入って同じタスクへ戻るだけなら退避が要らない』の根拠である**」（決定5の文でもある）。

**この主張は裸だった。** **決定5の静的検査（`kernel.elf`のXMM命令が0個）は「壊さない」の根拠だが、「壊したら気づく」ことは示していない。** **落とす破壊が無い判定は、何も主張していないのと同じである。**

**B-dで判定と破壊を1組置いた。**

- **判定**——**`/bin/ttfglyph`がRing 3で描いた`A`@16pxのビットマップが、同じ源をホストで建てて描いたものとバイト単位で一致する**（`cargo xtask run --ttf-test`）。**ラスタライズは何十回もカーネルへ入る**（`read`・`brk`・`write`。実測で46回）。
- **破壊**——`fp-clobber-on-kernel-entry-test`。**システムコールと割り込みの両方の入口で、`fxrstor`で512バイトの並びを読み込ませ、FPの状態を塗る。** **XMMのレジスタ名を書かないので、決定5の静的検査と衝突しない。**

**入口も塗る中身も、測って決め直した。** **最初の設計はどちらも外していた。**

**(1) システムコールの入口だけでは、1つも落ちなかった。** **理由はCの呼び出し規約である**——**XMMは全部caller-savedなので、`malloc`を跨ぐ時点で呼ぶ側が既に退避している。** **カーネルへ「同期的に」入る経路では、ユーザーのFPがレジスタに生きていることがない。**

**(2) 割り込みの入口でXMMを塗る形にすると、落ちたり落ちなかったりした**（実測。**3回走らせて1回**）。**理由は窓の狭さである**——**1文字の描画はホストで1マイクロ秒、TCGでもその数十倍で、ティックは10ミリ秒である。** **プリエンプションが描画の最中に入るかどうかは、時機に依る。**

**(3) MXCSRを塗る形にしたら、必ず落ちるようになった**（実測。**3回続けて落ちた**）。**丸めの制御ビットは呼び出しを跨いで保たれる約束で、コンパイラは退避も復元もしない。** **入口で丸めを0方向へ変えれば、その後の浮動小数点は必ず違う答えを出す。** **`A`@16pxのビットマップが実際に変わることを、先にホストで測った**（**最近接偶数・0方向・+∞方向の3通り。`W`@48pxは変わらなかったので、字と倍率に依る**）。

**いまの破壊は2つとも塗り、2つの入口に置く。** **MXCSRが「必ず落ちる」を担い、XMMが「レジスタが生きているところへ入る」を担う。**

**記録に残すのは、破壊の設計を3度やり直したからである。** **「カーネルへ入る」と一口に言っても、同期と非同期で主張の強さが違う。** **そして「FPの状態」と一口に言っても、レジスタと制御語では、呼ぶ側が退避するかどうかが違う。**
