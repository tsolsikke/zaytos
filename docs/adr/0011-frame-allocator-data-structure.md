# 0011. 物理フレームアロケータのデータ構造に範囲リストを採用する

## Status
Accepted

## Date
2026-07-20

## Context
M2-c で物理フレームアロケータ（`kernel/src/frame_allocator.rs`）を実装するにあたり、
空き物理フレームをどう管理するかで 3 案を比較検討した。

- **ビットマップ**（1 フレーム = 1 ビット）
- **侵入型フリーリスト**（各空きフレームの先頭に次フレームへのポインタを
  書き込み、連結リストとして管理する）
- **範囲リスト**（`(start_frame, frame_count)` の集合をソート済み・隣接
  結合済みで保持する）

この時点でヒープ（`alloc` クレート）はまだ有効化されていない（M2-e で
対応予定）。また、メモリマップ解析と空きフレーム
管理のロジックはハードウェア依存から分離し、ホスト上の `cargo test` で
検証可能にすることが求められている。

各案の検討結果:

- **ビットマップ**: フレーム数に比例したビット列を格納する領域が別途
  必要になる。ヒープがない現段階では、このビットマップ自身をどこに
  置くかという別の鶏卵問題が生じる。固定サイズの静的配列で確保する
  ことも考えられるが、対応する物理メモリ量の上限を先に決め打ちする
  ことになり、学習目的のプロジェクトとしては不自然な制約になる。
- **侵入型フリーリスト**: 追加のメモリを必要としない点は優れているが、
  実際に空きフレームの物理メモリへポインタを書き込む操作が常に
  `unsafe` になる。テストでは実在しない物理アドレスに対してこの
  書き込みを行うことができず、ロジックの大部分がホスト上でテスト
  できなくなる。ホスト上でテスト可能にする方針と相性が悪い。
- **範囲リスト**: UEFI メモリマップが最初から「範囲」の集合として
  与えられることと相性が良い。範囲の個数は実測（QEMU + OVMF, 256MiB
  割り当て）で数十程度であり、固定長配列に十分収まる。範囲の追加・
  結合・分割は生ポインタを一切使わない純粋なデータ操作であり、
  ホスト上の `cargo test` で全面的に検証できる。

## Decision
空き物理フレームを、`FrameRange { start_frame, frame_count }` の
ソート済み・隣接結合済みの集合として、固定長配列（既定容量 256、
`FrameAllocator<const CAP: usize = 256>` として const generic 化）で
管理する。

- 挿入時、前後の既存範囲と隣接・重複していれば結合する（隙間を
  ちょうど埋める場合は前後両方と結合する）。
- 確保 (`allocate_frame`) は先頭（最小フレーム番号）の範囲から行う。
- 解放 (`deallocate_frame`) は単一フレームの範囲として挿入し、
  隣接する既存の空き範囲と自動的に結合される。**解放は実装済みで
  あり、実地スモークテスト（1 フレーム確保→解放→カウント一致確認）
  も M2-c の時点で通っている。**
- 容量（範囲の断片数）が上限に達した場合は `FrameAllocatorError::
  CapacityExceeded` を返す。呼び出し側（`kernel/src/main.rs`）はこれを
  握りつぶさず、シリアルへエラーを出力したうえで `hlt` ループへ入る
  （ADR-0004: fail-fast）。

## Alternatives Considered
- **ビットマップ**: Context 参照。ヒープ未整備の段階でのビットマップ
  自身の配置問題により却下。ヒープ整備後（M2-e 以降）であれば
  再検討の余地はあるが、範囲リストで実用上困っていない限り変更する
  積極的な理由はない。
- **侵入型フリーリスト**: Context 参照。テスト可能性を著しく損なうため
  却下。

## Consequences
- **容量上限（256）について**: 実測（QEMU + OVMF, 256MiB 割り当て）では
  `EfiConventionalMemory` のエントリ数は数十程度であり、余裕を持った値
  にしている。断片化が激しい環境（多数の小さな空き領域が散在する構成）
  では 256 を超える可能性がある。超過時は `CapacityExceeded` エラーを
  返し、呼び出し側がエラーログ出力 + `hlt` で fail-fast する（黙って
  範囲を捨てて空きフレームを見失う、という最も危険な失敗モードは
  取らない）。初期化ログには使用した範囲数と容量の両方を出力し、
  実測でどれだけ余裕があるかを常に把握できるようにしている。
- **解放 (dealloc) の設計状況**: 実装済み。範囲リストへの単一フレーム
  挿入として扱われ、隣接する空き範囲との結合も自動的に行われる。
  M2-d（自前ページテーブル構築）では新規にフレームを確保するのみで
  解放は必要ないが、将来アドレス空間の解体（プロセス終了時のページ
  テーブル解放等）が必要になった際、この解放パスをそのまま利用できる。
- 範囲の個数が小さい前提のデータ構造であるため、フレームが非常に
  細かく断片化する状況（将来、汎用のヒープアロケータやユーザー
  プロセスの頻繁なメモリ確保/解放が加わった場合）では、この範囲リストは
  最適な選択ではなくなる可能性がある。その時点で、より高頻度の確保/
  解放に強い構造（バディアロケータ等）へ差し替えるかどうかを再検討する。
  現時点（M2-c、起動時に一度構築し主にページテーブル用に単発で確保する
  用途）では、シンプルさとテスト可能性を優先する。
