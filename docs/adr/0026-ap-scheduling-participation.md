# 0026. APのスケジューラ参加は静的な担当コアで閉じ、`CURRENT`条件を第2層に置く

## Status
Accepted

## Date
2026-08-02

## Context

S4-cでAP（application processor）をスケジューラへ参加させた。
それまでAPは`irq_entry`の早期リターンで手前へ戻っており、`pick_next`へ到達しなかった。
参加させると、**同じタスクを2つのコアが同時に選びうる**という問題が新しく実在する。
同じタスクを選べば同じスタックを2コアが走るので、被害はスタックの破壊である。

BKLはこれを防がない。
**タスク本体はBKLの外を走る**（ADR-0023 Addendum §5）。
`irq_entry`が次タスクのRSPを返し、スタブが`iretq`する形なので、**BKLの解放は`iretq`より前に来る。**
したがって「BKLがあるから同時に走らない」は成立しない。
**BKLの取得と解放の定義はADR-0023 Addendumが正であり、本ADRでは複製しない。**

上位方針との関係。
細く長く・堅牢優先の方針から、**この段では「速いスケジューラ」ではなく「間違いようのないスケジューラ」を選ぶ。**
`MAX_CPUS = 2`のままで、負荷分散もタスクの移動も持たない。

## Decision

### 1. 守りを2層にする。第1層は静的な担当コア

各タスクは`owner`（担当コア）を持ち、`pick_next`は**自コアが担当のタスクだけを巡回の候補にする。**
担当は静的で、実行中に変わらない。
BSPはメインと2本のワーカーを、APはAP用アイドルタスクを担当する。

**担当が互いに素なので、第1層だけで2コアが同じタスクを選ぶことは起きない。**

### 2. 第2層は`CURRENT`条件。本番では発火条件が無い

候補が他コアの`CURRENT`に入っていたら選ばない。
**第1層が担当を互いに素にしている限り、この条件は本番で成立しない。**

**発火条件が無いものを置くのは、第1層が壊れたときに残る守りが要るからである。**
「効いていないから消す」とはしない。
**発火条件が無いこと自体が主張であり、それを主張として保つにはコードが在る必要がある。**

### 3. 落ち先はコアごとに持つ

走行可能な担当タスクが無いとき、`pick_next`は**そのコアの既定タスク**を返す（`default_task_for`）。
BSPはメイン、APはAP用アイドルタスクである。

**固定の`0`を返す形は採らない。** `0`はBSPの担当なので、APがそこへ落ちると他コアのタスクを走らせる。
**しかも落ち先は候補ではないので、第1層も第2層も参照されない。**
**検査で防ぐのではなく、他コアのタスクへ落ちる経路そのものを無くす。**

### 4. 二重選択の検出器を本番ビルドに置く

2層とも迂回されたときだけ1行出す。系全体で1度、BKLの内側で出す。

**検出器は第2層と同じ述語を共有するが、破壊featureが無効にするのはフィルタでの参照だけで、検出器の参照には`cfg`を付けない。**
2層とも壊した構成でも検出器が生きている必要があるためである。

### 5. `TaskState::Running`を足さない

「実行中」を状態機械の値として持てば第2層は要らなくなるが、**採らない。**
理由は下の Alternatives Considered に書く。

## Alternatives Considered

- **`TaskState::Running`を足して状態で排他する。** 不採用。
  状態は**書いたコアと読むコアが違う**ので、`Ready`→`Running`の遷移が原子でなければ2コアが同時に`Running`にできる。
  原子にするには比較交換が要り、**それは実質的にタスクごとのロックである。**
  BKLファースト（ADR-0023）で「細粒度ロックを持たない」と決めた段で、タスクごとのロックを事実上導入することになる。
  **`CURRENT`条件は読み取りだけで済み、書き手は自コアに限られる。**

- **`Locked<T>`をスピンロック併用へ差し替える。** 不採用（S4で決定済み）。
  BKLの下では本番経路の競合が構造的に起きないので、**待機化は死んだコードになる。**
  「将来のために作り込まない」（§10）に従う。

- **タスクのコア間移動を実装する。** 不採用。
  **負荷分散を持たないことの帰結ではない。** `GPR_BUF`の安全がこれに依存している（ADR-0023 Addendum §5）。
  ワーカーは15本のGPRを共有バッファへ書いて照合しており、排他はasm内の生`cli`である。
  `cli`が止められるのは同一コアの割り込みだけなので、**別コアのタスクからの並行アクセスを防げない。**
  移動を入れると、この保護が理由もろとも消える。

- **APを参加させず、早期リターンを残す。** 不採用。
  「全コアが進行していること」がS4の到達条件であり、APがタスクを持たないままでは満たせない。

- **第1層だけにして第2層を置かない。** 不採用。§2のとおり。

## Consequences

### 得るもの

`MAX_CPUS = 2`で、2コアが同じタスクを選ぶ経路が構造的に存在しない。
第1層・第2層・検出器がそれぞれ独立に観測でき、隣り合う構成が層1つぶんだけ違う破壊の梯子になっている。

### 失うもの

負荷分散が無い。APはアイドルタスクしか走らせない。
**これは意図した制限であって、未実装の穴ではない。**

### 条件つきの安全（失効条件つきの決定）

**この節が本ADRの本体である。** 以下はいずれも「今は成り立つ」であって「常に成り立つ」ではない。

- **§3の落ち先は`MAX_CPUS = 2`でしか成り立たない。**
  `default_task_for`はAPをコアで区別していないので、**3以上になると2つ目以降のAPが同じアイドルタスク、すなわち同じスタックへ落ちる。**
  しかも落ち先は層を通らないので**検出器も鳴らない。**
  **失効条件は`MAX_CPUS > 2`である。** 上げるならコアごとのアイドルタスクを用意する作業が要り、それを`MAX_CPUS`を上げる費用に含める。
  ホストテストが`0..MAX_CPUS`を回すので、**上げた瞬間に落ちる。落ちるのが正しい振る舞いであり、通すために表明を弱めてはならない。**

- **`GPR_BUF`の実際の保護は時期で入れ替わっている。**
  S4-c-2まではAPが`pick_next`へ到達しないこと、S4-c-3以降は**第1層の静的な担当とタスクのコア間移動を実装しないこと**である。
  **`require_bootstrap_processor`はデモ開始の見張りにすぎず、ワーカーの継続では鳴らない。**
  「防衛線があるから安全」と読まないこと。

- **検出器が検出できるのは「2層とも迂回されたこと」だけである。**
  フィルタと検出器は同じ出所（`CURRENT`）から両辺を導くので、**述語自体の誤りは検出できない。**

- **`CURRENT`への直接代入は層を通らない。**
  `pick_next`を経ない書き込みは第1層も第2層も参照せず、検出器も鳴らない（検出器は「選択」を見ており、代入は選択ではない）。
  **層で守れるのは選択であって、`CURRENT`の値そのものではない。**
