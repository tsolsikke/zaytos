# 0032. 入力の制御文字のうち中断（Ctrl+C）だけをカーネルで解釈する

## Status
Accepted

## Date
2026-08-15

## Context

出力の側は`ADR-0029`で決めてある。
**画面制御はANSIエスケープシーケンスで行い、解釈はRing 3に置き、カーネルはバイトを運ぶだけである。**
入力の側に同じ形を当てると、**制御文字の解釈もRing 3が持つ**ことになる。

Ctrl+Cで走っている子を止められるようにしたい（シグナルの段階(1)と(2)）。
**素直に読めば、これもRing 3の仕事である**——シェルが0x03を受け取り、走らせた子を止めればよい。

**ところが、いまの構造ではそれが成り立たない。理由が2つあり、どちらも実測で確かめた。**

**1つ目。デコードの経路が1本しかなく、それは`input::read_bytes`である。**
あれは**Ring 3が`read`を出したときにしか動かない。**
キーボード割り込み（`keyboard::handle_irq`）はスキャンコードをリングへ積むだけで、デコードしない
（`ADR-0018` §5。ハンドラはリングへ積むだけである）。
**止めたい相手は`read`を出さずに回っている子なので、その子が走っている間、スキャンコードは誰にもデコードされない。**
リングに溜まるだけである。

**2つ目。`spawn`は同期で、子が走っている間シェルは`spawn`の中で待っている。**
**シェルは読める位置にいない。**

**そして「誰を止めるか」を決める情報がRing 3に無い。**
前景（`input`の`FOREGROUND`）はカーネルの概念で、**Ring 3から問う手段が無い。**

## Decision

**入力の制御文字のうち、中断（Ctrl+C）だけをカーネルで解釈する。**
**残りの制御文字は従来どおりバイトとして運び、解釈はRing 3に置く。**

**例外にする理由は、前景という概念がカーネルにしか無いことである。**
「誰を止めるか」は前景の持ち主から決まり、**Ring 3にはその情報が無い。**
`ADR-0029`が出力側で「解釈に必要な情報はRing 3が全部持っている」ことに依っていたのに対し、
**入力側の中断だけはそれが成り立たない。**

具体的には次の形にした。

- **キーボード割り込みで、Ctrl+Cだけを見る最小の追跡を持つ**（`input::note_scancode_for_interrupt`）。
  デコーダではない。表もShiftもCaps Lockも見ず、**Ctrlの押下状態とCの一致だけを見る。**
  **ロックを取らない**（状態はすべてアトミックで持つ）
- **見つけたら旗を立てるだけで、その場では畳まない。**
  **割り込み文脈から遠征を抜けると、割り込みを終えないまま出ることになる**
- **畳むのはタイマ割り込みのEOIを送った後である。**
  **キーボード割り込みの側では畳めない**——あちらのEOIはハンドラより後ろにあり、
  そこから抜けると**キーボードが二度と来ない**
- **深さ2以上（子が走っている）でのみ畳む。**
  深さ1のCtrl+Cは`Decoder`が0x03として出し、**行を捨てるのはシェルの仕事である**

## Alternatives Considered

**Ring 3で0x03を見て自分で終了する。**
`ADR-0029`と対称になるので、最初に検討した形である。**採らない。**

**理由は上のContextの1つ目である**——**子が`read`を呼ばない限り、デコードすら起きない。**
0x03はどこにも現れないので、Ring 3は見ようがない。
**`read`を呼んで待っている子には届くが、それは止めたい相手ではない。**
**止めたいのは回り続けている子で、あれは何も読まない。**

加えて2つ目の理由もある。**シェルは`spawn`の中で待っており、子が走っている間は読める位置にいない。**
**仮にデコードされても、受け取る者がいない。**

**キーボード割り込みの文脈で直接畳む。**
旗を立てて後で畳むより短い。**採らない。**
**あの経路のEOIはハンドラより後ろにあり、longjmpで抜けるとEOIを送らずに割り込みを出る。**
**以後IRQ1が来なくなり、キーボードが死ぬ。**

**`Decoder`に持たせた状態だけで済ませる。**
**採らない。**同じ理由で、`read`を呼ばない子には届かない。
**ただし`Decoder`にもCtrlを持たせてはいる**——**深さ1で0x03を順序どおりに届けるためである。**
**旗を消費して0x03を作る形も検討したが、採らなかった**——
**旗は打鍵の順序を持たないので、先に溜まっていた字より前に0x03が出る。**
`abc`と打ってからCtrl+Cを押すと、**行が捨てられた後に`abc`が入る**ことになり、捨てた意味が消える。

## Consequences

**得るもの。** 回り続ける子を外から止められる。
**カーネルが持つのは「中断」1つだけで、他の制御文字は従来どおりRing 3が解釈する。**

**失うもの。** **制御文字の解釈が2か所に分かれた。**
`Decoder`（文字を作る側）とキーボード割り込みの追跡（中断を見つける側）が、
**どちらもCtrlの押下状態を持つ。**
**統合するにはデコーダを割り込みハンドラへ持ち込むことになり、`ADR-0018` §5に反する。**
**住んでいる文脈が違うので分けたままにする。**

**いつ解消しうるか。**
**前景がRing 3側の概念になったときである。**
具体的には**プロセス表かセッションの概念が出て、「誰が前景か」をRing 3が答えられるようになった時点**である。
そのときこの例外は`SIGINT`の配送（シグナルの段階(4)）へ吸収され、
**カーネルが持つのは「シグナルを配送する」ことだけになる。**

**そのとき`ADR-0029`と対称に戻せる。**
**入力も出力も、解釈はRing 3が持つ形である。**

**失効条件——`spawn`が非同期になったら、この決定の前提が変わる。**
シェルが子を待たずに読める位置にいるなら、Contextの2つ目が消える。
**1つ目（デコードが`read`でしか起きない）は残るので、決定そのものは変わらない見込みだが、
そのとき読み直すこと。**
