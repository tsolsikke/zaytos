# 0008. bootloader と kernel を分離する

## Status
Accepted

## Date
2026-07-19

## Context
ExitBootServices 後、ZaytOS をどう実行し続けるかについて 2 案を検討した。

- 案A: bootloader（.efi, `x86_64-unknown-uefi`, `uefi` クレート使用）と
  kernel（ELF, `x86_64-unknown-none`, フリースタンディング）を別クレート・
  別ビルド成果物として分離し、bootloader が kernel の ELF をロードして
  制御を渡す。
- 案B: 単一 .efi のまま、同じバイナリ内で ExitBootServices 呼び出し後も
  実行を継続する。

この決定に先立ち、「bootloader/kernel の分離は ADR-0001（モノリシック
カーネル採用）が却下したマイクロカーネル的分離と同じ構造の判断ではないか」
という指摘を検討したが、これは誤りであると判断した。両者は異なる次元にある。

- マイクロカーネルの分離（ADR-0001 が却下した対象）は **実行時アーキテクチャ**
  の選択である。カーネル機能をプロセス単位に分割し IPC で通信させるため、
  カーネルが動作し続ける間ずっと発生し続ける複雑度（IPC 機構、プロセス分離、
  コンテキストスイッチのオーバーヘッド等）を伴う。
- bootloader/kernel の分離は **ビルド時・起動時の境界**に過ぎない。
  bootloader は kernel へ制御を渡した時点で役目を終え、以降の実行時複雑度を
  一切増やさない。実際、Linux はモノリシックカーネルでありながら
  bootloader（GRUB 等）とは完全に分離されており、この分離はモノリシック/
  マイクロカーネルという軸とは独立に、現実の OS でほぼ例外なく採用されて
  いる構成である。

したがって ADR-0001 は案A採用の妨げにならない（詳細は後述の
「ADR-0001 との関係」を参照）。

その上で、案Aを採用する理由は以下の通り:

1. 「ファームウェアから OS へ制御が渡る境界」は OS の最も本質的な概念の
   一つであり、これを省略せず実装すること自体が ZaytOS の学習目的
   （基本機能は省略しない）に直結する。
2. `docs/architecture.md` の技術スタック図は既に bootloader(.efi) と kernel
   を別レイヤとして図示しており、ADR-0005 も「カーネルは
   `x86_64-unknown-none` 想定」と明記している。案Bを採用するとこれらの
   既存記述からの設計後退になる。
3. 分離を先送りして M2〜M5 を単一 .efi のまま書き進めた場合、M6
   （簡易的なユーザープログラムのロード）で結局同種の ELF ローダーが
   必要になる。その時点でそれまでのコードのアドレス配置・実行前提を
   全面的に作り直すことになり、後回しにするほど移行コストが高くなる。
4. リンカスクリプトで kernel の仮想/物理アドレス配置を最初から自分で
   制御できるため、M2-c（自前ページテーブル構築）の設計自由度が上がる。
   案Bだと UEFI がロードした位置に配置が引きずられる。

## Decision
bootloader（.efi, `x86_64-unknown-uefi`, `uefi` クレート使用）と kernel
（ELF, `x86_64-unknown-none`, フリースタンディング）を別クレート・別ビルド
成果物として分離する。bootloader は UEFI Boot Services を使って
`kernel.elf` を ESP から読み込み、ExitBootServices の呼び出し（呼び出しに
必要な情報の収集を含む）を経て、`BootInfo` 構造体を介して kernel へ制御を
渡す。

具体的な役割分担・呼び出し順序（ExitBootServices を bootloader 側で呼ぶか
kernel 側に委ねるか等）や `BootInfo` 構造体の詳細設計は、M2-0c の実装案と
して別途提示し、レビューを経て確定する。

## Alternatives Considered
- **案B: 単一 .efi のまま ExitBootServices 後も実行継続**: 実装コスト・
  現構成からの移行コストは低いが、以下の理由で却下する。
  - 学習目的との不整合: ファームウェア→OS 境界の実装を省略することになり、
    「基本機能は省略しない」という上位方針に反する。
  - 既存ドキュメントとの齟齬: `architecture.md` の技術スタック図・
    ADR-0005 の記述と食い違う。
  - 移行コストの先送りに過ぎない: M6 のユーザープログラムロードで結局
    同種の仕組みが必要になり、その時点で M2〜M5 の全コードのアドレス
    配置前提を作り直すことになる。今分離するより後で分離するほうが
    影響範囲が大きい。
  - ADR-0001（モノリシックカーネル採用）は本判断を妨げない: ADR-0001 が
    扱ったのは実行時のアーキテクチャ分離（プロセス分割・IPC）であり、
    bootloader/kernel の分離はビルド時・起動時一回限りの境界に過ぎず、
    次元が異なる（下記「ADR-0001 との関係」を参照）。

## Consequences
- 実装コストとして、ELF64 ローダー（プログラムヘッダ解析・セグメント配置・
  `.bss` ゼロ埋め）、kernel 用リンカスクリプト（エントリアドレス・
  セクション配置の制御）、bootloader→kernel の引き渡し ABI（`BootInfo`
  構造体設計、呼び出し規約）、クレート再編（現 `kernel` クレートを
  `bootloader` へ改名し、`serial`/`log`/`cpu` を共有化、`panic_handler` を
  バイナリごとに用意）が必要になる。
- `xtask` の拡張が必要になる（bootloader と kernel を別々にビルドし、
  `kernel.elf` を ESP 上に配置して bootloader からロードする手順に変更）。
- M6（簡易的なユーザープログラムのロード）で必要になる ELF ローダーの
  実装・設計を再利用・共通化できる可能性がある。
- リンカスクリプトにより kernel の仮想/物理アドレス配置を最初から自分で
  制御できるため、M2-c（自前ページテーブル構築）の設計自由度が上がる。
- `BootInfo` 構造体は一度確定すると変更の影響範囲が広い（bootloader と
  kernel の双方に影響する）ため、確定前にレビューを経る（M2-0c 内で提示）。

## ADR-0001 との関係
ADR-0001（保護機構ありのモノリシックカーネルを採用する）が扱ったのは、
カーネル内部の機能をプロセス単位に分割し IPC で通信させるかどうか、という
**実行時アーキテクチャ**の選択である。これはカーネルが動作し続ける間ずっと
発生する複雑度（IPC 機構、プロセス分離、コンテキストスイッチのオーバー
ヘッド等）を伴う。

一方、本 ADR が扱う bootloader/kernel の分離は、ファームウェアから OS へ
制御が一度だけ渡される **ビルド時・起動時の境界**である。bootloader は
kernel へ制御を渡した時点で役目を終え、以降の実行時複雑度を一切増やさない
（Linux がモノリシックカーネルでありながら GRUB 等の bootloader と完全に
分離されているのはこの一例である）。

したがって本 ADR の決定は ADR-0001 の決定と矛盾しない。両者は独立した軸の
判断であり、ADR-0001 は本 ADR の案A採用を妨げない。
