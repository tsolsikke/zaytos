# 0008. bootloaderとkernelを分離する

## Status
Accepted

## Date
2026-07-19

## Context
ExitBootServices後、ZaytOSをどう実行し続けるかについて2案を検討した。

- 案A: bootloader（.efi, `x86_64-unknown-uefi`, `uefi`クレート使用）とkernel（ELF, `x86_64-unknown-none`, フリースタンディング）を別クレート・別ビルド成果物として分離し、bootloaderがkernelのELFをロードして制御を渡す。
- 案B: 単一 .efiのまま、同じバイナリ内でExitBootServices呼び出し後も実行を継続する。

この決定に先立ち、「bootloader/kernelの分離はADR-0001（モノリシックカーネル採用）が却下したマイクロカーネル的分離と同じ構造の判断ではないか」という指摘を検討したが、これは誤りであると判断した。
両者は異なる次元にある。

- マイクロカーネルの分離（ADR-0001が却下した対象）は **実行時アーキテクチャ** の選択である。カーネル機能をプロセス単位に分割しIPCで通信させるため、カーネルが動作し続ける間ずっと発生し続ける複雑度（IPC機構、プロセス分離、コンテキストスイッチのオーバーヘッド等）を伴う。
- bootloader/kernelの分離は **ビルド時・起動時の境界**に過ぎない。bootloaderはkernelへ制御を渡した時点で役目を終え、以降の実行時複雑度を一切増やさない。実際、Linuxはモノリシックカーネルでありながらbootloader（GRUB等）とは完全に分離されており、この分離はモノリシック/マイクロカーネルという軸とは独立に、現実のOSでほぼ例外なく採用されている構成である。

したがってADR-0001は案A採用の妨げにならない（詳細は後述の「ADR-0001との関係」を参照）。

その上で、案Aを採用する理由は以下の通り:

1. 「ファームウェアからOSへ制御が渡る境界」はOSの最も本質的な概念の一つであり、これを省略せず実装すること自体がZaytOSの学習目的（基本機能は省略しない）に直結する。
2. `docs/architecture.md`の技術スタック図は既にbootloader(.efi)とkernelを別レイヤとして図示しており、ADR-0005も「カーネルは`x86_64-unknown-none`想定」と明記している。案Bを採用するとこれらの既存記述からの設計後退になる。
3. 分離を先送りしてM2〜M5を単一 .efiのまま書き進めた場合、M6（簡易的なユーザープログラムのロード）で結局同種のELFローダーが必要になる。その時点でそれまでのコードのアドレス配置・実行前提を全面的に作り直すことになり、後回しにするほど移行コストが高くなる。
4. リンカスクリプトでkernelの仮想/物理アドレス配置を最初から自分で制御できるため、M2-c（自前ページテーブル構築）の設計自由度が上がる。案BだとUEFIがロードした位置に配置が引きずられる。

## Decision
bootloader（.efi, `x86_64-unknown-uefi`, `uefi`クレート使用）とkernel（ELF, `x86_64-unknown-none`, フリースタンディング）を別クレート・別ビルド成果物として分離する。
bootloaderはUEFI Boot Servicesを使って`kernel.elf`をESPから読み込み、ExitBootServicesの呼び出し（呼び出しに必要な情報の収集を含む）を経て、`BootInfo`構造体を介してkernelへ制御を渡す。

具体的な役割分担・呼び出し順序（ExitBootServicesをbootloader側で呼ぶかkernel側に委ねるか等）や`BootInfo`構造体の詳細設計は、M2-0cの実装案として別途提示し、レビューを経て確定する。

## Alternatives Considered
- 案B: 単一 .efiのままExitBootServices後も実行継続: 実装コスト・現構成からの移行コストは低いが、以下の理由で却下する。
  - 学習目的との不整合: ファームウェア→OS境界の実装を省略することになり、「基本機能は省略しない」という上位方針に反する。
  - 既存ドキュメントとの齟齬: `architecture.md`の技術スタック図・ADR-0005の記述と食い違う。
  - 移行コストの先送りに過ぎない: M6のユーザープログラムロードで結局同種の仕組みが必要になり、その時点でM2〜M5の全コードのアドレス配置前提を作り直すことになる。今分離するより後で分離するほうが影響範囲が大きい。
  - ADR-0001（モノリシックカーネル採用）は本判断を妨げない: ADR-0001が扱ったのは実行時のアーキテクチャ分離（プロセス分割・IPC）であり、bootloader/kernelの分離はビルド時・起動時一回限りの境界に過ぎず、次元が異なる（下記「ADR-0001との関係」を参照）。

## Consequences
- 実装コストとして、ELF64ローダー（プログラムヘッダ解析・セグメント配置・`.bss`ゼロ埋め）、kernel用リンカスクリプト（エントリアドレス・セクション配置の制御）、bootloader→kernelの引き渡しABI（`BootInfo`構造体設計、呼び出し規約）、クレート再編（現`kernel`クレートを`bootloader`へ改名し、`serial`/`log`/`cpu`を共有化、`panic_handler`をバイナリごとに用意）が必要になる。
- `xtask`の拡張が必要になる（bootloaderとkernelを別々にビルドし、`kernel.elf`をESP上に配置してbootloaderからロードする手順に変更）。
- M6（簡易的なユーザープログラムのロード）で必要になるELFローダーの実装・設計を再利用・共通化できる可能性がある。
- リンカスクリプトによりkernelの仮想/物理アドレス配置を最初から自分で制御できるため、M2-c（自前ページテーブル構築）の設計自由度が上がる。
- `BootInfo`構造体は一度確定すると変更の影響範囲が広い（bootloaderとkernelの双方に影響する）ため、確定前にレビューを経る（M2-0c内で提示）。

## ADR-0001との関係
ADR-0001（保護機構ありのモノリシックカーネルを採用する）が扱ったのは、カーネル内部の機能をプロセス単位に分割しIPCで通信させるかどうか、という **実行時アーキテクチャ**の選択である。
これはカーネルが動作し続ける間ずっと発生する複雑度（IPC機構、プロセス分離、コンテキストスイッチのオーバーヘッド等）を伴う。

一方、本ADRが扱うbootloader/kernelの分離は、ファームウェアからOSへ制御が一度だけ渡される **ビルド時・起動時の境界**である。
bootloaderはkernelへ制御を渡した時点で役目を終え、以降の実行時複雑度を一切増やさない（LinuxがモノリシックカーネルでありながらGRUB等のbootloaderと完全に分離されているのはこの一例である）。

したがって本ADRの決定はADR-0001の決定と矛盾しない。
両者は独立した軸の判断であり、ADR-0001は本ADRの案A採用を妨げない。
