# 0019. M5 は 6 段階に分け、コンテキストスイッチは IRQ スタブの復元経路に載せる

## Status
Accepted

## Date
2026-07-21

## Context

roadmap の M5 は「タスク構造・コンテキストスイッチ・スケジューラ・ユーザー/
カーネル権限分離の実運用」だが、**これは M4 と同等以上の規模**であり、しかも
現状の前提が足りていない。着手前に段階分割と方式を決める。

**最大の不足はページングである。** 現在のページテーブルは恒等マッピング 1 個で、
`PageTableBuilder` は 2MiB ページの**分割にもアンマップにも未対応**である
（`deferred-decisions.md`）。ガードページもユーザー空間もこれ抜きには成立しない。

## Decision

### 1. 段階分割

| 段階 | 内容 | 状態 |
|---|---|---|
| M5-a | `PageTableBuilder` のページ分割・アンマップ対応 | 通常運転 |
| M5-b | カーネルスタックのガードページ化（M5-a の最初の利用者） | 通常運転 |
| M5-c | タスク構造とコンテキストスイッチ（**協調的**。自発的 yield のみ） | プリエンプションなし |
| M5-d | プリエンプティブ化（タイマからのスケジューリング） | プリエンプション有効 |
| M5-e | ユーザーモードへの遷移（Ring 3、**単一アドレス空間のまま**） | 有効 |
| M5-f | システムコールとプロセスごとのアドレス空間 | 有効 |

**M5-a を先頭に置く。** ページングが律速であり、下から積む順序は M4 で
有効性が確認できている。

**M5-c と M5-d を分ける。** M4-d-1（`sti` できる状態を作る）と M4-d-2
（実際に割り込みを来させる）と同じ構図である。「切り替えが正しいか」と
「割り込みの中から切り替えても壊れないか」は別の問題で、協調的に動く
ところまで作れば、以降の不具合はプリエンプション固有と確定できる。

**M5-e は単一アドレス空間のまま Ring 3 へ落とす。** 権限分離（Ring 0/3）と
アドレス空間分離は別の機構であり、同時にやると切り分けられない。M5-e では
「Ring 3 に落ちて、特権命令で #GP になり、`iretq` で戻れる」までを検証する。

### 2. コンテキストスイッチは IRQ スタブの復元経路に載せる

現在の `zaytos_irq_common` は「GPR 15 本を退避 → Rust ハンドラを call →
復元 → `iretq`」という形で、**スタック上に完全な `IrqContext` が乗っている**。
これをそのままタスクの保存域として使い、**RSP の入れ替えだけ**で切り替える。
明示的なレジスタ復元は要らず、既存の復元経路と `iretq` がそのまま働く。

#### 2.1 RSP を入れ替えるのは Rust ハンドラの中ではない（重要）

**Rust ハンドラ関数の内部で RSP を入れ替えてはならない。** スタブは `call` で
ハンドラを呼んでおり、ハンドラの内部には `call` が積んだ戻り先アドレスと
Rust 側のフレームが**古いスタック上**にある。関数の途中で RSP を入れ替えると、
エピローグの `ret` が**新しいスタックから戻り先を取り出す**。そこにあるのは
次のタスクの `IrqContext` なので、まったく別の場所へ飛ぶ。

正しい構成は次のとおり。

1. Rust ハンドラは「次に使う RSP」を**戻り値として返す**（`extern "sysv64"`
   なので RAX で返る）
2. **スタブが `call` の直後に**それを RSP へ入れる
3. 切り替えが不要な場合は、現在の RSP をそのまま返す

これならスタックの形が `IrqContext` ちょうどである地点で入れ替わる。
M4-d-1 で入れた 16 バイト境界の実測検証も引き続き有効である
（切り替え後のスタックに対しても同じ検査が働く）。

**新規タスクの起動**は「偽の `IrqContext` をスタックへ積んでおく」形にする。
初回のスイッチが、あたかも割り込みから戻るかのようにタスクの入口へ
`iretq` する。

#### 2.2 TSS の RSP0 は切り替えのたびに更新する

RSP0 は Ring 3 → Ring 0 遷移時に CPU が切り替える先のスタックを指す。
タスクごとにカーネルスタックが分かれる以上、**切り替えのたびに現在のタスクの
スタック頂点へ更新しなければならない**。

更新を忘れると、あるタスクのシステムコールが**別のタスクのカーネルスタックを
使い、静かに破壊する**。症状は「しばらく動いた後に突然壊れる」形になる。

実際に効くのは M5-e だが、**M5-c のタスク構造の設計時点で RSP0 用の値を
持たせておく**。後から足すと、切り替え経路のすべてを見直すことになる。

### 3. タスクごとのカーネルスタックにはガードページが要る

現在は `.bss` の固定 1 本で、犠牲領域 + 毒値カナリア（`0xC5`）で代替している。
**タスクが増えるとこれでは足りない。**

1. あるタスクのオーバーフローが**別のタスクのスタックを壊す**。カナリアは
   「いつの間にか壊れていた」ことしか検出できず、**どのタスクが犯人か
   分からない**
2. スタックが動的確保になると、隣に何が来るかをレイアウト固定
   （`#[repr(C)]`）で保証できない。M4-a では「カーネルスタックの直下が
   ヒープと TSS」という危険な並びを固定配置で潰したが、その手が使えない

#### 3.1 #PF にも専用の IST スタックを割り当てる

**ガードページを置くだけでは、報告される例外が #DF になってしまう。**

オーバーフローでガードページに触れると #PF が発生する。しかし #PF ハンドラは
**まさに溢れたスタックの上で動こうとする**ため、そこでさらに #PF が起き、
ダブルフォルトへ昇格する。IST1 によりトリプルフォルトは免れるが、報告は
「ダブルフォルト」になり、**CR2（どのアドレスで溢れたか）が失われる**。

したがって **#PF にも専用の IST（IST2）を割り当てる**。これにより
スタックオーバーフローが「#PF、CR2 = ガードページのアドレス」として正確に
報告される。M4-a で IST1 を用意した仕組みがそのまま流用できる。

実装後、**意図的にスタックを溢れさせて #DF ではなく #PF として報告される
ことを確認する**。M4-b-2 では、ガードページが置けないために #PF ゲートの
Present ビットを落としてダブルフォルトを誘発する代用を採ったが、M5-b 以降は
本来の方法（スタックオーバーフロー）でダブルフォルトも検証できるようになる。

### 4. コンソールとシリアルは「出力するのは 1 箇所」を維持する

M3-c でコンソールをグローバル化せず `Locked<T>` も持たせなかったのは、
**「メインループだけが書く」前提**によるものだった。M5-d で複数タスクが
出力すると、この前提が崩れてカーソル位置とバックバッファが同時に更新され、
表示が壊れる。**シリアル側（`Logger<SerialPort>`）も同じ問題を持つ。**

**M5 では「出力するのはメインループだけ」を制約として維持する。** ワーカー
タスクは共有状態（カウンタ等）を更新するだけで、表示はメインループが行う。
**これは ADR-0018 §5 で割り込みハンドラに課したのと同じ構造**であり、新しい
機構を必要としない。

`Locked<T>` をコンソールに被せる案は**採らない**。フラッシュは 1 回で
数百 KB の転送になりうる（M3-c の実測で起動シーケンス全体では 4.4MB）。
その間ずっと割り込みが禁止されると、**ティックを大量に取りこぼす**。
ADR-0018 §5 がハンドラからの出力を禁じた理由（転送をハンドラ内で走らせない）
と同じ問題が、ロック保持区間として現れる。

本来の解は「メッセージをリングバッファへ積み、1 つの出力タスクが吐く」
（Linux の printk と同じ構造）であり、**M6 のユーザーランドで前景プロセスの
概念と併せて設計する**。

### 5. 既存の不変条件は成立し続ける

- **`Locked<T>` の「取得中は割り込み禁止」**: 成立する。プリエンプションは
  タイマ割り込みからしか起きず、保持中は `IF=0` なので**配送されない**。
  保持区間の途中でプリエンプトされることが構造的にない。
- **`InterruptGuard` を保持したままのスイッチ**: 起きない。同じ理由に加え、
  ガードは `!Send` である（M4-c-1）。将来「自発的 yield」をガード保持中に
  呼ぶコードを書いても、ガードが別コンテキストへ移らないことが型で保証
  される。M4-c-1 で「M5 で意味を持つ」と書いた箇所がここで効く。
- **キーボードのリングバッファ**: `Locked<T>` による排他は成立し続けるが、
  「どのタスクが受け取るか」という設計判断が新たに要る。これは前景プロセスの
  概念に相当するため、**M5 では単一消費者（メインループ）を維持**し、M6 へ送る。

### 6. 検証は「順序」ではなく「不変条件」で行う

M5-c（協調的）までは逐次的に検証できる。「A が yield → B が動く → B が
yield → A が続きから再開」は決定的で、ログの順序で示せる。**タスクごとに
異なる既知値を全 GPR へ入れ、切り替え後に一致すること**を確認する
（M4-b-2 / M4-d-1 と同じ手法）。

M5-d（プリエンプティブ）からは順序が非決定的になるため、判定を不変条件に
変える。

| 不変条件 | 観測方法 |
|---|---|
| 全タスクが進む（飢餓しない） | タスクごとのループカウンタが**全て単調増加** |
| 切り替え回数の会計が閉じる | `切り替え回数 == 各タスクの再開回数の合計`（M4-e の `balanced` と同じ発想） |
| レジスタが壊れない | 各タスクが自分の ID から導いた既知値を全 GPR に入れ、ループのたびに検算。壊れたら即 halt |
| スタックが混ざらない | 各タスクが自分の RSP を読み、自分のスタック範囲内であることを毎周確認 |
| ロックの整合性 | 二重取得検出（実装済み）が発火しないこと |
| ガードページ | 全タスクのガードが無傷であること |

**わざと壊しての確認**も設計に含める。スイッチで 1 本のレジスタを復元し
損ねるビルド、スタック切り替えを省くビルド、RSP0 の更新を落とすビルドを
用意し、上記の検証が実際に発火することを確かめる。

## Alternatives Considered

- **M5 を分割せず一気に実装する**: M4 と同等以上の規模で、非決定的な制御
  フローが加わる。問題が出たときの切り分け軸が多すぎる。却下。
- **コンテキストスイッチ専用の保存領域をタスク構造に持つ**: `IrqContext` と
  重複する。既に完全な退避があるのに二重に持つ理由が無い。却下。
- **割り込みから戻った後に専用ルーチンで切り替える**: 戻った先は中断された
  タスクのコードであり、そこから切り替えると「いつ切り替わるか」が
  タスク側のコードに依存する。プリエンプティブの意味が薄れる。却下。
- **コンソールに `Locked<T>` を被せる**: 転送中ずっと割り込みが禁止され、
  ティックを取りこぼす（§4）。却下。
- **ガードページを使わずカナリアを続ける**: どのタスクが溢れたか分からず、
  動的確保では隣接するものも保証できない（§3）。却下。

## Consequences

- M5-a と M5-b が済むまで、タスクの実装に入れない。ページングが M5 全体の
  律速になる。
- IST が 2 本（#DF 用と #PF 用）になり、その分の静的スタックが増える。
- コンテキストスイッチのコードは、IRQ スタブの一部として `global_asm!` に
  入る。Rust 側は「次の RSP を返す」だけになり、切り替えの本体はアセンブリの
  2 命令程度に収まる。
- 出力が 1 箇所に限られるため、ワーカータスクの診断はカウンタ越しにしか
  できない。M4 の割り込みハンドラと同じ制約が、タスクにも及ぶ。
- SYSCALL/SYSRET を使うかどうかを M5-e より前に決める必要がある
  （GDT の並び順が固定されるため。`deferred-decisions.md`）。
