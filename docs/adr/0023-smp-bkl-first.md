# 0023. SMPはBKL（ビッグカーネルロック）ファーストで実装し、seam整備を先行させる

## Status
Accepted

## Date
2026-07-25

## Context

ADR-0002でシングルコアを前提と決め、SMP対応は「将来のマイルストーン」へ回した。
higher-half B（カーネル高位化・恒等除去）の目処が立ち、SMPをどう実装するかを、着手より先に決める。

現在の排他は`common::critical`の`InterruptGuard`/`Locked<T>`で、「取得中は割り込み禁止（IF=0）」を排他の根拠にしている。
シングルコアではこれが暗黙のうちに「カーネル内に同時に入れるのは1実行文脈だけ」を保証している（ADR-0002 / ADR-0018）。
これは暗黙のジャイアントロックである。

SMPを「各サブシステムを細粒度ロックへ一斉に書き換える」形で入れると、規模が跳ね上がり「細く長く」（architecture §1）が崩れる。

## Decision

### 1. SMPはBKL（ビッグカーネルロック）ファーストで実装する

BKLの定義（本ADRでの意味を明確にする）:

- カーネル入口で取り、ユーザー空間（Ring 3）へ戻るときに離す単一の大域ロック。
- カーネル内に同時に入れるのは1コアだけ。ただし担当コアは時分割で入れ替わる（特定コア固定ではない）。ユーザー空間は全コア並行に走る。
- 効果: 既存の各サブシステム（スケジューラ・アロケータ・ページング・ドライバ）を並行対応へ書き換えずに、正しいマルチコアが即座に成立する。性能向上（細粒度化）は後日・必要な箇所のみ。

現在の`InterruptGuard`/`Locked<T>`（IF=0=排他、シングルコア）は暗黙のジャイアントロックであり、BKLはその明示化とNコアへの拡張である。
作り直しではなく、既存不変条件の昇格として位置づける。

### 2. BKLでも消えない新規作業を明示する

BKLが消すのは「全サブシステムの並行書き換え」であって、次の3点ではない。
これらはBKLでも新規に要る。

- AP（Application Processor）起こし: APIC + INIT-SIPI-SIPI + 16bitリアルモードトランポリン + コアごとのスタック/GS。ACPI（MADT）の解析が前提（ADR-0018 §6でM4がPITを選んだのと表裏）。
- APICへの移行: PIC / PITはSMPでは使えない。
- TLBシュートダウン: あるコアのページテーブル変更を他コアへIPIで伝える。

### 3. seam（継ぎ目）整備を先行させる

BKL本体の前に、既存コードを差し替え可能にする薄い整備を先に行う（先行）。

- 割り込み層をPIC→APIC差し替え可能に薄く抽象化する。
- 排他を`Locked<T>`の型の裏に閉じる（呼び出し箇所の直接`cli`/`sti`を潰す監査）。
- per-CPUアクセサを導入する（当面は単一CPUを返すだけ）。

これらは振る舞いを変えず、SMP非閉塞（higher-half BでPML4[257..510]をper-CPU用に温存、GSベース温存）を実際のper-CPUデータの置き場所へつなぐ。

### 4. 実装時期

- seam整備 = 先行（B完了を待たずに着手しうる、振る舞い不変の整備）。
- BKL本体 + AP起こし + TLBシュートダウン = higher-half B完了後。higher-half Bがきりのいい所で完了し次第、早期着手が有利ならBKLに着手する。SAA-C03最優先・「細く長く」は不変で、これを緩める理由にしない。

### 5. フル細粒度SMPはvisionに据え置く

BKLを分割して性能を上げる（細粒度ロック化）のはroadmapに載せない。
長期目標として`vision.md`に残す。

## Alternatives Considered

- 最初から細粒度ロックでSMP: 全サブシステムの並行書き換えが要り規模が跳ね上がる。完走リスクを上げる。却下（性能が要る箇所だけ後日）。
- SMPをvisionのまま据え置く: 実装方針（BKL）を決めておけば、seam整備を振る舞い不変で先行でき、B完了後の着手が軽くなる。方針だけ先に決めるコストはゼロに近い。roadmap入りとする。

## Consequences

- ADR-0002の「シングルコア前提」は当面有効。本ADRはその「将来のマイルストーン」をBKLで具体化し、roadmapへ移す。ADR-0002はSupersededにしない。
- ADR-0009のSupersede / ADR-0021のAddendum（higher-half B、B-2着手時）で書く「SMP非閉塞」（PML4[257..510]をper-CPU用に温存、GSベース温存）は、"非閉塞"から"BKLで実装する"根拠へ更新する。この接続はB-2のADRで書く。**この申し送りはADR-0024（ADR-0009をSupersede）で果たした**（PML4[256]=direct map、PML4[511]=kernel、PML4[257..510]=BKLのper-CPU用に温存、を数値で記録）。
- `Locked<T>`の中身は、BKL導入時に「IF=0だけ」からスピンロック/アトミック併用へ差し替える。呼び出し側インターフェースを安定させてきた（ADR-0002）ことで影響範囲が狭い。
- APIC / ACPI（MADT）の解禁条件が「BKL本体着手時」に定まる。`deferred-decisions.md`の該当行に申し送りを追記する（BKL本体は未着手のため、確定的な書き換えは着手時に行う）。

## Addendum（S4着手時点）: 取得と解放の点を、Ring 3が無いカーネルに合わせて定義しなおす

§1の定義「カーネル入口で取り、ユーザー空間（Ring 3）へ戻るときに離す」は、**定常的なRing 3を前提としている。現在のカーネルにそれは無い。**
定常状態は`kernel::interrupts`の`run_timer_loop`で、Ring 0のまま`hlt`で待つ。Ring 3へ降りるのは起動途中の2回の遠征だけである。
**§1をそのまま実装すると、最初にBKLを取ったコアが二度と離さず、もう一方のコアがIF=0で永久にスピンする。**
定義を消さずに、現在のカーネルにおける等価物を決める。

### 1. 等価物は「入口で取り、その入口から戻るときに離す」

| 入口 | 取得 | 解放 |
|---|---|---|
| IRQ | `irq_entry`の先頭 | `irq_entry`から戻る直前 |
| syscall（`int 0x80`） | `syscall_entry`の先頭 | `syscall_entry`から戻る直前 |
| 例外・ダブルフォルト・パニック | **取らない**（§3） | —— |
| AP起動直後 | スケジューラへ参加する直前 | 以降は入口の規則に従う |

Ring 3が定常状態になった段（S9以降）で、§1の字面が改めて成立する。**そのときこのAddendumは「Ring 3が無い間の等価物」として履歴に残る。**

### 2. 定常ループは入口ではない。タスクとして扱う

`run_timer_loop`は`sti`してから`hlt`まで**IF=1で走る**。一方、BKLの保持区間はIF=0である（§4）。
**したがって「1周の先頭で取り`hlt`の直前で離す」は成立しない。** 保持したままIF=1で走ればタイマが入り、同じコアが`irq_entry`でBKLを取ろうとして再帰する。

**採るのは「取る区間を1周の中の一部に絞り、その区間だけIF=0にする」である。**
`hlt`に達した時点でBKLは既に離れている。ガードのスコープに`hlt`を含めないので、**`hlt`しながら保持することが構造的に起きない。**

**「定常ループはBKLを取らない」案は採らない。** このループは`SCANCODES`（`Locked<T>`）・コンソール・i8042とPICのポート・シリアルを触る。触るものがper-CPUかアトミックだけなら成立するが、成立していない。
**列挙で守る形になり、列挙に無い形を静かに通す。**

**取得はcliが先である。** `cli`してからフラグを立てる。逆にすると、フラグを立ててからcliするまでの窓に割り込みが入り、同じコアが再帰する。`Locked::lock`が同じ順序を同じ理由で採っている。

### 3. 例外とパニックはBKLを取らない

`exception_entry`は`-> !`のfail-fastで、ダンプを出して停止する。**取れば、保持者が例外で死んだときに他コアが永久に待つ。**
代償はダンプが他コアのログと混線しうることで、これは受け入れる（どちらも停止する経路であり、書けないことの害のほうが大きい）。
**「取らない」ことは入口の分類の列挙に明示する。** 書かなければ、後から「取り忘れ」として足されうる。

### 4. 保持区間はIF=0の区間であり、BKLは再帰しない

**不変条件は「BKLを保持する区間 = IF=0の区間」である。** これが成り立つ限り、保持中に割り込みが入らないので、同じコアが別の入口から再取得することはない。
**再帰は構造的に起きないので、再帰を許す形にしない。** 保持者のCPU番号を持ち、自分が保持者なら停止する（`Locked<T>`の二重取得検出と同じ形）。
LinuxのBKLは再帰だったが、あちらは保持したままスリープする形を許していた。**ここは許さないので、前提が違う。**

**（2026-08-02 後日追記）** APを実際にスケジューラへ参加させたときの決定は**ADR-0026**にある。**本Addendumの§5はその前提の1つである。**
**内容はADR-0026を見ること。ここでは要約しない**——要約は古くなるので、指すのは番号だけにする。

### 5. タスクはBKLの外を走る。BKLは`GPR_BUF`を守らない

プリエンプティブスイッチは`irq_entry`が次タスクのRSPを返し、スタブが`iretq`する形なので、**BKLの解放は`iretq`より前に来る。**
したがってタスク本体はBKLを持たない。**「BKLがあるから`GPR_BUF`は安全」は成立しない。**
`GPR_BUF`の解禁条件（asmが自コアのスロットを選べる手段）は、BKLが入っても満たされない。
**帰結として、タスクのコア間移動を実装しない。** 負荷分散を実装しないことの帰結ではなく、`GPR_BUF`の安全がそれに依存しているからである。理由が違うので別に書く。

## Addendum（2026-08-13、S11-5）: `spawn`で§1の字面が成立した。Ring 3へ降りる間はBKLを離す

### 何が起きたか

S4のAddendumは「§1の定義はRing 3を前提としており、現在のカーネルにそれは無い」と書き、
等価物として**「入口で取り、その入口から戻るときに離す」**を置いた。
そして**「Ring 3が定常状態になった段（S9以降）で、§1の字面が改めて成立する」**と申し送っていた。

**`spawn`がその場所である。** 親のシステムコールの処理の中で子をRing 3で走らせ、子が終わったら親の続きへ戻る。
**入口からはまだ戻らないが、Ring 3へは降りる。** 2つの定義が初めて食い違う。

### 決定

**Ring 3へ降りる間はBKLを離す。** §1の字面どおりである。

`syscall_entry`は`SYS_SPAWN`のときだけ、パスをユーザー空間から写した後にガードを落とし、
**子が終わって戻ってきたところで取り直す。**
`SYS_EXIT`が`syscall_entry`に在るのと置き場所の理由は同じである
（**あちらは制御が戻らないから、こちらはロックを手放すから**）。

### 保持したまま降りると壊れる。実測ではなく構造で言える

- **子のシステムコールが`syscall_entry`へ入り、同じコアがBKLを取り直す。**
  §4の再帰検出が発火して停止する。**`hello`は`write`と`exit`を発行するので、確定的に起きる**
- **Ring 3は`RFLAGS = 0x202`（IF=1）で走る。** タイマが動いている段では`irq_entry`が同じことをする。
  **§4の不変条件「BKLを保持する区間 = IF=0の区間」に、保持したままの降下は直接反する**

**S11-2の入れ子の検証（`SYS_NEST_PROBE`）はこれを踏まなかった。**
あれの内側は`cli`1命令で、**入った瞬間に#GPで畳んで戻る。**
**例外経路はBKLを取らない**（§3）ので、再帰にならなかった。
**入れ子が動くことは示していたが、「子がシステムコールを発行する入れ子」は示していなかった。**

### 離す区間はどこか

**ユーザーメモリへ触り終えてから離す。** パスの写しは`copy_user_path`だけで、
あれは**「検証と読みが実質アトミック」**であることに依っている（`kernel/src/syscall.rs`の`copy_from_user`のTOCTOUの注記）。
**その区間はBKLの内側に残す。**

**写像と畳みはBKLの外で走る。これは新しい形ではない。**
起動時の`load_user_program`は最初からBKLを保持せずに写像しており（`kernel_main`はガードを持たない）、
**畳むときだけ自分で取る。** したがって**保持したまま入ると、そこでも再帰になる。**
**離すことで、あの関数がそのまま使える。**

### 失うもの

- **システムコールが不可分でなくなる。** `spawn`の途中で他コアがカーネルへ入れる。
  **`spawn`が触る共有物は、離す前と取り直した後で変わりうる。**
  現在触っているのは、フレームアロケータ（`ADR-0030`の貸し出しが排他を持つ）、
  隔離（`Quarantine`はローカル）、`crate::vfs`の`CURRENT_FILES`（`Locked<T>`）、
  そして遠征の記録（深さごとに分けてある）である。**どれも離した区間をまたいで前提を置いていない。**
- **取り直しに失敗する形が増えた**わけではない。`acquire`は待つか停止するかで、返らない道は無い。

### 条件つきの安全（失効条件つきの決定）

- **子が終わるまで親は動かない。** 同期の`spawn`だからである。
  **失効条件——非同期の`spawn`（子を起こして即座に戻る形）を作ったとき。**
  そのとき親はロックを持たないまま「子が走っている」状態で続きを実行するので、
  **離す・取り直すの対応が1対1でなくなる。**
- **離した区間でTLBの世代が上がりうる。** 取り直しの`acquire`が`flush_if_generation_is_stale`を通るので、
  **取り直した側は最新の写像を見る**（`ADR-0027`の「順序はBKL自身が与える」がそのまま効く）。
  **失効条件——`acquire`から世代フラッシュを外したとき。**

## Addendum（2026-08-13、S11-11）: 例外経路がBKLを取らない根拠を、コア数から独立させる

### 何が発火したか

S4のAddendum §3は`NON_ACQUIRING_ENTRIES`の`exception`について、
**「遠征がAP起こしより前の単一コア区間に閉じていて、戻った先で他コアと競合しないから安全」**と書き、
**「Ring 3が定常状態で走る段（S9）で再評価する」**と申し送っていた。

**S11-11でシェルが定常状態で走るようになった。AP起こしより後である。根拠が消えた。**

### 評価の結果——決定は生き延びる。根拠を書き直す

**主たる理由は変わらない。** 「取れば、保持者が例外で死んだときに他コアが永久に待つ」は、
**コア数にも実行時期にも依存しない。** ダンプを出して停止する経路でロックを取る形は、いつでも採らない。

**二次の心配（戻った先で競合しないか）を、いまのコードに当てて数え直した。**
畳みが戻る先は`ring3::enter`の末尾で、そこから`run_loaded_program`・`load_user_program`・`spawn`の順に帰る。
**BKLの外で触るものは5種類ある。**

- **`enter`の末尾が触る静的**（`EXCURSION_DEPTH`・`CURRENT_RECOVERY`・RSP0・ユーザー窓）。
  **APはRing 3へ入らないので、これらを書く者は常に1つである。**
  RSP0はTSSだが、**TSSはper-CPUである**（`gdt::set_rsp0`は`PerCpu::this_cpu_ptr`を通す）
- **`run_loaded_program`の末尾が触る前景と表**（`input`の`FOREGROUND`・`PENDING`、`vfs`の`CURRENT_FILES`）。
  **`FOREGROUND`は`compare_exchange`で取る。残りは`Locked<T>`である**——
  **`Locked<T>`は競合しても黙って壊れず、保持者を出して停止する**（`common::critical`。S4-b-1で保持者を足した）
- **`load_user_program`の後始末**（空間の破棄）。**あれは自分でBKLを取る**（`KernelEntry::SteadyLoop`）
- **`spawn`の後始末**（記録の復元と会計）。**フレームアロケータの排他は`compare_exchange`の旗が持つ**（`ADR-0030`）。BKLに依存していない
- **シリアル**（判定行の出力）。**これだけが排他を持たない。**
  ただし**BKLがシリアルを直列化していたことは一度も無い**——`ap_heartbeat_loop`も
  **BKLの外からCOM1へ書く**（`smp.rs`。「行頭にコア番号を置いて、混ざってもどのコアの行かが分かるようにする」と書いてある）。
  `SerialPort`は使うたびに作るポートI/Oで、**共有された記憶を持たない。混線するのは行の途中までである**

**したがって、畳みが戻った先でBKLの外にいる区間は、per-CPUの静的か、自分で排他を取るもの
（競合すれば停止するものを含む）しか触らない。例外はシリアル1つで、それは畳みに固有の話ではない。**

**根拠を「単一コア区間に閉じている」から「戻った先が、per-CPUか自前の排他を持つものしか触らない」へ書き直す。**
**新しい根拠はコア数に依存しない。**

**最初は3種類と数えた。** `enter`の末尾と2つの後始末だけを見て、
**その間の`run_loaded_program`の末尾と、全体に散らばるシリアルを飛ばしていた。**
**「数えている範囲は、数えた側が知っている範囲でしかない」を、根拠の数え上げそのもので踏んだ。**
**数え直したものを載せる**——3種類のまま失効条件を書くと、**次に数え直す者が誤った基準と突き合わせる。**

### これは3つ目の型である

**決定の記述を直す場面には、これまで2つの型があった。**

- **Addendum**——**書いた時点では正しく、状況が変わって成り立たなくなった。**
  本文は残し、後から起きたことを足す（`ADR-0027`のS8のAddendumがこれである）
- **本文の差し替え**——**書いた時点で既に誤っていた。**
  残しておくと誤りを参照させるので、本文を直す

**今回はどちらでもない。決定は生き延び、根拠だけが置き換わった。**
「取らない」という結論も、その主たる理由も一字も変わっていない。
変わったのは**二次の心配に対する答えの立て方**で、
**「まだ他コアが居ない」から「他コアが居ても触るものが被らない」へ移った。**

**この型を区別する実利は、失効条件の宛先が変わることである。**
Addendumなら「状況が変わったか」を見張るが、**根拠の置き換えでは「新しい根拠が数え上げたものが増えていないか」を見張る。**
**下の失効条件は後者の形で書いてある。**

### 失効条件（書き直した根拠に対して）

- **畳みが戻った先で、BKLを取らずに共有物を触る経路を作ったとき。**
  いまは上の5種類しか無いので数え上げられる。**増えたらここを数え直すこと。**
- **APがRing 3へ入るようになったとき。** `enter`の末尾が触る静的の書き手が2つになる。
- **`Locked<T>`が競合で停止しなくなったとき**（待つ形へ変えたとき）。
  **2番目の「競合すれば停止する」が消える。**
