# 0048. プロジェクトの知識はdocsに置き、Claudeへの指示だけを`.claude`に置く

## Status

Accepted

## Date

2026-08-28

## Context

`ADR-0031`でエージェント向けの設定ファイルを追跡下へ入れ、その後`CLAUDE.md`を索引へ分割した
（`roadmap.md`の「T. `CLAUDE.md`の分割」）。**`ADR-0031`は参照の書き方（節番号ではなく名前）まで
決めたが、同じ記述が両側に在るときにどちらが本体かを決めていない。**

**決めていなかった費用が、実測で2度出た。** どちらも「片方だけが古くなる」形である。

- **公開前の監査の手順が`.claude`と`docs/verification-coverage.md`の両方に在り、想定する文字の
  一覧がdocs側だけ4字古かった**（`×`・`±`・`µ`・`⟹`）。**どちらが正しいかは、読んだだけでは
  分からない。**
- **`ADR-0036`がI/O待ちを設計し直した後も、`.claude`と`docs/architecture.md`の両方が
  「S13で設計し直す」と書いたままだった。** **片方を直したときに、もう片方に気づいた。**

**機械で洗った範囲と結果**（2026-08-28）。`.claude`のMarkdown 10ファイルと`docs`+`README`の
Markdown 57ファイルの間で、20字以上の完全一致を集計すると19件出た。**振り分けた後は3件である。**
**洗い方の限界は、写しは見つかるが言い換えは見つからないことである**——監査の二重化は目視で
見つけており、機械が当てたのはその中の完全一致だけである。

**上位の方針との関係。** この体制は「二重に持つと片方だけが古くなる」を繰り返し書いており
（`ADR-0045`ほか）、実際にその形で`userlib.rs`を抽出している。**同じ規律を、文書の側にも当てる。**

## Decision

**記述の置き場所を、次の基準で決める。**

- **プロジェクト自体の知識**（設計 / 契約 / 外の道具の使い方 / 実測）
  → **`docs/`が本体。`.claude`と`CLAUDE.md`は指すだけで、内容を持たない**
- **Claudeへの指示**（実装して提示し止まる / 報告の型 / 承認前にコミットしない /
  破壊を足す基準）
  → **`.claude`か`CLAUDE.md`が本体**

**参照は節番号ではなく名前で行う**（`ADR-0031`のまま。番号は編集で動く）。

### 境目が微妙なものの扱い

**両方の性格を持つ記述は、「実測・外の道具・装置・コードの契約に依存する部分」と
「作業者の振る舞いだけを縛る部分」に割り、前者を`docs/`、後者を`.claude`か`CLAUDE.md`へ置く。**
**割れないほど短いなら、実測を含む側（`docs/`）へ寄せ、指示の側は名前で指す。**

**基準を「人も回す手順ならdocs」にしない。** **誰が回すかは変わるためである**——実際、
公開前の監査はキーワードgrepの一部が静的検査へ移っており、人の手順と機械の手順の境目は
動いている。**「実測を含むか」は記述に固有で、動かない。**

**古くなる速さが違うことが、この割り方の理由である。** 実測に依存する記述は、装置とコードが
動くたびに偽になりうるので、実測と検査の在り処（`docs/`）と同じ場所に置く。
**振る舞いの指示は、運用者の判断でしか変わらない。**

### 「外の道具」の範囲

**ここでいう外の道具は、成果物を作るか判定する道具である**（`e2fsck` / `dumpe2fs` /
`debugfs` / `mke2fs` / QEMUのモニタ）。**作業者が自分の作業環境を扱う道具は含まない**
（`pkill` / `git`の使い方 / Bashツールの`run_in_background`）。

**この区別は、基準を実際の行へ当てて出た。** 「プロセスを止める手順」は`pkill`という
外の道具の実測（**パターンが自分のコマンドラインに一致して自分を殺す**）を含むが、
**それはZaytOSについて何も語らない。** **成果物の知識ではないので、指示の側に残る。**

## 判定の表

**基準は抽象なので、実際の判定器になるのはこの表である。**
**新しく迷う記述が出たら、ここへ1行足すこと。** **表が育たないと、基準だけが残って
判定が属人的になる。** 足すときは「寄せた先」と「なぜ」を必ず並べる。

| 記述 | 本体 | なぜ |
|---|---|---|
| 公開前の監査の手順 | `docs/verification-coverage.md` | 想定する文字の一覧が実測である（実際、docs側だけ4字古くなった） |
| 同期方針（BKLと`Locked`の向き） | `docs/architecture.md` | コードの契約である（`ADR-0036`で契約が動いた） |
| パニックポリシー | `ADR-0004` | 設計の決定である |
| シリアルログ最優先 | `ADR-0003` | 設計の決定である |
| 実装ループの内訳（4構成・clippy・fmt） | `docs/coding-standards.md` | ビルドの構成という実測に依存する |
| ビルド環境の再現性（OVMFとEDK2） | `docs/architecture.md`の「技術スタック」 | 成果物を作る道具の使い方である |
| QEMUの引数と`-d int`を落とす例外 | **未移動**（いまは`.claude`側） | 実測を含むのでdocsへ寄る。移動は別のコミットで行う（下記「適用」） |
| ループを止めて人間へ渡す条件 | `CLAUDE.md` | 作業者の振る舞いだけを縛る |
| 報告の型 | `.claude/output-styles/zaytos-report.md` | 作業者の振る舞いだけを縛る |
| 破壊を足す基準 | `CLAUDE.md` | 作業者の振る舞いだけを縛る |
| 承認前にコミットしない | `CLAUDE.md` | 作業者の振る舞いだけを縛る |
| プロセスを止める手順 | `.claude/skills/stop-a-process/SKILL.md` | 実測を含むが、成果物についての実測ではない（上記「外の道具の範囲」） |
| 一時的な破壊・変更の手順 | `docs/coding-standards.md` | 手順の本体は既にdocs側にある。`.claude`は指すだけ |

**表の行が増えるほど、基準の当て方が具体になる。**
**「どれに似ているか」で決められる状態を保つことが、この表の目的である。**

## 適用——QEMUの「沈黙の失敗を必ず可視化する」

**この節は基準に従えば`docs/`へ寄る。** 実測を含むためである（既定構成の120秒の起動で記録が
5.6GiB、事象のうち`int 0x80`が99.7%、手で触る起動で毎分約2.9GiB）。

**いまは逆向きになっている。** 本体は`.claude/rules/qemu-and-build.md`に在り、
**6箇所がそこを指している**——`docs/coding-standards.md`・`docs/deferred-decisions.md`・
`docs/roadmap.md`・`xtask/src/main.rs`の3箇所である（実測。2026-08-28）。
**`docs`が`.claude`を指す形になっており、基準と実態がここだけずれている。**

**移す作業はこのADRでは行わない。別のコミットで行う。**
理由は2つある。**(1) ADRは基準を決める文書であり、移動は振る舞いを変えない作業である**
（T-1で移動と編集を分けたのと同じ形。混ぜるとどちらの差分も読めなくなる）。
**(2) 6箇所の参照が裏返るので、移動だけのコミットにして差分を読める形にしたい。**

**移す先は決めない**（下記「決めないこと」）。

## Alternatives Considered

**案2（`.claude`を本体にする）。却下。**
**実際にQEMUの件がその形になっており、動く。** それでも採らない理由は2つある。

- **`docs`は人も読む。** 公開リポジトリを実装内容そのもので評価できる状態に保つのが
  `ADR-0031`の目的で、**知識が`.claude`にしか無いと、その目的が薄まる。**
- **`.claude`はClaude Codeの仕組みに依存し、版で挙動が変わる。実測済みである**（版2.1.215）
  ——**rulesは`paths:`に一致するファイルをReadしたとき1回だけ入る**（作成でも編集でも
  `cat`でも入らない）。**skillsは作成した同じセッションでは入らない。**
  **`/skills`というコマンドはこの版に無い**（`/skills-reload`が在る）。
  **仕組みが変われば、置き場所ごと読まれなくなりうる。** **知識をそこへ置くのは賭けである。**

**案3（両方に置き、片方を「要約」とする）。却下。**
**要約は必ず古くなる。** `CLAUDE.md`を索引にしたときと同じ理由で、
**索引の1行は在り処だけにし、内容を1文字も持たせない**と決めてある。

## 決めないこと

- **`docs/`の中のどこが本体か**（ADRか`coding-standards.md`か`architecture.md`か）。
  **この基準は`docs`と`.claude`の境目だけを決める。** `docs`の中の配置は、
  `.claude/skills/record-a-decision/`が指す既存の運用に従う
- **コード中のdocコメントとの関係。** **今回洗っていない範囲である**——重複を洗ったのは
  `.claude`と`docs`+`README`の間だけで、`kernel`・`common`・`xtask`のコメントは見ていない。
  **洗っていないので、二重になっているかも分かっていない**

## ADRを書く条件に当てた結果

- **条件(1) 複数の有力案から一つを選ぶ——当たる。** 上の3案である。
- **条件(2) 後から変更すると作り直しが生じる——当たる。**
  **本体の位置を戻すと、参照を全部裏返すことになる。** 実際、QEMUの件だけで6箇所ある。
- **条件(4) 将来の保守者が単純化すると壊す——当たらない。** 機構ではない。

## Consequences

- **索引が指す先の実在は、機械で両向きに見ている**（`cargo xtask check`の
  `agent index links`）。**足した時点で既存の漏れが1つ出た**——hookと`settings.json`が
  索引から指されていなかった。**この基準を守るかどうかは、そこまでは見ない**
  （**見ているのは「指した先が在るか」だけで、「内容がどちらに在るべきか」は見ない**）
- **言い換えの重複は機械で見つからない。** 完全一致しか当たらないので、
  **同じ規則が言い換えで両側に在る状態は残りうる。目視に頼る**
- **`.claude`が薄くなるほど、Claude Codeの版の変化に対して弱くならない。**
  逆に、**指すだけになった分、`.claude`だけを読んでも文脈が足りない**——
  必ず`docs`まで辿ることになる
- **基準と実態が1件ずれたまま残る**（QEMUの件）。**移すまでのあいだ、
  この文書がそのずれを明示している**

## Addendum（2026-08-28、移動が済んだ）

**「適用」で予告した移動を行った。** **本文は1字も変えていない**（移す前と移した後で本文の
md5を取り、一致することを確かめた。30行）。**置き先は`docs/coding-standards.md`の
「回帰チェックの必須条件」の中である**——**`--manual`の例外が手順の話で、すぐ下の目視の手順と
同じ話だからである。**

- **指していた6箇所を裏返した**（`docs/coding-standards.md`は自己参照になったので「上の」に変えた）。
- **判定の表の「未移動」の行は、これで解消した。**
- **索引の検査は両向きとも緑のままである**——`.claude/rules/qemu-and-build.md`は
  `CLAUDE.md`の「ビルド環境の再現性」から引き続き指されている。

**移動で債務が1つ出た。** **`CLAUDE.md`は文体の規則1（和文と英数字の間に半角スペースを
入れない）の適用対象ではないが、`docs/`は対象である。** **移した30行は、スペースを入れる
書き方のままである。** **一括で直すと見出しの名前が変わり、名前で指している参照を同時に
直すことになる。** **規則1には機械の検査が無い**ので、`docs/coding-standards.md`自身の
「検査の無い規則は必ず腐るので、既存分を一括で直しても検査が無ければ同じ状態へ戻る」に従い、
**検査を入れるときにまとめて直す**（`deferred-decisions.md`に行を置いた）。
