# 0001. 保護機構ありのモノリシックカーネルを採用する

## Status
Accepted

## Date
2026-07-16

## Context
ZaytOSの主目的は学習である。
OSの基本機能を理解しながら自作すること自体が狙いのため、メモリ保護（ページング、ユーザー/カーネル権限分離）は学習対象そのものであり、省略できない。

一方でカーネル方式には複数の選択肢があり、それぞれ「堅牢さ」の意味と個人開発での完走可能性が異なる。
既存OSを並べて検討した:

- Linux: モノリシック・保護あり。数十年・数千人規模の蓄積で、個人が模倣する規模ではない。参考にとどめる。
- MikanOS: 小規模モノリシック・保護あり。個人が完走可能な現実的な落としどころ。
- TempleOS: Ring-0のみ・保護なし・単一アドレス空間。保護機構を複雑さの主要因とみなし丸ごと排除することで単独完走を実現した極端な最小主義。
- Redox OS: マイクロカーネル・保護あり・Rust製。設計思想は堅牢だがIPC等の実装コストが重く、動くものが完成するまでの距離が長い。

「堅牢さ」には(1)保護機構を厚くして被害を局所化する防御的な堅牢さと、(2)保護機構を削り複雑度を下げる単純さによる堅牢さ、の2方向がある。
本プロジェクトが意図するのは(1)である。

## Decision
保護機構あり（ページング、ユーザー/カーネル権限分離を持つ）のモノリシックカーネルを採用する。

## Alternatives Considered
- **マイクロカーネル（Redox型）**: 設計思想としては最も堅牢だが、IPC設計・実装コストが重く、初手では完走リスクが高い。却下（将来的な分離導入は構造で意識するにとどめる）。
- **保護なし・Ring-0のみ（TempleOS型）**: 学習目的と矛盾する。保護機構こそ学びたい対象であるため却下。
- **Linuxをそのまま参照した大規模モノリシック**: 個人開発の規模を超える。却下。

## Consequences
- 実装コストは中程度に抑えられ、個人開発で完走が現実的。
- 保護機構を自作するため、ページング・権限分離を実地で学べる。
- 将来マイクロカーネル的な分離を導入する場合は相応の書き直しが必要になる。
- Redoxのようなアーキテクチャレベルの強い分離は得られない（Rustの言語レベルの安全性で一部を補う）。
- 規模の暴走を避けるため、モノリシックでも機能スコープはroadmapで厳格に管理する。
