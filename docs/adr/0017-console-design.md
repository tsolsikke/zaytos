# 0017. 画面コンソールはバックバッファとダーティ矩形で構成し、`\r` は行を消去する

## Status
Accepted

## Date
2026-07-20

## Context
M3-c で画面コンソール（`core::fmt::Write` による文字出力、折り返し、
スクロール）を実装する。

フレームバッファは PCD（キャッシュ無効）でマップしている（ADR-0015）。
書き込みはキャッシュに載らず、読み出しはさらに遅い。したがって、
スクロールをフレームバッファ間のコピーで実装したり、文字を書くたびに
画面全体を転送したりすると実用にならない可能性がある。

**転送コストの実測は、現時点ではできていない。** rdtsc でプローブを入れて
計測したが、`cargo xtask run` が QEMU に `-accel kvm` を渡しておらず、
TCG（純粋エミュレーション）上での測定になっていた。キャッシュ有効な RAM への
書き込み（528 cyc/px）とキャッシュ無効なフレームバッファへの書き込み
（556 cyc/px）がほぼ同速で出ており、測れていたのはメモリ階層ではなく QEMU の
命令エミュレーション負荷である。したがって、この数字から「転送は高い／安い」
のどちらも結論できない。

この状況を踏まえ、**転送コストがどちらに転んでも損をしない設計**を選ぶ。

## Decision

**1. バックバッファを通常 RAM に置き、フレームバッファと同じ形式・同じ
stride で持つ。**
描画は全てバックバッファ（キャッシュ有効）に対して行い、フレームバッファへは
転送のみを行う。形式を揃えるのは、転送を単純なコピーにするため。転送は
キャッシュ無効側への書き込みで最も高い工程であり、そこに 1 ピクセルごとの
形式変換を挟むのは損にしかならない。色からピクセル値への変換は、描画時に
キャッシュ有効な RAM 上で済ませる（M3-a の `Color::to_pixel`）。
stride を揃えるのは、行のオフセット計算を両者で同一にし、`stride == width`
の環境では全体を 1 本の連続コピーにできるようにするため。

**2. 未転送範囲を外接矩形 1 個で追跡し、その範囲だけを転送する。**
領域のリストにはしない。逐次的なテキスト出力では外接矩形は十分に小さく
収まる。左上と右下だけを更新したような最悪の場合は全画面を送ることに
なるが、それは素朴な全面転送と同じであり、それより悪くはならない。
行ごとのダーティフラグ配列は、飛び飛びの更新に強くなるが、必要だという
根拠が無いので入れない。

**3. フラッシュ点は `write_fmt` 1 回ごと。**
`core::fmt::Write::write_fmt` を override し、`write!` / `writeln!` の
呼び出し 1 回につき末尾で 1 回だけ転送する。加えて明示的な `flush()` も
公開する。

`common::log::Logger` は 1 ログ行を `writeln!` 1 回で書くため、この方式で
ログ 1 行 = 転送 1 回になる。Logger 側の変更は不要。ただしこれは暗黙の
契約なので、`common::log` に「1 ログ行が `write_fmt` 1 回で書かれる」ことを
固定するテストを置く。

**4. スクロールはバックバッファ内の素朴なメモリコピーで実装する。**
表示開始行をずらすリングバッファ方式は採らない。スクロール時のコピーは
キャッシュ有効な RAM 内で完結しており、バス往復は発生しない。一方、
スクロール後は画面全体が変わるため、**フレームバッファへの転送コストは
どちらの方式でも同一**である。つまりリングバッファが節約するのは安い側だけで、
その対価として転送を 2 本に分割する複雑さを負う。割に合わない。

**5. `\r` は行頭へ戻すと同時に、その行を消去する。**
これは厳密な端末の挙動（カーソル移動のみ）からの**意図的な逸脱**である。
理由: `\r` の後に短い文字列で上書きすると、直前の行に全角文字があった場合に
**その後半セルだけが画面に残る**。半角 1 セルで上書きしても全角 2 セルは
消えないためである。行ごと消去すればこの不整合が構造的に発生しなくなり、
セルごとの占有種別（先頭セル / 後続セル）を管理する必要もなくなる。

**6. カーソルは前進と行頭復帰しかしない。**
対応する制御文字は `\n` / `\r` / `\t` の 3 つに限定する。バックスペースは
扱わない（キーボードは M4）。この制約により、「進むのは常にグリフ幅ちょうど」
「折り返しでグリフを分割しない」の 2 つが成り立ち、カーソルが全角セルの
途中を指さないことが不変条件として導かれる。セルごとの占有種別を持つ必要が
無いのはこのためである。

**7. 行末に収まらない全角は、残ったセルを空白のまま次行へ送る。**
半端に描かない。

これに関連して、**桁数が最も広いグリフを収められない格子は構築時に拒否する。**
桁数が 1 の格子に全角（2 セル）が来ると、「収まらないので折り返す →
折り返してもまだ収まらない」を繰り返して前へ進めなくなる。この状態は
`Grid::new` で「桁数 >= `MAX_GLYPH_WIDTH_CELLS`」を検証することで到達不能に
する。入口の不変条件で防ぐのであって、事後に取り繕うのではない。

`advance` に残してある「収まらないグリフを描かずに捨てる」処理は**防御的な
措置**である。構築時の検証を通っていれば、契約どおりの `width_cells` に対して
は到達しない。契約を破る値が渡された場合にのみ働き、そこで停止させるよりは
文字を失う方を選ぶ（進行不能を避けるため）。この二重化は、fail-fast の方針
（ADR-0004）に対して「まず入口で落とす、それでも通り抜けたら停止だけは
避ける」という関係にある。

格子が想定するグリフ幅の上限と、フォントに実際に収録されている最大幅が
食い違っていないことは、`console` のテストで機械的に検証する。日本語
（全角 2 セル）を収録した後もこの関係が保たれることを保証するため。

**8. コンソールはグローバルに置かず、ロックも持たない。**
現在のカーネルは直線的な起動シーケンスであり、離れた場所から出力する要求が
まだない。グローバルにしなければ `unsafe impl Sync` が不要になり、ロックが
存在しなければパニック時のデッドロック懸念（ADR-0013 Addendum）自体が
発生しない。割り込みハンドラから出力したくなるのは M4 であり、そのロック
設計は割り込み安全性のモデルと一体で決める。

**9. `Logger` をマルチシンク化しない。**
守るべき制約は「シリアル出力の経路を画面出力の経路に依存させないこと」で
ある。`common::log::Logger` に複数の出力先を持たせると、シリアル出力が
画面出力の経路を通ることになり、画面側の不具合（不正なポインタ、
バックバッファ確保失敗）がシリアルログを道連れにできる構造になる。
シリアルを唯一の信頼できる観測手段としてきた方針（ADR-0003）と正面から
衝突する。

「両方に出す」場合は、`Logger` ではなく呼び出し側に薄いヘルパを置き、
**必ずシリアルを先に**書く（`kernel::main::log_both`）。

この制約は `Logger` への変更を一切禁じるものではない。出力先を増やさない
限り、`Logger` に手を入れてよい。実際、M3-c-3 で
`Logger::emitted_line_count`（実際に書き出した行数を数える）を追加している。
これは出力先を増やさず、画面側への依存も作らないため、上記の制約に抵触
しない。

**10. バックバッファは `allocate_contiguous` で確保し、マップ済みを検証する。**
サイズは `stride * height * 4` から算出する（解像度に追従させる。定数に
しない）。確保後に `MappedRanges::contains_range` でマップ済みを確認する
（M2 以来の不変条件を踏襲）。確保に失敗した場合は fail-fast し、要求フレーム数・
空きフレーム総数・**最大連続空き範囲**をログに出す。「空き自体が不足」なのか
「空きはあるが連続領域が足りない（断片化）」なのかをログだけで判別できる
ようにするため。

**11. 転送は `copy_nonoverlapping` で行い、`write_volatile` は使わない。**
1 ピクセルずつの `write_volatile` ループでは、全面転送だけで 100 万回の
書き込みになる。行単位のコピーを取る。`copy_nonoverlapping` は volatile では
ないが、`memcpy` 相当の intrinsic として扱われ、書き込み先が整数から作った
生ポインタであるため、コンパイラがその領域を死んでいると証明する材料もない。
消去される現実的な懸念は無い。

ただし保険として、転送の直後に `compiler_fence(Ordering::SeqCst)` を置く。
命令を生成しないためコストはゼロで、コンパイラによる並べ替えだけを禁じられる。

グリフの描画（バックバッファへの書き込み）は `Framebuffer` の描画処理を
そのまま使う。描画コードを二重に持たないため。通常 RAM に対する
`write_volatile` は無駄だが、描画は安い側であり、実装を分けて食い違わせる
危険の方が大きい。一括操作（全面クリア・スクロール・行消去）だけは
スライスとして `fill` / `copy_within` を使う。

**12. 起動時テストパターンは feature フラグで切り替える。**
M3-a の描画テストパターン（RGB の四角・外周枠・はみ出し矩形）はフレーム
バッファへ直接描いており、コンソールは変更範囲しか転送しないため、描いた
ままにするとコンソール領域の外に残骸が残り続ける。

`gfx-test-pattern` feature で切り替え、通常起動では描かない。有効時は
テストパターンだけを描いてコンソールを起動しない。`cargo xtask run --gfx-test`
（および `screenshot --gfx-test`）で有効化する。

既存の `panic-test` feature + `cargo xtask run --panic-test` と同じ仕組みに
揃えてある。診断用の起動モードを増やすたびに別の仕組みを作らない。

**13. 画面へ流すのはコンソール構築以降のログだけとする。**
コンソールはバックバッファの確保にフレームアロケータを必要とし、フレーム
バッファへ書くには CR3 切り替え後である必要がある。したがってコンソールは
起動シーケンスの途中でしか作れず、それより前のログはシリアルにしか出ない。

起動ログをリングバッファに溜めてコンソール構築時にまとめて流す方式は採らない。
シリアルログが全量を持っている以上、画面が後半だけでも診断能力は落ちない。
バッファ用のメモリと溢れた場合の扱いを決める必要が生じるが、それを必要と
する根拠がまだ無い（先回りの作り込みの回避）。

これは異常な構造ではなく、実機の Linux も同じである。起動初期のログは
printk のログバッファに溜まり、コンソールドライバが登録されるまで画面には
出ない。画面が途中から始まるのは一般的な挙動である。

ただし画面だけを見た人が誤解しないよう、**コンソール構築時に画面の先頭へ
「ここより前のログはシリアルのみ」と、省略された行数を出す**。行数は
`Logger` が実際に書き出した行を数えて求める（`emitted_line_count`）。

**14. 画面とシリアルの両方へ出す場合、必ずシリアルを先に書く。**
`log_both` ヘルパはシリアルへ書いてから画面へ書く。順序を入れ替えると、
コンソールの不具合がシリアルログを道連れにできる構造になる。この順序は
実装のコメントで固定してある。

## Alternatives Considered

- **バックバッファを持たず、フレームバッファへ直接描く**: M3-a/M3-b と同じ
  やり方で、実装は最も単純。しかしスクロールがフレームバッファからの読み出しを
  伴い、PCD では読み出しが特に遅い。文字が流れ始めた時点で破綻する可能性が
  高い。却下。
- **バックバッファを内部正規形式（常に `0x00RRGGBB` 等）で持つ**: 形式非依存の
  ピクセル操作ができるようになるが、その要件が無い。転送のたびに全ピクセルを
  変換することになり、最も高い工程を重くする。却下。
- **1 文字ごとにフラッシュする**: 実装は単純だが、転送の往復が文字数分だけ
  発生する。転送が安かったとしても無駄でしかない。却下。
- **改行ごとにフラッシュする**: 一見自然だが、改行を含まない `write!` が
  画面に出ないことになる。ハングした際に書きかけの行が見えないのは、
  観測可能性を最優先してきた本プロジェクトの方針（ADR-0003）に反する。却下。
- **リングバッファ方式のスクロール**: 上記 4 のとおり、安い側だけを最適化して
  複雑さを増やす。却下（実測して RAM コピーが問題になれば再検討）。
- **`\r` をカーソル移動のみとする（厳密な端末挙動）**: 互換性は高いが、
  全角文字の後半セルが残る不整合を、セルごとの占有種別管理で別途解決する
  必要が生じる。現時点でその複雑さを負う理由が無い。却下（下記 Consequences の
  とおり、VT シーケンス対応を行う場合は再検討する）。
- **セルごとの占有種別（先頭 / 後続）を配列で持つ**: バックスペースや任意位置への
  カーソル移動を正しく扱うには必要になる。しかし M3-c の制御文字の範囲では
  不要であり、160x50 = 8000 セル分の状態を先回りで抱えることになる。却下
  （バックスペースを導入する M4 以降で再検討）。
- **テストパターンを描いたまま残す**: コンソールが変更範囲しか転送しない
  ため、コンソール領域の外に残骸が残り続ける。実際に M3-c-2 の実装前は、
  画面左上の RGB の四角と右下の橙が消えずに残っていた。却下。
- **コンソール初期化時に全画面をクリアし、テストパターンは一瞬だけ表示する**:
  残骸は消えるが、テストパターンの目的は screenshot による目視確認であり、
  表示が一瞬では撮影のタイミング次第になる。検証手段としての価値を失う。却下。
- **テストパターンをバックバッファ経由に移す**: 残骸の問題は消えるが、
  テストパターンが検証していた「フレームバッファへ直接描く経路」を検証
  しなくなる。また、コンソールのクリア対象になるため結局消える。却下。
- **テストパターンを削除する**: M3-a の検証手段を失う。却下。
- **コンソールをグローバル + `Locked<T>` にする**: `println!` 相当のマクロを
  どこからでも使えるようになる。しかし現時点で必要とする箇所が無く、
  `unsafe impl Sync` と M4 での見直し対象を増やし、パニック時のデッドロック
  懸念を新たに作る。却下（M4 で割り込み安全性と一体で決める）。

## Consequences
- 描画はキャッシュ有効な RAM 上で行われ、フレームバッファへの書き込みは
  変更範囲の転送だけになる。転送コストが高い場合ほどこの設計が効く。
- 転送コストが実測できていないため、この設計が最適である保証はない。ただし
  「素朴な全面転送より悪くなることはない」という下限は保証される。
- `\r` の挙動が一般的な端末と異なる。将来 VT エスケープシーケンスへ対応する
  場合、この逸脱は互換性の問題になるため、その時点でセルごとの占有種別管理と
  併せて見直すこと。**逸脱していることを明示的に記録しておくのが本項の目的**
  である。
- バックスペース・任意位置へのカーソル移動は扱えない。M4 でキーボード入力を
  導入する際に、セルごとの占有種別管理と併せて設計する。
- コンソールがグローバルでないため、`_start` から `&mut` を渡せる範囲でしか
  出力できない。M4 で割り込みハンドラから出力する必要が生じた時点で、
  グローバル化とロックを設計する。
- パニック時に画面へは何も出ない（ADR-0013 Addendum）。シリアルは独立して
  生きているため、診断はそちらで行う。
- KVM を有効にして転送コストを測り直した結果次第では、ADR-0015 で保留した
  Write-Combining の導入を前倒しする。その場合も本 ADR の構成（バックバッファ +
  ダーティ矩形）は変わらず、転送そのものが速くなるだけである。

## Addendum（2026-07-20、決定 9 の記述を実態に合わせて修正）

決定 9 は当初「`common::log::Logger` は一切変更しない」と書いていたが、
M3-c-3 で `Logger::emitted_line_count` を追加したため、記述とコードが
食い違っていた。記述の方を修正した。

食い違いの原因は、**制約そのものと、その時点でたまたま採った実現手段を
区別せずに書いていたこと**にある。設計時に必要だったのは「シリアル出力の
経路を画面出力の経路に依存させない」ことであり、「Logger を変更しない」は
それを満たす一つの手段にすぎなかった。手段の方を決定として書いたため、
制約に抵触しない変更（行数カウンタの追加）まで禁じる形になっていた。

ADR には、守るべき制約を書く。実現手段を書く場合は、それが制約そのもの
なのか手段なのかが読み取れるようにすること。
