# 0005. Rust + uefiクレートを採用し、EDK2を使わない

## Status
Accepted

## Date
2026-07-16

## Context
過去に「ゼロからのOS自作入門」（MikanOS / C++ / EDK2）で、EDK2のバージョン差に起因するビルド失敗により序盤で挫折した経緯がある。
この教訓から、(a)重量級フレームワーク（EDK2）への依存を避けたい、(b)バージョン差による「謎の失敗」を構造的に排除したい、という要求がある。

言語はGoを除外し、C++ / C / Rustから検討した。
以下が重要な評価軸となった:

- メモリ安全性のコンパイル時チェック（メモリ関連の誤りを実行前に検出できるか）
- `unsafe`の可視化（危険領域を人間がレビューしやすいか）
- ビルド環境の再現性
- OS自作領域でのコミュニティ・事例の厚み

EDK2は「UEFIファームウェアの参照実装を兼ねた巨大ビルドシステム」であり、ブートローダー1個を作るにはオーバースペック。
RustにはEDK2に依存せずUEFIアプリを書ける公式ターゲット（`x86_64-unknown-uefi`）と`uefi`クレート（uefi-rs）が存在し、要求(a)(b)を素直に満たす。

GNU-EFI / POSIX-UEFIもEDK2回避の選択肢だが、これらはC向けライブラリであり、Rustから使うにはFFIを挟むことになる。
Rustネイティブの`uefi`クレートが同じ目的を果たすため、そちらに一本化するのが自然。

## Decision
- 開発言語はRust。
- UEFIアプリは`uefi`クレート（uefi-rs）+ `x86_64-unknown-uefi`ターゲットで実装。
- EDK2のビルドシステムは使わない。
- QEMU用ファームウェアはOVMFの既製ビルド（ディストリのパッケージ）を導入して使う。これはEDK2由来のバイナリを「使うだけ」であり、EDK2のビルドには触れない。

## Alternatives Considered
- **C++ + MikanOS路線（EDK2）**: 手元の書籍資産を活かせるが、言語レベルの安全網が薄く、過去に挫折したEDK2依存を再び抱える。却下。
- **C + GNU-EFI/POSIX-UEFI**: EDK2回避には有効だが、Rustの言語レベルの安全性という今回の主目的を得られない。却下。
- Rust + GNU-EFI/POSIX-UEFI（FFI経由）: 技術的に可能だが実例が乏しく、Rustネイティブの`uefi`クレートで同じ目的を果たせるため不要。却下。
- **Go**: GCとランタイム前提でベアメタルカーネルに根本的に不向き。除外。

## Consequences
- 借用チェッカーが多くの誤りをコンパイル時に弾き、堅牢性に寄与する。
- `unsafe`ブロックで危険領域が明示され、人間レビューの焦点が絞れる。
- Cargoにより環境差異を吸収でき、EDK2で経験した再現性問題を回避できる。
- 借用チェッカーとの格闘で実装が滞る場面はあるが、これはバグの未然防止とトレードオフであり許容する。
- UEFI構造体はC ABI定義のため、`#[repr(C)]` / `extern "efiapi"`等のFFI記法を要所で挟む必要がある（`uefi`クレートが大部分を吸収する）。
- 手元のMikanOS書籍は「概念・章立ての参考」として使い、コードは写経しない。
