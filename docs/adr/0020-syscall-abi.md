# 0020. システムコールのレジスタ規約は最初からLinux x86-64に合わせ、入口は`int 0x80`から始める

## Status
Accepted

**（2026-08-10 後日追記）Decision 1の「中身は独自でよい」はAddendumで否定されている。** 番号の割り当てと構造体レイアウトもLinuxに合わせる。本文は当時の判断の記録として残してあり、書き換えていない。
そのAddendumの宛先はAddendum 2で2つに分かれた。ABIの中身はS9で、入口の機構は後段である。

## Date
2026-07-21

## Context

M5-fでシステムコールを導入する。
規約を決めるコストは今ならほぼゼロだが、後から変えると全システムコールと呼び出し側の書き直しになる。
実装するのはずっと先だが、決定だけを先に行う。

`docs/vision.md`に「静的リンクされたLinuxバイナリを実行できるようにする（BusyBoxのshellが動く程度）」を構想として記録している。**構想は現在の設計を縛らない**が、コストがゼロまたは無視できる場合に限り、構想に沿う側を選んでよいというのが`vision.md`自身の定めである。
レジスタ規約の選択はまさにこれに当たる。

## Decision

### 1. レジスタ規約はLinux x86-64に合わせる

| 役割 | レジスタ |
|---|---|
| システムコール番号 | RAX |
| 戻り値 | RAX |
| 第1〜6引数 | RDI, RSI, RDX, **R10**, R8, R9 |
| 失敗 | 戻り値が`-errno`（-1..-4095の範囲） |

**第4引数がRCXではなくR10である**のが要点。
`syscall`命令がRCXを戻りアドレスの保存に使うため、SysVの関数呼び出し規約（RCXが第4）からずらしてある。
`int 0x80`を使う第一段階ではRCXは空いているが、**それでもR10を使う**。
ここを揃えておかないと、後で`syscall`へ移るときに全呼び出し側の書き換えになる。

中身（番号の割り当てと各呼び出しの意味）は **ZaytOS独自でよい**。
Linux互換を足す段になっても、レジスタ規約が同じなら**番号と引数の意味を対応させる作業**に収まる。
構造体レイアウト（`struct stat`など）の一致は別途必要になるが、それはABIではなくインターフェースの問題で、レジスタ規約とは独立に後から合わせられる。

### 2. 入口は`int 0x80`から始める

M5-fの第一段階では`int 0x80`（IDTのベクタ0x80、DPL=3）を使う。

理由は **`syscall`がスタックを切り替えないこと**にある。

| | `int 0x80` | `syscall` / `sysret` |
|---|---|---|
| スタック切り替え | **CPUがTSS.RSP0から自動で行う** | 行わない。 Ring 0に入った瞬間、まだユーザーのRSPの上にいる |
| 必要な準備 | IDTエントリ1個 | STAR / LSTAR / SFMASKのMSR、GSベース、`swapgs` |
| GDTの並び順 | **制約なし** | STARの仕様で固定される |
| RCX / R11 | 保存される | **命令が破壊する** |

`syscall`でRing 0のスタックへ移るには、**メモリを触らずにカーネルのデータへ辿り着く**必要がある。
それが`swapgs`とGSベースの役割である。
ユーザーがGSを細工していても安全でなければならず、`swapgs`の対称性（入りと出で必ず1回ずつ）が崩れると特権昇格の穴になる。

M5-eで`iretq`によるRing 3遷移を初めて実装する段階で、これを同時にやると切り分け軸が多すぎる。
M4全体で「一度に1つずつ」を優先してきた判断と揃える。

副次的な利点として、`int 0x80`なら **GDTの並び順が自由**になる。
SYSCALLのSTAR制約（`deferred-decisions.md`）がM5-eの判断材料から外れる。

### 3. `syscall` / `sysret`は「速度の最適化」ではなく、Linuxバイナリ互換の前提条件である

**当初これを「速度が問題になったら差し替える」と位置づけたが、誤りである。**

x86-64のLinux静的バイナリ（musl / glibc）は`syscall`命令を発行する。
`int 0x80`は32bit互換の経路であり、64bitバイナリは使わない。
したがって`vision.md`の「静的リンクされたLinuxバイナリを動かす」を目指す限り、**`syscall`/`sysret`の実装は選択ではなく必須**である。

段階の位置づけを次のように定める。

| 段階 | 入口 | 対象 |
|---|---|---|
| 第一段階（M5-f） | `int 0x80` | **ZaytOS独自のユーザーランド** |
| 第二段階（Linuxバイナリ対応） | **`syscall` / `sysret`（必須）** | Linux静的バイナリ |

差し替えで変わるのは**入口の実装とRCX / R11の扱いだけ**である。
レジスタ規約を最初からLinuxに合わせておけば、システムコール本体には一切手が入らない。

`RCX` / `R11`については、第一段階から「システムコールをまたいで保存されない」と規約に含めておく。
`int 0x80`では実際には保存されるが、それに依存したコードを書くと差し替え時に壊れる。

### 4. 2つの入口を併存させるかは、その時点で判断する

独自ユーザーランドを`int 0x80`で作った後、Linuxバイナリ対応で`syscall`を足すと、**2つの入口が併存する**ことになる。

選択肢は2つあり、**どちらを採るかは決めない**（今決める必要が無く、決めても根拠が薄い）。

- **併存させる**: 独自ユーザーランドを書き換えずに済む。入口が2つになるが、どちらも同じディスパッチャへ落とすなら重複は入口だけに収まる
- **独自ユーザーランドも`syscall`へ移行する**: 入口が1つに保たれる。独自ユーザーランド側の呼び出しコードを書き換える必要がある

## Alternatives Considered

- **独自のレジスタ規約を決める**: 設計の自由度は上がるが、Linux互換を足す段で全システムコールと呼び出し側の書き直しになる。今揃えるコストがゼロである以上、採る理由が無い。却下。
- **最初から`syscall` / `sysret`を使う**: M5-eのRing 3遷移と`swapgs`を同時に実装することになる。`swapgs`の対称性が崩れると特権昇格の穴になり、しかも症状が出にくい。却下（第二段階で必ず実装する）。
- **第4引数をRCXにする（SysVに揃える）**: `int 0x80`の間は動くが、`syscall`へ移った瞬間にRCXが破壊されるため全呼び出し側の書き換えになる。却下。

## Consequences

- M5-fのシステムコール本体は、入口の方式に依存しない形で書ける。
- `syscall`/`sysret`の実装はLinuxバイナリ対応の前提条件として残る （`deferred-decisions.md`に解禁条件を記録）。
- `int 0x80`を使う間はGDTの並び順が自由。`syscall`へ移る時点でSTARの制約が復活するため、ユーザー用ディスクリプタの並びは最初からSYSCALL互換の順にしておくのが安全（カーネルコード、カーネルデータ、ユーザーコード32、ユーザーデータ、ユーザーコード64）。並べるだけならコストは無く、これも「コストがゼロなら構想に沿う」に当たる。
- ベクタ0x80はIDTの全256エントリに含まれており（M4-b-1）、現在は「予期しないベクタ」ハンドラが受ける。M5-fでここを差し替える形になる。

## Addendum（2026-08-10、番号割り当てと構造体レイアウトもLinuxに合わせる）

本文Decisionの1が「レジスタ規約だけを合わせ、中身は独自でよい」としていた範囲を広げる。
既存の決定の変更なので、新規ADRではなくここへの追記とする。

### 差し替える2文

Decision 1の末尾にある次の2文を、下記の決定で置き換える。

> 中身（番号の割り当てと各呼び出しの意味）は **ZaytOS独自でよい**。

> 構造体レイアウト（`struct stat`など）の一致は別途必要になるが、それはABIではなくインターフェースの問題で、レジスタ規約とは独立に後から合わせられる。

### 決定

`syscall`/`sysret`を設計する段で、レジスタ規約に加えて次の3つもLinux x86-64に合わせる。

- システムコール番号の割り当て（`read`=0、`write`=1というLinuxの番号表をそのまま使う）
- errnoの値（`-errno`で返す形は本文で決定済み。個々のerrnoの数値をLinuxに合わせる）
- システムコールが受け渡す構造体のレイアウト（`struct stat`、`struct iovec`など）

対象は実装する呼び出しに現れたものだけである。
Linuxの全システムコールを揃えるという決定ではない。
足す順序と範囲は従来どおり「必要になったものから」で、その1つ1つについて番号とレイアウトをLinuxから採る。

### なぜ変えたか

本文は「レジスタ規約を揃えるコストがゼロだから揃える」と決め、番号と構造体レイアウトは後から対応させる作業に収まると見た。
この見積もりが甘い。

番号を後から変えると、影響はカーネル内のディスパッチャに留まらず、その番号で書かれたユーザープログラム全部に及ぶ。
独自ユーザーランドが育ってから変えると、ユーザー側の書き直しが要る。
構造体レイアウトも同じで、`struct stat`を独自に決めれば、それを読むユーザープログラムが独自レイアウトに依存する。
本文が想定した「番号と引数の意味を対応させる作業」は、対応表を書く作業ではなく、両側の書き直しになる。

一方で揃える側のコストは調査だけである。
Linuxの番号表とerrnoと構造体はUAPIヘッダに公開されており、資料も多い（本文Contextの「x86-64のLinux ABIは安定していて資料も多い」と同じ根拠）。

### 却下した案

- **自前の番号割り当てで進め、Linuxバイナリ対応の段で変換層を足す**: 変換層は番号の対応表だけでは済まない。構造体レイアウトが違えば呼び出しごとに詰め替えが要り、その詰め替えは「Linux側の正しいレイアウト」を結局調べないと書けない。調査を先送りするだけで、そのうえ捨てる層を1枚作ることになる。却下。
- **番号だけ合わせ、構造体レイアウトは独自にする**: 番号は境界が明確で合わせやすいが、構造体はユーザープログラムの側に染み出す。`stat`を独自レイアウトで返すと、それを読む独自ユーザーランドのコードがレイアウトに依存し、後から変えると書き直しになる。番号を合わせる理由がそのまま構造体にも当たる。却下。

### 費用

`syscall`/`sysret`を設計する段に調査の作業が入る。
実装する呼び出しについて、Linuxの番号・errnoの値・構造体レイアウトを調べてから決める。
自分で決めるより時間がかかる。

得られるのは、Linuxバイナリ対応の段で変換層が要らなくなることである。

### 現在の実装への影響

`kernel/src/syscall.rs`の`SYS_CHECK_PTR`（0x2B）と`SYS_CHECKSUM`（0x2C）は、Linuxの43（`accept`）と44（`sendto`）に衝突する。
どちらもdocに「暫定割り当て」と書いた検証用の呼び出しなので、`syscall`/`sysret`へ移る段で衝突しない位置へ移すか廃止する。
`ENOSYS`（38）と`EFAULT`（14）は既にLinuxと同じ値である。

（この節はAddendum 2で訂正した。挙げ漏れが1件あり、移すか廃止する時期も違う。）

## Addendum 2（2026-08-10、ABIの中身と入口の機構で宛先を分ける）

Addendumの決定（番号・errnoの値・構造体レイアウトをLinuxに合わせる）の宛先を「`syscall`/`sysret`を設計する段」と書いた。
この宛先では発火しない。
`roadmap.md`のS9（埋め込みELFからのユーザープログラム起動）はシステムコール番号を新しく割り当てるが、S9は`syscall`/`sysret`を設計する段ではないためである。

### 決定

宛先を2つに分ける。

- ABIの中身（番号の割り当て、errnoの値、構造体レイアウト）は、システムコール番号を新しく割り当てるとき、またはユーザーへ渡す構造体を新しく定義するときに揃える。S9で発火する
- 入口の機構（`syscall`/`sysret`、STAR/LSTAR/SFMASKのMSR、`swapgs`とGSベース）は、ユーザーTLSが要るとき、またはLinuxバイナリの実行に着手するときに設計する。早いほうで発火する

あわせて、S9は入口を`int 0x80`のまま進める。

### なぜ分けられるか

ABIの中身と入口の機構は独立である。
番号がRAXに載り、戻り値がRAXで返り、第4引数がR10であることは本文のDecision 1で決まっており、`int 0x80`でも`syscall`でも変わらない。
したがって番号とerrnoの値と構造体レイアウトは、`int 0x80`のままLinuxへ揃えられる。
S9の到達条件（hello・syscall-test・fault-testが動くこと、壊したELFでプロセスだけが失敗すること）も`int 0x80`で満たせる。

逆向きも成り立つ。
入口を差し替えても、番号とerrnoの値と構造体レイアウトは変わらない。
本文Consequencesの「システムコール本体は入口の方式に依存しない形で書ける」が、宛先の分割にもそのまま当たる。

### なぜ入口の機構をS9に入れないか

`swapgs`の対称性が崩れると特権昇格の穴になり、症状が出にくい（本文Contextと、却下案の「最初から`syscall`/`sysret`を使う」）。
S9はELFローダーとアドレス空間とRing 3遷移を同時に動かす段なので、そこへ入れると何かが壊れたときの切り分けが難しくなる。
本文がM5-eとの同時実装を却下したのと同じ形である。

### 却下した案

- 入口の機構もS9に入れ、番号と一緒に片づける: 揃うのは見かけだけである。番号を揃える作業は調査で、`swapgs`は特権昇格の穴を作りうる実装である。性質の違う2つを1つの段に入れると、切り分けの軸が増える。却下
- ABIの中身もS9では触らず、入口の機構と一緒に後回しにする: S9で番号を割り当てる以上、後回しにできるのは「Linuxから採るかどうかの判断」ではなく「採る作業」だけである。独自番号を1つ増やしてから直すことになる。却下

### 現在の実装への影響（Addendumの記述を訂正する）

Addendumの「現在の実装への影響」は挙げ漏れが1件ある。
`kernel/src/syscall.rs`の`PROBE_NUMBER`（0x2A）もLinuxの42（`connect`）と衝突している。
衝突は3件（0x2A・0x2B・0x2C）で、いずれもdocに「暫定割り当て」と書いた検証用の呼び出しである。

移すか廃止する時期も訂正する。
Addendumは「`syscall`/`sysret`へ移る段」と書いたが、上の分割により「番号を新しく割り当てるとき」であり、S9である。
