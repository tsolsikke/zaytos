# 0020. システムコールのレジスタ規約は最初から Linux x86-64 に合わせ、入口は `int 0x80` から始める

## Status
Accepted

## Date
2026-07-21

## Context

M5-f でシステムコールを導入する。**規約を決めるコストは今ならほぼゼロだが、
後から変えると全システムコールと呼び出し側の書き直しになる。** 実装するのは
ずっと先だが、決定だけを先に行う。

`docs/vision.md` に「静的リンクされた Linux バイナリを実行できるようにする
（BusyBox の shell が動く程度）」を構想として記録している。**構想は現在の
設計を縛らない**が、**コストがゼロまたは無視できる場合に限り、構想に沿う側を
選んでよい**というのが `vision.md` 自身の定めである。レジスタ規約の選択は
まさにこれに当たる。

## Decision

### 1. レジスタ規約は Linux x86-64 に合わせる

| 役割 | レジスタ |
|---|---|
| システムコール番号 | RAX |
| 戻り値 | RAX |
| 第 1〜6 引数 | RDI, RSI, RDX, **R10**, R8, R9 |
| 失敗 | 戻り値が `-errno`（-1..-4095 の範囲） |

**第 4 引数が RCX ではなく R10 である**のが要点。`syscall` 命令が RCX を
戻りアドレスの保存に使うため、SysV の関数呼び出し規約（RCX が第 4）から
ずらしてある。`int 0x80` を使う第一段階では RCX は空いているが、**それでも
R10 を使う**。ここを揃えておかないと、後で `syscall` へ移るときに全呼び出し側の
書き換えになる。

中身（番号の割り当てと各呼び出しの意味）は **ZaytOS 独自でよい**。Linux 互換を
足す段になっても、レジスタ規約が同じなら**番号と引数の意味を対応させる作業**に
収まる。構造体レイアウト（`struct stat` など）の一致は別途必要になるが、
それは ABI ではなくインターフェースの問題で、レジスタ規約とは独立に後から
合わせられる。

### 2. 入口は `int 0x80` から始める

M5-f の第一段階では `int 0x80`（IDT のベクタ 0x80、DPL=3）を使う。

理由は **`syscall` がスタックを切り替えないこと**にある。

| | `int 0x80` | `syscall` / `sysret` |
|---|---|---|
| スタック切り替え | **CPU が TSS.RSP0 から自動で行う** | **行わない。** Ring 0 に入った瞬間、まだユーザーの RSP の上にいる |
| 必要な準備 | IDT エントリ 1 個 | STAR / LSTAR / SFMASK の MSR、GS ベース、`swapgs` |
| GDT の並び順 | **制約なし** | STAR の仕様で固定される |
| RCX / R11 | 保存される | **命令が破壊する** |

`syscall` で Ring 0 のスタックへ移るには、**メモリを触らずにカーネルのデータへ
辿り着く**必要がある。それが `swapgs` と GS ベースの役割である。ユーザーが GS を
細工していても安全でなければならず、**`swapgs` の対称性（入りと出で必ず 1 回
ずつ）が崩れると特権昇格の穴になる**。

M5-e で `iretq` による Ring 3 遷移を初めて実装する段階で、これを同時にやると
切り分け軸が多すぎる。M4 全体で「一度に 1 つずつ」を優先してきた判断と揃える。

副次的な利点として、`int 0x80` なら **GDT の並び順が自由**になる。SYSCALL の
STAR 制約（`deferred-decisions.md`）が M5-e の判断材料から外れる。

### 3. `syscall` / `sysret` は「速度の最適化」ではなく、Linux バイナリ互換の前提条件である

**当初これを「速度が問題になったら差し替える」と位置づけたが、誤りである。**

**x86-64 の Linux 静的バイナリ（musl / glibc）は `syscall` 命令を発行する。**
`int 0x80` は 32bit 互換の経路であり、64bit バイナリは使わない。したがって
`vision.md` の「静的リンクされた Linux バイナリを動かす」を目指す限り、
**`syscall`/`sysret` の実装は選択ではなく必須**である。

段階の位置づけを次のように定める。

| 段階 | 入口 | 対象 |
|---|---|---|
| 第一段階（M5-f） | `int 0x80` | **ZaytOS 独自のユーザーランド** |
| 第二段階（Linux バイナリ対応） | **`syscall` / `sysret`（必須）** | Linux 静的バイナリ |

差し替えで変わるのは**入口の実装と RCX / R11 の扱いだけ**である。レジスタ規約を
最初から Linux に合わせておけば、システムコール本体には一切手が入らない。

`RCX` / `R11` については、**第一段階から「システムコールをまたいで保存されない」
と規約に含めておく**。`int 0x80` では実際には保存されるが、それに依存した
コードを書くと差し替え時に壊れる。

### 4. 2 つの入口を併存させるかは、その時点で判断する

独自ユーザーランドを `int 0x80` で作った後、Linux バイナリ対応で `syscall` を
足すと、**2 つの入口が併存する**ことになる。

選択肢は 2 つあり、**どちらを採るかは決めない**（今決める必要が無く、決めても
根拠が薄い）。

- **併存させる**: 独自ユーザーランドを書き換えずに済む。入口が 2 つになるが、
  どちらも同じディスパッチャへ落とすなら重複は入口だけに収まる
- **独自ユーザーランドも `syscall` へ移行する**: 入口が 1 つに保たれる。
  独自ユーザーランド側の呼び出しコードを書き換える必要がある

## Alternatives Considered

- **独自のレジスタ規約を決める**: 設計の自由度は上がるが、Linux 互換を足す段で
  全システムコールと呼び出し側の書き直しになる。今揃えるコストがゼロである
  以上、採る理由が無い。却下。
- **最初から `syscall` / `sysret` を使う**: M5-e の Ring 3 遷移と `swapgs` を
  同時に実装することになる。`swapgs` の対称性が崩れると特権昇格の穴になり、
  しかも症状が出にくい。却下（第二段階で必ず実装する）。
- **第 4 引数を RCX にする（SysV に揃える）**: `int 0x80` の間は動くが、
  `syscall` へ移った瞬間に RCX が破壊されるため全呼び出し側の書き換えになる。
  却下。

## Consequences

- M5-f のシステムコール本体は、入口の方式に依存しない形で書ける。
- **`syscall`/`sysret` の実装は Linux バイナリ対応の前提条件として残る**
  （`deferred-decisions.md` に解禁条件を記録）。
- `int 0x80` を使う間は GDT の並び順が自由。`syscall` へ移る時点で STAR の
  制約が復活するため、**ユーザー用ディスクリプタの並びは最初から
  SYSCALL 互換の順にしておくのが安全**（カーネルコード、カーネルデータ、
  ユーザーコード32、ユーザーデータ、ユーザーコード64）。並べるだけならコストは
  無く、これも「コストがゼロなら構想に沿う」に当たる。
- ベクタ 0x80 は IDT の全 256 エントリに含まれており（M4-b-1）、現在は
  「予期しないベクタ」ハンドラが受ける。M5-f でここを差し替える形になる。
