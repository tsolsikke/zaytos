# 0002. シングルコアを前提に開始する

## Status
Accepted

## Date
2026-07-16

## Context
マルチコア（SMP）対応は、カーネルの複雑度を大きく引き上げる。
具体的には:

- 共有データ保護に、割り込み禁止だけでは不十分となり、スピンロックやアトミック命令（CAS等）による本格的な同期プリミティブが必要になる。
- 眠っている他コアを起動するAP起動シーケンス（ACPI MADT解析、INIT/SIPI送出、各コアのリアルモード→ロングモード遷移）という、ブートローダー相当の処理をコア数分だけ実装する必要がある。
- スケジューラがコアごとのキュー・ロードバランシング・アフィニティを扱う必要が出る。

学習目的・細く長く・完走優先の方針に照らすと、初手からこの複雑度を抱えるのは過剰であり、完走リスクを大きく上げる。

## Decision
当面はシングルコアを前提に設計・実装する。
SMP対応は将来のマイルストーンに回す。

共有データ保護は割り込み禁止（`cli`/`sti`）によるクリティカルセクションで行う。
ただしSMP移行時に中身を差し替えられるよう、ロック的なラッパーの「呼び出し側インターフェース」だけは安定させておく（中身は最小限）。

## Alternatives Considered
- **最初からSMP対応**: 設計としては将来性があるが、完走リスクが跳ね上がる。却下。
- **SMP用の抽象化レイヤーを先回りで作り込む**: 典型的な過剰設計。呼び出し側のインターフェースを意識するにとどめ、実体は作らない。

## Consequences
- 排他制御・AP起動・スケジューラが大幅に単純化され、完走しやすくなる。
- 割り込みハンドラが触る共有データは、シングルコアでもクリティカルセクションで守る必要がある（ここは省略しない）。
- 将来SMP対応する際、ロック実体の差し替えとAP起動の新規実装が必要になる。呼び出し側インターフェースを安定させておくことで、その影響範囲を狭める。
