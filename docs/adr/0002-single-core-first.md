# 0002. シングルコアを前提に開始する

## Status
Accepted

## Date
2026-07-16

## Context
マルチコア（SMP）対応は、カーネルの複雑度を大きく引き上げる。
具体的には:

- 共有データ保護に、割り込み禁止だけでは不十分となり、スピンロックやアトミック命令（CAS等）による本格的な同期プリミティブが必要になる。
- 眠っている他コアを起動するAP起動シーケンス（ACPI MADT解析、INIT/SIPI送出、各コアのリアルモード→ロングモード遷移）という、ブートローダー相当の処理をコア数分だけ実装する必要がある。
- スケジューラがコアごとのキュー・ロードバランシング・アフィニティを扱う必要が出る。

学習目的・細く長く・完走優先の方針に照らすと、初手からこの複雑度を抱えるのは過剰であり、完走リスクを大きく上げる。

## Decision
当面はシングルコアを前提に設計・実装する。
SMP対応は将来のマイルストーンに回す。

共有データ保護は割り込み禁止（`cli`/`sti`）によるクリティカルセクションで行う。
ただしSMP移行時に中身を差し替えられるよう、ロック的なラッパーの「呼び出し側インターフェース」だけは安定させておく（中身は最小限）。

## Alternatives Considered
- **最初からSMP対応**: 設計としては将来性があるが、完走リスクが跳ね上がる。却下。
- **SMP用の抽象化レイヤーを先回りで作り込む**: 典型的な過剰設計。呼び出し側のインターフェースを意識するにとどめ、実体は作らない。

## Consequences
- 排他制御・AP起動・スケジューラが大幅に単純化され、完走しやすくなる。
- 割り込みハンドラが触る共有データは、シングルコアでもクリティカルセクションで守る必要がある（ここは省略しない）。
- 将来SMP対応する際、ロック実体の差し替えとAP起動の新規実装が必要になる。呼び出し側インターフェースを安定させておくことで、その影響範囲を狭める。

## Addendum（2026-08-14、S12前の手当て）: 「将来のマイルストーン」が来た

### 覆したのではない。消化した

**この決定は順序の決定である。** `Decision`は「当面はシングルコアを前提とする。**SMP対応は将来のマイルストーンに回す**」と書いており、**SMPを採らないとは言っていない。**
**その将来がS1からS8で来た。** 順序の決定は、**その順序が来たときに覆されるのではなく消化される。**

**したがって本文は書き換えない。** **書かれた時点で正しく、いまも書かれた内容として正しい。**
`Status`も`Accepted`のまま残す——**却下された決定ではなく、果たされた決定である。**

### 差し替えは`ADR-0023`が引き取った

**`Decision`の「SMP移行時に中身を差し替えられるよう、ロック的なラッパーの呼び出し側インターフェースだけは安定させておく」は、`ADR-0023`（BKLを先に置く）が受け取っている。**
現在の同期方針は`docs/architecture.md`の§7にある。

### `Consequences`が予告した2つは、どちらもそのとおり起きた

**予告が当たった記録を残す。** これは**ADRの書き方そのものの検証**になる——**「将来こうなる」と書いた行が、実際にそうなったかを後から確かめられる形だった。**

- **ロック実体の差し替え。** 起きた。`Locked<T>`は割り込み禁止だけの形から、**取得フラグと保持者の記録を持つ形**になった（S4-b-1）。**保持者を足した理由は予告どおりである**——シングルコアの間は「既に取られている」が必ず同一コアの二重取得だったが、複数コアでは別の原因になり、**観測が同じままだとログからどちらか決められない。**
- **AP起動の新規実装。** 起きた。ACPIのMADTからLocal APIC IDを列挙し（S1-b）、トランポリンを置いてINIT/SIPIで起こし、リアルモードからロングモードへ遷移させる（S3-b）。**`Context`が挙げた「ブートローダー相当の処理」がそのまま作業になった。**

**そして「呼び出し側インターフェースを安定させておくことで影響範囲を狭める」も効いた。**
`Locked<T>`を使っている側（ヒープの`heap/allocator.rs`、キーボードのリングバッファの`keyboard/buffer.rs`、後から増えた`input.rs`と`vfs.rs`）は、**中身が変わっても呼び出しの形が変わっていない。**

### 当たらなかった予告は無いか

**`Context`が挙げた3つ目——「スケジューラがコアごとのキュー・ロードバランシング・アフィニティを扱う必要が出る」——は、まだ来ていない。**
**APはカーネルのタスクを走らせるが、Ring 3へは入らない**（`kernel/src/ring3.rs`の`enter`のdoc）。**ユーザープロセスのスケジューラそのものが無い。**
**これは予告の誤りではなく、まだ到達していない部分である。**
