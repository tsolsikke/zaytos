# 0013. フレームバッファ描画は形状を検証したうえでRgb/Bgrのみを扱う

## Status
Accepted

## Date
2026-07-20

## Context
M3でkernelからフレームバッファへ描画する。
フレームバッファの形状（物理アドレス・幅・高さ・stride・ピクセルフォーマット・バイトサイズ）はbootloaderがGOPから取得して`BootInfo.framebuffer`で渡してくるが、これは「GOPがそう申告している」という以上の意味を持たず、kernel側では一切裏を取っていなかった。

M2-dの検証で書いた64x64ブロックの描画コードには、次の問題があった。

- SAFETYコメントに`size_bytes = height * stride * 4`に収まると書いてあったが、この等式はどこでも検証していなかった。64x64の範囲しか描かないうちは表面化しないが、全画面を描いた瞬間に確保範囲外へ書き込む。
- 色を`const TEST_COLOR: u32 = 0x00FF_3366;`と生の32bit値で書いていた。実機（QEMU + OVMF）は`Bgr`なので意図した色に見えたが、`Rgb`の環境では赤と青が入れ替わる。
- `stride >= width`、`width > 0`、`height > 0`、物理アドレスのアラインメント、アドレス計算の桁溢れを、いずれも確認していなかった。

低レイヤのこの種の誤りは、書いた直後には症状が出ず、後から無関係に見える壊れ方をする。
実装より先に検証を置く。

なお実機の実測値は1280x800 / stride=1280 / Bgr / size=4096000であり、`800 * 1280 * 4 = 4096000`と完全に一致していた。
今は一致しているという事実の確認であって、一致し続ける保証ではない。

## Decision

**1. 形状はkernel側で検証してから使う。** `FramebufferLayout::from_info`が全項目を検証し、通ったものだけを`FramebufferLayout`として返す。
この型が存在すること自体が検証済みの証明になるよう、フィールドは非公開にし、他の構築経路を作らない。
検証項目はピクセルフォーマット、物理アドレスが0でなく4バイト境界にあること、幅と高さが0でないこと、`stride >= width`、`height * stride * 4 <= size_bytes`、アドレス計算がu64で溢れないこと。

**2. 扱うのは`Rgb`と`Bgr`の32bppのみ。** `Bitmask`はビット幅が可変で32bppを仮定できず、`BltOnly`は`Blt()`がプロトコル関数呼び出しであるためExitBootServices後には使えない。
どちらも「対応したふり」をせず、検証時に明示的に拒否する。

**3. 色は`Color`型で持ち、書き込み直前にフォーマットへ変換する。** 生の`u32`をコード中に書かない。
x86_64はリトルエンディアンなので、`Bgr`（メモリ上B, G, R, 予約の順）は`u32`として`0x00RRGGBB`、`Rgb`はその逆になる。
この変換はホストテストで両方向を固定する。

**4. 描画経路ではpanicしない。** 画面外の座標は無視し、はみ出した矩形は画面内へ切り詰める。
理由は、将来パニック処理から描画を呼んだ場合に、描画側のpanicがパニックハンドラを再入させうるため。
範囲チェックを「落ちる」のではなく「描かない」で扱う。

**5. パニック時の画面出力は行わない（当面シリアルのみ）。** 画面コンソールをグローバル状態 + `Locked<T>`で持つと、ロックを保持したままpanicした場合にパニックハンドラがデッドロックする。
現在のパニックハンドラはヒープにもロックにも依存せず完結しており、この性質を崩さない。
画面にも出すなら、ロックを取らず生ポインタで直接描く専用経路が必要であり、それはM3の範囲外とする。

**6. 検証に失敗した場合はERRORログを残して描画を諦め、起動処理は続ける。** haltしないのは、フレームバッファが使えない環境でも、それ以外の起動シーケンスの診断ログを最後まで取りたいため。
画面が主たる出力手段になるM3-cの時点で、この方針は見直す。

**7. バックバッファはM3-cまで導入しない。** フレームバッファはPCD（キャッシュ無効）でマップしているため読み出しが非常に遅く、スクロールをフレームバッファ間のコピーで実装すると実用にならない。
したがってバックバッファはいずれ必要になるが、それを要求するのはスクロールだけであり、スクロールの無いM3-a / M3-bでは不要。
描画関数は書き込み先を引数で受ける形にしておき、後から差し替えられるようにする。
導入時は4,096,000バイト（1000フレーム）を`allocate_contiguous`で直接確保する（ヒープは1MiBしかないため経由しない。
ADR-0012）。

## Alternatives Considered

- **形状を検証せずGOPの申告をそのまま使う**: 実装は短くなるが、申告が内部矛盾していた場合に確保範囲外へ書き込む。症状は「しばらく動いた後に突然壊れる」形になり、最も診断しにくい。却下。
- **`Bitmask`にも対応する**: マスクからシフト量とビット幅を導出すれば原理的には可能。しかし実機で`Bitmask`を返す環境を現に持っておらず、テストできない対応コードを抱えることになる。必要になった時点で、実物を観測してから実装する。却下（保留）。
- **範囲外の描画をpanicにする**: 誤りを早期に発見できる利点はあるが、描画経路からpanicが出る設計は、パニックハンドラが画面を使うようになった瞬間に再入の危険を生む。ホストテストで切り詰めロジックを検証する方が、同じ誤りをより早く捕まえられる。却下。
- **最初からバックバッファを持つ**: スクロール実装時に書き直さずに済むが、現時点で必要としない4MiBの確保と二重管理を先に抱え込むことになる。先回りの作り込みを避ける方針に反する。却下（M3-cで導入）。
- **検証失敗時にhaltする**: fail-fastの原則には合うが、M3-aの時点ではフレームバッファ以外の起動シーケンスの診断の方が価値が高い。ERRORをloudに残すことで見落とさない形にしたうえで継続する。M3-cで再検討。

## Consequences
- 全画面描画をしても確保範囲外へ出ないことが、型と起動時検証で担保される。
- ピクセルフォーマットの取り違えによる色の入れ替わりが、実機に依存せずホストテストで検出できる。
- `Bitmask` / `BltOnly`の環境では画面に何も出ない。その場合はERRORログで理由が分かる。
- 描画ロジック（形状検証・座標計算・色変換）はホスト`cargo test`で検証でき、実際に生ポインタを触るのは`graphics::framebuffer`だけに閉じ込められる。
- パニック時に画面へ何も出ないため、シリアルが取れない状況では診断できない。シリアルログを最優先の観測手段とする方針（ADR-0003）と整合しており、当面は許容する。
- M4で割り込みを有効化する際、画面コンソールをグローバル状態で持つなら、`heap::allocator::Locked<T>`と同じ「シングルコア + 割り込み常時禁止」への依存が増える。`docs/architecture.md` §6.5の見直し一覧に含める。

## Addendum（2026-07-20、M3-cの設計時に再確認）

M3-cでコンソールを導入するにあたり、決定5（パニック時の画面出力を行わない）を改めて検討し、**維持する**と判断した。
理由を明記しておく。

1. **ロックによるデッドロック**: コンソールがグローバル状態を`Locked<T>`で保護する構成を採ると、ロックを保持したままpanicした場合に、パニックハンドラが同じロックを取りに行って停止する。パニックハンドラは「何が起きたかを必ず残す」ためのものであり、状況次第で沈黙する実装にしてはならない。
2. **確保依存による無限再帰**: パニックハンドラが動的確保やバックバッファに依存すると、ヒープ枯渇に起因するpanicを処理する最中に再び確保を試みて失敗し、パニックが再帰する。現在のパニックハンドラはヒープにもロックにも触れず、シリアルへ直接書くだけで完結している。この性質はM3-c以降も崩さない。

**将来この判断を覆す場合の条件**: パニック時に画面へも出すなら、通常のコンソール経路を使ってはならない。
必要になるのは次の条件をすべて満たす専用経路である。

- ロックを一切取らない（保持者の有無に関わらず書ける）
- 動的確保を行わない（バックバッファも経由しない）
- 検証済みのフレームバッファ先頭アドレスと形状だけを頼りに、生ポインタで直接書き込む
- 通常のコンソールが保持している画面内容を破壊してよいことを前提とする（復帰しないため）

この経路は通常のコンソールとはコードを共有できない。
実装する場合は独立したモジュールとして起こし、パニックハンドラからのみ呼ぶこと。
