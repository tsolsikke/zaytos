# 0013. フレームバッファ描画は形状を検証したうえで Rgb/Bgr のみを扱う

## Status
Accepted

## Date
2026-07-20

## Context
M3 で kernel からフレームバッファへ描画する。フレームバッファの形状
（物理アドレス・幅・高さ・stride・ピクセルフォーマット・バイトサイズ）は
bootloader が GOP から取得して `BootInfo.framebuffer` で渡してくるが、
これは「GOP がそう申告している」という以上の意味を持たず、kernel 側では
一切裏を取っていなかった。

M2-d の検証で書いた 64x64 ブロックの描画コードには、次の問題があった。

- SAFETY コメントに `size_bytes = height * stride * 4` に収まると書いて
  あったが、この等式はどこでも検証していなかった。64x64 の範囲しか描かない
  うちは表面化しないが、全画面を描いた瞬間に確保範囲外へ書き込む。
- 色を `const TEST_COLOR: u32 = 0x00FF_3366;` と生の 32bit 値で書いていた。
  実機（QEMU + OVMF）は `Bgr` なので意図した色に見えたが、`Rgb` の環境では
  赤と青が入れ替わる。
- `stride >= width`、`width > 0`、`height > 0`、物理アドレスのアラインメント、
  アドレス計算の桁溢れを、いずれも確認していなかった。

低レイヤのこの種の誤りは、書いた直後には症状が出ず、後から無関係に見える
壊れ方をする。実装より先に検証を置く。

なお実機の実測値は 1280x800 / stride=1280 / Bgr / size=4096000 であり、
`800 * 1280 * 4 = 4096000` と完全に一致していた。今は一致しているという
事実の確認であって、一致し続ける保証ではない。

## Decision

**1. 形状は kernel 側で検証してから使う。**
`FramebufferLayout::from_info` が全項目を検証し、通ったものだけを
`FramebufferLayout` として返す。この型が存在すること自体が検証済みの証明に
なるよう、フィールドは非公開にし、他の構築経路を作らない。検証項目は
ピクセルフォーマット、物理アドレスが 0 でなく 4 バイト境界にあること、
幅と高さが 0 でないこと、`stride >= width`、
`height * stride * 4 <= size_bytes`、アドレス計算が u64 で溢れないこと。

**2. 扱うのは `Rgb` と `Bgr` の 32bpp のみ。**
`Bitmask` はビット幅が可変で 32bpp を仮定できず、`BltOnly` は `Blt()` が
プロトコル関数呼び出しであるため ExitBootServices 後には使えない。どちらも
「対応したふり」をせず、検証時に明示的に拒否する。

**3. 色は `Color` 型で持ち、書き込み直前にフォーマットへ変換する。**
生の `u32` をコード中に書かない。x86_64 はリトルエンディアンなので、
`Bgr`（メモリ上 B, G, R, 予約の順）は `u32` として `0x00RRGGBB`、`Rgb` は
その逆になる。この変換はホストテストで両方向を固定する。

**4. 描画経路では panic しない。**
画面外の座標は無視し、はみ出した矩形は画面内へ切り詰める。理由は、将来
パニック処理から描画を呼んだ場合に、描画側の panic がパニックハンドラを
再入させうるため。範囲チェックを「落ちる」のではなく「描かない」で扱う。

**5. パニック時の画面出力は行わない（当面シリアルのみ）。**
画面コンソールをグローバル状態 + `Locked<T>` で持つと、ロックを保持した
まま panic した場合にパニックハンドラがデッドロックする。現在のパニック
ハンドラはヒープにもロックにも依存せず完結しており、この性質を崩さない。
画面にも出すなら、ロックを取らず生ポインタで直接描く専用経路が必要であり、
それは M3 の範囲外とする。

**6. 検証に失敗した場合は ERROR ログを残して描画を諦め、起動処理は続ける。**
halt しないのは、フレームバッファが使えない環境でも、それ以外の起動
シーケンスの診断ログを最後まで取りたいため。画面が主たる出力手段になる
M3-c の時点で、この方針は見直す。

**7. バックバッファは M3-c まで導入しない。**
フレームバッファは PCD（キャッシュ無効）でマップしているため読み出しが
非常に遅く、スクロールをフレームバッファ間のコピーで実装すると実用に
ならない。したがってバックバッファはいずれ必要になるが、それを要求するのは
スクロールだけであり、スクロールの無い M3-a / M3-b では不要。描画関数は
書き込み先を引数で受ける形にしておき、後から差し替えられるようにする。
導入時は 4,096,000 バイト（1000 フレーム）を `allocate_contiguous` で直接
確保する（ヒープは 1MiB しかないため経由しない。ADR-0012）。

## Alternatives Considered

- **形状を検証せず GOP の申告をそのまま使う**: 実装は短くなるが、申告が
  内部矛盾していた場合に確保範囲外へ書き込む。症状は「しばらく動いた後に
  突然壊れる」形になり、最も診断しにくい。却下。
- **`Bitmask` にも対応する**: マスクからシフト量とビット幅を導出すれば
  原理的には可能。しかし実機で `Bitmask` を返す環境を現に持っておらず、
  テストできない対応コードを抱えることになる。必要になった時点で、実物を
  観測してから実装する。却下（保留）。
- **範囲外の描画を panic にする**: 誤りを早期に発見できる利点はあるが、
  描画経路から panic が出る設計は、パニックハンドラが画面を使うように
  なった瞬間に再入の危険を生む。ホストテストで切り詰めロジックを検証する
  方が、同じ誤りをより早く捕まえられる。却下。
- **最初からバックバッファを持つ**: スクロール実装時に書き直さずに済むが、
  現時点で必要としない 4MiB の確保と二重管理を先に抱え込むことになる。
  先回りの作り込みを避ける方針に反する。却下（M3-c で導入）。
- **検証失敗時に halt する**: fail-fast の原則には合うが、M3-a の時点では
  フレームバッファ以外の起動シーケンスの診断の方が価値が高い。ERROR を
  loud に残すことで見落とさない形にしたうえで継続する。M3-c で再検討。

## Consequences
- 全画面描画をしても確保範囲外へ出ないことが、型と起動時検証で担保される。
- ピクセルフォーマットの取り違えによる色の入れ替わりが、実機に依存せず
  ホストテストで検出できる。
- `Bitmask` / `BltOnly` の環境では画面に何も出ない。その場合は ERROR ログで
  理由が分かる。
- 描画ロジック（形状検証・座標計算・色変換）はホスト `cargo test` で検証でき、
  実際に生ポインタを触るのは `graphics::framebuffer` だけに閉じ込められる。
- パニック時に画面へ何も出ないため、シリアルが取れない状況では診断できない。
  シリアルログを最優先の観測手段とする方針（ADR-0003）と整合しており、当面は
  許容する。
- M4 で割り込みを有効化する際、画面コンソールをグローバル状態で持つなら、
  `heap::allocator::Locked<T>` と同じ「シングルコア + 割り込み常時禁止」への
  依存が増える。`docs/architecture.md` §6.5 の見直し一覧に含める。
