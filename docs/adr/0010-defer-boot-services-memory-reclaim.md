# 0010. EfiBootServicesCode/Data は当面回収しない

## Status
Accepted

## Date
2026-07-19

## Context
物理フレームアロケータ（M2-c）の設計にあたり、どの `EFI_MEMORY_TYPE` を
「空き」として扱うかを検討した。UEFI 仕様上、`EfiBootServicesCode` /
`EfiBootServicesData` は ExitBootServices 成功後は OS が自由に再利用してよい
（`EfiConventionalMemory` と同等に扱ってよい）と規定されており、
`uefi::boot::exit_boot_services` のドキュメントコメントにも同様の記述が
ある。これは事実として正しい。

しかし、この仕様上の許可は「OS がファームウェア由来の構造から完全に
自立した後」を前提にしている。**現時点の ZaytOS はまだ以下をすべて
UEFI（ファームウェア）が用意したものの上で動かしている。**

- ページテーブル（現在の CR3 が指す、UEFI が構築した恒等マッピング。
  ADR-0009 で検証済み）
- 実行中のスタック（kernel は bootloader が使っていた UEFI 由来のスタックを
  そのまま流用している。`docs/architecture.md` §6.3）
- GDT / IDT（UEFI が設定したもの。まだ自前の GDT/IDT を持たない）

実機（QEMU + OVMF）のレジスタダンプでは、これらは典型的に次のような
ファームウェア確保領域を指している。

```
CR3 = 0x0f801000  （ページテーブル）
GDT = 0x0f5dc000
IDT = 0x0f139018
RSP = 0x0fe95610  （スタック）
```

これらの領域の `EFI_MEMORY_TYPE` を精査していないが、一般に UEFI 実装は
自身が使うページテーブル・GDT/IDT・初期スタックの少なくとも一部を
`EfiBootServicesData` として確保することが多い。もし物理フレーム
アロケータが `EfiBootServicesData` を「空き」として配ってしまうと、
**現在まさに実行に使っているページテーブル・スタック・GDT/IDT を
他の用途（例: 次に確保する別のデータ構造）で上書きしてしまう可能性が
ある。** これは即座には症状が出ず、アロケータが該当フレームを実際に
使い切るまで（＝十分な回数のアロケーションが起きるまで）発現しないため、
初期のテストや短時間の動作確認をすべて通過したあとで、無関係に見える
場所が突然壊れるという、最も診断が困難な種類のバグになる。

## Decision
`EfiBootServicesCode` および `EfiBootServicesData` は、物理フレーム
アロケータにおいて**当面「空き」として扱わない**（除外側に置く）。

「空き」として扱うのは `EfiConventionalMemory` のみとする（物理アドレス 0
を含むページはこの型であっても別途除外する。理由は別途 M2-c 実装時の
方針提示を参照）。

## Alternatives Considered
- **仕様通り `EfiBootServicesCode`/`EfiBootServicesData` を空き扱いする**:
  UEFI 仕様上は正しいが、Context で述べた通り、自前のページテーブル・
  スタック・GDT/IDT を持つまではファームウェア由来の実行基盤を自ら破壊する
  リスクがある。学習目的のプロジェクトでこの種の「原因究明が極めて困難な
  自己破壊バグ」を抱え込む理由がないため却下する。
- **ページテーブル/スタック/GDT/IDT が使っている具体的な範囲だけを
  ピンポイントで除外する**: 理論上は可能だが、これらの範囲を正確に
  列挙する手段（UEFI から明示的に教えてもらえるわけではない）が
  M2-c 時点では存在せず、実装コストと誤りのリスクが高い。型全体を
  除外するほうが単純で堅牢。

## Consequences
- フレームアロケータが利用可能と判断する物理メモリの総量は、
  `EfiBootServicesCode`/`Data` 分だけ少なくなる。学習用途の小規模カーネルでは
  問題にならない想定。
- **回収を解禁できる条件**: 以下の 3 つがすべて揃った後（M4 以降が目安）。
  1. 自前のページテーブルを構築し、CR3 を切り替えている（M2-d）
  2. kernel 自身のスタックを用意し、UEFI 由来のスタックを使っていない
  3. 自前の GDT/IDT を設定している（M4）
  解禁する場合、この ADR を Superseded とし、新たな ADR で回収方針
  （どの時点で、どの範囲を、どう安全に回収するか）を定める。
- `docs/roadmap.md` に「BootServices 領域の回収」を将来の検討項目として
  残す。
