# 0010. EfiBootServicesCode/Dataは当面回収しない

## Status
Accepted

## Date
2026-07-19

## Context
物理フレームアロケータ（M2-c）の設計にあたり、どの`EFI_MEMORY_TYPE`を「空き」として扱うかを検討した。
UEFI仕様上、`EfiBootServicesCode` / `EfiBootServicesData`はExitBootServices成功後はOSが自由に再利用してよい（`EfiConventionalMemory`と同等に扱ってよい）と規定されており、`uefi::boot::exit_boot_services`のドキュメントコメントにも同様の記述がある。
これは事実として正しい。

しかし、この仕様上の許可は「OSがファームウェア由来の構造から完全に自立した後」を前提にしている。
現時点のZaytOSはまだ以下をすべてUEFI（ファームウェア）が用意したものの上で動かしている。

- ページテーブル（現在のCR3が指す、UEFIが構築した恒等マッピング。ADR-0009で検証済み）
- 実行中のスタック（kernelはbootloaderが使っていたUEFI由来のスタックをそのまま流用している。`docs/architecture.md` §6.3）
- GDT / IDT（UEFIが設定したもの。まだ自前のGDT/IDTを持たない）

実機（QEMU + OVMF）のレジスタダンプでは、これらは典型的に次のようなファームウェア確保領域を指している。

```
CR3 = 0x0f801000  （ページテーブル）
GDT = 0x0f5dc000
IDT = 0x0f139018
RSP = 0x0fe95610  （スタック）
```

これらの領域の`EFI_MEMORY_TYPE`を精査していないが、一般にUEFI実装は自身が使うページテーブル・GDT/IDT・初期スタックの少なくとも一部を`EfiBootServicesData`として確保することが多い。
もし物理フレームアロケータが`EfiBootServicesData`を「空き」として配ってしまうと、現在まさに実行に使っているページテーブル・スタック・GDT/IDTを他の用途（例: 次に確保する別のデータ構造）で上書きしてしまう可能性がある。
これは即座には症状が出ず、アロケータが該当フレームを実際に使い切るまで（＝十分な回数のアロケーションが起きるまで）発現しないため、初期のテストや短時間の動作確認をすべて通過したあとで、無関係に見える場所が突然壊れるという、最も診断が困難な種類のバグになる。

## Decision
`EfiBootServicesCode`および`EfiBootServicesData`は、物理フレームアロケータにおいて**当面「空き」として扱わない**（除外側に置く）。

「空き」として扱うのは`EfiConventionalMemory`のみとする（物理アドレス0を含むページはこの型であっても別途除外する。
理由は別途M2-c実装時の方針提示を参照）。

## Alternatives Considered
- 仕様通り`EfiBootServicesCode`/`EfiBootServicesData`を空き扱いする: UEFI仕様上は正しいが、Contextで述べた通り、自前のページテーブル・スタック・GDT/IDTを持つまではファームウェア由来の実行基盤を自ら破壊するリスクがある。学習目的のプロジェクトでこの種の「原因究明が極めて困難な自己破壊バグ」を抱え込む理由がないため却下する。
- ページテーブル/スタック/GDT/IDTが使っている具体的な範囲だけをピンポイントで除外する: 理論上は可能だが、これらの範囲を正確に列挙する手段（UEFIから明示的に教えてもらえるわけではない）がM2-c時点では存在せず、実装コストと誤りのリスクが高い。型全体を除外するほうが単純で堅牢。

## Consequences
- フレームアロケータが利用可能と判断する物理メモリの総量は、`EfiBootServicesCode`/`Data`分だけ少なくなる。学習用途の小規模カーネルでは問題にならない想定。
- **回収を解禁できる条件**: 以下の3つがすべて揃った後（M4以降が目安）。
  1. 自前のページテーブルを構築し、CR3を切り替えている（M2-d）
  2. kernel自身のスタックを用意し、UEFI由来のスタックを使っていない
  3. 自前のGDT/IDTを設定している（M4）解禁する場合、このADRをSupersededとし、新たなADRで回収方針（どの時点で、どの範囲を、どう安全に回収するか）を定める。
- `docs/roadmap.md`に「BootServices領域の回収」を将来の検討項目として残す。
