# 0045. ユーザープログラムは`common`の純粋な論理を`#[path]`で取り込む

## Status

Accepted

## Date

2026-08-23

## Context

**VIEW段で「見えている窓」の計算が要る。** **`zi`のスクロールと`less`が同じ規則を使う**——「現在行が窓の外へ出たら窓を動かす」である。**二重に持つと片方だけが直る**（`CLAUDE.md`の規律）。

**置き場所を決める必要がある。** **実測した結果、いまの形では選択肢が2つしか無い。**

### 実測——ユーザープログラムはクレートに依存できない

- **`kernel/userland/*.rs`はcargoのパッケージに属さない**（`userlib.rs`のdocが書いている）
- **`kernel/build.rs`が`rustc`を直に呼ぶ。** **`--extern`を1つも渡していない**（実測）。したがって`common`にも他のどのクレートにも依存できない
- **`cargo test --workspace`はユーザープログラムを見ない。** **`cargo fmt`と`clippy`も見ない**（`userlib.rs`のdoc）

### 実測——`#[path]`で取り込む形は既に在る

**`kernel/userland/zi.rs`は`#[path = "userlib.rs"] mod userlib;`と書いている。** **`ls` `cat` `zash`ほかも同じである。** **クレートを跨いでいないだけで、手口そのものは在る。**

### なぜホストテストが要るのか

**`CLAUDE.md`の絶対ルール5——「ハードウェア依存部と純粋ロジックを分離し、ロジックはホスト上でテスト可能に保つ」。** **窓の計算は純粋な論理で、ホストテストが最も安く効く種類である**（境界の条件が多く、QEMUを起こして確かめるには高すぎる）。

### この問題はCの移植で必ず再来する

**自前libcは「ユーザープログラムが共有する純粋な論理」の塊である**（文字列、数の書式、`ctype`相当）。**ホストで検算できないと苦しい。** **前例が無いなら、いま前例を作るのが正しい時期である**（運用者の判断）。

## Decision

### 1. ユーザープログラムが共有する純粋な論理は`common`へ置き、`#[path]`で取り込む

**置き場所は`common/src/<name>.rs`である。** **`common/src/lib.rs`が`pub mod`で持つので、`cargo test --workspace`が覆う。**

**ユーザープログラム側は`#[path = "../../common/src/<name>.rs"] mod <name>;`と書く。**

**最初の1本は`common/src/window.rs`である**（VIEW-a）。

### 2. 取り込むモジュールは自己完結でなければならない

**`crate::`を1つも参照しない。** **`core`だけを使う。**

**理由は、取り込まれた側では`crate`が`zi`になることである。** **参照があるとそこで壊れる。**

**壊れ方は静かではない**——**ユーザープログラムのビルドが落ち、`kernel/build.rs`が`panic!`する。** **黙って別のものが混ざる形にはならない。**

### 3. `kernel/build.rs`は取り込んだファイルを`rerun-if-changed`に載せる

**載せないと、`common`側を直してもユーザープログラムが建て直されない。** **`userlib.rs`を載せているのと同じ理由である。**

### 4. 置くのは純粋な論理だけである

**システムコールの包みは`userlib.rs`に残す。** **あちらは`int 0x80`を直に書くので、`common`には置けない**（`common`はkernelとbootloaderからも使われる。**ユーザー空間のABIをそこへ混ぜない**）。

**ハードウェアに触るもの、カーネルの内部を知っているものも置かない。**

### 5. 取り込むのは名指しした1モジュールだけである

**`common`の全体を取り込む形にはしない。** **いま取り込むのは`window`だけである。** **増やすときは、決定2の自己完結を満たすことを確かめてから足す。**

## Alternatives Considered

### (a) `userlib.rs`に置く（前例どおり）

**却下する。** **ホストテストが1つも置けない。** **`CLAUDE.md`の絶対ルール5に正面から反する。**

**「QEMUで確かめればよい」は成り立たない**——**窓の境界（上に出た/下に出た/ちょうど端/高さ1）を全部QEMUで通すのは高く、実際には数例しか通らない。** **ホストなら10例が0.00秒で通る**（実測）。

### (b) ユーザープログラムを本物のクレートにし、`common`に依存させる

**却下する。今は。** **`kernel/build.rs`の`rustc`呼び出し、リンカスクリプトの渡し方、`no_std`バイナリをワークスペースへ入れる形——3つとも作り直しになる。** **得るものは`#[path]`が要らなくなることだけである。**

**再来する条件を書いておく**——**ユーザープログラムが`common`の複数のモジュールに依存し始めたとき**、または**依存の向きが`common`の内部（モジュール間の参照）に及んだとき。** **そのとき決定2が守れなくなるので、この案へ戻ること。**

### (c) `zi`と`less`のそれぞれに同じ計算を書く

**却下する。** **二重に持つと片方だけが直る**（`CLAUDE.md`が繰り返し書いている形）。**実際、この体制は同じ理由で`userlib.rs`を抽出している。**

### (d) 窓の計算をカーネルへ置き、システムコールで訊く

**却下する。** **カーネルは窓を持つ理由が無い**——**画面に何を出すかはユーザー空間の判断である**（`ADR-0040`の分担）。**面が増えるだけで、得るものが無い。**

## Consequences

**得るもの。**

- **窓の計算がホストテストで覆える**（実測で10例）
- **`zi`と`less`と`more`が同じ規則を使う。** 片方だけが直る形にならない
- **Cの移植で「純粋な論理をどこへ置くか」の答えが既に在る**

**失うもの・引き受ける制約。**

- **同じソースが2通りにビルドされる**（`common`のクレートとして、ユーザープログラムの一部として）。**自己完結が崩れたら、後者だけが落ちる**
- **取り込みのパスが相対である**（`../../common/src/window.rs`）。**ファイルを動かすと切れる。** **切れ方はビルドの失敗なので、静かではない**
- **`cargo fmt`と`clippy`は、ユーザープログラム側の取り込みを見ない**（もともと見ていない）。**`common`側では見る**

## 決めないこと

- **ユーザープログラムを本物のクレートにするか**（却下案(b)。再来の条件を書いた）
- **`common`の他のモジュールを取り込むか**（いまは`window`だけである）
- **`less`と`more`が窓のどの機能を使うか**（VIEW-bとVIEW-cで決める。**使う者が来てから足す**）
