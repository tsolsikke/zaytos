# 0041. 環境変数はカーネルが1つ持ち、すべてのプロセスへ同じものを積む

## Status

Accepted

## Date

2026-08-22

## Context

**設定を渡す手段が1つも無い。** キーボード配列を選べないのも、`TERM`を名乗れないのも、`PS1`が固定なのも、根はこれである（`docs/deferred-decisions.md`・`docs/foundation-inventory.md`）。

### 実測——約束の枠は既に在る

**`kernel/src/userland.rs`の`build_initial_stack`が積んでいるものを実測した。** `rsp`の指す先から順に、`argc`・`argv`のポインタ列・NULL・**`envp`の終端**・`auxv`の`AT_NULL`である。**SysVの並びそのもので、`crt0`がそのまま書ける。**

**したがって、この段でやるのは「並びを作り直すこと」ではなく「空の枠に中身を入れること」である。**

- **`argv`は積んでいる。** 上限は`MAX_ARGV = 8`（実測）
- **`envp`は終端だけである**（`put(0, &mut at)`が1つ）
- **`auxv`は`AT_NULL`だけである**
- **読む側は`userlib::argument`が`rsp`から`argc`と`argv`を引いている**（実測）。**`envp`を読む道具は無い**
- **ユーザースタックは1ページ（4096バイト）で、`argv`の文字列も同じページに載る**（`USER_PROGRAM_STACK_TOP = 0x0080_0000`から1枚）

### 実測——1ページの余裕

**初期データの大きさは起動ログに出ている**（`user-load: <名前> initial stack at <番地>`）。

| プログラム | `argc` | 初期の`rsp` | 初期データ | 残り |
|---|---|---|---|---|
| `hello` | 1 | `0x7fffc0` | 64バイト | 4032バイト |
| `fault-test` | 1 | `0x7fffc0` | 64バイト | 4032バイト |
| `/bin/ls` | 1 | `0x7fffc0` | 64バイト | 4032バイト |
| `/bin/spawn-test` | 2 | `0x7fffb0` | 80バイト | 4016バイト |
| `syscall-test` | 2 | `0x7fffa0` | 96バイト | 4000バイト |

**組み立ての算術をホストで再現し、起動ログと突き合わせた。** 上の5点のうち4点が一致し、`syscall-test`だけ16バイト多い——**あれは第2引数が長いためで、モデルと矛盾しない**（`argc`が同じ`spawn-test`との差が第2引数の長さで説明できる）。

**残りはプログラム自身のスタックである。** **その使用量は測っていない**（後述）。

## Decision

**5つ決める。**

### 1. `envp`に中身を入れる。並びは変えない

**SysVの並び（`argc` / `argv` / NULL / `envp` / NULL / `auxv`）を変えない。** **`auxv`にも触らない**（`AT_NULL`のまま）。**足すのは`envp`のポインタ列と、その文字列だけである。**

### 2. **環境はカーネルが1つ持ち、すべてのプロセスへ同じものを積む**

**プロセスごとに違う環境を持たない。** カーネルの静的な表を1つ置き、`build_initial_stack`がそれを積む。

**この決定の効果は、費用よりも面にある**——**ユーザーポインタを1本も増やさない。** `spawn`が受け取るのは今までどおり`path`と`argv`だけで、**環境は user から来ない。** `copy_user_argv`に相当するものが要らない。

### 3. 最初の中身は`TERM`だけにする

**`TERM=zaytos`の1つから始める。** **`PS1`も`KEYMAP`も入れない**——**読む者が居ないものを積まない**（`docs/verification-coverage.md`の「使う者がいない機構は検算が置けない」）。

**この原則は、同じ段で読む側を作ることまで含む。** **積んだだけで誰も読まない状態が残れば、原則を破ったのと同じである。**
**したがって到達条件に入れる**——**`zash`が`TERM`を読み、その値で色が変わることを、判定が主張すること。**

### 4. ユーザースタックは増やさない。**そのかわり測る**

**1ページのままにする。** 根拠は上の実測である——**`TERM=zaytos`を足しても、ポインタ8バイトと文字列13バイトに整列を足して30バイト前後で、残りは約3.9KiBある**（見積もり）。

**ただし「残り」がいくら要るかを知らない。** **ユーザースタックの使用量は測っていない**（遠征スタックには高水位の測定があるが、ユーザースタックには無い。実測）。

**したがって、この段で測る。** 遠征スタックと同じ形——**張るときに既知のバイトで埋め、プロセスが終わってから高水位を読み、判定行に出す。** **半分を超えていたら、そのとき増やす判断をする。**

### 5. 上限を名前で置き、越えたら拒む

`MAX_ENVP`（要素数）と、**表と文字列がスタックの1ページに収まること**を、`argv`と同じ形で確かめる。**越えたら`UserLoadError::ArgumentsTooLong`と同じ族の誤りで拒む**（黙って切り詰めない）。

## Alternatives Considered

### (a) プロセスごとに環境を持ち、`spawn`が親の写しを子へ渡す

**却下する。** **親の環境はRing 3のスタックの上に在るので、カーネルが読むにはユーザーポインタの検証がもう1本要る。** **利用者が居ない**——**環境を変える手段（`export`相当）がそもそも無いので、写しても親と子で必ず同じである。**

**採るのは、シェルに`VAR=val cmd`か`export`が来たときである。** そのとき`spawn`の第3引数として受ける形になり、**`copy_user_argv`と同じ検証をもう1本書くことになる。**

### (b) `/etc/environment`を`init`が読む

**却下する。今は。** **一見こちらのほうが「設定」らしいが、書き込みが永続しない**（ADR-0037。**再起動で消える**）。**したがってファイルにしても、運用者が変えるには像を建て直すことになる**——**カーネルの定数と手間が変わらない。**

**採るのはP段（永続化）の後である。** **そのときは「設定の源をどこに置くか」の判断として、改めて決める。**

### (c) カーネルコマンドラインから受ける

**却下する。** **入口が無い**——bootloaderがカーネルへ文字列を渡す経路を作るところから要る。**`/etc/environment`より遠い。**

### (d) `envp`を使わず、専用のシステムコール（`getenv`相当）で引かせる

**却下する。** **枠がSysVの形で在るのに、別経路を作ることになる。** **Cの`crt0`は`envp`をスタックから読む**ので、**専用の経路はC移植のときに捨てることになる。**

## Consequences

**得るもの。**

- **設定を渡す面ができる。** 形はSysVなので、`crt0`がそのまま書ける
- **ユーザーポインタの面が増えない**（決定2）
- **ユーザースタックの使用量が観測できるようになる**（決定4）。**いまは誰も見ていない**

**失うもの・引き受ける制約。**

- **環境をプロセスごとに変えられない。** シェルから`export`はできない
- **`TERM`以外は入っていない。** 足すたびに「読む者が居るか」を問うことになる
- **キーボード配列の選択は、これだけでは解けない。** **配列を読むのはカーネルのデコーダで、Ring 3の`envp`を見ない**——**解くには「カーネルが読む設定の源」が別に要る**（`/etc/environment`か、システムコールか）。**`docs/foundation-inventory.md`の連鎖の表は、この点で楽観していた。** **`envp`が直接解くのは`TERM`と`PS1`の側だけである**

**将来のトレードオフ。**

- **`execve`が来たら、第3引数として`envp`を受ける形になる。** そのとき決定2を見直す
- **P段の後に`/etc/environment`を判断する**（却下案(b)）
