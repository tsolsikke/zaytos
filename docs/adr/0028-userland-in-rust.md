# 0028. ユーザーランドはRustで書き、ランタイムを持つ言語は移植しない

## Status
Accepted

## Date
2026-08-13

## Context

S10-bでファイル関連のシステムコールが揃い、S11で`init`と簡易シェルを書く段になった。
ここから先はカーネルではなくユーザープログラムを増やす作業が続く（`init`・`sh`・`ls`・`cat`・`echo`）。
**何語で書くかを決めていなかった。**

これまでのユーザープログラム（`hello`・`fault-test`・`syscall-test`）は
`#![no_std]`のRustで、`kernel/build.rs`が`rustc`を1回呼んで単独でリンクしている。
検証用に書いたものなので、言語の選択として決めた記録は無い。

「Goのプログラムを持ってきて動かせるか」という問いも出た。
これは言語の選択とは別の問い（移植の可否）だが、**同じ場所で答えないと後から混ざる。**

## Decision

**ユーザーランドはRustで書く。** `init`・`sh`・`ls`・`cat`・`echo`はいずれも`#![no_std]`のRustとする。

**とくに`init`はRustとする。** PID 1であり、落とすとシステムが終わる。
子プロセスの表を持ち回る仕事なので、境界検査のある言語で書く価値が最も大きい。

**Goの移植は行わない。**

## Alternatives Considered

- **C**: **却下しない。範囲を分けて別に扱う**（`vision.md`の「Cを最小限から順次移植する」）。
  ユーザーランドの本体をCで書く案は却下する——**`common::ext2`と同じ「ホスト上で純粋ロジックを試験する」様式が、この領域だけ効かなくなる。**
  Cの受け入れは「ZaytOS上でCのプログラムが動く」ことが目的であって、ユーザーランドの実装言語の問題ではない。

- **Go**: 却下。**Goのバイナリはランタイムを内蔵しており、`main`が呼ばれる前に`mmap`・`clone`・futex・シグナルを要求する。**
  ホストでビルドして持ってくる形はELFとしては成立するが、**`iretq`した直後に未実装のシステムコールで止まる。**
  動かすには`GOOS=zaytos`の移植が要り、その前に上記4つが要る。

  **これはGoに固有ではない。** ランタイムを持つ言語（Java・Python・Node）に共通する。
  **Cが例外的に軽いのは、言語側にランタイムを持たないからである**（Rustの`no_std`が動くのも同じ理由）。

- **アセンブリ**: 却下。`syscall-test`はABIの契約を確かめるために意図してアセンブリで書いているが、
  あれは**アセンブラが符号化することそのものが主張**だからである。`ls`や`cat`にその理由は無い。

## Consequences

- **新しい仕組みが要らない。** `build.rs`が`rustc`で建て、`mke2fs -d`が像へ入れる経路が既に動いている。
- **検証の様式が揃う。** 書式の組み立てのような純粋ロジックを、`cargo test`でホスト上から試験できる。
- **`unsafe`の境界が保てる。** システムコールの包みだけが`unsafe`で、本体は安全側に置ける。
- **失うもの——「既存のプログラムを持ってきて動かす」は当面できない。**
  Rustで書いたものしか動かないので、ユーザーランドの充実は自作の速度で決まる。
  **これはCの受け入れ（`vision.md`）で緩む見込みだが、それは別の段の話である。**
- **`GOOS=zaytos`の移植は否定していない。** 却下したのは「いま行うこと」であって、
  `mmap`・`clone`・futex・シグナルが揃った後に再検討できる。**そのとき参照する前提はこのADRに書いてある。**
