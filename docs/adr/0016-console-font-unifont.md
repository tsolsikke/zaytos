# 0016. コンソールフォントに GNU Unifont を採用し、半角と全角を最初から区別する

## Status
Accepted

## Date
2026-07-20

## Context
M3-b で文字を描くにあたり、ビットマップフォントを選ぶ必要がある。要求は
次の 3 つ。

1. 権利関係が明確で、リポジトリに含めて再配布できること。
2. 当面は英語（ASCII）だけでよいが、**将来的に日本語へ対応できること**。
3. 管理しやすいこと。等幅であること。

2 が設計上いちばん効く。日本語の文字はコンソール上で半角 2 つ分の幅を占める
（全角）。この区別を後から入れると、桁数の計算・折り返し・カーソル移動・
行内の消去といったコンソールの中核を全部見直すことになる。つまり、ASCII しか
描かない今の時点で幅の概念を持っておかないと、日本語対応は「追加」ではなく
「作り直し」になる。

フォント形式としては、アウトライン（TrueType 等）はラスタライザが必要で、
kernel に持ち込むには重い。ビットマップフォントなら、グリフのビット列を
そのまま画面へ展開するだけで済む。

## Decision

**GNU Unifont（バージョン 17.0.05）のビットマップグリフを採用する。**

- 半角は 8x16、全角は 16x16。半角 1 セル・全角 2 セルという、必要としている
  モデルがフォント側の構造そのものになっている。
- Unicode 全体を収録しており、日本語を追加する際にフォントを差し替える必要が
  ない。同じデータから範囲を足すだけで済む。
- ライセンスはグリフ部分が SIL Open Font License 1.1 と GPLv2 以降（フォント
  埋め込み例外つき）のデュアル。ZaytOS では OFL 1.1 の条件で利用する。
  Reserved Font Name の宣言は無い。日本語の漢字を担う `jiskan16` 由来の部分は
  パブリックドメインであると配布物の `COPYING` に明記されている。
  全文と出典は `third_party/unifont/` に置く。

**グリフの検索は `char` を鍵にする。** `u8` を入口にすると、日本語を追加する
時点でインターフェースごと変わる。

**半角・全角の区別を最初から持つ。** ASCII しか収録していない現時点でも、
グリフは占有セル数（1 または 2）を返す。

**上流の hex 形式を情報源とし、Rust のテーブルは生成する。**
`third_party/unifont/unifont-subset.hex` に使う範囲だけを抜き出して置き、
`cargo xtask gen-font` が `kernel/src/graphics/font/unifont_glyphs.rs` を
生成する。生成物もコミットする（ビルド時に上流ファイルを必要としないため）。
日本語対応は「hex に範囲を追記して再生成」で完了する。

**行データは半角・全角とも `u16` に最上位ビット詰めで格納する。**
半角（1 バイト）は 8 ビット左へ寄せる。こうすると描画側は幅に関わらず
「ビット `0x8000 >> x` が立っているか」だけを見ればよく、半角と全角で
描画コードが分岐しない。

**現時点の収録範囲は U+0020..U+007E と U+FFFD。** 未収録の文字は U+FFFD
（置換文字）へフォールバックする。フォールバックすら引けない場合は空白の
半角グリフを返し、決して panic しない。

## Alternatives Considered

- **IBM VGA 8x16（コードページ437）**: OS 自作でよく使われる古典的な選択肢で
  入手も容易だが、日本語を一切含まないため要求 2 を満たさない。また ROM 由来の
  ビットマップデータの権利状態が明確とは言いがたく、要求 1 の観点でも避けたい。
  却下。
- **Terminus / Spleen / Cozette 等の端末向けビットマップフォント**: ライセンスは
  明確（OFL / MIT）で字形も良いが、いずれも日本語を含まない。ASCII 用にこれらを
  採用し、日本語用に別のフォントを併用する構成も考えられるが、2 つのフォントで
  字形の高さ・太さ・ベースラインを揃える必要が生じ、管理が増える。却下。
- **東雲フォント / 美咲フォント**: 日本語のビットマップフォントとして実績があり
  権利上も扱いやすい。ただし収録は日本語圏の文字が中心で、Unicode 全体を 1 つの
  データで賄える Unifont の方が、範囲を足していく運用に向く。却下（Unifont の
  字形に不満が出た場合の代替候補としては残る）。
- **自前でグリフを起こす**: 権利問題は完全に消えるが、ASCII 95 文字ですら相当な
  作業量で、字形の質も期待できない。日本語に至っては現実的でない。却下。
- **アウトラインフォント（TrueType）をラスタライズする**: 任意のサイズで
  きれいに出せるが、kernel にラスタライザを持ち込むことになる。現時点で必要と
  していない複雑さ。却下。
- **半角固定で作り、日本語対応時に全角を導入する**: 今は最も単純。しかし
  コンソールの桁計算・折り返し・カーソル移動を後から全面的に見直すことになり、
  「追加」ではなく「作り直し」になる。要求 2 が最初から分かっている以上、
  幅の概念だけは先に入れる。却下。
- **ビルド時に hex を解析する（build.rs）**: 生成物をコミットせずに済むが、
  ホスト向けテストを含む全ビルドで解析が走り、`build.rs` の対象ターゲット
  判定（troubleshooting 参照）も絡んで複雑になる。生成物をコミットする方が、
  差分としてレビューでき、ビルドも単純。却下。

## Consequences
- 日本語対応は、hex への範囲追加と `cargo xtask gen-font` の再実行で済む。
  検索・描画・幅計算のコードは変更不要。
- 現時点のグリフデータは 96 文字で 3,072 バイト。kernel イメージへの影響は
  無視できる。CJK 統合漢字まで含めると 600KB 超になるため、その時点で
  部分集合に絞るか、ファイルシステム対応（M6）後にディスクから読み込む方式を
  検討する。判断は実際にその規模になってから行う。
- グリフデータと生成物は Unifont の派生物として OFL 1.1 の下にある。ZaytOS 自身の
  コードとはライセンスが異なるため、`third_party/unifont/` に出典と全文を置き、
  生成物のヘッダにも由来を明記する。ZaytOS 本体のライセンスを決める際は、
  OFL のフォントを同梱する構成であることを前提にする。
- 等幅・ビットマップであるため、字形の美しさは犠牲になる。コンソール用途では
  問題にならない。
- Unifont は結合文字・複雑な字形整形（アラビア文字等）を前提としない単純な
  グリフ集合であり、そうした言語の正しい表示はできない。日本語・英語の範囲では
  問題にならないため、現時点では扱わない。
