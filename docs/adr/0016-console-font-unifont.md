# 0016. コンソールフォントにGNU Unifontを採用し、半角と全角を最初から区別する

## Status
Accepted

## Date
2026-07-20

## Context
M3-bで文字を描くにあたり、ビットマップフォントを選ぶ必要がある。
要求は次の3つ。

1. 権利関係が明確で、リポジトリに含めて再配布できること。
2. 当面は英語（ASCII）だけでよいが、**将来的に日本語へ対応できること**。
3. 管理しやすいこと。等幅であること。

2が設計上いちばん効く。
日本語の文字はコンソール上で半角2つ分の幅を占める（全角）。
この区別を後から入れると、桁数の計算・折り返し・カーソル移動・行内の消去といったコンソールの中核を全部見直すことになる。
つまり、ASCIIしか描かない今の時点で幅の概念を持っておかないと、日本語対応は「追加」ではなく「作り直し」になる。

フォント形式としては、アウトライン（TrueType等）はラスタライザが必要で、kernelに持ち込むには重い。
ビットマップフォントなら、グリフのビット列をそのまま画面へ展開するだけで済む。

## Decision

**GNU Unifont（バージョン17.0.05）のビットマップグリフを採用する。**

- 半角は8x16、全角は16x16。半角1セル・全角2セルという、必要としているモデルがフォント側の構造そのものになっている。
- Unicode全体を収録しており、日本語を追加する際にフォントを差し替える必要がない。同じデータから範囲を足すだけで済む。
- ライセンスはグリフ部分がSIL Open Font License 1.1とGPLv2以降（フォント埋め込み例外つき）のデュアル。ZaytOSではOFL 1.1の条件で利用する。Reserved Font Nameの宣言は無い。日本語の漢字を担う`jiskan16`由来の部分はパブリックドメインであると配布物の`COPYING`に明記されている。全文と出典は`third_party/unifont/`に置く。

グリフの検索は`char`を鍵にする。
`u8`を入口にすると、日本語を追加する時点でインターフェースごと変わる。

半角・全角の区別を最初から持つ。
ASCIIしか収録していない現時点でも、グリフは占有セル数（1または2）を返す。

上流のhex形式を情報源とし、Rustのテーブルは生成する。
`third_party/unifont/unifont-subset.hex`に使う範囲だけを抜き出して置き、`cargo xtask gen-font`が`kernel/src/graphics/font/unifont_glyphs.rs`を生成する。
生成物もコミットする（ビルド時に上流ファイルを必要としないため）。
日本語対応は「hexに範囲を追記して再生成」で完了する。

行データは半角・全角とも`u16`に最上位ビット詰めで格納する。
半角（1バイト）は8ビット左へ寄せる。
こうすると描画側は幅に関わらず「ビット`0x8000 >> x`が立っているか」だけを見ればよく、半角と全角で描画コードが分岐しない。

現時点の収録範囲はU+0020..U+007EとU+FFFD。
未収録の文字はU+FFFD（置換文字）へフォールバックする。
フォールバックすら引けない場合は空白の半角グリフを返し、決してpanicしない。

## Alternatives Considered

- **IBM VGA 8x16（コードページ437）**: OS自作でよく使われる古典的な選択肢で入手も容易だが、日本語を一切含まないため要求2を満たさない。またROM由来のビットマップデータの権利状態が明確とは言いがたく、要求1の観点でも避けたい。却下。
- Terminus / Spleen / Cozette等の端末向けビットマップフォント: ライセンスは明確（OFL / MIT）で字形も良いが、いずれも日本語を含まない。ASCII用にこれらを採用し、日本語用に別のフォントを併用する構成も考えられるが、2つのフォントで字形の高さ・太さ・ベースラインを揃える必要が生じ、管理が増える。却下。
- **東雲フォント / 美咲フォント**: 日本語のビットマップフォントとして実績があり権利上も扱いやすい。ただし収録は日本語圏の文字が中心で、Unicode全体を1つのデータで賄えるUnifontの方が、範囲を足していく運用に向く。却下（Unifontの字形に不満が出た場合の代替候補としては残る）。
- **自前でグリフを起こす**: 権利問題は完全に消えるが、ASCII 95文字ですら相当な作業量で、字形の質も期待できない。日本語に至っては現実的でない。却下。
- **アウトラインフォント（TrueType）をラスタライズする**: 任意のサイズできれいに出せるが、kernelにラスタライザを持ち込むことになる。現時点で必要としていない複雑さ。却下。
- **半角固定で作り、日本語対応時に全角を導入する**: 今は最も単純。しかしコンソールの桁計算・折り返し・カーソル移動を後から全面的に見直すことになり、「追加」ではなく「作り直し」になる。要求2が最初から分かっている以上、幅の概念だけは先に入れる。却下。
- **ビルド時にhexを解析する（build.rs）**: 生成物をコミットせずに済むが、ホスト向けテストを含む全ビルドで解析が走り、`build.rs`の対象ターゲット判定（troubleshooting参照）も絡んで複雑になる。生成物をコミットする方が、差分としてレビューでき、ビルドも単純。却下。

## Consequences
- 日本語対応は、hexへの範囲追加と`cargo xtask gen-font`の再実行で済む。検索・描画・幅計算のコードは変更不要。
- 現時点のグリフデータは96文字で3,072バイト。kernelイメージへの影響は無視できる。CJK統合漢字まで含めると600KB超になるため、その時点で部分集合に絞るか、ファイルシステム対応（M6）後にディスクから読み込む方式を検討する。判断は実際にその規模になってから行う。
- グリフデータと生成物はUnifontの派生物としてOFL 1.1の下にある。ZaytOS自身のコードとはライセンスが異なるため、`third_party/unifont/`に出典と全文を置き、生成物のヘッダにも由来を明記する。ZaytOS本体のライセンスを決める際は、OFLのフォントを同梱する構成であることを前提にする。
- 等幅・ビットマップであるため、字形の美しさは犠牲になる。コンソール用途では問題にならない。
- Unifontは結合文字・複雑な字形整形（アラビア文字等）を前提としない単純なグリフ集合であり、そうした言語の正しい表示はできない。日本語・英語の範囲では問題にならないため、現時点では扱わない。
