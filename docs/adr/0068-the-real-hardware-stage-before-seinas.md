# 0068. 実機の段——VirtualBox で起動するまでの直しを、Seinas より先に閉じる

## Status

Accepted（設計。2026-09-22 に承認。運用者の決定は 2026-09-21 と 2026-09-22。小段ごとの実装はレビューを受ける）

## Date

2026-09-22

## Context

**実機の棚卸し（`docs/hardware-inventory.md`）で、QEMU でしか成り立たない前提が見つかった。** **いちばん重いのは、メモリが 1GiB を超えると起動しないことである**（実測。`tools/qemu-variants.py` の `q35-1500m` と `q35-6g`）。**`xtask` の QEMU は 256MiB の `pc` だけで走るので、`--full` の 357 項目はどれもこれを見ていなかった。**

**VirtualBox で起動するまでに、直すものが 4 つ在る**——**1GiB の壁・ディスク（virtio-blk が無い）・起動媒体の像、それに実機では i8042 の不在。** **PIT が刻まないと黙って止まる形も見つかった**（実測。`q35-no-pit`）。

**切り替え前に初期の恒等写像（物理 [0, 1GiB)）の下で触る箇所を数えると、3 つ在る**（読んだ）。

1. **BootInfo 本体**——今回の #PF はここである（`kernel_main` の `&*handoff.boot_info`）
2. **メモリマップの記述子**——`frame_allocator::build` と `MappedRanges::build` が読む
3. **自前のページ表に使うフレームへの書き込み**——**アロケータは範囲の表の先頭から配り、範囲はメモリマップの並びのままである**（並べ替えていない）。**UEFI の仕様はマップの並びを約束していないので、1GiB より上のフレームを書きうる。** **OVMF のマップは番地の順なので、QEMU では踏まない**（推測）

**フレームバッファと ACPI の表は、切り替えの前には値を控えるだけで、読むのは自前のページ表の下である**（読んだ）。**LOADER_DATA は「張るが配らない」分類である**（`memory_map::classify`）——**切り替えの後なら、BootInfo も像も安全に読める。**

## Decision（運用者の決定）

1. **設計は実機を前提にする。** **開発で確かめる機械は QEMU と VirtualBox の 2 つで、VirtualBox は「QEMU でしか成り立たない前提」を割る 2 台目として使う。** **将来は実機（USB のキーボードとマウス）で動かす**（2026-09-21）。
2. **実機対応を Seinas より先にやる**（2026-09-22）。**次の 6 つを 1 つの段として閉じてから、第2段階の設計へ進む**——**1GiB の壁、i8042、PIT の沈黙、RAM ディスク、起動媒体の像、それに切り替え前のフレームの配り（上の 3）。**
3. **段の到達条件**（2026-09-22）——**VirtualBox で ZaytOS が起動し、シェルのプロンプトが出る。** **QEMU で 6GiB・`i8042=off`・`pit=off` が止まらない**（`tools/qemu-variants.py` で確かめる）。
4. **1GiB を超える構成を検査に足す**（必須。**今回の壁が隠れていた理由である**）。**`xtask` の QEMU の既定を `q35` にするかは、AHCI を扱う段で判断する。**
5. **VirtualBox の VM を作ってよい**（2026-09-22）。**条件**——
   - **作るのは起動できるようになってから**（1GiB の壁・RAM ディスク・起動媒体の像が入った後）
   - **名前に接頭辞 `zaytos-` を付ける。** **接頭辞の無い VM には一切触らない。** **既存の VM は、読むことも含めて操作しない**
   - **作る・消す操作は、接頭辞を確かめてから行う。** **道具は接頭辞の無い名前を渡されたら拒む**
   - **消す手順を書く**
   - **VDI の置き場は `D:\Users\User\VirtualBox VMs\`**（WSL2 では `/mnt/d/Users/User/VirtualBox VMs/`）
6. **USB（xHCI と HID）は第2段階の設計で出す**（2026-09-21 の決定「今のうちに実装する」は変わらない）。

## 設計（2026-09-22 に承認）

### 刻み（6 つを 5 つの小段に分ける）

| 小段 | 中身 | 触るもの | 到達（この小段の判定） |
|---|---|---|---|
| HW-a | **1GiB の壁**と、**切り替え前のフレームの配り** | ブートローダ・`frame_allocator`・起動の最初期 | **`q35` の 6GiB でプロンプトが出る** |
| HW-b | **i8042 が無くても止まらない** | FADT の読み・`setup_keyboard` | **`i8042=off` でプロンプトが出る** |
| HW-c | **PIT が刻まなくても止まらない**（PM タイマで較正する） | FADT の読み・LAPIC タイマの較正 | **`pit=off` でプロンプトが出る** |
| HW-d | **RAM ディスク** | ブートローダ・BootInfo・像の出所 | **virtio-blk を外した QEMU でプロンプトが出る** |
| HW-e | **起動媒体の像**と、**VirtualBox の VM の道具** | `xtask`・`tools/` | **VirtualBox でプロンプトが出る**（段の到達条件） |

**順序は運用者の決定のとおりで、(d) の 3 つ目は HW-a に入れる**（同じ最初期の問題で、同じ 6GiB の判定で見える）。**各小段で既定の起動ログは動く見込み**（行が増える・番地が動く）——**何が動いてよいかは各小段の提示で先に書く。**

### HW-a——受け渡しを 1GiB の下へ、切り替え前の配りを低い番地から

- **ブートローダが受け渡しの領域を `AllocateType::MaxAddress(1GiB − 1)` で取る**（LOADER_DATA）。**BootInfo をそこへ書く。** **メモリマップは、ExitBootServices の後に uefi-rs のバッファからこの領域へ写す**（領域の大きさは、記述子の数の見込みに余裕を足して先に取る。**足りなければ飛ぶ前に止まり、理由を出す**）。**ExitBootServices の後もブートローダはファームウェアの恒等写像の下に居るので、写すことはできる**（推測。実装で確かめる）。
- **アロケータの範囲の表を、番地の順に並べる**（`frame_allocator::build` の中で。**純粋な処理なので、ホストのテストで固定する**）。**先頭の範囲は 1MiB から上の低い RAM になり、切り替え前の配り（ページ表の数十枚）は 1GiB の下に収まる。** **それでも、切り替え前に配ったフレームが 1GiB の下に在ることを実行時にも確かめる**（外れたら止めて理由を出す）。
- **この形は、レビューが推した形と違う。** **推されたのは「切り替え前の配りを 1GiB の下に限る」だった。** **採ったのは「番地の順に並べる＋実行時に確かめる」である。** **理由は、限る形だとアロケータに「切り替えの前か後か」の状態が増え、配る側が切り替えの位置を知ることになるからである。** **並べ替えは状態を持たずに「低い番地から配る」性質を与え、確かめが外れたときに声を出す**——**組み合わせとして成り立つ**（レビューの回答。2026-09-22）。**限る形は、確かめが実際に鳴ったときに考え直す。**
- **4GiB を超える RAM で次に何が起きるかは、直してから 6GiB で測る**（範囲の表の容量 256・計画の容量 256 など。**今は 1 行目で止まるので測れない**）。
- **判定**——**`q35` の 6GiB で起動してプロンプトが出る**（下の「検査に足す形」）。
- **破壊**——**(1) 受け渡しを `AnyPages` へ戻す**（6GiB の判定が #PF で落ちる）。**(2) 範囲の表を番地の逆順に並べる**（機会を作る形——**切り替え前のページ表が 1GiB より上から配られ、6GiB の判定が落ちる**。**QEMU のマップは番地の順なので、並べ替えを外すだけでは機会が無い**）。

### HW-b——i8042 が無くても止まらない

- **FADT を読む**（純粋な解析。ホストのテストで固定する）。**リビジョンが 2 以上で `IAPC_BOOT_ARCH` の 8042 のビットが落ちていれば、i8042 は無いとして探らない。** **リビジョン 1 ではこの欄は予約なので使わない。** **QEMU の `pc` の FADT は 116 バイトで、ACPI 1.0 の形の長さである**（起動ログの `length=116`。**リビジョンの値は読んでいない**——実装で行に出す）。
- **探って `InputBufferStuck` や状態 0xFF なら、「i8042 は無い」と 1 行出して、PS/2 の無いまま続ける**（いまは halting）。**IRQ1 は開けない。**
- **`q35` の FADT が `i8042=off` でビットを落とすかは確かめていない**（推測。**実装で FADT の値を行に出して確かめる**）。**落とさなくても、探る側で止まらない。**
- **判定**——**`i8042=off` でプロンプトが出て、「i8042 は無い」の行が出る。** **破壊**——**探って見つからないときに止める形へ戻す。**

### HW-c——PIT が刻まなくても止まらない（ACPI の PM タイマで較正する）

- **いまは PIT の IRQ0 のティックで LAPIC タイマを較正し、較正できなければ PIT のまま進む。** **PIT が刻まなければ、その先のティック待ちで黙る。**
- **案**——**PIT のティックが較正の締切までに 1 本も来なければ、ACPI の PM タイマ（FADT の `PM_TMR_BLK`。3.579545MHz、24 ビットか 32 ビット）で LAPIC タイマを較正し、LAPIC タイマへ移る。** **PM タイマは割り込みを要らず、ポートを読むだけである。** **PM タイマも進まなければ、理由を出して止める**（黙らない）。
- **到達条件の「止まらない」は、起動してプロンプトが出るという意味である**（運用者の回答。2026-09-22）。**したがって沈黙を止めるだけでは足りず、較正の代わりを入れる。**
- **PIT も PM タイマも無い機械は在りうる**（ACPI のハードウェア縮小形。**FADT が PM タイマを持たない**）。**両方無ければ、理由を出して止まる形はそのまま残す**（同）。
- **判定**——**`pit=off` でプロンプトが出て、較正に PM タイマを使ったことが行に出る。** **破壊**——**PM タイマの代わりを外す**（`pit=off` の判定が上限で落ちる）。
- **VirtualBox と実機の多くは PIT を持つ**（推測）。**この道を通すのは QEMU の `pit=off` だけである。**

### HW-d——RAM ディスク

- **ブートローダが ESP の `\zaytos\fs.img` を読み、BootInfo で渡す**（在れば。**BootInfo の版を 1 つ上げ、像の番地と長さを足す**）。**カーネルのファイルを読むのと同じ経路である。**
- **カーネルは、virtio-blk が在ればいまのまま使う。** **無ければ RAM の像を写して使う**（いまは halting）。**どちらも無ければ、いまと同じく止める。**
- **RAM の像では書き戻しをしない。** **締めの書き戻しは「装置が無いので RAM に残る」と 1 行出して飛ばす**（永続性は無い）。**virtio の割り込みの経路も作らない。**
- **判定**——**virtio-blk を外し、ESP に像を置いた QEMU でプロンプトが出る。** **破壊**——**RAM の像を見ない**（virtio-blk が無いので止まる）。

### HW-e——起動媒体の像と、VirtualBox の VM の道具

- **起動媒体の像**——**GPT の生の像に、ESP（FAT32）を 1 つ置く**（`\EFI\BOOT\BOOTX64.EFI`・`\zaytos\kernel.elf`・`\zaytos\fs.img`）。**`cargo xtask image` で `target/media/zaytos.img` を作る。** **同じ像を VirtualBox（`qemu-img convert -O vdi`）と、将来の実機の USB メモリに使う。**
- **FAT32 は `xtask` の中で書く**（設計の回答。2026-09-22）。**FAT を作る道具（`dosfstools`・`mtools`）は入っていない**（実測）。**外の依存を増やさない。**
- **自分で書いた FAT を自分で読んで確かめる形にしない。** **読み手は OVMF（外の道具）で、像だけから起動させて確かめる**（同）。
- **FAT32 の境界を守る。** **FAT32 はデータ領域のクラスタ数が 65,525 以上であることが仕様で、それより少ない像を FAT32 と名乗らせると、厳しいファームウェアは読まないことがある**（一般論。レビューの指摘）。**OVMF は寛容なので、通っても実機で落ちうる。** **大きさはこの境界から導く**——**クラスタを 512 バイト（1 セクタ）にすると、データ領域だけで 65,525 × 512 ≈ 32MiB が下限になる。** **予約領域と 2 つの FAT を足しても余裕が倍になるよう、ESP を 64MiB にする**（クラスタ数は約 13 万の見込み。計算）。**`xtask` は書いた像のクラスタ数を数え直し、65,525 以上 0x0FFFFFF5 未満でなければ像を作らずに止める。**
- **VirtualBox の EFI も EDK2 の系統である**（推測）。**2 台とも寛容な側かもしれないので、境界を守ることが実機への備えになる。****`qemu-img` の vvfat は、MBR に種類 0x0B の FAT32 を置いた 504MiB の像を作り、「FAT32 は試されていない」と警告した**（実測。GPT でも ESP の種類でもないので採らない）。
- **確かめ方**——**QEMU で、この像だけ（vvfat も virtio-blk も無し）を起動ディスクにして、プロンプトが出ること**（RAM ディスクで起動する）。**VirtualBox の前に QEMU で割る。**
- **VirtualBox の VM の道具**——**`tools/` の下に 1 つ置く**（案。名前は実装で決める）。**作る・像を差し替える・起こす・画面を読む・止める・消すの 6 つ。** **どの操作も名前が `zaytos-` で始まることを先に確かめ、始まらなければ拒む。** **VM の一覧（`list vms`）は使わない**——**接頭辞の無い VM の名前を読まないためである。**

### VirtualBox の VM の作り方（案）

- **置き場**——**VM の設定（`.vbox`）も VDI と同じ `D:\Users\User\VirtualBox VMs\<名前>\` の下に置く**（`createvm --basefolder`）。**VirtualBox の既定の機械フォルダは `C:\Users\User\VirtualBox VMs` で、指定の場所と違う**（実測。`list systemproperties`）。**既定の設定は変えない**（ホストの設定の変更になる）。
- **空白を含むパス**——**`wslpath -w` は `/mnt/d/Users/User/VirtualBox VMs` を `D:\Users\User\VirtualBox VMs` へ直し、逆向きも合った**（実測）。**そのパスを 1 つの引数として `VBoxManage.exe` へ渡すと、空白で切れずに届いた**（実測。存在しない媒体を `showmediuminfo` で訊き、エラーの文面にパスがそのまま出た。**何も作らず、何も登録していない**）。
- **作る**（名前の例 `zaytos-dev`）——`createvm --name zaytos-dev --ostype Other_64 --basefolder "D:\Users\User\VirtualBox VMs" --register`、`modifyvm zaytos-dev --firmware efi --memory 2048 --cpus 2 --uart1 0x3F8 4 --uartmode1 file "<置き場>\serial.log" --keyboard ps2 --mouse ps2 --nic1 none --audio-enabled off --usb-xhci off`、`storagectl zaytos-dev --name SATA --add sata`、`storageattach zaytos-dev --storagectl SATA --port 0 --type hdd --medium "<置き場>\zaytos.vdi"`。**メモリは 2GiB にする**——**1GiB の壁を VirtualBox でも越える構成である。** **オプションの綴り（音声と USB の切り方など）は 7.2 の `modifyvm` の help で確かめる**（案。確かめていない）。
- **像を差し替える**——**`storageattach ... --medium none` で外し、`closemedium disk "<VDI>"` で登録から外し、ファイルを置き換えてから付け直す**（同じパス・同じ名前の衝突を避ける）。
- **起こす・見る・止める**——`startvm zaytos-dev --type headless`、シリアルは `/mnt/d/.../serial.log` を読む、画面は `controlvm zaytos-dev screenshotpng`、止めるのは `controlvm zaytos-dev poweroff`。
- **Hyper-V の上で動いているか**——**`<置き場>\Logs\VBox.log` の `NEM` の行で確かめる**（推測を実測にする）。
- **消す手順**——**(1) 名前が `zaytos-` で始まることを確かめる。(2) 動いていれば `controlvm <名前> poweroff`。(3) `storageattach ... --medium none` で像を外し、`closemedium disk "<VDI>" --delete` で登録から外して消す。(4) `unregistervm <名前> --delete` で VM の設定とログを消す。(5) 置き場のディレクトリが空になったことを確かめる。**
- **道具の自己検査**——**接頭辞の無い名前を渡すと拒むことを、VBoxManage を呼ばずに確かめる**（ホストに触れない）。

### 検査に足す形（1GiB を超える構成は必須）

- **`--full` に「機械の変種」の項目を足す**——**既定の像を、QEMU の属性を変えて起こし、プロンプトが出て `[ERROR]` が無いことを見る。**
  - `q35` の 6GiB（HW-a）
  - `q35` の `i8042=off`（HW-b）
  - `q35` の `pit=off`（HW-c）
  - virtio-blk を外して ESP に像を置く（HW-d）
  - 起動媒体の像だけで起こす（HW-e）
- **破壊は上の各小段の 1 本ずつ**（HW-a は 2 本）。**見込みは既定 5・破壊 6 で、357 から 368 項目**（見込み。**項目数の契機 380 まで 12**）。
- **破壊の判定は「プロンプトが出ない」では足りない**（レビューの足す1点。2026-09-22）。**狙いと別の所で起動が止まっても「捕まった」になる**——**`shm-mmap-maps-nothing` と `shm-close-keeps-refs` で 2 回踏んだ形である**（`docs/verification-coverage.md` の「置けない破壊の一覧」）。**6 本それぞれに「狙いどおりに止まった行」を決め、その行が出たことまでを判定にする。**

| 破壊 | 変種 | 狙いどおりに止まった行 |
|---|---|---|
| 受け渡しを `AnyPages` へ戻す（HW-a） | `q35` の 6GiB | **#PF の `cr2` が、ブートローダが出した BootInfo の番地と等しい**（ブートローダが置いた番地を 1 行出すようにする） |
| 範囲の表を番地の逆順に並べる（HW-a） | `q35` の 6GiB | **切り替え前のフレームが 1GiB の下に無い、と言って止まる行**（HW-a で足す確かめ） |
| 探って見つからないときに止める形へ戻す（HW-b） | `q35` の `i8042=off` | **`i8042: failed to read the configuration byte (InputBufferStuck); halting`**（いまの行） |
| PM タイマを無いものとして扱う（HW-c） | `q35` の `pit=off` | **PIT が刻まず PM タイマも無い、と言って止まる行**（HW-c で足す。**両方無いときの道も通す**） |
| RAM の像を見ない（HW-d） | virtio-blk 無し | **装置も RAM の像も無い、と言って止まる行** |
| 像から `fs.img` を外す（HW-e） | 起動媒体の像だけ | **ブートローダの「`fs.img` が無い」の行と、HW-d の止まる行**（HW-e の提示で決め直す） |

- **所要の見積もり**——**既定の像でプロンプトが出るまでは、`pc` の 256MiB で 8.5〜8.7 秒、`q35` の 256MiB と 1GiB で 7.5〜7.6 秒だった**（実測。2 回ずつ。2026-09-22。**メモリの大きさで所要は変わらなかった**）。**既定の変種 5 つは像を共有するので建て直しが無く、1 つ約 10 秒で約 1 分。** **破壊 6 本はカーネルかブートローダを建て直すので、1 本あたり建て直し約 7 秒と起動を足して約 15 秒で、約 1.5 分。** **合わせて約 2.5 分の見込みである**（見込み。**6GiB の起動の所要は、直すまで測れない**）。**高負荷の回（起動が普段の 2.7 倍より遅かった回が在る）でも 7 分ほどで、`--full` の上限 195 分に対して、いまの壁時計（86.5〜141 分）に足しても収まる。**
- **起こし方は `tools/qemu-variants.py` の変種と同じにする**（道具は人が読むためのもの、`--full` の項目は判定を持つもの。**起こし方の表は `xtask` に持ち、道具は同じ値を使う**——二重に持たない形は実装で出す）。
- **VirtualBox の走行は `--full` に入れない**（ホストの VirtualBox に依り、重い）。**段の締めで道具を使って確かめ、結果を記録する。**

## 設計の回答（2026-09-22）

- **設計を承認する。** **(d) の 3 つ目がレビューの推した形から外れたことは、HW-a に理由と一緒に書いた。**
- **HW-c は PM タイマで較正する。** **両方無ければ理由を出して止まる。**
- **FAT32 は `xtask` の中で書く。** **読み手は OVMF で、FAT32 の境界（クラスタ数 65,525 以上）から大きさを導く。**
- **小段ごとに実装を提示して止まる。HW-a から。**

## Alternatives Considered

- **初期ページ表の恒等を 4GiB へ広げる**——**採らない。** **受け渡しの置き場がファームウェアの配り方に依ったままになる**（4GiB の上へ置く機械では同じことが起きる）。**切り替え前の配りの問題も残る。**
- **VirtualBox で virtio-scsi を使う**——**採らない。** **実機に無い。** **RAM ディスクで起動し、ディスクの装置は AHCI の段で扱う。**
- **VM の設定を既定の機械フォルダ（C:）に置く**——**採らない。** **VDI と設定が別の場所に分かれ、消す手順が 2 か所になる。**

## Consequences

- **VirtualBox で起動できれば、第2段階の全段を 2 台で確かめられる**（運用者の理由。2026-09-22）。
- **`docs/hardware-inventory.md` の冒頭は、この ADR を名前で指す**（決定は写さない）。
- **限界**——**RAM ディスクでは書いた内容が残らない**（AHCI の段まで）。**USB が無いので、VirtualBox では PS/2 の打鍵で確かめる**（USB は第2段階）。**`i8042=off` と `pit=off` の形は VirtualBox では作れない**（推測）——**QEMU だけで見る。**
