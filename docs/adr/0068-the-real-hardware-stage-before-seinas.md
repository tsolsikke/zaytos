# 0068. 実機の段——VirtualBox で起動するまでの直しを、Seinas より先に閉じる

## Status

Accepted（設計。2026-09-22 に承認。運用者の決定は 2026-09-21 と 2026-09-22（USB を HW-f に入れる決定を含む）。小段ごとの実装はレビューを受ける）

## Date

2026-09-22

## Context

**実機の棚卸し（`docs/hardware-inventory.md`）で、QEMU でしか成り立たない前提が見つかった。** **いちばん重いのは、メモリが 1GiB を超えると起動しないことである**（実測。`tools/qemu-variants.py` の `q35-1500m` と `q35-6g`）。**`xtask` の QEMU は 256MiB の `pc` だけで走るので、`--full` の 357 項目はどれもこれを見ていなかった。**

**VirtualBox で起動するまでに、直すものが 4 つ在る**——**1GiB の壁・ディスク（virtio-blk が無い）・起動媒体の像、それに実機では i8042 の不在。** **PIT が刻まないと黙って止まる形も見つかった**（実測。`q35-no-pit`）。

**切り替え前に初期の恒等写像（物理 [0, 1GiB)）の下で触る箇所を数えると、3 つ在る**（読んだ）。

1. **BootInfo 本体**——今回の #PF はここである（`kernel_main` の `&*handoff.boot_info`）
2. **メモリマップの記述子**——`frame_allocator::build` と `MappedRanges::build` が読む
3. **自前のページ表に使うフレームへの書き込み**——**アロケータは範囲の表の先頭から配る。** **範囲は `insert_free_range` が番地の順の位置へ差し込むので、メモリマップの並びに依らず番地の順に保たれ、最も低い空きから配られる**（読んだ。HW-a の実装の前に読み直して分かった）。**設計の提示では「並べ替えていない」と書いたが、読み違いだった。** **残る穴は、組み立ての側がこの性質を前提にしたまま、届く範囲を確かめていないことである**——**`PageTableBuilder` の注釈は「現在有効な（UEFI 由来の）ページテーブルの下で届く」と書いていたが、切り替え前に有効なのは [0, 1GiB) しか張らない初期ページ表である。**

**フレームバッファと ACPI の表は、切り替えの前には値を控えるだけで、読むのは自前のページ表の下である**（読んだ）。**LOADER_DATA は「張るが配らない」分類である**（`memory_map::classify`）——**切り替えの後なら、BootInfo も像も安全に読める。**

## Decision（運用者の決定）

1. **設計は実機を前提にする。** **開発で確かめる機械は QEMU と VirtualBox の 2 つで、VirtualBox は「QEMU でしか成り立たない前提」を割る 2 台目として使う。** **将来は実機（USB のキーボードとマウス）で動かす**（2026-09-21）。
2. **実機対応を Seinas より先にやる**（2026-09-22）。**次の 6 つを 1 つの段として閉じてから、第2段階の設計へ進む**——**1GiB の壁、i8042、PIT の沈黙、RAM ディスク、起動媒体の像、それに切り替え前のフレームの配り（上の 3）。** **USB（下の 7。HW-f）を足して 7 つになった**（2026-09-22）。
3. **段の到達条件**（2026-09-22）——**VirtualBox で ZaytOS が起動し、シェルのプロンプトが出る。** **QEMU で 6GiB・`i8042=off`・`pit=off` が止まらない**（`tools/qemu-variants.py` で確かめる）。**2 つ足した**（2026-09-22）——**VirtualBox で、USB キーボードの打鍵がシェルに届く。** **QEMU で、`i8042=off` と `qemu-xhci`・`usb-kbd` の変種がプロンプトまで進み、打鍵が届く**（USB キーボードしか無い機械の形。HW-b の変種と組む）。
4. **1GiB を超える構成を検査に足す**（必須。**今回の壁が隠れていた理由である**）。**`xtask` の QEMU の既定を `q35` にするかは、AHCI を扱う段で判断する。**
5. **VirtualBox の VM を作ってよい**（2026-09-22）。**条件**——
   - **作るのは起動できるようになってから**（1GiB の壁・RAM ディスク・起動媒体の像が入った後）
   - **名前に接頭辞 `zaytos-` を付ける。** **接頭辞の無い VM には一切触らない。** **既存の VM は、読むことも含めて操作しない**
   - **作る・消す操作は、接頭辞を確かめてから行う。** **道具は接頭辞の無い名前を渡されたら拒む**
   - **消す手順を書く**
   - **VDI の置き場は `D:\Users\User\VirtualBox VMs\`**（WSL2 では `/mnt/d/Users/User/VirtualBox VMs/`）
6. **PS/2 は残す。USB は置き換えではなく追加である**（2026-09-22）。**理由**（レビューの説明を運用者が受けた）——**ノート PC の内蔵キーボードは今も i8042 のことが多い。** **USB の開発中は、PS/2 が操作の手段になる。** **GUI や USB が壊れたときの最後の手段になる。** **既存の打鍵の検査がそのまま使える。**
7. **USB（xHCI と HID）は実機の段の最後（HW-f）に入れる**（2026-09-22）。**VirtualBox を USB キーボードで動かしてから、第2段階（Seinas）へ進む。** **前の版は「第2段階の設計で出す」だった**（2026-09-21 の決定「今のうちに実装する」は変わらない）。
8. **段の順序**（2026-09-22）——**HW-c（PIT）→ HW-d（RAM ディスク）→ HW-e（起動媒体と VirtualBox。PS/2 で起動を確かめる）→ HW-f（USB）→ 実機の段を閉じる → 第2段階の設計。** **HW-f の設計は HW-e を閉じた後に出してよい**（VirtualBox で xHCI がどこに居るかを実測できるため）。

## 設計（2026-09-22 に承認）

### 刻み（6 つを 5 つの小段に分ける）

| 小段 | 中身 | 触るもの | 到達（この小段の判定） |
|---|---|---|---|
| HW-a | **1GiB の壁**と、**切り替え前のフレームの配り** | ブートローダ・`frame_allocator`・起動の最初期 | **`q35` の 6GiB でプロンプトが出る** |
| HW-b | **i8042 が無くても止まらない** | FADT の読み・`setup_keyboard` | **`i8042=off` でプロンプトが出る** |
| HW-c | **PIT が刻まなくても止まらない**（PM タイマで較正する） | FADT の読み・LAPIC タイマの較正 | **`pit=off` でプロンプトが出る** |
| HW-d | **RAM ディスク** | ブートローダ・BootInfo・像の出所 | **virtio-blk を外した QEMU でプロンプトが出る** |
| HW-e | **起動媒体の像**と、**VirtualBox の VM の道具** | `xtask`・`tools/` | **VirtualBox でプロンプトが出る**（段の到達条件。PS/2 で確かめる） |
| HW-f | **USB キーボード**（xHCI と HID。**PS/2 は残す**） | PCI・xHCI・HID・入力 | **VirtualBox で USB キーボードの打鍵がシェルに届く。** **QEMU の `i8042=off`＋`qemu-xhci`＋`usb-kbd` でプロンプトまで進み、打鍵が届く** |

**HW-f は 2026-09-22 に足した**（運用者の決定。上の Decision の 7）。**HW-f の中の刻みは、HW-f の設計で出す**（下の「HW-f——USB キーボード」）。

**順序は運用者の決定のとおりで、(d) の 3 つ目は HW-a に入れる**（同じ最初期の問題で、同じ 6GiB の判定で見える）。**各小段で既定の起動ログは動く見込み**（行が増える・番地が動く）——**何が動いてよいかは各小段の提示で先に書く。**

### HW-a——受け渡しを 1GiB の下へ、切り替え前の配りを低い番地から

- **ブートローダが受け渡しの領域を `AllocateType::MaxAddress(1GiB − 1)` で取る**（LOADER_DATA）。**BootInfo をそこへ書く。** **メモリマップは、ExitBootServices の後に uefi-rs のバッファからこの領域へ写す**（領域の大きさは、記述子の数の見込みに余裕を足して先に取る。**足りなければ飛ぶ前に止まり、理由を出す**）。**ExitBootServices の後もブートローダはファームウェアの恒等写像の下に居るので、写すことはできる**（推測。実装で確かめる）。
- **アロケータの範囲の表は、既に番地の順に保たれている**（`insert_free_range`。上の Context の 3）。**この性質をホストのテストで固定する**（マップを高い番地から入れても、最も低い空きから配ること）。**先頭の範囲は低い RAM で、切り替え前の配り（ページ表の数十枚）は 1GiB の下に収まる。** **それでも、切り替え前の組み立ては、配られたフレームが初期ページ表の届く範囲に在ることを書く前に確かめる**（`PageTableBuilder` に届く範囲を渡す。外れたら止めて理由を出す）。
- **この形は、レビューが推した形と違う。** **推されたのは「切り替え前の配りを 1GiB の下に限る」だった。** **採ったのは「番地の順（既に在る性質）＋書く前の確かめ」である。** **理由は、限る形だとアロケータに「切り替えの前か後か」の状態が増え、配る側が切り替えの位置を知ることになるからである。** **番地の順は状態を持たずに「低い番地から配る」性質を与え、確かめが外れたときに声を出す**——**組み合わせとして成り立つ**（レビューの回答。2026-09-22）。**確かめは組み立ての側に置いた**——**窓で触れる範囲を知っているのは、窓を使う側だからである。** **限る形は、確かめが実際に鳴ったときに考え直す。**
- **4GiB を超える RAM で次に何が起きるかは、直してから 6GiB で測る**（範囲の表の容量 256・計画の容量 256 など。**今は 1 行目で止まるので測れない**）。
- **判定**——**`q35` の 6GiB で起動してプロンプトが出る**（下の「検査に足す形」）。
- **破壊**——**(1) 受け渡しを `AnyPages` へ戻す**（6GiB の判定が #PF で落ちる）。**(2) アロケータが最も高い空きから配る**（機会を作る形——**切り替え前のページ表が 1GiB より上から配られ、組み立ての確かめが止める**。**範囲は既に番地の順なので、並べ替えを壊すだけでは機会が無い**——配る向きを裏返す）。

### HW-b——i8042 が無くても止まらない

- **FADT を読む**（純粋な解析。ホストのテストで固定する）。**リビジョンが 2 以上で `IAPC_BOOT_ARCH` の 8042 のビットが落ちていれば、i8042 は無いとして探らない。**（**→ 境界は 3 である。** 下の「HW-b の実装」の「設計から外れたもの」）**リビジョン 1 ではこの欄は予約なので使わない。** **QEMU の `pc` の FADT は 116 バイトで、ACPI 1.0 の形の長さである**（起動ログの `length=116`。**リビジョンの値は読んでいない**——実装で行に出す）。
- **探って `InputBufferStuck` や状態 0xFF なら、「i8042 は無い」と 1 行出して、PS/2 の無いまま続ける**（いまは halting）。**IRQ1 は開けない。**
- **`q35` の FADT が `i8042=off` でビットを落とすかは確かめていない**（推測。**実装で FADT の値を行に出して確かめる**）。**落とさなくても、探る側で止まらない。**
- **判定**——**`i8042=off` でプロンプトが出て、「i8042 は無い」の行が出る。** **破壊**——**探って見つからないときに止める形へ戻す。**

### HW-c——PIT が刻まなくても止まらない（ACPI の PM タイマで較正する）

- **いまは PIT の IRQ0 のティックで LAPIC タイマを較正し、較正できなければ PIT のまま進む。** **PIT が刻まなければ、その先のティック待ちで黙る。**
- **案**——**PIT のティックが較正の締切までに 1 本も来なければ、ACPI の PM タイマ（FADT の `PM_TMR_BLK`。3.579545MHz、24 ビットか 32 ビット）で LAPIC タイマを較正し、LAPIC タイマへ移る。** **PM タイマは割り込みを要らず、ポートを読むだけである。** **PM タイマも進まなければ、理由を出して止める**（黙らない）。
- **到達条件の「止まらない」は、起動してプロンプトが出るという意味である**（運用者の回答。2026-09-22）。**したがって沈黙を止めるだけでは足りず、較正の代わりを入れる。**
- **PIT も PM タイマも無い機械は在りうる**（ACPI のハードウェア縮小形。**FADT が PM タイマを持たない**）。**両方無ければ、理由を出して止まる形はそのまま残す**（同）。
- **判定**——**`pit=off` でプロンプトが出て、較正に PM タイマを使ったことが行に出る。** **破壊**——**PM タイマの代わりを外す**（`pit=off` の判定が上限で落ちる）。
- **VirtualBox と実機の多くは PIT を持つ**（推測）。**この道を通すのは QEMU の `pit=off` だけである。**

### HW-d——RAM ディスク

- **ブートローダが ESP の `\zaytos\fs.img` を読み、BootInfo で渡す**（在れば。**BootInfo の版を 1 つ上げ、像の番地と長さを足す**）。**カーネルのファイルを読むのと同じ経路である。**
- **カーネルは、virtio-blk が在ればいまのまま使う。** **無ければ RAM の像を写して使う**（いまは halting）。**どちらも無ければ、いまと同じく止める。**
- **RAM の像では書き戻しをしない。** **締めの書き戻しは「装置が無いので RAM に残る」と 1 行出して飛ばす**（永続性は無い）。**virtio の割り込みの経路も作らない。**
- **判定**——**virtio-blk を外し、ESP に像を置いた QEMU でプロンプトが出る。** **破壊**——**RAM の像を見ない**（virtio-blk が無いので止まる）。

### HW-e——起動媒体の像と、VirtualBox の VM の道具

- **起動媒体の像**——**GPT の生の像に、ESP（FAT32）を 1 つ置く**（`\EFI\BOOT\BOOTX64.EFI`・`\zaytos\kernel.elf`・`\zaytos\fs.img`）。**`cargo xtask image` で `target/media/zaytos.img` を作る。** **同じ像を VirtualBox（`qemu-img convert -O vdi`）と、将来の実機の USB メモリに使う。**
- **FAT32 は `xtask` の中で書く**（設計の回答。2026-09-22）。**FAT を作る道具（`dosfstools`・`mtools`）は入っていない**（実測）。**外の依存を増やさない。**
- **自分で書いた FAT を自分で読んで確かめる形にしない。** **読み手は OVMF（外の道具）で、像だけから起動させて確かめる**（同）。
- **FAT32 の境界を守る。** **FAT32 はデータ領域のクラスタ数が 65,525 以上であることが仕様で、それより少ない像を FAT32 と名乗らせると、厳しいファームウェアは読まないことがある**（一般論。レビューの指摘）。**OVMF は寛容なので、通っても実機で落ちうる。** **大きさはこの境界から導く**——**クラスタを 512 バイト（1 セクタ）にすると、データ領域だけで 65,525 × 512 ≈ 32MiB が下限になる。** **予約領域と 2 つの FAT を足しても余裕が倍になるよう、ESP を 64MiB にする**（クラスタ数は約 13 万の見込み。計算）。**`xtask` は書いた像のクラスタ数を数え直し、65,525 以上 0x0FFFFFF5 未満でなければ像を作らずに止める。**
- **VirtualBox の EFI も EDK2 の系統である**（推測）。**2 台とも寛容な側かもしれないので、境界を守ることが実機への備えになる。****`qemu-img` の vvfat は、MBR に種類 0x0B の FAT32 を置いた 504MiB の像を作り、「FAT32 は試されていない」と警告した**（実測。GPT でも ESP の種類でもないので採らない）。
- **確かめ方**——**QEMU で、この像だけ（vvfat も virtio-blk も無し）を起動ディスクにして、プロンプトが出ること**（RAM ディスクで起動する）。**VirtualBox の前に QEMU で割る。**
- **VirtualBox の VM の道具**——**`tools/` の下に 1 つ置く**（案。名前は実装で決める）。**作る・像を差し替える・起こす・画面を読む・止める・消すの 6 つ。** **どの操作も名前が `zaytos-` で始まることを先に確かめ、始まらなければ拒む。** **VM の一覧（`list vms`）は使わない**——**接頭辞の無い VM の名前を読まないためである。**

### VirtualBox の VM の作り方（案）

- **置き場**——**VM の設定（`.vbox`）も VDI と同じ `D:\Users\User\VirtualBox VMs\<名前>\` の下に置く**（`createvm --basefolder`）。**VirtualBox の既定の機械フォルダは `C:\Users\User\VirtualBox VMs` で、指定の場所と違う**（実測。`list systemproperties`）。**既定の設定は変えない**（ホストの設定の変更になる）。
- **空白を含むパス**——**`wslpath -w` は `/mnt/d/Users/User/VirtualBox VMs` を `D:\Users\User\VirtualBox VMs` へ直し、逆向きも合った**（実測）。**そのパスを 1 つの引数として `VBoxManage.exe` へ渡すと、空白で切れずに届いた**（実測。存在しない媒体を `showmediuminfo` で訊き、エラーの文面にパスがそのまま出た。**何も作らず、何も登録していない**）。
- **作る**（名前の例 `zaytos-dev`）——`createvm --name zaytos-dev --ostype Other_64 --basefolder "D:\Users\User\VirtualBox VMs" --register`、`modifyvm zaytos-dev --firmware efi --memory 2048 --cpus 2 --uart1 0x3F8 4 --uartmode1 file "<置き場>\serial.log" --keyboard ps2 --mouse ps2 --nic1 none --audio-enabled off --usb-xhci off`、`storagectl zaytos-dev --name SATA --add sata`、`storageattach zaytos-dev --storagectl SATA --port 0 --type hdd --medium "<置き場>\zaytos.vdi"`。**メモリは 2GiB にする**——**1GiB の壁を VirtualBox でも越える構成である。** **オプションの綴り（音声と USB の切り方など）は 7.2 の `modifyvm` の help で確かめる**（案。確かめていない）。
- **像を差し替える**——**`storageattach ... --medium none` で外し、`closemedium disk "<VDI>"` で登録から外し、ファイルを置き換えてから付け直す**（同じパス・同じ名前の衝突を避ける）。
- **起こす・見る・止める**——`startvm zaytos-dev --type headless`、シリアルは `/mnt/d/.../serial.log` を読む、画面は `controlvm zaytos-dev screenshotpng`、止めるのは `controlvm zaytos-dev poweroff`。
- **Hyper-V の上で動いているか**——**`<置き場>\Logs\VBox.log` の `NEM` の行で確かめる**（推測を実測にする）。
- **消す手順**——**(1) 名前が `zaytos-` で始まることを確かめる。(2) 動いていれば `controlvm <名前> poweroff`。(3) `storageattach ... --medium none` で像を外し、`closemedium disk "<VDI>" --delete` で登録から外して消す。(4) `unregistervm <名前> --delete` で VM の設定とログを消す。(5) 置き場のディレクトリが空になったことを確かめる。**
- **道具の自己検査**——**接頭辞の無い名前を渡すと拒むことを、VBoxManage を呼ばずに確かめる**（ホストに触れない）。

### HW-f——USB キーボード（設計は HW-e を閉じた後に出す）

**設計で答えることは、レビューの指示（2026-09-22）のとおりである。** **設計を提示して止まる**（レビュー必須）。

- **刻み方**——**S13（virtio-blk）と同等以上の見込みなので、小段に分ける**（例: PCI と xHCI の初期化・ファームウェアからの引き継ぎ／リングと装置の列挙／HID キーボードから `input_event` とコンソール／VirtualBox）。
- **既に決めてあること（2026-09-21 の統合版の 2.）をそのまま当てる**——**カーネルは装置ごとのドライバで、すべて Linux の `input_event` で渡す。** **キーの番号を 1 つに揃える**（HID の用途コードをカーネルで `KEY_*` へ写す）。**USB キーボードでカーネルコンソール（CUI）が打てる経路を設計する**（いまの `Decoder` が PS/2 のスキャンコードを直に食べているなら、その扱い）。**複数の装置を 1 本の入力 fd に混ぜるか、装置ごとに分けるか。**
- **USB で答えること**——**ファームウェアからの引き継ぎ**（USB Legacy Support の所有権の移譲）。**割り込み**（INTx・MSI・MSI-X）。**HID のブートプロトコルで始めるか、レポート記述子を読むか。** **ハブ越しの装置を初版で扱うか、抜き差し**（起動時に在る装置だけでよいか）。**64 ビットの DMA 番地**（xHCI の AC64。**HW-a の持ち越しの行の契機がここで来る**）。**PCI がバス 0 だけの件**（`docs/hardware-inventory.md` の「PCIはバス0だけ」。**VirtualBox と QEMU で xHCI がどこに居るかを実測し、ブリッジの先を今扱うかを決める**）。**64 ビットの BAR の写像。**
- **USB マウスを HW-f に含めるか**——**レビューの推しは含める**（キーボードの上に乗るので小さい見込み。Seinas の zeyes がすぐ使える）。**含めるなら `EV_REL` と `BTN_*` の形で、カーソルの位置はカーネルに持たせない**（統合版のとおり）。**含めないなら理由を書く。**
- **確かめること**（推測を含む）——**QEMU の `sendkey` が `usb-kbd` に届くか**（i8042 が在るときと無いとき）。**打鍵の検査が USB でも使えるか。** **VirtualBox の USB キーボード（`--keyboard usb`）と xHCI（`--usbxhci`）の設定、拡張パックが要らないこと**（棚卸しでは本体に在る見込み）。
- **置けない破壊と置ける破壊を先に数える。**

### 検査に足す形（1GiB を超える構成は必須）

- **`--full` に「機械の変種」の項目を足す**——**既定の像を、QEMU の属性を変えて起こし、プロンプトが出て `[ERROR]` が無いことを見る。**
  - `q35` の 6GiB（HW-a）
  - `q35` の `i8042=off`（HW-b）
  - `q35` の `pit=off`（HW-c）
  - virtio-blk を外して ESP に像を置く（HW-d）
  - 起動媒体の像だけで起こす（HW-e）
- **破壊は上の各小段の 1 本ずつ**（HW-a は 2 本）。**見込みは既定 5・破壊 6 で、357 から 368 項目**（見込み。**項目数の契機 380 まで 12**）。
- **破壊の判定は「プロンプトが出ない」では足りない**（レビューの足す1点。2026-09-22）。**狙いと別の所で起動が止まっても「捕まった」になる**——**`shm-mmap-maps-nothing` と `shm-close-keeps-refs` で 2 回踏んだ形である**（`docs/verification-coverage.md` の「置けない破壊の一覧」）。**6 本それぞれに「狙いどおりに止まった行」を決め、その行が出たことまでを判定にする。**

| 破壊 | 変種 | 狙いどおりに止まった行 |
|---|---|---|
| 受け渡しを `AnyPages` へ戻す（HW-a） | `q35` の 6GiB | **#PF の `cr2` が、ブートローダが出した BootInfo の番地と等しい**（ブートローダが置いた番地を 1 行出すようにする） |
| アロケータが最も高い空きから配る（HW-a） | `q35` の 6GiB | **切り替え前のフレームが 1GiB の下に無い、と言って止まる行**（HW-a で足す確かめ） |
| 探って見つからないときに止める形へ戻す（HW-b） | `q35` の `i8042=off`（**→ `pc` の `i8042=off` で見る。** 「HW-b の実装」） | **`i8042: failed to read the configuration byte (InputBufferStuck); halting`**（いまの行） |
| PM タイマを無いものとして扱う（HW-c） | `q35` の `pit=off` | **PIT が刻まず PM タイマも無い、と言って止まる行**（HW-c で足す。**両方無いときの道も通す**） |
| RAM の像を見ない（HW-d） | virtio-blk 無し | **装置も RAM の像も無い、と言って止まる行** |
| 像から `fs.img` を外す（HW-e） | 起動媒体の像だけ | **ブートローダの `fs-image: no \zaytos\fs.img on the ESP` と、カーネルの `virtio-blk: no device with an I/O BAR0 was found on bus 0, and the bootloader handed over no RAM image` の両方**（HW-e で決めた。**止まる所は HW-d の破壊より前である**——実測） |

- **所要の見積もり**——**既定の像でプロンプトが出るまでは、`pc` の 256MiB で 8.5〜8.7 秒、`q35` の 256MiB と 1GiB で 7.5〜7.6 秒だった**（実測。2 回ずつ。2026-09-22。**メモリの大きさで所要は変わらなかった**）。**既定の変種 5 つは像を共有するので建て直しが無く、1 つ約 10 秒で約 1 分。** **破壊 6 本はカーネルかブートローダを建て直すので、1 本あたり建て直し約 7 秒と起動を足して約 15 秒で、約 1.5 分。** **合わせて約 2.5 分の見込みである**（見込み。**6GiB の起動の所要は、直すまで測れない**）。**高負荷の回（起動が普段の 2.7 倍より遅かった回が在る）でも 7 分ほどで、`--full` の上限 195 分に対して、いまの壁時計（86.5〜141 分）に足しても収まる。**
- **起こし方は `tools/qemu-variants.py` の変種と同じにする**（道具は人が読むためのもの、`--full` の項目は判定を持つもの。**起こし方の表は `xtask` に持ち、道具は同じ値を使う**——二重に持たない形は実装で出す）。
- **VirtualBox の走行は `--full` に入れない**（ホストの VirtualBox に依り、重い）。**段の締めで道具を使って確かめ、結果を記録する。**

## HW-a の実装（2026-09-22）

### 入れたもの

- **ブートローダ**——**受け渡しの領域（BootInfo 1 ページ＋メモリマップの写し 16 ページ）を `AllocateType::MaxAddress(BOOT_IDENTITY_REACH − 1)` で取る。** **ExitBootServices の後に、uefi-rs のバッファからメモリマップを写す。** **入りきらなければ飛ぶ前に止まる。** **置いた番地と写した先を 1 行ずつ出す。**
- **`common::boot_info`**——**`BOOT_IDENTITY_REACH`（1GiB）と `HANDOFF_MEMORY_MAP_PAGES`（16）。** **カーネルの静的な初期ページ表（2MiB × 512）がこの値と一致することを、コンパイル時に確かめる**（`const _: () = assert!(...)`）。
- **`PageTableBuilder`**——**届く範囲を持てるようにした**（`new_within_reach`）。**切り替え前の組み立て（d-1）だけが `BOOT_IDENTITY_REACH` を渡し、配られたフレームが外なら書く前に止める。** **止まるときは専用の 1 行を出す。** **`alloc_zeroed_table` の注釈にあった「UEFI 由来のページテーブルの下で届く」は、切り替え前の実態（初期ページ表）に合わせて直した。**
- **アロケータ**——**範囲が番地の順に保たれ、最も低い空きから配る性質をホストのテストで固定した**（`ranges_stay_in_address_order_whatever_the_map_order`）。**コードは変えていない。**
- **破壊 2 本**（`handoff-anywhere`（ブートローダ）・`frame-allocator-hands-out-high-first`（カーネル））と、**機械の変種の項目の族**（`cargo xtask run --machine-variant q35-6g`）。
- **検査の構成 1 つ**（`frame-allocator-high-after-switch`。**破壊ではないので `SABOTAGE_FEATURES` に入れない**）。**自前のページ表へ切り替えた後から、アロケータが最も高い空きから配る。** **4GiB の上から配った枚数を計器に出し、0 なら偽の緑として落とす**（レビューの足す1点。2026-09-22——**既定では低い番地から配るので、6GiB で起動しても 4GiB の上は張ってあることしか確かめられない**）。**破壊の `frame-allocator-hands-out-high-first` と同じ経路を、切り替えの後から通す形にまとめた。**
- **`--full` は 357 から 361 項目**（既定 1・検査の構成 1・破壊 2）。

### 実測

- **`q35` の 6GiB**——**受け渡しの領域は `0x3ffef000..0x40000000`（1GiB のすぐ下）に置かれた。** **ファームウェアのメモリマップのバッファは `0x7e66b018`（1GiB の上）だった**——**写しが要ったことの実測である。** **メモリマップは 6,624 バイト（138 本）で、256MiB の 6,192 バイト（129 本）より多い。** **張る範囲の計画は 6 つで、4GiB の上の RAM（`0x100000000..0x200000000`）も張られた。** **プロンプトまで 8.2〜9.6 秒**（`--machine-variant` の 3 回）。**`[ERROR]` と `[WARN]` は 0。**
- **`tools/qemu-variants.py` で、`pc` の 6GiB と `q35` の 1.5GiB もプロンプトまで進んだ**（直す前はどちらも #PF で止まった）。
- **受け渡しの領域は、写したメモリマップの中で「種類 2（LoaderData）・17 ページ」の 1 本として載っていた**（`0x3ffef000..0x40000000`。**プロンプトが出た後の物理メモリを QEMU の monitor の `pmemsave` で読み出し、ホストで解いた**。レビューの確かめ（a））。**カーネルは LoaderData を「張るが配らない」と分類する**（`memory_map::classify`）**ので、空きの表に一度も入らず、起動の後もずっと配られない**——**読み終えるまでではなく、恒久に取っておく形である。**
- **検査の構成では、4GiB の上から 2,481 枚が配られ、プロンプトまで進んだ**（3 回とも。7.9〜8.0 秒。`[ERROR]` は 0）。**上に置かれたものを行で確かめた**——**direct map のページ表（PML4 `0x1fffff000`）、ヒープ（`0x1ffafb000..`）、高位のページ表（`0x1ffafa000`）、virtio のリング（`0x1ffadb000..`。装置は上の番地で読み書きできた）、像の写し（`0x1ff600000..`）。** **起動の経路で、番地を 32 ビットへ切り詰めて壊れる箇所は表に出なかった。**
- **破壊は 2 本とも 3 回ずつ、狙いどおりの所で止まった**——**`handoff-anywhere` は #PF の `cr2` が BootInfo の番地と等しく（0x7e66c000）、`frame-allocator-hands-out-high-first` は組み立ての確かめが `0x1fffff000` で止めた。**

### 既定の起動で動いたもの（定型の 5 形）

- **起動ログ**——**69 行が動き、番地を伏せると 5 行が残った。** **4 行は U/S 監査の kernel entries が 1 つ増えた分**（4,297 → 4,298、2,917 → 2,918）**で、像の終わりが 1 ページ伸びた**（`0x4a8000` → `0x4a9000`）。**残る 1 行はカーネルスタックの高水位で、66,176 → 66,416 バイト（+240）。** **ブートローダの 2 行は揺れる行として伏せた**（受け渡しの番地は `-smp` の数で動く。実測で 1・2・4 が `0xde5f000`・`0xde74000`・`0xde78000`）。
- **高水位の +240 の内訳**（**2026-09-23 に直した**）——**+240 は `kernel_main` の枠の +96（39,320 → 39,416）と `build_and_verify_high_half` の枠の +144（9,816 → 9,960）で、ちょうど合う**（`.debug_frame` の CFA で読んだ。`f8f07a2` と `076b7fe` の像）。**どちらも最深の経路の上に在る**（下の「起動時のスタックの最深経路」）。**最初に書いた内訳は誤りだった**——**`objdump` で前置きの `sub rsp` を 1 つだけ読んだが、4KiB を超える枠は 4KiB ずつ段階的に確保されるので、最初の `sub` は枠の大きさではない**（`kernel_main` を 6,504 → 6,600 と読んだ）。**組み立ての鎖（`map_page`・`ensure_child`・`alloc_zeroed_table`）は広がったが、最深の経路の上に無い。** **残りは 64,656 バイトで、ガードページが在る。削らずに参照を録り直した。**
- **ページ表のフレームは 4 のまま。** **遠征スタックの高水位は動いていない。** **ホストのテストの名前は 663 本（+1）。**

### 限界

- **既定の構成では、6GiB で起動しても 4GiB の上のフレームは配られていない見込みである**（アロケータは低い番地から配るので。推測）。**上から配る形は検査の構成で見ている**（上の実測）。**見たのは起動からプロンプトまでで、シェルの上で動くものは見ていない。**
- **装置にも届く範囲がある**（DMA の番地の幅）。**持ち越しの行を立てた**（`docs/deferred-decisions.md` の「装置にも「届く範囲」がある」。契機は AHCI か xHCI の段）。
- **機械の変種の表は、`xtask`（判定を持つ）と `tools/qemu-variants.py`（人が読む）の 2 つに在る。** **いまは `q35-6g` が両方に同じ値で在る。** **二重に持たない形は、変種が増える小段（HW-b 以降）で出す。** **→ HW-b で解いた**（起こし方を `xtask/machine-variants.txt` の 1 つに置いた。**当時の限界としてこの行は残す**）。

## HW-b の実装（2026-09-22）

### 入れたもの

- **FADT を読む**（`kernel/src/acpi/fadt.rs`。純粋な解析で、ホストのテスト 4 本）。**`IAPC_BOOT_ARCH` の 8042 のビットだけを読み、答えを `acpi::I8042Presence`（在る・無い・言っていない）で出す。** **FADT の生の値は `acpi` の外へ出さない**（モジュールの「何を公開するか」）。**MADT の後に読む**——**起動ログの既存の行の並びを動かさないためである。**
- **`setup_keyboard`**——**FADT が「無い」と言えば、探らずに続く。** **言っていないか「在る」なら探り、答えが無ければ「無い」として続く**（直す前は halting）。**どちらも IRQ1 を開けず、I/O APIC へも配線しない。** **FADT が「在る」と言ったのに答えない形だけは `[ERROR]` を出す**（止めない。**言っていないときの答え無しは `[WARN]`**）。**答えが在れば、直す前と同じ手順である。**
- **i8042 が無いときの付随が 2 つ**——**`sti` 前の検証は、IRQ1 が閉じていることを期待にする。** **心拍の行の `i8042 OBF=` は、無ければポートを読まずに `absent` と出す**——**探らないと決めた機械でポートを叩かない。** **どちらも `keyboard::controller_present()`（`setup_keyboard` が開ける直前に立てる）で決める。**
- **破壊 1 本**（`i8042-halts-when-absent`。直す前の形）と、**機械の変種 2 つ**（`q35-no-i8042`・`pc-no-i8042`）。**判定はプロンプトと、どちらの道を通ったかの行である**（`VariantExpect::PromptAndLine`。**プロンプトだけでは道が分からない**）。
- **機械の変種の起こし方を 1 つのファイルに置いた**（`xtask/machine-variants.txt`。上の HW-a の限界の 3 つ目）。**`xtask` と `tools/qemu-variants.py` が両方ここを読む。** **判定は `xtask` だけが持つ**（`MACHINE_VARIANT_CHECKS` ほか）。**判定の表が指す名前が起こし方の表に在り、シリアルを持つことを、ホストのテストで見る**——**基底で捕まる。**
- **`--full` は 361 から 364 項目**（既定 2・破壊 1）。

### 設計から外れたもの（2 つ）

- **リビジョンの境界は 2 ではなく 3 である。** **上の設計は「リビジョンが 2 以上で」と書いていたが、8042 のビットはリビジョン 3（ACPI 2.0 の FADT）で定義された**——**ACPICA の `include/acpi/actbl.h` は、このビットに定義された版を `[V3]` と記している**（リビジョン 2 で定義されたのはレガシー装置のビットだけ）。**Linux も `FADT2_REVISION_ID`（3）以上でこのビットを読む**（`arch/x86/kernel/acpi/boot.c`）。**リビジョン 2 の FADT で予約の位置を「無い」と読むと、在る i8042 を探らなくなる**——**探る側へ倒した。**
- **変種を 2 つにし、破壊は `pc` で見る。** **設計は変種 1 つ（`q35` の `i8042=off`）で、破壊もそこで見る形だった。** **QEMU の `q35` は FADT のリビジョンが 3 で、`i8042=off` のときビットを落とす**（QEMU 8.2.2 の `init_common_fadt_data` が `iapc_boot_arch_8042()` を書く。**実測で `IAPC_BOOT_ARCH=0x0000`、在るときは `0x0002`**）——**FADT が先に答えるので、`q35` では探る側の道を通らない。** **したがって破壊は `q35` では捕まらない**（探らないので、止める形へ戻しても止まらない）。**`pc` は FADT のリビジョンが 1 で何も言わないので、探る道を通る。** **`pc` にも `i8042` の属性が在ることを確かめた**（`-machine pc,help`）。

### 実測

- **`q35-no-i8042`**——**FADT は `0xf779000` の 244 バイト、リビジョン 3、`IAPC_BOOT_ARCH=0x0000`。** **探らずにプロンプトまで 8.3〜8.8 秒**（4 回）。**`[ERROR]` は 0。** **心拍の行は `i8042 OBF=absent`。**
- **`pc-no-i8042`**——**FADT は 116 バイト、リビジョン 1。** **探って `InputBufferStuck`（状態 `0xff`）で、`[WARN]` を 1 行出して続いた。** **プロンプトまで 9.1〜9.5 秒**（4 回）。**`[ERROR]` は 0。**
- **破壊**——**4 回とも直す前の行（`i8042: failed to read the configuration byte (InputBufferStuck); halting`）で止まった**（5.4〜5.6 秒）。
- **`q35` の既定（i8042 が在る）**——**FADT が「在る」と言い（`0x0002`）、探って直す前と同じ手順で IRQ1 を開けた**（`cargo xtask run --machine-variant q35` で 1 回。9.2 秒）。
- **`q35-6g`**——**変えていない側も 3 回とも通った**（8.4〜8.5 秒）。

### 既定の起動で動いたもの（定型の 5 形）

- **起動ログ**——**564 行から 568 行。** **番地を伏せると、増えた 4 行（FADT の 3 行と `i8042: the FADT does not say ...`）のほかに 5 行が動いた。** **4 行は U/S 監査の kernel entries が 1 つ増えた分**（4,298 → 4,299、2,918 → 2,919）**で、像の終わりが 1 ページ伸びた**（`0x4a9000` → `0x4aa000`）。**残る 1 行はカーネルスタックの高水位で、66,416 → 66,816 バイト（+400）。**

### 限界

- **FADT が「無い」と言うのに在る機械では、キーボードを失う**（ファームウェアの誤り。在りうるかは推測）。**探らないと決めたので、その機械では確かめる道が無い。** **起動ログの `acpi: FADT revision …` の行で分かる。** **VirtualBox の FADT が何と言うかは読んでいない**——**VirtualBox では PS/2 の打鍵で確かめる予定なので、HW-e の最初の起動で読む**（持ち越しの行を立てた。`docs/deferred-decisions.md` の「FADT が「8042 は無い」と言うのに在る機械」）。

## HW-c の実装（2026-09-23）

### 入れたもの

- **FADT の PM タイマの欄を読む**（`kernel/src/acpi/fadt.rs`。**ホストのテスト 4 本**）。**`X_PM_TMR_BLK` を先に見て、0 なら旧い 32 ビットの欄へ落ちる**（ACPICA と同じ）。**幅は `Flags` の TMR_VAL_EXT が言う**（24 か 32）。**「無い」と「読めない形」を分ける**——**System I/O でない空間（ハードウェア縮小形の MMIO）は `Unsupported` で、無いものとして扱いつつ `[WARN]` を出す。**
- **PM タイマのモジュールを足した**（`kernel/src/pmtimer.rs`。**ホストのテスト 3 本**）。**ポートを 1 本読む `unsafe` と、幅で包み込む差、窓の実時間で割る式を持つ。** **時計として使わない**——**較正の窓を測るためだけに読む。** **書かない。**
- **較正を 2 つの基準で組み直した**（`kernel/src/apic.rs`）。**PIT の標本取りを関数へ出し、「ティックが 1 本も来ない」と「窓が閉じない」を分けた**——**前者だけが PM タイマへ倒す条件である**（後者は直す前どおり較正を諦め、PIT のまま進む）。**基準は戻り値に載せ、較正の行に出す**（`calibration against the PIT` / `against the ACPI PM timer`）。
- **両方無ければ理由を出して止まる**（運用者の決定）。**2 つの形がある**——**FADT が PM タイマを名乗らない**場合と、**名乗ったのに締切までに進まない**場合である。**どちらも `[ERROR]` の行を出して `halting` する**（直す前は、この先のティック待ちで黙って止まっていた）。
- **ICW2 の事後証明は、PIT が刻まない機械では取れない**——**`first_pic_vector()` が `None` のままになる。** **止めずに「言えない」と書く**（`sti` 前の項目 4 と同じ立ち位置）。**`None` を一色に扱わない**——**較正の基準を見て、ICW2 の誤りと PIT の不在を分ける。**
- **窓が一周より十分短いことを、const assert で守る**（レビューの確かめ。2026-09-23）。**幅で包み込む差は一周までしか正しくない**——**24 ビットは約 4.7 秒（16,777,216 刻み）で一周し、窓は 357,954 刻み（100ms）である。** **余裕を 10 倍に取り、窓を広げるか周波数の定数を変えたら建たない形にした。**
- **最初のエッジだけ締切を短くした**（同。**実機の起動時間に効く**）。**PIT が刻まない機械は、この締切ぶんだけ起動が延びる**——**実測で 10^10 TSC サイクルは 2.71 秒だった。** **1 本目だけ 10^9 サイクルにした**（TSC が 1GHz なら 1 秒、4GHz なら 0.25 秒で、10ms のティックに対して 25 周期以上の余裕がある）。**窓の中の待ちは長い上限のままである**（取りこぼしの回を諦めさせない）。
- **破壊 2 本**（`pm-timer-treated-as-absent`。**PM タイマを無いものとして渡す**。`pm-timer-double-frequency`。**周波数の定数を 2 倍にする**）と、**機械の変種 1 つ**（`q35-no-pit`）、**速さの判定 1 つ**（`lapic-timer-test rate-on-pm-timer`）。**`--full` は 364 から 368 項目。**
- **PM タイマで較正した値が正しいことを判定にした**（レビューの足す1点。2026-09-23）。**プロンプトが出るだけでは、周波数の定数や式を間違えてタイマが 2 倍の速さで刻んでも通る。** **既存の速さの判定（`lapic-timer-test` の `rate`。カーネルが言う経過秒とホストの実時間の比）を、`q35-no-pit` の機械でも回す形にした**——**`lapic-timer-test` に機械の変種の欄を足し、起こし方の表を共有する。** **破壊 `pm-timer-double-frequency` がその判定で落ちる。**
- **起こし方の表に `pc-no-pit` も足した**（`--full` は回さない。**旧い欄の道を人が確かめるためである**）。

### 実測

- **`q35-no-pit`**（3 回。**締切を短くした後**）——**FADT は PM タイマを `X_PM_TMR_BLK` で port `0x0608`、24 ビットと言う。** **較正の中央値は 62,510,557 Hz（ばらつき 15,270）。** **プロンプトまで 8.9〜9.0 秒で、`[ERROR]` は 0。** **`no PIC interrupt ever arrived ...` の行が出る**（ICW2 の証明が取れないこと）。
- **`pc-no-pit`**（1 回）——**FADT はリビジョン 1 なので旧い欄で、port `0xb008`、24 ビット。** **中央値 62,511,227 Hz（ばらつき 17,050）。** **プロンプトが出た。**
- **既定（PIT が在る）**——**基準は PIT のままで、中央値 62,491,770 Hz（ばらつき 155,330）。** **2 つの基準の差は 0.03%（約 310 ppm）である**——**独立した 2 つの時間基準が一致した。** **PM タイマのほうがばらつきが小さい**（窓の測り方が細かい）。
- **破壊 `pm-timer-treated-as-absent`**（3 回）——**`apic: the PIT did not tick and the FADT names no PM timer ...; halting` で止まり、プロンプトは出ない**（5.2〜5.3 秒）。
- **速さの判定**（`lapic-timer-test rate-on-pm-timer`）——**カーネルが言う 20 秒に対してホストの実時間も 20.0 秒で、比は 1.000 だった**（許容は 0.25）。**破壊 `pm-timer-double-frequency` では、カーネルが 10 秒と言う間にホストは 20.0 秒で、比は 0.500 で落ちた**（狙いどおり）。**「PM タイマへ倒すこと」と「PM タイマで正しく測ること」は、これで別々に見ている。**
- **起動の時間の内訳**（外から行の出た時刻を測った）——**締切を短くする前は、`pit=off` の起動が既定より約 2.4 秒長かった。** **内訳は、PIT の最初のティックの締切 2.71 秒（`waiting for the first tick` から `no PIT tick arrived` まで）と、PM タイマの 5 窓 0.52 秒である**（既定の PIT の 5 窓は 0.55 秒で、同じ）。**締切を 10^9 サイクルへ短くしたら、最初のエッジの待ちは 0.28 秒になり、`pit=off` のプロンプトは 11.17 秒から 8.29 秒になった**（既定の `pc` は 8.98 秒なので、いまは `pit=off` のほうが速い——`q35` の起動が `pc` より少し速いためである）。
- **他の変種**（`q35-6g`・`q35-no-i8042`・`pc-no-i8042`・検査の構成・HW-b の破壊）**も 1 回ずつ通した。**

### 既定の起動で動いたもの（定型の 5 形）

- **起動ログ**——**573 行から 574 行**（`acpi: FADT PM timer: ...` の 1 行）。**番地を伏せると、ほかに U/S 監査の kernel entries が +3 の行が 4 行**（像が 3 ページ伸びた。`0x4aa000` → `0x4ad000`）。
- **カーネルスタックの高水位は動いていない**（`66,816` / `68,280` / `70,968`）。**新しい枠はどれも最深の経路の上に無い**（`tools/frame-sizes.py` で読んだ——`fadt::pm_timer_block` 792、`sample_with_pit` 552、`read_pm_timer` 360、`sample_with_pm_timer` 264、`calibrate_timer` +96、`read_fadt` −176）。
- **遠征スタックの高水位も動いていない。** **ページ表のフレームも同じ。** **ホストのテストの名前は 671 本から 678 本（+7）。**

### 限界

- **32 ビットの PM タイマの道は、ホストのテストだけである。** **QEMU の `pc` も `q35` も TMR_VAL_EXT を落としていて 24 ビットだった**（実測）。
- **MMIO の PM タイマは読まない**（ハードウェア縮小形。`Unsupported` として無いものとして扱う）。**HPET も見ない。**
- **PIT が刻んでいて窓が閉じない回は、PM タイマへ倒さない**（較正を諦めて PIT のまま進む。直す前どおり）。**「刻んでいるが不安定」な機械は、この段では扱わない。**
- **VirtualBox と実機の多くは PIT を持つ見込みである**（推測）。**この道を通すのは QEMU の `pit=off` だけである。**
- **速さの判定が見るのは 20 秒である**（`lapic-timer-test` の窓）。**それより長い時間の漂流は見ていない**（`drift-test` は既定の構成で走る）。
- **PM タイマの幅が 32 ビットの機械では、窓の余裕はさらに広い**（一周が約 1,194 秒）。**const assert はいちばん狭い 24 ビットで守っている。**

## HW-d の実装（2026-09-23）

### 入れたもの

- **ブートローダが ESP の `\zaytos\fs.img` を読み、BootInfo で渡す。** **無ければ 0/0 で、行に「無い」と出す。** **`LOADER_DATA` の連続ページへ置く**（`AnyPages`。**受け渡しと違って 1GiB の下に置く必要は無い**——**カーネルが像を読むのは自前のページ表へ切り替えた後である**）。**中身は検証しない**（`ADR-0008` 「ローダは薄く」）。
- **BootInfo の版を 2 から 3 へ上げ、欄を末尾に 2 つ足した**（`fs_image`・`fs_image_bytes`）。**配置を固定するホストのテストに、末尾であることを書いた。** **片方だけが 0 の形は「無い」として扱う**（`fs_image_range`。ホストのテスト 1 本）。
- **カーネルは virtio-blk が在ればそちらを使い、無ければ渡された像から写す。** **どちらも無ければ、両方の不在を名指しで言って止まる**（直す前は「装置が無い」だけで止まっていた）。**長さが建てたときと違えば止める**（短い像を黙って写すと、後ろが 0 のまま残って別の所で落ちる）。**direct map の覆いは写す前に確かめる。**
- **RAM の像では書き戻さない。** **`fs-image-flush:` と `fs-image:` の 2 行で「装置が無いので書き戻さない・残らない」と言う**（黙って飛ばすと、「書き戻したのに残らない」と区別できない）。
- **ESP には常に `fs.img` を置く**（`stage_esp`）。**virtio-blk が在る回は使われない**——**VirtualBox と実機には装置が無く、起動媒体の像（HW-e）にも同じファイルが入るからである。**
- **起こし方の表に「ディスクの形」の欄を足した**（`virtio` / `none`）。**`none` の変種では `-device virtio-blk-pci` と対の `-drive` を落とす**（片方だけ落とすと QEMU が起動しない）。**`tools/qemu-variants.py` も同じ表を読む。**
- **渡された像は、長さだけでなく検査値でも照合する**（レビューの 1 点。2026-09-23）。**長さが同じで中身が古い `fs.img` は長さでは捕まらない**——**VDI の作り直し忘れや、ESP の片方だけの差し替えで起きる**（HW-e で VirtualBox を回し始めると起きやすい）。**建てたときの値は `build.rs` が出す**（`fsimage_info::IMAGE_CHECKSUM`。**式はカーネルの `image_checksum` と同じ重み付き和で、2 つに増やさない**）。**装置から読んだ回は照合しない**——**持ち越しの構成では `disk0.img` が前の起動で書いた中身を持っており、建てたときの値と違うのが正しい。**
- **書き戻しの入口を数え、装置の無い構成で待たないことを判定にした**（レビューの足す1点。2026-09-23）。**入口は 2 つである**（読んだ）——**起動の締め（`flush_fs_image_to_device`）と、Ring 3 の `close` からの書き戻し（`syscall` の `flush_root_image`）。** **どちらも装置が無ければ待たずに戻る**（前者は HW-d で足した枝、後者は `installed()` の早い戻り。**`claim()` も装置が無ければ `None` を返すので、二重に塞がっている**）。**判定は台本で通す**——**`zi` で書いて保存し、`cat` で読み直す。**
- **破壊 2 本**（`fs-ram-image-ignored`。**渡された像を見ない**。`flush-waits-without-device`。**装置が無いのに完了を待つ**）と、**機械の変種 1 つ**（`pc-no-virtio`）、**台本 1 つ**（`ram-disk-write-test`）。**`--full` は 368 から 372 項目。**

### 限界

- **RAM の像では書いた内容が残らない**（AHCI の段まで）。**永続性の検査（`--persist-test` の族）は virtio-blk の在る構成で走る。**

## HW-e の実装（2026-09-23）

### 入れたもの

- **`xtask/src/media.rs`**——**GPT と FAT32 を書く純粋ロジック。** **ファイルを触らない**（入口も出口もバイト列で、読み書きは呼ぶ側が行う）——**ホストのテストが、ファイルを 1 つも作らずに像を建てて読み返せる。** **CRC32 も自分で持つ**（GPT が要求する）。
- **`cargo xtask image [--without-fs-image]`**——**`target/media/zaytos.img` を建てる**（66MiB）。**`--without-fs-image` は破壊で、別の名前（`zaytos-no-fs-image.img`）へ書く**——**運用者が VirtualBox へ渡す像を上書きしない。**
- **機械の変種 `media-only`**——**起こし方の表に「ESP をどう渡すか」の欄が増えた**（`dir` / `media`）。**`media` の変種では、`fat:rw:` の drive を媒体の像と入れ替える**（位置は変えない。OVMF の起動の順に効く）。**virtio-blk も付けない**ので、**ファームウェアに見えるのは媒体 1 つだけである。**
- **基底に 2 項目**——**(1) 像を建て、読み返し、`sfdisk` と突き合わせる。(2) VirtualBox の道具の自己検査を回す。**
- **`tools/vbox-vm.py`**——**VM を作る・起こす・画面を読む・止める・消す・自己検査の 6 つ。** **名前が `zaytos-` で始まり小文字と数字と `-` だけであることを、`VBoxManage` を呼ぶ前に確かめる。** **`list vms` は使わない**（在るかどうかは `showvminfo <名前>` で見る。**接頭辞を確かめた名前だけを渡す**）。**逃げ道は置かない**——**`--force` も、名前の検査を飛ばす旗も無い。**
- **破壊 1 本**——**像から `fs.img` を外す。** **判定は、止まった行と「なぜそうなったか」の行の両方である**（`VariantExpect::StopsWithReason`。下の「設計から外れたもの」の 4）。

### 設計から外れたもの（4 つ）

1. **像を自分で読み返す形を足した。** **設計は「自分で書いた FAT を自分で読んで確かめる形にしない。読み手は OVMF（外の道具）である」と書いていた。** **判定は今も OVMF の起動である**（`media-only` の変種）——**足したのは基底の側である。** **理由は、起動の判定が `--full` にしか無いことである**——**書く側が壊れたことに、2 時間待たないと気づけない。** **読み返しは「正しさの証明」ではなく「退行の検出」である**（書く側と読む側が同じ勘違いを共有していれば、両方とも通る）。**共有していないことは、別に書いた読み手（Python。scratchpad の一時の道具）と `sfdisk` で見た。**
2. **VDI への直しは `qemu-img convert -O vdi` ではなく `VBoxManage convertfromraw` にした。** **VirtualBox 自身の道具である。** **像は先に置き場へ写してから直す**——**WSL の側の道（`\\wsl.localhost\...`）を VirtualBox へ渡さない**（UNC の道は遅く、失敗の切り分けが増える）。
3. **`--firmware efi` ではなく `efi64`**（明示）。**USB は明示的に切る**（`--usb-xhci off`・`--usb-ehci off`・`--usb-ohci off`）——**USB は HW-f である。** **キーボードとマウスは `ps2`。**
4. **破壊の判定に「理由の行」を足した**（`VariantExpect::StopsWithReason`）。**止まった行だけでは足りない**——**「装置も像も無い」で止まる形は、像から外れていなくても起きうる**（装置の無い構成で、ブートローダが読めなかった等）。**ブートローダが「ESP に `fs.img` が無い」と言う行まで見て、初めて「像から外れていた」ことの観測になる。** **なお、止まる所は HW-d の破壊とは違った**（実測）——**HW-d の破壊は像を渡された上で見ないので、写す所まで進んで `fs-image: there is no virtio-blk device and no RAM image to copy from` で止まる。** **こちらは像そのものが無いので、その前の装置の列挙の所（`virtio-blk: no device with an I/O BAR0 ...`）で止まる。** **提示の前は同じ行だと思っていた**——**回して違うと分かった。**

### FAT32 の大きさの決め方（なぜ 1 セクタ 1 塊なのか）

- **FAT32 は塊の数が 65,525 以上であることを要求する**（fatgen103）。**下回る像を FAT32 と名乗らせると、厳しいファームウェアは読まない。**
- **64MiB（131,072 セクタ）を 1 セクタ（512 バイト）1 塊で切ると、FAT は 1,009 セクタ、塊は 129,022 である**（この計算はホストのテストが数で固定している）。**下限の約 2 倍である。**
- **塊を 2 セクタ（1KiB）にすると 65,000 ほどで下限を割る**ので、**64MiB では 1 セクタ 1 塊しか選べない。** **これは Microsoft の表（fatgen103 の `DskSzToSecPerClus`）と同じ選択で、260MB 以下の FAT32 は 1 セクタ 1 塊である。**
- **FAT の大きさは自分自身に依る**（塊の数が FAT の大きさで決まり、FAT の大きさが塊の数で決まる）。**1,008 と 1,009 の間で振動するので、「足りるほう」の最小の不動点を採る。**
- **置くものは 9.4MB である**（実測。`kernel.elf` 7.2MB・`fs.img` 2MiB・`BOOTX64.EFI` 156KiB・`startup.nsh` 27B）。**使ったのは 18,657 塊で、余裕は 6.9 倍である。**

### 名前は全部 8.3 に収まる（長い名前を書かない）

- **置く 7 つの名前（`EFI`・`BOOT`・`BOOTX64.EFI`・`zaytos`・`kernel.elf`・`fs.img`・`startup.nsh`）は、全部 8.3 に収まる。** **小文字の 4 つは、予約バイト（12 番）の旗で見せる**（0x08 が本体、0x10 が拡張子）。**LFN の仕掛け（順序番号と短い名前のチェックサム）を持たない。**
- **旗を見ないファームウェアでも探す側は困らない**——**FAT の名前の照合は大文字小文字を区別しない**（UEFI 仕様の `EFI_FILE_PROTOCOL.Open`）。**旗が無視されると、Linux で見たときに大文字で出るだけである。**
- **収まらない名前を渡されたら拒む**（本体と拡張子のどちらかが大文字小文字の混ざった名前も拒む。**旗が部分ごとに 1 ビットしか無い**）。**黙って切り詰めると、ファームウェアが別の名前で探すことになる。**

### 実測（像の構造。2026-09-23）

- **像は 66MiB（135,168 セクタ）。** **ESP は LBA 2048..133119（64MiB）で、1MiB 境界から始まる。** **`sgdisk` で同じ大きさの参照を建てると、`firstlba` 34 と `lastlba` 135134 が一致した。**
- **`sfdisk --json` は `label gpt`・`start 2048`・`size 131072`・`type C12A7328-F81F-11D2-BA4B-00A0C93EC93B`・`lastlba 135134` を報せ、`sfdisk --verify` は "No errors detected." と言った。** **`sfdisk` は CRC を見るので、これで GPT の 3 つの CRC が正しいことも分かる。**
- **別に書いた読み手でも読めた**——**Python で書いた最小の FAT の読み手（scratchpad の一時の道具。カーネルも `xtask` も変えていない）で、4 つのファイルが道と長さのとおりに読め、sha256 が元のファイルと一致した**（`kernel.elf` だけは、並走していた `--full` が ESP を建て直した後だったので違った）。
- **外の道具の在りか**——**`mkfs.vfat`（dosfstools）と `mtools` はこの環境に無い。** **`sfdisk`（util-linux）・`sgdisk`（gdisk）・`partprobe` は在る。** **`sfdisk` を選んだのは util-linux がどの Linux にも入っているためで、パッケージの要求が増えない。**

### 実測（走行。2026-09-23）

**QEMU**（`media-only`。`-machine pc -m 256M`。virtio-blk も `fat:rw:` も無し）

- **既定の回はプロンプトまで 8.7 秒。** **`[ERROR]` は 0 行。** **`fs-image-load: copied` が出た**（RAM ディスクの道である）。
- **破壊（像から `fs.img` を外す）は 4.4 秒で止まった。** **ブートローダの `fs-image: no \zaytos\fs.img on the ESP` と、カーネルの `virtio-blk: no device with an I/O BAR0 ...` の両方が出て、プロンプトは出なかった。**
- **止まる所は HW-d の破壊とは違った**（**提示の前は同じだと思っていた**）——**HW-d の破壊は像を渡された上で見ないので、写す所まで進む。** **こちらは像そのものが無いので、その前の装置の列挙で止まる。** **判定の行を実測に合わせて直した。**

**VirtualBox**（`zaytos-hw-e`。`--firmware efi64`、メモリ 2048MiB、SATA/AHCI に VDI 1 つ、シリアルはファイル）

- **CPU 2 個では、VirtualBox の EFI 自身が起動の途中で落ちる**——**`!!!! X64 Exception Type - 0D(#GP - General Protection) CPU Apic ID - 00000000 !!!!`**（`RIP 0x7E50EFD8`。ファームウェアが自分で `CpuDxe.pdb` を指した）。**ZaytOS の行は 1 行も出ていない。**
- **こちらの像とは関係が無い**——**ディスクを 1 つも繋がずに同じ構成で起こしても、同じ所で同じ #GP が出た**（実測。切り分けのために外して起こし、戻した）。**ZaytOS が走る前の問題である**（**Hyper-V の上の NEM で走っている**。下記）。**「EFI 単体の欠陥」とまでは断定しない。**
- **CPU の数で比べた**（実測。2026-09-23 の調査。**ディスク無しの別の VM `zaytos-probe-cpu` で、完全停止から 2 巡**）——**1 個と 4 個は BDS まで進み（「No bootable option or device was found」）、2 個と 3 個は同じ RIP で同じ #GP になった。** **像を付けた VM では、4 個で ZaytOS が SMP で起動した**（AP 1 が起き、AP 2・3 は `MAX_CPUS=2` の方針で起こさない。プロンプトまで 11.3 秒）。
- **VirtualBox の障害報告 #799 との比較**——**あちらは 7.2.14・Windows 11 25H2（build 26200）・WHPX で、2 個で止まり 3 個以上で起きると報告している。** **こちらは 7.2.12 で、3 個でも落ちる**——**同じ族かは未確定である。** **#799 の「Hyper-V を使うホストで起きる既知の問題」という発言が VirtualBox の開発者のものかは確認していない**（レビューの訂正。2026-09-23）。**7.2.4 では起きないという話も利用者の発言である。**
- **CPU 1 個でも起動した。** **`zash: ready` が出て、シェルのプロンプトが画面に出た**（`target/hwe-vbox-screen.png` に画面を採った）。
- **PS/2 の打鍵がシェルに届いた**——**`VBoxManage controlvm ... keyboardputscancode 1e 9e 1c 9c`（`a` と Enter）を送ると、`zash: a: cannot run` が返った**（段の到達条件。**QEMU の `sendkey` と同じ経路で、i8042 の側から入れている**）。
- **Hyper-V の上で走っている**（運用者の問い）——**`HM: HMR3Init: Attempting fall back to NEM: VT-x is not available`。** **`WinHvPlatform.dll` の取り込みが並ぶ。** **`UseNEMInstead` は 0 だが、VT-x が使えないので NEM へ落ちている。**
- **受け渡しは 1GiB の下に載った**——**`handoff: BootInfo at 0x3ffef000, the handoff area is 0x3ffef000..0x40000000 (below 0x40000000 = true)`**（実測。**2GiB の機械の実ファームウェアで HW-a の性質が保たれた**）。**メモリマップは 5,424 バイト（48 バイト × 113 個）で、除外は 13,541 ページ（52MiB）。**
- **FADT は「8042 が在る」と言った**——**`i8042: the FADT says there is an 8042 controller; probing it`。** **探って答えがあり、設定バイトは 0b01100111 で、こちらの要求どおりだったので触っていない。** **持ち越しの行「FADT が「8042 は無い」と言うのに在る機械」に実測を書き足した**——**閉じてはいない**（**危険は「誤って落とす機械」に在り、VirtualBox はそれではなかった、が分かっただけである**）。
- **PIT は刻む**——**Local APIC タイマを PIT で較正した**（中央値 62,553,470 Hz、ばらつき 226,940 Hz）。**PM タイマの道は通っていない。**
- **virtio-blk は無い**——**RAM ディスクで起動し、`fs-image: the file system lives in RAM only ... nothing persists` が出た**（HW-d の道が実機の側でも通った）。
- **`[ERROR]` が 1 行出た**——**`apic: the I/O APIC MMIO does not look decoded (version=0x00170020 plausible=true, ID register reports 0 while the MADT says 1, matching=false)`。** **VirtualBox の I/O APIC は ID レジスタに 0 を返すが、MADT は 1 と言う。** **QEMU では一致する。** **カーネルは「下の一覧は信用できない」と言って進み、割り込みは届いた**（打鍵が届いている）。**棚卸しと持ち越しに行を立てた。**
- **`stack-water: before entering /bin/zash in Ring 3, the kernel stack used 71096 of 131072 byte(s); 59976 left`**（QEMU の既定と同じ値である）。

### 既定の起動で動いたもの（定型の 5 形）

- **カーネルとブートローダは 1 行も変えていない**（触ったのは `xtask`・`tools`・`docs` と変種の表だけである）。**起動ログ・スタックの高水位・遠征スタック・ページ表のフレームは、どれも動いていない。**
- **ホストのテストの名前は 679 本から 691 本（+12）**——**`media` の module のテストである**（`--update-reference` で録り直した）。
- **項目は base 35 → 37、`--full` は 372 → 376 の見込みである**（**base は実測で 37。** **`--full` の 376 は、足した 4 つ（基底 2・変種 1・破壊 1）からの導出で、まだ回していない**）。

### 限界

- **塊が 512 バイトなので、像を大きくするときは塊の大きさを決め直すこと**（持ち越しの行を立てた）。**64MiB を越えて伸ばすと、1 セクタ 1 塊では FAT が線形に伸びる**（1GiB なら FAT だけで 16MiB × 2）。
- **像の GUID と分割の GUID とボリューム番号は固定である**（像を決定的にするため）。**同じ機械に ZaytOS の媒体を 2 つ繋ぐと、GUID がぶつかる**（1 つずつ使う前提。持ち越しの行を立てた）。
- **`startup.nsh` を媒体にも置いている。** **これは OVMF が既定の起動パスを自動で探さないことへの回避策である**（`docs/troubleshooting.md`）。**VirtualBox と実機のファームウェアには要らない見込みで、置いてあっても害は無い**（推測。**VirtualBox で読まれたかは観測していない**）。
- **読み返しは退行の検出であって、正しさの証明ではない**（上の「設計から外れたもの」の 1）。
- **FAT を書き換える道具ではない**（1 度書いて読むだけ。空きの再利用も、断片化も、名前の変更も無い）。**像に置くものが増えたら、`MediaContents::paths` に足す。**
- **VirtualBox の走行は `--full` に入れない**（ホストの VirtualBox に依り、重い）。**段の締めで道具を使って確かめ、結果をここに記録する。**
- **VirtualBox の EFI は CPU 2 個と 3 個で落ちる**（1 個と 4 個は起動する。実測）。**道具（`tools/vbox-vm.py`）の既定は 1 個にした**——**4 個にすれば VirtualBox でも SMP の道を通せるが、どちらにするかは運用者の判断を待つ**（2026-09-23。答えが出るまでは 1 個）。**持ち越しの行を立てた。**
- **VirtualBox の I/O APIC の ID が MADT と食い違う。** **カーネルは `[ERROR]` を 1 行出して進む**——**「プロンプトが出て `[ERROR]` が無い」を判定にしている検査は、この機械では通らない**（`--full` は QEMU で走るので影響しない）。

## HW-e-2 の実装（2026-09-24）——I/O APIC の判定を写像・配送・ID に分ける

**レビューの承認（2026-09-23）に従った。** **ID の不一致は写像の不成立の証拠にならない**——**VirtualBox は I/O APIC の
ID レジスタを 0 のまま置き、MADT は CPU の数を ID にする**（実測。CPU 1 個で 1、4 個で 4）。**それでも IRQ1 は I/O APIC を
通って届いている**（VirtualBox のデバッガのベクタごとの計数）。

### 入れたもの

- **写像**——**版のレジスタが未デコードの見え方（全 0・全 1）でないこと**と、**IRQ1 の GSI を、デコードされた I/O APIC の
  項目が覆うこと。** **崩れたら `[ERROR]` で止める**（前は `[ERROR]` を出して進んでいた——**転送の項目を書いても届かないので、
  先へ進むと割り込みが来ない所で黙る**）。**判定の芯は純粋な関数で、ホストのテスト 5 本が守る**（VirtualBox と QEMU の実測の読み、
  全 0 と全 1、ID の桁、GSI の覆い方）。
- **配送**——**最初の打鍵が届いたベクタを 1 度だけ報せる行を、1 つの関数にまとめた**（`keyboard::report_first_delivery_once`）。
  **起動前のループと、プログラムを起こす入口（`userland::spawn`）の両方から呼ぶ。** **前は起動前のループでしか出なかったので、
  シェルが起きてから打つ機械（VirtualBox）では証拠が残らなかった。** **違うベクタなら今どおり止める。**
  **起こす入口はシェルが Enter のエコーを終えた後で、パスを引く前である**——**行の途中に入らず、無い名前（`a`）を打った回でも出る。**
  **最初は端末の `read` と入力の fd の読み手から出していた**が、**シェルがエコーしている行の途中へ割り込み、`--full` の打鍵の
  検査 4 本（`shell test` と、矢印・Esc を落とす形と、`keymap (us)`）が「打った行がエコーされた」で落ちた**（2026-09-24。実測）。
  **置き場を変えて 4 本とも通った。** **ロガーは起こす入口が既に持っているので、直接シリアルの許可リストは増えない。**
- **ID**——**一致は `[INFO]`、不一致は `[WARN]`。** **ID レジスタは書かない**（警告を消すために書き換えない）。
- **検査（`--full` に 3 項目）**——**打鍵を送る判定の形を足した**（`VariantExpect::PromptKeyAndLines`。プロンプトの後に monitor から
  `a` と Enter を打ち、シェルの答え `zash: a: cannot run` と、要る行と、出てはいけない行を見る）。
  - **既定（`pc-default`）**——配送の行（`first key arrived as vector 0x42`）と写像の行が出て、`[ERROR]`・`[WARN] apic:`・`vector 0x21`
    が出ない。
  - **構成 `ioapic-id-mismatch-test`（破壊ではない）**——**MADT の ID を 1 つずらして比べ、VirtualBox の形を QEMU で作る。**
    **`[WARN]` が出て、止まらず、`[ERROR]` が無く、打鍵が I/O APIC を通って届く。**
  - **破壊 `ioapic-reads-the-wrong-register`**——**版を ID の添字で読む**（QEMU の ID レジスタは 0 なので版が 0 に見える）。
    **写像の判定の行で止まる**（本物の写像の異常を、ID の不一致とは別に捕まえる）。

### 実測（2026-09-24）

- **QEMU**——既定はプロンプトまで 9.4 秒で、答えと配送の行が出た。構成も 9.4 秒で同じく通り、`[WARN]` が出た。破壊は 4.6 秒で
  `apic: the I/O APIC MMIO does not look decoded (version=0x00000000, …); halting` で止まった。**既存の `ioapic-decodes` と
  `interrupt-test keyboard` も通った。**
- **VirtualBox**（`zaytos-hw-e` を作業ツリーの像で作り直した。設定は前と同じ——CPU 1・2048MiB・efi64・PS/2）——**`[ERROR]` が消えた。**
  **写像の行と ID の `[WARN]` が出て、最初の打鍵で配送の行（ベクタ 0x42）が出て、シェルが答えた。** **VirtualBox の計数では、
  打鍵 4 バイト（`a` と Enter の押下と解放）でベクタ 0x42 が 0→4（+4）、8259 のベクタ 0x21 は計数そのものが無く、0x20 は 106 のまま
  だった。** **配送の行の置き場を直した後の最終の形の像（sha256 `e1cbd2fa…`）で測り直した値である。直す前の形でも同じく +4 と 0 だった。** **カーネルの行と、VM の外から数えた値が同じことを言っている。**

### 既定の起動で動いたもの（定型の 5 形）

- **起動ログ**——**判定の行が「写像の行」と「ID の行」の 2 行に分かれた**（`apic: I/O APIC MMIO decodes: …; 24 redirection
  entr(y/ies) from GSI 0` と `apic: the I/O APIC ID register reports 0, matching the MADT`）。**残りの差はカーネルが伸びて番地が
  動いた行だけである**（RIP・GDT の置き場・AP の入口。録り直した）。
- **ホストのテストの名前は 691 本から 696 本（+5）。** **項目は `--full` が 377 → 380**（基底は 37 のまま）。**380 は検査の組み立てを
  見直す契機である**——**USB の段に入る前に見直しを提案する。**

### 限界

- **配送の行は、打鍵が来るまで出ない。** **打たない走行では配送を主張しない**（写像の行と ID の行だけが出る）。
- **配送の行は、打鍵の後に最初にプログラムを起こした時に出る**（シェルの組み込みの命令だけでは出ない）。**シリアルだけに出る。**
- **I/O APIC が 1 台も無い機械は、覆いの確かめで止めない**（前からの振る舞いのまま。IRQ を移す側が扱う）。
- **打鍵を送る判定は PS/2 の経路だけに使う**——**QEMU に USB キーボードを付けると `sendkey` が PS/2 へ行かない**（持ち越しの行）。

## 起動時のスタックの最深経路（2026-09-23）

**レビューの指示で特定した。** **カーネルは切り替えの直後にスタックの未使用側を塗る**（`kernel::stack`）**ので、ある深さへ最初に書いた瞬間が 1 つに決まる。** **その番地へ QEMU の gdbstub で書き込みの見張りを置き、止まった瞬間の生きたスタックを `.debug_frame` の CFA で巻き戻した**（gdb は入っていないので、gdb のリモートの手順を話す一時の台本を `target/` の下に置いた。**カーネルは変えていない**）。**数字は `076b7fe` の像の実測である。**

- **`stack-water:` の行の 66,416 バイトを作ったのは次の経路である**（括弧は枠の大きさ）——`kernel_main`（39,416）→ `build_and_verify_high_half`（9,960）→ `core::array::from_fn::<u64, 512, _>`（4,136）→ `core::array::try_from_fn`（12,344）→ `try_from_fn_erased`（216）→ 閉包 2 つ（24・24）→ `paging::verify::read_pml4_entry`（72）→ `read_volatile::<u64>`（40）→ その前提の検査（40）→ `<*const ()>::is_aligned_to`（ここで書いた）。
- **`kernel_main` の枠だけで 39,416 バイトあり、高水位の 6 割を占める。** **残りの大半は、PML4 の 512 本を `u64` の配列（4KiB）として作る `core::array::from_fn` の鎖である。** **最適化の無い像では、配列が枠ごとに写されている見込み**（推測。`try_from_fn` の 12,344 は配列 3 つぶん（12,288）に近い）。
- **HW-a の前（`f8f07a2`）の 66,176 も、枠の和がこの経路で合う**（CFA で読んだ。見張りは置いていない）。
- **行の後に、もっと深く入る。** **`stack-water:` の行は `run_init` の前に出るが、プロンプトの時点の使用量は 70,568 バイトで、行より 4,152 バイト深い**（プロンプトで止めて、スタックの物理メモリを読んだ）。**経路は `kernel_main` → `run_init`（2,808）→ `userland::spawn`（8,424）→ `load_user_program`（6,552）→ 閉包 → `run_loaded_program`（7,768）→ `core::mem::take::<FileTable>`（1,576）→ `FileTable::default` → `FileTable::new`（3,784）→ `memcpy` で、`/bin/zash` を起こすところである。** **残りは 60,504 バイト。** **持ち越しの行を立てた**（`docs/deferred-decisions.md` の「カーネルスタックの高水位の行が、`init` より前で測っている」）。

### (c) の直し（2026-09-23。運用者の決定）

- **`stack-water:` の行を 2 つにした。** **1 つ目は `kernel_main` が出す「`init` の前まで」で、文面にそう書いた**（消していない）。**2 つ目は `userland::run_loaded_program` が、深さ 0 で Ring 3 へ落ちる直前に出す**（プログラムごと）。**Ring 3 へ落ちた後、そのプログラムのカーネル入場は遠征スタックに乗るので、2 つ目はそのプログラムが走っている間ずっとの値である。**
- **実測**（既定の起動）——**`init` の前は 66,816 バイト、`/bin/bss-test` の直前は 68,280、`/bin/zash` の直前は 70,968。** **プロンプトで止めて塗りを読んだ値も 70,968 で一致した**（`tools/stack-deepest.py`）。**残りは 60,104 バイト。**
- **`xtask` の余裕の判定は、`stack-water:` の全部の行の最小を見る**（`--shell-test`。**1 つ目だけを見ていた**）。
- **計器自身の費用を外した。** **最初の形は `format_args!` の一時値を `run_loaded_program` の枠へ乗せ、カーネルスタックと遠征スタックの高水位を 208 バイトずつ深くした**（実測。`tools/frame-sizes.py` で枠を読んだ）。**声を出す部分を `#[inline(never)]` の関数へ出して 0 に戻した**（W1-b-2 と同じ手当て）。
- **`stack-overflow-before-guard-test` の注釈の数も直した**（使用量 65,744 は古い。いまは 2 つの行が言う）。
- **受け渡しの安全の前提を固定した**（レビューの 1 点。HW-a の (a)）——**`memory_map::classify` の `LoaderData` に受け渡しの名を書き、ホストのテストを 2 本置いた**（`classify` の側と、アロケータの空きの表に一度も入らない側）。**一時的に `LoaderData` を `Free` へ動かして、2 本とも落ちることを確かめてから戻した**（md5 で一致を確認）。

## 設計の回答（2026-09-22）

- **設計を承認する。** **(d) の 3 つ目がレビューの推した形から外れたことは、HW-a に理由と一緒に書いた。**
- **HW-c は PM タイマで較正する。** **両方無ければ理由を出して止まる。**
- **FAT32 は `xtask` の中で書く。** **読み手は OVMF で、FAT32 の境界（クラスタ数 65,525 以上）から大きさを導く。**
- **小段ごとに実装を提示して止まる。HW-a から。**

## Alternatives Considered

- **初期ページ表の恒等を 4GiB へ広げる**——**採らない。** **受け渡しの置き場がファームウェアの配り方に依ったままになる**（4GiB の上へ置く機械では同じことが起きる）。**切り替え前の配りの問題も残る。**
- **VirtualBox で virtio-scsi を使う**——**採らない。** **実機に無い。** **RAM ディスクで起動し、ディスクの装置は AHCI の段で扱う。**
- **VM の設定を既定の機械フォルダ（C:）に置く**——**採らない。** **VDI と設定が別の場所に分かれ、消す手順が 2 か所になる。**

## Consequences

- **VirtualBox で起動できれば、第2段階の全段を 2 台で確かめられる**（運用者の理由。2026-09-22）。
- **`docs/hardware-inventory.md` の冒頭は、この ADR を名前で指す**（決定は写さない）。
- **限界**——**RAM ディスクでは書いた内容が残らない**（AHCI の段まで）。**HW-e までは USB が無いので、VirtualBox では PS/2 の打鍵で確かめる**（USB は HW-f。**2026-09-22 に第2段階から移した**）。**`i8042=off` と `pit=off` の形は VirtualBox では作れない**（推測）——**QEMU だけで見る。**
