# 0015. フレームバッファとMMIOはキャッシュ無効（PCD）でマップする

## Status
Accepted

## Date
2026-07-20

## Context
M2-dで自前のページテーブルを構築するにあたり、各範囲のキャッシュ属性を決める必要があった。

フレームバッファやMMIO領域は、通常のシステムメモリと違い、書き込みがそのままデバイス側の状態変化を意味する。
これをキャッシュ有効（ライトバック）でマップすると、書き込みがキャッシュに留まって画面に反映されない、反映の順序が入れ替わる、といった形で「書いたはずのものが出ない」状態になる。
この種の不具合は、コードを何度読んでも原因が見えない部類に入る。

一方で、フレームバッファに対してはWrite-Combining（WC）という選択肢もある。
書き込みをバッファにまとめてからバースト転送するもので、描画性能はキャッシュ無効より大幅に良くなる。
ただしWCの設定にはMTRRまたはPATの操作が必要であり、書き込み順序の保証もキャッシュ無効とは異なる。

## Decision
`memory_map::classify()`がMMIO相当と判定した範囲と、`BootInfo`から明示的に与えるフレームバッファ範囲を、PCD（Page Cache Disable）ビットを立ててマップする。
それ以外の通常メモリはキャッシュ有効のままとする。

Write-Combiningは採用しない。
M3以降、描画性能が実際に問題になった時点で改めて検討する。

## Alternatives Considered
- **すべてキャッシュ有効でマップする**: 実装は最も単純だが、画面に書いたものが出ない・出る順序が狂うという、原因の見えにくい不具合を招く。却下。
- フレームバッファを最初からWrite-Combiningにする: 描画性能は向上するが、MTRR/PATの操作という別の低レイヤ機構をM2の段階で持ち込むことになる。現時点で描画性能の要件はなく、まだ観測していない問題のために機構を増やすことになる。却下（保留）。
- **キャッシュ属性を範囲ごとに手で列挙する**: 判定基準が`classify()`と二重管理になり、片方だけ直したときに食い違う。却下。空き判定・マップ対象判定と同じく`classify()`に一本化する。

## Consequences
- 書いた内容が確実に画面へ反映される。M2-dのCR3切り替え後の検証で、実際に描いたブロックが`cargo xtask screenshot`に写ることを確認した。
- フレームバッファへの書き込みが遅く、読み出しはさらに遅い。これはM3-cでスクロールを実装する際に効いてくるため、スクロールはフレームバッファ間のコピーではなく、通常メモリ上のバックバッファで行う（ADR-0013）。
- キャッシュされないこと自体は、コンパイラによる書き込みの削除や並べ替えを防がない。それは`write_volatile`の役割であり、ページ属性とは別に必要。
- WCが必要になった場合は、MTRR/PATの設定を伴う別のADRとして検討する。

## Addendum（2026-07-20、M3-cの設計時に計測を試みた記録）

Write-Combiningを前倒しすべきかを判断するため、rdtscでバックバッファからフレームバッファへの転送コストを計測した。**結果は無効だった**ので、同じ失敗を繰り返さないよう記録しておく。

計測値（1280x800 = 1,024,000ピクセル）:

```
framebuffer fill (PCD)      = 556 cyc/px
ram buffer fill (cacheable) = 528 cyc/px
full flush ram->fb          = 766 cyc/px
```

無効と判断した根拠は2行目である。**キャッシュ有効な通常RAMへの書き込みが528 cyc/px** 出ている。
実機なら数サイクルであるべき値であり、しかもキャッシュ無効なフレームバッファへの書き込みとほぼ同速（比1.05倍）だった。
キャッシュの有無で差が出ない時点で、測れているのはメモリ階層ではない。

原因は、`cargo xtask run`がQEMUに`-accel kvm`を渡しておらず、TCG（純粋エミュレーション）で動いていたこと。
測っていたのはQEMUの命令エミュレーション負荷であり、PCDの実コストは一切反映されていない。

したがって現時点では、WCを前倒しすべきかどうかの判断材料が無い。
数字が無いことを理由にどちらにも賭けず、転送コストが高くても安くても損をしない構成（バックバッファ + ダーティ矩形による部分転送、ADR-0017）を採ることにした。

**測り直す際の注意**:

- xtaskの既定はTCGのままにする。全マイルストーンをTCGで検証してきており、既定を変えると挙動差の切り分け軸が増える。`cargo xtask run --kvm`のようなopt-inにして、計測時だけ使う。
- WSL2自体がHyper-V上のVMであるため、その上のKVMは入れ子の仮想化になる。TCGよりは遥かに実機へ近いが、実機そのものではない。特にTSCはハイパーバイザによる補正・オフセットの影響を受けうるため、絶対値ではなく「キャッシュ有効な書き込みとキャッシュ無効な書き込みの比」を見て判断すること。比が1倍前後のままなら、その計測もまだ信用できない。
- 計測用のプローブは`.local-probes/m3c-flush-cost-probe.patch`（追跡対象外）に置いてある。`git apply`で復元できる。

## Addendum 2（2026-07-20、KVM上で測り直した結果と判断）

KVMを有効化して測り直した。
結論から言うと、この計測もWrite-Combiningの判断には使えない。
保留を継続する。

### 計測値（1280x800 = 1,024,000ピクセル、ホストは3.6GHz）

| 計測 | TCG | KVM |
|---|---|---|
| (1)フレームバッファ書き込み（PCD）1周目 | 564 cyc/px | 32 cyc/px |
| (1b)同2周目 | — | 31 cyc/px |
| (2)通常RAM書き込み（キャッシュ有効）1周目 | 525 cyc/px | 45 cyc/px |
| (2b)同2周目 | — | 28 cyc/px |
| (3)全面フラッシュ（`copy_nonoverlapping`） | 5,526,188 cycles | 915,138 cycles |
| (4) 1セル（8x16）転送 | 15,551 cycles | 910 cycles |
| (5) 1行（640x16）転送 | 56,434 cycles | 3,875 cycles |

### 分かったこと

PCD自体は効いている。
2周目の比較が決定的だった。
通常RAMは45 → 28 cyc/pxと1.6倍速くなった（コールド → ウォーム、キャッシュが効いている）が、フレームバッファは32 → 31 cyc/pxでほぼ変わらない（キャッシュされていない）。
TCGではこの差が全く出なかったので、KVMの方が実機に近いことは間違いない。

それでも判断材料にはならない。
理由は2つ。

1. 比が判定基準を満たさない。ADR-0015 Addendumで定めた基準は「キャッシュ有効／無効の比が1倍前後なら信用できない」。実測は1周目同士で0.71倍、ウォーム同士で1.14倍と、いずれも1倍前後に留まる。真にuncachedなMMIOなら1桁以上開くはずで、開いていない。
2. 全面フラッシュが速すぎる。915,138サイクルで4,096,000バイト、つまり4.5バイト/サイクル。uncachedな書き込みは結合されないため、実機でこの速度は出ない。

数字が「速すぎる」方向にずれている理由として最も疑わしいのは、QEMUのディスプレイ更新のためのダーティページ追跡である。
KVMはフレームバッファのページを書き込み保護し、書き込みのたびにVM exitを起こしてQEMUに通知する。
この往復のコストが、メモリタイプ本来のコストを覆い隠している可能性が高い。
ただしこれは仮説であり、裏を取っていない。
確かなのは「測れているのは実機のメモリタイプの挙動ではない」という点だけである。

なお、1ピクセルずつのループ（(1)(2)）は最適化なしビルドのループoverhead（推定25 cyc/px前後）が支配的で、メモリコストの差が埋もれている。
`copy_nonoverlapping`を使う(3)の方が信号としては素直だが、上記のとおりその値自体が信用できない。

### 参考: この数字を額面どおり受け取った場合の試算

判断には使わないが、比較のために書いておく。

- 全面フラッシュ915,138サイクル / 3.6GHz = **約0.25ミリ秒**（1280x800）
- FHD（1920x1080）はピクセル数が2.025倍なので **約0.52ミリ秒**
- 60fpsの1フレームは16.7ミリ秒。FHD全面更新でも **3.1%** に収まる

この試算だけを見れば「WCは不要」に見える。
しかしこの数字は上記のとおり実機の挙動ではなく、しかも誤差の方向が分かっている（仮想化によりuncachedのコストを過小評価している）。
実機では1桁以上遅くなりうるため、「WCは不要」とは結論できない。

### 判断

Write-Combining / PATの導入は引き続き保留する。
前倒しする根拠も、不要と切り捨てる根拠も、どちらも得られていない。

判断できる材料が揃うのは次のいずれかの時点。

- 実機（ベアメタル）で動かして測れるようになったとき
- 描画性能が実際に問題として観測されたとき（GUI的な毎フレーム更新など）

現在の構成（バックバッファ + ダーティ矩形の部分転送、ADR-0017）は、転送コストが高くても安くても損をしないよう選んである。
WCを導入することになっても、この構成は変わらず、転送そのものが速くなるだけである。

### 計測環境についての注意

`cargo xtask run --kvm`は計測専用。
KVMでは`-d int`の記録が一切残らないため、`v=0e` / `v=08`による例外チェックが常に0を返す （`docs/troubleshooting.md`参照）。
デバッグと動作確認は既定のTCGで行うこと。
