# 0044. ユーザーのヒープは`brk`で伸ばす——`mmap`は採らない

## Status

Accepted

## Date

2026-08-23

## Context

**ユーザー空間にヒープが無い。`brk`も`mmap`も1つも無い**（実測。`docs/foundation-inventory.md`）。**`malloc`が書けないので、動的な大きさを扱うプログラムが1本も作れない。**

**基盤の棚卸しは「`brk`と`mmap`のどちらが安いかは測っていない。H段の入口で測ってから決める前提である」と書いた。** **測った。以下はその結果である。**

### 実測——置く場所は在る

| 何 | 番地 | 出所 |
|---|---|---|
| プログラムの像 | `0x400000`から | `kernel/userland/user.ld` |
| 一番大きい像（`zi`）の末尾 | `0x40a289`（ページ境界で`0x40b000`） | `readelf -l` |
| スタック | `0x7ff000..0x800000`（1ページ） | 起動ログ |

**したがって空いているのは`0x40b000..0x7ff000`で、1012ページ（約4MiB）である**（実測）。

### 実測——写像の道具は、システムコールの側から届く

- **`frame_allocator::take()`が`&'static mut FrameAllocator`を返す**（`ADR-0030`）。**遠征の中から取れる**
- **遠征の中では CR3 がそのプロセスのものである**（`run_loaded_program`が`switch_to(process.space.pml4())`してから入る）。**したがって`ActivePageTable::current()`が指すのはユーザーの表である**
- **`ActivePageTable::map_4kib`が在る**（`kernel/src/paging/active.rs`）。**新しい経路を作らずに写せる**
- **`AddressSpace`は`pml4`と`user_pml4_index`の2つしか持たない**ので、**システムコールの側で組み直せる**

**つまり「写す手立てが無い」という障害は無い。**

### 実測——状態を置く場所

**同時に生きているプロセスは`MAX_EXCURSION_DEPTH = 2`本までである**（実測）。**深さごとの配列で足りる**（`SPAWN_IMAGES`と同じ形）。

### 測った結果——`brk`のほうが面が小さい

| | `brk` | `mmap` |
|---|---|---|
| 引数 | 1つ（新しい上端） | 6つ（`addr` `len` `prot` `flags` `fd` `offset`） |
| 使わない引数 | 無い | **4つ**（`prot` `flags` `fd` `offset`）。**どう扱うかを決める必要がある** |
| 置き場所の判断 | **要らない**（1つの数が伸びるだけ） | **要る**（どこへ置くか、重ならないか） |
| 解放 | **同じ呼びで下げる** | **`munmap`が別に要る** |
| カーネルの状態 | 数が1つ | 区画の一覧 |

**外から来る`malloc`はどちらを前提にするか。** **musl は`mmap`を使う。** **`dlmalloc`と多くの教科書的な実装は`sbrk`を使う。** **最初のCの的は自前の小さなlibcなので、`brk`で足りる**（`docs/foundation-inventory.md`のCの道筋）。

## Decision

### 1. `brk`を実装する。`mmap`は採らない

**番号はLinuxと同じ`12`。** **`brk(0)`は現在の上端を返す**（Linuxと同じ問い合わせの形）。

### 2. ヒープは像の末尾の次のページから始まる

**プロセスごとに、読み込んだ像の末尾（ページ境界へ切り上げ）を初期値にする。**
**固定の番地にしない**——**像の大きさはプログラムごとに違う**（実測で`hello`が`0x401012`、`zi`が`0x40a289`）。

### 3. 伸ばすことも縮めることもできる

**上げれば写す。下げれば外して返す。**

**縮めない形は採らない。** **返せないと、`zi`が大きなファイルを開いて閉じるたびにフレームが減り続ける。** **そして`ADR-0011`の枠は256である**（実測）。

**縮む側が在ることで、判定が1つ置ける**——**伸ばして縮めれば、空きフレームの数が元へ戻る。** **既存の会計の判定（`leaked=0`）と同じ形である。**

**この判定は到達条件である。** **判定が無ければ、縮む側を作った意味が消える**——**縮めたつもりで返っていない形は、`-ENOMEM`が出るまで誰にも見えない。** **「伸ばして縮めたら、空きフレームの数が元へ戻る」を、この段の到達条件に入れる。**

### 4. スタックの1ページ下を上限にする

**`0x7ff000`を越えて伸ばせない。** **越えたら`-ENOMEM`。**

**ガードページは置かない。** **置く代わりに、上限で止める**——**スタックの下端そのものが境界なので、越えなければ衝突しない。**
**「ガードは写像の不在で作る」と同じ考えである**（`docs/verification-coverage.md`）が、**こちらは写像しないのではなく、写像を断る。**

### 5. 状態は深さごとの配列で持つ

**`MAX_EXCURSION_DEPTH`本ぶん**（実測で2）。**`SPAWN_IMAGES`と同じ形で、同じ理由である**（入れ子で上書きされない）。

## Alternatives Considered

### (a) `mmap`を実装する

**却下する。今は。** **面が大きい**（決定の表）。**使わない引数を4つ受けることになり、「受けるが無視する」と「受けたら断る」のどちらにするかを決める必要がある**——**どちらも、後から本物の`mmap`にするときに約束が変わる。**

**`brk`が`mmap`を塞がない。** **Linuxは両方を持つ。** **外から来る`malloc`が`mmap`を要求したら、そのとき足す**——**`brk`を消す必要は無い。**

### (b) ヒープを固定の番地から始める（たとえば`0x500000`）

**却下する。** **像の末尾との間に穴ができる。** **穴そのものは害が無いが、「なぜそこからなのか」を説明する定数が1つ増える**——**像の末尾から始めれば、説明が要らない。**

### (c) 縮めない（伸ばすだけ）

**却下する。** 理由は決定3にある。**返せないとフレームが減り続ける。**

### (d) カーネルのヒープ（`ADR-0012`）をユーザーへ貸す

**却下する。** **カーネルのヒープは1MiB固定で、拡張機構を持たない**（`docs/deferred-decisions.md`に行がある）。**ユーザーの要求で減るようにすると、カーネルの割り当てがユーザーの都合で失敗する。** **面を分けたままにする。**

## Consequences

**得るもの。**

- **`malloc`が書ける。** **`zi`のバッファを固定配列から動かせる**（64行×128バイトの上限が外れる）
- **伸ばして縮めれば元へ戻るので、判定が置ける**

**失うもの・引き受ける制約。**

- **`mmap`が無いので、ファイルの写像も共有メモリも無い。** **GUIの段で共有メモリが要るなら、そのとき決める**
- **上限が`0x7ff000`である。** **1012ページ（約4MiB）まで**（実測）。**越えたら`-ENOMEM`**
- **ヒープとスタックの間にガードページが無い。** **上限で止めるので衝突はしないが、「上限に当たった」と「本当に空きが無い」が同じ`-ENOMEM`になる**

**将来のトレードオフ。**

- **外から来る`malloc`が`mmap`を要求したら足す**（却下案(a)）
- **スタックを1ページより増やすなら、上限も動く**（ADR-0041の決定4に測る形が在る）

## 決めないこと

- **`munmap` / `mprotect` / 共有メモリ / ファイルの写像**
- **`realloc`の効率**（伸ばすときに写すかどうか）
- **スレッド**（ヒープの排他が要るのは、同じ空間に2本の実行文脈が居るときである。いまは1本）
- **ヒープの中の割り当て器そのもの**（**それはユーザー空間の話である**——`brk`が答えるのは「どこまで使ってよいか」だけである）
