# 0025. 最初のファイルシステムはext2とする（形式選定のみ）

## Status
Accepted

## Date
2026-07-27

## Context

`roadmap.md`と`deferred-decisions.md`は「最初のFSはFAT / ext2 / 独自簡易のいずれかを着手時に決める」として選定を保留してきた。
保留した理由は、選定の入力（ストレージ、VFS、ユーザーランドの形）が揃っていないと考えたためである。

長期方針を実コードと照合した結果、**形式選定に必要な入力は既に揃っている**と判断した。
判断材料はいずれも現時点で分かっており、S1からS9（SMPとユーザープログラム）の作業で変わらない。
一方で、保留を続けると、docsが「未決」と言い続ける状態がS10（ファイルシステムの実装）まで残る。

なお本ADRが決めるのは形式選定だけである。
ext2の中のパラメータ（block size、revision、inode size、未対応feature flagの扱い）は実装時に効く判断であり、今決める根拠がない。

## Decision

最初の本格ファイルシステムはext2とする。

理由:

- `mke2fs` / `debugfs` / `e2fsck`という独立実装を検証器として使える。ZaytOS自身が書いたテストだけで正しさを主張しなくて済む。これは本プロジェクトの検証方針（実装と同じ式だけで検算しない）に直接効く
- Linuxとディスクイメージを交換できる。ホスト側でイメージを作り、ZaytOSで読み、ホストで検証する往復が成立する
- inode・ディレクトリ・権限というUNIX的な構造を持ち、後のユーザーランドに向く
- ext3 / ext4より単純である（ジャーナルも複雑なfeature flagも無い）
- 仕様が公開されており、Linuxカーネルや`e2fsprogs`のGPLコードを写さずRustで独自実装できる。本リポジトリはMITで公開する

決めないこと（S10の着手時に決める。いずれも`deferred-decisions.md`の「規模・要件が変わったら見直すもの」に行がある）:

- block size（4KiBが第一候補）、revision、inode size（「ext2のパラメータ」の行）
- 未対応feature flagの扱い（同上。fail-fastで拒否する方針そのものは`roadmap.md`のS10に書く）
- 薄いVFSトレイト境界を先に引くか（「薄いVFSトレイト境界を先に引くか」の行）
- ext2イメージの持ち方（「ext2イメージの持ち方と取り出し」の行。カーネルへ埋め込むか、bootloaderが別モジュールとして読むか）

実装の段階は`roadmap.md`の段階列に置く。S10（RAM上のext2読み取りと最小VFS）、S12（ext2書き込み）、S13（永続ブロックストレージ）が該当する。

ext2対応で得るのはディスク形式の互換性だけである。
Linux syscall ABIやLinuxバイナリの互換とは分けて扱う（ZaytOSのユーザーABIはADR-0020の`int 0x80`規約の上に独自に育てる）。

## Alternatives Considered

- **FAT**: 実装が最も簡単で、UEFIのESPが既にFATなのでbootloader側と共有できる可能性があった。却下の理由は、パーミッション・inode・ハードリンクといったUNIX的な構造を持たず、ユーザーランドを育てる段でFSを乗り換える羽目になること。乗り換えはVFS境界・パーサ・イメージ生成・テスト資産の作り直しを意味する。学習目的としても、FATでは「ファイルシステムがどう権限とメタデータを表現するか」という主要な題材が扱えない
- **独自の簡易ファイルシステム**: 最も自由で実装量も小さい。却下の理由は、正解となる外部実装が存在しないこと。壊れた状態を作ったときに「実装が間違っているのか仕様の理解が間違っているのか」を切り分ける手段が無く、本プロジェクトが依存している「独立検証器で確かめる」形が使えない
- **ext4**: Linuxとの互換性は最も高い。却下の理由はextentツリー・ジャーナル・多数のfeature flagで規模が跳ね上がること。「細く長く」に反する
- **選定をS10着手時まで保留する（現状維持）**: 却下。入力が揃っている決定を待つ理由が無く、待つ間はdocs 3箇所が「未決」と言い続ける。保留の目的は情報が足りない判断を早まって固めないことであり、本件は当てはまらない

## Consequences

- `roadmap.md`のS10からS12がext2前提で書ける。イメージ生成は`mke2fs`、検証は`e2fsck`とLinuxでのマウントになる
- ホスト側に`e2fsprogs`が要る。QEMU + OVMFと同じく、ディストリのパッケージから導入する（EDK2で懲りた「ソースからビルドする依存」は増やさない）。**`e2fsprogs`が無い環境で、それに依存する検査を静かにスキップしないこと。** 未実施であることを出力するか、明示的に失敗させる。外部ツールの不在で検査が黙って消えるのは、本プロジェクトが3度捕まえてきた「検査があるように見えて何も検査していない」と同じ結果になる（`verification-coverage.md`）
- ext2にはジャーナルが無い。電源断時に常に無傷であることは初期目標にしない。書き込み順序・flush・clean/dirty状態・`e2fsck`による修復を前提として設計する（S12）
- GPLコードを写さないことが制約として残る。仕様と外部ツールの観測から実装するため、細部（ディレクトリエントリの詰め方など）は実物を`debugfs`で観測して確かめる作業が発生する
- 形式を後から変えるとVFS境界・パーサ・イメージ生成・テスト資産が作り直しになる。この不可逆性が、本ADRを書く理由そのものである（`roadmap.md`のADR方針のうち「後から変更すると大規模な作り直しになる」に該当する）
