# 0027. TLBシュートダウンはackを待たず、BKL取得時の世代フラッシュで閉じる

## Status
Accepted

## Date
2026-08-03

## Context

S5でIPIとTLBシュートダウンを入れた。
**BKL実装の古典的な罠がここで実在する。**

現象——コアAがBKLを保持し、コアBがカーネルへ入ってBKLを待つ。
**待機はIF=0のスピンである**（`bkl::acquire` は待つ前に`cli`する）。
そこでAがシュートダウンのIPIをBへ送り、ackを待つ。
**BはIF=0なのでIPIを処理できず、AはBKLを離さない。デッドロックする。**

**この罠はS4が意図的に先送りした論点である**（`docs/deferred-decisions.md`）。
S5がIPIを入れるまでは、送る相手がいないので発火しなかった。

**現在の本番にシュートダウンすべき対象が存在しないことは、この決定を変えない。**
発火条件の有無は`docs/verification-coverage.md`が、段の位置づけは`docs/roadmap.md`が正であり、
**本ADRでは再掲しない。**

## Decision

### 1. ackを待たない

送信側は、対象コアが処理したことを確かめない。
**ICRが受け付けたところまでしか見ない。**

**前例がある。** AP起こし（INIT-SIPI）が同じ形で成立している。
あちらもICRのdelivery statusだけを見ており、**相手が処理したことは確かめていない。**

### 2. 代わりに、取得する側が自分でフラッシュする（世代方式）

写像を変えたコアが**BKLを保持したまま**世代を上げる。
各コアは`bkl::acquire`で自分の見た世代と比べ、古ければCR3の載せ替えでTLBを落とす。

**コアの状態は3つで尽きる。**

- **タスク実行中でIF=1** — IPIが届く
- **BKL待ちでIF=0** — 取得するまで写像を使わない。**取得時のフラッシュで閉じる**
- **BKL保持中** — 変更した本人

**この3つが尽きている根拠は篩にある**（`verification-coverage.md`）。
**篩が変われば列挙も変わる。**

### 3. 世代方式が正しさの土台であり、IPIは早めるための手段である

カーネル入口はティックごとにBKLを取るので、走っている全コアは100Hzで必ず`acquire`を通る。
**したがって世代方式だけで「遅くとも1ティックで整合する」が保証される。**

**帰結——IPIが1つ落ちても正しさは保たれる。** 遅くなるだけである。

## Alternatives Considered

- **ackを待つ。** 不採用。**待った瞬間に上の罠が実在する。**
  送信側はBKLを保持したままackを待ち、対象コアはBKL待ちでIF=0でスピンしている。
  **健全性は§3の分担で別に確保できるので、罠を買う理由が無い。**

- **スピン中はIF=1にし、取得後に`cli`する（案1）。** 不採用。**予備として残す。**
  **単独では成立しない**——IPI以外も入る。タイマが入ると`irq_entry`がBKLを取りに行き、
  **BKL待ちの最中に同じコアがもう一度BKLを待つ。**
  再帰検出は「保持者が自分か」しか見ないので、**保持者が他コアなら掛からない。**
  入れ子のスピンになり、`irq_entry`のフレームが積み上がる。
  採るには**待機中にIPIだけを通す手段**（TPRなど）と、
  **再帰検出を「自分が既に待機中か」まで広げること**が要り、
  **ADR-0023の不変条件（保持区間=IF=0）の書き換えを伴う。**
  **前提条件——TPRはS4でもS5でも一度も触っていないので、採るなら先に読み書きの確認が要る。**

- **待機中のコアを静止状態として扱い、免除する（案5の素の形）。** 不採用。
  **取得後に成り立たない**——待機中は写像を使っていないが、**TLBには古い翻訳が残る。**
  取得した瞬間から使い始める。**世代フラッシュを足して直したものが採用案である。**

- **TLBシュートダウンをBKL保持外で行う。** 不採用。
  写像の変更がBKLで直列化されなくなり、**「変更は保持者しか行えない」という前提が消える。**
  その前提は世代方式の排他の根拠でもある（下記）。

## Consequences

### 得るもの

デッドロックが**構造から消える。** 待機中のコアに何も要求しないためである。
追加は`acquire`の1箇所に閉じており、**BKLの不変条件を1文字も変えていない。**

### 副次的な利点——IPIの畳み込みを扱わなくてよい

**同じベクタのIPIはLocal APICのIRRの1ビットなので、処理より速く送ると畳まれる**（S5-aで実測して分かった。送った数と受け取った数を一致させるために、1本ずつ受け取りを確かめてから次を送る形にした）。

**この設計では畳み込みが無害である。** フラッシュするかどうかを決めるのは**世代の比較**であって**受信回数ではない**。**IPIが何本畳まれても、取得時に見るのは「自分の見た世代」と「現在の世代」の差だけである。**

**ackを数える設計だったら、畳み込みを扱う必要があった**——「送った数だけackが返る」が成り立たないので、数え方か送り方に手当てが要る。**§1でackを待たないと決めたことの副次的な利点である。**

### 失うもの

**シュートダウンがいつ効いたかを送信側が知れない。**
知る必要が出たら、§3の分担では足りなくなる。

### 条件つきの安全（失効条件つきの決定）

**この節が本ADRの本体である。**

- **ack無しが健全なのは「解放も再利用もしない」間だけである。**
  写像を外すだけなら、古い翻訳が残っていても指す先は同じフレームで、差は観測されない。
  **外したフレームをアロケータへ返して再利用すると、その窓で古い翻訳が生きたページを
  別用途に使われる。**
  **失効条件——解放・再利用を伴う操作を導入したら、この設計は失効する。**

- **CR3の載せ替えはグローバルページを落とさない。**
  本カーネルはGビットを立てないので載せ替えで足りるが、**それは仮定ではなく起動時に検査している**
  （`CR4`とPGEを読み出し、Gビットが1つでも立っていたら停止する）。
  **失効条件——CR4.PGEを使い始めるか、Gビットを立て始めたとき。**

- **順序と排他は別の命題である。**
  **順序**は BKL 自身が与える（解放の`Release`と取得の`Acquire`の対）。
  **排他**は「世代を上げられるのは保持者だけ」という性質から来る。
  **`acquire`の順序を触るときは前者を、BKL保持外で写像を変え始めるときは後者を壊していないか見ること。**

- **例外・ダブルフォルト・パニックの経路はBKLを取らない**（ADR-0023）。
  **これらは戻らない経路である**ので、古い翻訳を持って走り続けることが無い。
  **失効条件——これらから戻る経路を作ったとき。**

### 他の記録との関係

**本ADRは決定と理由だけを持つ。**
検査・破壊feature・観測された事例は`docs/verification-coverage.md`が、
段階と到達条件は`docs/roadmap.md`が、
BKLの取得と解放の定義はADR-0023とそのAddendumが、
APのスケジューラ参加はADR-0026が正である。

## Addendum（S7着手時点）: 解放・再利用を、隔離で閉じる

### 失効条件が発火した

本文の「条件つきの安全」の1つ目——**解放・再利用を伴う操作を導入したら、この設計は失効する**——が、
S7（プロセス別アドレス空間）で発火した。**S7はアドレス空間の破棄を含み、破棄はフレームを返す。**

**書いておいた失効条件が、実際に発火した2件目である**（1件目はS4-c-2、`docs/verification-coverage.md`）。

### 決定は生き延びる。適用範囲を広げる

**ackは入れない。世代方式が土台であることも変えない。** 広げるのは**世代の使い道**である。

これまで世代は**「いつフラッシュするか」**を決めていた。ここから先は**「いつ再利用してよいか」**も決める。

**不変条件——フレームは、全コアの `SEEN_GENERATION` が解放時の世代を追い越すまで配られない。**

**これが本Addendumの本体である。** 追い越していれば、そのフレームの古い翻訳を持っているコアは無い。
**誰も持っていないことが、ackではなく世代の比較から出る。**

### なぜ成立するか

写像を外したコアは、BKLを保持したまま世代を上げる（本文§2）。
**カーネル入口はティックごとにBKLを取るので、走っている全コアは100Hzで必ず `acquire` を通る**（本文§3）。
`acquire` は自分の見た世代を現在の世代へ進めるので、**隔離は遅くとも1ティックで解ける。**

**新しいプロトコルは要らない。** 送るものも待つものも増えない。
**増えるのは「全コアの `SEEN_GENERATION` を読む手段」だけである**（現在は自コアぶんしか読めない）。

### 対象は「参加しているコア」である

**起きていないコアの `SEEN_GENERATION` は0のままである。** 「全コア」を素直に `MAX_CPUS` と読むと、
**`-smp 1` では隔離が永久に解けない。** 対象は**起こしたコア**である
（`smp::started_ap_count` と bootstrap processor）。

**AP起こしの最中に対象が増える窓がある。** 新しく起きたコアはCR3を新たに載せるので
古い翻訳を持たない、という論証が使えるはずだが、**確かめていない。** S7-bで確かめる。

### 条件つきの安全（この Addendum の失効条件）

- **あるコアが止まって二度と `acquire` しなくなると、隔離は解けない。**
  パニック方針はfail-fastで全体が止まるので、**「動き続けているのに解けない」状態にはならない。**
  BKLのタイムアウト（実測で約15秒）が先に報せる。
  **失効条件——1コアだけを止めて他を走らせ続ける経路を作ったとき。**

- **写像の変更がBKLの内側でしか起きないことに依存している。** 本文の「順序と排他は別の命題である」と
  同じ前提である。**失効条件——BKL保持外で写像を変え始めたとき。**

- **隔離の解除を判定する場所も、BKLの内側でなければならない。** 判定と再利用の間に
  他コアが割り込むと、追い越しの判定が古くなる。

### 実装の置き場所は決めない

**不変条件はここに書くが、それをどこに実装するかは本ADRの対象ではない。**
別の隔離リストで持つか、フリーリストのエントリに解放時の世代を刻むかは、
**フレームアロケータのデータ構造の見直しと同じ場所で決める**（`docs/roadmap.md` のS7）。
**どちらでも上の不変条件は同じである。**
