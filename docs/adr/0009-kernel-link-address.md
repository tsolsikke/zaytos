# 0009. kernel を低位固定アドレス（0x100000）にリンクする

## Status
Accepted

## Date
2026-07-19

## Context
ADR-0008 で bootloader/kernel を分離することを決定した。kernel
（`x86_64-unknown-none`, フリースタンディング ELF）を実際にリンクする際、
どの仮想アドレスに配置するかを決める必要がある。

`x86_64-unknown-none` の既定ターゲット設定を確認したところ（詳細は
`docs/architecture.md` §5）、以下がわかった。

- 既定の `code-model` は `kernel`。これは Linux の x86_64 カーネル同様、
  シンボルが高位負アドレス（`0xffffffff80000000`〜`0xffffffffffffffff`）に
  存在することを前提にした符号拡張ベースのアドレッシングを行う。
- 既定で `position-independent-executables: true`（PIE）。

したがって、この既定値をそのまま使う場合、kernel は higher-half
（例: `0xffffffff80000000` 付近）にリンクするのが「素直な」選択になる。

一方、higher-half を採用すると、以下の理由で M2-0c（ELF ローダー）・
M2-c（自前ページテーブル構築）の境界がにじむ:

- ExitBootServices 直後の時点では、UEFI が構築した既存のページテーブルが
  まだ有効であり、UEFI 仕様上 Boot Services 実行中は恒等マッピング
  （仮想アドレス = 物理アドレス）が保証されている。**M2-0c の最初の
  ステップとして、この前提を実際のメモリマップおよび CR3 が指す
  ページテーブルの手動ウォークにより検証済み**（結果は Decision 参照）。
  kernel を higher-half にリンクすると、ELF ローダーは kernel へ
  ジャンプする**前に**、その高位仮想アドレスを有効な物理フレームへ
  マップする最低限のページテーブルを自分で用意しなければならない。
  これは実質的に M2-c（自前ページテーブル構築）の一部を M2-0c に
  前倒しすることになり、ロードマップで意図した「1 ステップずつ」の
  区切りを崩す。
- 低位固定アドレス（例: `0x100000` = 1MiB、multiboot 系カーネルで
  伝統的に使われる開始アドレス）にリンクする場合、ELF ローダーは
  UEFI が残した既存のマッピングの下で kernel へ直接ジャンプできる
  可能性が高く、ページテーブル構築を M2-c まで純粋に遅延できる。

## Decision
kernel を低位固定アドレス `0x100000`（1MiB）にリンクする。

- `relocation-model=static` を明示し、PIE を無効化する（`EXEC` 型の
  非 PIE バイナリとしてリンクする）。
- `code-model=small` を明示し、既定の `kernel`（高位負アドレス前提）を
  低位アドレスと整合する設定に上書きする。
- 上記は `.cargo/config.toml` の `[target.x86_64-unknown-none]` に
  `rustflags` として集約する。
- リンカスクリプト（`kernel/link.ld`）で `KERNEL_LOAD_ADDR = 0x100000`
  を明示し、`.text`/`.rodata`/`.data`/`.bss` をこの位置から配置する。

M2-0b の時点でこのリンクアドレスを採用したビルドを行い、`readelf`/
`objdump` で実際の配置を確認した:

- ELF 型: `EXEC`（非 PIE）。エントリポイント `0x100650`。
- 3 つの `PT_LOAD` セグメントすべてが `0x100000`〜`0x104000` の範囲に収まり、
  仮想アドレスと物理アドレスが一致（`VirtAddr == PhysAddr`）。
- 動的セクション・再配置エントリは存在しない（`readelf -d`/`-r` とも
  「なし」）。`.got` の内容もすべてリンク時に確定した絶対アドレスであり、
  実行時の再配置処理は不要と確認できた。

この結果は、M2-0c の ELF ローダーが「セグメントをそのままメモリへコピー
するだけ」で済み、再配置処理系を実装する必要がないことを裏付けている。

さらに M2-0c の最初のステップとして、bootloader に一時的な検証コードを
追加し（QEMU 実行後に削除・元の状態へ復元済み）、以下 2 点を実機
（QEMU + OVMF）で確認した。

- **`0x100000`〜`0x104000` の範囲は `EFI_MEMORY_TYPE` が
  `EfiConventionalMemory`（空き通常メモリ）である。** 実測では
  `phys_start=0x100000`, `page_count=1792` の単一エントリが
  `0x100000`〜`0x800000` を覆っており、この範囲はファームウェアが
  他用途に予約していない。
- **恒等マッピングは推測ではなく検証済みの事実である。** 現在の CR3 が
  指す 4 レベルページテーブルを手動でウォークし、仮想アドレス
  `0x100000` が物理アドレス `0x100000` に一致することを確認した
  （`va == pa`）。

これにより、Context で述べた「UEFI 由来の既存マッピングの下で kernel へ
直接ジャンプできる可能性が高い」という前提は、本ワークスペースの QEMU +
OVMF 環境において検証済みの事実となった。

## Alternatives Considered
- **higher-half（例: `0xffffffff80000000`）を採用し、`code-model=kernel`
  の既定値をそのまま使う**: ターゲットの既定設定と素直に整合し、
  Linux 等の一般的な x86_64 カーネルの慣習にも合う。ただし Context で
  述べた通り、M2-0c の ELF ローダーに最低限のページテーブル構築を
  前倒しで要求することになり、マイルストーンの境界が崩れる。将来
  higher-half へ移行する場合、この ADR を Superseded とし、その時点で
  改めて ELF ローダー・ページテーブル構築の役割分担を設計し直す。

  **この却下理由の性質について**: higher-half を却下した主たる理由は
  「マイルストーンの境界がにじむ」という開発プロセス上の都合であり、
  higher-half 自体にアーキテクチャ上の欠陥があるという判断ではない。
  higher-half はむしろ x86_64 カーネルの一般的な慣習であり、ターゲットの
  既定設定（`code-model=kernel`）とも素直に整合する。つまり本 ADR は
  「技術的にどちらが優れているか」ではなく「今のマイルストーン分割を
  崩さずに進めるにはどちらが都合が良いか」を基準にした判断である。
  この区別は、将来 higher-half への移行を再検討する際に、却下理由が
  技術的必然ではなかったことを踏まえて判断できるよう明記しておく。

## Consequences
- kernel は当面、物理アドレスと仮想アドレスが一致する低位領域
  （`0x100000` 付近）で動作する。higher-half が一般的に持つ利点
  （ユーザー空間とカーネル空間のアドレス空間分離のしやすさ等）は
  M2-c 以降、自前のページテーブルを構築した段階で改めて設計する。
  低位リンクそのものがこれを妨げるわけではない（ページテーブルで
  higher-half の仮想マッピングを別途構築すればよい）。
- `code-model=small` への上書きにより、将来 kernel が 2GiB を大きく
  超える規模になった場合は再検討が必要になる（学習用途のカーネルでは
  当面問題にならない想定）。
- M2-c でページング設計を行う際、この ADR の前提（kernel は低位固定
  アドレスにロードされ、実行開始時点では UEFI 由来のマッピングに
  依存している）を踏まえること。

### 物理アドレス確保の失敗リスク

低位固定アドレスへのリンクは、ELF ローダーが `0x100000` という**特定の
物理アドレス**にセグメントを配置しなければならないことを意味する。UEFI
でこれを行うには `AllocatePages` を `AllocateAddress` モードで呼ぶ必要が
あるが、この呼び出しはファームウェアが既にその領域を別の用途
（例: ACPI テーブル、SMM 予約領域、既存のブートサービスコード等）に
使用している場合に失敗しうる。

- **検証済み**: UEFI メモリマップをダンプし、`0x100000`〜`0x104000` の
  範囲が `EfiConventionalMemory` に属することを確認した（Decision 参照）。
- **M2-0c で実装する**: 実際の ELF ローダーでは
  `AllocatePages(AllocateType::Address(0x100000), ...)` の戻り値を必ず
  検査し、失敗した場合は握りつぶさずエラーとして報告する（エラー処理を
  省略しないという方針）。上記のメモリマップ確認は静的な一時点の
  スナップショットにすぎず、`AllocatePages` 自体の成否を保証するもの
  ではないため、実装でも必ずエラーハンドリングを行う。
- 確保に失敗した場合の対応（別の低位アドレスへの変更、または
  higher-half への方針転換）は、その時点で改めて判断する。後者を選ぶ
  場合は本 ADR を Superseded とする。
