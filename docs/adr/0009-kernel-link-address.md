# 0009. kernelを低位固定アドレス（0x100000）にリンクする

## Status
Accepted

## Date
2026-07-19

## Context
ADR-0008でbootloader/kernelを分離することを決定した。
kernel（`x86_64-unknown-none`, フリースタンディングELF）を実際にリンクする際、どの仮想アドレスに配置するかを決める必要がある。

`x86_64-unknown-none`の既定ターゲット設定を確認したところ（詳細は`docs/architecture.md` §5）、以下がわかった。

- 既定の`code-model`は`kernel`。これはLinuxのx86_64カーネル同様、シンボルが高位負アドレス（`0xffffffff80000000`〜`0xffffffffffffffff`）に存在することを前提にした符号拡張ベースのアドレッシングを行う。
- 既定で`position-independent-executables: true`（PIE）。

したがって、この既定値をそのまま使う場合、kernelはhigher-half（例: `0xffffffff80000000`付近）にリンクするのが「素直な」選択になる。

一方、higher-halfを採用すると、以下の理由でM2-0c（ELFローダー）・M2-c（自前ページテーブル構築）の境界がにじむ:

- ExitBootServices直後の時点では、UEFIが構築した既存のページテーブルがまだ有効であり、UEFI仕様上Boot Services実行中は恒等マッピング（仮想アドレス = 物理アドレス）が保証されている。M2-0cの最初のステップとして、この前提を実際のメモリマップおよびCR3が指すページテーブルの手動ウォークにより検証済み（結果はDecision参照）。kernelをhigher-halfにリンクすると、ELFローダーはkernelへジャンプする**前に**、その高位仮想アドレスを有効な物理フレームへマップする最低限のページテーブルを自分で用意しなければならない。これは実質的にM2-c（自前ページテーブル構築）の一部をM2-0cに前倒しすることになり、ロードマップで意図した「1ステップずつ」の区切りを崩す。
- 低位固定アドレス（例: `0x100000` = 1MiB、multiboot系カーネルで伝統的に使われる開始アドレス）にリンクする場合、ELFローダーはUEFIが残した既存のマッピングの下でkernelへ直接ジャンプできる（M2-0cで実装・実機検証済み。ページテーブル構築をM2-cまで純粋に遅延できている）。

## Decision
kernelを低位固定アドレス`0x100000`（1MiB）にリンクする。

- `relocation-model=static`を明示し、PIEを無効化する（`EXEC`型の非PIEバイナリとしてリンクする）。
- `code-model=small`を明示し、既定の`kernel`（高位負アドレス前提）を低位アドレスと整合する設定に上書きする。
- 上記は`.cargo/config.toml`の`[target.x86_64-unknown-none]`に`rustflags`として集約する。
- リンカスクリプト（`kernel/link.ld`）で`KERNEL_LOAD_ADDR = 0x100000`を明示し、`.text`/`.rodata`/`.data`/`.bss`をこの位置から配置する。

M2-0bの時点でこのリンクアドレスを採用したビルドを行い、`readelf`/`objdump`で実際の配置を確認した:

- ELF型: `EXEC`（非PIE）。エントリポイント`0x100650`。
- 3つの`PT_LOAD`セグメントすべてが`0x100000`〜`0x104000`の範囲に収まり、仮想アドレスと物理アドレスが一致（`VirtAddr == PhysAddr`）。
- 動的セクション・再配置エントリは存在しない（`readelf -d`/`-r`とも「なし」）。`.got`の内容もすべてリンク時に確定した絶対アドレスであり、実行時の再配置処理は不要と確認できた。

この結果は、M2-0cのELFローダーが「セグメントをそのままメモリへコピーするだけ」で済み、再配置処理系を実装する必要がないことを裏付けている。

さらにM2-0cの最初のステップとして、bootloaderに一時的な検証コードを追加し（QEMU実行後に削除・元の状態へ復元済み）、以下2点を実機（QEMU + OVMF）で確認した。

- `0x100000`〜`0x104000`の範囲は`EFI_MEMORY_TYPE`が`EfiConventionalMemory`（空き通常メモリ）である。 実測では`phys_start=0x100000`, `page_count=1792`の単一エントリが`0x100000`〜`0x800000`を覆っており、この範囲はファームウェアが他用途に予約していない。
- 恒等マッピングは推測ではなく検証済みの事実である。 現在のCR3が指す4レベルページテーブルを手動でウォークし、仮想アドレス`0x100000`が物理アドレス`0x100000`に一致することを確認した（`va == pa`）。

これにより、Contextで述べた「UEFI由来の既存マッピングの下でkernelへ直接ジャンプできる」という前提は、本ワークスペースのQEMU + OVMF環境において検証済みの事実となった（推測ではない）。

さらにM2-0cで実際のELFローダー（`bootloader/src/loader.rs`）を実装し、上記の一時的な診断コードではなく本実装で最終確認した。
`uefi::boot::allocate_pages(AllocateType::Address(0x100000), ...)`が実機（QEMU + OVMF）で実際に成功し、その後UEFI由来のページテーブルを一切変更しないままkernelの`_start`（`0x100000`台の仮想アドレス）へジャンプし、kernel側が正常に動作（BootInfo検証OK、.bssゼロ埋め確認OK）することを確認した。
ADR-0009 Consequencesで懸念していた「物理アドレス確保の失敗リスク」は、少なくとも本ワークスペースのQEMU + OVMF環境では顕在化しなかった。

## Alternatives Considered
- higher-half（例: `0xffffffff80000000`）を採用し、`code-model=kernel`の既定値をそのまま使う: ターゲットの既定設定と素直に整合し、Linux等の一般的なx86_64カーネルの慣習にも合う。ただしContextで述べた通り、M2-0cのELFローダーに最低限のページテーブル構築を前倒しで要求することになり、マイルストーンの境界が崩れる。将来higher-halfへ移行する場合、このADRをSupersededとし、その時点で改めてELFローダー・ページテーブル構築の役割分担を設計し直す。

  **この却下理由の性質について**: higher-halfを却下した主たる理由は「マイルストーンの境界がにじむ」という開発プロセス上の都合であり、higher-half自体にアーキテクチャ上の欠陥があるという判断ではない。
  higher-halfはむしろx86_64カーネルの一般的な慣習であり、ターゲットの既定設定（`code-model=kernel`）とも素直に整合する。
  つまり本ADRは「技術的にどちらが優れているか」ではなく「今のマイルストーン分割を崩さずに進めるにはどちらが都合が良いか」を基準にした判断である。
  この区別は、将来higher-halfへの移行を再検討する際に、却下理由が技術的必然ではなかったことを踏まえて判断できるよう明記しておく。

## Consequences
- kernelは当面、物理アドレスと仮想アドレスが一致する低位領域（`0x100000`付近）で動作する。higher-halfが一般的に持つ利点（ユーザー空間とカーネル空間のアドレス空間分離のしやすさ等）はM2-c以降、自前のページテーブルを構築した段階で改めて設計する。低位リンクそのものがこれを妨げるわけではない（ページテーブルでhigher-halfの仮想マッピングを別途構築すればよい）。
- `code-model=small`への上書きにより、将来kernelが2GiBを大きく超える規模になった場合は再検討が必要になる（学習用途のカーネルでは当面問題にならない想定）。
- M2-cでページング設計を行う際、このADRの前提（kernelは低位固定アドレスにロードされ、実行開始時点ではUEFI由来のマッピングに依存している）を踏まえること。

### 物理アドレス確保の失敗リスク

低位固定アドレスへのリンクは、ELFローダーが`0x100000`という**特定の物理アドレス**にセグメントを配置しなければならないことを意味する。
UEFIでこれを行うには`AllocatePages`を`AllocateAddress`モードで呼ぶ必要があるが、この呼び出しはファームウェアが既にその領域を別の用途（例: ACPIテーブル、SMM予約領域、既存のブートサービスコード等）に使用している場合に失敗しうる。

- **検証済み**: UEFIメモリマップをダンプし、`0x100000`〜`0x104000`の範囲が`EfiConventionalMemory`に属することを確認した（Decision参照）。
- **M2-0cで実装・検証済み**: 実際のELFローダー（`bootloader/src/loader.rs`）で`AllocatePages(AllocateType::Address(0x100000), ...)`の戻り値を検査し、失敗した場合は握りつぶさずエラーログ + panicで報告するようにした（エラー処理を省略しない方針による）。実機（QEMU + OVMF）ではこの呼び出しは実際に成功しており、失敗時のエラーハンドリングパス自体は意図的な障害注入では未検証（コードレビューで確認済み）。上記のメモリマップ確認は静的な一時点のスナップショットにすぎず、`AllocatePages`自体の成否を保証するものではない点は変わらないため、このエラーハンドリングは維持する。
- 確保に失敗した場合の対応（別の低位アドレスへの変更、またはhigher-halfへの方針転換）は、その時点で改めて判断する。後者を選ぶ場合は本ADRをSupersededとする。
