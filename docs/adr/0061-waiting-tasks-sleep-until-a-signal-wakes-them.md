# 0061. 待つタスクは合図で起こす。上限で止めるのは検査の側である

## Status
Accepted

## Date
2026-09-16

## Context

**W1で2本のRing 3が同時に走るようになった**（`ADR-0060`）。**しかし、どちらも待てない。**

**実測が3つある。**

- **`read(0)`は溜まっていなければ`-EAGAIN`を返し、シェルは`continue`で空回りする**（`kernel/userland/zash.rs`）。**1セッションで1,282,916回のシステムコールを出した**（`--shell-test`のログ）。**そのほぼ全部が空振りの`read`である**（推測。内訳の計測は無い）。**毎秒約25,000回は導出である**（項目の51.6秒にビルドと起動が入っている）。
- **`sti; hlt`は3箇所しか無い**（`kernel/src/interrupts.rs`のハートビートのループ、`kernel/src/smp.rs`のAPの定常ループ、`kernel/src/virtio.rs`のI/O待ち）。**1つ目は`init`より前に抜けるので、`init`が引き取った後のBSPは1度も眠らない。**
- **待てるシステムコールが1つも無い**（実測。`read`・`write`・`open`・`close`・`stat`・`getdents64`・`lseek`・`mkdir`・`rmdir`・`unlink`・`brk`・`ioctl`・`exit`・`spawn`と、私物の3つ）。**`spawn`は親を止めるが、それは遠征の入れ子であって、スケジューラの待ちではない。**

**穴も1つ見つけた。** **`pick_next`の落ち先は固定でタスク0である**（`default_task_for`）——**タスク0が実行不可でも選ばれる。** **待たせ始めると、ここに当たる。**

## Decision

**5つ決めた**（運用者の承認。2026-09-16）。

1. **待てるのは前景の持ち主だけである。** **W2-c-2で狭めた（2026-09-16）**——**それでは足りなかった。** **`run_loaded_program`はどのプログラムにも前景を取らせるので、起動シーケンスの`/bin/syscall-test`も持ち主である。** **あれは`read(0)`と`read(1)`が`-EAGAIN`を返すことを主張しており**（失敗コード51と52。「打鍵が無い」）、**打鍵が無いのだからそれが正しい答えである。** **無条件に待つ形にしたら、起動がその主張の地点で止まり、シェルまで届かなかった**（実測。`docs/troubleshooting.md`）。**いまの規則は「対話の口（コンソールの前景）が据えられている間の、前景の持ち主だけが待てる」である**——**`init`がシェルを起動する区間だけが、誰かが打つ場所である。** **持たない1本の`read(0)`は`-EBADF`のままにする**（いまと同じ）。**取り合いも待ち行列も作らない**——**政策が要り、その利用者が居ない。** **「待てないことと、回ることは別である」**——**`-EBADF`は即返るので、2本目は空回りせずに終われる。**
2. **BSP用のアイドルタスクを足す**（`TASK_COUNT`を1つ増やす）。**本体は`sti; hlt`のループで、落ち先をコアごとのアイドルにする。** **足さない形（落ち先のタスクがその場で`hlt`する）は採らない**——**割り込みハンドラの中で眠ることになる。**
3. **`TaskState::Waiting(Wait)`を`Blocked`と分ける。** **`Blocked`はいま2つの意味を持っている**（メインの帰り先／締切で止めたワーカー）。**混ぜると、締切で止めたワーカーをキー入力で起こす。**
4. **起こす合図は、まずキーボードだけにする。** **タイマは任意の段階（W2-d）へ回す。** **I/Oはvirtioが既にBKLを解いて眠る形を持っているので触らない。**
5. **手順は4つである。** **W2-a（アイドルタスクを足す。振る舞い不変）／W2-b（`Waiting`の欄と遷移だけ。振る舞い不変）／W2-c（`read(0)`が待つ。振る舞いが変わる）／W2-d（タイマ。任意）。**

### 上限の置き場——**本番の待ちは上限で止めない**

**「上限の無い待ちを書かない」は道具と検査の規律である**（`CLAUDE.md`。**`--full`を待つ側に上限が無くて残骸が4時間39分ぶら下がった件**）。**本番のキー待ちに持ち込まない**——**人が席を外しただけで落ちる。**

**破壊テスト「起こさない」を観測するには上限が要る。** **置き場は2つのどちらかである。**

- **検査の構成の側に上限を置く**（featureで囲った構成だけが止まる）
- **上限に当たっても止めず、計測へ出して待ち直す**（本番にも置ける形）

**W2-cで、どちらを採るかを実装の前に決めること。**

### 破壊テストの下ごしらえ（W2-cで要る）

**`bkl-hold-across-hlt-test`は流用できない**（実測。2026-09-16）。**あの破壊テストの項目が待つのは`bkl: recursive acquisition on cpu`と`halting`で、仕込む場所はハートビートのループである**（`interrupts.rs`）——**`init`より前に走るので、同じfeatureをアイドルの`hlt`へ足しても、先にあちらが発火して新しい場所は観測されない。** **アイドルの側には別のfeatureを立てること。**

## W2-c-1で置いたものと、測った基準線（2026-09-16）

**落ち先と計測だけの段階である。** **待つ者はまだ居ない**（決定5の手順をさらに2つに割った。運用者の承認）。

### 落ち先は`Waiting`だけを見る

**`pick_next`の落ち先を、「既定のタスクが`Waiting`なら自コアのアイドルへ」にした。**

**`Blocked`では落ちない。** **プリエンプティブデモは締切でワーカーを`Blocked`にし、メインへ戻ることで終わる**——**そこをアイドルへ変えると、デモから戻れず起動が進まない。** **`ADR-0061`の決定3（`Waiting`を`Blocked`と分ける）が効く2つ目の場所である**（1つ目は起こす側が合図で引けること）。

**W2-c-1ではこの分岐を誰も通らない。** **通るのはW2-c-2からである。**

### 計測を2つ設けた。**W2-c-1では0である**

**BSP用アイドルが`hlt`した回数と、切り替えがそれを選んだ回数。** **シェルが終わった後にシリアルへ1行出す**（画面へは出さない）。

**0を先に記録しておく**（運用者の指摘。2026-09-16）——**W2-c-2の主張が「1以上である」ではなく「0から1以上へ変わった」になる。** **前後で言えるほうが強い。**

| 何 | W2-c-1の実測 |
|---|---|
| アイドルが`hlt`した回数 | **0** |
| 切り替えがアイドルを選んだ回数 | **0** |
| 1セッションのシステムコール | **1,377,679回** |
| 前景がRing 3へ渡したバイト | **584バイト**（受けたスキャンコードは1,297個） |
| 回数とバイトの比 | **約2,359倍**（導出） |

**システムコールの回数はツリーによって動く**——**以前のツリーでは1,282,916回だった**（同じ台本で、2026-09-16の別の回）。**だから判定1は固定の閾値ではなく関係で見る**（運用者の承認）。**「届いたバイト数の4倍以内」の4は見込みのままである**——**W2-c-2で待ち直しの回数を測ってから固定する**（運用者の条件）。

### 起動ログはアドレスだけ動いた

**行は1行も増えていない**（562行のまま。伏せると食い違い0行で、道具は`exit 0`）。**計測の行はシェルが終わった後に出るので、既定の起動の取り込みには入らない**——**入るのは`--shell-test`のログである。**

**参照は2つとも録り直した**——**起動ログ（アドレスが動いた）と、ホストテスト名（表明を1本足したので639名）。**

### 退行を2つ出した。1つは直し、1つは覆いを失った（2026-09-16）

**`--full`が120分の上限で終了した**——**264項目走って7項目が落ちた**（実測。期待は306）。**原因は2つあり、どちらもこの段階のものである。**

**(A) 台本の入力を待ってしまった。直した。**

**`script::next_bytes`は3つの場面で0を返す**——**出し切った・休み（`SCRIPT_PAUSE`）・作動前。** **どれも「もう入力は無い」であって、`-EAGAIN`がその答えだった**（`docs/coding-standards.md`の「「今は無い」を固定した記録は、代替の返り値ではない」）。**台本の実行では誰も打たないので、待ちが終わらない。**

**実測が機序と合っていた**——**共通261項目の所要が1.60倍**（73.2分→117.4分）**で、伸びた順が`persist (env)` 28.9→113.8秒、`zi`の持ち越し 20.9→100.0秒だった。** **0x04を含む台本は`zi-test`・`env-rewrite-test`・`keymap-rewrite-test`・`utf8-test`で、落ちたグループと一致する。** **足した3項目は52.0/57.5/57.3秒で、合わせて2.8分しかない**——**上限に当たったのは持ち越しの行が想定した「台本の長さ」ではなく、この退行である。**

**直しは述語1つである**——**`input::script_drives_input`が真の間は待たない。** **`arm_input_script`が立てるので、11のfeatureの一覧を3つ目にコピーせずに済む**（`docs/verification-coverage.md`の「列挙で守る機構の一覧」）。**実測で戻った**——**`zi test`がPASSで13秒、`persist (env)`がPASSで22秒である**（2026-09-16）。

**`--full`を実行し直して確かめた（2026-09-16）。** **306項目すべて走り、上限に当たらなかった**——**項目の所要の合計は73.2分、壁時計は77.1分である**（前回は264項目・120.2分で上限に当たり、壁時計126.7分だった）。**直前に成功した全検査は303項目・84.6分なので、項目が3つ増えて所要は減っている**（同じ機械の別の時刻。**上限まで46.8分の余裕**）。

**台本のグループが戻った値。** `persist (env)` 113.8→**18.0秒**、同（出どころを無視）114.1→**19.5秒**、同（間に作り直す）99.8→**17.9秒**、`zi`の持ち越し 100.0→**20.6秒**と100.0→**20.4秒**、`keymap (us)` 97.9→**59.2秒**、`keymap (us, always jis)` 90.6→**64.6秒**。**`keymap`の2つが他より高いのは、あちらがboot 2で`sendkey`を使うからである**（台本と本物の打鍵の両方を通る唯一のグループ）。

**落ちたのは2項目だけである**——**`boot log diff`と`shell test (kill-fold-at-depth-one-test)`。** **前者は参照が古いだけで、差分は1行・アドレスのみである**（`RIP=0xffffffff801c8af8`→`0xffffffff801c8b38`。+0x40バイト。**行は増えておらず、542行の突き合わせは`-smp 1`も`-smp 4`も通っている**）。**録り直した。** **後者が下の(B)である。**

**破壊テスト3つはすべて検出された**（`read-never-waits` / `keyboard-does-not-wake` / `idle-holds-bkl-across-hlt`）。**待ちの計測も安定している**——**システムコール2,969回 / 584バイト**（倍率5.08。上限は16）、**`hlt` 5,003回、アイドルを選んだのが1,147回、取りこぼし0、空振り586、安全網0。** **`cargo xtask flaky`も4項目とも1回目で通った。**

**(B) `kill-fold-at-depth-one-test`が検出されなくなった。覆いを失った。**

**あの破壊テストを落としていた判定は1本だけだった**——**`the shell was restarted exactly once = false`である**（実測。前の回のログで確認した）。**待つ形にすると真になり、破壊テストが素通りする。**

**3回続けて検出されなかった**（実測。2026-09-16）。**さらに`--full`の回でも検出されず、4回になった。**

**ただし「構造的に不可能」ではない。** **最初にそう書いたが、条件を数え直して訂正した**——**ウィンドウが消えたのではなく、極小になったのである。** **深さ1でRing 3に居る瞬間は残っている**（`read`が戻ってから次の`read`へ入るまで）**が、それはμs単位で、打鍵の間隔は32ミリ秒である。** **そこへIRQ1が入る確率は1%未満と見込む**（**測っていない。見込みである**）。**結論は変わらない**——**判定としては使えない**（`docs/coding-standards.md`の「確率的な項目を「直した」と言う基準」の種類。**5回の緑では足りないと書いてある側の逆で、4回の失敗でも「必ず捕まらない」とは言えない**）。

**機序は`fold_if_interrupted`の3条件のうち2つ目である**（読んで導いた。直接は計測していない）。**あれは`context.cs`のRPLが3であることを要求する**——**CPUが積んだ事実だけを見る形である。** **待つ形では、Ctrl+CのIRQ1が入る時点でシェルは`read(0)`の中で`Waiting`になっており、CPUはBSPのアイドル（Ring 0で`hlt`）に居る。** **したがってRPLは3ではなく、深さ1の終了処理は成立しない。** **深さ（条件1）は満たされたままである**——**`ring3::state()`はタスクのスロットごとに引くので、アイドルへ切り替わってもスロット0の深さは1のままである。** **深さ2の終了処理は働いている**（`ctrl_c stopped the spinning child = true`）——**子が空回りしている間はRing 3に居るからで、機序と整合する。**

**これは「能力を足したら、既存の判定が落ちずに意味だけ変わった」の種類である**（`docs/troubleshooting.md`）。

**観測を設け直した（運用者の承認。2026-09-17）。** **計測を1つ足し、判定を1本設けた**——**「深さがちょうど1だったので畳まなかった回数」である**（`kernel/src/idt`の`DEPTH_ONE_NOT_FOLDED`）。

**承認された形は「深さ1で畳んだ回数を数え、既定0・破壊1以上」だった。** **実装する前に、それでは破壊テストが検出されないと分かった**——**終了させるには「深さ1」と「Ring 3から来たIRQ」の両方が要るが、待つ形では後者のウィンドウが極小で、破壊テストを立てても0のままになる**（上の訂正と同じ理由）。**向きを逆にした**——**弾いた側を数えると、既定で1以上、破壊テストで0になる。**

**弾いた側は打鍵にも待ちにも依らない。** **シェルは遠征中（深さ1）にタイマIRQを受け続けるので、必ず通る**——**実測で3,965回である。** **破壊テストでは`MINIMUM_DEPTH`が1なので弾く分岐へ来ず、0である。** **桁で離れている。**

**運用者が挙げた「偽の赤」の懸念は、この向きでは起きない。** **承認された形（畳んだ側）なら、本物の打鍵が極小のウィンドウに当たった回に1になって既定の判定が落ちる**——**確率は1%未満だが0ではないので、揺らぎのグループに入っていた。** **弾いた側はタイマで成立するので、ウィンドウに当たるかどうかと無関係である。** **揺らぎの母数（32〜38本）も増えない**——**あれは項目で数えてあり、`--shell-test`は既に打鍵18本の側に居る**（`docs/verification-coverage.md`）。

**3回続けて落ちた**（実測。2026-09-17）。**3回とも`the shell was restarted exactly once`は真のままである**——**落としているのは新しい判定だけで、覆いが設け直されたことがそこに出ている。**

### 踏んだもの6つ（どれも実測）

1. **無条件に待たせたら、起動がシェルより前で静かに止まった。** **`/bin/syscall-test`が`read(0)`の`-EAGAIN`を主張しており**（失敗コード51と52）、**打鍵が無いのだからそれが正しい。** **決定1を「対話の口が据えられている間の、前景の持ち主だけ」へ狭めた**（`docs/troubleshooting.md`）。
2. **判定が読む回数が、間違った量だった。** **`init`がシェルの後に`invocation_count`を読むと76と出る**——**`spawn`が子の後に親の記録へ戻すからである。** **同じ回のシェルの実数は2,969で、それは`spawn`の行が戻す前に読んでいる。** **新しい計測を消し、既に在る行を読む形にした。**
3. **見込みの倍率が外れていた**（4に対して実測5.08）。**測ってから固定する条件が効いた。**
4. **破壊テストの1つが何も変えなかった。** **`wake-ignores-the-reason`は3回とも全判定を通した**——**合図が1つしか無いので、見なくても結果が同じである。** **書いた時点のコメントに「落ちるのは空振りの側である」と見込みを書いていたが、それも外れていた**（空振りの回数は変わらない。**両方が同じ集合を起こすからである**）。**消した。** **「3回続けて落ちること」を確かめる手順が、用意してよい破壊テストと用意できない破壊テストを分けた。**
5. **台本の入力も待ってしまった**（上の(A)）。**`-EAGAIN`を「まだ無い」と読んだのが2度目である**——**1つ目は起動シーケンスの検算、2つ目は台本の休みと出し切りである。** **同じ日に2度踏んだので、その種類を規約へ上げた**（`docs/coding-standards.md`）。
6. **自分の検査に穴が在った。** **`--commit`は台本の項目を1つも走らせない**ので、**34項目がすべて通ったのを見て`--full`へ進み、台本のグループ6項目を落とした。** **手順を足した**——**入力の経路に触る段階では、台本の項目を1つ実行してから`--full`へ行く**（`docs/coding-standards.md`）。

## W2-cの締め（2026-09-17）

### 発火した持ち越しは3行である

1. **「シェルが`read(0)`を回して待つ」**（`docs/deferred-decisions.md`）——**この段階そのものである。閉じた。** **あの行は条件の本体を出典（`zash.rs`の「待ち方」）に置く「宛先」の形だった**——**弱点がここに出た。** **出典が偽になったことは、表からは読めない。** **決着の要点は表の側にも書いた。**
2. **「`--full`が120分の上限に当たった」**——**2度目が発火した。** **ただし原因はあの行が想定した「台本の長さ」ではなく、私の退行だった**（上の(A)）。**字面の「2回続けて切れたら選ぶ余地は無い」は適用しない。** **直した後は306項目・64.2分で収まっている。**
3. **「眠りの『起こし忘れ』の破壊を、最小の実演では立てられない」**——**半分だけ発火した。** **`Waiting`経由の眠りができ、起こし忘れの破壊テスト（`keyboard-does-not-wake`）が立った。** **ただしあの行の対象はvirtioの`Ready`化忘れで、そちらはまだ立てられない**——**この段階で触っていない。** **行は閉じない。**

**発火しなかった隣の行を1つ挙げておく。** **「複数のI/O利用者が同時に眠る。またはSMPで眠るコアと起こすコアが分かれる」**（`ADR-0036`の再考のきっかけ）——**W2では1本しか待たないので、まだ当たらない。** **W2-dで2本目（タイマ）が入っても、待ち合わせる主体は増えない。**

### 偽になった決定

**`kernel/userland/zash.rs`の「待ち方」の3文である。** **どれも直した。**

- **「回して待つ」**——**いまは待つ。**
- **「カーネル側で眠らせる形はユーザープロセスのスケジューラを要求する」**——**要求しなかった。** **カーネルのタスクスケジューラで足りた。**
- **「カーネルが待つ形も採れない——`read`の中で眠るとBKLを保持したまま眠ることになる」**——**採れた。** **ここが要である**——**結論だけでなく、理由づけ自体が誤っていた。** **`ADR-0023`のAddendum §2が禁じているのは「保持したまま眠ること」であって「眠ること」ではない。** **`ADR-0036`が「解いてから眠る」踊りを既に持っており、`SYS_SPAWN`とvirtioが使っていた。** **`sys_read`はガードを引数で受け取っているので、落とすだけでよかった**——**新しい配管は1行も要らなかった。**

**決定1（待てるのは前景の持ち主だけ）も狭めた**（上のDecision）。**あれは偽になったのではなく、足りなかった。**

**道具は偽陽性を1つ出した。** **`tools/decisions-touched.py`を`fa2c2fa..acbc1af`で実行すると、この`ADR`が`MINIMUM_DEPTH`で当たった。** **あれは消していない**——**`if`の条件を変数へ分けたので、削除行に現れただけである。** **道具は「消えた語」を`git diff`の削除側から拾うので、行を書き換えると当たる。** **候補であって主張ではない、という道具自身の宣言どおりの振る舞いである。**

### 限界は3つ

1. **`kill-fold-at-depth-one-test`の元の判定は、覆いを失ったままである。** **`the shell was restarted exactly once`は待つ形では真へ倒れ、4回続けて破壊テストを通した。** **新しい判定6が設け直したが、元の判定が戻ったのではない**——**「深さ1でもRing 3に居れば畳む」という破壊テストの効き目そのものは、いまも観測していない。** **観測しているのは「深さ1を弾く分岐を通った回数」である。**
2. **台本のグループ11構成は、待ちの経路を通らない。** **意図した分業だが、待ちの判定はそこに1本も無い**（`docs/verification-coverage.md`の「待ちの経路を通る項目と、通らない項目」）。**通るのは21項目である。**
3. **極小のウィンドウは消えていない。** **深さ1でRing 3に居る瞬間は残っており、確率は1%未満の見込みだが測っていない。** **「構造的に不可能」と書いて、後から訂正した**（上）。

### この段で見つけた形は4つ

1. **「『今は無い』を固定した記録は、代替の返り値ではない」**（`docs/coding-standards.md`へ上げた。**実例2つ**——起動シーケンスの検算と、台本の休みと出し切り）。
2. **「構造的に不可能」と「極小になった」を分ける。** **4回の失敗は「必ず捕まらない」を意味しない**——**「5回の緑では足りない」の裏返しである。**
3. **待ちの経路の分業を書く。** **「通った」だけでは、どこが通ったかが言えない**——**退行(B)が見えたのも、通らない場所が在ったからである。**
4. **観測を設け直すときは、破壊を立てた側で値が動くことを先に確かめる。** **既定で動く量を数えても、破壊テストで動かなければ判定にならない。** **今回は「畳んだ側」と「弾いた側」で、同じ条件の裏表なのに片方だけが使えた。**

### `--full`の所要の推移と、運用者の目視

**73.2分 → 68.5分 → 64.2分**（退行を直した後の3回。306項目）。**上限（120分）まで約56分の余裕がある。** **壁時計は68.1分である。**

**運用者の目視は要らない。** **既定の起動で画面に出るものは何も変わっていない**——**足した計測の2行はシリアルだけへ出し、しかもシェルが終わった後に出す**（既定の起動ではシェルが終わらないので、1行も出ない）。**打鍵に対する応答は`--shell-test`の既存の判定が覆っている**（打った字が届き、`ls`・`cat`・`hello`が走る）。

## Alternatives Considered

- **前景を持たない1本を「前景になるまで待たせる」**——**却下。** **誰へ渡すかの政策（前面へ出す操作、持ち主が終わったときの引き継ぎ）が要る。** **利用者が居ない。**
- **前景を取り合わせる（最後に取った者が勝つ）**——**却下。** **「入力の消費者は同時に1つ」の不変条件を壊す**（`kernel/src/input.rs`）。
- **落ち先のタスクがその場で`hlt`する**——**却下。** **落ち先が選ばれるのは`schedule_switch`の中、すなわち割り込みハンドラの中である。** **そこで眠ると、BKLと割り込みの状態を持ったまま止まる。**
- **`Blocked`を使い回す**——**却下。** **起こす側が合図で引けない。** **締切で止めたワーカーをキー入力で起こす形が作れてしまう。**
- **タイマの待ちを同じ段階に入れる**——**却下（W2-dへ回す）。** **最初の利用者（シェル）はキーだけで足りる。** **新しいシステムコールを足す判断を、待ちの仕組みと同じ段に混ぜない。** **W2-d+で、後半の理由は覆した（2026-09-17。`ADR-0062`）**——**タイマの待ちは`nanosleep`と同じ段階で入れた。** **待つ者が居なければ、起こし方を壊す破壊テストが効く機会が無いためである。** **「W2-cでは混ぜない」は正しかった**（最初の利用者はキーだけで足りた）。

## Consequences

**得るもの。**

- **シェルが回さずに待つ。** **1セッションのシステムコールが桁で落ちる見込みである**（いま1,282,916回）。
- **BSPが眠る。** **`init`が引き取った後に眠る経路が、初めて出来る。**
- **`default_task_for`の穴が塞がる**（落ち先が実行不可のタスクになる形が消える）。
- **「2本が待ち合わせる形」がW2-dで作れる**——**キーとタイマで、2本が同時に待つ。** **実現しなかった（2026-09-17。W2-d+の締め）**——**`/bin/sleep`はシェルと同じタスクの中で走る子なので、待っているのはいつも1本である。** **2本が同時に待つには、別のタスク（`concurrent-test`の2本など）が眠る利用者が要る。** **`ADR-0062`の限界に書いた。**

**失うもの・残る限界。**

- **2本のRing 3が同時にキーを待つ形は作れない**（決定1）。**持ち越しの「キーボード入力をどのタスクが受け取るか」は閉じない**——**範囲を狭めたと書く。**
- **アイドルタスクの費用**（16KiBのスタック + ガードページ + タスク1本ぶんの静的領域）。**W2-aで測る。**
- **空振りの起床を許す形になる**（離鍵などで起きて、読めずにまた待つ）。**それが正しい形である**——**条件を確かめてから眠る並びを保つ。**
- **`--full`の余裕が減る**（いま303項目・84.6分。上限120分に対して35分）。**W2-cで項目数と所要を見ること。**
