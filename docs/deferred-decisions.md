# 保留中の判断事項

「その時点で判断する」「M4以降で見直す」として先送りした項目の一覧。
ADR・`architecture.md`・`troubleshooting.md`・コード内コメントに分散しているものを、解禁条件で引けるように集約する。

作る理由は、**M4が複数の保留項目の解禁条件を同時に満たす節目**だから。
一覧が無いと、解禁できる状態になったことに気づかないまま進むか、逆に解禁条件を満たさないまま手を出すことになる。

各マイルストーンの着手前に、この一覧の「解禁条件」列を確認すること。
項目を解禁したら、その行を削除し、対応するADRを更新すること。

最終更新: 2026-07-22（M5-a-1完了時点）

## M4（割り込み）で解禁・見直しになったもの

M4は完了した。
以下はM4の解禁条件で引いていた項目のうち、まだ残っているものである。
M4で処理したものは各「解決済み」節へ移してある。

これらはM4の名前で残っているが、実際の解禁条件はM4の外にある（コンソールの設計、ページングの分割・アンマップ、APICなど）。
M5着手前にこの節を通しで読むこと。

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| `Locked<T>`相当（コンソール） | ADR-0013 / ADR-0017 / `kernel/src/console/screen.rs` | 割り込みハンドラから画面出力が必要になった時点 | 現在コンソールはグローバルに置かずロックも持たない。グローバル化する場合、ロック設計は割り込み安全性のモデルと一体で決める |
| パニック時の画面出力 | ADR-0013 Addendum | 上記のロック設計が決まった後 | 解禁するならロックも確保も経由せず生ポインタで直接書く専用経路が必要。通常のコンソールとコードを共有できない |
| BootServices領域の回収 | ADR-0010 / architecture §6.2 | 条件はM4-bで充足済み。**M5でページテーブルの分割・アンマップに手を入れる時点**、またはフレーム不足が観測された時点 | **M4完了時点で実測のうえ見送った**（下記「BootServices回収の判断」）。回収量は11,042ページ = 43.1 MiBで、現在の空き52,558ページ = 205 MiBに対して +21%。需要側が桁違いに小さく、今やる理由が無い |
| ACPIテーブル領域のマッピング | architecture §6.4 | MADTを読んでAPICを構成する時点（**M4ではない**） | ADR-0018 §6でM4のタイマはPITに決めたため、M4中にACPIを辿ることはない。APICへ移る時点まで持ち越す。`EfiReservedMemoryType`や、メモリマップに現れない領域を踏むとページフォルトになる。`qemu-debug.log`のCR2で切り分け、判明した範囲を`extra`としてマッピング計画へ追加する。 ADR-0023でAPIC移行はBKL本体（higher-half B完了後）の作業と位置づけた。解禁条件は現行の「MADTを読んでAPICを構成する時点」のままとし、BKL本体着手時に確定する（BKL本体は未着手のため、確定的な書き換えはその時点で行う） |
| バックスペースの画面反映と任意位置へのカーソル移動 | ADR-0017 / `kernel/src/interrupts.rs` | **コンソールのセル占有種別を管理する時点**（M4-eでは解禁しなかった） | M4-eでBackspaceの**キーとしての認識は実装した**が、画面上の消去は行っていない。消去には全角の先頭 / 後続を区別するセル単位の管理が要り、割り込みではなくコンソールの仕事になる。解禁条件を「キーボード入力の導入時」から書き換えた |

**M4-dで解決済み（この表から外した項目）**

- **割り込みの再有効化**（ADR-0014）: M4-dで解禁。`_start`冒頭の`cli`は維持したまま、起動シーケンスの最後（PIT設定とIRQ0解禁の後）で`sti`する形に落ち着いた。`sti`は1箇所だけで、直前にADR-0018 §2の7項目を実行時検証する。**ADR-0014はSuperseded**（役目を終えた）。
- **PICのベクタオフセットの検証**: M4-c-3ではICW2が読み戻せないため未検証だったが、M4-d-2で最初のティックがベクタ0x20として届いたことで証明された。`alt-offset-test`（0x30-0x3Fへ再マップしても追随すること）により、OVMFが既に0x20を使っていた可能性による疑いも晴れている（ADR-0018 Addendum 3）。

**M4-b-2で解決済み（この表から外した項目）**

- **例外時のGPRフルダンプ**（ADR-0004 Addendum / ADR-0018 §4）: M4-b-2で対応。例外ハンドラはCPUが積んだフレーム + スタブがpushしたGPRという正確な値を持つ。GPRの並び順は既知値15個で実値検証済み。**`panic!()`については据え置きで確定**（保留ではない）。「フォーマット処理や関数呼び出しを経た後の値でしかない」という当初の理由はM4でも変わらないため、解禁されたのは例外側だけである。

**M4-c-2で解決済み（この表から外した項目）**

- `Locked<T>`の`unsafe impl Sync`（ヒープ）: `common::critical::Locked<T>`へ移し、前提を「割り込み常時禁止」から「取得中は割り込み禁止」へ差し替えた（ADR-0012 Addendum）。二重取得検出を追加し、`--critical-test double-lock`で検出が働くことを確認済み。

**M4-aで解決済み（この表から外した項目）**

- **カーネル自身のスタックへの切り替え**（architecture §6.3）: M4-aで対応。`.bss`の静的配列（通常64KiB / IST1用16KiB）へ切り替え済み。これにより「BootServices回収」の解禁条件のうち、自前スタックの分が満たされた。
- **自前GDT / TSS**: M4-aで対応。同じくBootServices回収の解禁条件の一部。残るは自前IDT（M4-b）のみ。

**M4-eで新たに生じた保留項目**

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| Caps LockのLED更新 | `kernel/src/keyboard/decode.rs` | LEDの状態が実際に必要になった時点 | キーボードへ0xED + ビットマスクを送りACKを待つ手順が要る。i8042への出力方向の扱いが新たに必要になり、M4-eの主題（割り込み）に対して複雑度が見合わない。**内部状態としてのCaps Lockは正しく管理している**ので、変換結果はLEDの有無に関わらず正しい |
| OBF確認と読み出しの間のレース | `kernel/src/keyboard/mod.rs` | 実際に取りこぼしが観測された時点 | ハンドラはOBFを見てから0x60を読む。i8042は外部ハードウェアなので割り込み禁止中でもOBFを立てられ、確認と読み出しの間に本物のキーが届くとstrayとして捨てられる。窓は数命令ぶんで確率は極めて低く、起きてもstrayカウンタで観測できる。**既知の限界として受け入れる** |
| キーリピート（タイプマティック）の制御 | M4-e | リピート速度の調整が必要になった時点 | 現在はキーボード側の既定のリピートをそのまま受け取る。速度・遅延はキーボードへ0xF3を送って設定するが、LEDと同じく出力方向の手順が要る。QEMUの`sendkey`はリピートを模擬しないため自動テストできず、手動確認に頼る点も併せて見直す |
| キーボードレイアウト | `kernel/src/keyboard/decode.rs` | US以外の配列が必要になった時点 | 現在はUS配列固定。変換表を差し替える形で対応できるが、配列の選択をどこで持つか（ビルド時か実行時か）は決めていない |

| `stray`の回数がrunごとに揺れる理由 | `kernel/src/keyboard/mod.rs` / `troubleshooting.md` 2026-07-21 | 増え続ける事象が観測された時点 | データを伴わないIRQ1の回数が、同一構成でも0と1で入れ替わる（4回で1,1,1,0）。「コンフィグバイト読み出しがIRQ1をラッチさせる」という仮説は`0x67`が消えた事実と整合するが、**回数が揺れる理由までは突き止めていない**。判定基準は「起動直後に0か1なら正常、増え続けるなら異常」 |

### BootServices回収の判断（M4完了時点、2026-07-21）

ADR-0010で保留した回収は、解禁条件（自前ページテーブル・自前スタック・自前GDT/IDT）がM4ですべて揃った。
実測して見送りを決めた。

実測（QEMU + OVMF、RAM 256MiB）:

| 項目 | ページ数 | 容量 |
|---|---|---|
| 現在の空きフレーム | 52,558 | 205 MiB |
| `EfiBootServicesCode` | 1,030 | 4.0 MiB |
| `EfiBootServicesData` | 10,012 | 39.1 MiB |
| **回収で増える量** | **11,042** | **43.1 MiB（+21%）** |

見送る理由:

1. 需要が桁違いに小さい。現在ヒープは固定1 MiB。M5でタスクごとに64KiBのカーネルスタックを取るとしても、100タスクで6.4 MiBである。205 MiBに対して不足が生じる見込みが立たない。
2. M5と同時にやると切り分け軸が増える。回収の失敗は「しばらく動いた後に突然壊れる」という最も診断しにくい形で出る（architecture §6.2）。M5自体がM4と同等以上の規模であり、両方を同時に動かすと、症状が出たときにどちらが原因か分からなくなる。M4全体で「切り分け軸を増やさない」ことを繰り返し優先してきた判断と揃える。
3. 必要になっていないものを今やることになる。先回りの作り込みを避けるのは本プロジェクトの基本方針である（`vision.md`冒頭）。

**次に判断するタイミング**: M5でページテーブルの分割・アンマップに手を入れる時点。
そこはどのみちページング周りを触るので、回収も同じ検証の中で扱える。
あるいはフレーム不足が実際に観測された時点。

**回収する際の検証方法**（設計として先に決めておく）:

- CR3が自前テーブルを指していること、RSPが`.bss`のスタック範囲内にあること、GDTR / IDTRがkernelイメージ内を指していることを、いずれも読み戻しで確認する（すべて実装済み）。
- 回収対象を毒値で埋めてから空きリストへ入れる。ヒープの`0xDE`、スタックの`0xC5`と同じ手法。UEFI由来の何かをまだ参照していれば、静かに壊れるのではなく即座に異常な値を読んで落ちる。「しばらく動いた後に突然壊れる」を「その場で落ちる」に変えるのが目的である。
- 毒値で埋めた状態で、起動シーケンス全体と回帰テスト一式（例外4種 / critical 2種 / interrupt 6種）を通す。

## M5（マルチタスク）で解禁・見直しになるもの

段階分割と方式はADR-0019。
M5に着手する前にこの節を通しで読むこと。

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| FPU / SSEの状態保存 | ADR-0019 / architecture §5 | ユーザープログラムがSSEを使うようになった時点（M5-f以降） | 現在カーネルはSSE無効（`-sse,-sse2,...,+soft-float`）でビルドしており、通常のコード生成がXMM/YMMを一切使わない。そのためコンテキストスイッチで浮動小数点の状態を保存する必要が無い。ユーザープログラムがSSEを使うようになると、CR0（EM / MP / TS）とCR4（OSFXSR / OSXMMEXCPT）の設定に加えて`FXSAVE` / `FXRSTOR`による退避・復元が要る。**保存領域は512バイト・16バイト境界**という制約もつく。「使ったタスクだけ保存する」遅延退避（TSビットと #NMを使う方式）にするかどうかも、その時点で判断する |
| コンソール / シリアルへの出力の多重化 | ADR-0019 §4 / ADR-0017 | **M6で前景プロセスの概念を設計する時点** | M5では「出力するのはメインループだけ」という制約で運用する（ADR-0018 §5で割り込みハンドラに課したのと同じ構造）。`Locked<T>`を被せる案は、フラッシュが1回で数百KBになりうるため、その間ずっと割り込みが禁止されてティックを取りこぼすので採らない。本来の解はメッセージをリングバッファへ積んで1つの出力タスクが吐く形（Linuxのprintkと同じ構造） |
| キーボード入力をどのタスクが受け取るか | ADR-0019 §5 | 同上（M6） | `Locked<T>`による排他はM5でも成立し続けるが、「どのタスクが受け取るか」は別の設計判断であり、前景プロセスの概念に相当する。M5では単一消費者（メインループ）を維持する |
| `syscall` / `sysret`への差し替え | ADR-0020 | Linux静的バイナリを実行する段階（必須。選択ではない） | x86-64のLinuxバイナリ（musl / glibc）は`syscall`命令を発行する。`int 0x80`は32bit互換経路で64bitバイナリは使わないため、`vision.md`の構想を目指す限り実装は必須。差し替えで変わるのは**入口の実装とRCX / R11の扱いだけ**で、レジスタ規約を最初からLinuxに合わせてあるため本体には手が入らない。必要になるのはSTAR / LSTAR / SFMASKのMSR設定と、`swapgs`によるGSベース経由のカーネルスタック切り替え（`syscall`は自動でスタックを切り替えない）。**`swapgs`の対称性が崩れると特権昇格の穴になる** |
| 2つのシステムコール入口の併存 | ADR-0020 §4 | 上記と同時 | 独自ユーザーランドを`int 0x80`で作った後に`syscall`を足すと入口が2つになる。**併存させる**（独自側を書き換えずに済む。同じディスパッチャへ落とせば重複は入口だけ）か、**独自ユーザーランドも`syscall`へ移行する**（入口が1つに保たれる）かを、その時点で判断する |

## 実装の前提が揃ったら対応するもの

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| スタックのガードページ化 | ADR-0018 / ADR-0019 §3 / `kernel/src/stack.rs` | **M5-b**（M5-aで`PageTableBuilder`が分割・アンマップに対応した直後） | 現在は恒等マッピングの途中に穴を開けられないため、各スタックの直下に4KiBの犠牲領域を置き毒値カナリア（`0xC5`）で埋めている。溢れた瞬間には気づけず、「いつの間にか壊れていた」ことしか検出できない。**この制約はM4-bのダブルフォルト誘発にも波及している**: 犠牲領域はマップ済みメモリなのでスタックを溢れさせてもページフォルトが起きず、ダブルフォルトに至らない。そのため #PFゲートのPresentビットを落とす方法で代用している（ADR-0018）。ガードページが置けるようになれば、溢れた瞬間の検出と、スタックオーバーフロー由来のダブルフォルト検証の両方が可能になる |
| `PageTableBuilder`のページ分割・アンマップ | 同上 | **M5-a**。M5全体の律速であり、最初に着手する | ガードページ（M5-b）とユーザー空間（M5-e / M5-f）の両方がこれを前提にする |
| EFER.NXEの有効化とNXビット | ADR-0018 / ADR-0021 | direct physical mapまたはユーザー空間の導入時 | 現在EFER.NXEを有効化しておらず、NXE無効のままNXビット（bit 63）を立てると予約ビット違反のページフォルトになる（ADR-0018で記録済み。M2-dでNXを立てなかった理由）。direct mapは本来NXにすべきで、ユーザー空間のデータページ・スタックにもNXが要る。有効化はEFER MSR（0xC0000080）のbit 11。既存エントリはすべてNX=0なので有効化自体の影響は無い見込みだが、有効化後に読み戻して検証すること |

| `DirectMap`を保持している型の作り直し | `common/src/addr.rs`、`kernel/src/graphics/layout.rs` | **higher-half移行の段階分割に必須の項目として含める** | `FramebufferLayout`は構築時に`DirectMap`を受け取って保持する。移行で`replace_direct_map`を呼ぶと、保持している窓が古いままになる。古い窓で変換を続けると、正規形ではあるが誤った仮想アドレスを返し、それがポインタになる。症状は「移行直後は動くが、ある操作をした瞬間に壊れる」形になる。T-2bで`ActivePageTable`と`PageTableBuilder`も同じ形にする予定で、対象が増える。対処は3案ある。(1)移行後に必ず作り直す（docと移行手順の両方に明記、最低限これは必須）、(2)保持せず変換のたびに`direct_map()`を呼ぶ、(3)保持する値に世代番号を持たせ、古い世代での変換をfail-fastにする。**ただし移行中は2つの窓が同時に正しい。** 恒等マッピングが生きている状態で新しいテーブルを組み立て、CR3を切り替え、高位へ飛んでから恒等を外す、という手順のため、`PageTableBuilder`は古い窓（恒等）で組み立て、切り替え後の`ActivePageTable`は新しい窓で辿る期間がある。したがって(2)は移行中に成立せず、(3)も単純な世代比較では表せない。窓を値として持ち回る現在の形はこの点では正しく、グローバルなstaticは「現在の標準的な窓」を配るだけのものと位置づけ、移行中はそれに依存しない経路が要る。3案の再評価は移行の段階分割案を作る時点で、この制約を前提に行う。 **B-0で再評価（2026-07-24）。** 長寿命保持者`FramebufferLayout`はA-2で高位窓へ作り直し済み（`rehome_framebuffer_to_window`、案1が既に適用）。`ActivePageTable`/`PageTableBuilder`は都度構築の値渡しで、移行中の2窓同時正当のもとでは値持ち回りが正しい（(2)は移行中不成立、(3)も単純世代比較で表せない）。B-0では現在の形を維持し文書化に留める。**B-2への繰り越し**: この値持ち回りの正しさは「恒等+高位窓が両方生きている」2窓同時正当を前提にする。B-2の恒等除去でこの前提が変わる（値持ち回りが古い窓=恒等への参照を握っていると壊れる）ため、B-2の恒等除去タイミング設計で再確認する |
| リンカシンボルの物理アドレスへの変換 | `kernel/link.ld`の`__kernel_start`/`__kernel_end`、`kernel/src/frame_allocator.rs` | **higher-half移行の段階分割に必須の項目として含める** | フレームアロケータはkernelイメージの領域を予約済みとして扱うためにこれらのシンボルを使う。現在はリンクアドレスが`0x100000`で恒等なので、値が物理としても仮想としても通る。higher-half化するとリンカが返すのは仮想アドレス（`0xFFFFFFFF80100000`付近）になり、物理としては使えない。一方アロケータが必要とするのは物理アドレスである。**この変換はdirect mapではなく、カーネルイメージのリンクアドレスとロードアドレスの差で決まる。** direct map経由の変換とは別の関係なので混同しないこと。T-2cで`kernel_image_phys_range()`（`kernel/src/main.rs`）としてシンボルを`VirtAddr`で受け取り、物理への変換を明示的に通す形にした。移行時はこの関数の中身を書き換える。恒等の間は素通しになるだけだが、型を通しておけば移行時にコンパイラが指摘する |
| split/unmapテストの恒等窓依存 | `kernel/src/main.rs`の`verify_split_and_unmap`/`run_paging_test` | **higher-half B（恒等マッピングを外す時点）** | この2つはページ分割・アンマップの機構の回帰テストで、読み戻しで「物理 == 仮想」を照合するため恒等マッピングを前提にする。A-2で登録`direct_map()`が高位を返すようになったため、両者には`DirectMap::identity(IDENTITY_MAX_LENGTH)`を明示的に渡し、恒等マッピングのsplit/unmapを対象に検証している。**Bで恒等を外すと、この明示的な恒等窓は存在しないアドレスを指し、2テストが壊れる。** Bで恒等を外すときに、対象をdirect mapの高位窓へ移すか（照合を`phys == window.virt_to_phys(virt)`へ一般化する）、テスト用の張り先を別に用意する。外し忘れると恒等除去の瞬間に顕在化する。 **B-0で解消済み（2026-07-24）。** `verify_split_and_unmap`/`run_paging_test`を登録direct map高位窓（`direct_map()`、A-2以降高位、Bでも残る）へ移し、照合を`phys == 窓のvirt_to_phys(virt)`へ一般化した（恒等窓をbase=0の特殊ケースに含む一般形）。恒等除去でこの2テストは壊れない。振る舞い不変（split-testが高位窓VA `0xffff8000...`で mismatches=0、--fullで確認）。なお他5箇所の`DirectMap::identity`利用（起動時検証）はB-0では触れない。それらが恒等除去より前に走ることをB-2の恒等除去タイミング設計で保証する（B-2繰り越し） |
| ガードページのsplit化 | `kernel/src/main.rs`の`install_kernel_stack_guard_page`、`kernel/src/stack.rs`の`StackBlock` | **StackBlockが2MiBページに載るレイアウト変更が起きたとき** | 現在`StackBlock`は`0x100000`〜`0x200000`の4KiBフリンジにあり、`kernel_guard`は4KiBページで張られているので、`unmap_4kib`だけでガードページを作れる。イメージが育って`StackBlock`が2MiBページへ載ると、unmapの前に`split_huge_page`が要る。M5-bでは「使わない分岐を今書かない」ためsplit分岐を配線せず、代わりにガード作成前に粒度をtranslateで確認し、4KiBでなければ名指しでfail-fastする。この事前アサートで止まったら、translate→split→unmapの分岐を足す（M5-a-2のsplitがこの時点で初めて実利用される）。M5-dでこの2MiB境界の事象を一度踏んだ。デモ用のNOPそりが`.text`を膨らませてイメージが2MiB境界をまたぎ、`StackBlock`ではなくH-2が`UnexpectedHugePageEntry`で止まった（`troubleshooting.md` 2026-07-23）。そりを遅延ループへ変えて回避しており、`StackBlock`が恒久的に2MiBへ載る条件は変わっていないため項目は残す |
| 大きなスタック配列とガード幅 | `kernel/src/main.rs`の`install_kernel_stack_guard_page`のコメント | 4KiBを超える単一のローカル配列をスタックに置くコードを導入するとき | ガード幅を1ページ（4KiB）にしたのは、現在コード全体でスタック上の単一配列の最大が`[u64; 512] = 4096`バイトで、1回のスタック伸長がガードを一撃で飛び越えないことを前提にしている。4KiBを超えるローカル配列を書くと、その前提が破れてガードを飛び越えうる（この穴はカナリア方式にも共通で、ガードページ固有の退行ではない）。大きなスタック配列を導入するなら、ガード幅を複数ページにするか、その配列をヒープ／静的領域へ移すかを判断する |
| M5-eユーザー空間アドレスの暫定配置 | `kernel/src/main.rs`の`USER_PML4_INDEX`（M5-e-2） | **higher-half B（カーネルを上位半分へ移し恒等を外す時点）** | M5-e-2/e-3のユーザーページを`PML4[1]`（仮想ベース`0x0000_0080_0000_0000`= 512 GiB）の専用サブツリーに置いている。x86-64 Linuxはアドレス空間を下位半分=ユーザー、上位半分=カーネルに二分し、M5-fのプロセス別アドレス空間で下位を差し替え上位を共有する。この向きに沿うため下位半分に置くが、通常のユーザーコード配置（低位、数MiB付近）ではなく512 GiBという不自然な位置なのは、**現在カーネルが`PML4[0]`（下位半分）に恒等で居るため`PML4[0]`を空けられない**からである。Bでカーネルを上位半分へ移し恒等を外せば、`PML4[0]`が空いてユーザー空間を通常の低位へ広げられる。**Linux型の「下位=ユーザー／上位=カーネル」の完全な分割はBの完了が前提であり、プロセス別アドレス空間（下位を差し替え上位は共有）に着手する前にこの依存関係を再確認すること。** この依存のため、ADR-0022はプロセス別アドレス空間をBの後の独立マイルストーンへ切り出し、M5-fの範囲をint 0x80（B非依存）に絞った。現在はBが未了なので、暫定として空きの下位半分スロット`PML4[1]`を1つ使う（コストは最小） |

### higher-half B の段階進捗（着手中の記録）

Bは段階分割で進めている（B調査の合意による）。

- B-0（済み）: split/unmapテストを恒等窓からdirect map高位窓へ一般化し、恒等除去でも壊れないようにした。DirectMap保持型の再評価も済み（上記2行に記録）。
- B-1（済み、その後B-2a-3aで撤去）: 高位実行の機構実証。`build_switch_probe_high_half`（H-3）で、恒等 + テスト高位ベース`0xFFFF_FFFF_8000_0000`のテーブルへCR3を切り替え、高位VAでプローブを実行し元テーブルへ戻した。「高位VAでコードが実行できる（RIPが高位になれる）」ことを実証した。実証はコミット`d7d56e1`とそのシリアルログに残る。**B-2a-3で真の高位化が高位到達を本体で実証したため、B-2a-3aで撤去した**（プローブ用テーブルの恒久保持11フレームも回収）。再リンク後はRSPが高位になり、B-1の切替前検査（現RSPを恒等前提で引く`resolves_to(rsp, rsp)`）が`rsp=false`となってCR3切り替えを拒否しhaltする。この検査（A-1から受け継いだ「切替前に必須領域を検証し壊れていれば切り替えない」型）が、想定していなかった状況で高位RSPを覆わないテーブルへの切り替えを未然に止めた。撤去はこの事実を確認したうえで行った。
- B-2a（進行中）: 真の高位化を段階分割で進めている。
  - B-2a-1（済み）: bootloaderをp_paddr配置・低位エントリ変換へ改めた。base=0で振る舞い不変。
  - B-2a-2（済み）: トランポリン（`.text.trampoline`、RIP相対のみ）と静的初期テーブル（`.data.bootpt`、PD共有で4フレーム、[0,1GiB)恒等+高位）とブートスタック（`.data.bootstack`、0xC5初期化16KiB）を追加し、kernelイメージの高位マッピングをM2-d/A-1の本流テーブルへ配線した。base=0で振る舞い不変・フレーム増0。
  - B-2a-3a（済み）: B-1撤去（この項目）。
  - B-2a-3b（着手予定）: 再リンク（`KERNEL_VIRT_BASE`=`0xFFFF_FFFF_8000_0000`・code-model=kernel・ENTRYをトランポリンへ）。高位到達を本体で実証する。恒等はまだ残す。
- B-2b（未着手）: 低位ポインタ（boot_info・ヒープ・mmapバッファ・恒等前提の検証ヘルパ）の高位化と恒等（PML4[0]）の除去。「恒等なしで動く」を初めて実証する。RSPは再リンクの副作用でB-2aの時点で高位化済み。B-2着手時にADR（ADR-0009のSupersede、ADR-0021のAddendum、SMP非閉塞と前提棚卸し）を起こす。
