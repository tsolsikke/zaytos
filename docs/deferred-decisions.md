# 保留中の判断事項

「その時点で判断する」「M4 以降で見直す」として先送りした項目の一覧。
ADR・`architecture.md`・`troubleshooting.md`・コード内コメントに分散して
いるものを、解禁条件で引けるように集約する。

作る理由は、**M4 が複数の保留項目の解禁条件を同時に満たす節目**だから。
一覧が無いと、解禁できる状態になったことに気づかないまま進むか、逆に
解禁条件を満たさないまま手を出すことになる。

各マイルストーンの着手前に、この一覧の「解禁条件」列を確認すること。
項目を解禁したら、その行を削除し、対応する ADR を更新すること。

最終更新: 2026-07-21（M4-d 完了時点）

## M4（割り込み）で解禁・見直しになるもの

M4 は GDT/TSS・IDT・例外ハンドラ・タイマ・キーボードを入れる段階であり、
下記の多くの解禁条件がここで揃う。**M4 に着手する前に、この節を通しで
読むこと。**

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| `Locked<T>` 相当（コンソール） | ADR-0013 / ADR-0017 / `kernel/src/console/screen.rs` | 割り込みハンドラから画面出力が必要になった時点 | 現在コンソールはグローバルに置かずロックも持たない。グローバル化する場合、ロック設計は割り込み安全性のモデルと一体で決める |
| パニック時の画面出力 | ADR-0013 Addendum | 上記のロック設計が決まった後 | 解禁するならロックも確保も経由せず生ポインタで直接書く専用経路が必要。通常のコンソールとコードを共有できない |
| BootServices 領域の回収 | ADR-0010 / architecture §6.2 | **条件は M4-b で充足済み**（自前ページテーブル・スタック・GDT/IDT が揃った） | 着手可能だが未着手。M4-d と同時にやるとメモリレイアウトが動いて切り分け軸が増えるため、割り込みが動いてから別途行う。解禁時は ADR-0010 を Superseded にして新 ADR を書く |
| ACPI テーブル領域のマッピング | architecture §6.4 | MADT を読んで APIC を構成する時点（**M4 ではない**） | ADR-0018 §6 で M4 のタイマは PIT に決めたため、M4 中に ACPI を辿ることはない。APIC へ移る時点まで持ち越す。`EfiReservedMemoryType` や、メモリマップに現れない領域を踏むとページフォルトになる。`qemu-debug.log` の CR2 で切り分け、判明した範囲を `extra` としてマッピング計画へ追加する |
| バックスペースと任意位置へのカーソル移動 | ADR-0017 | キーボード入力の導入時（M4-e） | 現在の制御文字は `\n` / `\r` / `\t` のみ。セルごとの占有種別（先頭 / 後続）の管理が必要になる |

**M4-d で解決済み（この表から外した項目）**

- **割り込みの再有効化**（ADR-0014）: M4-d で解禁。`_start` 冒頭の `cli` は
  維持したまま、起動シーケンスの最後（PIT 設定と IRQ0 解禁の後）で `sti` する
  形に落ち着いた。`sti` は 1 箇所だけで、直前に ADR-0018 §2 の 7 項目を実行時
  検証する。**ADR-0014 は Superseded**（役目を終えた）。
- **PIC のベクタオフセットの検証**: M4-c-3 では ICW2 が読み戻せないため
  未検証だったが、M4-d-2 で最初のティックがベクタ 0x20 として届いたことで
  証明された。`alt-offset-test`（0x30-0x3F へ再マップしても追随すること）に
  より、OVMF が既に 0x20 を使っていた可能性による疑いも晴れている
  （ADR-0018 Addendum 3）。

**M4-b-2 で解決済み（この表から外した項目）**

- **例外時の GPR フルダンプ**（ADR-0004 Addendum / ADR-0018 §4）: M4-b-2 で
  対応。例外ハンドラは CPU が積んだフレーム + スタブが push した GPR という
  正確な値を持つ。GPR の並び順は既知値 15 個で実値検証済み。
  **`panic!()` については据え置きで確定**（保留ではない）。「フォーマット
  処理や関数呼び出しを経た後の値でしかない」という当初の理由は M4 でも
  変わらないため、解禁されたのは例外側だけである。

**M4-c-2 で解決済み（この表から外した項目）**

- **`Locked<T>` の `unsafe impl Sync`（ヒープ）**: `common::critical::Locked<T>`
  へ移し、前提を「割り込み常時禁止」から「取得中は割り込み禁止」へ差し替えた
  （ADR-0012 Addendum）。二重取得検出を追加し、`--critical-test double-lock`
  で検出が働くことを確認済み。

**M4-a で解決済み（この表から外した項目）**

- **カーネル自身のスタックへの切り替え**（architecture §6.3）: M4-a で対応。
  `.bss` の静的配列（通常 64KiB / IST1 用 16KiB）へ切り替え済み。これにより
  「BootServices 回収」の解禁条件のうち、自前スタックの分が満たされた。
- **自前 GDT / TSS**: M4-a で対応。同じく BootServices 回収の解禁条件の一部。
  残るは自前 IDT（M4-b）のみ。

**M4-e で新たに生じた保留項目**

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| Caps Lock の LED 更新 | `kernel/src/keyboard/decode.rs` | LED の状態が実際に必要になった時点 | キーボードへ 0xED + ビットマスクを送り ACK を待つ手順が要る。i8042 への出力方向の扱いが新たに必要になり、M4-e の主題（割り込み）に対して複雑度が見合わない。**内部状態としての Caps Lock は正しく管理している**ので、変換結果は LED の有無に関わらず正しい |
| OBF 確認と読み出しの間のレース | `kernel/src/keyboard/mod.rs` | 実際に取りこぼしが観測された時点 | ハンドラは OBF を見てから 0x60 を読む。i8042 は外部ハードウェアなので割り込み禁止中でも OBF を立てられ、確認と読み出しの間に本物のキーが届くと stray として捨てられる。窓は数命令ぶんで確率は極めて低く、起きても stray カウンタで観測できる。**既知の限界として受け入れる** |
| キーリピート（タイプマティック）の制御 | M4-e | リピート速度の調整が必要になった時点 | 現在はキーボード側の既定のリピートをそのまま受け取る。速度・遅延はキーボードへ 0xF3 を送って設定するが、LED と同じく出力方向の手順が要る。**QEMU の `sendkey` はリピートを模擬しないため自動テストできず、手動確認に頼る点も併せて見直す** |
| キーボードレイアウト | `kernel/src/keyboard/decode.rs` | US 以外の配列が必要になった時点 | 現在は US 配列固定。変換表を差し替える形で対応できるが、配列の選択をどこで持つか（ビルド時か実行時か）は決めていない |
| i8042 の完全な初期化 | `kernel/src/keyboard/controller.rs` | 実機で初期化不足が問題になった時点 | 自己テスト（0xAA）・インターフェーステスト（0xAB）・デバイスリセット（0xFF）を行っていない。失敗時に何をすべきかを決められず、QEMU では必ず成功するため試せない（ADR-0013 と同じ理由）。**実機で動かす時点が見直しの契機になる**（`vision.md`） |

## 実測・観測が揃ってから判断するもの

| 項目 | 出典 | 判断の条件 | 内容 |
|---|---|---|---|
| Write-Combining / PAT の導入 | ADR-0015 Addendum 2 | **実機（ベアメタル）で測れるようになった時点**、または描画性能が実際に問題として観測された時点 | TCG・KVM の両方で測り直したが、**どちらも判断材料にならなかった**。KVM では PCD が効いていること自体は確認できた（2 周目で通常 RAM だけが速くなる）が、キャッシュ有効/無効の比が 1 倍前後に留まり、全面フラッシュも 4.5 バイト/サイクルと速すぎる。QEMU のディスプレイ更新用ダーティページ追跡が実コストを覆い隠している疑いが濃い（未検証の仮説）。プローブは `.local-probes/m3c-flush-cost-probe.patch` |
| スクロールのリングバッファ化 | ADR-0017 | RAM 内コピーが実測で問題になった時点 | 現在は素朴なメモリコピー。リングバッファは安い側（RAM コピー）だけを最適化し、高い側（転送）は変わらない |
| ダーティ矩形の行単位化 | ADR-0017 | 飛び飛びの更新が問題になった時点 | 現在は外接矩形 1 個。最悪ケースでも素朴な全面転送より悪くはならない |
| ヒープのサイズクラス方式 | ADR-0012 | 小オブジェクトの断片化が実機で観測された時点 | 現在は連結リスト単体。M5 のタスク管理で churn が増えた際に実測に基づいて再検討 |
| ヒープの拡張機構 | ADR-0012 | 1MiB で不足した時点 | 現在は固定サイズで拡張機構なし。不足時は診断ログを出してパニックする |
| フレームアロケータの容量（256） | ADR-0011 | 容量超過が起きた時点 | 超過は握りつぶさず fail-fast する設計になっている |
| フレームアロケータのデータ構造 | ADR-0011 | 細かい断片化が問題になった時点 | 範囲リスト方式。将来アドレス空間の解体（プロセス終了時）で細かく断片化するなら、バディ等への差し替えを再検討 |

## 実装の前提が揃ったら対応するもの

| 項目 | 出典 | 解禁条件 | 内容 |
|---|---|---|---|
| スタックのガードページ化 | ADR-0018 / `kernel/src/stack.rs` | `paging::table::PageTableBuilder` が 2MiB ページの分割とアンマップに対応したら | 現在は恒等マッピングの途中に穴を開けられないため、各スタックの直下に 4KiB の犠牲領域を置き毒値カナリア（`0xC5`）で埋めている。溢れた瞬間には気づけず、「いつの間にか壊れていた」ことしか検出できない。**この制約は M4-b のダブルフォルト誘発にも波及している**: 犠牲領域はマップ済みメモリなのでスタックを溢れさせてもページフォルトが起きず、ダブルフォルトに至らない。そのため #PF ゲートの Present ビットを落とす方法で代用している（ADR-0018）。ガードページが置けるようになれば、溢れた瞬間の検出と、スタックオーバーフロー由来のダブルフォルト検証の両方が可能になる |
| `PageTableBuilder` のページ分割・アンマップ | 同上 | 必要になった時点 | 上記のガードページのほか、将来ユーザー空間のアドレス空間を解体する際にも要る |
| GDT の並び順（SYSCALL/SYSRET 制約） | ADR-0018 / `kernel/src/gdt/mod.rs` | **M5 でユーザーモードを導入する時点** | 現在は null / カーネルコード / カーネルデータ / TSS(2 枠) の 5 スロット。SYSCALL/SYSRET を使う場合、STAR レジスタの仕様で並び順が固定される（カーネルコード、カーネルデータ、ユーザーコード32、ユーザーデータ、ユーザーコード64 の順）。**後から任意の順で追加するとセレクタ値の総入れ替えになる**ため、ユーザーモード用ディスクリプタを足す前にこの制約を確認すること |

## 規模・要件が変わったら見直すもの

| 項目 | 出典 | 見直しの条件 | 内容 |
|---|---|---|---|
| 日本語グリフの収録方法 | ADR-0016 | 日本語を実際に収録する時点 | CJK 統合漢字まで含めると 600KB 超。kernel イメージへの埋め込みが現実的でなくなったら、常用漢字などの部分集合に絞るか、M6 のファイルシステム対応後にディスクから読み込む |
| `Bitmask` ピクセル形式への対応 | ADR-0013 | 実際に `Bitmask` を返す環境を入手した時点 | 現在は起動時に拒否している。テストできない対応コードを抱えないため、実物を観測してから実装する |
| `\r` の挙動（VT シーケンス対応） | ADR-0017 | VT エスケープシーケンスへ対応する時点 | 現在の `\r` は行頭復帰に加えて行を消去する。厳密な端末挙動からの意図的な逸脱。セルごとの占有種別管理と併せて見直す |
| コンソール構築失敗時に halt するか | ADR-0017 | 画面が主たる出力手段になった時点 | 現在は halt せず続行する（シリアルが観測手段として残るため） |
| kernel の higher-half 化 | ADR-0009 | ユーザー空間との分離が必要になった時点 | 現在は低位固定 `0x100000`。ユーザー/カーネル権限分離の実運用（M5）で必要性を判断する |
| q35 machine type への移行 | ADR-0007 | PCIe / AHCI / 電源管理など q35 固有の機能が必要になった時点 | 現在は pc（i440fx）。M6 以降が目安 |
| SMP 対応 | ADR-0002 | 別途マイルストーンを立てた時点 | 現在はシングルコア前提。同期プリミティブの中身を差し替える前提で、呼び出し側インターフェースだけ安定させてある |
| 他アーキテクチャへの移植 | ADR-0006 | 移植を実際に行う時点 | アーキ依存部の切り出しが必要になる。先回りの抽象化はしない |

## 情報の追加が必要になったら対応するもの

| 項目 | 出典 | 条件 | 内容 |
|---|---|---|---|
| `BootInfo` への ACPI/RSDP 情報の追加 | `common/src/boot_info.rs` | ACPI を読む時点（**M4 ではない**。ADR-0018 §6 で M4 のタイマは PIT と決めたため） | 現在は必要最小限のみ。`BootInfo` は一度確定すると変更の影響範囲が広い（bootloader と kernel の双方）ため、変更時はレビューを経る |
| bootloader 自身のメモリ回収 | architecture §6.2 | 必要になった時点 | `EfiLoaderCode`/`EfiLoaderData` の一部。BootServices 回収とは別に設計する |
